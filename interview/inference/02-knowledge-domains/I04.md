# I04 Scheduler 与 Continuous Batching

## 范围与定位

本域覆盖 scheduler 从接收 tokenized request 到构造 `ScheduleBatch` 并调用 worker 之间的完整逻辑：admission 控制、token/KV budget、调度策略排序、`PrefillAdder` 逐请求准入、`ScheduleBatch` 构造、decode batch 维护、retraction 与重新排队。与 I02 的边界在 `waiting_queue` 入队，与 I03 的边界在 scheduler 进程内的 event loop，与 I05 的边界在 `run_batch` → `forward_batch_generation`。本域不处理 Transformer 计算细节，不定义 HTTP 协议字段。

## 核心概念与机制

**1. `event_loop_normal` 是动态控制循环**

`event_loop_normal`（`scheduler.py:1893-1925`）每轮：`ingest_requests` → `get_next_batch_to_run(running_batch, last_batch)` → 有 batch 则 `run_batch` + `process_batch_result`，无 batch 则 `on_idle`。`overlap` 变体（`scheduler.py:1927-1990`）把上批结果入 `result_queue`，当前 forward 与上批 CPU result processing 交错，必要时 stream/WAR barrier 保序。关键不变量：`running_batch`（仍活跃请求）与 `last_batch`（上轮 forward 快照）不是同一个对象；overlap 中 `last_batch`、`result_queue`、当前 `batch` 可能同时处于不同生命周期阶段。[C: `01-modules/M04-scheduler-batching/README.md:98-127`; `02-request-flow/03-调度器与连续批处理.md:102-166`]

**2. 调度策略不是简单 FCFS**

`SchedulePolicy.calc_priority`（`schedule_policy.py:222-301`）可用策略：LPM（最长前缀匹配）、DFS_WEIGHT、HRRN（响应比）、FCFS、LOF、RANDOM、ROUTING_KEY。LPM 用 `origin_input_ids + output_ids` 匹配 Radix tree，优先 cache-hit 高的请求以减少 prefill 计算。队列 > 128 时 LPM/HRRN 降为 FCFS 避免 CPU 调度瓶颈。HRRN 用 `processed_tokens_counter` 累计 prefill token 数，防短请求/高 cache-hit 请求导致长请求饥饿。优先级参与排序、队列满淘汰和抢占，但不改变采样概率。[C: `02-request-flow/03-调度器与连续批处理.md:277-336`]

**3. `PrefillAdder` 是入场检查器**

`PrefillAdder`（`schedule_policy.py:537-608`）构造时接收 `page_size`、`tree_cache`、`token_to_kv_pool_allocator`、`running_batch`、`max_prefill_tokens`、`chunked_prefill_size`、`max_prefill_bs`、`max_running_requests` 等。`add_one_req` 对每个候选请求先调 `req.init_next_round_input(tree_cache)` 计算本轮真正需要扩展的范围，再为这些新 token 分配 KV 位置。预算不足时返回 `NO_TOKEN`，允许截断时建 chunked prefill。`get_num_allocatable_reqs` 同时受 `pp_max_micro_batch_size - running_bs` 和 `req_to_token_pool.available_size()` 约束。beam width > 1 时 `available // beam_width` 限制新请求数。[C: `01-modules/M04-scheduler-batching/README.md:93-95`; `02-request-flow/03-调度器与连续批处理.md:339-429`]

**4. decode OOM → retract → 重新排队**

`update_running_batch`（`scheduler.py:4055-4137`）先 `filter_batch` 移除完成请求；再 `check_decode_mem` 把下一步所需 token 数交给 allocator `check_decode_capacity`。容量不足时 `retract_decode` 按 retraction order 移除：普通请求释放并备份以便恢复；beam group/host backup 不足时设 abort finish reason；可恢复请求 `is_retracted=True` 重新入队。释放前后 allocator 可用量差值是诊断 ownership 是否闭合的重要观测点。[C: `01-modules/M04-scheduler-batching/README.md:163-177`; `90-cross-module/pooling-and-resource-management.md:100-108`; `02-request-flow/03-调度器与连续批处理.md:553-574`]

**5. mixed chunk 的兼容条件**

`_get_new_batch_prefill_raw` 在满足条件时 `running_batch.filter_batch()` + `prepare_for_decode()` + `new_batch.mix_with_running(running_batch)`，将已有 decode 请求行带入同轮 prefill forward。限制：`return_logprob` 时不支持混合；`input_embeds` 存在时不能简单拼接；beam member rows 不放入 mixed batch。通用原则：batch 合并不是免费操作，只有所有请求的输入布局和结果语义可兼容时才合并。[C: `02-request-flow/03-调度器与连续批处理.md:629-649`]

## 常见误区

1. **"prefill 一定在 decode 之前全部完成"** — 错误。chunked prefill 可跨多轮处理同一长 prompt；mixed chunk 可在同轮混合 prefill 与 decode。[C: `02-request-flow/03-调度器与连续批处理.md:629-649`]
2. **"retract 等于删除请求"** — 错误。retract 释放 decode 资源并将请求重新排队，可恢复；仅当 host backup 不足或无法恢复时才 abort。[C: `02-request-flow/03-调度器与连续批处理.md:553-574`]
3. **"请求入 waiting_queue 就马上执行"** — 错误。执行时机取决于 running batch、token budget、KV 容量、prefix hit、priority、chunking、PP microbatch 和 backend tile。[C: `01-modules/M04-scheduler-batching/README.md:128-141`]
4. **"overlap 永远开启"** — 错误。grammar 状态推进、speculation 顺序、collective 一致性要求时会强制同步。[C: `02-request-flow/03-调度器与连续批处理.md:693-702`]
5. **"连续 batching 是把请求插入正在运行的 kernel"** — 错误。动态性来自每轮重新组成 batch，不修改已发射 kernel。[C: `02-request-flow/03-调度器与连续批处理.md:60-63`]
