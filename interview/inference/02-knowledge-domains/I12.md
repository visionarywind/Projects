# I12 量化与低精度 KV

## 范围与定位

I12 处理推理系统中"用更少 bit 表示模型权重、激活和 KV cache"时的误差-容量-性能权衡。它覆盖权重量化（W4A16/W8A8/FP8）、激活量化（dynamic per-token/per-tensor）、KV cache 量化（FP8/INT8/INT4 KV）、量化误差传播路径、以及不同量化方案对 attention 输出精度和服务吞吐的影响。本域决定了推理服务的显存效率上限和精度损失下界。

与相邻域的边界：I12 不定义 KV cache 组织（I08），但 KV 量化直接改变 KV pool 的 bytes/token 和物理容量；不定义 attention kernel（I07），但 KV dtype 影响 backend 选择和 FlashAttention 的 dtype 兼容性；不定义采样（I09），但量化误差经 attention 累积后影响 logits 分布。证据结构上，PagedAttention/FP8 KV 有 PDF 解析支撑，vAttention 连续 layout 下有量化相关讨论，SGLang M09/M14 有量化 backend 入口；真实量化精度、误差传播、性能收益未验证。

## 核心概念与机制

### 1. KV cache 容量的一阶公式

定义：KV cache 的显存占用决定了可服务的最大并发序列数，量化 KV 是提高容量的直接手段。

原理：

```text
bytes_per_token = num_layers × 2(K,V) × num_kv_heads × head_dim × bytes_per_element

KV_total_bytes = Σ(bytes_per_token_i) × seq_len_i   # 对所有序列求和
```

[C] `insights/03-arxiv-reading-notes.md:24-31`（PagedAttention 将 KV 切块管理，block size 决定分配粒度）；`sglang/90-cross-module/pooling-and-resource-management.md:64-68`（KV tensor 的 shape 为 `(size+page_size, head_num, head_dim)`，dtype 决定 bytes_per_element）。

例子：Llama-3-8B（32层、8 KV heads、head_dim=128），BF16 KV = 32×2×8×128×2 = 131072 bytes/token ≈ 128KB/token；FP8 量化后减半为 64KB/token，同等显存下并发翻倍。

### 2. 量化误差-精度权衡的本质

定义：量化是用低 bit 表示引入误差来换取容量/带宽收益；误差来源包括截断误差（clipping）、舍入误差（rounding）和量化粒度（per-channel/per-token/per-tensor）。

原理：权重量化误差在矩阵乘法中以乘法方式累积；KV 量化误差在 attention 中以加法方式影响 softmax 后的加权和。[I] 权重的 W4A16 把 int4 权重反量化后与 FP16 activation 相乘，误差取决于 calibration 质量；KV 量化中 key/value 分别量化，attention score 计算使用原始或反量化后的 key，value 在 softmax 后加权求和时引入误差。

关键不变量：KV 量化不改变 KV cache 的逻辑结构（slot/page 映射不变），只改变物理 dtype 和 bytes/token；但反量化操作增加计算步骤。[I] `sglang/90-cross-module/pooling-and-resource-management.md:64-68`（FP8 KV 将存储 dtype 改为 uint8）。

### 3. 三种量化路径的定义与特征

定义：推理系统通常有三条量化路径——权重量化（减少模型显存+计算量）、激活量化（减少 attention/FFN 中间结果）、KV 量化（减少 KV cache 显存+带宽）。

原理对比：

| 路径 | 主要收益 | 主要风险 | 实现位置 |
|---|---|---|---|
| 权重 W4A16/W8A8 | 显存减半、GEMM 加速 | 精度损失需 calibration | 离线量化，加载时反量化 |
| 激活 dynamic quant | 减少 HBM 读写 | 动态范围跟踪开销 | attention/FFN 算子内部 |
| KV FP8/INT8/INT4 | 直接减少 decode 带宽瓶颈 | 注意力输出精度下降 | KV pool dtype + attention backend |

[C] `sglang/90-cross-module/pooling-and-resource-management.md:64-68`（KVCache 对 FP8 将存储 dtype 改成 uint8）；[I] 激活量化细节本仓库无源码级文档，仅从 Megatron/推理通用知识推导。

### 4. KV 量化与 attention backend 的耦合

定义：KV dtype 不是独立配置——attention backend 必须支持对应的 KV 访问模式（quantized KV access）。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:50`

原理：FlashInfer backend 在 quantized KV access 下会维护多个 wrapper；FlashAttention 的 dtype 约定要求 KV 与 Q 的 dtype 匹配或 backend 支持混合精度；PagedAttention kernel 的 block table 映射与 KV dtype 无关，但物理 block 的 bytes 随 dtype 变化。[I] `insights/03-arxiv-reading-notes.md:46-51`（vAttention 提到 block size 影响 kernel execution time，类似地 KV dtype 也影响 kernel 选择）。

边界：KV 量化不影响 RadixCache 的索引映射逻辑（slot/page 映射与 dtype 无关），但物理 pool 的 capacity 计算必须按量化后的 bytes/token。[C] `sglang/01-modules/M08-kv-cache/README.md:64-68`

### 5. KV 量化误差传播路径

定义：KV 量化误差沿 "KV 写入 → attention 读取 → score 计算 → weighted sum → 下一层" 传播，与权重误差在矩阵乘法中的传播方式不同。

原理：

```text
1. key 量化误差 → attention score(Q, K_quant) 误差 → softmax 分布偏移
2. value 量化误差 → softmax_weighted_sum(V_quant) 误差 → attention output 误差
3. 多层累积 → logits 分布偏移 → 采样结果差异
```

[I] 本仓库无 KV 量化误差传播的源码级文档；路径分析基于 attention 公式推导。关键观察：value 误差在 softmax 归一化后加权求和，不会随序列长度放大（被概率归一化抑制）；key 误差通过 score 影响 softmax 分布，在长序列或高温下可能更显著。

量化缓解：per-channel/per-token 量化比 per-tensor 更精细；fp8 比 int8/int4 保留更多动态范围；部分系统对 key 和 value 使用不同精度（key 更高精度保护 score，value 更低精度节省容量）。

## 常见误区

- **"KV 量化会改变 slot/page 映射逻辑"**——错。RadixCache 的索引映射与 dtype 无关，量化只改变物理 pool 的 bytes/token 和 capacity 计算。[C] M08:64-68
- **"KV 量化越激进越好"**——错。int4 KV 精度损失可能显著影响长序列 attention 输出；key 量化误差通过 softmax 分布放大，在特定模型/任务上可能不可忽略。[I] 基于 attention 公式推导
- **"权重量化收益和 KV 量化收益可以简单叠加"**——不完全正确。权重量化减少模型显存和计算，KV 量化减少 decode 带宽瓶颈；两者收益来源不同，部署时需同时满足 dtype 兼容性和 backend 支持。[C] M09:50; pooling:64-68
- **"量化后模型结果完全等价于原始模型"**——错。量化引入误差，等价性只在统计意义上成立（perceptually negligible），任务敏感场景需逐任务评估。[I] 通用量化知识
- **"KV 量化不影响 CUDA Graph eligibility"**——需验证。Graph capture 与 KV dtype 无直接关系，但 quantized KV access 可能改变 backend wrapper 和 capture session。[C] M09:50; 实际需逐 backend 验证
