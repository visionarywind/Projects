# I18 安全与多租户

## 范围与定位

本域覆盖推理服务的安全加固与多租户隔离：认证鉴权、限流防 DoS、租户间 KV/显存/带宽隔离、输出脱敏、审计日志。核心问题是：**如何防止恶意或过量请求拖垮服务**、**多租户共享资源时如何保证公平与隔离**。

边界：与 I17（部署/扩缩）是限流与 autoscaling 的协同——限流拒绝的请求不应触发扩容；与 I15（长上下文与容量）是租户 quota 与全局 KV pool 的预算分配；与 I16（观测/测试）共用审计日志但目标不同。

证据等级说明：本仓库对安全与多租户的**成型文档较弱**——SGLang M02 有 admin auth 入口和 health/auth handler 的存在证据，M17 gateway 有认证或请求边界的模块描述，但具体安全实现（脱敏算法、限流公式、DoS 防护细节）**未在仓库内独立验证**。本域标注 [U] 且**禁编造**具体实现细节。

## 核心概念与机制

### 1. 认证与鉴权 [U]

- **定义**：确认请求来源身份并校验是否有权访问指定模型和 adapter。
- **原理**：M02 HTTP server 的管理类 endpoint（flush cache、profile、weights、LoRA、session、abort 等）"通常带 admin auth 或内部状态检查" [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:73`。M17 Model Gateway 的 middleware 包含 auth 模块 [已确认] `sglang/01-modules/M17-rust-router-gateway/README.md:60`。
- **不变量**：认证失败应返回 401/403 而非 500，不暴露内部实现细节。admin endpoint 的 auth 不应与普通推理 endpoint 共用同一套凭证体系。

### 2. 限流与防 DoS [U]

- **定义**：限制单个用户/租户/Token 的请求速率，防止恶意或过量请求耗尽资源。
- **原理**：SGLang M02 的 client disconnect 处理维护了"断连是取消，不是输入错误"的语义——流式 `ValueError` 同时检测到 client disconnected 时只记录并停止，不向已断开的客户端发送 400 [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:69-71`。M17 Router 的 circuit breaker 在首个 SSE chunk 前连接失败可按幂等策略重试；已发送部分输出则应终止并报告，不静默切换 worker [已确认] `sglang/01-modules/M17-rust-router-gateway/README.md:73`。
- **不变量**：限流应在多层实施——gateway 层做粗粒度 QPS 限制，scheduler 层做 KV budget 准入，两层不能互推。限流拒绝应返回 429（Too Many Requests）而非 500。
- **注意**：具体限流算法（token bucket/leaky bucket）、阈值设置、分级策略（按租户/按模型/按 adapter）本仓库无文档 [U]。

### 3. 多租户隔离 [U]

- **定义**：多个租户共享同一推理集群时，保证性能、数据和管理面的隔离。
- **原理**：设计建议将物理容量拆成全局保留区、租户 quota、系统 emergency reserve 和 prefix shared 区；admission 必须同时检查 request row、KV page、CPU/offload quota 与 transfer queue，而不能只看 `torch.cuda.mem_get_info()` [已确认] `insights/04-design-decision-and-validation.md:111`。
- **不变量**：租户隔离不仅是资源配额——KV cache 中的 prefix 可能包含敏感内容，跨租户的 prefix reuse 需要评估信息泄露风险。不同租户的 KV occupancy 需要独立计量，否则一个租户的长上下文请求会挤压其他租户的可用容量。
- **注意**：具体隔离实现（cgroup、MPS、MIG、网络策略）本仓库有 K05 覆盖但非推理侧专项 [U]。

### 4. 输出脱敏与审计 [U]

- **定义**：对模型输出中的敏感信息做处理，并记录操作日志。
- **原理**：SGLang M02 的 chat template/parser 处理 multimodal placeholder 和 reasoning/tool call，输出解析是脱敏的潜在介入点 [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:106-115`。每个请求应记录 reservation、实际 live tokens、prefix 命中、retract 次数和最终释放时间 [已确认] `insights/04-design-decision-and-validation.md:113-116`。
- **不变量**：审计日志不能包含完整 prompt/输出中的敏感内容——日志是安全边界内的产物。脱敏应在输出侧（detokenize 后）而非 KV 侧（KV 仍保留完整 token）。
- **注意**：具体脱敏算法（正则匹配、NER、分类器）、审计日志格式、保留期限本仓库无文档 [U]。

### 5. 故障注入与安全测试 [U]

- **定义**：通过故障注入验证安全边界和隔离有效性。
- **原理**：故障注入清单中的 duplicate/partial page 和 graph teardown 可映射到安全测试——验证租户 A 的 KV 泄漏到租户 B 的场景 [已确认] `insights/04-design-decision-and-validation.md:103-109`。Radix lock 泄漏测试可验证隔离失效时的恢复能力。
- **不变量**：安全测试的 oracle 是"租户 A 无法读取/影响租户 B 的 KV/输出"——任何 shared prefix cache 设计必须通过此 oracle 验证。

## 常见误区

1. **"限流只放在 gateway 层就够了"**。gateway 层限流看不到 scheduler 内部的 KV budget 压力，两层必须协同。
2. **"prefix cache 共享是纯性能优化"**。跨租户 prefix reuse 可能泄露敏感内容，需要评估信息泄露风险。
3. **"认证通过就完全信任"**。认证身份不等于授权使用特定资源——还需要模型级、adapter 级、quota 级的权限校验。
4. **"审计日志可以记录完整 prompt"**。日志是安全边界内的产物，记录完整敏感 prompt 会造成二次泄露。
5. **"多租户隔离只需要资源配额"**。隔离还包括 KV 数据隔离、prefix 隔离、性能隔离（噪声邻居）和管理面隔离。
