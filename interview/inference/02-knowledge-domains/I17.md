# I17 部署、扩缩与优雅关闭

## 范围与定位

本域覆盖推理服务的生命周期管理：canary 灰度发布、autoscaling 策略、drain 优雅关闭、以及回滚机制。核心问题是：**新版本如何安全上线**、**副本数如何随负载变化**、**实例下线时如何不丢请求**。

边界：与 I16（观测/测试）是发布门禁的上下游——可观测数据是灰度决策的输入；与 I15（长上下文与容量）是副本增减时 KV prefix cache 迁移的耦合；与 I02（HTTP/API）是 drain 时断连语义的协同。

证据边界：Ray Serve 状态机有源码分析 [已确认]；drain 与 graceful exit 有 SGLang 主循环和 lifespan 源码 [已确认]；冷启动耗时、autoscaling 阈值无文档 [待验证]。

## 核心概念与机制

### 1. 滚动发布与 Canary

- **定义**：滚动更新按批次替换 replica，canary 是先让少量流量验证新版本再全量。
- **原理**：Ray Serve 链路 `Deployment.bind → serve.run → Controller.deploy_applications → DeploymentState target/reconcile → replica start/health → router → DeploymentHandle.remote`；滚动更新、autoscaling、health check、backpressure 都是改变状态机的分支 [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:147-149`。每个发布分支必须补齐五项——容量边界、owner、失败恢复、指标、回滚方式 [已确认] `insights/04-design-decision-and-validation.md:65`。
- **不变量**：灰度决策依赖可观测指标——canary 阶段必须同时监控 TTFT、TPOT、错误率、P99，任一指标恶化触发回滚。新 replica 冷启动期间 prefix cache 为空，初期命中率接近 0，可能引发短期吞吐下降。
- **例子**：5% 流量切到 canary → 观察 5-10 分钟 → TTFT/P99 无恶化且错误率未上升 → 逐步放量到 50% → 全量。若 canary 的 P99 恶化，自动回滚到旧版本。

### 2. Autoscaling 策略

- **定义**：根据负载信号动态调整 replica 数，平衡资源利用率和服务质量。
- **原理**：伸缩信号必须用请求侧指标——KV occupancy = live KV ÷ physical capacity，不等于 GPU util [已确认] `insights/04-design-decision-and-validation.md:7`。GPU util 低可能来自 tokenize/IPC 排队而非计算空闲，用它做扩容信号会漏判瓶颈。
- **不变量**：伸缩需防震荡——必须设置冷却窗口（cooldown）避免副本数在阈值附近反复伸缩；新副本冷启动需要加载权重、建 KV pool、预热 CUDA Graph，冷启动期间 QPS 仍由原副本承担。只按排队数立刻扩会造成超调，只按 GPU util 扩会因长 prompt 让两者反向变化。
- **例子**：信号 = KV occupancy > 80% 持续 2 分钟 → 扩容 +1；KV occupancy < 30% 持续 10 分钟 → 缩容 -1。冷却窗口 5 分钟内不重复扩容。

### 3. Drain 与优雅关闭

- **定义**：drain 是在实例下线前停止接收新请求、等待已接收请求完成的过程。
- **原理**：SGLang HTTP server 的 lifespan 退出时以 `finally` 停止 sidecar、关闭 native gRPC、异步关闭 tool server、join warmup thread [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:44-45`。health endpoint 区分 shutdown/starting/unhealthy 状态——drain 期间应标记 unhealthy 让负载均衡器停止路由新请求 [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:147-148`。
- **不变量**：流式请求的 drain 必须等待 SSE 流完成或客户端断开——不能直接 kill 进程导致客户端收到不完整输出。CUDA Graph 的 flush/drain 有独立约束：graph pool/backing teardown 必须在 drain 后再 flush，eager fallback 可作为中间态 [已确认] `insights/04-design-decision-and-validation.md:109`。
- **例子**：K8s Pod 终止 → preStop hook 标记 unhealthy → 等待 30s drain → 关闭 lifespan → 进程退出。若 drain 超时仍有未完成的流式请求，强制关闭并记录 abort。

### 4. 回滚机制

- **定义**：发布异常时快速恢复到旧版本，最小化影响范围。
- **原理**：回滚前提是旧 replica 仍在运行或镜像可快速拉起——全量替换后旧版本镜像被覆盖会增加回滚延迟。Ray Serve 的 controller 支持重试、替换或标记 unhealthy，但 `serve.shutdown/delete` 的真实时序未验证 [已确认] `sglang/01-modules/M02-http-api-protocol/README.md:44-45`。
- **不变量**：回滚窗口必须实测——"有优雅关闭入口"不等于"关闭耗时可预测"。回滚后旧版本的 prefix cache 若未清除则可直接复用，新版本的 prefix cache 必须清除以避免 KV 污染。
- **例子**：canary P99 恶化 → 停止 canary 流量 → 旧副本继续全量服务 → 诊断 canary → 修复后重新灰度。

### 5. 零停机升级

- **定义**：升级过程中不拒绝任何请求、不中断任何流式输出。
- **原理**：需要滚动替换 + drain + 充足容量冗余。至少保留 N-1 副本的容量承载全量流量，才能逐个替换副本。零停机不等于零影响——新副本冷启动期间的 prefix cache 缺失可能导致短期 TTFT 上升。
- **不变量**：若副本数=1，零停机不可能实现——必须先扩容再缩容。零停机的代价是更高的资源开销（冗余副本）和更长的发布耗时（逐个 drain）。

## 常见误区

1. **"滚动更新 = 零停机"**。滚动更新需要容量冗余 + drain，否则升级期间吞吐会下降。
2. **"autoscaling 只用 QPS 就够了"**。长 prompt 场景 QPS 低但 prefill 计算量大，QPS 不能反映真实负载。
3. **"进程退出 = 请求完成"**。流式请求的 SSE 流可能被中断，需要 drain 等待完成或 abort。
4. **"新副本上线就能承担全量"**。冷启动期间 prefix cache 为空，短期命中率接近 0，需要 warmup。
5. **"回滚 = 重启旧版本"**。回滚还涉及 prefix cache 一致性——新版本产生的 KV 若未清除会污染旧版本。
