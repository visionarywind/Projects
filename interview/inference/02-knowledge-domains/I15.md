# I15 长上下文与容量

## 范围与定位

本域覆盖 context window 扩展后的显存规划、分页/虚拟映射、KV eviction 策略，以及长上下文场景下的尾延迟管理。核心问题是：**给定硬件和模型，能服务多长的上下文、多少并发**、**超出容量时怎么淘汰**、**尾延迟如何被长尾请求拖累**。

边界：与 I08（KV Cache 管理）是容量规划与 allocator 实现的上下游；与 I13（PD 分离）是纵向加层与横向拆角色的正交维度。与 I06（prefill/decode）是长上下文对 prefill 计算量和 decode 带宽的双重放大。

证据边界：容量公式与口径来自设计文档 [已确认]；分页与 eviction 来自 SGLang M08 源码分析 [已确认]；论文数字来自 arXiv PDF 解析 [已确认，PDF] 但非本地复现。

## 核心概念与机制

### 1. KV 容量预算：从 HBM 到可服务 token

- **定义**：KV cache 容量决定了单实例能承载的最大并发序列长度总和。
- **原理**：第一阶模型 `KV_bytes = live_tokens × layers × 2 × kv_heads × head_dim × dtype_bytes`；完整预算需从 HBM 总容量中减去权重、workspace、activations、graph 静态 buffer、通信 buffer 和安全余量 [已确认] `insights/04-design-decision-and-validation.md:16-36`。最终 `max_total_tokens ≈ floor(HBM_for_KV / bytes_per_token)`。
- **不变量**：对于 page allocator，`allocated_tokens = allocated_pages × page_size`，`page_waste = allocated_tokens - live_tokens` 是页内浪费而非外部碎片 [已确认] `insights/04-design-decision-and-validation.md:38-43`。
- **例子**：H100 80GB，Llama-3-70B 权重 ~80GB（FP16）→ KV 预算接近零；INT4 量化后权重 ~20GB，KV 预算 ~40GB（扣除余量），bytes_per_token ~26KB（GQA 8-head）→ 约 1.6M token 总容量。

### 2. 分页与虚拟映射

- **定义**：PagedAttention 借鉴 OS 虚拟内存，将 KV cache 切成固定大小 block，通过 `logical blocks → block table → physical blocks` 三层映射 [已确认，PDF] `insights/03-arxiv-reading-notes.md:26-30`。
- **原理**：SGLang 维护两类映射——`ReqToTokenPool` 记"row 第 n 个 token 用哪个 slot"，`RadixCache` 记"前缀对应哪些 KV indices" [已确认] `sglang/01-modules/M08-kv-cache/README.md:15-22`。`PagedTokenToKVPoolAllocator` 把 `size` 解释为 token 总数，`num_pages = size // page_size` 作为真正的页数 [已确认] `sglang/01-modules/M08-kv-cache/README.md:91-96`。
- **不变量**：前缀命中受 page 对齐限制，未对齐尾部不能作为 radix 节点的完整缓存页 [已确认] `sglang/01-modules/M08-kv-cache/README.md:44`。`ReqToTokenPool` row 0 是 padding row，承接 CUDA Graph dummy 读写 [已确认] `sglang/01-modules/M08-kv-cache/README.md:26-28`。
- **例子**：page_size=16 时，一个 30 token 的 prefix 只缓存前 16 token（1 页），剩余 14 token 不算完整页。

### 3. Eviction 策略与 Radix 树

- **定义**：当 KV pool 不足时，系统按策略淘汰低价值 prefix cache 以释放空间。
- **原理**：Radix eviction 从 `evictable_leaves` 构造 heap，按策略优先级取叶子，调用 allocator `free_segment` 释放 page-aligned KV，删除叶子，并在父节点变成无子且未锁定时把父节点重新放回 heap [已确认] `sglang/01-modules/M08-kv-cache/README.md:109-123`。策略包含 LRU/LFU/FIFO/MRU/priority-aware/SLRU，只决定选择顺序，不绕过 `lock_ref` 和 page ownership [已确认] `sglang/01-modules/M08-kv-cache/README.md:129-134`。
- **不变量**：叶子节点不等于可驱逐——正在被请求引用的 node 必须先解除 lock_ref [已确认] `sglang/01-modules/M08-kv-cache/README.md:102-107`。SLRU 的 protected 是策略分段，不等同于 Radix node 的 device lock protection。
- **例子**：priority-aware eviction 中较小请求 priority 先被驱逐；高优先级请求的 prefix 即使 LRU 较老也可能保留。

### 4. 输出长度不确定下的 Reservation

- **定义**：请求到达时必须为 KV cache 预留空间，但输出长度直到生成结束才知道。
- **原理**：under-reservation 触发 preemption，迫使请求终止并重算，带来显著 overhead；over-reservation 浪费 memory 降低吞吐 [已确认，PDF] `insights/03-arxiv-reading-notes.md:192-202`。reservation 不能简单取 `max_context_len`，要用历史分布、SLO、preemption/recompute 成本和多租户配额共同决定 [已确认] `insights/04-design-decision-and-validation.md:45`。
- **不变量**：workload 分布具有 non-stationarity，不同 task 的输出长度差异很大，单一 global quantile reservation 不能同时适配所有请求类别 [已确认，PDF] `insights/03-arxiv-reading-notes.md:199`。

### 5. 尾延迟的放大器

- **定义**：长上下文请求的 P99 延迟远高于平均值，常由 retraction、eviction 和带宽争用放大。
- **原理**：长序列 decode 每步读取 KV cache 线性增长，带宽压力持续增大。CPU offload 可缓解 HBM 容量但引入 PCIe 争用和 P99 尾风险 [已确认，PDF] `insights/03-arxiv-reading-notes.md:80-81`。KVPR 的 partial recompute 用额外 GPU 计算覆盖 I/O 等待，让 PCIe transfer 与 GPU 计算 overlap [已确认，PDF] `insights/03-arxiv-reading-notes.md:90-94`。
- **不变量**：平均 TPOT 改善但 P99 恶化，不能判定方案更优 [已确认] `insights/04-design-decision-and-validation.md:98`。

## 常见误区

1. **"max_context_len 就是可服务容量"**。这是模型结构上限，实际可服务容量受 HBM、并发数、输出长度分布共同约束。
2. **"page size 越小越好"**。小 page 减少内部碎片但增加 page table 大小和 kernel 访问开销，需要在 page 内浪费、kernel 开销、prefix 命中粒度之间取舍。
3. **"命中率高 = 容量充足"**。高命中率可能来自流量重复度高，不代表剩余容量能承载新请求。
4. **"eviction 只影响缓存命中"**。eviction 错误可能释放仍被请求持有的 prefix，导致 attention 读到无效 KV。
5. **"CPU offload 只增加容量不影响性能"**。offload 引入 PCIe 带宽争用，可能使 P99 TPOT 恶化。
