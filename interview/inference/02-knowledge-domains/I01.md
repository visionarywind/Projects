# I01 启动、配置与协议

## 范围与定位

本域覆盖从命令行输入到 SRT runtime 就绪之间的完整链路：CLI 解析 → backend 选择 → `ServerArgs` 固化 → Engine/TokenizerManager/Scheduler/Detokenizer 进程创建 → HTTP server 启动。它位于推理栈的最外层，与 I02（协议与请求状态）的边界在 `launch_server` 完成 `Engine._launch_subprocesses` 之后、HTTP server 进入稳态之前。本域不处理请求级调度（I04）和模型计算（I05/I06）。

## 核心概念与机制

**1. 三层 CLI 分发模型**

`sglang` 顶层 parser（`cli/main.py`）只识别子命令（`serve`/`generate`/`version`），使用 `parse_known_args()` 把模型自有参数作为 `extra_argv` 交给子命令。`serve` 层通过 `ServeBackendRegistry` 选择 backend：entry point group `sglang.serve_backends`，API version 1。自动探测顺序为：收集所有 `MATCH`，多匹配报错，无匹配回退内置 `llm`。这意味着 backend 选择是延迟到 `ServeRequest` 构造之后才最终确定的。[C: `01-modules/M01-cli-service-startup/README.md:19-78`]

**2. `ServeRequest` 不可变契约**

`ServeRequest` 是 frozen dataclass，字段为 `argv`、`model_path`、`model_path_is_positional`。`_normalize_positional_model_path` 将 `sglang serve <model>` 改写为 `--model-path <model>`，同时保留 positional 标记。这个标记传给 diffusion backend，使其能区分显式 positional 与默认值。关键不变量：`model_path_is_positional=True` 的参数不能被后续覆盖逻辑当作隐式默认值处理。[C: `01-modules/M01-cli-service-startup/README.md:40-49`]

**3. `resolve_once` 与配置固化**

`run_server` 调用 `server_args.resolve_once()` 将 raw config 固化为 `resolving_view`。这一步把旧 flag 折叠、互斥校验、默认值注入全部完成，后续代码不再重复解释参数。分支选择（encoder-only / SMG gRPC / Ray / HTTP）基于 resolved view 判断，而非用户原始输入。`launch_server` 在不同分支中才 import 对应模块：未启用 Ray 时不 import Ray，未启用 diffusion 时不加载 diffusion 依赖，未启用 gRPC 时不初始化 gRPC 组件。延迟 import 减少启动时间，也让不同硬件/安装变体的依赖保持可选。设计意图：避免子进程各自从未解析 config 推导出不同结果，同时最小化运行时依赖。[C: `01-modules/M01-cli-service-startup/README.md:79-81`; `02-request-flow/01-启动链路.md:119-134`]

**4. Engine 进程拓扑组装**

`Engine._launch_subprocesses` 的顺序是：`configure_logger` → `resolve_once/set_env/load_plugins` → `check_server_args` → `publish(tokenizer config)` → `PortArgs.init_new` → scheduler process(es) → detokenizer process(es) → TokenizerManager → `wait_for_ready` → watchdog。配置在 spawn 前 publish，子进程通过 `publish(server_args, role=...)` 读取，保证全局配置一致性。[C: `01-modules/M15-ipc-control-plane/README.md:55-73`; `02-request-flow/06-多进程与IPC.md:133-181`]

**5. 启动不变量与故障收敛**

`cli/serve.py:serve` 的 `finally` 调用 `kill_process_tree(os.getpid(), include_parent=False)` 覆盖所有退出路径。每个 scheduler 子进程通过单向 `mp.Pipe` 回传 ready 信息，`wait_for_ready` 阻塞直到所有 rank 就绪。子进程异常时记录 traceback、向 parent 发送 SIGQUIT，按 `SGLANG_KILLPG_ON_SCHEDULER_EXCEPTION` 决定是否 kill process group。不变量：进程退出不应留下被 watchdog 当作 crash 的子进程；graceful exit 与 hard-kill 必须分层兜底。[C: `01-modules/M01-cli-service-startup/README.md:82-108`; `01-modules/M15-ipc-control-plane/README.md:280-318`]

## 常见误区

1. **"CLI 直接启动 scheduler"** — 错误。CLI 是控制面入口，选择 backend 后通过 `launch_server` 间接创建 Engine，Engine 再 spawn 子进程。`serve --help` 在 `prepare_server_args` 前结束，不启动任何 runtime。[C: `01-modules/M01-cli-service-startup/README.md:66-81`]
2. **"所有参数都在顶层 parser 声明"** — 错误。`parse_known_args()` 把 backend 自有参数透传，错误可能延迟到 backend parser 才暴露。[C: `01-modules/M01-cli-service-startup/README.md:36-38`]
3. **"子进程各自解析命令行"** — 错误。配置在父进程 `resolve_once` + `publish`，子进程只读取已解析的 bags。[U: 具体 publish/get 的 bag 名称待逐一核实]
4. **"kill_process_tree 会清理所有资源"** — 不完整。`finally` 的 process tree cleanup 不替代 scheduler 自身的 IPC/设备清理；graceful exit 路径才会释放 host resources。[C: `01-modules/M01-cli-service-startup/README.md:106-108`]
5. **"entry point 发现会立即 import 外部实现"** — 错误。发现阶段只收集 entry point 元数据，不立即 import；`get()` 被调用时才加载工厂并检查 callable、返回类型和 API version。显式加载失败会抛错，自动探测时单个 detector 异常被记录并跳过。[C: `01-modules/M01-cli-service-startup/README.md:53-65`]
