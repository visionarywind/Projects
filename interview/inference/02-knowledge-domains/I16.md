# I16 观测、测试与故障

## 范围与定位

本域覆盖推理系统的可观测性设计、benchmark 方法论、故障注入与 oracle 验证、以及诊断排障的分段定位方法。核心问题是：**如何证明系统工作正常**、**数字怎么测才可信**、**故障时如何快速定位到具体阶段**。

边界：与 I06（prefill/decode 双阶段）是观测对象与分段测量的基准；与 I15（长上下文与容量）是容量指标与分段延迟的交叉；与 I18（安全/多租户）共用部分审计日志但目标不同。

证据边界：指标口径与分段测量来自设计文档和 roadmap [已确认]；测试 suite 结构来自 M18 源码分析 [已确认]；故障注入清单来自 design-decision [已确认]；真实故障注入与 oracle 验证均未运行 [待验证]。

## 核心概念与机制

### 1. 核心指标：TTFT、TPOT 与分段延迟

- **定义**：TTFT（Time To First Token）= 请求到达 → 首个 token 返回的延迟；TPOT（Time Per Output Token）= 相邻两个输出 token 的平均间隔；P99 = 99th percentile 端到端延迟。
- **原理**：服务侧五段测量——请求侧（tokenize/IPC/排队）→ prefill（prefix hit、chunk、KV 分配）→ decode（batch size、step 时间、retraction）→ worker（forward/collective/attention/sampling）→ 输出侧（copy-to-CPU、detokenize、stream 通知）[已确认] `sglang/99-roadmap/performance-guide.md:15-21`。段必须首尾相接、互不重叠，否则归因会重复计数。
- **不变量**：TTFT 和 TPOT 优化目标常冲突——降低 TTFT 需要更快完成 prefill，但大 prefill 会挤压 batch 内的 decode 带宽，抬高 TPOT。**至少同时报 TTFT、TPOT、P99、错误与撤回率**，平均值改善但 P99 或 abort 上升不能判定更优 [已确认] `insights/04-design-decision-and-validation.md:10-14`。
- **例子**：TTFT 恶化但 TPOT 不变，问题在 prefill 阶段（prefix miss、KV 分配、chunk 数）；TPOT 恶化但 TTFT 不变，问题在 decode 阶段（batch 过大、带宽饱和、retraction）。

### 2. Benchmark 方法论与可信度

- **定义**：benchmark 衡量吞吐/延迟/显存/kernel 性能，**不能作为 correctness 测试** [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:35`。
- **原理**：三条规则——① 必须记录 warmup、并发、输入输出长度、设备和版本，否则不同结果不可比较 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:50`；② 变体矩阵含 backend/device、API、execution、model/input、deployment 五维，单点结果不可外推 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:52-60`；③ registered 测试适合稳定行为，manual 测试需要特定环境，benchmark 不能替代 correctness [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:34-36`。
- **不变量**：测试文件存在只证明入口存在；suite 被注册只证明配置存在；**只有实际日志和结果才能证明某次运行成功** [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:72`。

### 3. Oracle 验证

- **定义**：oracle 是判定系统行为正确性的参照标准。
- **原理**：allocator 正确性 oracle——无 double free；live index 集合互斥；free + live + deferred release = capacity；page 对齐不变量成立 [已确认] `insights/04-design-decision-and-validation.md:69-76`。prefix cache oracle——命中部分不重复计算；lock_ref>0 节点不淘汰；eviction 只归还合法 page [已确认] `insights/04-design-decision-and-validation.md:79-83`。
- **不变量**：oracle 验证分两层——**数值正确**（allocator 计数闭合）和**语义正确**（attention 结果与 baseline 一致）。计数正确但 attention 错误，说明 page alignment 或 value/index 映射有 bug [已确认] `insights/04-design-decision-and-validation.md:74,83`。

### 4. 故障注入与诊断

- **定义**：主动注入故障验证系统恢复能力，配合诊断流程快速定位。
- **原理**：故障注入清单覆盖——KV slot 不足→限制 admission/retract/降级；Radix lock 泄漏→暂停 eviction/隔离 worker；offload transfer 超时→保留热 cache/降低 offload；P/D 节点失联→路由到聚合实例或重算 prefill；graph teardown→drain 后再 flush [已确认] `insights/04-design-decision-and-validation.md:103-109`。
- **诊断分段**：请求没输出时按 `rid_to_state → tokenize → dispatch → scheduler → forward → result → output` 顺序排查；显存不足时同时记录 PrefillAdder budget、allocator capacity、retraction order 和 abort reason [已确认] `sglang/99-roadmap/debugging-guide.md:15-33`。
- **不变量**：输出错位优先检查 batch 顺序和 `rids[i]` 对齐，再检查 `SamplingBatchInfo.filter_batch`、完成请求移除和 PP rank——通常不是 detokenizer 单点问题 [已确认] `sglang/99-roadmap/debugging-guide.md:34-35`。

### 5. 可观测体系设计

- **定义**：在系统各阶段暴露结构化数据，支撑告警、归因和容量决策。
- **原理**：每个请求应记录 reservation、实际 live tokens、prefix 命中、retract 次数和最终释放时间，才能识别"池不够"与"池有但不可用"的差异 [已确认] `insights/04-design-decision-and-validation.md:113-116`。
- **不变量**：可观测数据必须分粒度——请求级（per-request latency 分解）、batch 级（running batch 大小、prefill/decode 比例）、实例级（KV occupancy、free pages、eviction rate）。只靠 GPU util 无法区分"排队"与"计算饱和"。

## 常见误区

1. **"benchmark 通过 = 功能正确"**。benchmark 只衡量吞吐/延迟/显存，不能替代 correctness 测试。
2. **"平均值改善 = 系统更好"**。P99 或 abort 上升时，平均值改善可能掩盖长尾恶化。
3. **"故障注入只要看是否崩溃"**。故障恢复能力包括降级（retract）、回退（fallback）和优雅拒绝，不只是不 OOM。
4. **"GPU util 高 = 系统正常"**。util 高可能来自空转等待（如 PCIe transfer 阻塞），需要结合分段指标。
5. **"调试先看 detokenizer"**。输出错位通常是 batch 顺序或 `rids[i]` 对齐问题，不是 detokenizer 单点故障。
