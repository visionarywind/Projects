# I07 Attention Backend 与 CUDA Graph

## 范围与定位

I07 解决两个紧密耦合的问题：同一轮模型前向中，"用哪种 kernel 读 Q/K/V 和 KV cache"以及"这段 GPU 操作能否预先录制并在后续 batch 中重放"。前者是 attention backend 选择（FA/Flash/paged/native 等），后者是 CUDA Graph 的 capture/replay 与 eager fallback。本域在推理栈中位于模型执行层（M05），向上承接调度器提交的 ForwardBatch，向下消费 KV pool 暴露的物理 buffer。

与相邻域的边界：I07 不定义 KV cache 的组织方式（那是 I08 的范畴），只要求 KV 物理地址在 replay 期间固定；不定义采样逻辑（I09），但 graph 内同样包含 sample 前向；不定义多卡并行（I10），但 TP/DP/CP 均会改变 backend registry 和 graph eligibility。证据结构上，backend 选择、graph eligibility、capture 生命周期有源码级文档支撑，真实 GPU capture/replay/性能未验证。

## 核心概念与机制

### 1. Attention Backend 是执行策略，不是模型本身

定义：attention backend 回答"如何用当前硬件读取 Q/K/V 和 KV cache"，而非模型本身。同一模型可搭配 FlashAttention、FlashInfer、PyTorch Native SDPA、TRT-LLM MLA、TokenSpeed MLA 等不同 backend。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:16-22`

原理：`AttentionBackend` 合约将 forward metadata 分为三段——eager 入口 `init_forward_metadata`、graph 外动态准备 `init_forward_metadata_out_graph`、graph 内静态 shape 操作 `init_forward_metadata_in_graph`。因为 `.cpu()`、`.item()`、动态 shape tensor 不能录进 CUDA Graph，必须留在 graph 外。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:26-32`

例子：`TorchNativeAttnBackend` 是明确的正确性 fallback，用 PyTorch SDPA 逐请求循环；`FlashInferAttnBackend` 在非 MLA 时维护 quantized KV/sliding-window 等多个 wrapper，MLA 则转独立 `FlashInferMLAAttnBackend`。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:48-56`

### 2. backend 选择路径依赖多种部署模式

定义：backend 名称不等于"导入哪个 Python 文件"——设备类型、MLA、speculative、PDMUX、two-batch overlap 都会改变最终对象拓扑。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:34-46`

原理：`build_attention_backends` 先读取 prefill/decode backend 名称，再按模式分发：PDMUX 创建一个主 backend + 多个 decode backend；overlap 用 `TboAttnBackend` 包装子 backend；普通路径创建单一 resolved backend。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:38-44`

关键约束：TRT-LLM MLA 在 DCP+speculative 组合下直接拒绝，因为该实现不能提供跨 rank merge 所需的 metadata。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:50`

### 3. CUDA Graph capture/replay 的生命周期

定义：CUDA Graph 不是"另一种模型"，而是把形状稳定的一段 GPU 操作预先录制、后续用固定 buffer 重放。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:16`

原理：`DecodeCudaGraphRunner.capture` 先 warmup/autotune，按大 batch 到小 batch 逆序遍历 capture buckets（较小 graph 复用已建立的 CUDA memory pool），再为每个 shape × LoRA variant × DSA variant 各捕获一份图。Replay 只在 `can_run_graph=True` 时触发。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:109-131`

参数：capture bucket 按 batch size 分桶；prefill graph 还可能按 token bucket、prefix variant、CP/DP gather、backend mode 区分 key，实际 token 数与 capture bucket 不一致本身不是错误，但超出 padding/fitting 约束就必须回退 eager。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:128-131`

### 4. Graph eligibility 的判定

定义：graph eligibility 是运行时的动态检查，不满足就回退 eager，属于设计行为而非错误。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:59-95`

原理：decode runner 拒绝动态 token embedding override、ragged verify、speculative request width 不匹配、batch size 超范围、DP/MLP sync 条件不满足等情况。例如某请求有 `replace_embeds` 时 `can_run_graph=false`，直接走 eager。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:77-94`

例子：batch A 固定 decode width且在 capture bucket 内 → 尝试 replay；batch B 含 `replace_embeds` → eager；batch C speculative `num_tokens_per_req` 与 capture width 不同 → eager。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:80-92`

### 5. Prefill Graph vs Decode Graph 是独立 runner

定义：prefill 和 decode 不是同一个 graph runner，各自有独立的 bucket 和生命周期。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:72-75`

原理：`ModelRunner._forward_raw` 先判断 ForwardMode 是否允许 graph——decode 走 decode graph；extend 且 prefill graph eligible 走 prefill graph；其余走 eager。Prefill graph 还需检查 DP rank、replace embeds、target verify、LoRA、hidden mode、最大 token 数和 padding waste 阈值。[C] `sglang/01-modules/M09-attention-cuda-graph/README.md:59-75`

## 关键参数与公式

| 参数 | 含义 | 状态 |
|---|---|---|
| capture batch buckets | 按 batch size 分桶录制图，replay 时匹配最近桶 | [C] M09:113-114 |
| padding waste threshold | prefill graph 拒绝超过该值的 bucket | [C] M09:128 |
| graph key | 由 batch size / shape / LoRA variant / DSA variant / prefix variant / CP backend 复合构成 | [C] M09:113-115,130-131 |
| SharedReadEnds | scheduler 共享数据读取结束位置，用于 overlap 正确性 | [C] M09:30-32 |
| `can_run_graph` | 运行时 eligibility 检查，false → eager fallback | [C] M09:77-94 |
| capture 顺序 | 大→小 batch，以便小 graph 复用大 graph 的 CUDA memory pool | [C] M09:113 |

## 常见误区

- **"启用了 CUDA Graph 就一定 replay"**——错。`can_run_graph` 在动态 embedding、spec width 不匹配、ragged verify 等条件下返回 false，必须走 eager fallback。Graph 只是一种能力降级而非必然执行。[C] M09:77-94
- **"attention backend 名字决定一切"**——错。`--attention-backend flashinfer` 不等于最终 kernel layout；MLA、speculative、PDMUX、overlap、TP/DP/CP 都会改变 backend 对象拓扑和 KV layout。[C] M09:46-56
- **"graph replay 后模型结果不再经过 sample"**——错。graph 只加速 forward 的 attention/FFN 部分，logits/sample 仍在 graph 外执行，结果要经过 M04 result processor。[C] M09:95
- **"prefill 和 decode 共用同一张图"**——错。两者是独立 runner，独立 bucket，独立 capture 生命周期；prefill graph 还额外处理 prefix variant 和 chunked-prefix。[C] M09:72-75
- **"graph capture 失败等同于请求失败"**——错。Graph fallback 是能力降级，不是事务失败；target verify 或 commit 失败才需要回到安全提交点。[C] `insights/06-speculative-decoding-as-transaction.md:273`
