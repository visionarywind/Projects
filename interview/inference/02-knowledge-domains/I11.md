# I11 Speculative Decoding

## 范围与定位

I11 处理推测解码（Speculative Decoding）：用小模型（draft）一次猜多个 token，再用大模型（target）整体验证，从而减少昂贵 target forward 次数。本域覆盖 draft/verify 两阶段状态机、acceptance/rejection/replacement/bonus 决策、speculative 语义等价性证明、与 grammar/sampling 的交叉约束、CUDA Graph 兼容性、decoupled draft 的 IPC 协议。它本质上是在保持 target 采样分布正确性的前提下，通过投机计算换取延迟吞吐收益。

与相邻域的边界：I11 不定义 KV cache 组织（I08），但 speculative 必须区分 target 已提交 KV、verify 临时写入 KV、draft KV、rejected suffix 四种所有权；不定义采样（I09），但 acceptance/rejection 会影响 penalty/grammar/RNG 状态推进；不定义并行（I10），但多卡 verify 同样有 collective 路径。证据结构上，draft/verify 状态机、提交边界、acceptance 类型有源码级文档支撑；真实 acceptance rate、GPU 执行、吞吐收益未验证。

## 核心概念与机制

### 1. 两阶段状态机：Proposed → Verifying → Decided → Committing → BaseCommitted

定义：speculative decoding 可以理解为事务协议——draft 给出候选，target 验证后只有连续合法前缀能 commit。[C] `insights/06-speculative-decoding-as-transaction.md:28-54`

原理：`BaseCommitted` 是请求对外可见的 token/KV/sequence length 一致的稳定状态；`Proposed` 候选仅属 draft 工作区；`Verifying` 是 target 计算候选块概率；`Decided` 得到 accepted length/replacement/bonus；`Committing` 把多个状态推进到同一新边界；`RollingBack` 释放/截断未提交状态。[C] `insights/06-speculative-decoding-as-transaction.md:30-54`

关键不变量：理想不变量是 `visible_output_len == committed_target_token_len == grammar_consumed_len == request_valid_kv_len`。物理分配长度可大于逻辑 committed length，但有效边界必须一致。[C] `insights/06-speculative-decoding-as-transaction.md:71-80`

### 2. Acceptance 不只是整数

定义：acceptance 需要回答多个问题——accepted prefix 长度、reject 点是否需要 target replacement、bonus token 是否合法、candidate width 是否相同、grammar mask 对 draft/target 在哪一步生效。[C] `insights/06-speculative-decoding-as-transaction.md:109-121`

原理：不同算法（greedy match、rejection sampling、MTP/EAGLE、ngram、DFlash）共享 proposal/verify/commit 边界，但不共享所有 KV 和 graph 细节。[C] `insights/06-speculative-decoding-as-transaction.md:120-121`

k=4 最小例子：draft 给出 `[a,b,c,d]`，target 只接受 `a` 并给出 replacement `x` → commit `P+[a,x]`，rollback `[b,c,d]`。必须同步更新：用户输出、target KV、draft KV、`seq_lens`、request row、sampling/grammar state。[C] `insights/06-speculative-decoding-as-transaction.md:82-108`

### 3. KV ownership：target 与 draft 不能混账

定义：必须区分 target 已提交 KV、target verify 临时 KV、draft proposal KV、rejected suffix 和 accepted prefix 的下一轮可复用状态。[C] `insights/06-speculative-decoding-as-transaction.md:123-145`

三种常见布局：shared/same worker pool、independent draft pool、decoupled draft service/process。无论哪种都要区分四种 ownership。[C] `insights/06-speculative-decoding-as-transaction.md:127-145`

关键错误：reject 后只改 `Req.output_ids` 而不回收 target allocator slots、draft allocator、graph/static metadata、prefix/radix protection，会导致下一轮读到 rejected suffix 或 free page 持续下降。[C] `insights/06-speculative-decoding-as-transaction.md:147-157`

建议：为每个 request 记录 `visible_len == committed_len <= allocated_len` 三个长度。[C] `insights/06-speculative-decoding-as-transaction.md:158-166`

### 4. Grammar/sampling 的交叉约束

定义：grammar 只判定 token 是否合法语言，不决定 target 概率是否接受候选；target 概率可接受的 token 若违反 grammar 也不能提交。[C] `insights/06-speculative-decoding-as-transaction.md:168-182`

原理：candidate token → grammar legality → target probability/acceptance → commit matcher state。提交后 grammar matcher 必须与可见 token 一致。[C] `insights/06-speculative-decoding-as-transaction.md:175-181`

penalty/RNG：rejected draft token 不应永久推进 target 的 penalty/history/RNG 语义。[I] `insights/06-speculative-decoding-as-transaction.md:183-194`

### 5. CUDA Graph 与 ragged verify

定义：speculative verify 比普通 decode 更难 graph 化——candidate width 可能不同、accepted length 是动态值、batch 中可能同时出现 finished/rejected/full-accepted。[C] `insights/06-speculative-decoding-as-transaction.md:196-214`

原理：decode graph eligibility 会检查 speculative request width、ragged verify、batch size 等 variant；不匹配时 eager fallback 是正确行为。[C] `insights/06-speculative-decoding-as-transaction.md:204-205`

正确指标应区分 `graph eligible batches / actual replay batches / fallback reason distribution / capture padding waste`。[C] `insights/06-speculative-decoding-as-transaction.md:208-214`

## 常见误区

- **"speculative decoding 就是小模型猜 token"**——不准确。核心是保证只有经过 target 验证并完成状态提交的前缀才能成为请求可见的事实，涉及 KV ownership、状态一致性和回滚机制。[C] 06:10-27
- **"acceptance rate越高性能越好"**——错。高 acceptance rate 仍可能因 draft 过重、verify 失去 graph、batch padding 过多或 CPU commit 瓶颈而性能变差。[I] 06:306
- **"reject 后只需改 output_ids"**——错。必须同步回收 target allocator、draft allocator、graph metadata、prefix/radix protection、grammar/penalty 状态，否则出现悬挂映射。[C] 06:147-157
- **"启用了 speculative + CUDA Graph 就一定 replay verify"**——错。candidate width、ragged verify、finished/rejected 混合 batch 都可能导致 eager fallback。[C] 06:204-205
- **"graph fallback 是事务失败"**——错。Graph fallback 是能力降级，不是事务失败；target verify 或 commit 失败才需回到安全提交点或终止请求。[C] 06:273
