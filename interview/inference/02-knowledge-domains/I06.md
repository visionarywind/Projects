# I06 Prefill/Decode 与 ForwardBatch

## 范围与定位

本域覆盖 prefill 与 decode 两个阶段的差异及其通过 `ForwardBatch` 统一接口的实现：`ForwardMode.EXTEND` vs `ForwardMode.DECODE`、`prepare_for_extend` vs `prepare_for_decode`、`extend_lens`/`prefix_lens` 与 decode 单 token 追加的 shape 正确性、算术强度差异对 batch 策略的影响。与 I04 的边界在 `run_batch` 之前的 batch 准备，与 I05 的边界在 `ModelForward` 内部的 forward path 分叉。本域是 I04 调度决策和 I05 执行细节的交汇点。

## 核心概念与机制

**1. prefill 与 decode 的算术强度差异决定调度策略**

prefill 一次性并行处理 prompt 全部 token，主要计算是大矩阵乘法 GEMM，算术强度（FLOPs/byte）随 prompt 长度增长，通常落在 roofline 的 compute-bound 区。decode 每步只生成一个 token，计算量固定为一次前向，但 KV cache 读取量随序列线性增长，算术强度 ∝ 1/seq_len，最终变成 bandwidth-bound。硬件 ridge point I* = F_peak / B_peak：prefill 越过 ridge point 落在 compute 区，decode 几乎总是 bandwidth-bound。[C: `02-request-flow/03-调度器与连续批处理.md:606-626`; `01-question-bank/beginner.md:23-32`]

**2. `prepare_for_extend` 与 `prepare_for_decode` 的 shape 语义**

`prepare_for_extend`（`schedule_batch.py:2559-2605`）：`input_ids` 展平为新 token 拼接，`extend_lens` 记录每请求的新增 token 数，`prefix_lens` 记录缓存命中数，`out_cache_loc` 分配一段连续 KV 位置。例如 A 命中 4 + 新增 3、B 命中 2 + 新增 2 → `input_ids = [A_new1..A_new3, B_new1..B_new2]`、`extend_lens = [3,2]`、`prefix_lens = [4,2]`。`prepare_for_decode`（`schedule_batch.py:3343-3435`）：`seq_lens += 1`，每请求分配 1 个新 KV slot，`forward_mode = ForwardMode.DECODE`。attention backend 依靠 `extend_lens`/`prefix_lens` 知道每个 query 读取哪个请求的历史 KV；decode 依靠 `seq_lens` 的增量保持 KV 读取范围正确。[C: `02-request-flow/03-调度器与连续批处理.md:501-602`]

**3. `ForwardBatch` 统一接口中的双路径**

`ForwardBatch.init_new` 读取 `ScheduleBatch` 的 `forward_mode`：extend 模式时 `extend_lens`、`prefix_lens` 和 logprob 起点被放入 forward metadata；decode/idle 时这些 extend-only 字段置为 `None`。`ModelRunner.sample` 中 decode 用 positions，prefill 用 `seq_lens - 1` 的最后位置。这种"同一对象、不同字段激活"的设计让 worker 代码不需要为两阶段各写一条完整分支，但 shape 正确性依赖 `prepare_for_extend/decode` 的 metadata 精确填充。[C: `01-modules/M05-model-execution/README.md:44-53`; `01-modules/M05-model-execution/README.md:107-114`]

**4. mixed chunk 把 prefill 和 decode 合并到同一 forward**

`_get_new_batch_prefill_raw` 在满足条件时把 running batch decode 请求行带入同轮 prefill forward：`new_batch.mix_with_running(running_batch)`。限制：`return_logprob` 不支持、`input_embeds` 不支持、beam member rows 不放入。收益是减少 kernel launch 和调度间隙；代价是输入布局、logprob、beam、speculation 和 attention metadata 更复杂。连续 batching 的核心收益不依赖 mixed chunk——即使不能混合，相邻轮次仍可交替推进不同阶段。[C: `02-request-flow/03-调度器与连续批处理.md:629-649`]

**5. 双阶段资源模型差异驱动 `PrefillAdder` 预算**

prefill 的 token budget（`max_prefill_tokens`）防止单请求独占 GPU；decode 的 KV budget（`check_decode_mem`）防止活跃请求耗尽 pool。prefill batch 受显存限制（中间激活随 prompt 增长）且 compute-bound，batch 增大收益递减；decode batch 受带宽限制（KV 总读取量线性增长），batch 增大最终撞上带宽墙。`PrefillAdder.get_num_allocatable_reqs` 同时考虑 `pp_max_micro_batch_size - running_bs` 和 `req_to_token_pool.available_size()`。chunked prefill 把长 prompt 拆分，避免一个请求让其他请求长时间得不到 GPU 时间。[C: `02-request-flow/03-调度器与连续批处理.md:391-429`; `01-modules/M04-scheduler-batching/README.md:163-177`]

## 常见误区

1. **"decode 慢是因为计算量太大"** — 错误。decode 每步计算量固定（一次前向），慢的原因是 KV cache 访存随序列增长，瓶颈在带宽。[C: `01-question-bank/beginner.md:48`]
2. **"prefill 可以用 continuous batching 像 decode 一样持续交错"** — 有误。prefill 虽可被调度器交错到 batch 中，但其 GEMM 大矩阵特性意味着长 prefill 会独占计算资源，挤压同 batch 其他请求的 decode 进度。因此需要限制 prefill 预算。[C: `01-question-bank/beginner.md:49`]
3. **"prefill batch 越大越好"** — 错误。prefill 受显存限制且 compute-bound，batch 增大总计算量线性增长，收益递减。[C: `01-question-bank/beginner.md:41`]
4. **"decode 和 prefill 必须用两个不同的 ForwardBatch 子类"** — 错误。`ForwardBatch` 用同一对象，通过 extend-only 字段置 None 保持 shape 正确性。[C: `01-modules/M05-model-execution/README.md:44-53`]
5. **"mixed chunk 是 continuous batching 的必要条件"** — 错误。mixed chunk 是优化，不能混合时相邻轮次仍可交替推进。[C: `02-request-flow/03-调度器与连续批处理.md:629-649`]
