# I03 IPC 与进程边界

## 范围与定位

本域覆盖 SGLang 标准 SRT runtime 的进程间通信拓扑：主进程（FastAPI + TokenizerManager）与子进程（Scheduler、DetokenizerManager）通过 ZMQ 的消息契约、地址分配、序列化格式、ready 握手、背压机制、异常传播和优雅关闭。与 I01 的边界在 `PortArgs.init_new`，与 I02 的边界在 `_send_one_request` 的 `sock_send`，与 I04 的边界在 scheduler 进程内部的 event loop。本域不关心请求语义，只关心跨进程边界两侧消费和产生的对象。

## 核心概念与机制

**1. `PortArgs` 是拓扑地址的唯一来源**

`PortArgs`（`server_args.py:741-771`）集中携带：`tokenizer_ipc_name`、`scheduler_input_ipc_name`、`detokenizer_ipc_name`、`nccl_port`、`rpc_ipc_name`、`metrics_ipc_name`、`tokenizer_worker_ipc_name`、`decoupled_spec_ipc_config`、`load_collector_ipc_name`、`instance_id`。单机模式用 `ipc://` + 临时文件名生成 IPC endpoint；DP attention 模式派生 TCP 地址并在绑定前 `wait_port_available` 检查冲突。设计意图：避免各进程自行拼接地址导致 bind/connect 不一致或端口复用。[C: `01-modules/M15-ipc-control-plane/README.md:89-133`; `02-request-flow/06-多进程与IPC.md:187-254`]

**2. 每个进程只建自己的 socket，非 rank-zero 不接 API 输入**

`TokenizerManager.init_ipc_channels` 建 PULL 收 detokenizer 输出 + PUSH 发 tokenized request。`SchedulerIpcChannels.create` 只给 rank-zero scheduler 建 PULL + DEALER + PUSH；非 rank-zero 用 `SenderWrapper(None)`。`DetokenizerManager` PULL 收 scheduler、PUSH 回 tokenizer。`skip_tokenizer_init` 时 scheduler 的 `send_to_detokenizer` 实际连到 `tokenizer_ipc_name`，跳过 detokenizer 进程。不变量：请求入口和输出出口只有一个控制面（rank-zero scheduler）。[C: `01-modules/M15-ipc-control-plane/README.md:137-165`; `02-request-flow/06-多进程与IPC.md:396-454`]

**3. msgspec + PickleWrapper 的双轨序列化**

默认路径：`msgpack_encode` → `msgspec Encoder(enc_hook)` → `socket.send`。只有 msgspec Struct 和允许 primitive 可直接编码；opaque object 必须显式 `PickleWrapper`。环境开关 `_USE_PICKLE_IPC` 切换为 `send_pyobj`/`recv_pyobj`。`TokenizedGenerateReqInput` 批量发送时封装为 `BatchTokenizedGenerateReqInput(batch=tokenized_objs)`，每个 item 保留自己的 `http_worker_ipc`。设计意图：显式类型约束让 IPC schema 变化可被发现。[C: `01-modules/M15-ipc-control-plane/README.md:198-214`]

**4. `mp.Pipe` vs ZMQ 的分工**

每个 scheduler 子进程创建后通过单向 `mp.Pipe(duplex=False)` 回传 `scheduler.get_init_info()`，主进程 `wait_for_ready` 阻塞收集。ZMQ 用于稳态高频请求/结果/控制消息。二者不互相替代：Pipe 是启动同步信息，ZMQ 是长期数据流。Detokenizer 进程异常时记录 traceback、清理 socket mapping、向 parent 发 SIGQUIT；Scheduler 异常时额外按 `SGLANG_KILLPG_ON_SCHEDULER_EXCEPTION` kill process group。TokenizerManager 的 `soft_watchdog` 在阻塞接收前 disable watchdog，收到消息后 `last_receive_tstamp = real_time()` 并 `soft_watchdog.feed()`。这保证阻塞在 socket 上本身不是故障——真正要观察的是进程是否长期没有处理任何消息。[C: `01-modules/M15-ipc-control-plane/README.md:243-291`; `02-request-flow/06-多进程与IPC.md:615-672`]

**5. 优雅关闭的顺序与不变量**

SIGTERM 后 watchdog：停止接收新请求 → 等待 rid 清空 → dispatch `ShutdownReq` → 等 scheduler → `kill_process_tree` 兜底 → `sys.exit(0)`。`Engine.shutdown` 还停 watchdog、关 RPC、终止 weight-cache daemon、关 multimodal transport。不变量：已 dispatch 请求不能只删本地 state 而不通知 scheduler；daemon/IPC/multimodal 等非 scheduler 资源必须由拥有者清理；graceful wait 结束后仍需 hard-kill。Detokenizer 入口 `kill_itself_when_parent_died()` 防止孤儿进程。[C: `01-modules/M15-ipc-control-plane/README.md:293-318`; `02-request-flow/06-多进程与IPC.md:910-953`]

## 常见误区

1. **"ZMQ PUSH 发送成功 = 请求完成"** — 错误。PUSH 成功只表示消息进入发送路径，不代表 scheduler admission、GPU 执行或客户端收到。完成必须看 `BatchStrOutput`/abort 和 `ReqState.finished`。[C: `01-modules/M15-ipc-control-plane/README.md:251-255`]
2. **"每个 TP rank 都直接接收 HTTP 请求"** — 错误。只有 rank-zero scheduler 有 PULL + DEALER 主收发通道，其他 rank 通过分布式通信参与 forward。[C: `01-modules/M15-ipc-control-plane/README.md:149-158`]
3. **"msgpack 能自动序列化所有字段"** — 错误。任意 opaque object 必须 `PickleWrapper`，这是显式约束而非 bug。[C: `01-modules/M15-ipc-control-plane/README.md:198-214`]
4. **"SIGQUIT 是请求级错误 envelope"** — 错误。SIGQUIT 是子进程异常通知，不是请求级错误。[C: `01-modules/M15-ipc-control-plane/README.md:282-291`]
5. **"mp.Pipe 传逐 token 数据"** — 错误。Pipe 只传初始化 ready 信息，不承载请求/结果。[C: `01-modules/M15-ipc-control-plane/README.md:243-249`]
