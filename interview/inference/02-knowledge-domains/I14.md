# I14 LoRA / 适配器与多模态

## 范围与定位

本域覆盖三类"在基座模型上叠加差异化能力"的机制：LoRA/Adapter（参数高效微调）、多模态输入（视觉/音频的特征注入）、以及它们共存的运行时隔离。核心问题是：**如何在同一个 serving 实例里高效承载多个 adapter 或多种模态**、**请求路由如何感知 adapter 身份**、**cache key 如何隔离不同变体**。

边界：与 I15（长上下文与容量）是 KV 预算与 adapter 显存的叠加关系；与 I06（prefill/decode）是 adapter 在 forward 阶段通过低秩 delta 注入，不影响阶段划分。与 I02（HTTP/API）的边界是 adapter 在协议层已影响状态——M02 的 `_resolve_lora_path` 规定 model 参数中的 adapter 优先于显式 `lora_path` [已确认]。

证据等级说明：LoRA/适配器机制的仓库沉淀较强（M14 有完整的 LoRA 生命周期源码分析），本域主要内容为 [C]；多模态部分（M12）有接口边界但 GPU encoder 行为未验证，本域相关内容标注 [U] 且禁编造。

## 核心概念与机制

### 1. LoRA 生命周期：从加载到执行

- **定义**：LoRA 在基座模型权重上叠加低秩 delta（`W' = W + A·B`），serving 时按需加载/卸载 adapter 而不修改基座权重。
- **原理**：`LoRAManager`（`lora/lora_manager.py`）初始化 backend、形状和 memory pool；`load_lora_adapter` 加载 adapter 到 slot，`validate_lora_batch` 检查同一 forward batch 的 adapter 组合合法性，`prepare_lora_batch` 生成每 token 的 adapter id 元数据。HTTP 的 model 参数可携带 adapter 名称，M02 基类规定 model 中 adapter 优先于显式 `lora_path` [已确认] `sglang/01-modules/M14-moe-quantization-lora/README.md:32-38`。
- **不变量**：一个 batch 同时包含 base 与 adapter-A 请求时，manager 为 adapter-A 分配 slot，ForwardBatch 保存每 token 的 adapter id，backend 只对对应 token 加 delta；下一批 reset 不能泄漏 A 的 metadata [已确认] `sglang/01-modules/M14-moe-quantization-lora/README.md:57-58`。
- **例子**：请求 `model=my-lora-adapter` → M02 基类解析 adapter 名 → TokenizerManager resolve → LoRAManager 加载到 slot → prepare_lora_batch → backend apply delta → 完成后 unload/evict。

### 2. 多模态输入处理链 [U]

- **定义**：多模态处理器将请求中的 media（图像/音频/视频）转化为 tokenizer/model 可消费的文本 token、placeholder、特征和位置元数据。
- **原理**：`BaseMultimodalProcessor` 通过 `load_mm_data` → `process_and_combine_mm_data` → `_expand_input_ids` → `MultimodalInputs/mm_items` 完成处理链 [已确认] `sglang/01-modules/M12-multimodal-runtime/README.md:32-48`。特征可通过 CUDA IPC/CPU transport 传到 ForwardBatch。
- **不变量**：特征数量与 placeholder 数量必须一致，否则 M05 的 input ids、position ids 和 embedding splice 会错位 [已确认] `sglang/01-modules/M12-multimodal-runtime/README.md:57-59`。
- **注意**：真实图像/音频/视频 GPU encoder 行为未验证，本仓库仅记录接口边界。异步预处理通过 `MultimodalProcessorExecutor` 在线程/进程 executor 中执行；`shutdown` 必须在 server 退出时回收 worker。

### 3. Cache Key 隔离

- **定义**：不同 adapter 和不同模态配置产生不同的 KV cache，不能混用。
- **原理**：Radix Cache 的 key 构造包含 `extra_key/cache_salt` 以区分不同 variant [已确认] `sglang/01-modules/M08-kv-cache/README.md:62-63`。多模态的 cache identity 由 `multimodal/cache/identity.py` 定义，避免把相同媒体和不同 processor 配置误认为同一结果 [已确认] `sglang/01-modules/M12-multimodal-runtime/README.md:36-37`。
- **不变量**：修改 placeholder/token count 会影响 M03 token budget、M04 admission、M08 KV positions 和 M05 embedding splice [已确认] `sglang/01-modules/M12-multimodal-runtime/README.md:71`。

### 4. Batching 隔离

- **定义**：同一 forward batch 内的请求可能使用不同 adapter，batch 级别需要正确调度。
- **原理**：`validate_lora_batch` 检查同一 forward batch 的 adapter 组合——某些 backend 可能不支持混合 adapter 或需要特殊处理 [已确认] `sglang/01-modules/M14-moe-quantization-lora/README.md:36`。ForwardBatch 保存每 token 的 adapter id，backend 根据 id 决定是否加 delta。
- **不变量**：LoRA slot/adapter 改动会跨 M02 model listing、M03 request state、M05 graph eligibility、M09 CUDA Graph 和 M10 sampling metadata [已确认] `sglang/01-modules/M14-moe-quantization-lora/README.md:66-67`。

## 常见误区

1. **"LoRA 请求可以随意混入任何 batch"**。`validate_lora_batch` 可能拒绝不兼容的 adapter 组合，backend 能力差异会导致混合 batch 失败。
2. **"adapter 在 kernel 层才影响状态"**。adapter 选择发生在 M02 协议解析阶段，早于 tokenizer 和 scheduler。
3. **"多模态特征通过普通 pickle 跨进程传输"**。大特征使用 CUDA IPC handle，接收端必须在特征生命周期结束后释放句柄，不是普通 Python pickle。
4. **"不同 adapter 可以共享 KV cache"**。不同 adapter 产生不同 KV，必须通过 cache_salt 隔离，否则会出现 KV 污染。
5. **"多模态 placeholder 数量不影响 KV 容量规划"**。placeholder 扩展的 token 数直接影响 token budget 和 KV 分配。
