# I02 协议、tokenizer 与请求状态

## 范围与定位

本域覆盖请求进入推理栈到离开 tokenizer 层之间的全部处理：HTTP body 校验 → 协议字段到内部请求的映射 → `GenerateReqInput` → `TokenizerManager` → tokenize → `TokenizedGenerateReqInput` → IPC dispatch → `ReqState` 生命周期与流式输出。与 I01 的边界在 `launch_server` 返回之后，与 I03 的边界在 `TokenizerManager._send_one_request` 的 `sock_send` 之后，与 I04 的边界在 scheduler 创建 `Req` 并加入 `waiting_queue` 之后。本域不处理 admission、batch 构造或模型计算。

## 核心概念与机制

**1. 协议适配层只做校验和转换，不做 admission**

M02（HTTP/API 协议层）的职责是 body/schema 校验、协议字段到 `GenerateReqInput`/`EmbeddingReqInput` 的映射、流式响应封装和错误序列化。`ORJSONRoute` 缓存 body 并 `orjson.loads`，`validate_json_request` 强制 `content-type: application/json`。`OpenAIServingBase.handle_request` 调用 `_validate_request` → `_convert_to_internal_request` → 选择 streaming/non-streaming → 捕获异常并 `create_error_response`。关键不变量：协议层不创建 scheduler 侧的 `Req`，不影响 admission 决策。[C: `01-modules/M02-http-api-protocol/README.md:19-73`]

**2. Chat 不是字段重命名，而是多阶段编码**

`serving_chat.py` 的 chat 处理链：`normalize_tool_content` 合并 text parts → `parse_tool_call_arguments` 校验 JSON → chat template 或 dsv4/dsv32 编码 → assistant prefix/`continue_final_message` 改写 prompt → response parser 将 reasoning/tool call/logprob 转换为 OpenAI chunk。"OpenAI compatible"是协议 schema、模板、约束编译和输出 parser 的组合。LoRA adapter 通过 `_parse_model_parameter` 以 `base:model-or-adapter` 形式指定，优先于显式 `lora_path`。[C: `01-modules/M02-http-api-protocol/README.md:104-116`]

**3. `ReqState` 与 scheduler 侧 `Req` 通过 `rid` 关联**

`ReqState`（`tokenizer_manager.py:224-269`）维护本地等待状态：`out_list`、`finished`、`event`、`obj`、`dispatched`、`abort_sent`、`text_chunks`。不变量：`dispatched=False` 时失败清理直接删除本地 state；`dispatched=True` 时必须先发 abort 等 scheduler 回应。Scheduler 侧的 `Req`（`schedule_batch.py:926-1018`）保存长期执行状态。两个对象通过同一个 `rid` 关联，不共享 Python 引用。[C: `01-modules/M03-tokenizer-request-state/README.md:83-130`; `02-request-flow/02-请求进入与分发.md:308-336`]

**4. tokenize 的三分支与 multimodal 覆盖**

`_tokenize_one_request`（`tokenizer_manager.py:970-1138`）的优先级：(1) `input_embeds` → 要求关闭 radix cache；(2) `input_ids` → 跳过 tokenizer；(3) 文本经 tokenizer 编码。multimodal 输入经 `mm_processor.process_mm_data_async` 可能覆盖 `input_ids` 和 `token_type_ids`。这意味着图片请求的 token ids 不是普通 tokenizer 的直接结果，而是 multimodal processor 根据占位符和图像信息加工后的产物。`_validate_one_request` 在 tokenize 后统一校验 prompt 长度、`input + max_new_tokens` 是否超 context_len、embedding 请求是否连接到 embedding 模型、token ids logprob 是否在词表范围内。若允许自动截断则截断 input 或降低 `max_new_tokens`，否则抛出错误。[C: `01-modules/M03-tokenizer-request-state/README.md:174-183`; `02-request-flow/02-请求进入与分发.md:343-487`]

**5. 增量 streaming 的 coalesce 与 backpressure**

`_stream_one_response`（`tokenizer_manager.py:1740-1852`）中 `incremental_stream` 且 `len(out_list)>1` 时调 `_coalesce_streaming_chunks` 合并 text/ids，从最后一个 chunk 取 meta_info。非增量 streaming 中间 `text` 设为 `None`，避免每步复制完整字符串。`asyncio.wait_for(state.event.wait(), timeout=_REQUEST_STATE_WAIT_TIMEOUT)` 检查 `request.is_disconnected()` 后调 `abort_request`。backpressure 来自 streaming chunk coalescing、scheduler waiting/running batch、detokenizer decode capacity 和 TokenizerManager event loop。[C: `01-modules/M03-tokenizer-request-state/README.md:191-194`; `01-modules/M15-ipc-control-plane/README.md:257-268`]

## 常见误区

1. **"TokenizerManager 就是 tokenizer"** — 错误。TokenizerManager 还承担 HTTP/Scheduler 桥接、`ReqState` 管理、detokenize 输出汇聚、abort、session、metrics 和控制面操作。[C: `02-request-flow/02-请求进入与分发.md:1136-1143`]
2. **"stream=true 改变模型执行"** — 错误。stream 只改变 HTTP 层消费异步生成器的方式，Scheduler 用同一套 forward 代码。[C: `01-modules/M02-http-api-protocol/README.md:70-72`; `02-request-flow/02-请求进入与分发.md:173-187`]
3. **"ReqState 和 Req 是同一个对象"** — 错误。ReqState 在主进程，Req 在 Scheduler 子进程，通过 `rid` 跨 IPC 关联。[C: `02-request-flow/02-请求进入与分发.md:1145-1148`]
4. **"tokenize 完成就是请求处理的终点"** — 错误。tokenize 是从 API 对象到执行对象的第一道转换，后续还有 dispatch、admission、forward、detokenize。[C: `02-request-flow/02-请求进入与分发.md:108`]
5. **"HTTP 返回就是模型原始输出"** — 错误。模型产 logits，经采样、finish 检查、detokenize、meta_info 组装和 SSE/JSON 编码后才到客户端。[C: `02-request-flow/02-请求进入与分发.md:1164-1167`]
