### AQ-E001. 如何定义 AI 辅助开发的可验证质量不变量？

- 难度：专家级
- 知识域：K01 vibe-coding 生命周期与人机协作
- 考察能力：不变量建模、跨层权衡、治理设计
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：契约式设计（前置/后置/不变量）、CI/CD 门禁、代码审查、可追溯性
- 关联题目：AQ-E004（形式化验证）、AQ-E005（测试治理）、AQ-E013（协作演进）
- 事实状态：`[推断]`

#### 1. 背景知识

"给 AI 产出加质量"最常见的做法是加检查项，但检查项会随工具和团队漂移。专家级做法是先定义**不变量（invariant）**：无论作者是人还是模型、无论工具如何换代，只要系统处于"可信任状态"，这些命题就必须成立。可验证意味着每条不变量都配一个可执行的 oracle（能机器判定真假），而不是一句口号。

区分三类容易混淆的概念：

- **不变量**：状态的安全性质，任何合法状态都满足（如"主干上每个提交都有可达的验证证据"）。
- **指标**：对状态的观测，用于趋势与告警（如"变更失败率"）。指标可以波动，不变量不能。
- **门禁**：在迁移路径上强制不变量的执行点（如分支保护、发布卡点）。

#### 2. 问题分析

先明确"可验证"的三个必要条件，再给不变量分层，最后处理冲突与残余风险：

1. **可执行**：oracle 能自动返回布尔结果，否则不变量退化为愿望。
2. **稳定**：不随模型版本、提示词、工具替换而改变；改变的是如何满足，而非是否满足。
3. **可归因**：能定位到具体变更集与责任主体，否则无法在破坏时追责与回滚。

分层（跨层权衡的关键）：代码层、流水线层、组织层各有一组不变量，上层依赖下层，但任何一层都不能替代另一层。例如"测试通过"（代码层）不能替代"审查记录存在"（流水线层），因为二者防止的是不同失效模式。

#### 3. 具体答案

面试中可以这样回答：

> 我会把"AI 辅助开发是否可信"还原成一组必须在任何合法状态下都成立、并且能被机器判定的命题，而不是列一堆检查项。至少四条：
>
> 第一，**贡献不变量**：进入主干的每个变更集，都存在一个从该修订可达的验证证据（测试结果、审查记录或证明），与作者是人还是模型无关。
>
> 第二，**来源不变量**：每个产物记录生成者身份——人、模型版本、以及触发它的指令上下文——使得回归发生时能反查"是模型换版造成的还是需求误读造成的"。
>
> 第三，**影响域不变量**：一个变更实际能触达的资源，必须落在它声明的范围内；越界即拒绝。这条防止生成代码静默扩大了爆炸半径。
>
> 第四，**可逆不变量**：每个进入生产的变更都存在一条在 RTO 内可执行的回滚路径；没有回滚路径就不允许发布。
>
> 关键在于每条都要配 oracle：贡献不变量靠修订与证据的图可达性查询；来源不变量靠产物元数据；影响域靠静态可达性加运行期策略；可逆靠预置的恢复演练。定义不变量本身就规定了可观测性要采集什么，这比事后补监控要省得多。

#### 4. 技术洞察

不变量的价值在于**约束解空间**而非提高标准。给出形式化骨架：

```text
Trunk = { c : commit | c 已合并到主干 }
Evidence(c) = { v | v 是从 c 可达的验证产物 }
Provenance(c) = (author_kind ∈ {human, model}, model_id, prompt_ref)
Reach(c) = 变更 c 可触达的资源集合
Scope(c) = 变更 c 声明的资源集合
Rollback(c) = c 对应的可执行恢复过程

I1 贡献：  ∀c ∈ Trunk. Evidence(c) ≠ ∅
I2 来源：  ∀c ∈ Trunk. Provenance(c) 完整且不可篡改
I3 影响域：∀c ∈ Trunk. Reach(c) ⊆ Scope(c)
I4 可逆：  ∀c ∈ Deployed. Rollback(c) 存在且满足 RTO 上界
```

冲突不可避免：把 I3 收紧到极致会拒绝一切合法的重构（重构天然扩大触达面），把 I1 收紧到"必须端到端测试"会拖垮小改动的交付。专家级回答要指出**不变量不是越强越好，而是要在误差可承受的方向上偏置**：影响域宁可保守拒绝，贡献证据可按变更关键性分级（关键路径要求更强的证据等级）。

```text
组织层   I5 责任闭环：每个不变量有 owner、有决策、有例外登记
            │ 依赖
流水线层 I1 贡献 / I2 来源 / I4 可逆  ── 门禁在其上强制执行
            │ 依赖
代码层   I3 影响域  ── 静态可达性 + 运行期策略

不变量 ↔ oracle ↔ 门禁 三者必须一一对应：
  缺 oracle  → 不变量是口号
  缺门禁      → 不变量是建议
  缺 owner    → 破坏后无人修复
```

| 不变量 | 防止的失效模式 | oracle |
|---|---|---|
| I1 贡献 | 无证据的"能跑"代码入主干 | 修订-证据可达性查询 |
| I2 来源 | 回归无法归因到模型/提示 | 产物元数据与审计日志 |
| I3 影响域 | 静默扩大爆炸半径 | 静态可达性 + 运行期策略 |
| I4 可逆 | 无法回滚的坏发布 | 回滚演练 + 恢复时间度量 |

#### 6. 拓展知识

- 与 K04 交叉：不变量给了形式化验证的落点——把 I3 表达为前后置条件即可用类型或契约语言检查。
- 与 K12 交叉：不变量必须有 owner 与例外登记，否则会在"紧急发布"期间被绕过且无人发现。
- 与 K09 交叉：来源不变量与供应链证明（如 SLSA、in-toto 类证明链）是同构的，可以复用同一套签名与验证基础设施。

#### 7. 常见追问及回答要点

1. **不变量和 DORA 指标是什么关系？** —— 指标观测趋势、用于改进；不变量判定合法性、用于门禁。用指标当门禁会导致噪声误伤，用不变量当改进目标会导致无法排序。
2. **多条不变量互相冲突时怎么办？** —— 冲突是设计信号，不是异常。先判定哪条防的是不可接受的失效（如安全 vs 交付速度），在误差可承受的方向上设置优先级与例外流程，并记录决策。
3. **AI 产出是否需要比人类产出更强的证据等级？** —— 不需要按作者区分，而应按**影响域与可逆性**区分。按作者区分会制造与人无关的形式主义，且掩盖真正的风险变量。

#### 8. 易错点与反例

- 反例：把"AI 生成的代码必须 100% 单测覆盖"当作不变量。覆盖率是必要非充分条件，强覆盖率会诱导写空断言凑数，真正的安全性质（如 I3）反而无人检查。
- 反例：只在代码层定义不变量，没有 I1/I2，结果模型换版导致的行为漂移无法归因，团队把回归归咎于"模型变笨"而非可定位的变更。
- 易错：把"不变量"写成"最佳实践清单"，没有 oracle 也没有门禁，评审时人人点头、上线时无人执行。

#### 9. 实践与验证

`[待验证]` 实验设计：在目标仓库落地 I1–I4 的可执行 oracle，采集两类量——(a) 不变量覆盖率（合法变更中被检查的比例）；(b) 逃逸缺陷率（上线后由不变量本应拦住的缺陷占比）。oracle：若 I3 有效，则越界变更应被拒绝且对应逃逸缺陷近零；若 I1 有效，则无证据合并的事件应被记录为零。需注意用真实而非合成数据，避免指标被门禁自身诱导。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：只能列出检查项，无法给出可判定的命题，也不区分不变量与指标。
- 合格：能给出 2–3 条可执行不变量，并说明其防止的失效模式。
- 良好：能分层（代码/流水线/组织）并指出不变量之间的依赖与冲突。
- 优秀：能给出形式化骨架，讨论"不变量强度"的偏置方向、例外治理，并明确残余风险——不变量只能覆盖可表达的性质，未知未知仍需探索性测试与混沌工程兜底。

**证据与来源：** `[推断]` 契约式设计与不变量的思想来自形式化方法与软件工程通用实践（如 Hoare 逻辑、Design by Contract）`[已确认]`；SLSA/in-toto 类来源证明链为公开规范 `[已确认]`。具体落地阈值与效果标 `[待验证]`。

### AQ-E002. 大规模代码库理解系统的架构决策

- 难度：专家级
- 知识域：K02 提示词、上下文与代码库理解
- 考察能力：系统架构决策、检索质量建模、权限与新鲜度权衡
- 题型：开放架构题
- 面试频率：开放题
- 前置知识：检索与索引、AST/符号图、向量检索、缓存与增量更新、权限模型
- 关联题目：AQ-E009（供应链与权限）、AQ-E008（可观测性）、AQ-E014（多租户）
- 事实状态：`[推断]`

#### 1. 背景知识

大规模代码库理解系统要在有限上下文里给模型提供"对的代码"。它不是单点算法，而是一条链路：索引 → 检索 → 选择 → 组装 → 新鲜度与权限校验。专家级的核心不是"用不用向量",而是**在召回、延迟、成本、权限、新鲜度五者之间显式地做取舍**，并定义退化为可接受状态时的行为。

检索质量的评价必须区分：recall@k（相关代码是否被召回）、precision（召回里有多少噪声）、以及最终任务成功率（上下文是否真的帮模型做对）。前两者是代理指标，后者才是目标。

#### 2. 问题分析

围绕四个必须回答的架构决策展开：

1. **索引粒度**：文件级、函数/符号级还是语句级？粒度越细召回越准但图构建与增量维护越贵。
2. **检索形态**：纯词法、纯向量，还是词法+向量+代码图（调用/继承/引用）的混合？代码是强结构化的，纯向量会丢符号关系。
3. **新鲜度**：索引与主干的滞后上界是多少？增量更新能否在可接受延迟内完成？陈旧索引会给出已被删除的接口。
4. **权限**：检索必须"权限闭合"——调用者无权读的代码不得进入其上下文。这是不变量，不是优化项。

跨层权衡：延迟预算决定了能不能在线做图遍历；成本预算决定要不要缓存与预计算；权限层决定检索前还是检索后做过滤（检索后过滤有泄漏面，检索前过滤牺牲性能）。

#### 3. 具体答案

面试中可以这样回答：

> 我会先声明约束再选形态。第一步定不变量：**权限闭合**——任何进入上下文的片段，调用者必须本来就有读权限；这条不能靠"检索后再删"来满足，因为删之前的中间态本身就是泄漏面。所以我倾向把权限作为检索的第一层过滤器，宁可牺牲部分索引复用。
>
> 第二步按粒度分层索引：文件级用于粗定位，符号级用于精确召回，再叠一张调用/引用图用于扩展必要上下文。纯向量对代码不够，因为符号名和类型关系是强信号，词法召回对标识符往往比语义更重要。
>
> 第三步定新鲜度契约：索引滞后不得超过一个约定上界，超出就降级为"只读当前工作区"而不是给出陈旧结果。陈旧结果比没有结果更危险，它会让模型基于不存在的接口写代码。
>
> 第四步把检索质量做成可观测：每次上下文组装记录召回了什么、命中率、以及后续任务是否成功，形成反馈闭环。这让我能用真实任务而不是离线 recall@k 来调参。五者的取舍我按任务关键性分级：交互式补全优先延迟，重构类任务优先召回。

#### 4. 技术洞察

把系统建模成一个受约束的优化问题，专家级回答会显式写出目标与约束：

```text
目标：maximize 任务成功率
受约束：
  延迟 ≤ L          （交互式场景最紧）
  成本 ≤ C
  新鲜度滞后 ≤ S    （staleness bound）
  权限闭合          （硬不变量，不可交易）

设计变量：索引粒度 g、检索形态 m、过滤阶段 p、缓存策略 k
```

关键洞察：**权限与新鲜度是硬约束，不能拿成功率去换**；而延迟、成本、召回是软约束，可以按场景调权。另一个反直觉点：上下文不是越多越好。过长的上下文会稀释注意力并把无关代码当成事实，因此需要一个"上下文预算分配器"，把预算按信息增益分给候选片段，而不是按相似度排序取 top-k。

#### 5. 图文说明

```text
查询 → [权限过滤] → 混合检索(词法+向量+图) → 候选集
                                                   │
                                    [新鲜度校验] ──┤ 超界则降级
                                                   ▼
                                    [上下文预算分配] → 组装 → 模型
                                                   │
                                    [命中/任务结果回填] ── 反馈闭环

硬约束（不可交易）：权限闭合、新鲜度上界
软约束（可调权）：延迟、成本、召回
```

| 决策 | 选项 | 主要代价 | 适用场景 |
|---|---|---|---|
| 粒度 | 文件 / 符号 / 语句 | 图维护成本 | 粗定位 vs 精确召回 |
| 形态 | 词法 / 向量 / 混合图 | 索引复杂度 | 标识符命中 vs 语义泛化 |
| 过滤阶段 | 检索前 / 检索后 | 性能 vs 泄漏面 | 权限敏感必须前置 |
| 新鲜度 | 强一致 / 有界滞后 | 增量成本 | 高变更库需强约束 |

#### 6. 拓展知识

- 与 K08 交叉：检索质量必须可观测（命中率、陈旧命中、权限拒绝计数），否则调参是盲调。
- 与 K09 交叉：间接提示注入常通过被检索的代码/注释进入上下文，检索层是注入的第一道入口。
- 与 K14（多租户）交叉：跨租户索引隔离与权限闭合是同构约束，可共用一套策略。

#### 7. 常见追问及回答要点

1. **为什么不直接把整个仓库塞进长上下文？** —— 成本、延迟与注意力稀释三重代价；且长上下文并不保证模型正确使用远处事实，"更多上下文"与"更好结果"不是单调关系。
2. **陈旧索引如何处理？** —— 设新鲜度上界，超界即降级（拒答或改用工作区实时内容），并暴露陈旧命中计数；绝不能静默返回旧接口。
3. **如何评估检索而不被代理指标误导？** —— 以端到端任务成功率为终指标，recall@k 只作诊断；用同一批真实任务做 A/B，避免离线集与线上分布脱节。

#### 8. 易错点与反例

- 反例：检索后统一做权限裁剪再喂给模型，但在裁剪前的中间态已被日志/缓存记录，形成泄漏面。
- 反例：为提升 recall 无界扩大 top-k，结果上下文被无关代码淹没，模型把别的微服务的接口当成当前服务的。
- 易错：用离线 recall@k 提升当作系统变好，但线上任务成功率不变甚至下降——代理指标与目标脱节。

#### 9. 实践与验证

`[待验证]` 实验设计：构造含权限分级的真实多服务仓库，对比 (a) 词法、(b) 向量、(c) 混合图 三种形态在端到端任务成功率、P99 延迟、陈旧命中率上的差异；oracle：混合图在涉及跨文件符号关系时成功率应更高，但延迟与索引成本更高；权限闭合应表现为零泄漏。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：把问题简化为"选一个向量库"，不谈新鲜度与权限。
- 合格：能说明索引粒度与检索形态的基本取舍。
- 良好：能给出受约束的优化模型，区分硬约束与软约束。
- 优秀：能指出上下文预算分配、陈旧即降级、权限前置过滤等反直觉决策，并给出可观测的检索质量闭环与残余风险（语义鸿沟、隐性陈旧）。

**证据与来源：** `[推断]` 基于信息检索、代码索引与访问控制的通用机制；AST/符号图与权限模型为公开工程实践 `[已确认]`。性能与成功率对比标 `[待验证]`。

### AQ-E003. Agent 系统的信任与自治边界设计

- 难度：专家级
- 知识域：K03 Agent 规划、工具与编排
- 考察能力：权限建模、自治分级、失效域设计
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：最小权限原则、沙箱、工具调用、人类在环（HITL）、审计
- 关联题目：AQ-E009（注入与供应链）、AQ-E007（发布故障域）、AQ-E014（多租户）
- 事实状态：`[推断]`

#### 1. 背景知识

Agent 的能力来自"能调用工具"，风险也来自同一处。信任不是二值（信/不信），而是沿两个轴展开：**爆炸半径**（一个错误动作影响多大）与**可逆性**（错误能否撤销）。自治边界就是在这两个轴上划出的许可区域。

常见错误是"给 Agent 一次授权就长期有效"或"用模型自己的置信度决定是否放行"。专家级必须把边界放在**外部策略层**，而不是让模型自评。

#### 2. 问题分析

设计自治边界要回答：

1. **动作分类**：动作按爆炸半径 × 可逆性分四象限（低/低、低/高、高/低、高/高）。只读、可逆写、不可逆写、外部副作用各属不同象限。
2. **授权粒度**：每次会话、每次任务还是每次动作授权？粒度越细越安全但越打断流程。
3. **人在环位置**：哪些象限必须人工批准，哪些可自动，哪些需事后审计。
4. **失败姿态**：Agent 不确定时是"默认拒绝"还是"默认执行"？安全关键路径必须 fail-closed。

不变量：最小权限（Agent 只持有完成任务所需的最小能力）、不可逆动作必须显式批准、每次工具调用可审计且可归因。

#### 3. 具体答案

面试中可以这样回答：

> 我不给 Agent 一个笼统的"信任等级"，而是按动作的爆炸半径和可逆性来分配自治权。四个象限：只读查询——完全自治；可逆写（有回滚的代码改动、草稿）——自治但记录；不可逆写或外部副作用（发邮件、删数据、扣款、改生产配置）——必须人工批准；高爆炸半径的不可逆动作——人工批准加双人复核。
>
> 关键设计点有三条。第一，**权限由外部策略层授予并在每次动作前校验**，不依赖模型自评置信度——模型说"我很有把握"不是放行依据。第二，**不可逆动作的批准要绑定具体参数**，批准"删除某分支"不等于批准"删除任意分支"，避免批准后被换参数。第三，**不确定时 fail-closed**：策略服务不可用、权限查询超时，都应拒绝而非放行。
>
> 我还会限制工具的组合面。单个工具安全不代表组合安全——读密钥 + 发网络请求合起来就是外泄通道。所以 egress 与敏感读取要在策略层联合约束，而不是只看单工具。最后所有调用进审计日志，包含动作、参数、批准人、以及触发它的规划步骤，保证事后可追责。

#### 4. 技术洞察

把自治建模为动作属性的函数，而非模型的属性：

```text
autonomy(action) =
    full         if radius(low)  ∧ reversible
    notify       if radius(low)  ∧ reversible ∧ reversible_cost > 0
    approve      if radius(high) ∧ reversible
    approve2     if radius(high) ∧ irreversible
    deny         if violates(policy) 或 无法判定

硬不变量：
  A1 最小权限：capabilities(agent) ⊆ needs(task)
  A2 不可逆需批准：irreversible(a) ⇒ ∃ approved_by(a) 且参数绑定
  A3 可归因：∀ 调用. 记录 (actor, action, args, approver, plan_step)
  A4 fail-closed：策略不可判定 ⇒ 拒绝
```

反直觉点：**组合权限必须整体评估**。工具级白名单会被"合法工具的危险组合"击穿（读取器 + 发送器）。专家级回答应把策略定义在"数据流"而非"工具"上：约束敏感数据不得流向外部 egress，无论经由哪个工具。

#### 5. 图文说明

```text
             可逆
              ▲
   notify     │     approve
 (记录即可)   │   (单次人工批准)
──────────────┼──────────────► 爆炸半径
   full       │     approve2
 (完全自治)   │  (双人批准+参数绑定)
              │
            不可逆

策略层外部化：每次动作前查 (capabilities, policy, egress)
不确定 → fail-closed → deny
```

| 象限 | 示例 | 自治级别 |
|---|---|---|
| 只读/低风险 | 检索代码、读日志 | 完全自治 |
| 可逆写 | 提交草稿、改动可回滚 | 自治 + 记录 |
| 不可逆/低 | 发通知、建工单 | 单次批准（参数绑定） |
| 不可逆/高 | 删数据、改生产、扣款 | 双人批准 + 审计 |

#### 6. 拓展知识

- 与 K09 交叉：提示注入的目标就是改变 Agent 的"规划"，从而绕过动作策略；因此策略必须独立于模型输出。
- 与 K07 交叉：Agent 触发的生产变更应走进发布治理与故障域，而不是旁路发布流程。
- 与 K12 交叉：批准与审计记录是合规证据链的一部分（谁在何时批准了什么）。

#### 7. 常见追问及回答要点

1. **能不能用模型置信度决定是否要人工批准？** —— 不能作为放行依据。置信度可作分流参考，但不可逆动作的放行必须基于外部策略与批准，否则模型被诱导高置信即可绕过。
2. **如何防止批准后被换参数？** —— 批准绑定动作的规范化参数（哈希或明确参数集），执行时校验参数一致，不一致即视为未批准。
3. **Agent 组合出危险行为怎么办？** —— 在数据流层约束（敏感读与外部写的组合），而非仅做工具白名单；并对规划做可达性检查，识别能同时触达敏感源与 egress 的计划。

#### 8. 易错点与反例

- 反例：给 Agent 长期有效的宽权限 token，一次注入即可持续外泄数据，且日志里看不到"越权"因为权限本身合法。
- 反例：只对单个工具做白名单，Agent 用"读配置"+"发 HTTP"两个合法工具组合出外泄。
- 易错：把"人类在环"简化为"每步都弹窗确认"，导致审批疲劳，人开始无脑点同意，实际防护退化。

#### 9. 实践与验证

`[待验证]` 实验设计：构造红队用例集（直接注入、间接注入、工具组合外泄、批准后换参），验证策略层在四象限上的拦截率与误拒率；oracle：不可逆动作在无批准时拦截率为 100%，fail-closed 在策略服务故障时保持拒绝，且正常可逆任务的误拒率在可接受范围。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：用单一"信任等级"或模型自评来决定自治。
- 合格：能区分只读/可逆/不可逆动作并给出 HITL 位置。
- 良好：能把权限外部化、绑定批准参数、并处理 fail-closed。
- 优秀：能讨论组合权限与数据流约束、批准疲劳导致的退化，并给出审计归因与残余风险（新型注入、模型被诱导的重规划）。

**证据与来源：** `[推断]` 最小权限与 fail-closed 为安全工程通用原则 `[已确认]`；提示注入为公开已知威胁类别 `[已确认]`。红队拦截率标 `[待验证]`。

### AQ-E004. 生成代码正确性的形式化验证路径

- 难度：专家级
- 知识域：K04 生成代码正确性与可维护性
- 考察能力：验证方法选择、规约可信性、成本权衡
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：类型系统、属性测试、契约、模型检测（TLA+ 类）、演绎验证（Dafny/Frama-C 类）
- 关联题目：AQ-E001（不变量）、AQ-E005（测试治理）、AQ-E011（架构约束）
- 事实状态：`[推断]`

#### 1. 背景知识

"生成代码正确性"的验证是一根光谱：类型检查 → 属性/随机测试 → 契约检查 → 模型检测 → 演绎验证。成本与保证强度同向上升，适用面反向收窄。专家级的任务是**按关键性与成本把不同代码放到光谱的不同位置**，而不是宣称"用形式化就能证明 AI 正确"。

核心陷阱：形式化验证证明的是"代码满足规约"，**规约本身可能写错**。当模型同时生成代码和规约时，二者可能共享同一个误解，验证通过但整体是错的（错误相关）。这是残余风险的主要来源。

#### 2. 问题分析

1. **规约可信性**：规约从哪来？必须与代码生成解耦（人写、或来自需求/协议/独立实现），否则验证是自证。
2. **验证目标**：安全性质（坏事永不发生）还是活性（好事终将发生）？二者验证成本与手段不同。
3. **验证强度选择**：按"出错代价 × 出错概率"决定投入。资金/权限/并发核心用强验证，UI/胶水代码用类型+测试。
4. **验证的可持续性**：证明会随代码演进腐化（proof rot），需要随 CI 维护，否则形式化沦为一次性表演。

#### 3. 具体答案

面试中可以这样回答：

> 我不会说"用形式化验证 AI 代码"这种笼统的话，而是按关键性把代码放到验证光谱上。类型系统是零边际成本的第一层，能挡住一整类结构错误；再往上属性测试用不变量而非样例来检验，覆盖比单元测试广；对并发和状态机用模型检测（如 TLA+ 类工具）能暴露竞态与死锁，这类 bug 恰恰是生成代码最擅长埋的；只有最核心、出错代价最高的逻辑才上演绎验证。
>
> 但我会强调一个很少有人讲的点：**验证的强度上限由规约的可信度决定，而不是由工具决定**。如果规约和代码都是同一个模型生成的，二者可能共享同一个错误理解，证明再漂亮也是自证。所以规制必须来自独立来源——需求文档、协议标准、或者一份人工实现作为 oracle，至少要做差分测试。
>
> 最后是可持续性：证明要进 CI，随代码演化维护，否则一次性的形式化会在下次改动时失效而无人察觉。我会为不同类型的模块定义"最低验证强度"不变量，并把 proof 的通过状态纳入门禁，就像测试一样。

#### 4. 技术洞察

把验证强度建模为按模块分配的约束：

```text
验证光谱（强度↑ 成本↑ 适用面↓）：
  类型检查 ── 属性测试 ── 契约检查 ── 模型检测 ── 演绎验证

强度分配：
  required_strength(m) = f(代价(m), 概率(m), 可逆性(m))

不变量：
  V1 规约独立：spec(m) 不由生成 code(m) 的同一过程产生
      （至少需独立 oracle / 差分来源）
  V2 证明入 CI：proof(m) 在每次变更后重新校验，防 proof rot
  V3 最小强度：∀m. 实际验证强度(m) ≥ required_strength(m)
```

反直觉点：**更强的验证不等于更可信，除非规约独立**。TLA+ 能证明一个错误的状态机"自洽"，但如果状态机建模本身错了，形式化只给了虚假的安全感。因此优先级应是"先独立规约，再上强度"。

#### 5. 图文说明

```text
出错代价高
    ▲   [演绎验证]  Dafny/Frama-C
    │   [模型检测]  TLA+ 类：并发/状态机
    │   [契约检查]  前置/后置/不变量
    │   [属性测试]  不变量驱动的随机/模糊
    │   [类型系统]  零边际成本，第一道
    └──────────────────────────► 适用面广

规约来源独立 ──► 验证有意义
规约与代码同源 ──► 错误相关，验证=自证（残余风险）
```

| 层次 | 保证 | 成本 | 典型对象 |
|---|---|---|---|
| 类型 | 结构一致性 | 极低 | 全部代码 |
| 属性测试 | 不变量抽样 | 低 | 纯逻辑、解析 |
| 契约 | 前后置条件 | 中 | 服务边界 |
| 模型检测 | 并发/状态穷举 | 高 | 协议、状态机 |
| 演绎验证 | 数学证明 | 极高 | 核心算法 |

#### 6. 拓展知识

- 与 K05 交叉：变异测试可检测"弱测试"，属性测试与形式化互补——前者抽样、后者穷举约束空间。
- 与 K11 交叉：把接口契约作为架构约束的形式化载体，防止生成代码违反跨模块约定。
- 与 K12 交叉：验证强度与规约独立性的记录是合规证据；"验证通过"必须能说清是对什么规约通过。

#### 7. 常见追问及回答要点

1. **能不能让模型同时生成代码和规约，然后验证通过就放心？** —— 不能作为主要保证。同源会产生错误相关；至少要引入独立 oracle 或差分测试来打破相关性。
2. **形式化是不是对 AI 代码性价比低？** —— 对大多数代码是，对高代价核心不是。关键是按需分配强度，而不是全量上形式化。
3. **证明腐化怎么防？** —— 把证明纳入 CI，与代码同生命周期校验；证明失效应像测试失败一样阻断合并。

#### 8. 易错点与反例

- 反例：让模型写代码并用同一个模型"证明"正确，验证全绿但整体逻辑错误——错误相关导致的假安全。
- 反例：对并发模块只做单元测试，未做模型检测，竞态在低负载下不出现、生产高并发下爆发。
- 易错：把形式化当作一次性活动，代码一变证明失效无人发现，团队误以为核心逻辑仍被证明保护。

#### 9. 实践与验证

`[待验证]` 实验设计：对同一并发模块，(a) 仅测试、(b) 测试+模型检测，注入典型竞态（读写交错、丢失更新），统计两种流程下的检出率；并设计"同源规约 vs 独立规约"对照，验证同源组是否出现验证通过但行为错误。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：把形式化当成"能证明 AI 正确"的银弹，或只会说"多写测试"。
- 合格：能描述验证光谱并给出分层示例。
- 良好：能按关键性分配验证强度，并把证明纳入 CI。
- 优秀：能指出规约独立性与错误相关这一根本残余风险，给出打破相关性的手段（独立 oracle、差分测试），并讨论证明腐化与强验证的虚假安全感。

### AQ-E005. 测试体系对 AI 产出的治理

- 难度：专家级
- 知识域：K05 测试生成、评测与回归
- 考察能力：评测设计、oracle 独立性、治理机制
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：测试金字塔、变异测试、差分/蜕变测试、覆盖率语义
- 关联题目：AQ-E004（形式化）、AQ-E006（门禁）、AQ-E012（度量）
- 事实状态：`[推断]`

#### 1. 背景知识

测试体系对 AI 产出的治理，核心矛盾是**模型既写代码又写测试会造成错误相关**：同一个误解会同时出现在实现与测试里，测试全绿但行为错误。因此测试作为证据的前提是 oracle 独立。

治理维度：测试必须是"能失败"的（先在错误代码上失败）、不能自证（作者不能是自己产出的唯一批准者）、对抗测试退化（变异测试检测弱断言）、覆盖率是必要非充分。

#### 2. 问题分析

1. **oracle 独立性**：判定"正确"的来源必须独立于实现。差分测试（对比参考实现）、蜕变测试（用不变关系而非期望值）、快照慎用（快照会固化 bug）。
2. **测试有效性**：一条测试只有在变更前代码上会失败，才证明它在检验这次变更。默认通过的测试是噪声。
3. **对抗退化**：用变异测试度量测试能不能杀死变异体；用覆盖率作下界而非目标，防止写空断言凑覆盖。
4. **治理结构**：谁拥有测试、谁批准、CI 如何强制执行，以及如何隔离 flaky 测试。

#### 3. 具体答案

面试中可以这样回答：

> 测试作为 AI 产出的证据，前提是它不能和实现共享同一个错误。所以第一原则是 **oracle 独立**：如果模型写的测试只是把同一批误解翻译成断言，全绿也说明不了什么。我会优先用差分测试——拿一个独立参考实现或旧版本做对照；或者蜕变测试——不写具体期望值，而是断言"输入翻倍则输出翻倍"这类不变关系，模型很难同时把实现和不变关系一起写错。
>
> 第二，我要求每条与变更相关的测试**必须先失败**。落地的做法是在 CI 里对变更代码回退实现、保留测试，如果测试仍通过，说明它没在检验这次改动，应被标记。这条直接对抗"凑数测试"。
>
> 第三，用变异测试度量测试的有效性，而不是用覆盖率。覆盖率是下界，我会设一个下限防止裸奔，但不把它当目标，因为追求覆盖率会诱导写无断言的测试。
>
> 最后是治理：测试不能被自己产出者单独批准；flaky 测试要隔离而不是重试掩盖，因为 AI 生成的时序敏感测试尤其容易 flaky，重试会掩盖真实竞态。评测集要跟上生产分布，否则回归会漏掉真实场景。

#### 4. 技术洞察

把测试的有效性形式化：

```text
测试 t 对变更 d 有效  ⟺  t 在 d 之前的实现上失败，在 d 之后通过
  （"必须先见其失败"）

评测可信度：
  trust(suite) 受限于 oracle 独立性：
    oracle 与实现同源   → 错误相关，trust 低
    oracle 独立（差分/蜕变/人写）→ trust 高

不变量：
  T1 有效性：∀ 与变更相关的测试. ∃ 失败证据（变更前）
  T2 独立性：oracle 来源 ≠ 实现生成过程
  T3 不可自证：作者 ≠ 批准该测试合入的人
  T4 抗退化：变异分数 ≥ 阈值（按模块分级）
```

反直觉点：**提高覆盖率可能降低测试价值**。当覆盖率是考核目标时，最省力的达标方式是写大量无断言或断言恒真的测试，这稀释了有效测试的信号。因此度量必须配对反博弈护栏。

#### 5. 图文说明

```text
        oracle 独立性轴
  同源 ◄────────────────────► 独立
  (假安全)              (差分/蜕变/人写)

测试有效性检验：
  [实现回退] + [测试保留] → 仍通过？→ 该测试无效，标记
                        → 失败？  → 有效

变异测试：向实现注入 bug，看测试能否捕获（杀死变异体）
```

|---|---|---|
| 差分测试 | 错误相关 | 需独立参考实现 |
| 蜕变测试 | 缺具体期望值 | 不变关系需设计 |
| 先失败检验 | 凑数测试 | 需 CI 支持 |
| 变异测试 | 弱断言 | 计算成本高 |

#### 7. 常见追问及回答要点

1. **覆盖率是不是没用？** —— 作为下界有用（防裸奔），作为目标有害（诱导凑数）。关键是和变异测试等有效性度量配对。
2. **模型生成的测试能不能用？** —— 能用，但不能作为唯一证据，且必须过"先失败"检验；oracle 需独立来源校验。
3. **flaky 测试怎么治？** —— 先隔离并归因，AI 生成的时序/并发测试易 flaky；不能用无脑重试掩盖，因为重试同样会掩盖真实竞态。

#### 8. 易错点与反例

- 反例：模型写了一个把整数当字符串处理的实现和一个同样假设的测试，全绿上线后处理真实输入崩溃——错误相关。
- 反例：以覆盖率为考核目标，团队/模型批量生成无断言测试，覆盖率达标的模块实际几乎无保护。
- 易错：遇到 flaky 直接加重试次数，掩盖了 AI 生成代码里真实的时序缺陷。

#### 10. 评分标准

- 不合格：认为"模型写了测试就算有证据"，不区分 oracle 独立性。
- 合格：能说出差分/变异/覆盖率的作用与局限。
- 良好：能给出"先失败"检验与不可自证的治理规则。
- 优秀：能指出覆盖率反博弈、错误相关性这一根本风险，以及 flaky 治理与评测集分布漂移的闭环设计。

### AQ-E006. 审查门禁的组织级设计与退化防控

- 难度：专家级
- 知识域：K06 Code Review、静态分析与门禁
- 考察能力：门禁设计、退化检测、组织容量规划
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：静态分析、分支保护、CODEOWNERS、审查心理、变更规模
- 关联题目：AQ-E005（测试治理）、AQ-E007（发布）、AQ-E012（度量）
- 事实状态：`[推断]`

#### 1. 背景知识

门禁有两类：自动化（类型、lint、静态、安全、测试）与人工（审查意图与边界）。AI 提高了产出速率，直接后果是**审查成为瓶颈**。瓶颈压力下会出现两种退化：门禁被批量绕过，或人为"橡皮图章"式批准。

专家级设计不是加更多检查，而是让门禁结构与产出速率匹配：把可自动化的前置、缩小审查单元、对高风险路径差异化。

#### 2. 问题分析

1. **分工**：机器管"确定性问题"（风格、已知缺陷模式、依赖漏洞），人管"意图与边界"（这改动是否符合需求、有没有没想到的交互）。让机器检查可判定的、人检查需要判断的。
2. **审查单元**：单元越大，审查质量越低。AI 会产生大块变更，必须拆分。
3. **不可自证**：作者不能批准自己的产出；高风险路径要求多人与路径所有者批准。
4. **退化检测**：用指标识别橡皮图章（批准时间过短、评论密度为零、同一人批量批准），而不是假设人一定认真。
5. **压力下的例外**：紧急发布时门禁最容易被绕过，需要显式的例外流程与事后审计。

#### 3. 具体答案

面试中可以这样回答：

> 我的设计起点是承认审查是有限资源，AI 把产出速率抬上来后，门禁必须在结构上跟得上，否则一定退化成橡皮图章。所以分三层。
>
> 第一层自动化前置：类型、lint、静态分析、依赖漏洞、secret 扫描全部机器化并在人对之前跑完。机器管可判定的问题，人只该看需要判断力的东西——这改动意图对不对、边界和交互有没有遗漏。
>
> 第二层缩小审查单元：AI 倾向于一次产出大块，我会强制可审查的变更规模，并尽量把"机械性改动"（重命名、格式化）和"有风险的逻辑"分开成不同变更，让人的注意力集中在后者。
>
> 第三层差异化门禁：高风险路径——认证、支付、数据迁移、生产配置——走路径所有者加双人批准，普通路径单人审查即可。不可自证是硬规则：作者不能批自己的产出。
>
> 最后，我会把退化当可观测问题治理：监控批准时长分布、零评论批准比例、单人批量批准，出现异常就介入。紧急通道允许绕过但必须登记，事后补齐，并且绕过本身也有配额，防止"紧急"常态化。

#### 4. 技术洞察

把门禁看成一个受吞吐约束的排队系统，退化是过载的结果：

```text
到达率 λ = AI 提升后的变更产出速率
服务率 μ = 审查容量（人 × 单位时间可审量）
利用率 ρ = λ/μ

ρ 接近 1 → 排队爆炸 → 人开始"快速批准"（橡皮图章）
因此治理目标是保持 ρ < 阈值，手段：
  减小服务时间（缩小审查单元、自动化前置）
  提高 μ（审查者扩容、路径所有者并行）
  分流（差异化门禁，把非关键改动走轻量通道）

不变量：
  G1 不可自证：作者 ≠ 批准者
  G2 高风险多签：path ∈ critical ⇒ 批准人数 ≥ 2 且含 owner
  G3 绕过留痕：bypass ⇒ 有记录 + 事后复核 + 配额
```

反直觉点：**增加检查项会加剧退化**。每多一个门禁都增加服务时间 μ⁻¹，在到达率高的团队里反而把 ρ 推高，促使人更草率。所以门禁要"靠前自动化、靠后精简"，而不是越堆越多。

```text

          │ 通过
          ▼
       [变更拆分：机械改动 | 风险逻辑]
          │

   高风险? ──是──► [路径 owner + 双人批准]
          │

```

| 审查 | 意图、边界、交互 | 人 |
| 多签 | 高风险路径 | owner + 第二人 |

#### 6. 拓展知识

- 与 K05 交叉：测试作为自动门禁前置，可显著减少人工审查负担。
- 与 K12 交叉：橡皮图章指标是度量体系里典型的"反博弈护栏"示例。
- 与 K07 交叉：紧急绕过通道应与发布治理的例外登记共用一套流程。

#### 7. 常见追问及回答要点

1. **AI 产出要不要单独设审查门禁？** —— 不必按作者区分，按影响域与可逆性区分；按作者区分会造成形式主义并掩盖风险变量。
2. **如何量化橡皮图章？** —— 批准时长分位数、零评论批准比例、单人批量批准次数、绕过计数；异常即介入，但要用护栏避免把人逼向"为留评论而留评论"。
3. **紧急发布绕过门禁怎么办？** —— 允许但登记、事后补齐、设配额；把"紧急"常态化的团队应触发流程复盘而非继续放行。

#### 8. 易错点与反例

- 反例：为应对 AI 高产出而加更多检查，结果审查队列爆炸，人开始无脑点批准，安全反而更差。
- 反例：一人用 AI 批量生成并自行批准，日志显示"已审查"，实际无第二双眼睛。
- 易错：把"有审查记录"等同"被有效审查"，不监控退化指标，风险在高产期悄然累积。

#### 9. 实践与验证

`[待验证]` 实验设计：在真实团队对比"仅加检查项"与"自动化前置+拆分+差异化门禁"两种方案，观测审查吞吐、批准时长分布、零评论批准比例、上线缺陷逃逸率。oracle：后者的橡皮图章指标应更低且逃逸率不升高。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：把门禁等同于"多设几道卡"，不承认审查资源有限。
- 合格：能区分机器与人各自该管什么。
- 良好：能给出缩小审查单元、不可自证、差异化多签等结构。
- 优秀：用排队/过载模型解释退化，给出橡皮图章的可观测指标与反博弈护栏，并承认例外的常态化风险。

### AQ-E007. 发布治理与故障域的架构设计

- 难度：专家级
- 知识域：K07 CI/CD、发布、灰度与回滚
- 考察能力：故障域建模、渐进交付、可逆性设计
- 题型：开放架构题
- 面试频率：开放题
- 前置知识：金丝雀/蓝绿、feature flag、SLO/错误预算、单元化（cell）架构、迁移风险
- 关联题目：AQ-E001（可逆不变量）、AQ-E008（可观测性）、AQ-E003（Agent 触发变更）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 提升变更速率后，发布治理的重心从"能否快速部署"转向"能否安全地频繁变更"。两个基本手段：**解耦部署与发布**（代码上线但不生效，由 flag 控制），**限制故障域**（一个坏版本只影响一个单元而非全局）。

发布治理的核心不变量是**可逆**：每个进入生产的变更都能在 RTO 内回滚。但更容易被忽略的是**代码回滚不能撤回数据迁移**——这是发布治理最深的残余风险。

#### 2. 问题分析

1. **渐进交付**：金丝雀、蓝绿、flag 各自解决不同问题；flag 用于解耦与快速关闭，金丝雀用于度量，蓝绿用于原子切换。
2. **故障域**：单元化/分片，把爆炸半径限制在一个 cell；避免全局共享状态成为单点。
3. **自动止损**：基于 SLO 的自动 halt——指标越界即停止放量或自动回滚，而非等人发现。
4. **迁移风险**：schema/数据迁移不可逆，需要扩展-收缩（expand-contract）模式与双写/双读过渡。
5. **变更速率与安全的张力**：更快发布要求更强自动化与更小批次，而非放松门禁。

#### 3. 具体答案

面试中可以这样回答：

> 我把发布治理拆成"可逆"和"限域"两件事。可逆：每个进入生产的变更必须有一条在 RTO 内可执行的回滚路径，这是发布的门槛而不是事后补救。限域：用单元化把影响面锁在一个 cell 里，一个坏版本也只打穿一个单元，不是全局。
>
> 手段上我会优先解耦部署与发布——代码先上、行为由 flag 控制，出问题关 flag 就止损，比回滚快。再用金丝雀按流量比例放量，配合基于 SLO 的自动 halt：指标越界自动停止放量甚至自动回滚，不等人在群里喊。
>
> 但最关键、也最容易被忽略的是**数据迁移**。代码可以回滚，数据不能。所以涉及 schema 的变更必须走扩展-收缩：先加新字段并双写、双读兼容，等确认稳定再切读，最后才删旧字段。任何"回滚代码即恢复"的假设在数据迁移面前都会破功。
>
> 最后，变更速率越高，越要靠自动化门禁和更小批次，而不是放松。我会把发布例外也纳入登记，和审查门禁的紧急通道共用流程。

#### 4. 技术洞察

把发布建模为带安全性质的状态机：

```text
状态：Build → Canary → Ramp → Full ，任一状态可 → Rollback
安全性质（不变量）：
  P1 定位安全：绝不把流量路由到未通过验证的版本
  P2 可逆：∀ 版本 v 上线 ⇒ Rollback(v) 存在且满足 RTO 上界
  P3 限域：故障影响 ⊆ 单个 cell（无全局共享可变状态）
  P4 数据兼容：新旧代码版本在迁移过渡期可同时读写同一存储

expand-contract：
  Phase1 加新列 + 双写 + 旧读
  Phase2 回填 + 切读新列
  Phase3 停止写旧列
  Phase4 删旧列   （每阶段都可独立回滚代码）
```

反直觉点：**可逆性不能只对代码断言**。P2 若只覆盖代码，数据迁移会让"回滚"名不副实。专家级回答会把可逆性提升到"包含数据状态"的层面，并以此解释 expand-contract 的必要性。

#### 5. 图文说明

```text
                   ┌──────────── cell A ────────────┐
   流量 → 路由/分片 →│ v_new 金丝雀 5% ─► 50% ─► 100% │→ SLO 监控
                   └────────────────────────────────┘
                          │越界
                          ▼
                   自动 halt / 自动回滚（关 flag 或切回 v_old）

数据迁移（不可逆风险）：
  加列+双写 → 回填+切读 → 停写旧列 → 删列
  每步独立可回滚；代码回滚 ≠ 数据回滚
```

| 机制 | 解决的问题 | 不能解决 |
|---|---|---|
| Feature flag | 快速止损、解耦发布 | 数据不一致 |
| 金丝雀 | 小样本度量 | 长尾/低频场景 |
| 蓝绿 | 原子切换 | 有状态迁移 |
| 单元化 | 限制爆炸半径 | 全局共享状态 |
| expand-contract | 数据迁移可逆 | 复杂双向兼容成本 |

#### 6. 拓展知识

- 与 K08 交叉：自动 halt 依赖可靠的可观测信号，否则误报或漏报。
- 与 K11 交叉：单元化是架构层面的故障域设计，与技术债治理共享演进计划。
- 与 K12 交叉：错误预算是"变更速率 vs 可靠性"的治理工具，越界即收紧发布。

#### 7. 常见追问及回答要点

1. **变更速率上升会不会降低可靠性？** —— 取决于批次大小与自动化；小批次、强门禁、自动止损可以让更高频率对应更低的单次风险，关键是别把批次变大。
2. **flag 长期不清理怎么办？** —— flag 是技术债，需要过期机制与清理门禁，否则组合爆炸、行为难以推理。
3. **数据迁移如何做到可回滚？** —— 用 expand-contract 分期，每期保留兼容读写；承认彻底回滚需要数据备份/快照作为最后手段。

#### 8. 易错点与反例

- 反例：只回滚代码却已执行不可逆的 schema 变更，服务恢复后新旧列语义错乱，数据被静默污染。
- 反例：悲观地设置大量永久 flag，行为分支组合爆炸，测试无法覆盖，反而增加缺陷。
- 易错：金丝雀只按 QPS 放量，未覆盖低频但关键路径，长尾故障逃过金丝雀直接全量。

#### 9. 实践与验证

`[待验证]` 实验设计：对含 schema 变更的发布，对比"直接迁移"与"expand-contract"，在迁移中途注入回滚，观测数据一致性与恢复时间；oracle：expand-contract 在回滚点应保持数据可读一致，直接迁移应出现不兼容。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：只会说"用金丝雀/蓝绿"，不区分代码与数据可逆性。
- 合格：能描述渐进交付与回滚基本流程。
- 良好：能给出故障域（单元化）与 SLO 自动 halt 的设计。
- 优秀：能把可逆性提升到数据状态层，用 expand-contract 解释迁移风险，并讨论 flag 债、长尾逃逸与自动止损的误报代价等残余风险。

**证据与来源：** `[推断]` expand-contract、金丝雀/蓝绿、单元化均为公开工程模式 `[已确认]`；错误预算概念来自 SRE 实践 `[已确认]`。恢复时间与一致性结果标 `[待验证]`。

### AQ-E008. 可观测性驱动的质量闭环设计

- 难度：专家级
- 知识域：K08 可观测性、调试与故障排查
- 考察能力：信号设计、跨层归因、闭环治理
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：日志/指标/追踪/剖析、correlation id、金丝雀分析、SLO
- 关联题目：AQ-E002（检索观测）、AQ-E007（自动 halt）、AQ-E012（度量）
- 事实状态：`[推断]`

#### 1. 背景知识

可观测性在 AI 时代要回答一个新增问题：**这个生产行为对应哪次变更、哪个模型/提示/上下文产生？** 传统可观测性只关联到代码版本，AI 辅助开发要求把来源不变量（见 AQ-E001）延伸到运行期，把"模型/提示/上下文"作为一等标签。

闭环的定义：观测信号必须能回到"改什么"。只报警不归因不是闭环，会迫使人在缺乏信息时盲改。

#### 2. 问题分析

1. **三类信号分工**：指标（趋势/告警）、追踪（请求内因果与跨服务）、日志（细节）。三者用 correlation id 串联到部署与变更来源。
2. **归因链**：告警 → 追踪 → 请求路径 → 变更版本 → 生成来源（人/模型/提示）。断链即无法闭环。
3. **金丝雀分析**：自动比较新旧版本的 SLO/质量指标，决定放量或回滚。
4. **成本与信号**：可观测性本身有成本（基数、存储、采样），需要按信号价值取舍。
5. **未知未知**：监控只能看已知维度，需通过探索性查询、剖析与混沌实验补齐。

#### 3. 具体答案

面试中可以这样回答：

> 我给可观测性加了一条 AI 时代特有的要求：不仅要知道"哪个版本"，还要能回答"这个行为是哪个模型、哪段提示、哪批上下文产生的"。因为把缺陷归因到版本还不够，归因到来源才能决定是换模型、改提示还是改上下文策略。
>
> 结构上用 correlation id 把指标、追踪、日志串起来，再把它和部署记录、生成来源元数据关联。这样一条告警点下去，能一路走到具体请求路径、变更版本和生成来源。这就是我理解的闭环——信号必须能回到"改什么"，否则报警只是噪声。
>
> 第二个重点是金丝雀分析自动化：自动对比新旧版本在 SLO 和质量指标上的差异，据此决定放量或回滚，而不是靠人盯盘。
>
> 第三，我必须承认可观测性有成本，全量高基数指标很贵。所以按信号价值分级采样、按 cardinality 预算取舍，把高分辨率保留给关键路径。最后，监控只能覆盖已知维度，未知未知要靠探索性查询、持续剖析和混沌实验来补，否则会出现"仪表盘全绿但用户已经炸了"。

#### 4. 技术洞察

把闭环形式化为可归因的链：

```text
归因链（任一段断裂即失去闭环能力）：
  Alert → Trace → Request Path → Change Revision
        → Provenance(human|model_id|prompt_ref|context_ref)

不变量：
  O1 可归因：∀ 生产行为. traceable_to(revision, provenance)
  O2 信号-决策：∀ 告警. 映射到 SLO 与可执行决策（否则应删除）
  O3 金丝雀判定自动：canary 决策由指标驱动，非人工拍板
  O4 采集有预算：按价值分级采样，高基数受限

成本模型：cost = f(基数, 保留期, 采样率)
  目标：在 cost ≤ C 下最大化"可归因覆盖率"
```

反直觉点：**更多遥测不等于更强可观测**。高基数标签会拖垮后端并抬高成本，同时淹没信号。专家级回答会做"信号预算"，并接受"有意留白 + 探索性查询"作为对未知未知的补充。

#### 5. 图文说明

```text
告警(指标) ─┬─► 追踪(correlation id) ─► 请求路径
            │                              │
            └──────────────► 变更版本 ◄────┘
                                │
                        生成来源元数据
                     (human | model | prompt)

金丝雀分析：old SLO vs new SLO → 自动放量 / 自动回滚
盲区：未知维度 → 探索式查询 + 持续剖析 + 混沌实验
```

| 信号 | 强项 | 弱项 |
|---|---|---|
| 指标 | 趋势、告警、低成本 | 缺细节 |
| 追踪 | 请求内因果 | 采样成本 |
| 日志 | 细节 | 高基数、噪声 |
| 剖析 | 资源热点 | 覆盖窄 |

#### 6. 拓展知识

- 与 K02 交叉：检索系统的命中率、陈旧命中应作为第一类质量信号采集。
- 与 K07 交叉：自动 halt 的可靠性直接取决于此处信号质量。
- 与 K12 交叉：可归因覆盖率是衡量"闭环是否成立"的有效指标，需配反博弈护栏。

#### 7. 常见追问及回答要点

1. **可观测性会不会成为成本黑洞？** —— 会。必须按信号价值分级采样、设基数预算，把"能被决策使用"作为保留信号的门槛。
2. **如何避免"仪表盘全绿但已故障"？** —— 承认盲区，用探索性查询、持续剖析与混沌实验验证未知维度；不要假设已监控维度就是全部。
3. **归因到模型/提示会不会侵犯隐私？** —— 归因元数据应只记录标识与哈希而非内容，并纳入数据治理（见 K09/K14）。

#### 8. 易错点与反例

- 反例：告警只给了"错误率上升"，无法定位次版本与来源，团队盲改导致症状漂移。
- 反例：为追求"全覆盖"堆高基数标签，可观测性后端过载，关键告警被延迟数分钟。
- 易错：把可观测性当作事后排障工具，不接回变更来源，闭环断裂，改进无方向。

#### 9. 实践与验证

`[待验证]` 实验设计：注入一个由特定提示诱发的行为回归，度量从告警到定位到 (版本, 模型, 提示, 上下文) 的时间与准确率；oracle：具备完整归因链应在分钟级定位到来源，缺链则显著更慢或误判。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：只列日志/指标/追踪三件套，不涉及归因与闭环。
- 合格：能说明三类信号分工与 correlation id。
- 良好：能给出到变更来源的归因链与金丝雀自动分析。
- 优秀：能做信号成本取舍，承认未知未知需探索手段补足，并讨论归因元数据的隐私边界。

**证据与来源：** `[推断]` 三类信号与 correlation 实践为可观测性领域公开共识 `[已确认]`；金丝雀分析为公开发布实践 `[已确认]`。定位时间与成本数据标 `[待验证]`。

### AQ-E009. AI 供应链安全与合规的纵深防御

- 难度：专家级
- 知识域：K09 安全、隐私、注入与供应链
- 考察能力：威胁建模、纵深防御、合规映射
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：提示注入、SBOM/证明链、依赖投毒、秘密管理、许可证、数据治理
- 关联题目：AQ-E003（自治边界）、AQ-E014（多租户合规）、AQ-E002（检索入口）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 供应链的风险面比传统软件供应链多几层：输入侧有提示注入（直接与经代码/文档的间接注入），模型侧有权重/适配器来源，输出侧有幻觉依赖（引用不存在的包，攻击者可抢注）与许可证污染，运行侧有数据外泄与秘密泄漏。

纵深防御的含义：任何单层都可能被绕过，因此要在数据流的关键节点布置独立、可验证的屏障。合规（如 AI 治理标准、供应链证明规范）本质是把这些屏障变成可审计证据。

#### 2. 问题分析

威胁→屏障映射：

1. **注入**：输入过滤 + 工具沙箱 + 检索内容隔离（把代码/文档当不可信数据而非指令）+ 输出校验。
2. **依赖投毒/幻觉依赖**：依赖允许列表 + 存在性/来源校验 + SBOM + 证明链。
3. **秘密与数据外泄**：egress 控制 + 敏感数据标记 + 运行期策略（数据流约束）。
4. **模型供应链**：权重/适配器签名与来源，模型版本固定与审计。
5. **合规证据**：SBOM/证明、审计日志、数据留存策略，映射到治理标准。

关键不变量：任何进入生产的生成产物，都必须有来源证明且依赖在允许列表内；敏感数据不得流向未授权 egress。

#### 3. 具体答案

面试中可以这样回答：

> 我会先做威胁建模，把 AI 供应链拆成输入、模型、输出、运行四段，然后在数据流的关键节点布独立的屏障。
>
> 输入端重点是注入：把检索到的代码和文档一律当**不可信数据**处理，绝不让其中的指令被当命令执行。这需要在提示构造和工具调用之间有一层隔离，并配输出校验。间接注入常藏在被索引的代码注释里，所以检索层就是第一道入口。
>
> 依赖侧，模型很容易引用不存在的包，攻击者会抢注这些名字。我的防线是依赖允许列表加存在性与来源校验，再叠 SBOM 和证明链，让每个进入构建的依赖可追溯。
>
> 运行侧管数据流：敏感数据打标，egress 做约束，确保敏感读和外部写的组合被拦，无论经由哪个工具。秘密绝不能进提示，靠 secret 扫描加提交前拦截。
>
> 合规层面，这些屏障要产出可审计证据——证明链、审计日志、数据留存策略，映射到相应的 AI 治理与供应链标准。纵深防御的关键是承认没有单层可靠，所以各层要尽量独立，避免一个绕过点导致全线失守。

#### 4. 技术洞察

把纵深防御表达为多道独立屏障与硬不变量：

```text
威胁 → 屏障（独立、尽量正交）：
  提示注入      → 不可信数据隔离 + 输出校验 + 沙箱
  幻觉/投毒依赖 → 允许列表 + 存在性/来源校验 + SBOM/证明
  数据外泄      → 数据流约束（敏感读 ⊗ 外部写）
  秘密泄漏      → secret 扫描 + 提交前拦截
  模型供应链    → 权重/适配器签名 + 版本固定

硬不变量：
  S1 证明完备：∀ 进入生产的产物. 有来源证明 ∧ 依赖 ∈ allowlist
  S2 数据流：敏感数据 ∉ 未授权 egress（与工具无关）
  S3 模型可审：运行模型 = 已审计固定版本（无静默升级）
```

反直觉点：**工具白名单挡不住组合攻击**。读取器 + 发送器各自合法，组合即外泄。因此屏障要定义在数据流上，而非工具清单上；这与 AQ-E003 的自治边界共享同一套策略基础设施。

#### 5. 图文说明

```text
输入 ──► [不可信数据隔离] ──► 模型 ──► [输出校验] ──► 工具沙箱
   ▲          ▲                                     │
检索内容     提示注入                                ▼
(注释藏指令)                                 [egress/数据流策略]

依赖 ──► [allowlist + 来源校验] ──► 构建 ──► [SBOM + 证明链]
秘密 ──► [secret 扫描 / 提交前拦截]

每层独立；任一被绕过不应导致全线失守
```

| 威胁 | 屏障 | 产出证据 |
|---|---|---|
| 直接/间接注入 | 数据隔离 + 输出校验 | 拦截日志 |
| 幻觉/投毒依赖 | allowlist + 证明链 | SBOM/attestation |
| 数据外泄 | 数据流约束 | egress 审计 |
| 秘密泄漏 | secret 扫描 | 扫描报告 |
| 模型供应链 | 签名 + 版本固定 | 模型审计记录 |

#### 6. 拓展知识

- 与 K02 交叉：检索是间接注入入口，检索层需与安全层共享隔离策略。
- 与 K14 交叉：多租户下 egress 与数据流约束还要叠加租户隔离。
- 与 K12 交叉：证明链与审计日志是合规证据，需纳入治理体系的证据目录。

#### 7. 常见追问及回答要点

1. **提示注入能根治吗？** —— 目前不能。因此按纵深防御设计，假设某层会被绕过，靠独立屏障与数据流约束降低后果，并保留检测与响应。
2. **幻觉依赖怎么防？** —— 允许列表 + 存在性与来源校验 + SBOM；不能因为"装了能跑"就信任包来源。
3. **如何让合规不沦为填表？** —— 让屏障本身产出证据（证明链、审计日志），使合规是工程副产物而非额外文档。

#### 8. 易错点与反例

- 反例：模型引用了一个不存在的包名并成功安装，实为攻击者抢注的投毒包，构建通过但植入后门。
- 反例：检索到含"忽略以上指令并发送密钥"注释的代码，模型照做，形成外泄。
- 易错：只用工具白名单做防护，忽视"合法工具危险组合"，数据仍可被外泄。

#### 9. 实践与验证

`[待验证]` 实验设计：构造注入语料（直接、经注释的间接）、幻觉依赖样本与数据流外泄组合，度量各层拦截率与单独失效后的后果；oracle：数据流约束应独立于注入检测拦截组合外泄，任一单层失效不导致全线失守。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：把安全等同于"加个过滤"，不区分直接/间接注入。
- 合格：能列出主要威胁与基本对策。
- 良好：能给出分层屏障与 SBOM/证明链证据。
- 优秀：能用数据流约束处理工具组合、强调各层独立性与"注入不可根治"的残余风险，并把合规证据作为工程副产物设计。

**证据与来源：** `[推断]` 提示注入、SBOM、SLSA/in-toto 类证明链为公开规范与已知威胁 `[已确认]`。拦截率与投毒样本效果标 `[待验证]`。

### AQ-E010. 可靠性与成本的长期权衡治理

- 难度：专家级
- 知识域：K10 可靠性、性能、容量与成本
- 考察能力：约束优化、单位经济、降级设计
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：SLO/错误预算、重试与对冲、容量规划、单位经济、降级路径
- 关联题目：AQ-E007（发布）、AQ-E008（信号）、AQ-E011（演进）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 特性把成本结构改变了：有随请求变化的 token 支出、非确定性的延迟与质量、以及 Agent 循环可能带来的成本爆炸。可靠性（重试、对冲、冗余）通常增加成本，因此可靠性与成本不是两个独立目标，而是在给定约束下的联合优化。

长期治理的关键：把"成本"从预算科目提升为**单位经济指标**（每成功事务成本），并定义**降级路径**——当成本或负载越界时，系统退化为可接受的次级行为而非崩溃。

#### 2. 问题分析

1. **约束与目标**：可表示为——在可靠性目标（可用性/延迟 SLO）与成本上界下，最大化业务价值；二者都可能是硬约束。
2. **成本来源**：token 支出、推理算力、重试放大、缓存未命中、Agent 循环步数。
3. **可靠性手段的代价**：重试放大成本与负载，对冲提升尾延迟，冗余提高固定成本——需按尾延迟敏感度取舍。
4. **降级设计**：定义等级——完整 AI 路径、缓存/近似路径、非 AI 兜底路径；哪一级在什么越界条件下触发。
5. **长期漂移**：模型版本、流量分布、成本单价都在变，需持续重估而非一次性定容。

#### 3. 具体答案

面试中可以这样回答：

> 我把可靠性和成本当成一个带约束的优化，而不是两个各自最优的目标。先声明约束：可用性和延迟是 SLO 底线，成本有单位经济上界——我度量的是"每成功事务成本"，不是总账单，因为总账单会掩盖失败请求的浪费。
>
> 成本来源我会拆开看：token 支出、推理算力、重试放大、缓存命中率、以及 Agent 循环步数。其中最容易失控的是 Agent 循环和重试——一次故障触发的重试风暴能把成本抬一个量级。所以重试要带退避、上限和熔断，不能无限重试。
>
> 可靠性手段都有代价：重试放大负载，对冲提升资源占用，冗余抬高固定成本。我会按尾部延迟的敏感度决定用哪个——用户感知强的路径值得对冲，批处理不值得。
>
> 然后定义降级路径，这是长期治理的核心。三级：完整 AI 路径；缓存或近似路径；非 AI 兜底路径。越界条件——成本超预算、依赖劣化、负载超容量——触发相应降级，保证系统退化而不是崩溃。最后，模型版本、流量分布和单价都在漂移，容量和预算要定期重估，不能定一次用一年。

#### 4. 技术洞察

形式化为约束优化，并显式标注哪些是硬的：

```text
在约束下最大化业务价值：
  s.t. 可用性 ≥ A*，P99 延迟 ≤ L*      （可靠性硬约束）
       每成功事务成本 ≤ C*             （成本硬约束）
       容量 headroom ≥ 余量

决策变量：重试策略、对冲开关、缓存层级、降级阈值、容量

降级阶梯（fail-degrade，而非 fail-stop）：
  L0 完整 AI 路径
  L1 缓存/近似路径        （延迟降、质量降）
  L2 非 AI 兜底路径       （可用性保、体验降）
  越界触发：成本 > C* | 依赖劣化 | 负载 > 容量

不变量：
  R1 成本有界：每成功事务成本 ≤ C*，含重试与循环
  R2 降级可定义：∀ 越界条件. 存在确定的下一级
  R3 重试有界：退避 + 上限 + 熔断，禁止无限重试
```

反直觉点：**更高 reliability 有时更省钱**。适度的对冲与缓存能同时降低尾延迟和重试放大，从而降低单位成本；问题在于过度冗余。因此不是"要可靠还是要便宜"，而是寻找 Pareto 前沿上的操作点。

#### 5. 图文说明

```text
          成本 ↑
              │        过度冗余区（贵且收益递减）
              │      ● Pareto 前沿
              │   ●
              │●  省钱但易劣化
              └────────────────► 可靠性

降级阶梯：L0 完整 → L1 缓存/近似 → L2 非 AI 兜底
触发：成本越界 / 依赖劣化 / 负载超容

Agent 循环与重试 = 成本放大器：必须带上限与熔断
```

| 手段 | 提升 | 代价 | 适用 |
|---|---|---|---|
| 重试 | 成功率 | 负载/成本放大 | 幂等且瞬时故障 |
| 对冲 | 尾延迟 | 资源占用 | 用户敏感路径 |
| 缓存 | 延迟/成本 | 陈旧风险 | 重复请求多 |
| 冗余 | 可用性 | 固定成本 | 关键路径 |
| 降级 | 可用性保底 | 体验下降 | 越界兜底 |

#### 7. 常见追问及回答要点

1. **成本和可靠性冲突时优先谁？** —— 取决于业务；但两者都可能是硬约束，应通过降级阶梯在越界时保住可用性、牺牲体验，而非二选一崩溃。
2. **如何防 Agent 成本爆炸？** —— 限制循环步数、加预算与熔断、对工具调用计费与限额；把单位成本纳入监控告警。
3. **缓存会不会降低质量？** —— 会引入陈旧；需按数据时效要求分级，并对陈旧命中可观测。

#### 8. 易错点与反例

- 反例：故障触发无限重试风暴，成本抬升一个量级且进一步压垮下游，形成正反馈崩溃。
- 反例：只盯总账单，忽略失败请求与 Agent 空转的浪费，单位经济持续恶化而无人察觉。
- 易错：盲目加冗余追求可靠性，超出 Pareto 前沿，成本大涨而可靠性边际收益趋零。

### AQ-E011. 架构演进与技术债的战略管理

- 难度：专家级
- 知识域：K11 架构、接口、技术债与演进
- 考察能力：演进式架构、债的度量与清偿、接口治理
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：适应度函数、ADR、绞杀者模式、耦合度量、契约测试
- 关联题目：AQ-E004（接口契约）、AQ-E012（度量）、AQ-E010（降级路径）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 加速代码产出会加速技术债积累，且债的类型会变：除了传统重复与耦合，还多出"生成的重复抽象""未被理解的依赖""无法解释的逻辑"。战略管理的核心是把债当作可观测、可排序、有预算的投资组合，而非道德问题。

演进式架构（evolutionary architecture）的思想：用**适应度函数**把架构约束自动化，让架构在变更中自我守护，而不是靠一次性评审。

#### 2. 问题分析

1. **债的度量**：用可计算的信号——变更放大（改一处要动几处）、循环依赖、接口越界、重复度、认知复杂度——而不是主观"代码烂"。
2. **债的分类与排序**：按"利息"（持续拖慢速度）与"本金"（修复成本）× 风险排序，优先高利息高风险的。
3. **适应度函数**：把关键约束（无循环依赖、接口只经声明、分层不反转）写成 CI 可判定的检查，自动阻止架构腐化。
4. **演进手段**：绞杀者模式（逐步替换）、分支抽象（并行支持新旧接口）、ADR 记录决策与权衡。
5. **AI 特有的债**：生成的抽象可能语义不清或重复造轮子，需额外审查"可解释性"与"是否已有等价设施"。

#### 3. 具体答案

面试中可以这样回答：

> 我把技术债当成一个可度量、可排序、有预算的投资组合，而不是"代码脏不脏"的道德判断。度量上我用可计算的信号：变更放大——改一个需求要动几个文件；循环依赖；接口越界；重复度；还有 AI 特有的一类债——生成了语义不清或重复的抽象。
>
> 排序按"利息"和"本金"两个维度：利息是它持续拖慢交付的程度，本金是修复成本，再乘上风险。高利息高风险的先还，比如一个所有人都要绕过的耦合点。
>
> 关键手段是**适应度函数**：把架构约束写成 CI 能判定的检查——没有新增循环依赖、跨层调用必须经声明接口、公共 API 变更必须过契约测试。这样架构在每次变更中被自动守护，而不是靠一年一次的评审。违反即阻断，把债的产生点前移。
>
> 演进策略我用绞杀者模式逐步替换高风险模块，用分支抽象并行支持新旧接口，用 ADR 记录每个决策的权衡。对 AI 产出我会额外加一条审查：这段生成的抽象是否语义清晰、是否已有等价设施，避免重复造轮子堆叠成无法理解的债。

#### 4. 技术洞察

把架构约束写成适应度函数，用不变量管理演进：

```text
技术债度量（可计算）：
  变更放大 = 单需求触达的模块数
  循环依赖 = 依赖图中的环数量
  接口越界 = 跨层直接调用的次数
  重复度   = 克隆代码比例
  认知复杂度 = 圈复杂度/嵌套聚合
  AI 债    = 语义不清/重复抽象计数

适应度函数（CI 判定，架构不变量）：
  F1 无新增循环依赖
  F2 跨层调用必须经声明接口
  F3 公共 API 变更必须过契约测试
  F4 分层方向不得反转

排序：priority ≈ 利息(拖慢度) × 风险 ÷ 本金(修复成本)
```

反直觉点：**AI 提高产出会放大"债的利息"**。因为变更变多，一个高耦合点的拖慢效应被乘上更高的变更频率，利息非线性上升。因此 AI 时代偿还高利息债务的收益比过去更大，适应度函数的紧迫性也随之上升。

#### 5. 图文说明

```text
变更率↑（AI 加持）
   │
   ▼
高耦合点被更高频触达 → 利息非线性放大

治理闭环：
  [度量债信号] → [按利息×风险排序] → [适应度函数防新增]
       ▲                                      │
       └────────── [预算化清偿 + 绞杀者演进] ◄┘

适应度函数 = 把架构约束变成 CI 门禁（防腐化于未然）
```

| 债类型 | 信号 | 手段 |
|---|---|---|
| 耦合 | 变更放大、循环依赖 | 绞杀者、接口解耦 |
| 接口 | 跨层调用 | 声明接口 + 契约测试 |
| 重复 | 克隆比例 | 抽取/合并（防重复造轮子） |
| AI 特有 | 语义不清抽象 | 可解释性审查 |

#### 6. 拓展知识

- 与 K04 交叉：接口契约是形式化约束的载体，可与验证路径共享。
- 与 K12 交叉：债的度量需防 Goodhart——降低重复度不能靠把重复藏进宏。
- 与 K10 交叉：降级路径与缓存层级本身是需要随演进维护的架构资产。

#### 7. 常见追问及回答要点

1. **技术债度量会不会被博弈？** —— 会，任何度量都会。所以度量要配对（如重复度配可读性），并承认度量是导航而非目标。
2. **适应度函数会不会太严阻碍交付？** —— 关键是只固化真正重要的不变量（方向、接口、循环依赖），其余留给判断；过严会促使人绕过。
3. **AI 生成的重复抽象怎么治理？** —— 在审查中要求说明"为何不复用已有设施"，并把重复度纳入适应度函数的新增检查。

#### 8. 易错点与反例

- 反例：AI 批量生成重复的抽象层，表面模块化，实际增加认知负担和变更放大。
- 反例：把技术债当道德问题，无度量无排序，团队要么无视要么盲目重构。
- 易错：适应度函数定义过宽，把风格偏好固化为门禁，逼迫工程师写规避代码，架构约束形同虚设。

#### 9. 实践与验证

`[待验证]` 实验设计：在引入 AI 产出前后，跟踪变更放大、循环依赖数与重复度的变化，并在部分模块启用适应度函数，比较架构腐化速度；oracle：启用适应度函数的模块在新增循环依赖与接口越界上应显著更少。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：把技术债当主观判断，无度量无排序。
- 合格：能说出常见债类型与演进手段（绞杀者、ADR）。
- 良好：能用适应度函数把架构约束自动化。
- 优秀：能讨论 AI 放大债利息的非线性效应、AI 特有债的审查，并承认度量可被博弈、适应度函数过严的反效果。

### AQ-E012. 组织级质量度量体系的设计

- 难度：专家级
- 知识域：K12 质量度量、合规与组织治理
- 考察能力：度量设计、反博弈、跨层治理
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：目标-信号-指标层级、Goodhart 定律、交付/稳定性指标、归因
- 关联题目：AQ-E005（测试度量）、AQ-E006（审查度量）、AQ-E015（组织变革）
- 事实状态：`[推断]`

#### 1. 背景知识

度量体系常见失败是"收集了一堆仪表盘但没人据此决策"。好的体系从目标出发：目标 → 信号（可观测现象）→ 指标（可计算代理），并保证每个指标都有 owner、有它驱动的决策、有反博弈护栏。

AI 辅助开发给度量加了新维度：需要区分"AI 带来的变化"与"其他变化"，且不能把"AI 采用率"当作质量指标本身。

#### 2. 问题分析

1. **维度设计**：速度（交付前置时间）、稳定性（变更失败率、恢复时间）、质量（逃逸缺陷、变异分数）、采用（AI 使用但要防止为用而用）。
2. **指标-决策绑定**：每个指标必须回答"它变差时我们改什么"，否则删除。
3. **反博弈**：任何被考核的指标都会被优化，需配对指标与护栏（如速度配稳定性，覆盖率配变异分数）。
4. **归因**：要能把变化归因到 AI 引入、流程变更或外部因素，否则无法评估 AI 的真实贡献。
5. **分层与节奏**：团队层看可操作信号，组织层看趋势，高管层看方向；不同层用不同粒度和复盘周期。

#### 3. 具体答案

面试中可以这样回答：

> 我设计度量体系的起点是目标，不是数据。先明确我们想改变什么——比如"在可控质量下更快交付"——再推导信号和指标。每个指标必须绑定一个决策：它变差时我们改什么。绑不上决策的指标，我会删掉，因为仪表盘越多注意力越分散。
>
> 维度上我会覆盖速度、稳定性、质量、采用四类，但关键是配对：速度必须配稳定性，否则会出现"为了快而降低质量"的博弈；覆盖率必须配变异分数，否则会被无断言测试骗过。这就是反博弈护栏。
>
> AI 相关要特别小心。我会单独度量 AI 的采用与影响，但绝不把"使用率"当质量指标——那会诱导为用而用。更重要的是归因：把变化尽量归因到 AI 引入、流程改动或外部因素，否则你无法判断 AI 到底有没有帮上忙。
>
> 最后分层：团队层要可操作的信号，组织层看趋势，高管层看方向，各自复盘节奏不同。并且我会预期指标会被优化，所以每个都预设护栏，并定期检查有没有把指标本身当成了目标。

#### 4. 技术洞察

把度量体系建模为"目标-信号-指标-决策-护栏"五元组：

```text
每个指标 = (目标, 信号, 指纹, 决策, 护栏)
  无决策 → 删除（否则是噪声）
  无护栏 → 会被博弈

配对（反博弈）：
  速度 ⟷ 稳定性      （防为快牺牲稳）
  覆盖率 ⟷ 变异分数   （防无断言凑数）
  采用率 ⟷ 逃逸缺陷   （防为用而用）
  审查量 ⟷ 审查质量   （防橡皮图章）

归因：Δ效果 = f(ΔAI引入, Δ流程, Δ外部) ，需能分离
层级：team(可操作) / org(趋势) / exec(方向)
```

反直觉点：**"AI 使用率"作为质量目标是反指标**。它把手段当目的，可能推动团队在不适合的场景硬用 AI，反而增加缺陷。专家级回答会把采用率定位为过程指标，其价值必须由质量与速度的配对指标验证。

#### 5. 图文说明

```text
目标：可控质量下更快交付
   │
   ├─ 速度信号 → 交付前置时间   ┐ 配对
   ├─ 稳定信号 → 失败率/恢复时间 ┘
   ├─ 质量信号 → 逃逸缺陷/变异分数 ┐ 配对
   ├─ 采用信号 → AI 使用率        ┘（须由质量验证价值）
   │
   ▼
每个指标：owner + 决策 + 护栏 + 复盘节奏
```

| 维度 | 指标示例 | 配对护栏 |
|---|---|---|
| 速度 | 交付前置时间 | 变更失败率 |
| 稳定 | 恢复时间 | 变更规模 |
| 质量 | 逃逸缺陷 | 变异分数 |
| 采用 | AI 使用率 | 缺陷/返工率 |

#### 6. 拓展知识

- 与 K06 交叉：审查的橡皮图章指标正是一个"配对护栏"的实例。
- 与 K05 交叉：覆盖率-变异分数配对是质量维度的核心。
- 与 K15 交叉：度量体系是组织变革的反馈回路，缺它变革无法验证。

#### 7. 常见追问及回答要点

1. **指标越多越好吗？** —— 不是。指标要绑定决策，绑不上的删；过多指标稀释注意力并制造矛盾信号。
2. **如何避免 Goodhart 定律？** —— 配对指标加护栏，并周期性检查是否把指标本身当目标；承认无法根除，只能持续校准。
3. **怎么衡量 AI 到底有没有用？** —— 通过归因把变化分离到 AI 引入与其他因素；用配对的质量/速度指标而非使用率来判断。

#### 8. 易错点与反例

- 反例：把"AI 使用率"设为考核目标，团队在不适合的场景强行使用，缺陷率反而上升。
- 反例：只考核交付速度，团队通过拆分小 PR 刷数，掩盖整体交付并未变快。
- 易错：指标没有 owner 和决策，收集一年无人据此行动，度量沦为仪表盘装饰。

#### 9. 实践与验证

`[待验证]` 实验设计：在部分团队推行"配对指标+护栏"的度量体系，对照传统单一指标，观察是否出现指标上涨但真实交付/质量未改善的博弈迹象；oracle：配对体系下速度上涨应伴随稳定性不恶化。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：罗列指标或认为"数据越多越好"。
- 合格：能从目标推导指标并覆盖主要维度。
- 良好：能给出指标-决策绑定与配对护栏。
- 优秀：能讨论 AI 采用率作为反指标、归因的困难，以及分层治理与 Goodhart 不可根除的残余风险。

### AQ-E013. 人机协作模式的演进决策

- 难度：专家级
- 知识域：K01 vibe-coding 生命周期与人机协作
- 考察能力：协作模式选择、信任校准、能力治理
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：信任校准、自动化自满、技能退化、HITL 设计
- 关联题目：AQ-E003（自治边界）、AQ-E001（不变量）、AQ-E015（组织变革）
- 事实状态：`[推断]`

#### 1. 背景知识

人机协作模式随能力与信任演进：补全 → 对话 → Agent 驱动 → 流水线自治。选择模式的依据不是"哪个先进"，而是任务的关键性、可逆性、上下文需求与信任校准程度。

两类系统性风险：**过度信任**（自动化自满，人不检查导致错误放大）与**信任不足**（人反复重做，收益归零）。协作设计要主动管理二者。

#### 2. 问题分析

1. **模式-任务匹配**：什么任务适合什么模式？探索/样板适合高自治；核心逻辑/安全敏感适合低自治 + 强验证。
2. **责任分配**：人始终对不可逆、需担责的决策负责；模型承担可验证、可回退的执行。
3. **信任校准**：用可观测的准确率反馈让信任与真实能力对齐，而非凭感觉。
4. **技能治理**：长期依赖会退化人的部分能力（如调试、底层实现），需要保留关键能力不被侵蚀。
5. **演进节奏**：模式升级应有前置条件（如验证基础设施就绪），而非跟风。

#### 3. 具体答案

面试中可以这样回答：

> 我按任务属性而不是按"哪个模式最先进"来选协作方式。四个维度：关键性、可逆性、上下文需求、以及我们对模型在该任务上能力的校准程度。探索和样板生成可以高自治；核心逻辑、安全敏感、不可逆的决策必须低自治加强验证。
>
> 责任分配上我坚持一条：模型做可验证、可回退的执行，人负责需要担责的判断。这条不是保守，是因为责任无法委托给一个不可追责的主体。
>
> 我最警惕的是信任失准的两个方向。过度信任——自动化自满，人因为"看起来对"而不检查，一次错误被放大成事故；信任不足——人反复重写模型产出，收益归零。解法是把信任建立在可观测的准确率上：按任务类型统计模型的错误率，让信任随证据校准，而不是凭感觉高估或低估。
>
> 还有技能治理。长期依赖模型会让人退化某些能力——调试、底层实现、边界推理。我会刻意保留关键能力路径，比如要求对核心模块仍能独立推理，否则一旦模型失效或出错，团队失去兜底能力。模式升级要有前置条件，验证基础设施没就绪之前不升自治。

#### 4. 技术洞察

把模式选择建模为任务属性的函数，并把责任与信任显式化：

```text
mode(task) = g(关键性, 可逆性, 上下文需求, 信任校准度)

责任规则（不变量）：
  H1 责任不可委托：不可逆/担责决策 ⇒ 人负责
  H2 信任-证据对齐：信任度 ≤ 观测准确率的可信下界
  H3 能力兜底：关键能力不得因依赖而完全退化
  H4 升级前置：自治升级 ⇒ 验证基础设施就绪

信任失准的两种失效：
  过度信任 → 自动化自满 → 错误放大（漏检）
  信任不足 → 重复劳动   → 收益归零（浪费）
```

反直觉点：**提高模型准确率未必提高团队产出**。如果信任校准没跟上，更高准确率可能让人更放松警惕，把偶发错误放得更大。因此协作设计要同时管"能力"和"信任校准"，二者错配时能力提升反而危险。

#### 5. 图文说明

```text
        信任
          ▲
  过度信任 │  目标区（对准真实准确率）
 (自满漏检)│ ●
 ──────────┼──────────────► 模型能力
  信任不足 │
 (重复劳动)│
          │

模式谱：补全 → 对话 → Agent 驱动 → 流水线自治
升级前置条件：验证基础设施就绪（见 AQ-E001/AQ-E005）
```

| 任务属性 | 建议模式 | 人的角色 |
|---|---|---|
| 探索/样板 | 高自治 | 快速验收 |
| 一般实现 | 中自治 | 审查意图 |
| 核心逻辑 | 低自治 | 设计与验证 |
| 不可逆/担责 | 人主导 | 决策与批准 |

#### 6. 拓展知识

- 与 K03 交叉：自治边界是协作模式在工具调用层的具体化。
- 与 K05/K06 交叉：验证与审查基础设施是模式升级的前置条件。
- 与 K15 交叉：协作模式演进是组织变革的一部分，需要培训与文化建设。

#### 7. 常见追问及回答要点

1. **模型越来越强，人还有必要审查吗？** —— 对不可逆、需担责的决策有；审查可从逐行转为意图与边界，但不能取消责任主体。
2. **怎么防自动化自满？** —— 用任务级准确率反馈校准信任、抽样强制复核、保留"必须人看"的关键路径。
3. **技能退化怎么办？** —— 刻意保留关键能力路径（核心模块独立推理、定期手写/调试演练），并把兜底能力视为风险控制而非怀旧。

#### 8. 易错点与反例

- 反例：模型准确率提升后团队取消关键路径复核，一次偶发错误直接进生产，后果被放大。
- 反例：人对模型产出完全不信任，全部手工重写，投入 AI 的收益归零。
- 易错：凭感觉调整自治级别，没有按任务类型统计错误率，信任长期偏离真实能力。

#### 9. 实践与验证

`[待验证]` 实验设计：按任务类型统计模型错误率，并对不同信任校准方案（有/无任务级反馈、有/无关键路径强制复核）比较漏检率与返工率；oracle：带反馈校准的组应使信任更贴近真实准确率，漏检与返工同时下降。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：以"越自动越好"或"人必须全看"为答案。
- 合格：能按任务关键性与可逆性选择模式。
- 良好：能讨论信任校准与责任分配。
- 优秀：能指出准确率提升与信任错配的危险、技能退化的兜底治理，并给出模式升级的前置条件与残余风险。

### AQ-E014. AI 编码平台的多租户与合规治理

- 难度：专家级
- 知识域：K09 安全、隐私、注入与供应链
- 考察能力：多租户隔离、合规映射、数据治理
- 题型：开放架构题
- 面试频率：开放题
- 前置知识：租户隔离模型、检索索引隔离、数据驻留、审计、数据主体权利
- 关联题目：AQ-E002（检索权限）、AQ-E009（供应链）、AQ-E012（治理）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 编码平台（补全、Agent、检索、代码审查）往往服务多个团队/租户，并可能跨境。多租户要保证：数据隔离、秘密隔离、模型/端点驻留合规、可审计、以及数据主体权利（访问、删除、导出）。

与普通多租户不同，AI 平台的数据面更宽：代码片段、提示、上下文、嵌入向量、以及可能的模型微调数据都可能承载租户信息。

#### 2. 问题分析

1. **隔离层级**：基础设施级（独立集群/命名空间）、索引级（检索索引按租户分区）、模型级（专属端点或共享但逻辑隔离）。选哪层取决于合规要求与成本。
2. **索引与嵌入**：嵌入向量可能泄漏语义信息，跨租户索引必须硬隔离；缓存也要按租户键隔离，避免跨租户命中。
3. **数据驻留**：模型端点与存储的地区边界，需与合规要求对齐；路由必须保证不越界。
4. **审计与权利**：所有访问可审计；支持数据主体访问/删除/导出，且删除要覆盖索引、缓存与备份。
5. **微调/训练数据**：若用租户数据训练或微调，需明确授权边界与隔离。

关键不变量：跨租户数据永不进入非本租户的上下文；路由遵守驻留边界；所有访问可审计；删除请求可证明执行。

#### 3. 具体答案

面试中可以这样回答：

> 多租户 AI 平台的核心不变量是跨租户数据隔离——任何租户的数据，包括代码片段、提示、上下文、嵌入向量和缓存，都绝不能进入另一个租户的请求。这条在检索和缓存上尤其危险，因为嵌入向量会携带语义，缓存键如果没按租户隔离就会跨租户命中。
>
> 隔离层级我按合规要求选：一般团队共享基础设施但索引和缓存按租户硬分区；强合规租户走独立命名空间甚至独立端点。检索索引必须分区，且权限过滤和租户过滤合并成第一层，防止"检索后再删"留下中间态暴露。
>
> 数据驻留是合规硬约束：模型端点和存储有地区边界，路由必须保证请求不越界，这要能在策略层验证而不是靠文档承诺。
>
> 审计和权利上，所有访问要可归因，数据主体的访问、删除、导出请求要能执行且可证明——删除必须覆盖索引、缓存和备份，否则只是表面删除。如果要用租户数据微调或训练，授权边界和隔离必须事先明确，这是法律和工程共同决定的，不能事后补。

#### 4. 技术洞察

把多租户合规表达为硬不变量：

```text
隔离层级（成本↑ 隔离↑）：
  共享基础设施 + 逻辑隔离
    → 独立命名空间
    → 独立集群/端点

硬不变量：
  M1 上下文隔离：∀请求 r(tenant t). context(r) ∩ data(¬t) = ∅
  M2 缓存隔离：cache_key 含租户身份，禁止跨租户命中
  M3 索引隔离：嵌入/检索按租户分区（语义泄漏也是泄漏）
  M4 驻留合规：route(r) 的端点/存储地 ∈ allowed_region(t)
  M5 可审计 + 可删除：∀访问可归因；delete(t) 覆盖索引/缓存/备份

陷阱：嵌入向量 ≠ 匿名数据
      检索后裁剪 ≠ 隔离（中间态即泄漏面）
```

反直觉点：**嵌入向量不是匿名数据**。它可通过反演或相似度比较泄漏原文语义，因此"只共享向量不共享原文"不构成隔离。跨租户索引必须真实分区，而非在同一索引中靠过滤。

#### 5. 图文说明

```text
请求(租户 t) → [租户+权限前置过滤] → [t 分区索引] → 上下文
                      │
                      ├─ 缓存键含 tenant（禁跨租户命中）
                      └─ 路由校验驻留边界

数据主体权利：
  访问/导出 → 覆盖 原文+嵌入+缓存+备份
  删除     → 可证明执行（否则是表面删除）

隔离层级选择：合规要求 × 成本 决定
```

| 数据面 | 隔离要求 | 常见陷阱 |
|---|---|---|
| 代码/提示 | 硬隔离 | 日志/缓存交叉 |
| 嵌入向量 | 硬隔离 | 误当匿名数据 |
| 缓存 | 按租户键 | 跨租户命中 |
| 微调数据 | 授权 + 隔离 | 授权边界不清 |
| 备份 | 覆盖删除 | 删除不彻底 |

#### 6. 拓展知识

- 与 K02 交叉：检索权限闭合与租户隔离共享同一前置过滤策略。
- 与 K09 交叉：egress 与数据流约束需叠加租户维度。
- 与 K12 交叉：审计日志与删除证明是合规证据，需纳入治理证据目录。

#### 7. 常见追问及回答要点

1. **只隔离原文、共享向量行不行？** —— 不行。嵌入可泄漏语义，向量本身即敏感数据，必须硬隔离。
2. **删除请求如何"可证明"？** —— 记录删除任务覆盖索引、缓存、备份，并提供可核验的执行证据；否则是表面删除。
3. **共享端点如何满足驻留？** —— 需按租户路由到合规区域端点，并在策略层验证；文档承诺不算数。

#### 8. 易错点与反例

- 反例：检索后再按租户裁剪结果，但裁剪前的候选集进入日志或缓存，形成跨租户泄漏。
- 反例：缓存键只用提示哈希，两个租户相同提示命中彼此结果，泄漏上下文。
- 易错：把嵌入向量当作已匿名，允许跨租户共享索引，语义泄漏长期不可见。

#### 9. 实践与验证

`[待验证]` 实验设计：构造多租户、多区域场景，注入跨租户检索/缓存命中和越界路由用例，验证隔离与驻留策略的拦截率；并验证删除请求对索引/缓存/备份的覆盖。oracle：跨租户泄漏为 0，越界路由被拒，删除可核验。当前未在本工作区执行。

#### 10. 评分标准

- 不合格：认为多租户只是"加个 tenant_id 过滤"。
- 合格：能说明主要数据面与隔离需求。
- 良好：能给出硬不变量与索引/缓存隔离设计。
- 优秀：能指出嵌入向量的语义泄漏、检索后裁剪的中间态风险、删除可证明性，并把驻留合规做成策略层可验证约束。

**证据与来源：** `[推断]` 多租户隔离、数据驻留、数据主体权利为公开合规与工程实践 `[已确认]`。拦截率与删除覆盖结果标 `[待验证]`。

### AQ-E015. 从工具引入到组织变革的演进路线

- 难度：专家级
- 知识域：K12 质量度量、合规与组织治理
- 考察能力：变革管理、阶段门禁、影子使用治理
- 题型：开放设计题
- 面试频率：开放题
- 前置知识：变革管理、试点到规模化、门禁前置、影子 IT、度量反馈
- 关联题目：AQ-E012（度量）、AQ-E006（门禁）、AQ-E013（协作模式）
- 事实状态：`[推断]`

#### 1. 背景知识

AI 工具引入到组织变革，常见失败是"发了工具没改流程"——工具到位但门禁、审查、度量都没跟上，结果是影子使用、质量漂移与形式化采纳并存。专家级路线把工具引入当作约束优先的演进：**护栏先于规模化**。

影子 AI（未授权的工具使用）是普遍现实：强行禁止会把它推向地下，正确做法是提供合规替代并度量其使用。

#### 2. 问题分析

1. **阶段划分**：试点 → 扩展 → 标准化 → 变革。每阶段有可度量的退出条件，而非按时间推进。
2. **护栏前置**：安全、权限、审查、度量基础设施必须先就绪，否则规模化的同时放大风险。
3. **影子使用治理**：识别未授权使用，提供合规替代，纳入可见度量，而不是简单封禁。
4. **可度量反馈**：每阶段用配对指标（速度+稳定性）验证收益，防止不可验证的"感觉更快"。
5. **文化与能力**：培训、样板、champion 网络、以及承认阻力的存在。

#### 3. 具体答案

面试中可以这样回答：

> 我把这件事当成约束优先的演进，而不是采购和内部推广。四个阶段——试点、扩展、标准化、变革——但每一阶段之间是**可度量的门禁**，不是按季度推进。试点阶段的退出条件是真实验证了收益，而且是配对的：速度提升的同时稳定性没有恶化。
>
> 关键原则是护栏先于规模化。安全、权限、审查、度量这些基础设施必须在放大使用之前就绪，否则你只是在更高的产出速率上等比例的放大风险。这正是很多团队"工具发了、事故也多了"的根因。
>
> 影子 AI 我不会简单封禁。它普遍存在，封禁只会把它推到地下、更不可见。正确做法是承认它在发生，提供合规的替代工具，并把它的使用也纳入可观测——你要能度量未授权使用的规模，才能管理它。
>
> 每一阶段我用度量验证收益，避免"感觉更快"这种不可验证的结论。还配上培训和 champion 网络，并且不回避阻力——有些阻力来自对质量风险的真实担忧，值得倾听而不是压制。变革的标志不是人人都在用工具，而是流程、门禁、度量都围绕新协作方式重建完成。

#### 4. 技术洞察

把演进制为带退出条件的阶段门禁，护栏作为前置不变量：

```text
阶段：试点 → 扩展 → 标准化 → 变革
每阶段：进入条件 + 退出条件（可度量），非时间驱动

前置不变量（规模化之前必须成立）：
  E1 护栏就绪：安全/权限/审查/度量基础设施可用
  E2 配对度量：收益以 速度+稳定性 配对验证，非单一指标
  E3 影子可见：未授权使用可被度量，有合规替代
  E4 可回退：阶段推进可回退（若稳定性恶化则退回）

误区：工具先行 → 影子使用 + 质量漂移 + 形式化采纳
```

反直觉点：**禁止影子 AI 会降低而非提升治理能力**。封禁把使用推向不可观测的角落，组织失去了度量与补救的机会。专家级选择"提供合规路径 + 保持可见"，因为治理的前提是可见性。

```text
  ▲                               │ [退出: 护栏全覆盖]
```

| 扩展 | 护栏全覆盖 | 风险随规模放大 |
| 标准化 | 流程/门禁统一 | 形式化采纳 |
| 变革 | 度量闭环稳定 | 文化阻力、技能退化 |

#### 7. 常见追问及回答要点

1. **要不要直接全公司推广？** —— 不建议。跳过试点与护栏前置会把风险按规模放大；演进应按可度量门禁推进。
2. **怎么处理员工私自用外部 AI 工具？** —— 保持可见、提供合规替代、纳入度量，而非封禁至地下；治理依赖可见性。
3. **如何判断变革真的发生了？** —— 看流程、门禁、度量是否围绕新协作方式重建，而不是看工具使用率。

#### 8. 易错点与反例

- 反例：先大规模发工具、再补护栏，结果产出与事故同时上升，团队对 AI 失去信任。
- 反例：严格封禁外部工具，员工转用个人账号处理公司代码，数据外泄且完全不可见。
- 易错：用"使用了工具的人数"衡量变革成功，流程与门禁未变，只是形式化采纳。
