# K03 Agent 规划、工具与编排

## 范围

任务拆解、工具调用、状态机、权限和预算。

## 领域边界

**本域解决什么。** 把"一次性生成"升级为"多步自主执行"时，需要的一整套机制：Agent 如何决定下一步（规划）、如何作用于环境（工具）、如何观察结果（observation）、失败后如何恢复、在什么权限下运行、何时停止、预算多大、多个 Agent 如何分工。

**本域不负责什么。**

- 不负责单次调用的上下文构建与提示词工程（K02），本域消费其产物。
- 不负责生成代码的正确性判据（K04）与测试 oracle（K05）。
- 不负责门禁语义与审查规则（K06）、CI 引擎（K07）。
- 不负责 Agent 的模型训练；本域只处理推理时的编排逻辑。

**与相邻域的接口。**

| 本域交付 | 接收方 |
|---|---|
| 工具的沙箱与权限边界（哪些操作可自动执行） | K01（Agent 可自主的状态划分） |
| 工具返回值格式（observation 契约） | K02（动态上下文） |
| 多步执行中的产物（diff、测试结果）作为证据 | K05/K06 |
| 高风险工具（写文件、装依赖、发请求）的审批点 | K09 |

## 先修知识

- 工具调用（function calling / tool use）的基本形态：模型输出结构化调用意图，运行时执行后把结果回填。
- 状态机与循环控制：条件、迭代、终止。
- JSON Schema / 类型约束基础。
- 沙箱与最小权限原则。
- 预算概念：token、时间、调用次数、成本。

## 核心机制

### 1. Agent 循环：model → tool → observation

Agent 的基本单位是一个受控循环：

```text
状态 S
  → 模型基于 S 输出一个动作 a（调用工具 或 给出最终答案）
  → 若 a 是工具调用：运行时执行 a，得到观察 o
  → S := S ∪ {a, o}     （把动作与结果追加进上下文）
  → 回到循环
  → 若 a 是最终答案：退出循环
```

三个必须显式设计的约束：

1. **终止条件**：什么时候算完成（模型自认完成 / 通过测试 / 达到目标谓词）。
2. **预算**：最多多少轮、多少 token、多少工具调用、多少墙钟时间、多少钱。
3. **可观察性**：每一步的 (动作, 观察) 都要可记录、可回放，否则失败无法归因。

失败模式：循环不收敛（反复试同一步）、过早终止（没验证就说完成）、目标漂移（做偏了却仍在推进）。

### 2. 工具 schema 设计

工具是 Agent 唯一的作用于真实环境的手脚，schema 质量直接决定可靠性：

- **名称与描述**：用模型能区分的语义命名（`read_file` vs `get_content`），描述里写清"何时用、何时不用"。
- **参数类型**：用严格类型与枚举约束，避免自由字符串；必填/选填分明。
- **返回值**：结构化、可截断、带错误码。返回超大内容会挤爆上下文，应支持分页或摘要。
- **幂等性**：读操作应幂等；写操作需标注是否可安全重试。
- **错误语义**：区分"参数错（模型可改）"与"环境错（重试无效）"，让模型知道下一步该改什么。

反模式：一个包罗万象的 `run_shell(command)` 会绕过所有权限控制；应拆成有边界的具体工具，或对 shell 施加白名单。

### 3. 规划：ReAct 与 Plan-Execute

两种主流范式，适用场景不同：

| 范式 | 机制 | 优势 | 代价 |
|---|---|---|---|
| ReAct | 交替"推理一步→行动一步"，边做边想 | 灵活、能即时纠偏 | 每步都调模型，成本高、易短视 |
| Plan-Execute | 先产出完整计划，再逐步执行 | 全局一致、可审查计划 | 计划可能失真，环境变化后需重规划 |

实践中的混合策略 `[推断]`：先 Plan 出高层步骤（可给人工审批），每个步骤内部用 ReAct 处理局部不确定性；当观察显著偏离计划时触发重规划。

规划质量检查点：步骤是否有可验证的完成定义、依赖顺序是否正确、是否包含"验证"步骤（很多 Agent 失败于只做不验）。

### 4. 失败恢复与重试

失败是常态，恢复策略要分类：

- **瞬时错误**（网络抖动、限流）：指数退避重试，设上限。
- **可修复错误**（参数错、语法错）：把错误信息回填，让模型修正后重试；要防止"同错循环"，可要求每次尝试必须改变策略。
- **环境错误**（依赖缺失、权限不足）：重试无效，应上报或换工具。
- **语义错误**（做对了动作但结果不对）：需要验证步骤发现，靠测试/断言而非重试解决。

关键不变量：**重试必须改变输入**。原样重放只会消耗预算并放大错误。

### 5. 工具权限与沙箱

按"可逆性 × 影响面"给工具分级授权：

| 级别 | 例子 | 授权策略 |
|---|---|---|
| 只读 | 读文件、检索、查日志 | 默认允许 |
| 可逆写 | 改工作区文件、跑测试 | 沙箱内允许，git 可回滚 |
| 外部副作用 | 装依赖、发网络请求、调云 API | 需审批或白名单 |
| 不可逆 | 删数据、发布、转账、改权限 | 强制人工签字，禁止自主 |

沙箱要求：文件系统隔离、网络默认关闭（按需开白名单）、资源限额（CPU/内存/时间）、凭证不进 Agent 上下文（用代理注入）。

### 6. 多 Agent 委派

把任务拆给多个 Agent 时的收益与风险：

- **收益**：并行探索、角色分工（检索/实现/审查）、上下文隔离（避免单一窗口过载）。
- **风险**：委派语义丢失（子 Agent 不知道全局约束）、结果冲突（两个子 Agent 改同一文件）、汇总瓶颈、成本翻倍。

设计要点：

1. **委派契约**：给子 Agent 明确的输入（目标、约束、可用上下文）与输出 schema（结果、证据、未决问题）。
2. **单一写者**：对同一文件/资源只允许一个 Agent 写，避免冲突。
3. **可验证的交接**：子 Agent 的产出必须能被验证（测试、类型），而不是"相信我"。
4. **汇总去重**：父 Agent 负责合并冲突、剔除重复、做最终验证。

### 7. 终止条件与预算

必须显式定义"成功"与"放弃"：

- **成功终止**：目标谓词满足（测试通过、编译通过、断言成立），而不是模型自称完成。
- **放弃终止**：预算耗尽、连续 N 次无进展、触发不可恢复错误 → 上报人工。
- **无进展检测**：若连续若干步状态无实质变化，提前终止，避免烧预算。

反模式：只设"模型说停就停"，导致未验证的半成品被当作完成品交付。

### 检查清单（上线一个 Agent 前）

- [ ] 每步动作与观察是否可回放？
- [ ] 是否有独立于模型自述的"完成"判定？
- [ ] 预算（轮数/token/时间/成本）是否设上限？
- [ ] 无进展循环是否有检测与熔断？
- [ ] 工具是否按影响面分级授权？不可逆操作是否强制人工？
- [ ] 失败重试是否保证改变输入？
- [ ] 多 Agent 是否有单一写者与冲突消解规则？

### 8. 一次失败恢复走查

任务："修复 test_login 的失败。"

```text
轮1  动作：run_test("test_login")
    观察：AssertionError: expected 401, got 200    → 语义/行为问题
轮2  动作：read_file("auth/login.py")
    观察：发现未校验密码哈希
轮3  动作：edit_file("auth/login.py", 补校验)
    观察：edit ok
轮4  动作：run_test("test_login")
    观察：通过                                → 成功终止（目标谓词满足）
```

对照反例：若轮4仍失败，正确做法是**改变假设/策略**（读依赖、看日志、缩小用例），而不是原样重跑 `run_test`。无进展检测应在连续 2-3 步无状态变化时熔断上报。

另一类失败：轮1 观察是 `ConnectionError`（环境错），此时重试可能有效；若是 `ModuleNotFoundError`（环境缺失），重试无效，应上报或安装依赖（后者是外部副作用，需授权）。

### 9. 工具 schema 示例

一个边界清晰的"读文件"工具：

```json
{
  "name": "read_file",
  "description": "读取仓库内单个文本文件的内容。用于查看实现、配置、测试。不用于写入，不访问仓库外路径。",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {"type": "string", "description": "仓库相对路径"},
      "start_line": {"type": "integer", "minimum": 1},
      "max_lines": {"type": "integer", "default": 200, "maximum": 1000}
    },
    "required": ["path"]
  }
}
```

要点：描述里显式写出"何时用/何时不用"；`max_lines` 上限防止一次拉爆上下文；`path` 限制为仓库相对路径以防越权。写入类工具需要额外标注可逆性与审批要求。

### 10. 预算与进度表

把预算写成显式契约，而不是隐含假设：

| 预算维度 | 上限来源 | 超限动作 |
|---|---|---|
| 步数/轮次 | 任务复杂度估计 | 终止并上报，附已完成与未决 |
| token | 窗口与成本 | 触发上下文压缩或摘要 |
| 工具调用次数 | 速率与外部配额 | 退避或终止 |
| 墙钟时间 | SLA | 终止 |
| 成本 | 单位调用价格 × 次数 | 达到阈值需人工放行 |

`[推断]` 无进展熔断 + 显式预算是防止 Agent 烧光资源的两条主线；两者都要能产出"已做什么、卡在哪、待人工决定什么"的上报。

### 11. Agent 产物如何进入生命周期

Agent 每完成一个可验证子目标，就应产出一个"检查点"：可读 diff + 测试结果 + 未决问题。这些检查点对应 K01 状态机里的出口证据，使 Agent 的自主执行可以被分阶段审查，而不是最后一次性交出巨量改动。多步 Agent 最容易失控的地方就是"中间不可见、结尾难审查"。

## 常见陷阱与反例

- **反例：给 Agent 一个无限制的 `run_shell`。** 等于把所有权限一次性授予，沙箱形同虚设。
- **反例：以模型自称完成作为终止条件。** 未跑测试、未验证结果就交付。
- **反例：无进展循环。** 模型反复尝试同一失败动作，烧光预算；缺少"每次必须改变策略"的约束。
- **反例：把工具返回的巨型日志原样回填。** 挤爆上下文，且把无关信息当证据。
- **反例：多 Agent 并发写同一文件。** 后写覆盖先写，且无人发现。
- **易错：规划步骤里没有"验证"步。** 只做不验，错误一路带到下游。
- **易错：把凭证放进 Agent 上下文。** 一旦上下文被日志/回放暴露，即为泄露。
- **易错：重试原样重放。** 既耗预算又强化错误。

## 与其他知识域的连接

- **K01**：本域的权限分级与终止条件，是 K01 "Agent 可自主的状态边界"的输入；Agent 每一步产物要能作为状态机的出口证据。
- **K02**：observation 是动态构建的上下文，必须遵守最小充分、留输出余量、抗中段衰减的规则。
- **K04**：Agent 产出的 diff 要过与人工代码相同的正确性判据（K04）。
- **K05**：把"跑测试"作为终止谓词，依赖 K05 的可信 oracle。
- **K06**：Agent 的每一步可视为一次小 PR，审查与门禁的语义复用。
- **K07**：CI 中嵌入 Agent 会引入非确定性与权限问题，需与流水线设计对齐。
- **K09**：工具权限、沙箱、凭证隔离直接对应安全边界；提示注入可使 Agent 执行被劫持的工具调用。
- **K10**：预算与成本控制是本域与性能/成本域的交集。

## 证据与缺口

- `[已确认]` 工具调用的基本机制（结构化调用回填）、最小权限与沙箱为通用工程实践。
- `[推断]` ReAct 与 Plan-Execute 的混合策略、无进展熔断、委派契约与单一写者由机制推导。
- `[待验证]` 预算上限的经验值、无进展检测的窗口大小、多 Agent 的成本-收益交叉点，需在目标系统实测。
- 缺口：本工作区无 Agent 运行时与回放数据，任何"成功率/步数"类数字均未验证，不得编造。
