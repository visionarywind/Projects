# K02 提示词、上下文与代码库理解

## 范围

上下文选择、检索、约束和 grounding。

## 领域边界

**本域解决什么。** 回答"模型凭什么信息做出这个生成/修改"，即把正确的项目事实（接口、类型、约定、示例、错误日志、测试）放进上下文，并把指令（角色、任务、格式、约束）表达清楚。核心命题：**输入的准确性与充分性决定输出的正确性上限**。

**本域不负责什么。**

- 不负责生成后的正确性判定（K04）、测试 oracle（K05）、审查门禁（K06）。
- 不负责 Agent 的多步循环与工具编排（K03），本域只提供"每次调用喂什么"。
- 不负责模型本身的训练/对齐能力，只处理推理时的输入工程。
- 不负责索引基础设施的运维（向量库部署、增量更新调度），只给出检索设计与新鲜度约束。

**与相邻域的接口。**

| 本域交付 | 接收方 |
|---|---|
| 最小充分上下文集与 grounding 证据 | K01（上下文准备状态的出口） |
| 工具返回值如何回填进模型上下文（观察格式） | K03 |
| "引用必须可解析"的可验证性约束 | K04 |
| 让模型看到测试与 oracle 的上下文模板 | K05 |

## 先修知识

- 自回归语言模型按 `P(token | 已见上下文)` 采样，上下文之外的信息不存在。`[已确认]`
- 上下文窗口是有限 token 预算，窗口内的注意力分布不均匀，中段信息更易被忽略（Lost in the Middle，Liu et al. 2023）。`[已确认]`
- 检索基础：词法检索（ripgrep/BM25）、向量检索（embedding 近邻）、结构化检索（AST/LSP/符号图）三类信号。
- 代码库结构概念：包、模块、符号表、定义-引用、调用图、类型系统。
- 分块（chunking）：按行切 vs 按符号边界切的区别。

## 核心机制

### 1. 提示词结构

一条可复用的生成提示通常包含以下可分离的槽位，缺哪个就在哪个维度失控：

```text
[角色/约束]    你是在 <repo> 中工作的工程师，遵循 <规范文件>
[任务]         实现 X，使得 <可测的完成定义>
[上下文证据]   <相关接口签名> <调用点> <类型定义> <既有测试> <相关配置>
[范例]         <本仓库中同类实现的两三个片段>
[格式契约]     只输出 diff / 输出 JSON，字段为 ...
[禁止项]       不新增第三方依赖、不改公共接口、不写跨层调用
```

关键区分：**指令通道（怎么说）** 与 **证据通道（给什么看）** 是同一条信息通道的两端。措辞能提高命中率，但无法弥补缺失的证据——"请遵循本仓库风格"在没有放风格规范或范例时等于没说。

### 2. few-shot 示例的选择

- few-shot 的价值是**把隐式约定显式化**：命名风格、错误处理范式、日志格式、测试写法。
- 示例要**同构**：选取与目标任务结构相似（同层、同类型、同调用模式）的片段，而不是随机贴几段代码。
- 示例要**权威**：从主干的真实实现里取，而不是模型凭空构造的"标准写法"；错误示例会被忠实模仿。
- 数量收益递减：能覆盖关键约定即可，堆得越多越挤占窗口并引入噪声（`[推断]`，具体拐点依任务与模型而定）。

### 3. 上下文窗口预算

把窗口当成一种预算来分配，而不是"能塞多少塞多少"：

| 预算项 | 目的 | 典型占用 |
|---|---|---|
| 任务与约束 | 定义目标与边界 | 小 |
| 精确符号证据（签名/类型） | 保证接口兼容 | 中 |
| 相关实现与调用点 | 保证风格与语义一致 | 中到大 |
| 测试与 oracle | 保证可验证 | 中 |
| 输出格式契约 | 保证可解析、可 diff | 小 |
| 余量 | 留给模型推理与输出 | 应显式保留 |

三条预算规则：

1. **最小充分**：上下文是"回答所需的最小充分集"，不是仓库快照。
2. **留出输出余量**：把输入塞满窗口会导致输出被截断。
3. **抗中段衰减**：最关键的定义不要埋在大段无关内容的中间，靠近首尾放置。`[已确认]` Lost in the Middle 为公开研究观察。

### 4. 检索增强（RAG）用于代码库理解

自然语言 RAG 直接搬到代码上会失手，因为代码的强信号是结构而非语义相似度。三类检索应分工使用：

- **结构化检索（首选）**：用符号表、定义-引用、调用图精确定位目标符号及其依赖/被依赖方。
- **词法检索**：找符号名、字符串、配置键、错误信息。精确、可解释、零幻觉。
- **语义检索**：只用于"意图相似但名字不同"的候选召回，且**必须二次筛选**——它容易召回表面相似、语义不同的片段。

### 5. 代码索引与 embedding

- 分块按**符号边界**切（函数/类/方法），一个块连同签名、类型、紧邻测试一起给出，优于按固定行数硬切。
- 索引必须与代码版本绑定：**分支不可互相污染**，否则检索会命中已删除的旧契约。
- embedding 是补充信号，不应作为唯一检索通道；对代码而言符号名与结构的精确性通常高于语义近邻（`[推断]`）。

### 6. 长上下文 vs 检索的取舍

| 手段 | 优势 | 代价 | 适用 |
|---|---|---|---|
| 塞满长窗口 | 配置简单、无召回损失 | 成本高、噪声大、中段衰减、难归因 | 小仓库、一次性任务 |
| 检索 + 精确插入 | 成本可控、可解释、可复现 | 需索引、有漏召回风险 | 大仓库、持续开发 |

决策规则：**上下文的可解释性与新鲜度优先于容量**。当检索能稳定命中所需符号时，检索优于塞满窗口；当仓库小且任务需要全局一致性时，直接给全量更可靠。

### 7. 上下文污染

污染指把错误、过时、冲突的信息放进窗口，且模型会忠实放大它：

- **过时契约**：给了旧接口签名，模型认真按旧签名写调用。
- **冲突示例**：同时给了两种风格的实现，模型随机选一种或混合。
- **无关噪声**：大段无关文件稀释注意力，挤掉真正相关的定义。
- **毒化内容**：从 issue/注释/依赖文件里检索进来的恶意指令（提示注入），见 K09。

对策：每次生成前做**上下文审计**——列出进入窗口的每个片段及其来源与版本，删掉不能解释其必要性的片段。

### 8. 代码库地图

让模型"看懂仓库"的有效手段是维护一份结构化地图，而不是让它自己摸索：

- **入口与分层**：主入口、各层职责、依赖方向（谁可以调用谁）。
- **符号导航**：核心接口、基类、关键数据结构的定义位置。
- **约定索引**：命名规范、错误处理、日志、测试组织方式所在文件。
- **禁区**：不可改动的公共接口、已废弃模块、生成代码目录。

地图本身应作为高优先级上下文片段提供，并能随代码演进更新。

### 检查清单（生成前）

- [ ] 任务有可测的完成定义吗？
- [ ] 目标符号的真实签名/类型进窗口了吗？
- [ ] 至少一个同构范例进了吗？
- [ ] 约束（依赖、接口、跨层）写清楚了吗？
- [ ] 上下文里有没有过时/冲突片段？
- [ ] 窗口是否留了输出余量？
- [ ] 模型引用到的每个既有符号能否在符号表解析？

### 9. 一个可复用的上下文构建流程

把"给模型看什么"做成流水线而非临时拼凑：

```text
输入：任务描述 T，仓库 R，目标符号 S（若有）
1. 定位：用结构化信号解析 S 的定义、类型、调用点、被调用点
2. 扩展：取 S 的直接依赖与被依赖的签名（不取实现体，除非必要）
3. 找范例：在 R 中检索同类实现（同层/同模式）1-3 个
4. 拉约定：读取风格/错误处理/测试组织相关的约定文件
5. 取测试：找到 S 现有的测试，作为可验证性证据
6. 裁剪：按最小充分原则删片段，留输出余量
7. 审计：列出每个片段的来源与版本，剔除冲突/过时项
输出：上下文清单（片段 + 来源 + 理由）+ 指令块
```

这个流程的产物本身就是"上下文准备"状态的出口证据（K01），可被评审和复用。

### 10. 检索质量的评估

检索是工程，需要可度量的评估，而不是凭感觉：

- **命中率（recall）**：任务真正需要的符号/文件，有多少被召回。漏召回是主要失败源。
- **精确率（precision）**：召回内容里有多大比例真正相关。低精确率带来噪声与污染。
- **新鲜度**：召回结果是否与当前分支版本一致。
- **构建评测集**：从历史任务/修复中整理"给定任务 → 应召回的最小集"，作为回归基准。

`[推断]` 检索评测集是唯一能把"上下文工程"从玄学变成工程的手段；没有它，调参只能靠个案体感。

### 11. 分块与索引更新

- **按符号边界分块**：函数/类/方法为最小单元，附带签名与紧邻测试；跨块引用用符号 ID 连接而非复制全文。
- **层次化索引**：文件级摘要 + 符号级细节两层，先粗召回再精召回，控制单次注入量。
- **新鲜度策略**：索引随提交增量更新或按需重算；不同分支用独立命名空间，禁止跨分支命中。陈旧索引是"看似有证据、实则过时契约"的隐蔽失败源。
- **变更感知**：当依赖的符号变了，缓存里的上下文片段要失效，避免复用过期证据。

### 12. 长上下文 vs 检索：一个决策走查

场景 A：小仓库（几千行）、任务需要改动跨多个模块的命名约定。
→ 直接给全量核心文件更可靠，检索的召回风险大于容量成本。

场景 B：大型单体、任务是修一个具体函数。
→ 结构化检索定位该函数及其依赖，注入最小集；塞全量既不可能也无必要。

场景 C：任务涉及"全仓一致性"，如替换某废弃 API。
→ 先用地检索/符号图找出所有引用点（这是结构化问题），再分批生成，而非让模型在长窗口里自己找。

`[推断]` 共性结论：**能用结构化信号精确定位的问题，就不要交给长窗口的注意力去"找"。**

## 常见陷阱与反例

- **反例：只打磨措辞。** 提示词写得再清楚，没把真实接口和约定放进上下文，生成结果仍会自由发挥。
- **反例：把整个仓库塞进 1M 窗口。** 噪声与中段衰减导致漏掉真正相关的定义。
- **反例：语义检索命中"错的相似"。** 同名/近名符号被召回，模型照错的实现改。
- **反例：索引陈旧。** 检索命中已删除的旧代码，模型基于过时契约生成。
- **易错：few-shot 用模型自造的"标准示例"。** 示例里的坏习惯会被当作规范复制。
- **易错：把上下文当一次性产物。** 代码变了、接口变了，上下文模板不更新，grounding 逐步失效。
- **易错：忽视提示注入。** 从外部内容检索进窗口的指令被模型当命令执行。

## 与其他知识域的连接

- **K01**：本域是"上下文准备"状态的具体实现，其出口证据（上下文清单）由 K01 的状态机消费。
- **K03**：Agent 每一步的观察（工具返回值）本质是动态构造的上下文，返回格式要与本域的预算与新鲜度规则一致。
- **K04**：本域的"引用可解析"不变量直接支撑 K04 的幻觉 API 检测。

## 证据与缺口

- `[已确认]` 自回归条件生成、Lost in the Middle 现象、grounding 降低幻觉为公开研究结论。
- `[推断]` 三类检索分工、按符号边界分块、最小充分上下文、上下文审计流程由机制推导。
- `[待验证]` few-shot 数量收益拐点、长窗口 vs 检索的成本-正确率交叉点、embedding 在代码检索中的相对收益，均需在目标仓库实测。
- 缺口：本工作区无检索质量评测集，召回率/精度类结论一律标待验证，不得编造数字。
