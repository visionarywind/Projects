# K12 质量度量、合规与组织治理

## 范围

质量指标、责任、合规、培训和平台治理。

## 学习重点

- 把 AI 生成行为放入软件生命周期，追踪需求、上下文、变更、测试、发布和运行质量。
- 同时考虑正确性、可维护性、安全、可靠性、性能、成本和人工责任。
- 模型能力和生成代码结论没有项目运行证据时标为 [待验证]。

## 领域边界

覆盖"如何用度量、流程与责任机制，把前面各域的质量控制长期稳定地运转起来"：质量度量体系（DORA、覆盖率、缺陷率/逃逸率）、合规（审计追溯、许可、数据与 AI 使用政策）、组织治理（责任分配、培训、平台团队）、度量误用（Goodhart 定律）、团队效能。

不覆盖：

- 具体度量信号怎么采集属 K08。
- 单个门禁的技术实现属 K06/K07。
- 安全与隐私的具体控制属 K09。
- 架构决策记录属 K11（本域关注其文化与管理）。

分界直觉：其他知识域提供**能力和控制**，K12 提供**持续运转它们的机制**：谁来负责、用什么衡量、越界怎么办、如何培训与审计。核心矛盾是——度量既是改进的指南针，又极易被当成目标而失效（Goodhart 定律）。

## 先修知识

- 度量基础：有效性（是否真的测到了想测的）、可靠性、代理指标与目标变量的差异。
- DORA 四指标的定性含义。
- 合规基础概念：审计追溯、许可（license）、数据保护、SBOM。
- 组织行为基础：激励、指标博弈、责任分配。
- 平台工程与内部开发者平台（paved road）的概念。

## 核心机制

### 1. 质量度量体系

常见指标及其陷阱：

- **DORA 四指标**：部署频率、变更前置时间（lead time）、变更失败率（change failure rate）、恢复时间（MTTR）。它们衡量**交付系统的健康**，不是个人绩效。`[已确认]`（作为框架存在。）具体数值基准随组织类型差异大，标 `[待验证]`。
- **覆盖率**：行/分支/增量覆盖率。覆盖率高不等于测试好——覆盖只说明代码被执行，不说明断言有效。用**增量覆盖率**门禁比追总量更有意义。`[推断]`
- **缺陷率与逃逸率**：单位时间缺陷数、生产缺陷相对于测试发现的缺陷（逃逸率）。逃逸率更能反映门禁有效性。
- **评审时效**：PR 首次响应时间、合并时长，反映流程是否阻碍交付。
- **AI 相关指标**：AI 生成代码的占比、AI 变更的事故率/回滚率、AI 审查的采纳率。这些用于评估 AI 工具的净效应，而非考核人。`[待验证]`（缺乏公认标准。）

度量设计原则：

- 一个指标必须配一个"它可能如何被错误优化"的反面说明。
- 度量团队/系统，不度量个人（见团队效能）。
- 优先聚合与趋势，而非单点数字。

### 2. 度量误用与 Goodhart 定律

Goodhart 定律：**当一个度量成为目标，它就不再是好的度量**。`[已确认]`（作为概念。）

典型崩坏路径：

- 覆盖率成为目标 → 写无断言的"测试"刷覆盖率。
- 缺陷数成为目标 → 不报缺陷、把 bug 降级成"特性"、拆小算少。
- 部署频率成为目标 → 无意义的小发布刷数字。
- 用 AI 提升指标 → 用 AI 生成大量无价值测试/文档，指标好看但质量未变。
- 个人排名 → 团队内耗、隐藏问题、跨团队推诿。

对冲手段：

- 指标组合看（速度 + 稳定性 + 成本），单一指标不作决策。
- 度量系统与流程，不排名个人。
- 定期审查指标是否仍与目标一致（度量本身也会漂移）。
- 允许定性判断补充定量指标，避免"数字没坏就没问题"的错觉。

### 3. 合规

- **审计追溯**：从需求 → 变更 → 审查 → 测试 → 发布 → 运行的全链路留痕，能回答"这个行为谁在何时因为什么做出"。AI 参与的变更同样要可追溯（模型、版本、prompt、审查记录）。
- **许可合规**：依赖许可扫描，识别 copyleft/商业限制，避免引入不兼容许可。SBOM 是响应基础。
- **数据合规**：数据分类、保留期、删除权（被遗忘权）、跨境传输限制、PII 处理（详见 K09）。
- **AI 使用政策**：哪些数据可发给外部模型、哪些场景必须人工复核、AI 产出是否需要声明、模型供应商的数据使用条款。
- **生成内容合规**：AI 生成代码可能复制受版权保护的片段；生成内容的知识产权与来源需要政策约束。`[待验证]`（法律结论需专业审查。）

合规不是一次性检查，而是持续的控制 + 证据。

### 4. 组织治理

- **责任分配**：明确 code owner、AI 产出的责任人（合并者是责任人）、安全与合规负责人。责任不能因为"AI 写的"而模糊。
- **培训**：让成员理解 AI 的能力边界、常见失效模式、门禁的意义——不理解门禁的人会绕过门禁。
- **平台团队（paved road）**：提供经治理的默认路径（模板、CI、门禁、扫描、可观测性 SDK），让正确做法成为最省力的做法。降低"走正路"的成本比惩罚"走歪路"更有效。
- **门禁治理**：门禁的增删、豁免、过期要有统一机制与负责人；否则门禁只增不减，成本压垮交付（与 K06/K07 联动）。
- **AI 使用登记**：登记在用的 AI 工具、权限、数据范围、审批状态，便于审计与事故响应。

### 5. 团队效能

- **度量系统不等于度量人**：个人指标（如个人提交数、个人缺陷数）会导致博弈与伤害；效能是系统属性。
- **SPACE 框架**（Satisfaction、Performance、Activity、Communication、Efficiency）提示效能是多维的，单看活跃度（commit 数）会误导。`[推断]`
- **关注流（flow）**：WIP 限制、前置时间、排队时间，比"忙碌程度"更能反映效能。
- **心理安全**：复盘要blameless——追系统缺陷而非追人，否则问题被掩盖，度量失真。

### 6. 检查清单

```text
[ ] 质量指标成组使用(速度+稳定+成本), 不单点决策
[ ] 指标度量系统/团队, 不排名个人
[ ] 每个指标有"可能被错误优化"的说明
[ ] AI 参与的变更可追溯(模型/版本/审查/责任人)
[ ] 依赖许可与 SBOM 有持续扫描
[ ] AI 使用政策明确(数据范围/复核/声明)
[ ] 门禁有增删与豁免的统一治理与过期机制
[ ] 复盘 blameless, 改进项带 owner 与截止
```

### 7. 决策矩阵

| 情境 | 推荐做法 | 反模式 |
|---|---|---|
| 想提升交付速度 | 看 DORA 组合 + 前置时间 | 只看部署频率刷数字 |
| 想提升测试质量 | 增量覆盖率 + 逃逸率 | 追总覆盖率 |
| 想评估 AI 工具 | 净效应指标 + 对照 | 用 AI 直接刷指标 |
| 团队信心不足 | 降低走正路的成本 | 增加惩罚性门禁 |
| 合规要求 | 持续控制 + 可导出证据 | 一次性检查 |

### 8. 设计一组互补的度量

单指标必然被博弈，组合与反指标是基本手段：

| 主指标 | 反指标（防止错误优化） | 说明 |
|---|---|---|
| 部署频率 | 变更失败率 | 只快不稳 → 失败率上升暴露 |
| 覆盖率 | 变异测试存活率 / 逃逸率 | 假测试被测出 |
| 缺陷关闭数 | 缺陷重开率 / 逃逸率 | 防止仓促关闭 |
| AI 生成占比 | AI 变更事故率/回滚率 | 防止只追数量 |
| 前置时间 | 评审耗时 / 队列时间 | 定位瓶颈在谁 |

原则：**任何鼓励"更快/更多"的指标，都要配一个约束"更好/更稳"的指标**，否则系统会朝未被约束的方向漂移。

### 9. 治理机制的落地形态

- **平台即产品**：把合规、门禁、扫描、可观测做成默认提供的平台能力（paved road），开发者用默认路径就自动合规。`[推断]`
- **门禁生命周期管理**：每个门禁有 owner、目的、误报率、成本；定期复审，失效或高成本即下线。
- **豁免机制**：允许显式、留痕、带过期的豁免（与 K06/K07 一致），禁止静默跳过。
- **度量评审**：定期检查指标是否仍与目标一致、是否被博弈、是否需要替换。
- **事故驱动的治理**：每次事故的改进项（runbook、门禁、告警）进入治理台账，闭环跟踪。

### 10. AI 使用政策要点（示例框架）

```text
[ ] 可用的 AI 工具与模型清单(经审批)
[ ] 数据分级: 哪些数据可发送到外部模型
[ ] 必须人工复核的场景(安全/合规/资金/生产变更)
[ ] AI 产出的声明与署名要求
[ ] AI 产出的追溯字段(模型/版本/prompt/审查人)
[ ] 违规使用的处理与报告渠道
[ ] 政策的复审周期与负责人
```

政策要可执行、可审计，而不是原则声明；否则无法落地也无法验证。

### 11. 度量健全性检查

引入任何新指标前，先用四个问题自检：

```text
1) 它测的是哪个真实目标? (代理是否偏离目标)
2) 如果被当成目标, 团队会怎么以最省力的方式刷高它?
3) 它度量的是系统还是人? (若是人, 会不会引发博弈)
4) 它是否与其他指标冲突? 冲突时如何权衡?
```

如果第 2 问想不出作弊路径，通常是因为还不够熟悉被度量的系统；能想出的作弊路径就是必须预先设计的反指标（见上表）。**度量的价值在于驱动正确的行动，而不是产出好看的数字。**

### 12. 从度量到行动的闭环

度量不产生改进，闭环才产生改进：

```text
度量 -> 解读(结合定性与上下文) -> 识别瓶颈 -> 形成假设
     -> 小步试验 -> 验证效果 -> 标准化或回退 -> 更新度量
```

关键：每一步都要有 owner 与时间盒；没有行动项的度量是装饰。复盘（blameless）与改进项跟踪是这个闭环的常态化载体。

## 常见陷阱与反例

- 反例：把覆盖率设成 90% 硬指标，团队写出大量 `assert True` 式测试达标，缺陷率不变。
- 反例：按个人缺陷数排名，工程师开始不报 bug 或把 bug 归为"已知限制"，隐患被藏起来。
- 反例：用 AI 批量生成测试和文档冲指标，数字漂亮但质量没变，还增加了审查负担。
- 反例：门禁只加不减，几年后流水线要跑一小时，所有人绕开——治理变成负担。
- 反例：AI 生成的变更没有记录模型与审查，出事故后无法回答"这个决策谁负责、依据是什么"。
- 反例：引入 GPL 依赖进闭源产品，发布后才在许可扫描中发现，返工成本高。
- 易错：把度量当成目的，忘记它只是理解系统的工具；指标一旦变成 KPI 就开始失真。
