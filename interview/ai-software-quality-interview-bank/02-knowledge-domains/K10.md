# K10 可靠性、性能、容量与成本

## 范围

SLO、并发、延迟、资源、限流和预算。

## 学习重点

- 把 AI 生成行为放入软件生命周期，追踪需求、上下文、变更、测试、发布和运行质量。
- 同时考虑正确性、可维护性、安全、可靠性、性能、成本和人工责任。
- 模型能力和生成代码结论没有项目运行证据时标为 [待验证]。

## 领域边界

覆盖"系统在压力下仍满足承诺，且代价可控"：可靠性设计（冗余、隔离、降级、重试、超时、熔断）、性能回归与基准、容量规划与压测、成本模型（尤其 token/算力成本）、限额与熔断。

不覆盖：

- 观测信号如何采集、告警如何配置属 K08（本域定义目标，K08 提供测量）。
- SLO 与发布节奏的联动执行属 K07。
- 单次性能剖析的排障流程属 K08；本域关注"是否达标、是否回归、能否扩容"。
- 成本的组织预算与治理属 K12；本域建立单位成本模型。

分界直觉：性能是"单位资源能做多少事"，可靠性是"承诺不被打穿"，容量是"按需求预留多少资源"，成本是"这些资源值不值"。四者共享同一套资源与需求模型，必须一起权衡——只优化其中一个必然牺牲另一个。

## 先修知识

- 延迟与吞吐、并发与并行、排队的基本直觉。
- 分位数与长尾、Little's Law（并发 ≈ 到达率 × 停留时间）的定性理解。
- 缓存、连接池、批处理、背压的基本概念。
- 重试、退避、幂等、超时的语义。
- 基本成本结构：计算、存储、网络出口、外部 API 调用。
- LLM 服务的特殊成本项：输入/输出 token 定价、上下文长度、缓存、算力（GPU 时）。

## 核心机制

### 1. 可靠性：目标、冗余、隔离、降级

- **SLO/错误预算**：定义见 K08。可靠性设计的预算就是错误预算——把容错能力花在影响用户的地方。
- **冗余**：N+1、多可用区/多副本，消除单点。冗余必须配合故障转移验证，否则是"纸面冗余"。
- **故障隔离（舱壁/bulkhead）**：资源池按租户/功能隔离，防止一个慢依赖拖垮全部线程池。线程池、连接池、信号量、独立部署都是舱壁。
- **降级（graceful degradation）**：依赖不可用时返回降级结果（缓存旧值、关闭非核心功能、简化响应），而不是直接失败。
- **重试与退避**：重试要配指数退避 + 抖动（jitter），并设上限；无退避的重试会放大故障（重试风暴）。
- **超时**：每个外部调用必须有超时，且短于上游超时，形成超时预算递减链。
- **熔断**：连续失败达到阈值后快速失败（open），过一段时间半开试探，成功则闭合。
- **幂等**：重试/重放不应产生重复副作用，是安全重试的前提。

失败模式：无限重试 + 无超时 = 级联雪崩；共享线程池 + 单慢依赖 = 全站排队。

### 2. 性能回归

性能回归往往来自无害的重构：多一次序列化、循环里做 I/O、少了一个索引、缓存失效。

- **基准（benchmark）**：可重复、有代表性负载、固定环境；记录分布而非单点。
- **回归门禁**：CI 中对关键路径跑基准，与基线对比，超过容差则告警或阻断。
- **噪声控制**：重复运行取统计量（中位/分位）、控制环境变量、区分信号与抖动。
- **统计显著性**：小差异在噪声内不可判定；样本不足不做结论。
- **剖析（profiling）**：CPU（火焰图/采样）、内存（分配热点、泄漏）、I/O、锁竞争。先定位热点，再优化。

反模式：在不可比的环境里对比基准（不同机器/负载/数据），得出"优化了 30%"的假结论。

### 3. 容量规划与压测

- **需求模型**：峰值 QPS、请求大小分布、读写比、并发用户数，以及这些量的增长趋势。
- **资源模型**：每请求资源消耗 × 峰值 QPS = 所需资源；再叠加冗余（N+1）与突发 headroom。
- **排队论直觉**：利用率接近 100% 时排队延迟急剧上升（非线性）；健康系统通常把稳定利用率控制在有 headroom 的区间。`[推断]`（具体目标利用率随系统标定。）
- **压测类型**：负载测试（预期峰值）、压力测试（找拐点）、浸泡测试（长时间泄漏/抖动）、尖峰测试（突发流量）。
- **验收**：压测要验证的是"在目标负载下 SLO 是否满足"，而不只是"系统会不会挂"。

### 4. 成本模型

云与 AI 服务的成本要落到**单位经济**：每次请求、每千 token、每次推理的成本。

- **token 成本**：输入 token + 输出 token 分别计价；上下文越长成本越高，且长上下文还抬高延迟。RAG 与压缩上下文是成本与质量的权衡。
- **缓存**：prompt caching、结果缓存、语义缓存可显著降本，但要注意失效与一致性。
- **算力成本**：GPU 时、利用率、批处理（batching）提高吞吐利用率；低利用率是主要浪费。
- **存储与出口**：日志/追踪的存储、跨区流量、外部 API 调用。
- **成本可观测**：按功能/租户/请求打成本标签，才能定位"谁在烧钱"（与 K08 标签治理相关）。

关键不变量：**成本要能和需求挂上钩**——每单位业务的成本。否则无法判断优化是否值得。

### 5. 限额、熔断与负载削减

- **限流**：按用户/租户/接口设速率与并发上限，保护自身与下游。令牌桶/漏桶是常用实现。
- **配额**：长周期用量上限（日/月），用于成本控制与公平性。
- **熔断**：见可靠性一节。
- **负载削减（load shedding）**：过载时主动丢弃低优先级请求，保核心功能。
- **背压**：下游慢时向上游施压，而不是无限缓冲导致延迟失控。
- **舱壁 + 限流 + 熔断 + 降级**组合成过载保护网。

### 6. 决策矩阵

| 场景 | 主策略 | 配合手段 | 风险 |
|---|---|---|---|
| 依赖抖动 | 重试+退避+超时 | 熔断 | 无退避放大故障 |
| 依赖长时间不可用 | 熔断+降级 | 缓存旧值 | 降级结果正确性 |
| 突发流量 | 限流+负载削减 | 自动扩容 | 扩容延迟追不上峰值 |
| 单租户打爆资源 | 舱壁+配额 | 熔断 | 隔离粒度不当 |
| 成本超预算 | 单位成本治理 | 缓存/批处理/降采样 | 为省钱牺牲质量 |

### 7. 检查清单

```text
[ ] 所有外部调用有超时且短于上游超时
[ ] 重试有退避+抖动+上限, 且操作幂等
[ ] 存在熔断与降级路径, 且降级被测试
[ ] 关键路径有基准与回归门禁
[ ] 峰值负载下 SLO 经压测验证
[ ] 资源有冗余(N+1)且故障转移被演练
[ ] 单位成本(请求/token/推理)可观测
[ ] 限流/配额/负载削减策略已定义
```

### 8. 缓存：性能与成本的双刃剑

缓存同时改善延迟、降低后端负载、降低 token/算力成本，但它引入一致性风险：

- **缓存键必须包含所有影响结果的维度**：用户、租户、权限、语言、模型版本、温度。漏一个维度就是串数据。
- **失效策略**：TTL、写时失效、事件失效；缓存穿透（不存在的数据反复查）、缓存击穿（热点失效瞬间打爆后端）、缓存雪崩（大量同时失效）。
- **一致性取舍**：强一致 ↔ 性能；对可容忍陈旧的数据用缓存，对授权/金额等用直读或严格失效。
- **AI 场景的特殊性**：语义缓存（相似问题复用答案）成本收益高，但相似度阈值误判会把不同问题的答案串用，需要人工抽检。

缓存收益要量化：命中率 × 单次成本节省 vs 失效开销与不一致风险。

### 9. 可靠性演练

冗余与降级只有被验证过才算数：

- **故障注入（混沌工程）**：主动制造依赖超时、实例宕机、网络分区，观察系统是否正确降级/转移。
- **故障转移演练**：定期真的切换主副本/可用区，确认切换时间在容忍范围内。
- **容量演练**：按规划峰值实压，确认扩容策略与限流阈值有效。
- **回滚演练**：与 K07 联动，验证恢复路径可用。

原则：**在受控条件下主动制造故障，好过在生产里第一次遇到它。** `[推断]`

### 10. 检查清单（容量与成本）

```text
[ ] 峰值 QPS/并发需求有明确来源与增长假设
[ ] 资源按 N+1 冗余预留, 有 headroom
[ ] 压测在目标负载下验证 SLO, 非仅"不挂"
[ ] 扩容策略与触发条件明确, 且演练过
[ ] 单位成本(请求/token/推理)按维度可观测

[ ] 故障注入/转移/回滚定期演练
```

### 11. 一个超时预算的推演

超时预算要求从外到内逐层收紧，否则重试会叠加成远超用户容忍的等待：

```text
用户请求 SLO: 1s 内返回
  网关超时:        950ms
    服务 A 超时:   800ms
      服务 B 超时: 500ms
        依赖 C 超时: 200ms

若每层都重试 3 次而不缩短预算:
  最坏耗时 ≈ 200ms × 3(B) × 3(A) ≈ 1.8s > 用户等待
  且瞬间产生 9 倍于正常的依赖请求 → 放大故障
```

对策：超时随层递减；重试次数在最内层受限；重试总时间包在父超时内（budget）；幂等才可重试。

### 12. 性能优化的顺序

不要凭直觉优化，按证据排序：

1. **先测**：定位真正的热点（profiling / trace 关键路径），而非最显眼的代码。
2. **减少工作**：算法、去重、批处理、避免重复序列化——比"让它更快"更有效。
3. **减少往返**：批量化、合并 RPC、缓存。
4. **并行化**：仅在前三者做尽后，且注意并发带来的资源与顺序风险。
5. **加资源**：最后手段，且要算成本。

反模式：第一步就加机器或换语言，忽略 O(n²) 之类的根本问题。

## 常见陷阱与反例

- 反例：给下游加无限重试但不加超时与退避，一次抖动被放大成重试风暴，拖垮整个调用链。
- 反例：在本地开发机上对比优化前后性能，环境差异远大于改动影响，结论无意义。
- 反例：压测只测"会不会挂"，没有在目标负载下校验 SLO，上线后 p99 超标但容量"看起来够"。
- 反例：为了降低 token 成本，无脑截断上下文，导致答案质量下降而引入业务错误——省了小钱亏了大钱。
- 反例：SLO 定 99.99% 却只有单实例无冗余，预算必然击穿，团队对指标失去信任。
- 反例：缓存了带用户差异的结果却没进 key，A 用户看到 B 用户的数据。
- 易错：把利用率优化到接近 100% 当成绩，尾部延迟与突发余量被吃掉，稳定性反而下降。
