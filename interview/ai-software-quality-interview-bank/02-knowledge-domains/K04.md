# K04 生成代码正确性与可维护性

## 范围

行为、接口、复杂度、风格、依赖和技术债。

## 领域边界

**本域解决什么。** 回答两支问题：生成的代码**行为对不对**（正确性），以及**能不能长期维护**（可维护性）。前者包括逻辑、边界、类型、契约、并发、错误处理；后者包括一致性、命名、重复、复杂度、依赖、风格与技术债。

**本域不负责什么。**

- 不负责"怎么让模型生成得对"（K02 上下文工程、K03 Agent 编排），本域只做生成结果的判定。
- 不负责测试生成与 oracle 设计（K05），本域消费其证据。
- 不负责流水线怎么跑、门禁如何阻塞（K06/K07）。
- 不负责运行期性能剖析与容量（K10），本域只做静态层面的复杂度与资源审查。

**与相邻域的接口。**

| 本域交付 | 接收方 |
|---|---|
| 正确性判据（类型/契约/边界/并发） | K05（测试设计的目标） |
| 可维护性判据（一致性/重复/复杂度） | K06（审查与规则） |
| 依赖引入与幻觉 API 的检出点 | K09（供应链） |
| 技术债识别与登记 | K11（架构与债演进） |

## 先修知识

- 类型系统与契约：接口、泛型、可空性、前置/后置条件。
- 常见缺陷模式：边界值、空值、并发竞态、资源泄露、整数溢出、错误吞噬。
- 代码质量度量：圈复杂度、重复率、耦合/内聚。
- 依赖管理：锁文件、语义化版本、传递依赖。
- 语言与框架的惯用法（idioms）。

## 核心机制

### 1. 正确性验证的三条通道

| 通道 | 机制 | 能证明什么 | 盲区 |
|---|---|---|---|
| 测试 | 执行具体用例，比对 oracle | 已知输入的期望行为 | 未覆盖的输入、oracle 本身错 |
| 类型检查 | 静态验证类型/契约一致性 | 类型层面的不可能状态 | 类型系统外的不变量（业务规则） |
| 契约/断言 | 前置后置条件、不变量检查 | 运行时约束被满足 | 未声明的约束 |

三者互补，缺一不可。**"能编译"只证明类型通道通过，不证明行为正确**（K01 反复强调的不变量）。

### 2. 生成代码的典型正确性缺陷

- **边界条件**：空集合、单元素、越界、最大/最小值，模型常给"主路径正确、边界全错"的实现。
- **空值/缺失处理**：假设输入总是存在，漏掉 nil/undefined/零值。
- **错误吞噬**：`catch` 后不处理、不记录、返回默认值，把失败伪装成成功。
- **并发正确性**：共享状态无同步、复合操作非原子、锁顺序不一致。
- **资源管理**：文件句柄、连接、锁未在异常路径释放。
- **契约漂移**：实现了意图但违反既有接口约定（如改变了异常语义、返回顺序）。
- **off-by-one 与算错**：循环边界、索引、切片范围。
- **幻觉 API**：调用不存在的函数/参数/配置项，见下节。

### 3. 幻觉 API 与依赖

模型会生成"看起来合理但不存在"的东西：

- 不存在的库函数、方法、参数名、配置键。
- 不存在或已被弃用的第三方包（有时是拼写相近的恶意包名，供应链风险）。
- 版本不匹配的 API（用了新版本签名去调旧版本）。

检出手段：

1. **符号可解析性检查**：每个对既有符号的引用必须能在真实符号表/编译器中解析；解析不到即判为幻觉。`[推断]` 这是低成本、高确定性的门禁。
2. **依赖白名单/锁文件校验**：新依赖必须已登记、来源可信、版本已锁。
3. **编译/类型检查**：能挡住大部分签名级幻觉，挡不住语义幻觉。

### 4. 可维护性维度

| 维度 | 具体检查 | 为什么重要 |
|---|---|---|
| 一致性 | 与仓库既有风格、错误处理、日志范式是否一致 | 降低认知负担，避免"两种写法" |
| 命名 | 是否表意、是否与领域词表一致 | 命名是主要文档 |
| 重复 | 是否复制粘贴出可提取的重复逻辑 | 重复是缺陷与漂移之源 |
| 复杂度 | 圈复杂度、嵌套深度是否超阈值 | 复杂处即缺陷聚集处 |
| 依赖 | 是否引入非必要依赖、是否放大依赖面 | 依赖是长期负债 |
| 测试友好 | 是否可注入、可隔离、无隐藏全局状态 | 决定可验证性 |
| 债登记 | 出现的妥协是否被记录并排期 | 债务可见才可管理 |

### 5. 生成代码的审查要点

人工审查 AI 生成代码时，优先级应与审查人工代码不同，重点从"语法细节"转向"意图与边界"：

1. **意图对不对**：代码实现的是需求，还是实现了一个相邻但不同的问题？
2. **接口契约**：有没有偷偷改了公共签名、异常语义、返回结构？
3. **边界与失败路径**：空值、越界、错误分支是否都处理了？
4. **依赖与外部调用**：新增了什么依赖？调用了什么外部服务？有无幻觉？
5. **测试是否验证了意图**：测试是在验证行为，还是在迁就实现（见 K05）？
6. **可维护性**：命名、重复、复杂度是否在可接受范围？

### 6. 与人工代码的质量对齐

原则：**AI 生成的代码不享受任何豁免**。它必须过与人工代码相同的质量门禁。若要差异化，只能是"更严"而不能"更松"（因为生成速度带来更高的审查吞吐压力）。`[推断]`

对齐的具体做法：

- 同一套 lint/format/类型规则，禁止为通过而放宽规则。
- 同一套覆盖率与审查阈值。
- 同一套依赖审批流程。
- 生成代码同样进入技术债台账，不因"反正能生成"就放任。

### 7. 决策矩阵：如何判定一段生成代码可合入

| 检查 | 工具化程度 | 失败时的动作 |
|---|---|---|
| 类型/编译通过 | 高（可自动） | 阻断，回改 |
| 单测覆盖主路径+边界 | 中（需设计用例） | 阻断，补测试 |
| 符号可解析（防幻觉 API） | 高 | 阻断 |
| 依赖白名单 | 高 | 阻断，走审批 |
| 契约/接口未破坏 | 中（需对比基线） | 阻断，需评审 |
| 可维护性（重复/复杂度） | 中（规则+人工） | 警告或要求重构 |
| 意图正确 | 低（需人判断） | 人工评审决定 |

### 8. 正确性缺陷的逐类检查法

把常见缺陷类别做成一张"生成后自检表"，逐项对照：

| 类别 | 具体问法 | 常见生成表现 |
|---|---|---|
| 输入边界 | 空/单元素/极值/超限会怎样？ | 只处理主路径 |
| 空值 | 缺失/None/未定义如何处理？ | 假定一定存在 |
| 错误路径 | 异常是否被正确传播/记录？ | 空 catch、吞异常 |
| 并发 | 共享状态是否同步？复合操作是否原子？ | 单线程假设 |
| 资源 | 异常路径是否释放句柄/锁/连接？ | 只在成功路径释放 |
| 数值 | 溢出/精度/除零？ | 直接用原始类型 |
| 契约 | 异常语义/返回顺序/副作用是否变？ | 实现意图但破坏约定 |
| 外部符号 | 引用的函数/参数/配置是否存在？ | 幻觉 API |

`[推断]` 逐类检查比"泛读 diff"更有效，因为生成缺陷往往成簇出现在某一类，而非随机分布。

### 9. 可维护性的重构指引

当生成代码在一致性/重复/复杂度上越界时，修复方向：

- **风格不一致**：抽取并复用仓库既有的错误处理、日志、校验辅助函数，而不是让新代码自带一套。
- **重复**：把复制出的相似块提取为参数化函数，但注意别过度抽象——两三处相似就抽取往往制造更差的抽象。
- **复杂度过高**：拆成有名字的小函数，用早返回替代深嵌套，把循环内条件提取为谓词。
- **隐藏全局状态**：把依赖显式注入，让代码可隔离测试。
- **依赖膨胀**：优先用标准库/既有依赖，新增依赖要有理由并登记。

原则：**生成代码的"第一版"通常追求可跑，可维护性需要一次显式的整理；这次整理不能靠继续生成，要靠理解。**

### 10. 一个审查走查

AI 生成了如下片段：

```python
def find_user(uid):
    conn = get_conn()
    cur = conn.cursor()
    row = cur.execute("SELECT * FROM users WHERE id = " + uid).fetchone()
    return row
```

审查逐项：

1. **正确性**：SQL 拼接（注入）、无空值处理（`uid` 非法时可能异常）、未关闭 cursor/conn（资源泄露）。
2. **契约**：若原实现约定返回 None 表示不存在，`fetchone()` 恰好符合；但 `SELECT *` 使返回结构随表结构漂移。
3. **可维护性**：命名尚可，但硬编码 SQL 未复用既有的参数化查询辅助。
4. **修复方向**：参数化查询、显式处理不存在、用连接管理（with）、避免 `SELECT *`、复用仓库查询范式。

这个走查同时命中 K04 正确性、K09 安全（注入）与 K06 审查清单，说明四个域在同一个 diff 上协同。

## 常见陷阱与反例

- **反例：用"能编译"当作正确性证明。** 类型通过只说明类型层面一致，业务逻辑可能完全错。
- **反例：测试迁就实现。** 测试断言照抄生成代码的输出，等于把 bug 固化成"期望"（K05 展开）。
- **反例：为通过 lint 而放宽规则。** 在生成代码所在目录加 `# noqa` / `eslint-disable` 批量压制，掩盖真实问题。
- **反例：引入模型幻觉的包名。** 编译可能通过（若恰好存在同名包），但供应链未审计。
- **反例：错误吞噬。** 空 catch 让失败静默，运行"成功"但状态已损坏。
- **易错：只审主路径。** 边界与错误分支才是缺陷聚集地。
- **易错：把重复当成"局部一致性"。** 生成代码常复制既有片段，短期看似风格统一，长期是漂移源。
- **易错：忽视并发。** 生成的代码常在单线程假设下正确。

## 证据与缺口

- `[已确认]` 编译/类型通过不构成行为正确性证明；幻觉 API 与依赖为已知的模型输出风险。
- `[推断]` "AI 代码不享受豁免、只能更严"、符号可解析性检查作为门禁、审查重点转向意图与边界，由机制推导。
- `[待验证]` 生成代码在边界/并发缺陷上的相对发生率、复杂度阈值、可维护性收益，需在目标项目对比实测。
- 缺口：本工作区无生成代码缺陷统计，任何"缺陷率下降 X%"类结论均不得写入。
