# K08 可观测性、调试与故障排查

## 范围

日志、指标、trace、复现和根因分析。

## 学习重点

- 把 AI 生成行为放入软件生命周期，追踪需求、上下文、变更、测试、发布和运行质量。
- 同时考虑正确性、可维护性、安全、可靠性、性能、成本和人工责任。
- 模型能力和生成代码结论没有项目运行证据时标为 [待验证]。

## 领域边界

覆盖"生产运行中如何用证据理解系统、定位异常、恢复并复盘"：结构化日志、指标、分布式追踪、告警设计、SLO/SLI/错误预算、故障排查流程、AI 辅助的日志聚类与根因分析。

不覆盖：

- 可靠性目标如何与业务协商、容量与降级设计属 K10（本域消费 SLO，不定义它）。
- 发布/回滚的执行机制属 K07（本域提供触发回滚的信号）。
- 日志中的 PII、审计留痕、供应链属 K09。
- 度量如何组织化使用属 K12。

分界直觉：K07 回答"要不要撤回这次发布"，K08 回答"为什么坏、坏在哪、怎么先止血"。故障排查的第一原则是**先缓解、后根因**：用户受影响时，恢复服务优先于弄清机制，除非弄清机制是恢复的前提。

## 先修知识

- 日志、指标、追踪三种信号的差异与各自成本。
- 分位数（p50/p95/p99）与平均值的差异，以及长尾为何重要。
- 时间序列、标签（label/dimension）与基数（cardinality）的基本概念。
- 分布式调用跟踪、span、上下文传播的基础。
- SLO/SLI/错误预算的定义。
- 基本统计直觉：相关不等于因果、采样偏差、显著性。

## 核心机制

### 1. 结构化日志

日志是带时间戳的事件流。可观测性要求日志是**结构化事件**而非自由文本：

- 固定字段：时间、级别、服务、版本、环境、trace_id/span_id、请求/用户标识、事件名。
- 错误日志必须携带根因上下文：异常类型、堆栈、上游依赖返回码、重试次数。
- 级别语义要一致：ERROR 表示需要人介入的问题，不是"打印点东西"；WARN 表示潜在异常；INFO 记录关键状态转换。
- 采样与聚合：高流量路径按比例采样，错误全量保留。
- 成本约束：日志量线性增长，热存储贵；冷热分层与保留期要按合规（K09）与排障需要平衡。
- 脱敏：PII、密钥、token 不进日志；在写入端脱敏而非查询端。

关键不变量：**日志必须能把一个请求在多服务间的轨迹串起来**——靠 trace_id/关联 ID 贯穿。没有关联 ID 的日志在微服务下几乎不可用于定位。`[推断]`

### 2. 指标与两类黄金信号

- 指标类型：counter（单调计数，适合算比率）、gauge（瞬时值）、histogram（分布，用于分位数）。
- RED（面向服务/请求）：Rate（请求速率）、Errors（错误率）、Duration（时延分布）。
- USE（面向资源）：Utilization（利用率）、Saturation（饱和度/排队）、Errors（错误）。
- 分位数必须在服务端由 histogram 聚合，客户端算平均会掩盖长尾。

反模式：

- 用平均值表示延迟：均值正常但 p99 爆炸，用户体感与服务指标背离。
- 标签基数爆炸：把 user_id、request_id 当标签，时间序列数爆炸拖垮存储。
- 指标命名不一致，同一含义在不同服务用不同名字，无法聚合。

### 3. 分布式追踪

- 一条 trace 由多个 span 组成，span 之间有父子/因果关系；通过上下文传播跨进程、跨消息队列传递。
- 采样策略：head-based（入口决定，简单但可能漏掉慢/错请求）与 tail-based（收集后按条件保留，贵但能保证错误/慢请求被采到）。
- 用途：定位关键路径上的瓶颈、识别哪一跳贡献了延迟/错误、发现重试风暴。

失败模式：

- 异步/消息场景上下文传播断裂，trace 断成多段，错误无法归因到上游。
- 全量采样导致存储与开销过高，于是无采样，结果错误请求恰好没被采到。

### 4. 告警设计

告警要回答"现在是否需要人介入"，不是"某个数值超过了某条线"。

- **症状告警优先于原因告警**：告"用户登录失败率上升"，而不是告"某个内部队列深度瞬时升高"。原因告警容易误报且通常不是用户可感知的。
- **基于 SLO 的烧钱率（burn rate）告警**：按错误预算的消耗速度触发，兼顾快慢——短窗口高消耗触发紧急，长窗口低消耗触发工单。`[推断]`（具体窗口与倍数随项目标定。）
- 降噪：告警分组、抑制（依赖故障时抑制下游）、静默计划维护、去重。
- 可执行性：每条告警关联 runbook（怎么查、怎么缓解）、负责人、影响面。
- 分级：P1 立即呼叫、P2 工作时段处理、P3 记录。

反模式：全员通知所有告警导致"告警疲劳"，最终所有人忽略告警；这是比没有告警更危险的状态。

### 5. SLO / SLI / 错误预算

- SLI（指标）：可测量的用户视角指标，如"HTTP 2xx/总请求比""成功读取占比""请求延迟 < 阈值的比例"。
- SLO（目标）：SLI 的期望水平，如"30 天滚动窗口内成功率 ≥ 99.9%"。
- 错误预算：1 - SLO，允许的失败量。预算充足时可以激进发布，预算耗尽则冻结高风险变更。

常见错误：

- 把技术指标（CPU 使用率）当 SLI，它不反映用户体感。
- SLO 定得过高（99.999%）导致预算几乎不可用，团队被迫造假或直接放弃。
- 只设一个 SLO 覆盖所有接口，掩盖关键路径的差异。

### 6. AI 辅助根因分析

AI 在这类任务里的可落点：

- **日志聚类/模板挖掘**：把海量异构日志归并成少量模板，异常模板数量突增常指向故障（Drain 等在线模板挖掘思路）。`[推断]`
- **异常检测**：对指标做时序异常检测，辅助发现偏离基线的信号。
- **根因候选排序**：结合最近变更（部署/配置/开关）与 trace 关键路径，给出可疑组件排序。
- **历史工单检索**：RAG 检索相似历史故障与 runbook，加速分诊。

必须坚守的边界：

- **相关性不等于因果。** 聚类出的"异常模板"可能与故障同时发生但无因果。
- 模型给出的根因是**候选假设**，必须用可观测证据验证后才能写入结论。
- 数据漂移、日志格式变化会让聚类/检测失效，需要监控模型本身的准确性。
- AI 归因不能替代缓解：先止血，再验证假设。

### 7. 故障排查流程

```text
1. 检测     告警/SLO 烧钱触发
2. 分诊     影响面多大? 哪些用户/功能? 是否在扩散?
3. 缓解     优先恢复: 回滚/切流量/开 kill switch/限流降级 (K07/K10)
4. 定位     用信号收敛: 最近变更 -> 关键路径 -> 依赖健康
5. 修复     根因修复, 走常规发布门禁
6. 复盘     时间线 + 根因 + 逃逸原因 + 可执行的改进项(带 owner)
```

分诊时最重要的两个问题：**最近有什么变更**（部署、配置、开关、依赖、证书、上游），以及**影响是否与某维度相关**（区域/版本/租户/请求类型）。变更相关性是最高信噪比的线索之一。

### 8. 复现与差分调试

排障的难点常是"无法复现"。可复现性要靠先设计而不是事后碰运气：

- **请求捕获**：记录足以重放的输入——请求体、头部、认证上下文（脱敏后）、随机种子、时间戳相关的输入。
- **环境快照**：服务版本、配置、特性开关状态、依赖版本、数据一致性检查点。行为差异常来自"开关/配置组合"而非代码。
- **确定性重放**：固定随机种子、模拟外部依赖、冻结时间，使同一输入产生同一路径。
- **差分调试**：不猜根因，而是找"好与坏的两个观测"之间的最小差异——二分查找引入问题的变更（bisect）、对比健康与异常请求的 trace、对比两个环境的配置。
- **最小化复现**：从复杂现象收敛到最小输入组合，去掉无关变量，是定位的本质。

差分调试的核心問題永远相同：**"坏的这次和好的那次，到底哪里不一样？"**

### 9. 时间线与变更关联

事故复盘与定位都依赖一条可信时间线：

```text
  T0  最近一次部署 / 配置变更 / 开关切换 / 依赖升级 / 证书轮换
  T1  首个异常信号(日志/指标/告警)出现
  T2  用户开始受影响 / 上游开始重试
  T3  告警触发 / 值班介入
  T4  缓解动作(回滚/切流/限流)
  T5  恢复确认
```

把"变更事件"与"异常信号"放在同一条时间轴上，是最高信噪比的定位方法。很多故障在时间轴上会立刻暴露为"某次变更之后 N 分钟开始"。因此变更（含 AI 生成的变更）必须进入统一的事件时间线，而不是散落在不同系统。

### 10. 检查清单（可观测性就绪度）

```text
[ ] 关键用户路径有 SLI, 且 SLO 已定义
[ ] 每条错误日志可关联到 trace/请求
[ ] 延迟以分位数呈现, 有长尾视图
[ ] 告警绑定 runbook 与负责人, 并做过降噪
[ ] 最近变更(部署/配置/开关)在统一时间线可见
[ ] 错误预算消耗有告警
[ ] AI 辅助分析的结论有人工验证环节
```

### 11. 决策矩阵：先做什么

| 现象 | 首查维度 | 优先动作 | 避免 |
|---|---|---|---|
| 整体错误率骤升 | 最近变更 + 依赖健康 | 回滚/切流 | 先改代码再定位 |
| 单一区域异常 | 区域维度聚合 | 切流量/隔离 | 全局重启 |
| 延迟长尾变差 | p99 + 关键路径 trace | 找慢依赖/锁/GC | 只看均值 |
| 资源饱和 | USE 指标 | 限流/扩容/降级 | 无脑加机器 |
| 间歇性复现不了 | 请求捕获 + 开关状态 | 差分对比 | 靠猜 |

## 常见陷阱与反例

- 反例：只监控平均值。发布后均值正常，p99 翻倍，大量慢请求用户投诉才发现。
- 反例：把 request_id 当指标标签，基数爆炸导致监控后端被写挂，事故期间监控本身不可用。
- 反例：告警配了但没有 runbook，值班人收到后无从下手，检测时间被"找不到人/不知道怎么查"浪费。
- 反例：用 AI 生成的根因报告直接作为事故结论，报告中混入了与本次无关的历史模式，误导修复方向。
- 反例：日志里记了完整 Authorization header 和用户手机号，排障方便了，合规事故也来了（见 K09）。
- 易错：把"服务恢复"当成"问题解决"，根因未修，同样故障反复发生。
- 易错：SLO 定得过严导致错误预算瞬间耗尽，随后所有人无视 SLO——目标失去约束力。

## 与其他知识域的连接

- **K07 发布回滚**：K08 的 SLI 是 K07 回滚判据的来源；错误预算联动发布节奏。
- **K09 安全隐私**：日志/追踪/告警通道是 PII 与密钥泄漏的高发区，脱敏与保留期属合规要求。
- **K10 可靠性与容量**：SLO、降级、限流、熔断的设计在 K10，K08 负责观测其效果。
- **K03 Agent 编排**：Agent 的工具调用链同样需要 trace 与审计，否则无法解释 Agent 的决策路径。
- **K12 组织治理**：故障复盘、改进项跟踪、度量团队恢复能力是治理闭环的一部分。
- **K04/K05**：AI 生成代码的"运行质量"最终由 K08 的证据决定，而非编译通过。
