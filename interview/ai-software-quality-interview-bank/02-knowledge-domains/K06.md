# K06 Code Review、静态分析与门禁

## 范围

人工审查、lint、类型、SAST 和质量规则。

## 领域边界

**本域解决什么。** 解决"如何在代码进入主干前发现缺陷、一致性问题与安全风险"，并把这些检查组织成可靠的门禁。三个支柱：人工审查（判断意图与设计）、静态分析（规则化地抓可模式化的问题）、门禁（决定检查结果如何阻断或放行）。

**本域不负责什么。**

- 不负责测试 oracle 与有效性（K05），只负责"测试证据是否作为门禁条件"。
- 不负责流水线引擎、部署编排（K07），只负责门禁语义与证据格式。
- 不负责运行时安全/供应链的具体审计手段（K09），只负责"安全扫描结果如何进入门禁"。
- 不负责状态机整体设计（K01），只负责其中评审/CI 转移的落点。

**与相邻域的接口。**

| 本域交付 | 接收方 |
|---|---|
| 阻塞/警告语义与豁免留痕格式 | K01/K07 |
| 静态规则与审查清单 | K04（可维护性判据） |
| 误报/漏报治理流程 | K09/K12 |
| 审查证据的留存与可复核要求 | K12（治理与审计） |

## 先修知识

- 静态分析基本原理：解析→AST/IR→数据流/控制流分析。
- 分析工具类别：lint、格式化、类型检查、SAST、SCA（依赖）、密钥扫描。
- 精确率（precision）/召回率（recall）与误报/漏报概念。
- CI 分支保护、必需检查、审批规则。
- 代码评审的工程实践：小 PR、diff 上下文、评论与批准。

## 核心机制

### 1. 静态分析工具分类

| 类别 | 抓什么 | 典型误报倾向 | 适合门禁 |
|---|---|---|---|
| 格式化 | 空格、换行、导入顺序 | 极低 | 阻塞（自动修） |
| Lint | 风格、可疑构造、未用变量 | 低 | 阻塞 |
| 类型检查 | 类型不一致、可空、未处理分支 | 低 | 阻塞 |
| 数据流/复杂规则 | 空指针、资源泄露、死代码 | 中 | 阻塞（关键项） |
| SAST | 注入、XSS、路径穿越、不安全反序列化 | 中高 | 阻塞高危，其余警告 |
| SCA/依赖 | 已知 CVE、许可证、过时版本 | 中 | 阻塞高危 CVE |
| 密钥扫描 | 硬编码密钥、凭证 | 低 | 阻塞 |

**确定性（格式化、类型、密钥、CVE）适合阻塞；启发式（部分 SAST 规则）适合分级。**

### 2. AI 审查 vs 规则的互补

| 维度 | 静态规则 | AI 审查 |
|---|---|---|
| 确定性 | 确定（同输入同输出） | 非确定 |
| 擅长 | 可模式化的缺陷、一致性 | 意图判断、跨文件语义、缺失的边界 |
| 盲区 | 语义/意图问题、新缺陷模式 | 精确复现、可审计性、可能漏报 |
| 误报 | 有，但可枚举抑制 | 不稳定，可能随措辞变化 |

互补原则：

1. **AI 审查不单独承担阻塞职责**（非确定性）。它可以给建议、做初筛、抓规则覆盖不到的问题，但"AI 说通过"不能作为合并的唯一证据。
2. **规则先跑**，把确定性问题清掉，让人和 AI 只处理语义与意图。
3. **AI 抓的意图问题**要能转成人工判断或新规则，形成"AI 发现→规则固化"的闭环。

### 3. 门禁设计：阻塞 vs 警告

判定标准是**确定性与后果严重度**：

- **阻塞（blocking）**：结果确定、后果严重、可自动复核。如类型错、密钥、高危 CVE、覆盖阈值、必需审批。
- **警告（warning）**：启发式、需人判断、或历史误报率高。如部分 SAST 规则、复杂度提示、AI 审查建议。
- **升降级规则**：警告累积或落在高危路径时升级为阻塞；阻塞项在明确豁免流程后可降级。

门禁的三条不变量（与 K01 一致）：

- 通过必须留**机器可读证据**（报告、扫描结果、审查记录）。
- 等待时间必须**低于绕过阈值**，否则门禁会被绕过。
- **不可静默降级**：豁免必须留痕、带责任人、带到期时间。

### 4. 误报/漏报治理

- **误报（false positive）**：报告了不是问题的问题。治理：精确抑制（针对具体行而非整文件）、记录抑制原因、定期复审；统计误报率，过高时调整规则或阈值，而不是整条关闭。
- **漏报（false negative）**：没抓到真问题。治理：用逃逸缺陷回流补规则（回归到规则集）、引入更强的分析（数据流/变异）、用 AI 审查补充语义盲区。
- 关键纪律：**禁止用"关闭规则"来降误报**，那只把问题从"看得见的误报"转成"看不见的漏报"。

### 5. 审查证据留存

证据要能在事后回答"这段代码当时是怎么被放行的"：

- 审查记录：谁批准、在什么 diff 上、有哪些评论与解决状态。
- 扫描报告：规则版本、扫描范围、结果、豁免项与理由。
- 门禁结果：每次检查的通过/失败/豁免、时间戳、关联 commit。
- 证据必须与代码版本可对应（commit/produce hash），否则不可复核。

### 6. 绕过门禁的防控

开发者绕过门禁的动机来自"成本 > 收益"。防控要同时约束技术和流程：

- **技术**：分支保护、必需状态检查、签名提交、禁止本地跳过标记进入主干。
- **流程**：豁免必须走显式流程（谁批、为什么、多久到期），而不是 `--no-verify` 或改流水线。
- **度量**：监控绕过率（跳过次数、豁免数量、规则被禁用次数）。绕过率上升是门禁设计失败的最强信号。
- **根因**：若某个门禁被大量绕过，先问"是不是成本太高/误报太多"，再决定优化而非加罚。

### 决策矩阵：某检查该阻塞还是警告

| 问题 | 答案倾向 |
|---|---|
| 结果是否确定？ | 否 → 警告 |
| 漏判后果是否严重？ | 是 → 阻塞 |
| 误报率是否高？ | 高 → 警告 + 优化规则 |
| 能否自动复核？ | 否 → 警告 + 人工 |
| 是否卡在高危路径？ | 是 → 升级阻塞 |

### 7. 一次 PR 审查的完整流程

把人工审查、静态分析、门禁串成一条可复现的流程：

```text
1. 作者自审 diff（产出：改动摘要 + 测试证据 + 未决问题）
2. 快检查（秒级）：格式化、lint、类型、密钥扫描  → 失败即回改，不占用人工
3. 自动分析（分钟级）：SAST、SCA、覆盖率         → 高危阻塞，其余警告
4. AI 辅助审查：意图、边界、缺失处理、跨文件影响   → 产出建议，非阻塞
5. 人工审查：聚焦设计、契约、风险、AI 与规则都不擅长的语义问题
6. 门禁汇总：必需检查全绿 + 审批 → 允许合并
7. 证据归档：审查记录 + 扫描报告绑定 commit
```

关键是**让机器做确定的事、人做判断的事**：把语法、密钥、类型这类确定性问题在第 2-3 步清掉，人工在第 5 步才有精力做高价值判断。若第 2 步缺失，人工审查会被琐碎问题淹没，迅速退化为形式批准（K01 的审查疲劳）。

### 8. 一次门禁配置走查

以"提交→合并"链路为例，说明每一项为什么这样设：

| 检查 | 级别 | 理由 |
|---|---|---|
| 格式化 | 阻塞（自动修） | 结果确定、零误报、自动可修 |
| lint | 阻塞 | 结果确定、误报低 |
| 类型检查 | 阻塞 | 结果确定、漏判后果重 |
| 单测 + 覆盖率门槛 | 阻塞 | 证据可复核；门槛防止覆盖骤降 |
| 密钥扫描 | 阻塞 | 泄露不可逆、后果极重 |
| SAST 高危 | 阻塞 | 后果重、且高危规则误报相对可控 |
| SAST 低危 | 警告 | 误报率高，需人判断 |
| SCA 高危 CVE | 阻塞 | 供应链后果重 |
| AI 审查 | 警告 | 非确定性，不能单独阻塞 |
| 复杂度提示 | 警告 | 需结合上下文判断 |

### 9. 豁免与过期机制

门禁必须允许"合理地不满足"，否则开发者会绕过：

- 豁免要有**显式载体**（配置文件/注释），而非口头或临时跳过。
- 每条豁免记录：**谁批准、为什么、针对哪个检查、到期时间**。
- 到期自动失效并重新告警，防止"临时豁免永久化"。
- 定期复审豁免清单，统计哪些检查最常被豁免——高频豁免意味着该门禁设计有问题，应优化而非加罚。

### 10. 审查证据的可复核性

一条好的审查证据链应能回答事后问题：

- "谁批准了这次改动？" → 审查记录 + 审批人。
- "当时扫了哪一版代码？" → 报告绑定 commit/hash。
- "用了哪版规则？" → 规则集版本入报告。
- "有没有豁免？理由是什么？" → 豁免台账。
- "这次放行是否合规？" → 证据在保留期内可检索。

`[推断]` 证据若不能与代码版本对应、不能回答"当时依据什么放行"，在事故复盘与合规审计中等于不存在。审查证据的价值是**可追溯**，而非"存过一份"。

## 常见陷阱与反例

- **反例：把 AI 审查通过当唯一门禁。** 非确定性检查不能单独阻塞，可能这次漏了下次抓到。
- **反例：为降误报整条关闭规则。** 误报消失，漏报接管，问题转入不可见。
- **反例：警告堆积无人处理。** 全部警告化等于没有门禁，团队学会无视。
- **反例：门禁慢到被 `--no-verify` 绕过。** 见 K01，门禁信誉崩塌。
- **反例：豁免无到期时间。** 临时豁免变成永久豁免，安全债沉积。
- **易错：审查只看 diff 不看上下文。** 改动可能破坏不在 diff 里的调用方。
- **易错：把覆盖率当唯一质量信号。** 覆盖率高但断言无效（K05）。
- **易错：证据不绑定代码版本。** 事后无法复现"当时扫了哪一版"。

## 证据与缺口

- `[已确认]` 静态分析按类别确定性不同；AI 审查为非确定性；覆盖率不等于有效性。
- `[推断]` 阻塞/警告分级标准、误报/漏报治理、证据留存与绕过防控由工程机制推导。
- `[待验证]` 各工具类别的误报率量级、门禁等待阈值、绕过率警戒线，需在目标项目实测。
- 缺口：本工作区无真实扫描报告与审查记录，任何误报率/绕过率数值均不得编造，一律标待验证。
