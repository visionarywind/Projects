# K05 测试生成、评测与回归

## 范围

oracle、覆盖、变形、基准和评测集。

## 领域边界

**本域解决什么。** 回答"如何证明生成代码的行为是对的，以及改动之后是否仍然对"。核心是设计可信的 oracle（如何判断一个结果正确）、用覆盖率与有效性度量测试质量、防止假测试、用变异测试检验测试本身的强度、治理 flaky 与回归、管理 golden/快照测试。

**本域不负责什么。**

- 不负责代码本身的正确性判据（K04），本域提供验证手段。
- 不负责门禁/审查规则（K06）与流水线编排（K07），只产出它们消费的测试证据。
- 不负责生产运行的观测（K08），本域聚焦开发期验证。
- 不负责性能基准的容量结论（K10），但提供基准方法论的基础。

**与相邻域的接口。**

| 本域交付 | 接收方 |
|---|---|
| 可复核的测试报告作为门禁出口证据 | K01/K06/K07 |
| oracle 设计与"意图而非实现"的断言原则 | K04 |
| 回归评测集与变异得分 | K11/K12（质量度量） |

## 先修知识

- 测试基础：单元/集成/端到端、测试金字塔、断言、fixture。
- oracle 概念：判断程序输出是否正确的机制（期望值、参考实现、性质）。
- 覆盖率口径：行/分支/路径覆盖及其局限。
- 属性测试与变形测试（metamorphic testing）的基本思想。
- 变异测试原理：故意注入缺陷，看测试能否捕获。
- flaky 测试：非确定性失败的测试。

## 核心机制

### 1. 测试生成策略

AI 生成测试的有效顺序，是从"确定能站住"到"容易过拟合"：

1. **基于类型/契约**：从接口签名、类型约束、前置后置条件生成边界用例（空、单元素、极值）。
2. **基于既有测试范式**：模仿仓库已有测试的组织与断言风格，保证一致性。
3. **基于属性/不变量**：生成性质测试（如"排序后长度不变、元素多重集不变"），比具体断言更强。
4. **基于需求验收标准**：每条验收标准至少一个用例，确保覆盖意图而非实现。
5. **基于实现反推**：最弱，容易过拟合到实现细节，仅作补充。

### 2. 覆盖率 vs 有效性

这是本域最重要的区分：

- **覆盖率**度量"执行到了多少代码"，不度量"断言是否有意义"。
- **有效性**度量"测试能否发现缺陷"。
- 高覆盖率可以有零有效性：断言写成 `assert result is not None`、或断言照抄实现输出，覆盖率满格但不验证正确性。

`[推断]` 覆盖率是必要不充分条件：低覆盖几乎必然漏测，但高覆盖不保证有效。应把覆盖率作为"发现未测试区域"的地图，而不是质量分数。

### 3. 防"假测试"（过拟合断言）

假测试是 AI 生成测试最主要的失效模式。识别特征：

- **断言实现快照**：断言等于当前实现的输出（包括其 bug），实现一改测试就失败，或 bug 被固化为期望。
- **无意义断言**：只断言非空、不抛异常、类型正确，不校验值。
- **同义重述**：测试逻辑复制实现逻辑，两者犯同一个错，永远一致。
- **依赖固定随机/时间**：测试结果由实现的偶然行为决定。
- **只测 happy path**：没有失败、边界、异常用例。

对冲手段：

1. **从 oracle 出发写测试，而不是从实现出发**：先明确"什么结果算对"，再写断言。
2. **独立计算期望值**：期望值来自需求/独立参考，不能来自被测实现。
3. **审查断言的语义**：把"这个断言能区分对与错吗"作为审查问题。
4. **变异测试检验**：见下节，假测试在变异下会暴露。

### 4. 变异测试

机制：向被测代码注入小缺陷（翻转条件、改边界、删语句、换运算符），然后跑测试集。若测试**没失败**，说明该变异"存活"，意味着测试无法发现这类缺陷。

- **变异得分**＝被杀的变异 / 总变异，度量测试集的实际杀伤力，比覆盖率更接近"有效性"。
- 存活变异是具体线索："如果把 `<=` 改成 `<` 测试仍通过"，说明边界没被测试。
- 代价：计算量随变异体数量增长，通常选取针对性变异算子并抽样。

`[推断]` 变异测试是治理假测试的强手段，因为它不关心断言写了什么，只关心测试能否因缺陷而失败。

### 5. 回归测试

- 回归集的价值在于**捕获已修复缺陷的复现**和**已确立的行为契约**。
- 每次真实缺陷修复，应固化为一个回归用例（bug→test 的闭环）。
- 回归集规模增长需要治理：按风险分层（核心路径全测、边缘抽样），避免回归集膨胀到不可运行。
- 对生成代码，回归尤其重要：它把"这次对了"变成"以后还错不了"。

### 6. flaky 测试治理

非确定性失败会摧毁测试证据的可信度——一旦团队习惯"红了就重跑"，门禁就失效了。

常见来源：并发时序、共享状态/测试间污染、时间/时区、随机种子、外部依赖、网络、资源泄漏。

治理流程：

1. **隔离**：把 flaky 测试从阻塞门禁中移出（quarantine），但必须登记并有修复期限，不能永久挂在"允许失败"列表。
2. **定量**：统计失败率，区分"真 flaky"与"真缺陷导致的间歇失败"。
3. **去随机化**：固定种子、注入时钟、隔离状态、mock 外部依赖。
4. **熔断**：连续 flaky 的测试若无人认领，直接删除而不是无限重跑。

### 7. golden / 快照测试

- **机制**：把当前输出存为基线（golden），后续运行比对差异。
- **优势**：对复杂结构化输出（序列化、渲染、协议）成本低。
- **风险**：容易掩盖"基线本身就是错的"——若生成代码改变了行为，快照被无脑更新，等于把 bug 固化为基线。
- **纪律**：快照必须能审阅 diff、更新必须走评审、关键快照要与 oracle 交叉验证。禁止"测试失败就 `--update-snapshot`"。

### 检查清单（接受一批生成测试前）

- [ ] 期望值来自需求/独立参考，而非被测实现？
- [ ] 有边界、失败、异常用例，而非只有 happy path？
- [ ] 断言能区分正确与错误实现（变异会被杀）？
- [ ] 没引入随机/时间/外部依赖的非确定性？
- [ ] 覆盖率是否用来找空白区，而不是当分数？
- [ ] 更新快照/基线是否走了评审？

### 8. oracle 的几种类型

oracle 是"判断结果对错"的依据，强度差异很大：

| oracle 类型 | 机制 | 强度 | 适用 |
|---|---|---|---|
| 精确期望值 | 断言等于预先算好的值 | 强（但依赖期望值正确） | 逻辑明确的小函数 |
| 参考实现 | 与独立实现比对 | 强（需独立来源） | 算法、协议 |
| 性质/不变量 | 断言恒成立的性质 | 强，覆盖输入空间大 | 排序、序列化、转换 |
| 变形关系 | 输入变换后期望输出按已知关系变化 | 强，无需 oracle 值 | 难算期望的复杂系统 |
| 一致性 | 与旧版本/其他组件比对 | 中（旧版可能有 bug） | 重构、迁移 |
| 非空/不抛异常 | 只验证"没崩" | 弱，几乎无效 | 仅作冒烟 |

**生成测试时优先选择强 oracle**；弱 oracle（非空、不抛异常）是假测试的主要温床。

### 9. 属性测试与变形测试

- **属性测试（property-based）**：描述函数应满足的通用性质，由框架自动随机生成输入（如"反转两次等于原串""排序后有序且多重集不变"）。它能用少量代码覆盖巨大输入空间，是抵抗过拟合断言的利器。
- **变形测试（metamorphic）**：当期望输出难以直接计算时，构造输入变换并断言输出间的关系。例如"把商品价格统一加 1，总价应加购买数量"；"把输入列表做置换，排序结果不变"。适合无可靠 oracle 的系统（编译器、数值计算、机器学习）。

`[推断]` 属性/变形测试天然与具体实现解耦，因而对生成代码尤其实用——它们检验的是"行为性质"而非"实现快照"。

### 10. 回归集的治理与分层

回归集随项目增长，需分层运行以控制成本：

| 层 | 内容 | 运行时机 |
|---|---|---|
| 冒烟层 | 核心路径、秒级 | 每次提交 |
| 核心回归层 | 历史缺陷复现、关键契约 | 合并前 |
| 全量层 | 边界、组合、慢用例 | 每日/发布前 |
| 探索层 | 变异、属性随机 | 定期/夜间 |

纪律：每个真实缺陷修复都要固化一个回归用例，并归入对应层；回归用例要能指出它保护的是哪个历史缺陷（可追溯）。

### 11. flaky 的定量治理走查

假设门禁里 `test_concurrent_update` 每周红 1-2 次，重跑即绿：

1. **隔离**：标记 flaky，暂时不阻塞主门禁，但登记为待修，设 2 周到期。
2. **定量**：统计失败率与失败条件（是否总在并发高负载时）。
3. **根因**：定位为共享 fixture 未隔离，两个用例互相污染。
4. **修复**：给每个用例独立 fixture，去除时序依赖。
5. **回归**：修复后连续观察一段时间，确认失败率归零再重进门禁。
6. **熔断**：若到期仍未修复，直接删除该用例（不允许长期"允许失败"）。

反之，若定性为"真实并发缺陷导致的间歇失败"，则它不是 flaky 而是真 bug，绝不能隔离了事。

## 常见陷阱与反例

- **反例：断言照抄实现。** 实现有 bug，测试把 bug 固化为期望，覆盖率 100% 但完全无效。
- **反例：覆盖率驱动。** 为凑数字写无意义断言，覆盖上去了，缺陷照漏。
- **反例：无脑更新快照。** 行为变化被快照基线吸收，回归保护归零。
- **反例：把 flaky 测试长期挂在"允许失败"。** 团队习惯忽略红色，门禁信誉崩塌。
- **反例：只测主路径。** 边界和错误路径是缺陷聚集地，恰好没测。
- **易错：测试复制实现的分支逻辑。** 两者同错，永远一致，无法发现缺陷。
- **易错：把"测试通过"当成"需求满足"。** 测试只覆盖到它写到的范围。
- **易错：回归集只增不减。** 运行成本上升直到被绕过，保护反而消失。

## 与其他知识域的连接

- **K01**：测试报告是"验证→评审→CI"转移的出口证据；门禁会诱导假测试，本域提供对冲。
- **K04**：本域为正确性判据提供执行证据；变异测试直接暴露 K04 关心的边界与并发缺陷。
- **K06**：覆盖率阈值、变异得分是否作为门禁，属于门禁设计。
- **K07**：回归集在 CI 中运行，flaky 治理影响流水线稳定性。
- **K08**：生产观测发现的逃逸缺陷应回流为回归用例。
- **K11**：回归集与快照基线是长期资产，随架构演进维护。
- **K12**：变异得分、覆盖率、flaky 率是质量度量指标。

## 证据与缺口

- `[已确认]` 覆盖率高不蕴含测试有效；快照被无脑更新会掩盖行为变化；flaky 测试会侵蚀测试可信度。
- `[推断]` 测试生成优先级、变异测试作为有效性度量、oracle 先行、快照纪律，由测试理论与机制推导。
- `[待验证]` 变异得分阈值、flaky 率的可接受下限、覆盖率与逃逸缺陷的相关强度，需在目标项目实测。
- 缺口：本工作区无测试集与缺陷数据，不得编造变异得分、覆盖率或缺陷逃逸的具体数值。
