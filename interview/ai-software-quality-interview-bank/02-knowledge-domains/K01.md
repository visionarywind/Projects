# K01 vibe-coding 生命周期与人机协作

## 范围

需求、生成、反馈、审查和交付。

## 领域边界

**本域解决什么。** 把"AI 生成代码"这件事放回软件生命周期，回答四个问题：产物在哪个状态产生、状态之间的准入门禁是什么、谁对每个状态的出口负责、人机各自的权限边界在哪。它关心的是**流程与责任**，不是单点技巧。

**本域不负责什么。**

- 不负责"怎么写提示词/怎么检索代码"（K02）。这里只说"进入生成状态前必须准备哪些上下文证据"，不教检索算法。
- 不负责 Agent 的循环实现、工具 schema、重试策略细节（K03）。这里只规定"自主 Agent 在哪个状态下可以无人工干预"，不规定循环怎么写。
- 不负责测试 oracle、变异测试、覆盖率口径（K05），只规定"验证状态必须产出什么证据"。
- 不负责具体静态规则、SAST 引擎选型（K06），只规定"评审与 CI 状态的阻塞/警告语义"。
- 不负责流水线引擎、灰度算法、回滚编排（K07），只规定"发布/观测状态的门禁判据由谁定义"。

**与相邻域的接口。**

| 本域向下游交付 | 接收方 |
|---|---|
| 上下文最小充分集的**准入条件**（哪些证据必须进窗口） | K02 |
| Agent 在哪些状态可自主、哪些必须有人工审批 | K03 |
| "验证状态必须产出可复核测试证据"的硬约束 | K05 |
| 门禁的阻塞/警告语义、豁免留痕格式 | K06 |
| 发布/灰度/回滚的判据归属 | K07 |
| 由状态机导出的可度量指标（绕过率、逃逸率） | K12 |

## 先修知识

- 软件开发生命周期（SDLC）的基本阶段划分与产物。
- 持续集成/持续交付的基本概念：提交、构建、制品、环境、审批。
- 代码评审的常规做法：diff、评论、批准、分支保护。
- 测试金字塔与"证据"的含义：测试报告、覆盖率、扫描结果是机器可读产物。
- 版本控制与分支模型（主干、特性分支、合并请求）。
- 基本的风险分级：什么改动必须走完整门禁，什么改动可以走快速通道。

## 核心机制

### 1. vibe-coding 与 AI 辅助开发的责任边界

二者常被混为一谈，但决定质量的是**人机责任划分**，不是"有没有用 AI"。

| 维度 | vibe-coding | AI 辅助开发 |
|---|---|---|
| 优化目标 | 探索速度 | 可控质量下的效率 |
| 责任主体 | 模糊（"能跑就行"） | 人 + 自动化门禁 |
| 验证证据 | 体感/手测 | 测试 + 审查 + CI 记录 |
| 逐行审查 | 弱 | 强（或由等价自动化替代） |
| 安全/依赖审查 | 弱 | 强 |
| 适用阶段 | 原型、个人脚本 | 主干、生产、团队协作 |

判断规则只有两条不变量：

- **不变量 A（可追责）**：始终存在一个能对这段代码正确性负责的人，无论作者是不是 AI。
- **不变量 B（可复核证据）**：进入主干/生产的代码必须有机器可读的验证证据（测试报告、扫描结果、审查记录），而不是"我看过了"。

**迁移触发条件**（任一满足即应从 vibe-coding 升级为 AI 辅助开发）：代码进入共享主干；需要长期维护或多人协作；涉及安全/隐私/支付/合规；有 SLA 或生产流量。

`[推断]` vibe-coding 在原型阶段是合法选择，其风险不是"用了 AI"，而是把原型流程的产物直接当成品交付。

### 2. 生命周期状态机

把生命周期建成一条有向状态链，每个状态定义**进入条件、出口证据、失败动作**：

```text
需求澄清 → 上下文准备 → 生成 → 本地验证 → 代码评审 → CI 校验 → 发布 → 生产观测 → 治理
```

- **需求澄清**：把模糊需求变成可测的验收标准。出口证据＝验收用例草稿。失败动作＝退回澄清。
- **上下文准备**：确定生成任务所需的最小充分证据集（接口、类型、约束、范例、测试）。出口证据＝上下文清单。失败动作＝补证据后重来。
- **生成**：模型产出候选代码。出口证据＝可审阅的 diff。失败动作＝丢弃重生成，不进下游。
- **本地验证**：最便宜的确定性检查（格式化、类型检查、单测）。出口证据＝本地测试报告。
- **代码评审**：人或 AI 辅助的意图审查。出口证据＝审查记录 + 批准。
- **CI 校验**：静态扫描、依赖审查、安全扫描、集成测试。出口证据＝扫描与测试报告。
- **发布**：灰度、性能、端到端。出口证据＝基准与灰度指标。
- **生产观测**：SLI/SLO 对比。出口证据＝指标对比与告警基线。
- **治理**：事故归因、豁免到期复审、指标回流。出口证据＝治理记录。

`[推断]` 状态机的价值在于把"要不要 AI"这种情绪化争论，转成"这个转移有没有出口证据、由谁签字"的可操作判断。

### 3. 内外环与门禁落点

- **内环（试错环）**：生成 ↔ 本地验证。允许脏代码、无测试、反复重来，**不设阻塞门禁**，否则扼杀探索速度。
- **外环（合并环）**：从"离开本地"到"进入主干/生产"的所有转移，**每个都必须设门禁**。

门禁设计的核心矛盾是**证据强度 vs 通过成本**。两条经验：

1. 把确定性的检查左移到本地（格式、类型、单测），把昂贵/需环境的检查右移到 CI/预发（端到端、性能、安全）。
2. 门禁成本必须低于开发者的绕过收益阈值（经验上分钟级是分水岭，`[待验证]`），否则一定被 `--no-verify`、跳过检查或改流水线绕开。

| 转移 | 门禁检查 | 出口证据 | 失败动作 | 绕过控制 |
|---|---|---|---|---|
| 需求→生成 | 可测性、验收标准 | 验收用例草稿 | 退回澄清 | 评审前置 |
| 生成→本地验证 | 可读 diff、无脏标记 | diff 摘要 | 重生成 | 无（内环） |
| 本地验证→评审 | 单测/类型/格式 | 本地测试报告 | 阻断提交 | 提交钩子可禁但留痕 |
| 评审→CI | 静态、依赖、AI 审查 | 扫描结果+审查记录 | 阻断合并 | 分支保护 |
| CI→发布 | 端到端、安全、性能 | 测试与基准报告 | 阻断发布 | 发布审批 |
| 发布→生产 | 灰度判据 | SLI 对比 | 自动回滚 | 自动执行 |
| 生产→治理 | 逃逸缺陷归因 | 复盘记录 | 触发规则修订 | 治理评审 |

### 4. 人机协作模式

同一套状态机下，人机分工有几种典型模式，各有失手点：

- **补全模式（assist）**：人写主体，AI 补行内代码。人承担全部设计责任；失手点是"惯性接受补全"，把看似合理的错误片段焊进代码。
- **委派模式（delegate）**：人定接口/架构，AI 填实现。人负责接口契约；失手点是接口没写死，AI 自由发明签名。
- **Agent 模式（agentic）**：AI 自主多步执行（读代码、改多文件、跑测试）。人从"写代码"转为"审结果 + 定权限"；失手点见 K03 的终止条件与预算失控。
- **对等审查模式**：AI 审查人的 PR，或人审查 AI 的 PR。失手点是"AI 审查通过"被当成唯一证据（非确定性检查不应单独阻塞）。

`[推断]` 模式选择应由**风险分级**驱动：低风险、可快速回滚的改动可放开到 agentic；高风险（金额、权限、数据边界）必须收回到 delegate/assist 并强制人工签字。

### 5. 审查疲劳与退化路径

这是 AI 辅助开发最主要的质量退化机理：

```text
门禁等待时间长 / 单次 diff 过大
   → 开发者体感"审查不值得"
   → 跳过或形式化通过门禁
   → 信任模型输出，逐行审查消失
   → 实际退化为 vibe-coding（但穿着工程流程的外衣）
   → 缺陷逃逸率上升，直到一次生产事故暴露
```

对策（按优先级）：

1. **可自动化的确定性检查前置**，让人工审查只处理机器判断不了的意图与边界。
2. **限制单次改动规模**（小 PR、单一主题），让审查保持可完成。
3. **证据驱动评审**：人审的是"测试是否覆盖了意图"和"边界反例"，而非逐字符读 diff。
4. **抽样深审 + 告警抽检**，对高危路径强制全审。
5. **度量绕过率**：绕过率上升本身就是门禁设计失败的信号。

### 6. 决策矩阵：给改动配流程

| 改动风险 | 典型例子 | 生成模式 | 必要门禁 |
|---|---|---|---|
| 低 | 文档、注释、测试补齐 | agentic 可接受 | 单测 + lint |
| 中 | 内部业务逻辑、重构 | delegate | 单测 + 类型 + 审查 + CI |
| 高 | 鉴权、支付、数据迁移、加密 | assist + 强制人工 | 全部门禁 + 安全审查 + 灰度 |
| 极高 | 密钥、证书、合规边界 | 人工主导，AI 仅建议 | 双人评审 + 合规签字 |

### 7. 需求可测性：把意图转成门禁能吃的东西

vibe-coding 与受控开发的第一个分水岭其实在需求状态。如果需求是"做一个好用的搜索"，模型只能猜，门禁也无从判定。可测化就是把需求改写为**可观察的完成定义**：

```text
模糊需求：让登录更安全
可测化：  登录接口 1) 密码以 bcrypt(cost>=10) 存储；
         2) 连续 5 次失败后锁定 15 分钟；
         3) 所有查询使用参数化语句；
         4) 失败响应不区分"用户不存在/密码错误"。
         验收：上述四条各有一个自动化用例。
```

可测化的产出是验收用例草稿，它同时是生成阶段的上下文证据、验证阶段的 oracle、评审阶段的判定基准。**需求不可测 → 后续所有门禁都只能靠人感觉，等于整条状态机失去机器判据。**

### 8. 一次完整走查（示例）

以"给订单服务加一个导出 CSV 的接口"为例：

1. **需求澄清**：明确列、编码、大数据量分页、权限。出口＝3 条验收用例。
2. **上下文准备**：喂入既有路由定义、鉴权中间件、DTO 类型、一个同类导出实现。出口＝上下文清单。
3. **生成**：产出 diff，新增 handler + service 方法。出口＝可读 diff。
4. **本地验证**：跑格式化、类型、单测（含空结果、超大数据量、无权限）。出口＝本地测试报告。
5. **评审**：人重点看权限校验是否绕过中间件、分页是否内存爆炸、CSV 注入是否防护。出口＝审查记录。
6. **CI**：静态扫描、依赖审查（有没有引入新 CSV 库）、覆盖率门槛、SAST。出口＝扫描报告。
7. **发布**：灰度 1%，观察内存与错误率。出口＝SLI 对比。
8. **生产观测**：P99 延迟、内存、导出失败率。
9. **治理**：若发现某次导出 OOM，回流为回归用例并加内存上限门禁。

每一步都有"若失败退回哪里"的明确路径；没有证据就不允许推进。

### 9. 度量与反馈回路

状态机要能自我改进，靠的是指标回流（细节口径见 K12）：

| 指标 | 反映 | 异常含义 |
|---|---|---|
| 缺陷逃逸率 | 门禁漏掉的缺陷比例 | 门禁强度不足或证据无效 |
| 门禁绕过率 | 跳过/豁免/禁规则的频率 | 门禁成本过高，必须优化 |
| 门禁平均等待时间 | 反馈速度 | 超过阈值将诱发绕过 |
| 返工率 | 生成后被打回的比例 | 上下文准备或需求可测性不足 |
| 审查覆盖 | 高危改动是否有审查记录 | 存在无审查通道 |

`[推断]` 这些指标的价值不在于打分，而在于**定位状态机在哪一步失守**：绕过率高→门禁成本问题；逃逸率高→证据有效性问题；返工率高→需求/上下文问题。

## 常见陷阱与反例

- **反例：把 vibe-coding 流程用到生产。** 生成"能跑"的登录接口直接上线，缺 SQL 注入防护与密码哈希，运行通过但留下高危漏洞。
- **反例：认为"AI 生成的代码不用审"。** 责任始终落在合并代码的人身上；AI 不是责任主体。
- **反例：把外环门禁前移到内环。** 每改一行跑全量端到端，流水线 40 分钟，团队最终统一 `git commit --no-verify`，门禁形同废除。
- **反例：只设计门禁不设计豁免。** 导致"要么全过、要么全绕"的二元局面，没有中间态。
- **反例：把唯一出口证据押在非确定性检查上。** 用"AI 审查通过"作为合并的唯一依据，见 K06。
- **易错：把"有 AI 参与"当成质量风险本身。** 真正的风险是缺少验证证据，与作者是不是 AI 无关。
- **易错：用 prompt 补丁代替流程门禁。** "请在提示词里要求模型写测试"不是门禁，无法在模型不遵守时阻断。

## 与其他知识域的连接

- **K02**：本域定义"生成前需要哪些证据进窗口"，K02 提供检索与上下文构建的实现手段。上下文缺失是本域状态机在"上下文准备"状态最常见的失败源。
- **K03**：本域划分 Agent 可自主的状态边界，K03 提供循环、工具、预算与终止条件；两者的结合点是"权限与审批"。
- **K04**：本域要求"验证状态产出证据"，K04 定义正确性与可维护性的具体判据。
- **K05**：门禁要求测试证据，会诱导"为过门禁写假测试"，对冲手段在 K05（防过拟合断言、变异测试）。
- **K06**：本域规定门禁语义，K06 给出静态分析、AI 审查、误报治理的实现。
- **K07**：发布/灰度/回滚门禁的判据归属，与 CI/CD 编排衔接。
- **K09**：依赖门禁要能挡住模型幻觉出的包名，供应链校验在 K09。
- **K12**：本域导出的绕过率、逃逸率、门禁等待时间是指标体系的输入。

## 证据与缺口

- `[已确认]` 模型输出不等于系统正确性证明；静态规则通过不等于语义正确。
- `[推断]` 状态机、内外环划分、迁移触发条件来自软件工程与持续交付的通用机制。
- `[待验证]` 门禁等待时间分水岭（分钟级）、绕过率阈值、审查疲劳与退化路径的量化关系，需要目标团队实测。
- 缺口：本工作区无真实团队实验数据，所有涉及百分比、时间阈值的结论均未执行验证，不得对外引用为实证。
