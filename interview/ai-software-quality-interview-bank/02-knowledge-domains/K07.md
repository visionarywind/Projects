# K07 CI/CD、发布、灰度与回滚

## 范围

构建、制品、环境、审批、灰度和恢复。

## 学习重点

- 把 AI 生成行为放入软件生命周期，追踪需求、上下文、变更、测试、发布和运行质量。
- 同时考虑正确性、可维护性、安全、可靠性、性能、成本和人工责任。
- 模型能力和生成代码结论没有项目运行证据时标为 [待验证]。

## 领域边界

覆盖"从代码进入主干之后到生产稳定运行"这一段：构建、制品与版本、环境与配置、部署策略（滚动/蓝绿/金丝雀）、特性开关、发布门禁与审批、回滚与恢复、恢复后的验证。核心问题是：**同一个已经通过评审的制品，如何安全地到达生产，出了事如何在可接受时间内回到已知良好状态。**

不覆盖或只做接口的部分：

- 代码审查、静态分析与"能不能进主干"的判定属 K06。
- 测试用例设计与 oracle 定义属 K05。
- 运行时的日志/指标/追踪与排障属 K08。
- SLO、容量、成本建模属 K10。
- 依赖供应链、密钥与审计属 K09。

分界直觉：K06 决定"变更质量是否达标"，K07 决定"达标制品能否安全交付并可撤回"。AI 审查作为门禁手段属 K06，但它在流水线里的**触发时机、并发控制、成本与失败处置**属 K07。一个常见误解是把"发布"等同于"部署"——部署是让新版本运行，发布是让用户流量真正使用它，二者通过特性开关或灰度解耦。

## 先修知识

- Git 分支模型、合并策略、提交与标签语义。
- 制品仓库、容器镜像、不可变制品与内容寻址（digest）的基本概念。
- 配置管理与基础设施即代码（IaC）的差异：代码化 vs 手工控制台。
- 依赖锁文件与构建工具链版本固定的意义。
- 测试分层（单元/集成/端到端）与各自的成本。
- Linux 进程、端口、健康检查、负载均衡与 DNS 的入门知识。
- 至少一种 CI 平台（GitHub Actions、GitLab CI、Jenkins 等）的作业与流水线概念。

## 核心机制

### 1. 流水线阶段与不变量

一条可交付的流水线通常按成本从低到高排列：

```text
触发(push/PR/tag/schedule/webhook)
  -> 静态阶段(lint/类型/SAST/依赖扫描/AI 审查)
  -> 构建(编译/打包/生成制品+元数据)
  -> 测试(单元 -> 集成 -> 端到端)
  -> 制品入库(不可变/内容寻址/签名/SBOM)
  -> 部署(dev -> staging -> prod 灰度)
  -> 验证(健康检查/SLI 对比/自动分析)
  -> 晋级全量 或 回滚
```

四条不变量：

- **一次构建，多处部署（build once, deploy many）。** 同一个制品 digest 依次进入各环境，避免"每环境重新构建"导致环境间行为漂移。`[推断]`
- **制品不可变且可寻址。** 版本号只是标签，真正的身份是内容摘要（如镜像 digest、制品哈希）。回滚应能精确指向某 digest。
- **配置与代码分离，但配置也要版本化。** 环境差异集中在配置层，且每次变更留痕。
- **低成本的确定性检查左移，高成本的环境相关检查右移。** 静态/单元在提交后立刻跑；端到端/性能/安全在合并或预发阶段跑。

### 2. AI 检查的集成点

把 AI 产出当作**进入门禁的输入**，而不是门禁本身：

| 环节 | AI 的角色 | 集成要求 | 失败处置 |
|---|---|---|---|
| 生成侧 | 产出补丁/测试/配置候选 | 与人类变更同流程 | 走常规门禁 |
| 审查侧 | PR 机器人给审查建议 | 记录模型、版本、prompt、输出哈希 | 非阻塞告警（默认） |
| 修复侧 | 自动修复/auto-fix | 必须产出可读 diff | 走同样门禁，人工复核 |
| 分类侧 | 给失败测试/告警分级 | 结果需可复核 | 仅作辅助排序 |

- AI 审查是非确定性的，同一 diff 两次结果可能不同，因此**不能单独承担阻塞职责**（与 K06 一致）。`[推断]`
- 每次 AI 检查要留可审计记录：模型标识、prompt 摘要、输入摘要、输出、耗时。否则线上回归时无法复现"当时的判断依据"。`[待验证]`（具体留存字段随平台而定。）
- 按 diff 大小与文件类型分级触发 AI 检查，避免全量重跑造成的排队与成本放大。
- 关键约束：**AI 检查的失败不应静默放过**。宁可标为显式豁免并留痕，也不要 `|| true` 吞掉。

### 3. 构建缓存与可复现构建

缓存是流水线速度的主要来源，也是隐蔽错误的主要来源。

缓存层次与 key 设计：

- 依赖缓存：key 应基于锁文件哈希 + 工具链版本；锁文件一变即失效。
- 编译/构建缓存：key 必须覆盖所有影响输出的输入（源码、编译参数、目标平台、环境变量白名单）。
- 容器层缓存：底座镜像 digest 变化必须使下游层失效。

可复现构建（reproducible build）的可操作判据：

- 固定工具链与依赖版本（锁文件 + 显式版本）。
- 消除不确定性输入：构建时间戳、绝对路径、随机数、并发顺序、locale。
- 内容寻址输出：用 digest 校验，而非"看起来一样"。
- 验收方式：**相同输入在干净环境两次构建，产出 digest 相同**。`[推断]`

失败模式：

- 缓存 key 漏掉编译参数，A 配置的产物被 B 配置命中，表现为间歇性、难复现的行为差异。
- 共享可写缓存在不可信分支下被投毒，形成供应链风险（详见 K09）。
- 依赖"最新版"而未锁定，构建结果随时间漂移，回滚时无法重建同一制品。

### 4. 灰度发布（canary / 金丝雀）

灰度是用一小部分真实流量验证新版本，本质是**在可控爆炸半径内暴露风险**。

流量切分方式：

- 按权重：1% → 5% → 25% → 100%（具体档位是实践约定，非硬性标准 `[待验证]`）。
- 按属性：header、cookie、用户 ID 哈希，保证同一用户稳定落在一侧，避免抖动。
- 按维度：特定区域、租户或内部用户先行。

推进判据（决策核心）：

- 与**对照组（旧版本/基线）**比较错误率与延迟分位，而不是只看绝对阈值。
- 自动金丝雀分析需要最小样本量与统计显著性；样本不足时"看起来没问题"不构成通过证据。
- 观测窗口要覆盖慢故障：内存泄漏、连接池耗尽、缓存逐步失效往往不在前几分钟出现。

灰度期的兼容性要求：

- 数据库 schema 与消息格式要能同时被新旧两版读写（expand/contract，见 K11）。
- 灰度实例与基线实例应在可比条件下比较：硬件、缓存状态、数据分布、上游依赖版本。否则差异来自环境而非代码。

### 5. 回滚策略与判据

回滚的目标是最小化 MTTR（平均恢复时间）= 检测时间 + 决策时间 + 执行时间。降低后两者靠自动化。

回滚形式：

- 制品回退：重新部署上一个已知良好 digest。
- 特性开关关闭：不用重新部署，秒级生效，但要保证开关路径本身被测试过。
- 流量切回：网关/负载均衡把流量指回旧集群（蓝绿场景）。
- 数据补偿：对不可逆副作用做逆向操作（补偿事务、冲正）。

判据要用可观测信号，而不是"感觉不对"：

```text
触发回滚的候选信号（需按项目标定阈值 [待验证]）：
  错误率      > 基线 + 容差，持续 N 个窗口
  p99 延迟    > 基线 + 容差
  健康检查    连续失败
  业务 KPI    (下单/登录成功率等) 显著偏离
  资源饱和    (CPU/内存/连接池) 逼近上限
```

回滚成立的前提：

- 新旧版本数据兼容（可同时运行两版）。
- 无不可逆副作用，或副作用可补偿；操作幂等，避免重放产生重复扣款/重复消息。
- 回滚路径被演练过——没演练过的回滚等于没有回滚。`[推断]`

不适合直接回滚的场景：破坏性数据迁移、已对外承诺的状态变更、缺失幂等导致重放有害。这些场景要在发布前设计前向修复（roll forward）方案。

### 6. 特性开关（feature flag）

开关把"部署"与"发布"解耦，是灰度和回滚的轻量实现。

类型与生命周期：

| 类型 | 用途 | 生命周期 | 风险 |
|---|---|---|---|
| 发布开关 | 分阶段放量 | 短期 | 忘了删，成为死代码 |
| 运维开关 | 紧急关停（kill switch） | 长期 | 默认值错误导致误关 |
| 实验开关 | A/B 实验 | 中短期 | 分流与统计污染 |
| 权限开关 | 按用户/租户开放 | 长期 | 组合爆炸 |

开关债务：每个开关都应在创建时登记 owner 与到期时间，验证完成后清理。否则开关组合数指数增长，测试矩阵无法覆盖，且"关掉某个开关"本身可能触发未测路径。开关配置的变更也要走门禁与审计，不能是控制台里的裸改动。`[推断]`

### 7. 发布门禁

门禁分入口与出口两端：

- **入口门禁**（允许开始发布）：制品签名校验通过、SBOM 无已知高危、必需测试全绿、审批记录齐全、变更与工单可追溯。
- **出口门禁**（允许放量到下一档/全量）：灰度判据满足、观测窗口内无回归、错误率与延迟在容差内。

检查清单（发布前逐项确认）：

```text
[ ] 制品 digest 与待发布版本一致，且已签名
[ ] 数据库/消息 schema 向后兼容，回滚可行
[ ] 配置已就绪且与代码版本匹配
[ ] 可观测性覆盖新路径（日志/指标/追踪埋点）
[ ] 回滚命令/开关已演练，负责人明确
[ ] 灰度档位与判据、观测窗口确定
[ ] 若涉及 AI 产出：已过与人类代码相同门禁，AI 记录留存
```

### 8. 决策矩阵：发布策略选择

| 条件 | 推荐策略 | 理由 |
|---|---|---|
| 变更小、易回滚、影响面窄 | 滚动发布 | 成本最低 |
| 需瞬间切换、资源充足 | 蓝绿 | 切换快、回滚即切回 |
| 影响面大、需用真实流量验证 | 金丝雀 + 自动分析 | 控制爆炸半径 |
| 不可逆（数据迁移） | expand/contract + 前向修复演练 | 回滚不可行，靠兼容性过渡 |
| 需要按用户/租户精细控制 | 特性开关 | 秒级、无需部署 |

## 常见陷阱与反例

- 反例：把"部署成功"当成"发布成功"。服务起来了、健康检查过了，但真实流量路径有回归，因为健康检查只探活不探业务。
- 反例：灰度只看新版本绝对指标，不与基线对比。凌晨低峰期新版本错误率"看起来很低"，其实相对旧版本已翻倍。
- 反例：灰度期数据库做了破坏性迁移（删列/改类型），导致无法回滚，只能硬着头皮向前。
- 反例：缓存 key 不含编译参数，A/B 组件混用不同配置的产物，出现随机崩溃却复现不了。
- 反例：特性开关只在"开"分支测试过，"关"分支（旧路径）早已腐烂，紧急关停时反而触发新故障。
- 反例：CI 里 `npm audit || true`、`ai-review || echo skip`，门禁形同虚设，事故后无人能解释为何放行。
- 易错：把回滚时间只算成"执行回滚"的几分钟，忽略检测与决策耗时——真实 MTTR 往往是执行时间的数倍。

## 与其他知识域的连接

- **K01 生命周期**：K07 是生命周期状态机"发布→观测"之间的门禁与恢复机制的展开（见 AQ-I001）。
- **K05 测试**：灰度的自动分析本质是运行时的对照实验，与测试 oracle 的设计一脉相承。
- **K06 审查与门禁**：AI 审查的集成点是两个域的接缝；门禁的绕过治理由 K06 定义，落点成本由 K07 权衡。
- **K08 可观测性**：没有 SLI 就没有回滚判据；K07 的出口门禁完全依赖 K08 提供的信号。
- **K09 安全供应链**：制品签名、SBOM、缓存投毒、CI 凭证最小权限都在两域交界。
- **K10 可靠性**：错误预算告警与发布节奏联动（烧钱太快就冻结发布）。
- **K11 架构演进**：expand/contract 是兼容发布的架构前提。
- **K12 度量**：部署频率、变更失败率、恢复时间（DORA 指标）直接度量 K07 的健康度。
