# K11 架构、接口、技术债与演进

## 范围

边界、契约、兼容、重构和可替换性。

## 学习重点

- 把 AI 生成行为放入软件生命周期，追踪需求、上下文、变更、测试、发布和运行质量。
- 同时考虑正确性、可维护性、安全、可靠性、性能、成本和人工责任。
- 模型能力和生成代码结论没有项目运行证据时标为 [待验证]。

## 领域边界

覆盖"系统的长期结构与变化成本"：架构决策记录（ADR）、接口契约与兼容性、技术债的分类与度量、演进策略（重构、迁移、替换）、抽象层次与模块边界。

不覆盖：

- 单次代码的正确性与可维护性属 K04。
- 发布与回滚的执行机制属 K07（架构为其提供兼容性前提）。
- 安全信任边界属 K09（本域定义模块边界，K09 定义信任策略）。
- 容量与可靠性架构（舱壁、降级）属 K10。
- 度量如何组织化治理属 K12。

分界直觉：架构关注的不是"能不能实现"，而是**当需求变化时，改动会波及多远**。AI 生成擅长局部最优，恰恰最容易破坏这个"波及范围"性质——它会在不了解全局约束时复制、绕过或腐蚀既有抽象。`[推断]`

## 先修知识

- 模块化、内聚与耦合、依赖方向、分层与接口隔离。
- API 设计基础：REST/gRPC、schema、版本化、幂等。
- 向后兼容与语义化版本（SemVer）语义。

- 技术债的常见比喻（Fowler 的技术债象限）。

## 核心机制

### 1. 架构决策记录（ADR）

ADR 记录"为什么这样设计"，避免决策在人员流动后失传。

结构（常见简化模板）：

```text
标题：<决策一句话概括>
状态：提议 / 接受 / 废弃 / 被 <某 ADR> 取代
背景：面临的问题、约束、驱动因素
决策：选择了什么
替代方案：考虑过哪些、为什么没选
后果：正面与负面结果、需要后续跟进的事项
```

要点：

- **记录权衡而非结论**：光写"我们用了 X"没有价值，价值在"为什么不用 Y"。
- **不可变**：新决策写新 ADR 并标记取代旧的，不改写历史。
- **可追溯**：ADR 与代码、接口、发布变更相互引用。
- AI 可以帮助起草 ADR 与检索历史决策，但**决策责任与批准仍属人**。

### 2. 接口契约与兼容性

契约是模块/服务之间的承诺，是演进的核心。

- **版本化**：显式版本（v1/v2、schema 版本号）或兼容演进。破坏性变更必须走新版本。
- **向后兼容**：新增字段可选、不删除、不改语义、不改类型；旧客户端能继续工作。
- **schema 演进策略**：
  - 加性变更（additive）：先加、双读、后写、稳定后清理。
  - expand/contract：加新字段/新表 → 双写/回填 → 切换读 → 移除旧。用于破坏性变更（改名、改类型、拆分）。
- **错误契约**：错误码、错误结构、重试语义也是一部分契约，不能随意改。
- **幂等与重试语义**：写接口要声明幂等键与重试行为。
- **契约测试**：消费者驱动的契约测试（consumer-driven contract）在提供方变更时检测破坏，是比"文档约定"更硬的保障。`[推断]`

失败模式：改了字段语义但不改版本，调用方"编译通过、运行错误"；删了被依赖的字段，下游静默出错。

### 3. 技术债：分类与度量

技术债不是"写得丑"，而是**为了短期收益做出的、未来需要偿还的妥协**。

Fowler 四象限（维度：审慎/鲁莽 × 故意/无意）：

| | 故意 | 无意 |
|---|---|---|
| 审慎 | "先上线，已知要重构"（可管理的债） | "现在才知道更好的做法" |
| 鲁莽 | "没时间做设计" | "不懂好的实践" |

度量（避免臆造数字，用可观测代理指标 `[推断]`）：

- 变更成本：co-churn（频繁一起改的文件）、改一处要动很多文件。
- 复杂度：圈复杂度、扇入扇出、重复代码、长函数。
- 缺陷关联：高缺陷密度模块、修复耗时（time-to-fix）。
- 债务老化：TODO/FIXME 的存在时长、未清理的兼容层。
- 兼容层数量：为了兼容临时保留的 shim，是否有人清理。

偿还策略：把债务登记成可排序的工单（含影响面与修复成本），在容量里预留固定比例偿还，而不是"等有空再说"。技术债度量用于**排序与沟通**，不用于给个人打分（见 K12 Goodhart）。

### 4. 演进策略

- **绞杀者（strangler fig）**：新系统逐步接管旧系统功能，按路由/功能切流，最后关停旧系统。适合大系统替换。
- **并行运行（parallel run）**：新旧同时跑，对比输出，验证一致后再切换。
- **双写 + 回填**：迁移期间同时写新旧，回填历史数据，校验一致后切读。
- **迁移开关**：用特性开关控制走新/旧路径，可随时回退（与 K07 联动）。
- **expand/contract**：见契约章节，是破坏性结构变更的通用节奏。
- **可替换性**：通过稳定接口把实现藏在边界后，使得替换实现不需要改调用方。

原则：演进要**可增量、可回退、可验证**。一次性大爆炸重写是高风险反模式。

### 5. 抽象层次与模块边界

- **依赖方向**：高层策略不依赖低层细节（依赖倒置）；避免循环依赖。
- **接口隔离**：客户端不应依赖它不用的方法；窄接口优于胖接口。
- **边界与 seam**：在变化点设置接缝（seam），使替换与测试成为可能。
- **信息隐藏**：模块隐藏其内部实现细节，只暴露契约。
- **一致性边界**：事务/一致性范围应与模块边界一致，跨边界用最终一致。

AI 生成对边界的典型破坏：

- 复制粘贴实现绕过既有抽象，产生多份真相。
- 直接依赖内部细节（访问私有、跨层调用），腐蚀边界。
- 为通过测试写特判分支，污染核心逻辑。
- 生成风格不一的平行实现，增大认知负担。

### 6. 检查清单

```text
[ ] 关键架构决策有 ADR, 记录权衡与替代方案
[ ] 对外接口有版本与兼容策略
[ ] 破坏性 schema 变更走 expand/contract
[ ] 有消费者契约测试覆盖关键接口
[ ] 技术债有登记、排序与偿还预算
[ ] 模块边界清晰, 无循环依赖
[ ] AI 生成未绕过既有抽象或复制核心逻辑
[ ] 演进路径可增量、可回退、可验证
```

### 7. 决策矩阵

| 变更类型 | 策略 | 关键风险 |
|---|---|---|
| 加字段 | 加性演进 | 忘记处理旧数据默认值 |
| 改字段语义/类型 | 新增版本或 expand/contract | 双写不一致 |
| 拆分服务 | strangler + 契约测试 | 分布式事务与一致性 |
| 替换实现 | 稳定接口后换实现 | 隐藏耦合未暴露 |
| 大系统重写 | 增量绞杀, 避免大爆炸 | 并行维护成本 |

### 8. 重构与迁移的操作手法

安全重构依赖"小步、可验证、可回退"：

- **保持行为不变的重构**：先有测试（或先补特征测试 characterization test）锁定现状，再改结构；测试失败即行为漂移。`[推断]`
- **绞杀者式迁移示例**：新服务先实现只读接口 → 灰度切读 → 双写 → 切写 → 关停旧服务。每一步都可独立回退。
- **接口演进示例**（破坏性改名的 expand/contract）：

```text
1) expand:  新增 new_field, 提供方同时写 old 与 new
2) migrate: 消费方逐步改用 new_field (契约测试保障)
3) verify:  确认无消费方再读 old_field
4) contract:移除 old_field
```

- **迁移进度可观测**：用指标追踪"还有多少流量/多少记录走旧路径"，否则永远不知道能否安全移除兼容层。
- **AI 辅助重构的边界**：AI 适合机械、局部、有测试保护的重构；跨模块语义改动需人主导，AI 产出必须逐段验证。

### 9. 边界防腐

- **防腐层（anti-corruption layer）**：在与外部/旧系统集成处加一层转换，隔离外部模型对内部结构的污染。
- **禁止循环依赖**：用依赖分析工具在 CI 中检测，循环是架构腐化的早期信号。
- **明确所有权**：每个模块有 owner，跨边界变更需要相应 owner 参与，防止"无人负责的公共区域"。

## 常见陷阱与反例

- 反例：没有 ADR，两年后没人知道某个设计为何如此，改动时误删关键约束引发事故。
- 反例：直接把接口字段从必填改成可选并复用同一版本，下游以为语义未变，产生静默错误。
- 反例：破坏性数据库迁移没有 expand/contract，灰度与回滚同时失效（与 K07 交叉）。
- 反例：让 AI 在每个文件里各自实现一遍日期格式化/鉴权逻辑，产生多份实现，修 bug 只修了一处。
- 反例：把"代码覆盖率低"直接等同于"技术债高"，忽略覆盖率与债务是不同维度。
- 反例：宣称"重写就能解决一切"，低估了并行维护与业务连续性的成本。
- 易错：把技术债当成一次性清理项目，而不是持续登记、排序、按比例偿还的过程。

## 与其他知识域的连接

- **K04 生成代码质量**：局部可维护性与全局架构健康是两个层次，AI 常牺牲后者换前者。
- **K06 审查**：审查要能识别"绕过抽象""复制核心逻辑"这类架构级问题，而非只看语法。
- **K07 发布**：expand/contract 与迁移开关是兼容发布的架构前提。
- **K09 安全**：信任边界与模块边界一致时，安全策略才可落地。
- **K10 可靠性**：舱壁、降级、缓存策略是架构决策在可靠性维度的体现。
- **K12 治理**：技术债偿还预算、ADR 文化、契约治理属于组织机制。
