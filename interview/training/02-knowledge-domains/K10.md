# K10 检查点、恢复与容错

版本锚点：Megatron-LM `main` @ `3703d4e33a3a2b2d11ebcc8e41f45af7ce7d1eda`。证据：`C` 源码/模块文档明确、`I` 跨文档推断、`U / 待验证` 运行类。

## 范围

本域回答"一个可续训的检查点由哪些状态组成、在哪个边界落盘、跨拓扑如何 reshard、故障时如何保持有效进度"。核心是两层 checkpoint 结构、状态集合、统计切面语义、reshard、重放等价性、容错与降级。

本域**不负责**：优化器内部状态数学（K08）、并行度选择（K02/K05）、训练—推理权重交接（K12/K11）。

## 先修知识

- `optimizer.step` 的提交语义（K08）。
- RNG 与 per-device CUDA generator。
- 并行拓扑与 shard 概念（K02）。

## 核心机制

### 1. 两层 checkpoint 结构

Megatron 的 checkpoint 分两层（`C`，`M05-optimizer-checkpointing/implementation.md`）：

- **training checkpointing**：负责命名、tracker、参数校验与全局训练状态（`megatron/training/checkpointing.py:176-230`）。
- **`dist_checkpointing`**：负责 sharded mapping 的存储/加载（`checkpointing.py:611+,1567+,2469+`）。

`GPTModel.sharded_state_dict` 是模型到 checkpoint 层的适配边界（`C`，`gpt_model.py:939+`）。传统 checkpoint 按 iteration、TP/PP/EP rank 与 distributed optimizer 形成路径；distributed checkpoint 用 sharded state dict + metadata，并支持并行度变化时 reshard（`C`，`M05/README.md`）。

### 2. 状态集合

save/load 同时涉及模型、optimizer、scheduler、RNG、tokenizer、数据加载状态和 tracker（`C`，`M05/README.md`）：

| 状态 | 类别 | 缺失后果 |
|---|---|---|
| model params | 计算 | 从头开始，等价未训练 |
| optimizer (m,v,master) | 计算 | 动量丢失，loss 抖动 |
| LR scheduler | 控制 | 学习率跳变 |
| RNG | 控制 | dropout/采样流错位 |
| 数据迭代位置 | 控制 | 重复或跳过样本 |
| tokenizer/tracker | 元数据 | 校验失败或指标断裂 |
| loss scaler scale（fp16/FP8） | 控制 | 溢出行为突变（`I`） |

Megatron 的随机性分成三股相对独立的流（`C/I`，`insights §4.6`）：权重初始化用基础 seed 加 rank 派生 offset；data loader 用独立 seed 控制 shuffle；inference sampling 由采样层自己管。断点续训主要关心前两股，再加驱动 dropout 的 per-device CUDA generator。

### 3. 保存与恢复流程

```text
save: train loop 触发 → save_checkpoint → generate model/optimizer/training state
      → dist checkpoint writer → tracker/metadata finalize
load: load_checkpoint → 解析 iteration/path → check_checkpoint_args
      → 载入 model + optimizer + scheduler/RNG/data → 返回 (iteration, consumed_samples)
```

（`C`，`M05/execution-flows.md`。）`load_checkpoint` 返回的 iteration 与 consumed samples 由训练循环用来重建 sampler 的 epoch 与偏移（`C`）。

### 4. 状态集合点

checkpoint 只能写在一个"整步终了"的边界：清 grad buffer → `zero_grad` → schedule → finalize grads → `optimizer.step` → 聚合 update 状态 → 推进 scheduler（`C`，`M03/implementation.md`）。最自然的切点是一次 `optimizer.step` 成功之后、下一次 forward 之前（`I`，`insights §12.5`）。

- 若这步被 loss scaling 判成溢出而 skip，scheduler 不推进，checkpoint 也应忠实记录这个 skip 状态。
- 写到 step 中途会让参数分片与 optimizer 分片的时间戳不一致。

### 5. reshard 与配置校验

metadata 描述"这个 shard 属于哪个逻辑张量的哪一部分"，因此 load 时能重组或 reshard（`C`）。换并行度（TP/PP/DP）时，把旧 shard 重新映射到新拓扑；这比"换并行度必须重训"前进了一大步（`C`，`insights §14.1`）。

`check_checkpoint_args` 会拒绝或警告关键结构参数不匹配，这是 load 失败的第一道排查点（`C`，`M05/README.md`）。

| 变更 | 影响 | 处理 |
|---|---|---|
| 改 TP/PP/EP | 物理 shard 布局变 | 依赖 metadata reshard |
| 改 num_layers/hidden | 逻辑张量形状变 | `check_checkpoint_args` 拒绝 |
| 换 optimizer 实现 | state 布局变 | 需能映射或转换 |
| 异步保存中断 | tracker 未 finalize | 该 checkpoint 不可用 |

失败排查顺序（`I`）：先看报错是否为 checkpoint args 校验 → 再看 shard metadata 与当前拓扑是否对得上 → 再看 tracker 与文件路径 → 最后怀疑文件系统或异步保存未 finalize。

### 6. 一致切面与异步保存

一次 checkpoint 必须是跨越所有 rank、跨越所有状态分量的"切面"，所有 rank 停在同一 global step（`I`，`expert.md` T-E006）：

```text
Save(step k):
  barrier_all_ranks()                 # 所有 rank 到同一 step
  assert step_r == k for all r
  persist { model_k, opt_k, sched_k, rng_k, data_pos_k, scaler_k }

Load -> Resume:
  restore all above components atomically
  assert resumed_step == saved_step
  assert data_pos consistent with step        # 无重复/无跳段
```

异步保存最危险的地方：后台线程读参数时主循环可能已在写下一步，于是存下"参数是第 k 步、优化器状态是第 k+1 步"的拼接体。防线是保存屏障，或在保存期间冻结参数更新（`I`）。异步保存与 non-persistent/local checkpoint 的清理与恢复语义尚未实测（`C`，`M05` 风险）。

### 7. 重放等价性

重放的等价目标不能是逐位相同：并行改变归约顺序会带来浮点差异。目标是"分布等价/曲线连续"（`I`）：

```text
Replay equivalence (目标, 非逐位):
  E[ loss_resume(t) ]  ≈  E[ loss_no_restart(t) ]   for t > restart
```

验收做法：把"连续跑 N 步"与"跑 N/2 步后存盘、恢复再跑 N/2 步"的 loss 逐点叠图；若恢复点后两条轨迹重合（容差内）则状态集合点正确（`U / 待验证`）。

### 8. 容错与降级

Megatron 训练错误大体分三类（`C`，`insights §14.7`）：

- 配置/初始化错误（整除失败、非法组合、数据集缺失）——早失败。
- 数值/收敛错误（inf/nan）——查 scaling/FP8/学习率/数据。
- 系统/通信错误（NCCL hang、OOM、checkpoint 不一致）。

核心策略是"频繁可恢复的 checkpoint + 快速重启"。可用性建模（`I`，用于推理非实测）：

```text
checkpoint 间隔 = T_ckpt
故障到达率 = λ (1/MTBF)
平均每故障白跑时间 ≈ T_ckpt / 2
恢复开销 r = 检测 + 重启 + 加载
goodput ≈ MTBF / (MTBF + T_ckpt/2 + r)
最优 T_ckpt* ≈ sqrt(2 * r / λ)
```

降级设计成阶梯且可回滚：降在飞 microbatch 与 batch 缓解 OOM → 关部分 overlap → 回退精度档/引擎路径 → reshard checkpoint 换更小拓扑 → 隔离坏节点。每一级都能用上一步的 checkpoint 回滚（`I`）。

### 9. CUDA Graph 与 NCCL MemPool 资源边界

启用 optimizer CUDA Graph 时，optimizer step 与 full-iteration graph 可能共享 capture stream 与 graph memory pool；NCCL `MemPool` 注册/注销必须覆盖实际通信 group（`C`，`M05/README.md`）。恢复路径要覆盖这些资源边界（`C`，`90-cross-module/cuda-graph-resource-lifecycle.md`）。

## 关键不变量

- checkpoint 的 optimizer shard 布局必须与"恢复所用并行拓扑"的 shard 布局匹配；不匹配走 reshard 而非强行 load（`C`）。
- 恢复后"迭代数、样本位置、学习率、随机流"必须与保存点严格衔接（`C`）。
- 保存点必须落在一次成功 step 之后，所有 rank 同一步（`C/I`）。
- RNG 要按 device 逐个存（CPU + 各 CUDA device + data seed）（`C/I`）。
- `check_checkpoint_args` 对关键结构参数不匹配拒绝或告警（`C`）。

## 常见陷阱与反例

- 只存模型权重、不存 RNG 与数据位置：恢复后 dropout mask 与 batch 顺序变样，loss 在恢复点错位，难以定位。
- 把 consumed_samples 设为 `iteration × global_batch`：忽略 shuffle 的 epoch 边界与多数据集 blend 权重，样本顺序对不上。
- 只在 iteration 是 save-interval 倍数时存盘，忽略 `optimizer.step()` 被 skip 的步：scheduler 状态与 iteration 计数脱节。
- 改了 TP/PP 后强行 load 旧 checkpoint：metadata 对不上却不看校验输出，把错误归因到数据或学习率。
- 只存 model 不存 optimizer 分片：resume 后 Adam 状态归零，恢复点附近 loss 抖动。
- 异步保存读到"参数 k 步、优化器 k+1 步"的拼接体：恢复后 loss 突跳。
- 恢复时把"同一配置恢复"当成"逐位一致"：重叠、归约顺序和非确定性 kernel 会改变浮点累加顺序。
- 降级时换了拓扑但没 reshard checkpoint：恢复失败又被误判为新故障。
