## 范围

本域回答"一次 `optimizer.step()` 到底改了哪些状态、在什么条件下提交、状态分片如何影响内存与恢复"。核心是 Adam 状态构成、混合精度 master 参数、distributed optimizer 的分片与通信、update successful 提交语义、梯度裁剪时机、大 batch 稳定性、以及跨版本的 optimizer 契约。

本域**不负责**：DP 的梯度归约原语选择（K03）、混合精度的格式细节（K09）、checkpoint 文件布局（K10）。

## 核心机制

### 1. step 改的不只是参数

以混合精度 + Adam 为例，每参数的状态集合（`C/I`，`insights §12.1/§12.2`）：

| 状态 | 精度 | 是否分片 | 是否入库 |
|---|---|---|---|
| 参数 | bf16/fp16 | TP/PP 切 | 是 |
| fp32 master | fp32 | 随优化器分片 | 是 |
| 一阶/二阶动量 m, v | fp32 | 随优化器分片 | 是 |
| 梯度 | 低精度 | 临时 | 否 |
| grad norm | 标量 | 全局 | 日志 |

每参数账（fp16 + fp32 master，`I`）：`weight(2) + grad(2) + master(4) + m(4) + v(4) = 16 B/param`。参数量 P 时，优化器相关状态可达 `P·12B` 量级，单卡装不下模型未必装不下优化器状态，这正是 ZeRO/分布式优化器存在的理由。

### 2. optimizer factory 与后端可插拔

`get_megatron_optimizer` 根据参数组、混合精度、distributed optimizer、FSDP、CPU offload、MuP、TE/Apex/PyTorch fallback 选择实现；`ChainedOptimizer` 可组合多个 optimizer（`C`，`core/optimizer/__init__.py:1004+`）。optimizer 模块优先 import Transformer Engine，再 Apex，最后 Torch fallback（`C`，`core/optimizer/__init__.py:13-35`）。

`MixedPrecisionOptimizer` 维护低精度参数/主参数、loss scaling 与溢出处理；`FP32Optimizer` 走普通精度路径。**具体 wrapper 选择依赖 config 与可选 backend，不能仅凭类名推导最终运行 kernel**（`C`，`M05/implementation.md`）。

### 3. 一次 step 的时序

```text
1. scaler: if inf/nan -> skip update, adjust scale
2. prepare fp32 master params (mixed precision)
3. gather grads:
     normal: all-reduce
     distributed: reduce-scatter -> 本 rank 分片
4. Adam: m = b1*m + (1-b1)*g ; v = b2*v + (1-b2)*g^2
        p = p - lr * m_hat / (sqrt(v_hat) + eps)     # 对负责分片
5. (optional) all-gather 参数分片
6. record grad_norm -> clip / log
```

（`I`，`insights §12.5` 与 `M05/execution-flows.md`。）关键点：**只有 `optimizer.step()` 报告 update successful 时才推进 scheduler 与迭代计数**（`C`，`M03/implementation.md`）。溢出步被丢弃时，参数、学习率、迭代计数都不动。

### 4. distributed optimizer 的内存模型

`DistributedOptimizer` 以参数 range 和 DP shard 管理 optimizer state，保存/恢复时需与 model sharding metadata 对齐（`C`，`core/optimizer/distrib_optimizer.py`）。

```text
state_total ≈ P · 12B / DP        # master + m + v 分片，grad 也分片
step: reduce_scatter(grad) -> local Adam -> all_gather(param)
     ≡ all_reduce 拆成 RS + AG（与 SP 的带宽等价思路同源）
```

- **省的是状态**：分片对象是梯度与 optimizer state，参数量本身在 DP 副本间仍复制（除非叠加 FSDP）。
- **通信形态改变**：`reduce-scatter` + `all-gather`，带宽与一次 all-reduce 等价，但需 overlap 隐藏两段。
- **与 TP 的关系**：optimizer 状态不随 TP 分片（TP 全量），"TP 越大状态越省"是误解。
- **与 checkpoint 耦合**：shard 布局必须与 model sharding metadata 对齐，换并行度要 reshard（K10）。

### 5. 梯度裁剪与 NaN 防线

```text
# 1) 归约（DP 全局）
grads = all_reduce(grads)              # 某 rank NaN -> 全组 NaN
# 2) 全局范数
total_norm = sqrt(sum(p.grad^2 for p in params))
clip_coef = max_norm / (total_norm + eps)
if clip_coef < 1: grads *= clip_coef    # 全局缩放
# 3) 更新前防线
if scaler.has_inf_nan(): skip; adjust_scale()
else: optimizer.step() -> update_successful
if successful: scheduler.step()
```

（`C/I`，`M05/README.md:22,37`、`M03/implementation.md:23-25`、`insights §12.5`。）

裁剪语义：常用的全局范数裁剪把所有参数梯度当成一个大向量算 L2 范数，超阈值则整体缩放，保持各方向比例。**裁剪必须发生在 DP 归约之后**，否则各 rank 用不同局部阈值，破坏一致性。NaN 是"一点污染、全局扩散"：某 rank 某梯度 NaN，all-reduce 后整组 NaN；两道防线（scaler 检测 + update successful 门）拦住后，坏步被丢弃，状态退回上一步。

### 6. 大 batch 稳定性

```text
global_batch = micro_batch · DP · grad_accum              # I
LR 缩放（常用，I）：
  线性：lr' = lr · k         （k = batch 放大倍数）
  平方根：lr' = lr · sqrt(k) （更保守，大 batch 常用）
warmup：前若干 step 从 0 线性升到目标 LR
clip：||g||_global = sqrt(Σ_shards ||g_shard||²) 后按阈值缩放   # 需跨 DP 聚合
skip：loss/grad 出现 inf/nan → scaler 跳过更新，不推进 scheduler（C 语义）
```

放大 batch 会降低梯度噪声，若不相应调 LR，收敛变慢或停滞。监控三条曲线：loss、grad norm、skipped updates。出现尖峰的排查顺序：先查 precision scale（fp16 loss scaling / FP8 amax），再查 LR/数据（`U / 待验证`）。distributed optimizer 下 grad norm 的聚合与裁剪必须与分片一致，否则裁剪阈值失真。

### 7. 跨版本的 optimizer 契约

升级时最易破坏的是"隐式契约"：optimizer shard 与 model sharding metadata 的对齐关系、参数顺序、命名映射（`C/I`）。兼容性拆成五条契约维度（`I`，`expert.md` T-E015）：

```text
model_structure | parallel_topo | sharded_schema | opt_shard_layout | api_semantics

升级 -> 迁移:
  reshard(old_ckpt) -> new_schema
  校验不变量:
    coverage:   ∀ param -> 恰好一个 shard 覆盖（无遗漏/无重叠）
    alignment:  opt_shard_range 与 model_sharding_metadata 对齐
    equivalence: load 后参数/中间量与升级前在容差内一致
    semantics:  新 API 路径 == 目标路径（不依赖隐式 fallback）
```

`check_checkpoint_args` 会拒绝/告警关键结构参数不匹配，但覆盖的是显式项；`coverage` 与 `alignment` 是分布式 checkpoint 特有的隐式不变量，也是升级事故高发点（`C`，K10）。

## 关键不变量

- 只有 update successful（无 inf/nan）才推进 scheduler 与迭代计数（`C`）。
- 累积阶段对每个 microbatch 梯度除以 `num_microbatches`，且只除一次（`C/I`）。
- 裁剪阈值比较对象必须是 DP 归约后的全局 grad norm（`I`）。
- distributed optimizer 的 shard 所有权与布局必须与 model sharding metadata 对齐（`C`）。
- optimizer 状态不随 TP 分片；省状态靠 DP 分片或 FSDP（`C/I`）。
- GTP rematerialization 与多个 distributed-optimizer instance 当前互斥（`C`）。

## 常见陷阱与反例

- 忽略 scaler 的 inf/nan，坏梯度写进主参数，loss 立刻 NaN。
- 检测到 NaN 仍 step：NaN 写入主参数，之后每步都 NaN。
- 在 DP 归约前按局部梯度裁剪：各 rank 阈值不同，聚合后行为不可预期。
- 把 distributed optimizer 分片状态当普通参数存/读：恢复后分片错位、loss 漂移。
- 以为加大 TP 能省优化器状态：状态不随 TP 分片。
- batch 放大 8 倍但 LR 不动：loss 下降明显变慢，误判为数据质量差。
- 在累积阶段和 finalize 阶段各除一次 M：梯度被缩小 M 倍，几乎不收敛。
- 融合路径只处理参数更新、忘了 scheduler 不推进：学习率按"成功步数"多走。
- 升级后 optimizer shard 与 model metadata 未对齐：load 成功但训练数值漂移，被当成超参问题。
