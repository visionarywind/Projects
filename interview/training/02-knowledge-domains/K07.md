# K07 MoE 与专家并行

版本锚点：Megatron-LM `main` @ `3703d4e33a3a2b2d11ebcc8e41f45af7ce7d1eda`。证据：`C` 源码/模块文档明确、`I` 跨文档推断、`U / 待验证` 运行类。参考 NVIDIA Megatron-Core 官方 MoE 文档。

## 范围

本域回答"MoE 层如何在参数与计算解耦的前提下被分布式执行"。核心是 router/top-k、token dispatch 与 combine、expert parallel（EP）的 all-to-all、容量与丢弃、负载均衡、Parallel Folding。

本域**不负责**：attention 层切分（K04）、序列并行（K06）、优化器（K08）。EP 相关通信域由 K02 建立。

## 先修知识

- softmax/top-k 路由、grouped GEMM。
- all-to-all 通信与 NVLink/IB 差异。
- SP 与 TP 的关系（K04、K06）。

## 核心机制

### 1. MoE 把参数与计算解耦

MoE 每个 token 只路由到 top-K 个 expert，参数量大但每 token FLOPs 不线性增长。若像 DP 一样复制全部 expert，每个 rank 都要装下所有专家，显存浪费；EP 把 expert 分布到多个 rank，token 通过 all-to-all 被派发到持有目标 expert 的 rank（`C`，`insights §11.1`）。

### 2. 一次 MoE 层的前向

```text
X: s×b×h
1. router: score = local_GEMM(X)            # 需完整 token 表示
2. top-k: 每 token 选 K 个 expert（常见 top-2）
3. dispatch: token 重排 → 目标 expert rank   # allgather / alltoall / flex
4. expert FFN: grouped GEMM
5. combine: 同 token 的 K 个输出加权求和
6. 回到原 rank 的统一 layout
```

（`I`，`insights §11.5`。）步骤 3 与 5 是 all-to-all，可与 FFN 计算重叠（`--overlap-moe-expert-parallel-comm`）。

### 3. dispatcher 选择

| dispatcher | 机制 | 通信量 | 适用 |
|---|---|---|---|
| allgather | 全量汇聚后分拣 | 高 | 简单/小规模 |
| alltoall | 直接交换 token | 中 | 常规 EP |
| flex (DeepEP/HybridEP) | 去冗余、跨节点融合 | 优化 | 细粒度 MoE |

（`C`，官方。）A2A 体积量级（`I`）：

```text
dispatch ≈ num_tokens · topK · hidden · dtype_bytes
combine  ≈ 同量级（反向再传一遍）
EP 显存收益：per_rank_expert_params ≈ total_expert_params / EP
```

### 4. 容量与丢弃

为保证计算 shape 可控，可给每个 expert 设容量上限，超出容量的 token 被丢弃（dropping）或保留（dropless）（`C`）：

```text
capacity = ceil(capacity_factor · num_tokens · topK / num_experts)
每个 expert 实际处理 min(route_count, capacity) 个 token
溢出量 = Σ_experts max(0, route_count_e - capacity)

dropless：shape = Σ route_count_e（动态）  → 难 graph capture
dropping+pad：shape = num_experts · capacity（静态）→ 可 graph capture
```

相关配置：`--moe-expert-capacity-factor`、`--moe-pad-expert-input-to-capacity`、`--moe-token-drop-policy probs/position`（`C`）。

capacity factor 是三个目标的旋钮：吞吐（越小越易被 CUDA Graph 捕获）、显存与通信（决定每 expert 缓冲与 A2A 体积上限）、质量（丢弃 token 等价于对部分样本少算，`I`）。

### 5. 负载均衡

路由偏移会让少数 expert 成为热点，A2A 长时间等待，多数 expert 空闲。标准代价函数（`I`，官方）：

```text
L_aux = α · E · Σ_e f_e · P_e
  其中 f_e 是路由到 expert e 的 token 比例、P_e 是门控概率均值
  α 越大路由越均匀但可能牺牲"该专家更合适"的偏好
```

均衡手段：aux loss / sinkhorn 校准路由分布，配合合理 capacity。判据不是"capacity 越大越好"，而是"丢弃率与 graph 收益的平衡点"。

### 6. 并行折叠与 EP 前置约束

- **EP + TP 组合时必须开 SP**，因为 token dispatch 需要统一 layout（`C`，`insights §7.6/§11.2`）。
- **Parallel Folding** 把 attention 层与 MoE 层的并行拓扑解耦：attention 用 `TP×CP×DP×PP`，MoE 用 `ETP×EP×EDP×PP`，因为 MoE 层喜欢高 EP 而没必要高 TP（`C`，`insights §11.3`）。
- FSDP+EP 用双 DeviceMesh，使专家参数只在 EDP 组内 shard，减轻全 EP 组的 all-gather/reduce-scatter 带宽（`C`）。
- `--moe-layer-recompute` 提供 per-layer per-expert 的激活管理（`C`，`insights §12.4`）。

### 7. CUDA Graph 与动态 shape

dropless 的 shape 随路由变化，难以被 CUDA Graph 捕获；token dropping + pad 换来静态 shape 与稳定吞吐（`C`，`insights §11.6/§13.3`）。官方建议动态容量场景只捕获 attention 部分。

## 关键不变量

- EP 与 TP 组合时必须开 SP（`C`）。
- 每 token 恰好路由到 K 个 expert，combine 需按权重求和（`C`）。
- `capacity` 决定每 expert 队列长度与 A2A 缓冲上限；dropping 时 shape 静态、dropless 时动态（`C`）。
- 派发到错误 rank = layout 不一致，前向出错或静默错误（`C`）。
- MoE 参数量不随 FLOPs 增长，但所有 expert 参数仍存在，只是分摊到 EP 组（`C`）。

## 常见陷阱与反例

- 开了 EP 却忘开 SP：token dispatch 的 layout 与 TP 分片不一致，出错或静默错误。
- capacity factor 设得过小导致大量 token 被丢，收敛变差却误以为是学习率问题。
- 开 dropless 又开 CUDA Graph：动态 shape 让捕获失败或 replay 出错。
- 只调 capacity 不加 aux loss：热点专家长期溢出、冷门专家闲置，丢弃率与不均衡同时恶化。
- 以为 MoE 一定比稠密模型省显存：参数量不随 FLOPs 增长，但 expert 参数总量仍存在。
- experts 只有 8 个、batch 很小却强行开大 EP：A2A 开销占比高，吞吐不如 DP 式复制。
- 把 expert 数除以 world_size 当作每 rank 专家数：忽略 ETP/EP 的乘积与 EDP（`I`）。
