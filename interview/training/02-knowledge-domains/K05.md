# K05 流水线并行与调度

## 范围

本域回答"层如何被切成 stage、microbatch 如何在 stage 间流动、气泡从哪来、显存代价是什么"。核心是 1F1B 调度、warmup/steady/cooldown、气泡公式、在飞激活上界、interleaved/virtual pipeline，以及 schedule 的分派规则。

本域**不负责**：层内切分（K04）、序列切分（K06）、并行度的全局组合（K02 给框架，本域给 PP 的定量）。

## 核心机制

### 1. PP 与 microbatch

PP 把模型的层分成多个 stage，每 stage 放在一个（或多个）rank 上，边界用 P2P 传递激活（前向）和梯度（反向）（`C`，`insights §8`）。朴素流水（整批先全 forward 再全 backward）气泡很大，最坏效率趋近 `1/PP`（`C`）。

microbatch 的作用：把 batch 切成多个 microbatch 并在相邻 stage 间流水化，一部分 stage 在算、另一部分在传，填掉气泡（`C`）。若 `MB < PP`，流水线填不满，吞吐退化为接近单 stage 串行——性能远低但不报错。

### 2. 1F1B 时间线与气泡

1F1B（one-forward-one-backward）在稳定阶段让每个 rank 交替执行一个 forward 与一个 backward；关键在于**在飞 microbatch 数被限制在 stage 数量级 PP，而不是总 microbatch 数 MB**（`C`）。

时间线切成三段（`C`，`M02-parallelism/implementation.md` 非交错调度）：

- **warmup**：只 forward，逐 stage 首次前向。
- **steady**：交替 F/B（1F1B）。
- **cooldown**：补齐剩余 backward。

时隙总数 = `MB + PP - 1`，两端各有 `PP - 1` 个气泡时隙：

```text
efficiency ≈ 1 - (PP - 1) / (MB + PP - 1)
```

代入：`MB=16, PP=4` → 气泡 3/19 ≈ 15.8%，效率约 84%；`MB=8, PP=8` → 气泡 7/15 ≈ 46.7%，效率约 53%。经验值：`MB = 4·PP` 约 81%、`8·PP` 约 90%（`C`，论文报告，非本地复现）。

激活驻留：1F1B 下每 rank 同时最多持有 PP 个 microbatch 的激活（`C/I`），不随 MB 线性膨胀；GPipe 需保存整批在飞激活。

### 3. 调度伪代码

```text
for step in range(num_microbatches + num_pipeline_stages - 1):
    if should_forward(step):        # warmup / steady
        forward(microbatch(step))
    if should_backward(step):       # steady / cooldown
        backward(microbatch(step - num_pipeline_stages))
        maybe_finalize_grads()
```

（`I`，基于论文描述与 `M02` 执行流程；控制结构而非每分支精确调用。）

### 4. schedule 分派

`get_forward_backward_func` 的选择规则（`C`，`schedules.py:53-168`）：

```text
PP == 1                          -> forward_backward_no_pipelining
PP > 1 and VP == 1               -> 非交错 pipeline
PP > 1 and VP > 1                -> 交错 pipeline
多模块 process-group collection  -> 多模块兼容的非交错路径
```

非交错调度先算当前 stage 的 warmup microbatch 数，得到发送/接收 tensor shape；每阶段通过 `P2PCommunicator` 收发 activation/gradient，并在完成发送后释放不再需要的 output storage（`C`，`schedules.py:2147+`）。

### 5. output 释放不变量

`deallocate_output_tensor` 不是真正删除 Python tensor，而是保留标量 storage/grad_fn 关系并配合 `custom_backward` 完成反向。`TransformerBlock` 对最终输出创建 viewless tensor，正是为了避免该机制遇到 view tensor（`C`，`schedules.py:171-220`，`transformer_block.py:762-780`）。

### 6. microbatch 数量与整除

```text
local_batch      = global_batch / DP
num_microbatches = local_batch / micro_batch_size
                 = global_batch / (micro_batch_size × DP)

约束1: global_batch % (micro_batch_size × DP) == 0
约束2: num_microbatches >= PP - 1   (实用上 >= 4×PP)
约束3: data iterator 数量与 schedule 匹配
```

（`C/I`，`insights §8`、`M02/README.md` 不变量。）"microbatch"在不同语境既可能指 micro batch size 也可能指切割数，回答时必须点明量纲。

### 7. interleaved / virtual pipeline

VP 把模型层切成多个虚拟 chunk，每个 PP rank 轮流处理多个 chunk，单 chunk 层数从 `L/PP` 降到 `L/(PP·vp)`，在飞激活进一步下降（`C`，`M02/design.md`）。代价是 stage 边界数增多，P2P 次数与 tensor 保存增加，调试复杂度上升。VP 只有在 PP>1 时合法（`C`）。

工程边界：非交错 schedule 启用不支持的 `overlap_p2p_comm` 会抛 `ValueError`（`C`，`M02/execution-flows.md`）——这是非法配置，不是性能问题。

### 8. 并行选择是带约束的优化

把配置选择写成约束优化（`I`，`expert.md` T-E002）：

```text
minimize  T(cfg) = T_compute + T_comm + T_idle
cfg = (tp, pp, cp, dp, mb)
s.t.  world_size == tp*pp*cp*dp
      mem_weight + mem_opt + mem_act(cp, mb, recompute) <= mem_gpu
      global_batch == dp * mb * micro_bs
      pp > 1  if vp > 1

T_idle ~ T_compute * (PP-1)/(MB+PP-1)     # 气泡主导
```

关键洞察：`T_idle` 随 PP 升而升、随 MB 升而降；`T_compute` 随 TP 升（GEMM 碎片化）而效率降。二者对 PP、TP 的单调性相反，因此存在内点最优，不是"每个轴都拉满"。strong scaling（固定 global batch）与 weak scaling（batch 随卡数放大）口径不同，比较前必须声明。

## 关键不变量

- `num_microbatches >= PP - 1`，实用上 `MB ≫ PP`（`C`）。
- 一个 forward 只能消费对应序号 microbatch 的激活，收发必须按序遍历（`C`）。
- schedule 的 model/data iterator 数量必须与调度类型匹配（`C`）。
- VP 合法当且仅当 PP>1（`C`）。
- 非交错 schedule 不支持 `overlap_p2p_comm`（`C`）。
- stage 层数应尽量均匀，否则慢 stage 拖整条流水线（`C`）。

## 常见陷阱与反例

- MB 设得比 PP 还小：流水线几乎填不满，吞吐远低但无报错。
- 把 `pipeline-model-parallel-size` 从 4 调到 8 而不改 global batch：MB 相对 PP 变小，气泡从约 16% 涨到近 50%，吞吐反降。
- 以为 PP 能省激活：PP 省权重/梯度/优化器状态，不省激活；每在飞 microbatch 的激活都得驻留。
- stage 层数不均衡（首尾 stage 多背 embedding/output）：慢 stage 成瓶颈，气泡公式在不均衡时不再成立。
- 在非交错 schedule 上开 `overlap_p2p_comm`：直接抛 `ValueError`（非法配置）。
- interleaved 与 recompute 简单叠加：两者都降低激活但也都增加调度复杂度，收益可能部分重叠。
