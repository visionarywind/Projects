# K13 模型结构与计算图

版本锚点：Megatron-LM `main` @ `3703d4e33a3a2b2d11ebcc8e41f45af7ce7d1eda`。证据：`C` 源码/模块文档明确、`I` 跨文档推断、`U / 待验证` 运行类。

## 范围

本域回答"配置、ModuleSpec 与 GPT 模型如何装配成可执行的 Transformer，forward 的输入输出契约是什么，并行下输出语义如何变化"。核心是装配链、`TransformerConfig`/`ModuleSpec`/`GPTModel` 三者分工、`pre_process`/`post_process` stage 职责、`parallel_output` 分片语义、CE 融合、以及 forward 与 schedule 的边界。

本域**不负责**：microbatch 顺序与 P2P（K05）、优化器（K08）、数据（K12）。模型只做数学，调度归 schedule。

## 先修知识

- embedding、attention、MLP、LayerNorm、logits/CE loss。
- TP 的 hidden/词表分片（K04）。
- PP stage 与 `pre_process`/`post_process`（K05）。

## 核心机制

### 1. 装配链：配置 → spec → 模型

真实装配链是 `model_provider` → `gpt_builder` → `GPTModel.__init__` → `TransformerBlock`（`C`，`M01-core-models/README.md`）：

```text
model_provider(args,...)
  -> model_builder(args,...)
    -> gpt_builder()
      -> branch: args.spec / experimental / num_experts / heterogeneous / default
        -> get_*_layer_spec()
          -> GPTModel(...)
            -> LanguageModelEmbedding + TransformerBlock + output_layer
              -> GPTModel.forward()
                -> TransformerBlock.forward()
                  -> layer attention/MLP/TE kernels
                    -> logits or hidden-state output
```

（`C`，`gpt_builders.py:24-110`，`gpt_model.py:98-242`。）三者的分工：

- **`TransformerConfig`**：模型蓝图（维度与特性），约束模型结构。
- **`ModuleSpec`**：每层使用哪个实现（本地 / TE / MoE / 实验 / 异构）。
- **`GPTModel`**：把蓝图实例化的容器。

模型接受 `ProcessGroupCollection` 作为通信上下文（`C`，`gpt_model.py:95-130`），不自行创建 distributed group。GPTModel 明确发出 deprecated warning，迁移目标是 HybridModel（`C`，`gpt_model.py:123-128`）。

### 2. spec 分派

builder 的分支顺序（`C`，`gpt_builders.py:31-54`）：

```text
if explicit spec: use it
elif experimental attention: choose experimental spec
elif experts: choose MoE block spec
elif heterogeneous: choose heterogeneous spec
else: choose local/TE/inference spec
```

`gpt_builder` 的分支改变的是 Transformer layer spec，不改变 provider 的外部返回契约（`C`）。

### 3. forward 契约

`GPTModel.forward(tokens, position_ids, attention_mask, labels)` 输出 hidden/logits/loss，且 stage、dtype、shape 必须与 config 匹配（`C`，`M01/interfaces.md:21`）：

```text
GPTModel.forward(tokens, position_ids, mask, labels):
    if pre_process:  hidden = embed(tokens, position_ids)   # 词表列切 + allreduce
    hidden = transformer_block(hidden, mask, ...)
    if post_process:
        logits = output_layer(hidden)          # parallel_output -> 分片
        loss = cross_entropy(logits, labels)   # 融合，只通信 loss 标量
    return (output, loss_func?)                # schedule 期望 (output, loss_func)
```

（`C`，`M01/implementation.md:63-70`；核心 forward 行号 `gpt_model.py:567-676`。）

关键契约：

- **两段式职责**：`pre_process`/`post_process` 决定本 stage 是否拥有 embedding/output；GPTModel 据此条件创建子模块（`C`，`gpt_model.py:175-182,256-279`）。
- **TP 输出语义**：`parallel_output=True` 时 output logits 保持 TP 分片 `[b, s, v/t]`，调用方不能假定全词表已 gather（`C`，`gpt_model.py:104-109`）。
- **`forward_step_func` 返回 `(output_tensor, loss_func)`**；schedule 不要求模型知道具体 loss 聚合策略（`C`，`M02/interfaces.md:24`）。
- **schedule 边界**：模型只输出 hidden states；stage 间收发与 activation 生命周期由 pipeline schedule 拥有（`C`，`M02/design.md:19`）。

| 张量 | 形状 | TP 语义 |
|---|---|---|
| tokens | `[b, s]` | 复制 |
| hidden | `[s, b, h/t]`（SP 下） | 序列/隐藏分片 |
| logits | `[b, s, v/t]` | 词表分片 |
| loss | 标量 | 跨 rank 归约 |

### 4. CE 融合与词表分片

logits 与交叉熵损失融合：先算局部 `[Y1,Y2]`，只对 loss 标量跨 rank all-reduce，通信量从 `b·s·v` 降到 `b·s`（`C`，`insights §6.13`）。这是"为什么 logits 不直接 all-gather"的答案：词表极大，全量通信体积是 `b·s·v`。

embedding 按词表列切后需一次 all-reduce 汇总 token 的 embedding；输出投影行切后 all-reduce（K04）。

### 5. ModuleSpec 的代价

ModuleSpec 把"层实现规格"与"实现"分离，支持同一 GPT 外壳适配多种后端（local/TE/MoE/异构）。代价是 spec 与实际 class 的绑定藏在 registry、读代码跳转变多（`C`，`insights §4.2`）。这是设计取舍：变化频率高、隔离价值高的抽象值得做；为一次性差异加 registry 则是过度设计（K12 展开）。

### 6. 关键不变量

- `config` 与 layer spec 的维度、normalization、MoE 属性必须兼容；builder 对 inference optimized/MTP 有断言（`C`，`gpt_builders.py:55-87`）。
- `pre_process`/`post_process` 决定 pipeline stage 是否拥有 embedding/output（`C`）。
- `parallel_output=True` ⇒ logits 保持 TP 分片，调用方不能假定全 vocab 已 gather（`C`）。
- `pg_collection` 被下传给 embedding、decoder 和 MTP；缺失时存在兼容 fallback/全局路径（`C`）。
- 模型接受通信上下文，不创建 default distributed group（`C`，`M01/README.md` 职责与非职责）。
- forward 不在模型内做 P2P；stage 间收发归 schedule（`C`）。

## 常见陷阱与反例

- 外部对分片 logits 直接做全词表 softmax/argmax：把分片当全量，产生错误概率/错误 token，不报错。
- 非最终 stage 也去计算 loss：缺少 label 语义，结果无意义；PP 下中间 stage 只输出 hidden。
- 以为 forward 输出一定是 logits：PP 下中间 stage 只输出 hidden。
- 把模型构造放在 `initialize_model_parallel` 之前：TP 层不知道自己的 rank，权重分片位置错误（K01/K02）。
- 在 model forward 里自己发 P2P：与 schedule 职责重叠，收发错位。
- 修改 `TransformerConfig` 字段而不核对所有消费方：影响 argument parser、YAML、builder spec、checkpoint key 和模型测试（`C`，`M01/design.md`）。
