# K02 显存与内存管理

## 学习目标

分清驱动、分配器、框架三套显存账本各自的口径，理解段/块/size class 的分配状态机与碎片成因，能判断一次 OOM 是容量型还是碎片型并给出从无损到减载的回收顺序。掌握 stream-aware 的延迟复用与生产 allocator 在并发、限额、多租户下的取舍。

## 核心机制

- 账本关系：allocated ≤ reserved ≤ 设备总显存，cached = reserved − allocated；驱动视角的 free 另算，与池内空闲不是一回事。
- 两级结构：向驱动申请段（segment），段内切成块（block），块按 size class 分桶，靠 split/merge 调整大小并做 best-fit 查找。
- 待回收（pending）状态：块被 free 后若仍有 stream 在引用，要等该 stream 到达同步点才真正回到空闲链表，这是延迟复用的正确性关键。
- 碎片判定量是最大连续空闲块 L，而不是空闲总量 F；L 不满足请求或对齐要求时，即使 F 充足也会分配失败。
- 生产 allocator 的权衡：预留换时间、锁粒度、大请求绕过池、按 stream 分池、多租户配额与分级 OOM 策略。
- 回收与成本耦合：碎片抬高达到同吞吐所需容量，容量换算成设备数与电费，联合优化时把碎片率与延迟当作成本约束项。

## 常见坑

- 把 reserved 当成「已用显存」、把 cached 当成泄漏，得出错误的显存泄漏结论。
- 只看 nvidia-smi 的数字判断框架真实占用，忽略分配器自己的账本。
- 用空闲总量 F 判断能否分配，忽略最大连续块 L 与对齐要求。
- free 之后认为地址可立即复用，忽略 pending 状态与跨流登记。
- 一遇 OOM 就杀请求，跳过无损的池内归并与空段归还。
