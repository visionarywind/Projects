# K01 Runtime 分层与设备边界

## 学习目标

分清 Framework、Runtime、用户态/内核态驱动、Device 各层各自持有什么状态、负责哪种转换，并能沿一次调用链指出异步边界与错误反向传播的落点。掌握执行对象（device/context/stream/module）的归属关系，能解释跨 context 句柄失效、取消与超时的语义边界，以及 ABI/版本/能力对兼容性和故障域的影响。

## 核心机制

- 分层职责按「谁持有状态、谁做转换、谁保证完成」划分：框架管算子语义与 Tensor，runtime 管执行队列与内存池，驱动管句柄、地址映射与硬件提交，设备真正执行。
- 执行对象是四种不同性质的东西：device 是硬件实体，context 是资源域，stream 是顺序域，module 是代码实体，包含关系为 device ⊃ context ⊃ {stream, module, 显存分配}，句柄只在创建它的 context 内有效。
- 完成语义分层：同步 API 返回等价于「执行完成且结果可见」，异步 API 返回只表示「已提交入队」，两者相差一次设备执行。
- 错误反向传播：设备错误经内核驱动、用户态驱动、runtime 才能在 join 点被框架观测，因此常在很晚的同步点才暴露。
- 兼容性靠运行期协商：ABI、驱动/运行时/固件版本与架构能力共同决定 feature fallback，能力缺失应显式声明而非静默走慢路径。
- 故障域与热升级：隔离强度分进程级、上下文级、设备级，设备侧状态（已捕获图、注册内存）不可迁移时只能排空。

## 常见坑

- 说「runtime 负责计算」，把执行落点错放到 runtime（计算在设备）。
- 把异步提交返回当成执行完成，提交后立刻释放被引用的内存。
- 认为框架层能即时捕获设备侧错误，忽略设备错误的异步反向传播。
- 把 device（硬件实体）与 context（资源域）混为一谈，忽略跨 context 句柄失效与线程局部性。
- 用后端版本号到处写条件分支，而不是按能力协商，抽象层退化成版本分发器。
