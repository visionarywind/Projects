# K04 张量与图执行

## 学习目标

理解 Tensor 的逻辑形状与物理布局的差别（shape/dtype/stride/contiguous），分清 eager 与 graph 两种执行路径在分派开销与内存规划上的不同，能沿「Python → 图/算子 → 执行引擎 → 设备适配 → 驱动」追踪抽象边界与报错落点，并在框架迁移时按目标版本事实做分层验证。

## 核心机制

- Tensor = 一块内存 + 一套解释规则：shape/dtype 定义逻辑结构，stride 把多维索引映射到内存偏移，行优先连续时 stride[i] 等于其后各维长度之积。
- 非连续视图：转置、permute 往往只改 stride 不搬数据；把非连续 tensor 送进要求连续的 kernel 会触发隐式拷贝，是常见性能陷阱。
- eager 与 graph 的执行差异：eager 逐算子即时分派 launch，灵活可调试但每步都付固定开销；graph 先捕获命令序列再整体重放，把分派开销摊薄，但要求序列与地址稳定。
- 内存规划差异：静态图在编译期按张量 live interval 做区间复用与 arena 偏移切分，峰值可预测；动态图运行时逐次分配、靠引用计数与池复用，峰值事后才知。
- 抽象边界：第一边界在「是否进入图」，第二边界在「执行引擎 → 设备适配」（算子注册与可插拔后端落点），第三边界在「设备适配 → 驱动」。
- 版本事实纪律：只依据目标版本源码与官方文档判断行为，避免把其它框架的同类机制直接类比过来。

## 常见坑

- 认为 shape 相同就是同一布局，忽视 stride 与隐式 contiguous 拷贝的开销。
- 假设 graph 自动支持任意动态控制流，或在捕获区内做 device synchronize 与普通分配。
- 把图编译期的报错与执行期、设备期的报错混为一谈，归因到错误的层。
- 运行时才发现算子不支持，而不在计划阶段用能力矩阵前置判定，产生不可预测的停顿。
- 把动态图实测峰值直接反推静态图容量，无视编译期内存规划的差异。
