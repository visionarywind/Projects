# K03 异步执行与同步原语

## 学习目标

掌握同一 stream 内的顺序保证与跨 stream 依赖的表达方式，理解 event record/wait 只传递进度而不搬运数据，并能据此设计安全的生产者-消费者编排、延迟复用与进程 teardown。理解 graph capture 对地址稳定和执行序列的约束，以及取消/超时/尾延迟争用下的调度取舍。

## 核心机制

- 顺序范围：同一 stream 内命令按提交顺序全序执行；跨 stream 之间无序，必须用 event 显式建立 happens-before。
- event 语义：record 在某条流上标记触发点，wait 在另一条流上制造依赖，两者都是设备队列上的异步操作，不阻塞 host；order 建立即附带数据可见性。
- 延迟复用：异步引用在完成被确认前，buffer 既不能释放也不能复用；靠 stream 记录或 record_stream 语义保护，跨流共享必须登记全部使用流。
- 生产者-消费者用 full/empty 一对 event 加多 buffer 轮转，构成基于流的事件信号量：full 防读早，empty 防覆写。
- graph capture 要求执行序列与内存地址稳定，捕获期不允许非法同步与普通分配，动态部分要么走图安全池，要么移出捕获区。
- teardown 与回收顺序：停提交 → join → 排空同步 → 取出异步错误 → 逆序释放；取消与超时都不等于设备已停，回收仍等真实完成。

## 常见坑

- 以为不同 stream 之间也有顺序，跨流共享 buffer 却不加 event。
- record 之后立即查询耗时或释放资源，读到未触发时的无效值。
- 只建单向 full 依赖，漏掉 empty，导致生产者覆写消费者尚未读完的 buffer。
- 复用同一 event 覆盖尚未被消费的依赖，新旧依赖混叠。
- 把 event synchronize 当成全局同步，或在信号处理函数里直接释放设备资源。
