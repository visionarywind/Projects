## I001. 一次 framework→runtime→driver 的 kernel 调用链上依次发生了什么？

- 难度：中等级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：流程追踪
- 面试频率：高频
- 前置知识：B001 分层模型、命令队列、launch 的异步语义
- 关联题目：I002, B001
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

表面看，一次 kernel launch 就是一行函数调用：`y = op(x)`。实际上它要穿过前端解释、算子分派、后端 kernel 选择、参数打包、命令入队、驱动下发、硬件调度这一整条链路。逐段看清每一层做了什么，才能判断「返回」到底停在哪一层。

### 2. 问题分析

追踪的目标有三个：状态在哪一层被创建或修改、异步边界在哪一步形成、失败可能在哪一段发生。不要把它当成一次函数调用，而要当成一次「命令的生产与入队」。

### 3. 具体答案

按顺序拆成以下阶段：

1. 前端（Python 或图前端）：确定调用哪个算子，收集参数与关键字，选择分派键（autograd、device、dtype、layout），必要时登记反向节点。
2. 框架 C++ 分派层：做 shape/dtype/device 合法性检查，处理内存格式与广播，选出具体后端 kernel 实现，计算 grid/block 等 launch 配置；首次使用某 context 时可能触发惰性初始化。
3. 分配器：若该算子需要输出或中间 buffer，先向 caching allocator 申请；命中池则直接返回块，否则向驱动申请新段。
4. 框架 → runtime：把 kernel 参数、stream 句柄、launch 配置打包成一条提交描述，调用 runtime 的 launch 入口。
5. runtime → UMD：runtime 把命令写入某条 channel 的提交队列；用户态驱动校验句柄、为首次访问的新显存更新页表映射、生成硬件命令。
6. UMD → KMD → 硬件：通过 ioctl/门铃通知内核驱动，内核驱动把命令交给设备的调度单元或直接写入硬件队列。
7. 设备：硬件调度器取出这一格 grid，加载对应代码与数据，开始执行。
8. 完成与上报：执行结束写入进度值/fence，内核驱动收到中断，event 状态更新；只有 synchronize 或 event wait 才会把这个完成信号暴露给上层。

返回语义：这条链路里，函数返回发生在第 5 步左右——命令已入队但设备尚未执行。第 6 步之后的任何失败都是异步暴露的。

### 4. 技术洞察

- host 看到的「调用成功」等价于「命令入队成功」，与「设备算对」之间隔着一次完整执行。
- 首次触及新分配显存时，页表映射可能在提交路径上被补齐，这是某些 launch 突然变慢的原因之一。
- 设备侧错误（越界、非法指令）只能经内核驱动与 runtime 异步回传，因此常在很晚的 join 点才被检查到。
- 图捕获把第 4~6 步的 host 往返压缩成一次重放，收益主要来自省掉重复的提交与校验开销。

### 5. 图文说明

```text
[Python/前端] 选算子、分派键
      │
[框架 C++]    shape/dtype 检查 → 选 kernel → 打包参数
      │
[分配器]      申请/复用输出 buffer
      │
[runtime]     写提交描述 → channel 队列        ← 函数返回点约在此层
      │
[UMD/KMD]     校验/页表/命令 → 门铃/中断
      │
[Device]      调度 grid → 执行 → 写 fence
      │
[join 点]     synchronize / event wait 才可见完成
```

### 6. 拓展知识

可以延伸到图捕获与重放、设备端持久 kernel 与自旋调度、launch 边界与占用率、以及 MPS/多进程共享设备时的提交路径差异。

### 7. 常见追问及回答要点

- **怎么区分是提交慢还是执行慢？** 用 profiler 把 host 提交时间与设备执行时间分轴对齐，提交慢则 host 侧堆栈在等锁或页表，执行慢则 device 轴上的 kernel 段变长。
- **为什么第一次 launch 特别慢？** 惰性初始化、模块加载、页表补齐都发生在首次；预热后这些开销消失。
- **异步边界出错会怎样？** 返回成功但设备随后报错，表现为「当时没事、后面某次同步突然异常」，需要保留反压到具体 get_last_error 查询点。

### 8. 易错点与反例

- 把 launch 返回当成 kernel 执行完成。
- 以为框架层能捕获设备侧错误并即时抛出。
- 忽略页表/惰性初始化对首帧延迟的影响，把首帧慢误判成算子本身慢。

### 9. 实践与验证

写一个程序，在 launch 前后各打 host 时间戳，并在 launch 后立刻调用一次会暴露错误的查询；再用 profiler 对齐 host 提交段与 device 执行段，确认「返回点」在提交之后、执行之前。

### 10. 评分标准

- 合格：能按层次说出这条调用链。
- 良好：指出异步边界与错误反向传播的位置。
- 优秀：用 profiler 把提交与执行分轴归因，并解释首帧慢的原因。

## I002. stream 的创建、销毁与复用应该怎么管理？

- 难度：中等级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B002 执行对象、B007 同流顺序、channel 与硬件队列
- 关联题目：I006, B002
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

stream 是一条命令队列，归某个 context 所有。每条 stream 在底层往往对应一个硬件通道或提交队列，通道数量有限。创建、销毁和复用如果随意，会同时踩到顺序语义、资源上限和 teardown 三类坑。

### 2. 问题分析

设计要回答三件事：什么时候建、建多少、什么时候销毁；以及复用同一 stream 时如何保持顺序语义。核心矛盾是「独立工作流需要不同 stream 才能并发」对「通道有限、stream 太多会互相挤压」。

### 3. 具体答案

- 创建时机：按执行角色建立，而不是按算子建立。典型角色包括计算流、H2D 拷贝流、D2H 拷贝流、集合通信流。角色数量在一个稳定集合内，启动时一次性建好。
- 数量控制：先用最少的 stream 满足流水线需求（常见是计算 1 条 + 拷贝 2 条 + 通信若干）。stream 数量逼近通道上限后，新的提交会被迫串行或直接失败，所以要留余量。
- 优先级：对延迟敏感的流（如交互式 decode）设高优先级，后台/预取设低优先级，让调度器在资源紧张时正确取舍。
- 复用方式：同一角色内用「流池 + 轮转」复用，避免反复创建销毁；每条流内部靠 FIFO 保证顺序，跨流依赖用 event 显式建立。
- 销毁前提：销毁前必须保证该 stream 上所有命令已完成，否则属于未定义行为。方法是对该 stream synchronize，或等它已 record 的最后一个 event 触发。
- 生命周期归属：stream 属 context；context 销毁前所有 stream 必须先销毁或同步。进程 teardown 时按「先停提交、再同步、后销毁」的顺序收尾。

### 4. 技术洞察

- 「每个算子建一条 stream」是最常见反模式：既丢失同流顺序保证，又迅速耗尽通道，还制造大量创建销毁开销。
- stream 是顺序域而非算力，多 stream 只在确实想并发独立工作量时才有意义。
- 默认流有隐式同步语义，混用默认流与显式流可能把本该并发的部分串起来，需要明确使用每线程默认流或全部用显式流。
- 复用 stream 时要注意 event 也复用其所属流的状态，重 record 之前要确保旧的 wait 已消费。

### 5. 图文说明

```text
启动：
  compute = create()      (高优先级)
  h2d     = create()      (拷贝)
  d2h     = create()
  comm    = create()      (通信)
运行：提交都复用到对应角色流，跨流依赖用 event 连接
关闭：
  停提交 → 每条流 synchronize → destroy 各流 → 销毁 context
```

### 6. 拓展知识

可以延伸到每线程默认流与显式流的选择、stream 优先级在抢占中的作用、CUDA Graph 对流的约束、以及多进程中 channel 的分配。

### 7. 常见追问及回答要点

- **stream 能不能无限建？** 不能，通道与句柄有限；接近上限后并发退化为串行或创建失败。
- **销毁前不同步会怎样？** 未定义行为，可能崩溃或留下悬空句柄，设备上正在跑的命令失去归属。
- **怎么决定流数量？** 按需要并发的独立工作流数量定，再用 profiling 验证是否真的重叠。

### 8. 易错点与反例

- 用 stream 数量去追求「并行」，结果通道耗尽反而更慢。
- 图方便在算子层反复 create/destroy。
- 销毁时不做同步，teardown 阶段偶发崩溃。

### 9. 实践与验证

建立一个小的流池，交替提交计算与拷贝，用 profiler 观察计算与拷贝是否重叠；再把流数量逐级增加，找出并发收益饱和甚至下降的拐点。

### 10. 评分标准

- 合格：说出按角色建流、销毁前要同步。
- 良好：讲清通道上限与复用池的必要性。
- 优秀：把优先级、默认流语义与并发收益饱和一起纳入设计。

## I003. caching allocator 的状态机和 size class 如何决定一次分配的走向？

- 难度：中等级
- 知识域：K02（显存与内存管理）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B004 账本、B005 碎片、B006 保留动机
- 关联题目：I004, I005, B004
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

caching allocator 在驱动分配之上叠了一层池。池里的空闲空间被切成「段（segment）」和「块（block）」，块按大小分档管理。一次 allocate/free 会推动块在这些状态之间迁移，走哪条路径取决于请求大小和当前池状态。

### 2. 问题分析

要回答两件事：块的有限状态如何迁移，以及 size class 如何把「找一个够大的块」变成「在某个桶里找」。理解这两点，才能解释为什么同样大小的请求有时秒回、有时触发新段申请，以及 OOM 时为什么要按特定顺序回收。

### 3. 具体答案

块的状态迁移：

- 空闲（free）：在某个 size class 的空闲链表里，可被复用。
- 已分配（allocated）：已交给上层 tensor。
- 待回收（pending）：被 free 了但仍有 stream 在使用，只有相关 stream 到达同步点后才真正回到空闲。
- 已分段（split 出的剩余）：大块切小后剩下的部分回到对应 size class。
- 已归并（coalesced）：相邻空闲块合并成更大块，可能升到更大的 size class。
- 已归还（released）：整段空闲后交还驱动，从池中消失。

一次 allocate(size) 的走向：

1. 把 size 向上取整到所在 size class（小请求按固定对齐，如 512 字节量级；不同实现对大小池设阈值，常见在 1MB 量级分离大小池）。
2. 在该 class 的空闲链表里找可满足请求的块，优先选浪费最小的（best-fit 类策略）。
3. 命中则切分：取走请求部分，余量放回更小的 class。
4. 未命中则向上一级更大 class 借块切分，仍不满足才向驱动申请新段。
5. 超过大池阈值的请求可能绕过池直接向驱动申请，用完即还，避免污染池。
6. 申请新段失败（驱动 OOM）时，触发回收流程后重试。

一次 free(ptr) 的走向：

1. 定位该指针所属块，标记为待回收，记录使用它的 stream。
2. 若没有跨流使用，立即回到空闲链表；若有，等该 stream 到达同步点再入池。
3. 入池时尝试与地址相邻的空闲块归并，归并后若整段空闲，可选择归还驱动。

### 4. 技术洞察

- size class 是「用内部碎片换查找速度」：请求被取整，桶内块大小一致，查找只需在固定链表上做；代价是块尾浪费。
- 待回收状态是正确性的关键：它保证 in-flight 访问的块不会被立刻复用。
- 大请求绕过池是为了防止一块巨型 buffer 长期占住池、抬高后续小请求的峰值。
- 归并只能对地址相邻的空闲块做，因此碎片严重时「总空闲够但最大连续块不够」。

### 5. 图文说明

```text
allocate(s):
  s → size_class ──命中空闲块──▶ 切分 → allocated
                 └─未命中─▶ 更大 class 借块 → 切分
                            └─仍无─▶ 向驱动申请新段
free(p):
  allocated →(有跨流使用?)─是─▶ pending ─流到同步点─▶ free
                          └─否─▶ free ─▶ 与邻块归并 ─▶ 段全空则归还驱动
```

### 6. 拓展知识

可以延伸到 stream-ordered allocator 与驱动原生异步分配、可扩展段、size class 阈值调参、内存快照工具，以及多线程下小池的轮转分布策略。

### 7. 常见追问及回答要点

- **为什么同样大小有的快有的慢？** 命中桶就快；需要切大块或申请新段时就慢，取决于池当时的最大块与水位。
- **size class 会不会造成浪费？** 会，取整带来内部碎片；桶越粗浪费越大、查找越快，是权衡。
- **pending 状态怎么观测？** 在内存快照里表现为「已 free 但尚未归还的空闲量」与 stream 的对应关系。

### 8. 易错点与反例

- 把「块已 free 入池」等同于「驱动已释放」，混淆池内空闲与驱动视角空闲。
- 忽视 pending 状态，认为 free 后地址可立即复用。
- 忽略大请求绕过池的行为，用池指标解释其实来自直连驱动的分配。

### 9. 实践与验证

记录一段分配-释放序列，导出内存快照，观察块在 class 间的迁移与归并；再构造相邻小块，验证 free 后是否归并成更大块并影响后续请求能否命中。

### 10. 评分标准

- 合格：说出空闲/已分配两态与桶查找。
- 良好：补上 pending 与切分/归并。
- 优秀：讲清 size class 的取舍、大请求绕过池与 OOM 重试路径。

## I004. OOM 发生时回收顺序应该怎么设计才能最大化释放？

- 难度：中等级
- 知识域：K02（显存与内存管理）
- 题型：故障排查
- 面试频率：高频
- 前置知识：I003 状态机、B004 账本、B006 释放权衡
- 关联题目：I003, I005, B004
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

OOM 有两种：真容量不足，和池内碎片导致「总空闲够、最大连续块不够」。回收顺序若设计成「一上来就杀掉请求」，会把本可救活的碎片型 OOM 也判死刑；若只做无损整理，也可能在容量型 OOM 上白等。

### 2. 问题分析

设计目标是让回收尽量无损、按代价从低到高推进，并在每次回收后重试原分配，直到成功或确认无法救回。顺序要兼顾三类对象：池内空闲、不再被引用的 tensor、以及可放弃的新请求。

### 3. 具体答案

推荐的回收顺序（代价从小到大，逐级重试）：

1. 池内整理：合并相邻空闲块，检查是否只是最大连续块不足；若合并后能命中，直接复用，不惊动任何上层对象。
2. 释放整段空闲：把池内已完全空闲的段归还驱动，降低 reserved，给驱动侧腾出真空间。
3. 清理非当前 stream 的空闲缓存：某些实现按 stream 分池，把活跃 stream 之外的空闲块回收。
4. 触发上层垃圾回收：释放 Python/C++ 中引用已消失的 tensor（引用计数 + 循环 GC），让它们真正把块还给池。
5. 释放临时中间量：推理场景优先回收已结束请求的 KV cache 与临时激活；训练场景回放已过期的中间激活。
6. 设备同步兜底：对相关 stream synchronize，让处于 pending 的块到达同步点真正入池，释放被异步访问钉住的空间。
7. 减载：仍失败则拒绝或排队新请求、降低 batch，把到达率压到处理率以下。
8. 最后手段：记录完整内存快照、上报可读错误、必要时重启进程恢复干净状态。

每做一步都重试原分配；成功即停止，避免过度回收。

### 4. 技术洞察

- 先区分 OOM 类型再决定策略：碎片型靠第 1、3 步，容量型必须走到第 7 步。
- pending 块数量在 OOM 时往往偏高，因为很多 free 都卡在异步未完成上；第 6 步的同步是释放它们的前提。
- 回收顺序不能跨越「正在使用的块」：任何 step 都要检查块的 stream 状态。
- 清空缓存在多租户下要谨慎，可能把本进程峰值预留让出后又被同机其它进程抢走。

### 5. 图文说明

```text
OOM ─▶ 池内归并 ─命中?─▶ 复用成功
        │否
        ▼
      释放空段 ─▶ 重试
        │否
        ▼
      GC + 释放临时量 ─▶ 重试
        │否
        ▼
      同步释放 pending ─▶ 重试
        │否
        ▼
      拒绝/排队新请求（降载）
        │否
        ▼
      快照 + 报错 + 重启
```

### 6. 拓展知识

可以延伸到内存快照分析、可扩展段对碎片的影响、多租户显存配额、以及推理里 KV 的换出（swap）作为额外一级回收。

### 7. 常见追问及回答要点

- **为什么先合并再删对象？** 合并是无损的，能把可救的碎片型 OOM 就地解决，避免误伤正在跑的任务。
- **同步会不会拖慢关键路径？** 会引入等待，所以只作为回收的一级，且仅在必要时触发。
- **反复 OOM 怎么办？** 说明工作集本身超过容量，应调小 batch/并发或降低精化，而不是靠回收硬扛。

### 8. 易错点与反例

- 一遇 OOM 就杀请求，损害可用性且掩盖碎片问题。
- 只清缓存不做归并，忽略 pending 块。
- 把「总量够」当成「一定能分配」，不在回收后重试。

### 9. 实践与验证

构造一个碎片型 OOM（交错分配多种大小再释放一部分），验证归并后能救回；再构造容量型 OOM，验证只有降载能恢复，并记录每级回收实际释放的字节数。

### 10. 评分标准

- 合格：给出从无损到减载的回收顺序。
- 良好：区分碎片型与容量型并逐级重试。
- 优秀：把 pending 与跨流释放纳入，并能用快照量化每级回收效果。

## I005. 如何定量分析显存碎片？

- 难度：中等级
- 知识域：K02（显存与内存管理）
- 题型：实现设计
- 面试频率：中高
- 前置知识：I003 块状态、B005 碎片种类、内存快照工具
- 关联题目：I003, I004
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

「碎片严重」是一句定性判断，面试里需要落到可计算的指标。碎片的核心矛盾是「总空闲量」与「最大可分配连续块」不一致。要定量，就得从分配器导出块的分布，再计算能反映这种矛盾的量。

### 2. 问题分析

设计一套指标与流程：先取快照拿到块的列表，再计算外部碎片率、内部浪费、块数分布，最后用「请求 X 是否可满足」做验证。指标要能区分外部碎片、内部碎片和 pending 占用。

### 3. 具体答案

核心指标：

- 最大连续空闲块 `L`：真正决定大请求能否成功的量。
- 空闲总量 `F`：所有空闲块之和。
- 外部碎片率 `frag_ext = 1 - L / F`：越接近 1 越碎；`F` 大而 `frag_ext` 高即典型碎片。
- 内部浪费 `waste_int = Σ(rint(size) - size)`：请求取整到 size class 后累计的浪费。
- 空闲块大小直方图：按数量与字节两个维度分桶，看长尾小块是否过多。
- pending 占比：处于待回收态的字节 / 总 reserved，反映异步钉住的空间。
- 失败裕度：分配失败时仍剩余的空闲总量 `F_fail`，直接量化「够却分不出」。

执行流程：

1. 用分配器提供的快照接口导出一份带地址、大小、状态、所属 stream 的块表。
2. 按地址排序，识别空闲区段并计算 `L`、`F`、块数、中位数。
3. 对各 size class 统计命中率，估算请求取整后的浪费。
4. 用一组代表性的请求尺寸做「能否满足」模拟，输出命中率。
5. 沿时间轴重复采样，画 `L`、`F`、`frag_ext`、pending 占比的曲线，观察碎片随 workload 的演化。

对比实验：固定 shape 循环 vs 变长 shape 循环，比较两条 `frag_ext` 曲线的差异，验证「定长降低碎片」这一结论。

### 4. 技术洞察

- 判断是否能分配，必须用 `L` 而不是 `F`；只看总量的结论会误导。
- 内部碎片和外部碎片要分开算：前者是 size class 设计的代价，后者是分配时序的代价，缓解手段不同。
- pending 高会同时抬高 reserved 并延后归并，使 `frag_ext` 虚高；分析前要先区分它。
- 碎片率是随工作负载时序变化的动态量，单次快照不足以定论。

### 5. 图文说明

```text
块表(按地址)  [used][F 8][used][F 16][used][F 8]
                       ↑ 三个空闲块
F = 32,  L = 16,  frag_ext = 1 - 16/32 = 0.5
请求 24 → 失败（无 ≥24 的连续块），F 却剩 32
```

### 6. 拓展知识

可以延伸到内存快照的可视化工具、interval 着色式内存规划、可扩展段对 `L` 的影响，以及把碎片指标接进训练/推理的监控与告警。

### 7. 常见追问及回答要点

- **为什么不用空闲总量判断？** 分配需要连续块，`F` 够不代表存在满足请求的 `L`。
- **碎片率多少算高？** 没有固定阈值，要和同一 workload 的历史曲线比，看它是否在攀升并伴随分配失败。
- **怎么降低内部碎片？** 用更细的 size class 或按实际尺寸分配，代价是查找变慢、簿记变多。

### 8. 易错点与反例

- 用空闲总量代替最大连续块下结论。
- 把缓存的空闲块当成碎片率的一部分而不先扣除 pending。
- 只看一次快照就断定碎片「恢复了」。

### 9. 实践与验证

实现一个脚本从快照计算 `L`、`F`、`frag_ext`、内部浪费并画时间曲线；然后对同一模型跑定长与变长输入，比较两者的碎片率曲线并解释差异。

### 10. 评分标准

- 合格：说出最大连续块与碎片率的关系。
- 良好：区分内部/外部碎片并给出计算方式。
- 优秀：用时间序列与失败裕度定量归因，并解释 pending 的干扰。

## I006. 多 stream 生产者/消费者如何用 event 正确编排？

- 难度：中等级
- 知识域：K03（异步执行与同步原语）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B008 event 语义、B007 同流顺序、双缓冲思想
- 关联题目：I007, B007, B008
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

计算流与拷贝流、或多条计算流之间常形成生产者-消费者关系：一条流产出数据，另一条流消费它，之后还要把 buffer 还回去给生产者覆写。event 是跨流建立这种先后关系的最小工具。

### 2. 问题分析

关键是把「数据就绪」和「buffer 可复用」两个依赖都表达出来。只建单向依赖会漏水：消费者可能读到半成品，或者生产者覆写了消费者还没读完的 buffer。需要一对 event（full/empty）加多 buffer 轮转。

### 3. 具体答案

以 N 个缓冲区（双缓冲即 N=2）的流水线为例：

1. 预分配 N 个 buffer，为每个 buffer 准备两个 event：`full[i]`（生产完成）、`empty[i]`（消费完成）。
2. 初始时把每个 buffer 的 `empty[i]` 标记为已触发，表示可被生产。
3. 生产者：在 producer stream 上 `wait(empty[i])` → 写入 buffer → `record(full[i])`。
4. 消费者：在 consumer stream 上 `wait(full[i])` → 读取 buffer → `record(empty[i])`。
5. 生产者下一轮选中同一个 buffer 时，第 3 步的 `wait(empty[i])` 会挡住，直到消费者用完，从而避免覆写。
6. 若还有第三方复用（如把 buffer 交回分配器），需在归还前确保所有相关流完成：用 event 同步或把 buffer 登记到所有使用它的 stream（record_stream 语义）。
7. host 若要读取最终结果，用一次同步拷贝或 `event synchronize` 收尾。

编程约束：同一 event 在被重新 record 前，要保证上一轮的 wait 已经被消费，否则新旧依赖会混叠。实践中用每 buffer 独立的 event 即可天然满足。

### 4. 技术洞察

- event 传递的是顺序，不搬数据；数据可见性由 happens-before 自动附带。
- 生产者-消费者的双向 event 构成一个基于流的事件信号量，是流式流水线正确重叠的基础。
- N 越大，重叠越充分但内存占用越高；N 的选择是吞吐与显存的权衡。
- 跨流共享 buffer 必须先建立依赖再使用，否则错误取决于调度时序，复现困难。

### 5. 图文说明

```text
producer: wait(empty[i]) → [write buf i] → record(full[i])
consumer:                    wait(full[i]) → [read buf i] → record(empty[i])
下一轮:   wait(empty[i]) ─────────────────────────────────┘（挡住覆写）
```

### 6. 拓展知识

可以延伸到多级流水线（prefill/拷贝/计算/后处理）、与 CUDA Graph 结合固化这套依赖、以及把 CPU 参与的流水线换成纯设备侧编排。

### 7. 常见追问及回答要点

- **为什么需要 empty event 而不只有 full？** 只建 full 只能防止消费者读早，不能防止生产者覆写消费者未读完的数据。
- **event 能复用吗？** 能，但要确保上一轮 wait 已消费；用每 buffer 独立 event 最安全。
- **buffer 数量怎么定？** 用 profiling 看重叠是否已经饱和，再取能满足带宽的最小 N，避免浪费显存。

### 8. 易错点与反例

- 只 record(full) 不 record(empty)，导致覆写竞态。
- 复用同一 event 覆盖尚未消费的依赖。
- 忘记把 buffer 登记到所有使用它的流，归还时被提前复用。

### 9. 实践与验证

搭一个 H2D 拷贝流 → 计算流的双缓冲流水线，用 event 串联，用 profiler 确认拷贝与计算在时间轴上重叠；再故意去掉 empty event，观察是否出现偶发数值错误。

### 10. 评分标准

- 合格：用 event 建起单向跨流依赖。
- 良好：补齐双向依赖与多 buffer 轮转。
- 优秀：讲清 event 复用的约束、buffer 数量权衡与归还时的流登记。

## I007. record/wait event 的常见接线错误有哪些？

- 难度：中等级
- 知识域：K03（异步执行与同步原语）
- 题型：故障排查
- 面试频率：中高
- 前置知识：I006 生产者-消费者、B008 event 语义
- 关联题目：I006, I008, B008
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

event 本身语义简单，但接线（在哪条流 record、在哪条流 wait、什么时候查询/复用）很容易出错。错误往往不立即报错，而是表现为偶发数值错误或 hang，排查成本高。

### 2. 问题分析

把错误归成三类：时序类（在 event 未触发时就用它）、拓扑类（依赖建在错误的流上）、生命周期类（event 或其保护的内存被过早释放/复用）。逐条对照即可覆盖大多数故障。

### 3. 具体答案

常见接线错误：

1. record 后立即查询耗时或状态：event 尚未触发，读到无效值或零值。必须先 synchronize 或确认触发。
2. wait 挂在错误的 stream 上：依赖建在了与数据无关的流上，被保护的 stream 仍然跑在依赖之前。
3. event 过早复用：同一 event 被重新 record，而前一次 wait 还没执行到，导致依赖丢失或错配到新一轮。
4. 缺少反向 event：只保护「读早」不保护「覆写」，生产者覆盖消费者未读完的 buffer。
5. 用 event 代替内存所有权管理：顺序建对了，但 host 侧提前释放（free）了被保护的 buffer。
6. 跨 context/进程复用 event 句柄：句柄在另一处无效，属于未定义行为。
7. 未带计时标志却查询 elapsed：不支持计时查询的 event 取耗时会报错或得到垃圾值。
8. 默认流混用：默认流的隐式同步语义让本该建立的依赖被隐藏，或把并发的流意外串起来。
9. 同流内顺序颠倒：先 wait 后 record 同一条 event，逻辑上自我等待，可能 hang。
10. 误把 event synchronize 当全局同步：它只等这一个 event，不等于所有流都完成。

### 4. 技术洞察

- 绝大多数 event bug 都能通过「把 record/wait 画成时间轴、标注所属 stream」定位。
- event 保护的是顺序，不是内存生命周期；两者要分开设计。
- 复用一个 event 是允许的，但语义是「覆盖」，因此每轮的关键依赖最好用独立 event 或确保消费完再覆盖。
- 计时 event 和不计时 event 往往需要不同标志位创建，混用是查询失败的常见原因。

### 5. 图文说明

```text
正确: S0 [write]→record(E)      S1 wait(E)→[read]
错误①: S0 [write]→record(E)     S1 (无 wait)→[read]      ← 漏接
错误②: S0 record(E)→record(E)   S1 wait(E)（只等到第二次） ← 覆盖
错误③: S0 record(E) 后立刻 query elapsed → 未触发，值无效
```

### 6. 拓展知识

可以延伸到 event 标志位（计时、阻塞同步）、跨进程共享 event、图捕获对 event 表达的固化，以及用 profiler 的依赖箭头做自动校验。

### 7. 常见追问及回答要点

- **event 会阻塞 host 吗？** record/wait 本身不阻塞，只有 event synchronize 才阻塞 host。
- **怎么快速定位漏接？** 在时间轴上画依赖箭头，任何跨流共享的数据都必须有一条 full 箭头，任何覆写都必须有一条 empty 箭头。
- **事件查询失败怎么排？** 先确认创建时是否带了计时标志，再看是否在触发前就查询。

### 8. 易错点与反例

- 只建一条依赖就以为安全。
- record 后立刻读耗时或释放资源。
- 跨 context 复用 event 句柄。

### 9. 实践与验证

构造一个带竞态的跨流读写，分别注入「漏接」「覆盖」「提前查询」三种错误，观察它们的表现（错误结果、异常值、偶发 hang），再加正确 event 验证修复。

### 10. 评分标准

- 合格：能列出几类常见错误。
- 良好：按时序/拓扑/生命周期归类并给出修法。
- 优秀：用时间轴与依赖箭头系统化排查，并区分 event 顺序与内存生命周期。

## I008. 进程关闭时的异步 teardown 怎么做才安全？

- 难度：中等级
- 知识域：K03（异步执行与同步原语）
- 题型：故障排查
- 面试频率：中高
- 前置知识：B003 异步语义、I002 stream 生命周期、析构顺序
- 关联题目：I007, I002, B003
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

正常运行时设备上总有 in-flight 操作，进程退出如果直接销毁 context 和内存，会让仍在执行或仍在等待设备的工作失去归属，表现为退出时崩溃、hang 或吞掉真正的异步错误。

### 2. 问题分析

teardown 的问题是「多线程/多对象在不确定顺序下析构」。要保证：先停止产生新工作，再让设备排空，然后按依赖逆序释放，并把异步错误显式取出而不是丢失。

### 3. 具体答案

安全的 teardown 顺序：

1. 关闭工作入口：停止接收/生成新请求，join 掉仍在提交工作的线程，确保没有新的 launch 进入。
2. 排空设备：对每条使用过的 stream synchronize，或做一次 device synchronize；对通信组调用 destroy，其内部通常也需要先同步。
3. 取出异步错误：在同步点检查 last_error，把设备侧错误显式记录/上报，避免退出时被静默丢弃。
4. 逆序释放对象：先释放流、event，再释放 tensor 与缓存；通信组、图、模块按创建逆序销毁。
5. 清空缓存/归还显存（可选）：进程退出会整体回收，但显式归还可避免与其它析构交叠。
6. 销毁 context；必要时做设备重置，保证下次启动干净。

要规避的陷阱：

- 全局/静态对象析构顺序不确定，可能出现 runtime 已卸载而 tensor 还在析构，触碰已失效的 runtime。
- Python 解释器关闭阶段仍可能触发 GC，从而调用设备 API，而底层 CUDA/MUSA runtime 可能已进入卸载流程。
- 子进程/多进程：子进程退出前要显式同步，否则父进程复用时子进程可能还在用同一设备或显存。
- 在信号处理函数里做 teardown 不安全，信号上下文只允许 async-signal-safe 操作，应改为设置标志、由主循环收尾。

### 4. 技术洞察

- 「先停生产、再排空、后释放」是把并发终止问题变成确定顺序问题的通用手法。
- 析构里绝不 launch 新工作，也不做会阻塞过久的同步，否则可能导致退出阶段的死锁。
- 给 teardown 设超时是工程必要项：正常排空应很快完成，超时说明有 hang，需记录并强制退出。
- 显式同步的价值不只是防崩溃，还能把此前被推迟的异步错误暴露出来。

### 5. 图文说明

```text
停入口 ─▶ join 线程 ─▶ 各流/设备 synchronize ─▶ 取出异步错误
        ─▶ 逆序释放: 流/event → tensor/缓存 → comm/图 → context
        ─▶（超时未完成）记录 + 强制退出
```

### 6. 拓展知识

可以延伸到 atexit 与析构钩子、Python GC 在解释器关闭时的行为、多进程共享 context 的清理，以及看门狗进程监控退出 hang。

### 7. 常见追问及回答要点

- **为什么不能直接 exit？** in-flight 操作未排空，销毁顺序不可控，会导致崩溃或错误丢失。
- **析构里能同步吗？** 尽量不在析构里做长同步，集中在一个显式的 shutdown 流程中完成更好。
- **信号里怎么处理退出？** 只设置原子标志，由主循环检测后走标准 teardown，不在信号上下文调用设备 API。

### 8. 易错点与反例

- 依赖析构函数自动收尾，结果因顺序不定而崩溃。
- 退出时不做同步，吞掉了设备侧的真实错误。
- 在信号处理函数里直接释放设备资源。

### 9. 实践与验证

写一个提交长 kernel 后立即退出的程序，去掉同步观察崩溃/hang，再用「停入口→同步→释放」的 shutdown 验证稳定退出；再加一个会报错的异步操作，确认错误能被取出。

### 10. 评分标准

- 合格：说出先同步再释放。
- 良好：给出完整逆序流程并指出析构顺序陷阱。
- 优秀：覆盖多进程、信号上下文与超时兜底，并强调异步错误的显式取出。

## I009. MindSpore 从 Python 到 device 的执行抽象边界在哪里？

- 难度：中等级
- 知识域：K04（张量与图执行）
- 题型：流程追踪
- 面试频率：中高
- 前置知识：B011 eager/graph、图编译、后端适配
- 关联题目：I010, B011
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

MindSpore 这类框架从 Python 前端到设备执行，中间隔着图编译、执行引擎、设备适配几层。不同模式（逐算子执行与图模式）走的路径不同，抽象边界也不同。理清边界，才能解释「哪一层的错误对应哪一层的语义」。

### 2. 问题分析

要沿着「前端 → 图/算子 → 执行引擎 → 设备适配 → 驱动/硬件」逐段找出边界：每一段对上提供什么抽象、对下依赖什么接口。重点是识别「进入图」和「进入设备」两个关键切换点。

### 3. 具体答案

按层追踪：

1. Python 前端（Tensor 操作、nn.Cell）：表达计算。它决定当前处于逐算子执行还是图构建。
2. 构图/编译：在图模式下，前端表达被 lowering 成中间表示（如 MindIR），做算子选择、图算融合、内存规划，产出执行计划；逐算子模式下跳过这一步，算子直接进执行引擎。
3. 执行引擎（runtime）：把算子或执行计划分派到后端，管理内存、流与执行顺序，负责异步提交与同步。
4. 设备适配/插件：把执行引擎的算子映射到具体厂商的运行时接口（如 Ascend 的 ACL、CUDA 的 runtime、MUSA 的 runtime）。这里是屏蔽硬件差异的边界。
5. 驱动与硬件：真正下发与执行，完成信号经驱动回传。

抽象边界小结：

- 第一边界在「是否进入图」：逐算子模式下 Python 与执行引擎之间是逐调用边界；图模式下 Python 只负责构图，边界落在编译产物的执行计划上。
- 第二边界在「执行引擎→设备适配」：算子通过注册的 device 后端实现接入，是「统一算子语义」与「厂商运行时」的分界。
- 第三边界在「设备适配→驱动」：句柄、地址、命令提交的硬件边界。

与 PyTorch 对照：PyTorch 的分派层对应 MindSpore 的算子分派，但 MindSpore 图编译更重、内存规划更多发生在编译期。

### 4. 技术洞察

- 图模式把内存规划和调度提前到编译期，逐算子模式把这两件事推到最后执行时，两者的错误特征不同。
- 设备适配层是「可插拔后端」的落点：新增硬件主要在这一层注册算子实现。
- 图模式与逐算子模式可以混合，理解边界有助于判断「这个报错是构图问题还是执行问题」。

### 5. 图文说明

```text
Python 前端 ──(进入图?)──▶ 构图/编译(MindIR,融合,内存规划)
      │逐算子                    │执行计划
      └──────────┬──────────────┘
                 ▼
          执行引擎(runtime 内存/流/调度)
                 ▼
          设备适配/插件(ACL / CUDA / MUSA runtime)
                 ▼
          驱动 + Device
```

### 6. 拓展知识

可以延伸到 MindIR 与算子注册机制、图算融合与内存复用策略、动态 shape 下的编译与重编译、以及跨后端精度一致性的验证方法。

### 7. 常见追问及回答要点

- **边界为什么重要？** 报错落点不同意味着排查手段不同：构图期看 IR，执行期看流与内存，设备期看驱动日志。
- **逐算子模式还需要编译吗？** 需要算子级的分派与内核选择，但没有整图规划那一步。
- **怎么新增一种硬件后端？** 主要在设备适配层注册算子与内存/流管理，复用上层执行引擎。

### 8. 易错点与反例

- 把图编译错误和执行错误混为一谈。
- 认为 Python 层能直接控制设备执行顺序（实际经执行引擎与流）。
- 忽略设备适配层，误以为上层算子直接对应硬件指令。

### 9. 实践与验证

同一段模型分别用逐算子模式和图模式运行，打印各阶段耗时与内存指标，比较两种路径在内存规划与执行开销上的差异；在设备适配层打点确认算子下发的落点。

### 10. 评分标准

- 合格：说出从 Python 到 device 的主要层次。
- 良好：指出「进入图」与「进入设备」两个边界。
- 优秀：能按边界对报错做归因，并说明可插拔后端的接入方式。

## I010. 图模型与动态图在内存规划和执行器上有哪些实现差异？

- 难度：中等级
- 知识域：K04（张量与图执行）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B011 两种执行流程、I009 抽象边界、张量生命周期
- 关联题目：I009, I013
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

动态图逐算子即时执行，静态图先把一段计算编译成计划再整体执行。这个差别直接决定了两者在「什么时候分配内存」「中间张量怎么复用」「峰值能不能预测」上的实现路径。

### 2. 问题分析

从执行器结构和内存规划两条线对比：执行器关注分派开销与调度方式，内存规划关注张量 live range、复用算法与峰值可预测性。再补上二者混合的工程做法。

### 3. 具体答案

执行器差异：

- 动态图：解释执行，每个算子即时经分派层选择内核并提交，host 参与每一次 launch；支持任意动态控制流，调试直观，但固定开销（分派、launch、解释）每步都付。
- 静态图：编译成执行计划，按拓扑序执行，host 只在必要处介入；可做算子融合、重排、通信与计算重叠，固定开销摊薄，但动态 shape/控制流需要特判或重编译。

内存规划差异：

- 动态图：每算子即时向缓存分配器申请，靠引用计数决定何时 free；中间张量存活时间不可静态预知，峰值事后才知，主要靠池复用降低碎片。
- 静态图：编译期分析每个张量的 live interval（从生产到最后一个消费者），把区间不重叠的张量映射到可复用的 buffer，常采用一块 arena 按偏移切分；峰值可在编译期算出。
- 静态图可做 in-place 优化（输入输出复用同一块）与内存重计算（用计算换显存，如梯度检查点）。

对比要点：

| 维度 | 动态图 | 静态图 |
| --- | --- | --- |
| 分派开销 | 每算子 | 编译期摊薄 |
| 分配时机 | 运行时逐次 | 编译期规划 + 运行时复用 |
| 峰值可预测 | 否 | 是 |
| 动态控制流 | 天然支持 | 需特判/重编译 |
| 调试性 | 好 | 差 |

混合做法：动态图捕获成图（torch.compile / MindSpore jit），用一次 trace 换取后续重放的规划与融合收益。

### 4. 技术洞察

- 内存规划本质是一个带时间维度的分配问题：把「同时活着的张量不能共享地址」转成区间不重叠即可复用。
- 静态图峰值可预测，使容量规划与 batch 选择更有依据；动态图只能靠实测峰值加余量。
- 复用地址对图捕获是利好（地址稳定），但也带来约束：一旦运行期改变了本该固定的地址假设就会出错。
- 重计算是用额外计算换显存，和内存规划一起决定峰值。

### 5. 图文说明

```text
动态图: op1→alloc→launch → op2→alloc→launch ...   (逐次, 峰值事后知)
静态图: 编译期: 分析 live interval
        arena: | a0 | a1 | a0复用 | a2 ... |
        运行期: 按偏移复用同一块      (峰值编译期知)
```

### 6. 拓展知识

可以延伸到图算融合、内存重计算策略、可扩展段与 arena 分片、动态 shape 的重编译阈值，以及编译器如何自动做内存规划和调度。

### 7. 常见追问及回答要点

- **静态图一定更省显存吗？** 通常峰值更低且可预测，但若规划不当（如过度保守不复用）也可能不省。
- **动态图怎么降峰值？** 及时释放不再引用的中间量、用重计算、控制 batch，让池复用生效。
- **混合模式风险是什么？** 捕获时的地址/控制流假设在重放时被破坏，需要处理重捕获或 guard。

### 8. 易错点与反例

- 认为静态图不需要运行时分配器（仍需要，只是分配被规划驱动）。
- 用动态图峰值反推静态图容量而无视规划差异。
- 在捕获区内做动态控制流或非法同步。

### 9. 实践与验证

把同一模型分别用动态图与静态图（或编译模式）运行，打印峰值显存与每步 host 时间，对比分派开销与峰值的差异；再打开重计算观察显存与时间的此消彼长。

### 10. 评分标准

- 合格：说出两者在执行器与内存分配上的基本差别。
- 良好：用 live interval 与 arena 复用解释峰值可预测性。
- 优秀：讲清重计算、in-place 与混合模式引入的约束和风险。

## I011. Ring AllReduce 与 Tree AllReduce 的执行过程与适用场景？

- 难度：中等级
- 知识域：K05（集合通信）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B012 AllReduce 语义、通信量模型、拓扑
- 关联题目：I012, I015, B012
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

AllReduce 让所有 rank 拿到相同的归约结果。实现它有两类典型拓扑：环（ring）与树（tree）。二者在步数、每步消息大小、对带宽与延迟的敏感度上截然不同，实际库会按消息规模自动切换。

### 2. 问题分析

要分别描述两种算法的执行步骤，比较通信量与步数随 N 的变化，再据此给出「大消息用环、小消息用树」的选型依据，并说明哪些因素会改变这个结论。

### 3. 具体答案

Ring AllReduce（两阶段）：

1. 把每个 rank 的数据切成 N 份。
2. reduce-scatter 阶段：共 N−1 步，每步每个 rank 把一块发给下游、从上游收一块并累加，循环推进，使每个 rank 得到其中一份的完整归约。
3. all-gather 阶段：再 N−1 步，每步转发已归约好的块，直到所有 rank 拼齐全部 N 份。
4. 每 rank 通信量约为 `2(N−1)/N × 数据量`，趋近于 2 倍数据量，与 N 基本无关，带宽利用最优。
5. 步数随 N 线性增长，启动与握手延迟在大 N 下累积，小消息不友好。

Tree AllReduce（归约 + 广播）：

1. 归约阶段：数据沿树向上汇聚，各节点两两归约，最终根节点得到总和。
2. 广播阶段：结果沿树向下分发到所有节点。
3. 步数约 `2 log N`，延迟低。
4. 通信不是全网均衡：靠近根的链路负载更重，总通信量/带宽利用不如环。

适用场景：

- 环：大消息、带宽受限、N 较大（如梯度张量大、数据并行规模大）。
- 树：小消息、延迟敏感、N 大（如频繁的小 AllReduce、同步开销占比高）。
- 实际选择：按消息大小设阈值自动切换；同时受物理拓扑影响（NVLink 内可先做子环，再跨节点树/环组合）。

### 4. 技术洞察

- 环把通信量摊平到所有链路，追求带宽上限；树把步数压到对数级，追求延迟下限，二者的优化目标不同。
- 大 N 时环步数多的代价显现，因此大消息仍用环、小消息转树。
- 拓扑分层（节点内 NVLink + 节点间网络）常把两种算法级联，节点内用环、节点间用树。
- 通信与计算重叠时，环的稳定带宽更易预测重叠收益。

### 5. 图文说明

```text
Ring (N=4, 数据切 4 份):
  reduce-scatter: r0→r1→r2→r3→r0 ... (N-1 步, 每步归约一块)
  all-gather    : 归约块再转一圈 (N-1 步)
Tree:
  归约:   叶子 ─▶ 父 ─▶ 根 (log N 步)
  广播:   根 ─▶ 子 ─▶ 叶 (log N 步)
```

### 6. 拓展知识

可以延伸到 halving-doubling、NCCL 的算法自动选择与拓扑探测、分层 AllReduce，以及 AllReduce 与 ReduceScatter+AllGather 的等价在参数分片中的应用。

### 7. 常见追问及回答要点

- **为什么大消息选环？** 环每 rank 通信量趋近常数倍，带宽利用率高，大消息下带宽是瓶颈。
- **为什么小消息选树？** 树步数呈对数，启动延迟低，小消息下延迟是瓶颈。
- **阈值固定吗？** 不固定，随拓扑、硬件带宽、消息形状变化，需按实测或库的拓扑感知结果决定。

### 8. 易错点与反例

- 认为所有规模都用一种算法。
- 忽略拓扑分层，只按消息大小选型。
- 混淆「步数」与「通信量」，用错指标衡量优劣。

### 9. 实践与验证

在不同消息大小下测 AllReduce 时间随 N 的变化，观察曲线在大消息与小消息区间的不同斜率；再对比强制 ring 与 tree 的实现，验证切换阈值的存在。

### 10. 评分标准

- 合格：说清两种算法的基本结构。
- 良好：用通信量与步数解释各自适用范围。
- 优秀：结合拓扑分层与自动选型讲清级联与切换依据。

## I012. 通信 buffer 的生命周期如何管理，避免未完成通信时被复用？

- 难度：中等级
- 知识域：K05（集合通信）
- 题型：故障排查
- 面试频率：中高
- 前置知识：I011 通信算法、B009 异步释放、record_stream 语义
- 关联题目：I011, I015, B009
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

集合通信也是异步的：调用返回只代表命令已入队。send/recv buffer 在通信真正完成前既不能被修改（send 侧）也不能被读取/覆写（recv 侧）。生命周期管理稍有不慎，就会出现数值错乱或 hang。

### 2. 问题分析

要覆盖三段时间：通信入队到完成之间 buffer 不能被改动；复用时新旧通信不能踩同一块；释放时不能有 in-flight 通信仍引用它。还要处理通信与计算重叠带来的跨流复用问题。

### 3. 具体答案

生命周期规则与做法：

1. send buffer：在对应通信完成前保持只读，禁止写入或覆写；recv buffer：在完成前不可读取，也不可被别的写操作占用。
2. 把通信登记到一条通信流上；用 event 或通信完成查询建立「通信完成→复用」的顺序。
3. 多 buffer 轮转：为重叠准备多份 buffer，每份配一个完成 event；下一轮复用它前先 wait 它的完成 event，避免新旧通信冲突。
4. 释放前排空：释放任何 buffer 前确保所有引用它的通信已完成（synchronize 通信流或等完成 event 触发）。
5. 跨流登记：当 buffer 同时被计算流和通信流使用，要把它登记到所有相关流（record_stream 语义），否则分配器只等其中一条流就复用，会踩到另一条。
6. 与反向计算重叠：梯度 buffer 要等 AllReduce 完成才能被下一步骤覆盖，重叠时的复用点必须挂在通信完成之后。
7. in-place AllReduce：某些实现允许原地归约、无独立输出 buffer，需知悉语义，不要假设存在可单独释放的输出。

常见故障对照：

- 异步入队后立刻读 recv buffer → 读到旧值/半成品。
- free 掉被 in-flight 通信引用的 tensor → 地址被复用，通信写坏数据。
- 只登记计算流未登记通信流 → 分配器提前复用，偶发数值错乱。
- 复用前不等完成 event → 两轮通信写同一块，结果不可预测。

### 4. 技术洞察

- 集合通信的「完成」必须用通信流上的完成信号确认，不能用 host 侧调用返回代替。
- 跨流复用的正确性依赖分配器知道全部使用流；漏登记一个就失去保护。
- 重叠越多，buffer 轮转与 event 编排越复杂，是通信正确性 bug 的高发区。
- 用多 buffer + 完成 event 把「异步完成」显式化，是把不确定时序变成确定顺序的关键。

### 5. 图文说明

```text
comm stream: [AllReduce(send,recv)]→record(E)
compute:                        wait(E)→[复用 recv]
释放前:   wait(E) 或 comm.synchronize → 再 free
漏登记:   buf 只用 compute 流登记, comm 流未登记 → 提前复用 → 错乱
```

### 6. 拓展知识

可以延伸到通信与计算重叠的调度、梯度累积中的 buffer 复用、NCCL 的 group 与 stream 语义，以及用内存快照定位跨流未登记的 buffer。

### 7. 常见追问及回答要点

- **通信返回后能用 recv 结果吗？** 不能，必须等通信完成信号，返回只是入队。
- **怎么保证跨流复用安全？** 把 buffer 登记到所有使用它的流，并在复用前等完成 event。
- **重叠会不会破坏正确性？** 不会，只要复用点严格挂在完成 event 之后；错误来自漏掉这个依赖。

### 8. 易错点与反例

- 把通信入队当成完成，立即读取结果。
- 释放被 in-flight 通信引用的 tensor。
- 跨流使用但只登记部分流。

### 9. 实践与验证

构造一个多 buffer 重叠的 AllReduce 流水线，故意在完成前复用 recv buffer，观察数值错误；再补上完成 event 与跨流登记，验证稳定正确，并用快照确认流信息完整。

### 10. 评分标准

- 合格：指出通信未完成不能复用。
- 良好：给出完成 event、多 buffer 轮转与释放前排空的做法。
- 优秀：讲清跨流登记、重叠复用点与 in-place 语义的影响。

## I013. 单个请求的 KV cache 占用如何计算？

- 难度：中等级
- 知识域：K06（LLM 推理与 KV Cache）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B013 prefill/decode、注意力机制、张量并行与 GQA
- 关联题目：I014, B013
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

自回归解码需要缓存每层注意力的 Key 和 Value，避免重复计算历史。KV cache 随序列长度线性增长，是长上下文推理显存的主要开销，也是并发请求容量的决定因素。

### 2. 问题分析

先给出每个 token 的 KV 字节公式，再乘上序列长度得到单请求占用；然后考虑张量并行、GQA/MQA、量化、分页粒度等修正项，最后落到容量规划：显存预算除以单请求峰值即最大并发数。

### 3. 具体答案

每 token 的 KV 字节数：

```
per_token = 2 (K,V) × L (层数) × H_kv (KV 头数)
          × D (每头维度) × b (每元素字节)
```

- `2`：Key 和 Value 各存一份。
- `L`：Transformer 层数。
- `H_kv`：KV 头数；采用 GQA/MQA 时小于 query 头数，直接按比例降低占用。
- `D`：每个头的维度。
- `b`：元素字节数，fp16 为 2、fp8/int8 为 1。

单请求占用：

```
request_bytes = per_token × seq_len
seq_len 峰值 = prompt_len + max_new_tokens
```

张量并行修正：按 KV 头切分时，每张卡只存 `1/TP`，即每卡 `per_token / TP`（注意切分不总是整除，需按各卡实际头数计算）。

示例计算（数值仅用于演示公式，非实测）：取 `L=32, H_kv=8, D=128, b=2`，则

```
per_token = 2 × 32 × 8 × 128 × 2 = 131072 B = 128 KiB
4096 token → 128 KiB × 4096 = 512 MiB
```

分页缓存：按固定 block（如每块若干 token）分配，占用按块取整：

```
blocks = ceil(seq_len / block_size)
kv_bytes = blocks × block_size × per_token
```

容量规划：`最大并发请求数 ≈ (显存 − 权重 − 激活峰值 − 预留) / 单请求 KV 峰值`。

### 4. 技术洞察

- KV 随序列长度线性增长，长上下文场景下往往超过权重本身，是显存规划的第一约束。
- GQA/MQA 通过减少 `H_kv` 直接成倍降低 KV，是最有效的结构性优化。
- KV 量化把 `b` 从 2 降到 1，占用减半，但要在精度与带宽之间权衡。
- 分页粒度带来取整浪费，block 越小越省但元数据开销越大。
- 张量并行只切分 KV 头，不减少总核算量，每卡占用约为总量的 `1/TP`。

### 5. 图文说明

```text
每 token: K[L,H_kv,D] + V[L,H_kv,D]  →  2·L·H_kv·D·b 字节
单请求:   per_token × (prompt + generated)
分页:     ceil(seq/block) × block × per_token
并发上限 ≈ (总显存 − 权重 − 激活 − 预留) / 单请求峰值
```

### 6. 拓展知识

可以延伸到 PagedAttention 的块表与共享前缀、prefix caching 复用公共前缀的 KV、滑窗注意力对有效长度的限制，以及投机解码对 KV 的额外占用。

### 7. 常见追问及回答要点

- **为什么用 GQA 能省很多？** 它让多个 query 头共享一份 KV，`H_kv` 成倍下降，占用同比例减少。
- **张量并行后每卡怎么算？** 按该卡实际分到的 KV 头数与层数计算，通常约为总量的 1/TP。
- **分页会浪费吗？** 会，最后一块可能只填了几个 token，浪费与 block 大小成正比。

### 8. 易错点与反例

- 忘记乘 2（K 和 V 两份）。
- 用 query 头数代替 KV 头数，忽略 GQA/MQA。
- 只用 prompt 长度估算，漏掉生成长度，低估峰值。

### 9. 实践与验证

对给定模型参数用公式算出每 token 占用，再与实际运行时每请求显存增量对比校验；改变 GQA 配置与 dtype，验证占用按预期成比例变化。

### 10. 评分标准

- 合格：写出每 token 的 KV 公式。
- 良好：补上序列长度、张量并行与分页粒度。
- 优秀：用公式做容量规划，并解释 GQA/量化/分页的取舍。

## I014. continuous batching 下调度器如何决定一个 batch 的组成？

- 难度：中等级
- 知识域：K06（LLM 推理与 KV Cache）
- 题型：实现设计
- 面试频率：高频
- 前置知识：I013 KV 计算、B013/B014 prefill/decode 与队列、chunked prefill
- 关联题目：I013, B014
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

传统批处理要等一个 batch 全部结束才能开下一个，利用率低。continuous batching 在每次迭代重新组装 batch，让已就绪的请求立即加入、已完成的请求立即退出。调度器每步要回答：这一步放哪些请求、prefill 和 decode 各占多少。

### 2. 问题分析

调度的输入是两队列（等待、运行）、每请求的元数据（长度、优先级、deadline）和两类资源预算（token 预算、KV 预算）。目标是在不超预算的前提下最大化吞吐并满足延迟 SLO。需要把「凑 batch」拆成一个每步执行的确定性流程。

### 3. 具体答案

每步调度流程：

1. 回收：移除已完成（命中 stop）或超时/被取消的请求，释放它们的 KV block。
2. 续算 decode：为仍在运行的请求预留本步的 1 个 token 的 KV，纳入候选。
3. 计算剩余预算：`剩余 token 预算 = 每步 token 上限 − 已占用`；`剩余 KV = 可用 block 数`。
4. 决定是否加入新 prefill：只有当 prefill 的 token 数与 KV 需求落在剩余预算内才可加入；否则让它在等待队列里等，或用 chunked prefill 分块插入。
5. 选择顺序：按调度策略（FCFS、优先级、SJF 等）从等待队列取请求，逐个判断能否容纳。
6. 组装 batch：把选中的 decode（每个 1 token）与 prefill（各自 prompt/chunk 长度）拼成一个混合 batch，总 token 数不超预算。
7. 资源不足时抢占：从运行队列中挑低优先级/超期的请求换出（swap 到 CPU 或 recompute 丢弃 KV），腾出 KV 给更高优先级的请求。
8. 提交本步 batch，等待完成后进入下一步。

关键约束：

- token 预算：单步处理的 token 总量上限，用来平衡 prefill 与 decode 的算力分配，避免长 prefill 独占导致 decode 停顿。
- KV 预算：可用 block 数量，直接限制并发请求数与序列长度。
- 内存水位：接近阈值时倾向拒绝新请求或换出。

### 4. 技术洞察

- continuous batching 的核心是「batch 成员每步可变」，让 GPU 在请求的整个生命周期内持续被填满。
- prefill 与 decode 混排是吞吐与延迟的调节旋钮：多放 prefill 降 TTFT 但抬高 decode 的 TPOT，反之亦然。
- chunked prefill 把长 prompt 切块，避免它一次性占满 token 预算而卡住正在 decode 的请求。
- 抢占是保证 SLO 与公平性的兜底，代价是 recompute 的重复计算或 swap 的传输开销。
- KV 预算是硬约束：再好的调度也无法在 block 用尽时再多塞一个请求。

### 5. 图文说明

```text
每步:
  回收完成/超时请求(释放 KV)
    → 运行请求各留 1 token KV
    → 计算剩余 token/KV 预算
    → 按策略从等待队列取请求
    → 组装 decode(1 token) + prefill(chunk) 混合 batch
    → (不足) 抢占低优先级 → swap/recompute
    → 提交执行
```

### 6. 拓展知识

可以延伸到调度公平性与饥饿、优先级与 SLA 隔离、prefill/decode 分离部署、投机解码与 batch 的交互，以及用排队论分析 token 预算对延迟的影响。

### 7. 常见追问及回答要点

- **为什么不能等 batch 满了再跑？** 会浪费设备空闲时间，短请求也要陪跑；continuous batching 让请求随到随走。
- **长 prompt 怎么不阻塞其他请求？** 用 chunked prefill 分块处理，把长 prefill 拆散到多步。
- **KV 不够时怎么办？** 先抢占低优先级请求（swap/recompute），再不行就拒绝或排队新请求。

### 8. 易错点与反例

- 把 continuous batching 当成固定 batch 大小。
- 不加 token 预算，长 prefill 独占导致 decode 尾延迟飙升。
- 抢占后忘记真正释放或重算 KV。

### 9. 实践与验证

固定请求流，改变 token 预算与调度策略，测量吞吐、TTFT 与 TPOT 的变化，观察 prefill 占比对延迟的影响；再开启 chunked prefill 验证长 prompt 下 decode 延迟的改善。

### 10. 评分标准

- 合格：说明每步动态组装 batch 的思路。
- 良好：讲清 token/KV 预算与 prefill/decode 混排。
- 优秀：把 chunked prefill、抢占策略与 SLO 权衡纳入完整调度设计。

## I015. NUMA、NIC、CPU affinity 如何一起影响通信性能？

- 难度：中等级
- 知识域：K07（服务端调度与稳定性）
- 题型：实现设计
- 面试频率：中高
- 前置知识：B012 集合通信、I011 通信算法、服务器拓扑
- 关联题目：I012, I011
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

多路服务器里，GPU 和网卡各自挂在某个 CPU socket（NUMA node）下。跨 socket 的访存与传输要经过片间互联，延迟更高、带宽更低。通信线程若被调度到远端 core，或者数据放在远端内存，都会让通信性能明显退化。

### 2. 问题分析

要理清三者的耦合：GPU-NIC 的物理亲和决定数据路径的长短，CPU affinity 决定通信线程跑在哪个 node，NUMA 内存放置决定 staging buffer 的本地性。设计的目标是让「算数据的那颗 GPU、发数据的 NIC、跑通信的 core、放 buffer 的内存」尽量落在同一个 node。

### 3. 具体答案

关键设计点：

1. GPU-NIC 亲和：把用于通信的 NIC 选在目标 GPU 同一 PCIe root complex / NUMA node 上，走最短数据路径；跨 socket 会增加一次片间 hop。
2. CPU affinity：把通信相关的线程（如 NCCL 的 proxy 线程、通信库的进度线程）绑定到该 node 的物理核，减少跨 node 迁移与缓存失效。
3. 内存本地性：host staging buffer 用 pinned 内存并分配在本地 node，避免远端内存访问；GPU 与 NIC 间的 GPUDirect/RDMA 能绕开 host 时收益更大。
4. GPU 绑定：进程绑定到指定 GPU，避免误用远端 GPU 使通信走跨 socket 路径。
5. 拓扑感知：通信库会读拓扑选择 NVLink/PCIe/IB 路径与通道数，并据此选算法；拓扑错配会退化到跨 socket 或低带宽链路。

配置手段：

- 用 `numactl`/`taskset` 设置 CPU affinity 与内存节点。
- 用工具查看 GPU-NIC-CPU 拓扑（如 `nvidia-smi topo -m`）。
- 设置通信库的拓扑/通道相关环境变量，确保 GPU-NIC 配对正确。

观测与验证：对比绑定前后同一集合通信的延迟与带宽，查看是否有跨 socket 流量；用 NUMA 工具确认内存分布。

### 4. 技术洞察

- 通信性能瓶颈常在「路径」而非「算法」：算法相同，拓扑绑定不同可以差出可观幅度。
- 跨 socket 的代价同时体现在延迟和带宽上，且在多卡集合通信中会被放大（每一跳都经过）。
- pinned + 本地 node 是 host 参与传输时降低延迟的基础；能走 RDMA/GPUDirect 时应尽量绕开 host。
- 拓扑是动态可探测的，好的部署脚本会按机器实际拓扑自动配对，而不是写死。

### 5. 图文说明

```text
Socket0                          Socket1
 ├─ CPU core ─通信线程            ├─ CPU core
 ├─ 本地内存 ─staging buffer      ├─ 远端内存 (跨 UPI)
 ├─ GPU0 ─┐                       ├─ GPU1
 └─ NIC0 ─┘ 同 node: 短路径       └─ NIC1
跨 socket: GPU0 → ... → NIC1 走 UPI，延迟↑带宽↓
```

### 6. 拓展知识

可以延伸到 GPUDirect RDMA、NCCL 拓扑探测与环境变量调优、多 rail 网络、PCIe 与 NVLink 的带宽差异，以及容器环境下 NUMA 的透传。

### 7. 常见追问及回答要点

- **为什么绑核能提速？** 通信线程留在本地 node，避免跨 socket 迁移和远端访存，降低每次通信的固定开销。
- **GPU 和 NIC 不同 node 会怎样？** 数据要跨片间互联，延迟升高带宽下降，多卡通信时被逐跳放大。
- **怎么自动配对？** 读机器拓扑，按 NUMA node 把 GPU、NIC、core、内存分组，部署时按组绑定。

### 8. 易错点与反例

- 只调通信算法，不管拓扑绑定。
- 把 staging buffer 分配在远端 node。
- 忽视 GPU-NIC 配对，让大流量跨 socket。

### 9. 实践与验证

在同一集合通信用例上对比「默认调度」与「numactl 绑定到同 node」的延迟/带宽，并用拓扑工具与 NUMA 工具确认流量与内存的分布变化。

### 10. 评分标准

- 合格：说出 NUMA 与 affinity 会影响通信。
- 良好：把 GPU-NIC-core-内存四者按 node 对齐。
- 优秀：用拓扑工具与带宽测试量化绑定收益，并说明自动配对与 RDMA 路径。

## I016. 如何把端到端延迟拆成排队/提交/传输/计算/同步？

- 难度：中等级
- 知识域：K08（性能测量与可观测性）
- 题型：实现设计
- 面试频率：高频
- 前置知识：B016 粒度口径、B017 可观测性、异步流水
- 关联题目：I017, B016
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

端到端延迟是一个复合量，笼统测一个数无法指导优化。要把它拆成排队、预处理/提交、传输、计算、同步、后处理等可测量的段，逐段归因，才能知道优化点落在哪。异步流水让 host 时间与 device 时间可能重叠，拆分时要尤其小心对齐。

### 2. 问题分析

设计包含三部分：定义清楚每段的边界与含项，确定用什么时钟与手段测量，以及如何处理重叠与打点开销。难点在 host/device 时间不同轴，直接相减会得出错误结论。

### 3. 具体答案

分段定义：

- 排队：请求入队到被调度选中，用入队时间戳与开始处理时间戳之差衡量。
- 预处理/提交：host 侧 tokenize/构造输入、launch 提交的耗时，用 host 时间戳测量。
- 传输：H2D/D2H 拷贝以及网络/通信传输，用拷贝 event 或传输起止时间戳测量。
- 计算：设备上的 kernel 执行（prefill/decode 各段），用设备 event 或 profiler。
- 同步：synchronize/join 的等待时间，即等待此前所有操作完成的空档。
- 后处理：detokenize、组装响应、返回。

测量方法：

1. 在每段边界打点，host 用单调时钟（如 CLOCK_MONOTONIC），设备用 event 计时。
2. 用 profiler 的 trace 把 host 轴与 device 轴对齐，区分「提交耗时」与「执行耗时」。
3. 计算设备忙碌时间与墙钟时间之差，差值即气泡（排队、同步、等待）。
4. 把各段画成堆叠图，找主导项；若同步/排队占大头，优化 kernel 意义不大。

重叠处理：异步流水下，host 的提交时间与 device 的执行时间可重叠。不能简单把 host 各段相加，要按时间轴看真实占用；用 trace 上的重叠区域判断哪些开销被掩盖。

打点开销：高频打点会扰动测量，采用采样、聚合或粗粒度分段，并区分「测量开销」与「被测延迟」。

### 4. 技术洞察

- 端到端延迟由最长关键路径决定，而非各段之和；重叠段应从关键路径中剔除。
- 同步时间常被忽略，却是很多系统的隐藏大头——它把并行流水串行化。
- 排队延迟对到达率高度敏感，过载时它会主导端到端，此时优化计算收效甚微。
- host/device 时间轴必须对齐，否则会把「提交慢」误判成「执行慢」。

### 5. 图文说明

```text
端到端: |排队|提交|--传输--|--计算--|同步| 后处理
host 轴:   |--|------|                      |----|
device 轴:        |--H2D--|--kernel--|--D2H--|
关键路径: 排队 + max(提交, 传输后段) + 计算 + 同步 + 后处理（按重叠修正）
```

### 6. 拓展知识

可以延伸到分布式 tracing、请求级 span 打点、带宽与算力利用率指标、以及把分段延迟接进监控做分位数告警。

### 7. 常见追问及回答要点

- **为什么不能把各段直接相加？** 存在重叠，关键路径由最长链决定，相加会高估。
- **同步时间怎么测？** 用同步调用前后的墙钟差，配合设备忙碌时间反推等待量。
- **打点会影响结果吗？** 会，需采样或粗粒度，并把测量开销与真实延迟分开。

### 8. 易错点与反例

- 用 host 时间戳近似设备执行时间。
- 忽略排队与同步，把端到端当成 kernel 时间之和。
- 打点过密，测量本身成了瓶颈。

### 9. 实践与验证

在一个推理服务上按上述分段打点并抓 trace，画出分段堆叠图，验证各段之和与实测端到端的关系；再改变到达率，观察排队段的增长是否主导端到端。

### 10. 评分标准

- 合格：给出各段的定义与测量方式。
- 良好：处理 host/device 对齐与重叠，识别关键路径。
- 优秀：用分段与忙碌时间差把气泡定位到具体段，并控制打点开销。

## I017. 如何设计一个可复现的性能对比实验来验证优化？

- 难度：中等级
- 知识域：K08（性能测量与可观测性）
- 题型：实现设计
- 面试频率：高频
- 前置知识：I016 延迟拆分、B015 基线与 oracle、控制变量
- 关联题目：I016, B015
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

一次优化是否真的带来提升，需要可信的对比。跑一次、看一个数就下结论，很容易把噪声、环境漂移或缓存效应当成收益。可复现的对比要把变量、环境、输入、测量方法全部固定并记录。

### 2. 问题分析

设计围绕「固定、可重复、有门禁」三点：固定除被测点外的所有因素，用多轮统计降低噪声，用正确性门禁保证等价，并让整套流程脚本化可重跑。

### 3. 具体答案

实验要素：

1. 明确变量：只改一个优化点，其余保持默认不变；把改动点写成可关闭的开关，便于 A/B。
2. 固定环境：同硬件、同驱动、同库版本、同拓扑绑定；锁频避免动态调频干扰；隔离其它进程占用。
3. 固定输入：同数据、同随机种子、同 shape/batch、同 warmup 次数，排除首次编译与分配开销。
4. 正确性门禁：改动前后对独立参考（oracle，如 CPU 参考实现或高精度库）比对，落在容差内才比较性能。
5. 测量方法：多轮 warmup + 多轮计时，报告中位数与 P50/P99，并给出方差；交替运行 A/B/A/B 降低时间漂移影响。
6. 统计判断：若两版差异落在噪声范围内，不下结论；用重复次数与置信区间支撑结论。
7. 记录与复现：保存完整配置、原始数据与脚本，任何人可一键重跑复现结果。
8. 结论口径：说清测的是 kernel、step 还是端到端，避免口径混淆。

输出物：baseline 与新实现的指标对比表、正确性校验结果、可重跑的实验脚本与原始日志。

### 4. 技术洞察

- 控制变量是结论成立的前提：差一点点环境就可能翻转结果。
- warmup 不只热代码，还热分配器、页表与通信链路；预热不足会把冷启动开销算进去。
- 交替 A/B 能抵消系统随时间的漂移（如温度、后台任务），比「先跑完 A 再跑完 B」更可靠。
- 性能提升必须以不破坏正确性为前提，容差门禁是防止「更快但算错」的关键。
- 方差本身是有用信息：方差大说明测量不可靠，应先降低噪声再比较。

### 5. 图文说明

```text
固定: 环境/拓扑/锁频 + 输入/种子/shape + warmup 次数
流程: warmup ─▶ [A 计时] ─▶ [B 计时] ─▶ A ─▶ B ...（交替多轮）
判据: 对 oracle 过容差 且 指标差异 > 噪声 → 采纳
输出: 对比表 + 正确性结果 + 可重跑脚本
```

### 6. 拓展知识

可以延伸到基准测试框架、统计显著性检验、影子流量比对、锁频与温控，以及把性能门禁接进 CI 防止回归。

### 7. 常见追问及回答要点

- **为什么不只跑一次？** 单次结果受噪声与环境漂移影响，无法区分真实收益与波动。
- **为什么要有 oracle？** 优化常改数值或重排，只有独立参考能自动判定是否算错。
- **结论和噪声接近怎么办？** 增加重复次数、降低噪声或改用更敏感的指标，否则不宣称有提升。

### 8. 易错点与反例

- 不预热、不隔离环境就下结论。
- 先跑完 A 再跑完 B，忽略系统漂移。
- 只看跑分不看正确性，或不做重复统计。

### 9. 实践与验证

针对一个具体优化（如换用更快的 kernel）设计 A/B 实验：固定输入与拓扑、锁频、warmup 后交替多轮计时，对 oracle 校验正确性，报告指标与方差，最后用脚本一键复现。

### 10. 评分标准

- 合格：能固定环境与输入并多次测量。
- 良好：加入正确性门禁与 A/B 交替。
- 优秀：给出统计判据、方差分析与完整可复现脚本。

## I018. 如何把个人项目事实映射到源码事实并区分证据等级？

- 难度：中等级
- 知识域：K09（项目表达与职业叙事）
- 题型：故障排查
- 面试频率：中高
- 前置知识：B018 叙事主线、源码阅读、可核验证据
- 关联题目：B018, I017
- 事实状态：[推断] [P-待补充]

### 1. 背景知识

面试或复盘里，个人项目描述很容易与可核验事实脱节：把团队成果说成个人、把推测当结论、报了没有出处的数字。把每条声明拆成可验证命题、再逐条找证据并标注等级，是让表述经得起追问的方法。

### 2. 问题分析

问题包含两步：一是映射，把「我说我做过什么」转成「源码/日志/提交里能查到什么」；二是分级，明确哪些是机制事实、哪些是本人证据、哪些还只是推断。目的是既不夸大，也不因为谦虚而埋没真实贡献。

### 3. 具体答案

证据等级定义：

- `[S-已确认]`：源码、规范或官方文档可引用的机制事实。
- `[推断]`：由机制推导、逻辑自洽但无直接证据。
- `[P-已确认]`：自己做过且留有证据（代码、提交、日志、测试结果）的项目事实。
- `[P-待补充]`：自己陈述但暂时拿不出证据，需补实验或材料。

映射方法：

1. 拆命题：把项目描述里的每句拆成可验证命题，尤其是机制、职责、数字三类。
2. 找证据：为每条定位源码行、提交、issue、benchmark 记录、监控曲线或测试用例。
3. 标等级：给出对应证据等级；`[P-待补充]` 的要么补证据，要么把表述降级为定性。
4. 分归属：区分「我做了」与「团队做了」、「我提出」与「我实现」。
5. 校口径：性能数字必须带测量口径（硬件、负载、指标定义、对比基线），没有口径就标注待补充或改成定性。
6. 预演追问：对每条准备「细节在哪、怎么验证、反例是什么」，确保能落到具体文件或数据。

### 4. 技术洞察

- 面试官真正在意的是「能不能被追问下去」，而不是名词堆得多不多；可核验性比华丽更值钱。
- 把机制事实（[S]）和个人事实（[P]）分开，能避免用「源码里这么做」冒充「我这么做」。
- 无口径的数字最容易在追问中崩塌，宁可给范围和口径，也不给孤立百分比。
- 诚实标注 `[P-待补充]` 反而是加分项，说明有边界意识；缺的是补齐计划而非信用。
- 源码事实可以支撑「我理解这个机制」，但不能自动支撑「这块是我做的」。

### 5. 图文说明

```text
项目声明
  ├─ 机制类 → 查源码/规范 → [S-已确认] / [推断]
  ├─ 职责类 → 查提交/分工 → [P-已确认] / [P-待补充]
  └─ 数字类 → 查 benchmark/口径 → 有口径: [P-已确认]; 无: [P-待补充]或降级
每条都要能回答: 在哪? 怎么证? 反例?
```

### 6. 拓展知识

可以延伸到 STAR 与「问题—约束—机制—验证」结合、术语映射表、避免堆砌名词，以及准备一到两个可深挖的案例用于压力测试。

### 7. 常见追问及回答要点

- **没有源码证据怎么办？** 用测试结果、日志或复现步骤替代，实在没有就降级为 `[P-待补充]` 并说明补证据计划。
- **怎么区分个人与团队贡献？** 按提交历史、设计文档署名、负责模块界定，表述时明确「我负责哪一段」。
- **数字没有口径怎么办？** 补测或改成定性描述，绝不保留孤立百分比。

### 8. 易错点与反例

- 把机制事实当成个人经历。
- 报没有出处的性能百分比。
- 把团队成果整体归到个人，追问时说不清自己那部分。

### 9. 实践与验证

挑三到五条项目声明，逐条写成「命题—证据—等级—追问预案」的表格，请他人按表格追问，检验能否每条都落到具体文件或数据；对 `[P-待补充]` 项制定补齐计划。

### 10. 评分标准

- 合格：能给声明标注证据等级。
- 良好：能区分机制事实与个人事实、个人与团队贡献。
- 优秀：每条声明都有可核验证据与口径，并诚实标注待补充部分。
