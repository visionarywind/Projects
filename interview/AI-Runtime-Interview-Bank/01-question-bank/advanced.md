## A001. 如何设计一层可插拔的 Device Runtime 抽象，兼容多后端？

- 难度：高级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：系统设计
- 面试频率：高频
- 前置知识：分层调用栈、句柄与生命周期、后端能力差异
- 关联题目：A002, A011
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

训练与推理栈常需要在不同厂商设备之间切换，上层希望只写一份算子与调度逻辑。可插拔抽象的目标是把设备差异收敛到适配层，但抽象的难点不在定义几个接口，而在决定哪些能力可以统一、哪些必须显式暴露。

### 2. 问题分析

统一抽象面对三类冲突：能力不对等（有的后端有 event、有的用 fence），性能要求（抽象不能进入逐算子热路径的瓶颈），以及演进压力（后端不断新增特性）。设计前要先画能力矩阵，再决定接口粒度、热路径是否绕过抽象、以及逃生舱如何留。

### 3. 具体答案

- 设备枚举与能力查询：统一返回属性集合（内存层次、异步原语、图支持、P2P、拓扑、原子能力），上层据此选择路径。
- 资源对象：opaque handle 表示 context/stream/event/buffer，配套创建到销毁的生命周期与引用计数。
- 执行接口：submit、kernel launch、memcpy、synchronize、event record/wait，语义与完成点必须写进契约。
- 逃生舱：后端专有扩展通过带命名空间的接口暴露，默认路径不依赖它。
- 版本与协商：接口带版本号，运行时协商能力，缺失能力走降级而非直接失败。

核心决策是把抽象停在语义稳定的层，热路径允许直接调用后端以减少间接开销。

### 4. 技术洞察

- 抽象层若吃掉设备属性，上层就无法做拓扑与容量决策，这是最常见的隐性代价。
- 虚函数、表查找、锁会放大到每算子开销，设计上要区分冷路径（建对象）与热路径（提交）。
- 能力不均等时，宁可显式声明"此后端不支持"，也不要静默用慢路径掩盖。

### 5. 图文说明

```text
Framework / 调度层
      │ 统一接口(能力查询 / 句柄 / 提交 / 同步)
      ▼
Runtime 抽象层 ── capability 协商 + 版本
      ├── Backend A 适配器
      ├── Backend B 适配器
      └── 逃生舱(后端扩展)
      ▼
各厂商 Runtime → Device
```

### 6. 拓展知识

可参考 DLPack 的张量互操作、oneAPI/SYCL 的插件式后端、图抽象（捕获与重放）如何跨后端统一，以及驱动 ABI 与用户态 runtime 的分界。

### 7. 常见追问及回答要点

- **抽象层如何不拖慢热路径？** 把对象创建与能力协商放冷路径，提交路径用函数表甚至内联，避免锁与动态分配。
- **后端能力缺失怎么处理？** 用 capability 查询决定路径，缺失时显式降级并暴露成本，而不是假设统一语义。
- **怎么防止接口被某厂商绑架？** 公共接口只放跨后端可表达的语义，专有特性走逃生舱并标注依赖。

### 8. 易错点与反例

- 假设所有后端都有 stream/event 的相同语义。
- 把某后端专有参数塞进公共接口，污染抽象。
- 抽象层丢弃设备属性，导致上层容量与拓扑决策失据。

### 9. 实践与验证

写一个最小适配器，让同一算子跑在两个后端上；建立能力矩阵测试各后端缺失能力时的降级路径；用微基准确认抽象层带来的调用开销处于可接受范围。[P-待补充]

### 10. 评分标准

- 合格：说清抽象分层与统一接口的作用。
- 良好：指出能力查询、逃生舱与热路径开销的取舍。
- 优秀：能把能力矩阵、版本协商、性能边界与演进策略一起讲清，并区分哪些是通用设计、哪些依赖具体后端。

## A002. 异步 API 的契约应该如何设计，才能表达取消、超时和错误？

- 难度：高级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：系统设计
- 面试频率：高频
- 前置知识：异步提交语义、完成与可见性、错误传播路径
- 关联题目：A001, A003
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

设备 API 大多异步，提交返回不代表完成。当上层需要取消、限时或区分错误来源时，若契约不清晰，就会在资源回收和错误归属上踩坑。设计异步契约，本质是定义返回时处于哪个状态，以及如何到达可观测的终态。

### 2. 问题分析

一个异步操作至少有三态：已提交、已完成、已失败；取消引入第四态"已请求取消"。难点在于取消不是即时的（设备可能已在执行），错误也不能只在同步点被笼统抛出。契约必须区分提交失败与执行失败，并明确取消之后内存与队列资源的归属。

### 3. 具体答案

- 完成对象：每次提交返回一个 future/handle，携带状态与最终错误，而不是只返回一个立即值。
- 取消语义：区分提交前可撤销与提交后只能等完成或尽力中止；取消是请求、不保证生效，返回值必须报告实际状态。
- 超时语义：超时触发的是等待端的放弃，不等于设备停止；资源必须等真正的完成信号才能复用。
- 错误分层：参数错误在提交时同步返回；设备错误在 join 点暴露，并携带操作上下文（哪个 kernel、哪块内存）。
- 组合：用 event、回调或 future 建立等待点，允许一次等待多个操作。

关键决策是拒绝把取消实现成"假装完成"，所有终态都必须可观测且幂等。

### 4. 技术洞察

- 提交成功与执行成功必须分开表达，否则错误归属混乱。
- 被取消或超时的操作仍可能占用内存与队列，回收要等真实完成。
- 契约里写清同步点落在哪里，是避免偶发读旧值的根本手段。

### 5. 图文说明

```text
提交 → [已提交] ──完成──→ [成功]
         │  ├──────失败──→ [错误(含上下文)]
         └─ cancel() ─→ [取消请求] → 实际可能是 成功/失败/已中止
超时: 上层放弃等待 ≠ 设备停止执行
```

### 6. 拓展知识

可联系 C++ future/promise、取消令牌（类似 stop_token 的风格）、RPC 的 deadline 与取消传播，以及分布式集合通信中成员失败后的中止语义。

### 7. 常见追问及回答要点

- **取消后立刻释放资源可以吗？** 不行，设备可能仍在读写该内存，要等真实完成或安全点。
- **超时和取消有什么区别？** 超时是等待端的放弃，取消是主动请求停下，两者都不等于设备已停。
- **错误怎么归因到具体操作？** 在 handle 中携带操作的元数据，在 join 点按 handle 报告。

### 8. 易错点与反例

- 把提交返回当成完成，把取消当成已停止。
- 超时后立即复用内存。
- 只用一个布尔错误标志，丢失了是参数错还是设备错。

### 9. 实践与验证

实现一个带 future 的异步提交接口，注入慢 kernel 与错误 kernel，验证取消、超时后的资源状态与错误报告是否符合契约。[P-待补充]

### 10. 评分标准

- 合格：说明异步返回不代表完成。
- 良好：区分取消、超时与真实完成的语义边界。
- 优秀：给出带状态的 future、错误分层与安全回收的完整契约设计。

## A003. 如何设计版本兼容与 ABI 演进的策略？

- 难度：高级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：系统设计
- 面试频率：中高
- 前置知识：二进制接口、结构体布局、动态链接
- 关联题目：A002, A012
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

设备 runtime 与上层框架、已编译算子、驱动之间存在多个二进制接口。软件升级时，任何一侧的不同步都可能造成加载失败、符号缺失或静默的行为变化。ABI 演进的目标是让新旧组件在一定窗口内共存，而不是每次升级都要求全量重编译。

### 2. 问题分析

兼容有三个维度：源兼容（重编译即可）、二进制兼容（不重编译也能跑）、行为兼容（接口不变但语义或性能改变）。难点集中在结构体布局、符号可见性、枚举扩展，以及运行期组件版本错配。三者需要不同手段，混为一谈会得到错误结论。

### 3. 具体答案

- 版本策略：区分 major 与 minor，major 允许破坏，minor 只增不删；接口自带版本号，运行期校验。
- 结构体演进：用带 size 字段的可扩展结构体，新增字段追加在尾部并默认为零，避免改动已有字段偏移。
- 符号与命名：内部符号隐藏，公共 API 用稳定前缀，避免导出会随实现波动的符号。
- 枚举与常量：预留未知值处理路径，遇未知枚举走安全分支而非崩溃。
- 运行期协商：加载时比对 runtime、驱动、算子库版本，不满足则给出明确诊断或降级。
- 弃用流程：标记、警告、保留兼容、移除，跨版本留出迁移窗口。

核心决策是加法优先，破坏性变更走 major 并配合过渡期。

### 4. 技术洞察

- 结构体中间插入字段是 ABI 破坏的常见来源，追加并靠 size 判断才是安全做法。
- 行为兼容最难：接口没变但数值或性能变了也是回归，需要测试门禁拦住。
- 多组件错配（框架新、驱动旧）应尽早检测，而不是运行到一半才崩。

### 5. 图文说明

```text
接口 v1: {size, a, b}
接口 v2: {size, a, b, c=0}   ← 追加字段, 旧 caller 传小 size 也安全
调用方 ──版本校验──> Runtime ──版本校验──> Driver
        不匹配 → 明确诊断 / 降级 / 拒绝启动
```

### 6. 拓展知识

可延伸到 C++ 的 inline namespace 与符号版本、ELF symbol versioning、语义化版本实践，以及驱动与用户态库的兼容矩阵管理。

### 7. 常见追问及回答要点

- **加字段为什么不破坏 ABI？** 只要追加在尾部并由 size 决定可见范围，旧调用方不受影响。
- **行为变了算不算兼容？** 不算，数值与性能回归也需要门禁拦住。
- **怎么处理未知枚举？** 默认走安全分支并记录，不因未知值崩溃。

### 8. 易错点与反例

- 在结构体中间插入字段。
- 导出实现相关的内部符号。
- 只在编译期检查版本，忽略运行期错配。

### 9. 实践与验证

构造新旧两个版本的调用方与库交叉加载，验证 size 的向前与向后兼容、未知枚举处理与错误诊断是否符合预期。[P-待补充]

### 10. 评分标准

- 合格：说清兼容的三个维度。
- 良好：给出结构体、符号与运行期协商的具体做法。
- 优秀：能把弃用流程、行为兼容门禁与错配诊断一起纳入演进策略。

## A004. 多级异步 allocator 的缓存层次与回收策略如何设计？

- 难度：高级
- 知识域：K02（显存与内存管理）
- 题型：系统设计
- 面试频率：高频
- 前置知识：分配器分层、stream 语义、异步完成
- 关联题目：A005, A006
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

设备内存申请昂贵，主流做法是分层缓存：小块池、大块池，以及跨进程或跨设备的更大段。层级带来命中率，也带来回收时机与碎片管理的复杂度。异步访问又要求回收必须尊重完成顺序。

### 2. 问题分析

要点有三：不同大小走不同层，各层回收策略不同；回收必须尊重异步完成；在多流场景下，块何时可复用取决于引用它的流是否到达安全点。设计要在命中率、碎片与同步开销之间平衡。

### 3. 具体答案

- 分层：按尺寸类划分小块、中块、大段，每层用 free list 或 bitmap 管理，命中直接复用。
- 异步安全：块被释放时不立即入池，而是绑定到使用它的 stream 或 event，待其到达同步点再回收。
- 跨流处理：若块被多条流使用，记录使用集合，最慢的流决定可回收时间，避免提前复用。
- 回收策略：按空闲时长、外部压力、层级水位分级触发；大段比小块更值得尽早归还驱动。
- 扩容与缩容：容量按历史峰值增长，长期低水位再归还，避免反复向驱动申请。

核心决策是把逻辑释放与物理可复用分开，前者立即发生，后者等异步完成。

### 4. 技术洞察

- 复用的正确性依赖 happens-before，不是时间到了就能用。
- 层级划分不合适会让大请求落到小块池，产生内部碎片或频繁降级。
- 跨流共享的块是延迟回收的主要来源，也是最容易出错的地方。

### 5. 图文说明

```text
小请求 → 小块池 ─命中→ 复用
大请求 → 大段池 ─命中→ 复用
              └未命中→ 向驱动申请 → 新段
free 块 → 绑定 stream/event → 到达安全点 → 回池可复用
```

### 6. 拓展知识

可联系 stream-ordered allocator、可扩展段、跨进程共享显存，以及缓存分配器的 memory_stats 观测字段。

### 7. 常见追问及回答要点

- **free 之后能立刻复用吗？** 要等引用它的流到达安全点，异步访问未完成前不能复用。
- **跨流共享怎么管？** 记录使用集合，按最慢的流决定回收时机。
- **层级阈值怎么定？** 依据大小分布与命中率统计，过小产生碎片，过大浪费缓存。

### 8. 易错点与反例

- 把逻辑释放当成可立即复用。
- 大块塞进小块层导致碎片。
- 忽略跨流引用，提前复用造成数据竞争。

### 9. 实践与验证

多种尺寸交错分配释放，检查命中率与最大连续块；跨流共享后再释放，验证是否在安全点才复用。[P-待补充]

### 10. 评分标准

- 合格：说清分层与回收的基本思路。
- 良好：说明异步安全与跨流引用。
- 优秀：能把层级阈值、分级回收与碎片治理结合成完整策略。

## A005. 碎片与容量策略如何在吞吐、延迟和内存之间取舍？

- 难度：高级
- 知识域：K02（显存与内存管理）
- 题型：权衡分析
- 面试频率：高频
- 前置知识：碎片分类、缓存分配器、外部压力感知
- 关联题目：A004, A006
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

同一套内存策略，追求高吞吐会倾向多缓存、少归还；追求低延迟会倾向稳定命中；追求省内存会倾向早归还。三者互相牵制，策略选择取决于服务目标与外部压力。

### 2. 问题分析

吞吐偏好把内存留在池中减少申请；延迟在意避免因回收和申请引发的同步停顿；内存约束要求尽快归还给系统或其它租户。碎片是三方共同的敌人：它既降低命中，又抬高容量需求，因此治理碎片往往能同时改善多项。

### 3. 具体答案

- 偏吞吐：加大缓存、按尺寸类池化、延迟归还未用段，代价是常驻显存高。
- 偏延迟：预分配热点尺寸、固定地址、避免运行期合并带来的停顿，代价是灵活性下降。
- 偏省内存：及时归还大段、限制缓存水位、必要时压缩工作集，代价是申请频率上升、尾延迟波动。
- 折中手段：分桶减少碎片、按外部压力动态调整水位、对关键路径保留固定池、对非关键路径即用即还。

核心决策是把常驻容量当作可调旋钮，随外部压力与 SLO 动态移动，而不是固定一种策略。

### 4. 技术洞察

- 碎片对三方都是负面项，优先治理碎片通常能同时改善多项指标。
- 早归还省内存，但把成本转成申请延迟，适合内存紧张的多租户环境。
- 固定分桶牺牲一点内部空间，换来稳定的命中与可预测的延迟。

### 5. 图文说明

```text
多缓存 ──── 吞吐↑   常驻内存↑
早归还 ──── 内存↓   延迟抖动↑
固定分桶 ── 延迟稳   内部碎片↑
目标: 按外部压力在这三者构成的空间内移动工作点
```

### 6. 拓展知识

size-class 划分、buddy 与 segment 方案、best-fit 与 first-fit 对比、内存压缩与冷热分层。

### 7. 常见追问及回答要点

- **吞吐和低延迟能兼得吗？** 部分可以，靠固定热点池并让非热点走即用即还。
- **碎片怎么权衡？** 用分桶与相邻合并控制，碎片治理通常对三项都有益。

### 8. 易错点与反例

- 用固定策略应对变化的外部压力。
- 把 cached 偏高误判为泄漏而盲目清空。

### 9. 实践与验证

在相同 workload 下切换三种策略，记录吞吐、P99、常驻容量与最大连续块，画出各自的工作点并比较。[P-待补充]

## A006. 多租户显存配额与 OOM policy 如何设计才公平？

- 难度：高级
- 知识域：K02（显存与内存管理）
- 题型：系统设计
- 面试频率：中高
- 前置知识：显存记账、碎片、隔离机制
- 关联题目：A004, A005
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

一张卡或多张卡被多个任务或租户共享时，显存不是无限资源。租户 A 的突发占用可能让租户 B 直接 OOM。配额与 OOM 策略决定共享环境是否公平和可预测。

### 2. 问题分析

难点在于显存难像 CPU 那样强制抢占；碎片让配额内仍可能 OOM；OOM 发生时该杀谁、何时杀、如何避免误伤都需要明确。要区分硬配额（驱动级隔离）与软配额（分配器级记账加拒绝），并设计分级处置。

### 3. 具体答案

- 配额模型：硬隔离用设备或上下文级限制（分区、显存上限）；软配额由分配器记账，超限则拒绝新申请而非触发全局 OOM。
- 预留与突发：给每租户基线配额并允许受限借用，借用在压力下可被回收。
- OOM policy：分层处理，先拒绝或排队新请求，再回收可释放缓存，再对超配额租户降级，最后才中止，且中止前记录现场。
- 公平性：按配额而非先到先得分配，避免一个租户的峰值拖垮其它租户。
- 可观测：暴露每租户的 allocated/reserved、等待与拒绝计数，供容量治理使用。

核心决策是把 OOM 从进程崩溃转化为可控拒绝加分级的降级路径。

### 4. 技术洞察

- 配额内仍可能 OOM 是因为碎片，容量治理必须同时治理碎片。
- 硬隔离最公平但损失弹性，软配额灵活但依赖记账准确性。
- 中止应是最后手段，前面每一级都要能止损，避免一步到崩溃。

### 5. 图文说明

```text
租户配额 ─┬─ 硬: 设备/上下文上限(隔离)
          └─ 软: 分配器记账 → 超限拒绝
申请 → 配额内? ─是→ 分配
        └否→ 回收缓存 → 仍不足 → 拒绝/排队 → 降级 → 中止(最后)
```

### 6. 拓展知识

MPS 与 MIG 分区、显存不足时框架的既有行为、设备插件层面的配额、QoS 等级与优先级。

### 7. 常见追问及回答要点

- **配额内为何还 OOM？** 碎片或其它租户占用，要看最大连续块与外部占用。
- **怎么做到公平？** 按配额分配并允许受限借用，压力下优先回收借用部分。
- **OOM 先中止谁？** 先降级超配额租户，保留基线租户，避免误伤。

### 8. 易错点与反例

- 让一个租户的峰值触发全局崩溃。
- 只设软配额却不治理碎片。
- 不做分级，直接中止进程。

### 9. 实践与验证

模拟多租户并发申请，验证超限时是拒绝与降级而非全局 OOM，并检查各租户的指标是否准确。[P-待补充]

### 10. 评分标准

- 合格：说清硬配额与软配额的区别。
- 良好：给出分级 OOM 处置与公平分配思路。
- 优秀：能把配额、碎片治理、借用回收与可观测整合成完整方案。

## A007. 跨设备 stream/event 模型如何统一？如何处理多副本依赖？

- 难度：高级
- 知识域：K03（异步执行与同步原语）
- 题型：系统设计
- 面试频率：中高
- 前置知识：stream/event 语义、P2P 与拓扑、集合通信
- 关联题目：A008, A013
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

多设备与多副本场景下，一条逻辑数据依赖可能横跨设备与副本，例如数据并行中的梯度聚合、流水线中的跨设备传递。各后端对 stream 与 event 的表达不同，需要统一的依赖模型，否则同步会遗漏或过度。

### 2. 问题分析

难点在于跨设备同步不只是有序，还要处理数据搬运（P2P 或经 host）；多副本意味着同一逻辑事件对应多个物理完成。需要区分设备内顺序、设备间依赖、副本间一致性这三层，并明确每一层的实现路径。

### 3. 具体答案

- 统一抽象：用逻辑 stream 与 event 表达顺序，底层映射到各后端的物理流与同步原语。
- 跨设备依赖：event 在源流记录，跨设备 wait 时若支持 P2P 就在设备间传递，否则经 host 中转并显式拷贝与同步。
- 多副本依赖：集合操作视为一个跨副本事件，所有 rank 完成后才触发，避免部分完成被误当整体完成。
- 拓扑感知：优先在同 NUMA 或同交换机内配对，减少中转。
- 失效边界：P2P 不可用、副本数变化、rank 掉线时，要有降级或重建依赖图的路径。

核心决策是把逻辑顺序点与物理同步原语分离，用 event 统一表达，物理实现按后端与拓扑选择。

### 4. 技术洞察

- 跨设备同步的代价取决于是否需要 host 中转以及是否支持 P2P。
- 多副本的完成必须是集合意义，单副本完成不代表整体就绪。
- 拓扑信息缺失会让同步走远路，容量规划也会偏高。

### 5. 图文说明

```text
Device0 StreamA ─record(E0)─┐   (P2P 可用 → 直连)
                             ├─→ wait(E0) on Device1
Device1 StreamB ─record(E1)─┘   (否则经 host 中转)
多副本: [rank0..rankN] 全部完成 → 触发集合 event
```

### 6. 拓展知识

P2P 与 GPUDirect、通信库的 stream 语义、event 跨设备传递、PCIe/NVLink 拓扑对同步路径的影响。

### 7. 常见追问及回答要点

- **跨设备 event 一定能直连吗？** 不一定，取决于 P2P 能力与拓扑，否则经 host 中转。
- **多副本怎么表达依赖？** 用集合事件，所有副本完成后统一触发。
- **副本数变化怎么办？** 重建通信域与依赖图，避免残留旧引用。

### 8. 易错点与反例

- 把单设备顺序语义套到跨设备。
- 用单副本完成代表整体完成。
- 忽略 P2P 不可用时的降级路径。

### 9. 实践与验证

在两台设备或两个副本间传数据，对比 P2P 直连与 host 中转的时序与正确性；验证集合事件在所有副本完成后才触发。[P-待补充]

### 10. 评分标准

- 合格：说清三层依赖的区分。
- 良好：说明 P2P 与 host 中转的取舍。
- 优秀：能把集合事件、拓扑感知与失效重建整合成统一模型。

## A008. 并发 contention 导致尾延迟升高时如何定位和缓解？

- 难度：高级
- 知识域：K03（异步执行与同步原语）
- 题型：权衡分析
- 面试频率：高频
- 前置知识：排队与分位数、资源争用分类、trace 分段
- 关联题目：A007, A016
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

设备资源（计算单元、访存带宽、拷贝引擎、锁、分配器、网卡队列）被多任务共享时，平均延迟可能正常，但 P99 明显升高。尾延迟通常是争用与排队叠加的结果，只看均值会完全错过它。

### 2. 问题分析

先分类争用源：计算资源争用、访存带宽争用、拷贝与 DMA 争用、host 侧锁与分配器争用、网络队列争用。定位要做分段测量，把排队时间与执行时间分离，找到究竟哪一段的尾部变长，再对症缓解。

### 3. 具体答案

- 定位：用 trace 对齐各任务时间线，统计每类资源的等待时间分布，关注 P99 而非均值，检查是否同时有 kernel、拷贝、通信竞争同一资源。
- 计算争用：多任务同卡时配额导致长 kernel 被拖慢，用优先级或分区隔离。
- 带宽争用：访存密集与拷贝同时发生，错峰或限制并发拷贝数。
- host 争用：分配器锁、日志、解释器开销造成提交抖动，减少热路径锁与序列化。
- 网络争用：网卡队列与流控引发排队，用 QoS、分流或增加队列。
- 缓解手段：优先级、隔离、限并发、错峰、批量，代价常是吞吐或公平性下降。

核心决策是把尾延迟目标转化为对争用资源的配额与排队策略，而不是平均优化。

### 4. 技术洞察

- 平均延迟看不到争用，必须用分位数与分资源的等待时间。
- 排队是尾延迟的主因，削减尾部就是削减排队时间。
- 隔离能压尾延迟，但降低资源利用率，是一项明确取舍。

### 5. 图文说明

```text
任务A: [执行]......[等计算资源]...[执行]
任务B: ....[拷贝]......[等带宽]...
                          ↑ 争用点
P99 = 执行 + 排队 + 争用放大
```

### 6. 拓展知识

排队论基础、优先级反转、NUMA 与缓存争用、MPS/MIG 隔离、QoS 与限流。

### 7. 常见追问及回答要点

- **平均值正常但 P99 高说明什么？** 存在排队或争用，尾部被少数慢任务拉高。
- **怎么区分排队与执行变慢？** 用 trace 分段，比较等待段与执行段各自的分位数。
- **隔离一定好吗？** 压尾延迟但牺牲利用率，需按 SLO 权衡。

### 8. 易错点与反例

- 只看平均值。
- 把尾延迟归因于单个慢 kernel 而忽略争用。
- 靠加机器掩盖争用而不治根因。

### 9. 实践与验证

构造多任务竞争同卡或同网，记录 P50/P99 与资源等待时间，逐一引入优先级、隔离、错峰观察尾部的变化。[P-待补充]

### 10. 评分标准

- 合格：能列出主要争用源。
- 良好：说明用分位数与分段定位。
- 优秀：能把尾延迟目标转成配额与排队策略并讲清代价。

## A009. graph capture 与动态资源分配如何共存？

- 难度：高级
- 知识域：K03（异步执行与同步原语）
- 题型：系统设计
- 面试频率：中高
- 前置知识：图捕获与重放、内存池、动态 shape
- 关联题目：A011, A015
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

图捕获要求执行序列与内存地址稳定才能重放。但很多工作负载需要动态 shape、动态 KV 增长或临时缓冲。二者的冲突是固定与变化之间的矛盾，处理不当就会捕获失败或重放踩内存。

### 2. 问题分析

冲突点有两个：捕获期不允许非法同步与普通分配；重放期若内存被别的路径复用会破坏图。解决方向是把动态部分移出图、使用图安全的分配器，或用图内节点表达有限的动态。

### 3. 具体答案

- 图安全分配器：分配从图专用内存池取，地址在图生命周期内固定，池随图重建而释放。
- 动态移出：把形状或长度变化的分配放到捕获区外，图只处理稳定计算；变长用多份预捕获实例或条件、循环节点。
- 参数化重放：允许重放时更新部分输入指针或标量，而结构保持不变。
- 多实例：对常见 shape 预捕获多个图，运行时按 shape 选择，命中不足则回退 eager。
- 生命周期：捕获、实例化、重放分阶段，重放前保证输入地址合法。

核心决策是稳定结构进图、易变资源走池外或参数更新，边界要显式。

### 4. 技术洞察

- 捕获期的一次隐式分配或同步都会破坏图，必须走图安全路径。
- 地址稳定是硬约束，任何外部复用都可能踩到图内存。
- 动态不是不能进图，而是要拆成有限的、可预捕获的形态。

### 5. 图文说明

```text
捕获期: [kernel...] + 图安全池分配(地址固定) → Graph
重放期: Graph.submit() 结构不变
动态部分(变长/KV) ── 池外分配 or 条件节点 / 多实例
```

### 6. 拓展知识

图捕获的三阶段（capture/instantiate/replay）、条件与循环节点、内存池与图的绑定、编译器自动捕获。

### 7. 常见追问及回答要点

- **捕获时能分配显存吗？** 用图安全池可以，普通分配会破坏捕获。
- **动态 shape 怎么处理？** 预捕获多实例或条件、循环节点，否则回退 eager。
- **重放能改地址吗？** 结构固定，通常只能更新有限的输入指针或标量。

### 8. 易错点与反例

- 在捕获区做同步或普通分配。
- 假设重放能任意改变结构。
- 图内存被其它路径复用导致踩踏。

### 9. 实践与验证

对一个含动态 KV 的推理步骤，对比全 eager 与"稳定部分进图加动态池外"两种方案的时序与正确性。[P-待补充]

### 10. 评分标准

- 合格：说清捕获对稳定性的要求。
- 良好：给出图安全池与动态移出的方法。
- 优秀：能把多实例、参数化重放与回退策略组合成完整方案。

## A010. 算子 fallback 与降级策略如何设计，保证正确性？

- 难度：高级
- 知识域：K04（张量与图执行）
- 题型：系统设计
- 面试频率：中高
- 前置知识：算子覆盖、数值容差、能力判定
- 关联题目：A011, A012
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

设备 kernel 可能不覆盖某些 dtype、shape 或后端组合。框架需要有 fallback 路径，例如回退到通用实现或 host，但 fallback 若引入数值差异或性能悬崖，就会变成隐性 bug 与 SLO 风险。

### 2. 问题分析

要点有四个：如何判定需要 fallback（能力查询而非运行时才发现）、fallback 的数值是否等价（dtype 提升与累加精度）、性能悬崖如何暴露、以及 fallback 期间资源与同步如何保证。

### 3. 具体答案

- 触发条件：在计划阶段用能力矩阵判断 dtype、shape、后端，尽量提前，而不是执行中途才回退。
- 等价性：明确 fallback 的数值容差，必要时用更高精度累加，并用独立参考结果验证，记录差异门槛。
- 性能可见：fallback 要打点（计数、耗时），避免悄悄变慢；对热点路径回退应告警。
- 资源与同步：回退到 host 或另一引擎时，需在设备与 host 之间建立正确的同步与数据可见性。
- 渐进策略：优先在设备内用通用 kernel，再退到另一设备实现，最后才回 host。
- 版本演进：新 kernel 覆盖后逐步关闭 fallback，并保留开关以便回退。

核心决策是能力矩阵前置判定、数值参考校验、性能打点三者齐备。

### 4. 技术洞察

- 运行时才发现不支持会带来不可预测的停顿。
- 数值等价要显式定义容差，否则回归难以判定。
- 隐性 fallback 是性能回归的常见来源，必须可观测。

### 5. 图文说明

```text
计划 → 能力矩阵支持? ─是→ 设备 kernel
                      └否→ 通用设备 kernel → 另一后端 → host fallback
每级: 打点(计数/耗时) + 独立参考校验 + 容差门槛
```

### 6. 拓展知识

算子覆盖矩阵、dtype 提升规则、数值容差设定、CPU 与设备双实现的一致性测试。

### 7. 常见追问及回答要点

- **怎么保证 fallback 数值正确？** 用独立参考与容差门槛，复杂度敏感处提高累加精度。
- **如何避免性能悬崖？** 提前判定并打点，热点路径回退时告警。
- **回退到 host 要注意什么？** 正确同步与数据搬运的可见性，避免读到未完成结果。

### 8. 易错点与反例

- 运行时才发现不支持，导致停顿。
- 不做数值容差校验。
- 隐性 fallback 没有打点。

### 9. 实践与验证

构造一批未覆盖的 dtype 与 shape，验证 fallback 触发、数值容差与打点是否齐全。[P-待补充]

### 10. 评分标准

- 合格：说清 fallback 的触发与路径。
- 良好：说明数值容差与性能打点的重要性。
- 优秀：能把能力矩阵、参考校验、渐进策略与版本演进讲成完整设计。

- 难度：高级
- 知识域：K04（张量与图执行）

- 面试频率：高频
- 前置知识：图执行、算子融合、设备队列
- 关联题目：A001, A009
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

谁来负责算子融合、并行切分、内存规划与执行提交？框架层看得懂计算图与语义，runtime 层看得懂设备与队列。边界划错会让双方都做不好，或者互相打架。

### 2. 问题分析

两类信息决定了边界：语义信息（shape、依赖、数值要求）在框架侧，设备信息（队列深度、内存层次、同步代价）在 runtime 侧。边界应落在能同时获得必要信息又不过度往返的位置，否则会产生责任真空或重复决策。

### 3. 具体答案

- 框架侧负责：图与算子语义、shape 与依赖、并行策略的高层切分、内存规划意图。
- runtime 侧负责：具体设备选择、队列与流管理、内存落盘与复用、同步与提交、设备相关融合（如合并小 kernel）。
- 接口：框架给出做什么和约束，runtime 决定怎么做，靠能力查询向框架反馈设备特性。
- 反馈回路：runtime 把实测资源与延迟反馈给框架，让调度决策有真实依据。
- 失效边界：跨层来回决策会造成信息真空，需要明确单一 owner。

核心决策是语义与计划在框架，映射与执行在 runtime，避免两头都做融合又互相冲突。

### 4. 技术洞察

- 融合做在哪层取决于该层能否看到依赖和设备代价，只看一侧容易过度或不足融合。
- 来回往返会引入同步与序列化开销，边界要尽量粗粒度。
- 反馈缺失时框架的静态计划会偏离真实设备行为。

### 5. 图文说明

```text
Framework: 图语义 / 依赖 / 并行意图 / 内存规划意图
        │  "做什么 + 约束"
        ▼
Runtime: 设备选择 / 流与队列 / 内存复用 / 融合与提交
        │  实测资源/延迟反馈
        ▲
```

### 6. 拓展知识

编译器与 runtime 的职责划分、图优化 pass、JIT 与 AOT、算子库内部的调度层次。

### 7. 常见追问及回答要点

- **融合该在哪层做？** 谁同时看到依赖和设备代价就在哪层，通常 runtime 做设备相关融合。
- **为什么避免频繁往返？** 每次跨层都可能有同步与序列化成本。
- **反馈有什么用？** 让框架的静态决策基于真实资源与延迟。

### 8. 易错点与反例

- 两层都做融合导致重复或冲突。
- 边界模糊造成责任真空。
- 框架在不知设备代价时做激进切分。

### 9. 实践与验证

对比"框架全权计划"与"框架给约束、runtime 决策"两种划分在端到端的差异。[P-待补充]

- 合格：说清双方各自的职责。
- 良好：指出运行时反馈与粗粒度边界。
- 优秀：能把融合归属、往返成本与责任 owner 讲清并给出划分原则。

## A012. MindSpore 版本迁移时如何控制风险？

- 难度：高级
- 知识域：K04（张量与图执行）
- 题型：权衡分析
- 面试频率：中高
- 前置知识：框架版本差异、算子覆盖、回归测试
- 关联题目：A003, A010
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

框架版本升级常伴随算子行为、接口与默认精度变化。迁移风险来自隐式行为差异和生态组件版本错配。控制思路应是系统性分层验证与灰度，而不是逐个 bug 救火。

### 2. 问题分析

风险面包括 API 变化（改名、弃用）、算子数值差异、图编译器优化变化、算子覆盖变化，以及上下游组件（runtime、驱动、算子库）的版本耦合。控制手段是分层验证加灰度，并对版本组合整体锁定。

### 3. 具体答案

- 盘点：列出依赖的 API、算子与默认配置，标记弃用与变更项。
- 基线：在旧版本固化一组端到端与算子级用例作为回归基线，留存输入输出。
- 分层验证：先算子级数值对拍（新旧版本加独立参考），再小模型端到端，再真实 workload。
- 精度与性能门禁：定义数值容差与性能回归阈值，超阈值即拦截。
- 灰度：先影子运行比对，再小流量切新版本，保留回退。
- 版本耦合管理：锁定 runtime、驱动、算子库的组合，记录已知兼容矩阵。
- 回退预案：旧版本镜像可随时切回，数据与配置保持兼容。

核心决策是把迁移当成带门禁的渐进切换，而不是一次性升级。

### 4. 技术洞察

- 隐式行为变化（默认精度、融合顺序）最难发现，靠端到端数值对拍暴露。
- 版本耦合是迁移失败的常见根因，需要整体锁定而非单点升级。
- 灰度与影子流量能在真实分布上暴露差异。

### 5. 图文说明

```text
盘点变更 → 固定基线(旧版本) → 算子对拍 → 小模型 → 影子流量 → 灰度切流 → 全量
                                   ↑ 容差/性能门禁拦截
任何失败 → 切回旧版本
```

### 6. 拓展知识

语义化版本、算子覆盖矩阵、数值容差实践、AB 与影子部署、容器化回退。

### 7. 常见追问及回答要点

- **怎么发现隐式数值差异？** 端到端加算子级对拍，用独立参考与容差。
- **先升级哪个组件？** 整体锁定组合，先验证再逐步放开，不要单点跳版本。
- **怎么快速回退？** 保留旧镜像与兼容配置，切换即回退。

### 8. 易错点与反例

- 一次性全量升级。
- 只测小模型，漏掉长尾算子。
- 忽略上下游版本耦合。

### 9. 实践与验证

对同一模型在两个版本上跑同一组输入，逐层对拍数值并记录性能，建立兼容矩阵。[P-待补充]

### 10. 评分标准

- 合格：说清迁移的主要风险面。
- 良好：给出分层验证与门禁的思路。
- 优秀：能把灰度、版本锁定与回退预案整合成完整迁移策略。

## A013. 集合通信的 overlap pipeline 如何设计？

- 难度：高级
- 知识域：K05（集合通信）
- 题型：系统设计
- 面试频率：高频
- 前置知识：集合通信原语、流与依赖、带宽与计算比
- 关联题目：A014, A017
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

集合通信与计算若串行，通信时间直接叠加到 step 时间。Overlap 的思路是用分块或分片让通信与计算并行，把通信藏在计算背后。这是分布式训练性能的核心手段。

### 2. 问题分析

前提是通信与计算使用不同资源（网卡与 DMA 对计算单元），且存在可分割的批次或参数分片。难点在于依赖关系（通信需要梯度或激活就绪）、缓冲区复用，以及不同分片的通信量不均导致尾部无法完全隐藏。

### 3. 具体答案

- 分块：把梯度或参数按层或按 chunk 切分，前一块通信与后一块计算重叠。
- 依赖管理：通信依赖该块计算完成，用 event 与流建立依赖，避免过早发起用到未完成数据。
- 资源隔离：通信流与计算流分离，共享带宽要限量，防止通信挤占计算。
- 参数分片：大参数切分后 all-gather 与计算重叠。
- 尾部处理：最后一块无法隐藏，用通信与计算比例调优 chunk 大小以减小尾块。
- 混合并行下：不同通信（数据并行、张量并行、流水并行）优先级不同，需按关键路径排序。

核心决策是按可分割粒度把通信切块，用依赖与流把通信塞进计算空隙，chunk 大小以最小化尾块为目标。

### 4. 技术洞察

- overlap 的上限由通信量与计算量之比决定，通信过重时无法完全隐藏。
- 依赖建错会读到未完成数据，建得过保守则重叠不足。
- 通信与计算共享带宽时会互相拖慢，需要配额。

### 5. 图文说明

```text
计算: [chunk0][chunk1][chunk2][chunk3]
通信:        [comm0 ][comm1 ][comm2 ]  ← 与后续计算重叠
                                 └ 尾块无法隐藏
```

### 6. 拓展知识

梯度分桶、数据并行的通信钩子、张量并行与流水并行的通信模式、分层 allreduce。

### 7. 常见追问及回答要点

- **为什么不能完全隐藏？** 尾块没有后续计算可重叠，且通信与计算比过高。
- **依赖怎么建？** 每块通信 wait 该块计算完成的 event。
- **带宽竞争怎么处理？** 给通信限量并设优先级，避免挤占计算。

### 8. 易错点与反例

- 依赖过早导致读到未完成梯度。
- 只用一条流，无法重叠。
- 忽略尾块，chunk 切得过细反而增加启动开销。

### 9. 实践与验证

在有通信的 step 中对比串行与分块 overlap 的 step time，扫描 chunk 大小观察尾块的影响。[P-待补充]

### 10. 评分标准

- 合格：说清分块重叠的基本思路。
- 良好：说明依赖管理与带宽竞争。
- 优秀：能把尾块处理、混合并行优先级与 chunk 调优讲清。

## A014. RDMA QP/CQ/MR 资源路径如何规划容量与故障恢复？

- 难度：高级
- 知识域：K05（集合通信）
- 题型：系统设计
- 面试频率：中高
- 前置知识：RDMA 原语、连接拓扑、内存注册
- 关联题目：A013, A017
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

RDMA 通信依赖 QP（队列对）、CQ（完成队列）、MR（内存注册）等资源。资源数量有限且与内存注册开销相关，大规模部署时容量规划与故障恢复直接决定可靠性。

### 2. 问题分析

要点在于：QP 数量随连接数增长（全连接会呈平方增长），CQ 可共享以减少资源，MR 注册有固定内存与页表开销；故障时 QP 进入错误态需要重建或迁移。要区分容量（能建多少）与恢复（坏了怎么最快恢复），二者需要不同设计。

### 3. 具体答案

- QP 容量：用连接池与共享 QP（或选 UD、DC 等更省连接的传输类型）减少数量，避免全连接平方增长。
- CQ：多 QP 共享 CQ 减少事件队列资源，但要注意事件集中带来的处理开销。
- MR：一次性注册大块并在内部切分，减少注册次数；控制固定内存总量，避免注册耗尽。
- 容量规划：按 rank 数、每 rank 连接数、消息深度估算 QP/CQ/MR 与固定内存上限。
- 故障恢复：检测 QP 错误态，重建 QP 并重登记 MR，或迁移到备用路径；保证重试幂等，避免重复提交。
- 隔离：故障域隔离，单连接故障不影响整机通信。

核心决策是用共享与池化把资源从每连接独占降为按需复用，同时为 QP 错误准备好重建路径。

### 4. 技术洞察

- 全连接 QP 是规模化的第一道墙，拓扑感知能显著降低数量。
- MR 的代价在注册与固定内存，不是句柄本身。
- 故障恢复的关键是幂等重建，避免半重建状态。

### 5. 图文说明

```text
Rank ── N 个连接 ──> QP 池 ──共享──> CQ
                       │
                    MR(注册大块, 内部切分)
故障: QP 错误 → 重建 QP + 重登记 MR → 幂等重试
```

### 6. 拓展知识

RC/UD/DC 传输类型、RoCE 与无损网络、PFC 与 ECN、通信库的连接管理。

### 7. 常见追问及回答要点

- **QP 为什么会有平方级增长？** 全连接下每对 rank 一个 QP，连接数随规模平方增长。
- **MR 的代价在哪？** 注册与固定内存、页表，不是句柄本身。
- **QP 坏了怎么办？** 检测错误态，重建并重登记，重试要幂等。

### 8. 易错点与反例

- 全连接建 QP 导致资源耗尽。
- 频繁注册与注销 MR 带来开销。
- 故障后不清理半重建状态导致重复提交。

### 9. 实践与验证

估算一定 rank 数下的 QP/CQ/MR 与固定内存需求；注入 QP 故障验证重建与幂等重试。[P-待补充]

### 10. 评分标准

- 合格：说清三类资源的作用与限制。
- 良好：给出共享与池化的容量规划思路。
- 优秀：能把故障恢复、幂等重建与故障域隔离讲成完整方案。

## A015. Paged KV Cache allocator 如何设计以支撑高并发服务？

- 难度：高级
- 知识域：K06（LLM 推理与 KV Cache）
- 题型：系统设计
- 面试频率：高频
- 前置知识：KV cache、注意力机制、分页与引用计数
- 关联题目：A016, A004
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

LLM 推理的 KV cache 随序列长度动态增长，若按最大长度预分配会严重浪费显存。分页方案把 KV 切成固定大小的块，按需分配并维护逻辑到物理的映射，从而提升并发与显存利用率。

### 2. 问题分析

要点包括块大小取舍（大块减少映射开销但增加内部碎片，小块反之）、块表与映射管理、块的分配与回收与换出、与注意力 kernel 的配合（需按块表读取），以及前缀共享（多请求共享相同前缀的块）。

### 3. 具体答案

- 分块：把每层的 KV 按固定 token 数切成物理块，序列由多个块组成，维护 block table。
- 分配器：维护空闲块池，请求增长时按需分配，结束或回收时归还；留少量预留减少分配失败。
- 前缀共享：相同前缀的块用引用计数共享，减少重复 KV，例如系统提示词与 few-shot。
- 换出与换入：显存紧张时把冷块换到 host 或下层存储，按访问热度决定。
- kernel 配合：注意力按 block table 收集逻辑块，支持不连续的物理布局。
- 容量：并发上限近似由可用块数除以每请求平均块数决定，块越大内部浪费越多。

核心决策是块大小与预留量决定并发与浪费的平衡，前缀共享决定实际效率。

### 4. 技术洞察

- 块越小内部碎片越小，但映射与 kernel 开销越大，存在与 kernel 实现相关的甜点。
- 前缀共享对长系统提示场景收益巨大，但需要内容寻址或哈希匹配。
- 换出能把并发做大，但换入换出的带宽成本可能拖慢 P99。

### 5. 图文说明

```text
请求 A: 逻辑块 [b0 b1 b2] → block table → 物理块 [P7 P2 P5]
请求 B: 前缀相同 → 共享 P7 P2, 新增 P9
空闲池: [P3 P4 P8 ...]  ← 按需分配/回收, 紧张时换出冷块
```

### 6. 拓展知识

分页注意力、前缀缓存与哈希、KV 量化、换出到 CPU 或 NVMe、块大小对 kernel 的影响。

### 7. 常见追问及回答要点

- **块大小怎么定？** 在 kernel 开销与内部碎片之间取平衡，通常与硬件访存粒度相关。
- **怎么提升并发？** 前缀共享减少块占用，换出释放显存，提高可用块数。
- **换出会影响延迟吗？** 会，换入换出消耗带宽，只有冷块才值得换。

### 8. 易错点与反例

- 按最大长度预分配导致浪费。
- 忽略前缀共享。
- 块太小导致 kernel 与映射开销上升。

### 9. 实践与验证

模拟不同块大小与前缀共享率，测量并发上限、显存利用率与端到端延迟。[P-待补充]

### 10. 评分标准

- 合格：说清分页与 block table 的作用。
- 良好：说明块大小取舍与前缀共享。
- 优秀：能把换出、kernel 配合与容量估算整合成完整设计。

## A016. continuous batching 的调度如何兼顾吞吐与 P99？

- 难度：高级
- 知识域：K06（LLM 推理与 KV Cache）
- 题型：系统设计
- 面试频率：高频
- 前置知识：连续批处理、prefill 与 decode、排队与分位数
- 关联题目：A015, A008
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

连续批处理让新请求在旧请求未结束时即可加入批次，动态拼批以提高设备利用率。它显著提升吞吐，但若调度不当，会让个别长请求或新请求拖高尾部延迟。

### 2. 问题分析

要点包括批次在每步动态重组、长度不一的请求混批带来负载不均、新请求加入可能抬高高优先级请求的等待，以及 prefill 与 decode 混批时的资源竞争。目标是在吞吐与 P99 之间找到调度策略。

### 3. 具体答案

- 动态组批：每步根据排队与新到达重批，已完成的请求退出，新请求补入。
- 排序与准入：按优先级或截止时间排序，给短请求或高优先级请求优先；对长请求做隔离或限流。
- prefill 与 decode 混批：把 prefill 分块（chunked prefill）与 decode 交错，避免长 prefill 阻塞 decode 造成首 token 与每 token 延迟抖动。
- 上限控制：限制 batch token 总数与并发请求数，超限排队而非无限扩张，保护尾延迟。
- 公平：避免饥饿，给长时间等待的请求保底机会。
- 观测：按批次记录排队时间与每请求的 TTFT、TPOT 分位数，指导参数。

核心决策是用排序与准入加上批次上限把尾部请求隔离，用 chunked prefill 平滑 prefill 对 decode 的冲击。

### 4. 技术洞察

- 吞吐来自更大更满的批次，P99 来自排队与负载不均，二者常常冲突。
- prefill 是批次内的长尾，分块是解耦关键。
- 批次上限既是吞吐旋钮，也是尾延迟保护。

### 5. 图文说明

```text
t0: [req1 decode][req2 decode] + 新 req3 prefill(chunked)
t1: req1 done → 移除; req3 decode 加入; req4 准入
批次上限: token 预算 / 并发数  → 超限排队
```

### 6. 拓展知识

调度器对批次的取舍、chunked prefill、优先级与抢占、SLO 感知调度、饥饿避免。

### 7. 常见追问及回答要点

- **连续批处理为何提升吞吐？** 减少设备空闲，让每步批次更满。
- **P99 怎么被拖高？** 长请求或大 prefill 占用批次，导致其它请求排队。
- **怎么兼顾两者？** 排序与准入加批次上限，再配合 prefill 分块。

### 8. 易错点与反例

- 无上限扩批导致尾延迟失控。
- 让长 prefill 阻塞所有 decode。
- 忽略饥饿，低优先级请求长期得不到调度。

### 9. 实践与验证

在混合长度负载下对比不同排序与批次上限的吞吐与 P99，观察 chunked prefill 的影响。[P-待补充]

### 10. 评分标准

- 合格：说清连续批处理的基本机制。
- 良好：指出吞吐与 P99 的冲突来源。
- 优秀：能把排序、批次上限、prefill 分块与公平性组织成完整调度策略。

## A017. 拓扑感知与 NUMA 如何影响集群通信容量规划？

- 难度：高级
- 知识域：K07（服务端调度与稳定性）
- 题型：系统设计
- 面试频率：中
- 前置知识：NUMA、网络拓扑、集合通信容量
- 关联题目：A014, A018
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

集群里设备、网卡、CPU 内存分布在不同的 NUMA 节点与交换层级上。跨 NUMA 或跨交换机的通信带宽更低、延迟更高。容量规划若不考虑拓扑，会高估可用带宽或低估同步成本。

### 2. 问题分析

要点包括拓扑层次（设备内、同 NUMA、跨 NUMA、跨交换机），每层带宽与延迟不同；NUMA 节点的内存本地性影响 host 中转与固定内存；网卡亲和性决定数据是否走远路。规划必须按最紧的链路估算，而不是按标称带宽。

### 3. 具体答案

- 拓扑建模：把设备、网卡、CPU 插槽、交换机建成层次图，标注每层的带宽与延迟。
- 亲和绑定：进程与线程绑到本地 NUMA 与就近网卡，避免跨节点访存与远路通信。
- 容量按瓶颈算：集群聚合通信带宽受限于最窄链路与共享交换机，不能简单相加。
- 分层通信：优先在近层做局部归约，再跨层聚合，减少远路流量。
- 超额订阅：交换机的超额订阅会放大拥塞，规划要留带宽余量。
- 观测：按链路统计利用率与排队，识别热点链路。

核心决策是以拓扑层次和最窄链路为约束做容量估算，并用亲和绑定让流量走最短路径。

### 4. 技术洞察

- 忽略 NUMA 会把 host 中转变成跨节点访存，代价被低估。
- 交换机超额订阅是聚合带宽的隐藏上限。
- 分层通信能显著减少跨层流量。

### 5. 图文说明

```text
[Device0|NIC0|CPU0]  [Device1|NIC1|CPU1]
        └── NUMA0 ──┐  ┌── NUMA1
                     switch (超额订阅 N:1)
        └────────────┴──┘
就近: Device0-NIC0-CPU0;  远路: Device0→NUMA1 (额外延迟)
```

### 6. 拓展知识

设备互联与 PCIe 拓扑、GPUDirect RDMA、NUMA 绑定实践、fat-tree 与龙型拓扑、超额订阅比。

### 7. 常见追问及回答要点

- **为什么聚合带宽不能简单相加？** 共享交换机与超额订阅使最窄链路成为上限。
- **NUMA 如何影响通信？** 跨节点访存与远路网卡都会增加延迟、降低带宽。
- **怎么减少跨层流量？** 分层做局部归约再跨层聚合。

### 8. 易错点与反例

- 忽略超额订阅高估带宽。
- 不做 NUMA 与网卡亲和绑定。
- 按本地带宽线性外推集群容量。

### 9. 实践与验证

采集实际拓扑与链路利用率，把设备与网卡就近绑定前后对比跨节点通信带宽。[P-待补充]

### 10. 评分标准

- 合格：说清拓扑层次对通信的影响。
- 良好：指出超额订阅与亲和绑定的作用。
- 优秀：能把分层通信、最窄链路估算与拓扑建模整合成容量规划方法。

## A018. 如何设计性能模型与实验来支撑容量规划决策？

- 难度：高级
- 知识域：K08（性能测量与可观测性）
- 题型：系统设计
- 面试频率：中高
- 前置知识：roofline 直觉、缩放实验、分位数统计
- 关联题目：A016, A017
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

容量规划要回答需要多少设备、能承载多少负载、瓶颈在哪。这需要能预测性能的模型与能验证假设的实验，而不是拍脑袋或用单点跑分。模型给出方向，实验校正偏差，两者缺一不可。

### 2. 问题分析

模型要抓住主导项（计算、访存、通信、排队），实验要能分离变量并验证模型预测；容量决策还要考虑峰值、利用率目标与故障余量。核心是把"预测"与"验证"接成闭环，而不是各自为政。

### 3. 具体答案

- 建立模型：按 roofline 思路拆解每类负载的计算量与访存量，估算理论下界，把通信与排队作为附加项。
- 关键指标：每设备吞吐、资源利用率、P50 与 P99 延迟、显存与带宽占用。
- 实验设计：固定输入与配置做缩放实验（batch、并发、序列长度、设备数），观察各指标随规模的变化，找饱和拐点。
- 校准与验证：用实测数据拟合模型参数，再用未参与拟合的点验证预测误差。
- 容量推算：目标负载除以单设备有效吞吐得到设备数，再叠加峰值与故障余量；用排队模型估算满足 SLO 的并发上限。
- 敏感性分析：识别哪些参数（带宽、命中率、通信占比）对结果最敏感，优先优化。

核心决策是先分清瓶颈资源，再按瓶颈做容量换算，模型与实验互相校正，最后用敏感性分析定优先级。

### 4. 技术洞察

- 容量往往由单一瓶颈资源决定，找到它比细化其它项更有价值。
- 用单点跑分外推会忽略拐点，缩放实验才能暴露饱和。
- 模型的价值在于给出数量级与瓶颈，而非精确到小数点。

### 5. 图文说明

```text
负载参数(batch/并发/序列) → 模型(计算/访存/通信/排队) → 预测吞吐/延迟
        ↑                                              ↓
        └──── 缩放实验校准 ← 实测指标(P50/P99/利用率) ──┘
容量 = 目标负载 / 单设备有效吞吐 × (1 + 峰值与故障余量)
```

### 6. 拓展知识

roofline 模型、Little 定律、可扩展性模型、敏感性分析、压测方法论与拐点识别。

### 7. 常见追问及回答要点

- **模型要多精确？** 给出量级与瓶颈即可，用于决策而非替代实测。
- **怎么找拐点？** 做缩放实验，观察吞吐随规模增长何时饱和。
- **余量怎么留？** 按峰谷比与故障域大小，结合 SLO 定冗余。

### 8. 易错点与反例

- 用单点跑分外推容量。
- 模型与实验脱节，不做校正。
- 忽略峰值与故障余量。

### 9. 实践与验证

对一类负载做 batch、并发、设备数缩放实验，拟合吞吐模型并在留出点上验证预测误差，据此推算设备数。[P-待补充]

### 10. 评分标准

- 合格：说清模型与实验各自的作用。
- 良好：给出缩放实验、校准与容量换算的流程。
- 优秀：能把瓶颈识别、敏感性分析与余量设计整合成完整决策方法。
