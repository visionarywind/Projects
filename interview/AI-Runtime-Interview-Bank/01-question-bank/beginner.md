# 入门级题目

> 面向 AI Runtime / 设备软件 / 显存 / 异步执行方向的入门概念与机制辨析。答案为通用机制模型；个人项目细节标注为 [P-待补充]。

## B001. Framework、Runtime、Driver、Device 各层分别负责什么？

- 难度：入门级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：C++/Python 调用栈、设备执行模型、用户态与内核态
- 关联题目：B003, B009
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

一个 device 调用（launch kernel、拷贝、集合通信）通常跨越四个边界：上层框架、用户态 runtime、用户态驱动（UMD）/内核驱动（KMD）、以及设备硬件。弄清每层拥有什么状态、负责什么转换，是后面所有异步、内存、错误处理问题的地基。

### 2. 问题分析

关键是把「谁持有状态」「谁做转换」「谁保证完成」分开：框架管 Tensor 和算子语义，runtime 管执行队列与内存池，驱动管通道、上下文和硬件提交，设备真正执行。混层会直接导致「以为同步了其实没有」「free 之后设备还在用」这类问题。

### 3. 具体答案

- Framework：把用户语义翻译成算子/张量操作，负责 shape/dtype/device 检查、autograd、图构建。它不知道队列深度，也不保证设备完成。
- Runtime：管理执行上下文、stream/event、内存分配器，把算子变成具体的 device 调用并提交到队列。它决定异步语义和缓存复用。
- Driver（UMD/KMD）：把提交的命令下发到硬件通道，管理句柄、地址映射、调度；KMD 还负责中断和错误上报。
- Device：按队列真正执行计算与访存，完成后通过中断/信号让上层可观测。

一句话：越往上越接近「语义」，越往下越接近「执行」；异步边界的核心是「函数返回只代表到某一层为止」。

### 4. 技术洞察

- 层级越多，越容易把中间层的「已受理」误当成「已完成」。
- 性能问题要分层归因：排队延迟在 runtime/驱动，执行延迟在设备，不能只看端到端。
- 错误传播是反向的：设备错误要经驱动、runtime 才能被框架感知，因此异步错误常在很晚才暴露。

### 5. 图文说明

```text
用户代码 / Framework        ← 语义、Tensor、Shape 检查
        │ 算子调用
   Runtime（队列/内存池）    ← 异步提交、缓存复用
        │ 命令下发
   Driver (UMD / KMD)       ← 句柄、地址映射、中断
        │
   Device                    ← 真正执行、完成通知
```

### 6. 拓展知识

分层模型可以延伸到「可插拔后端」：统一 runtime 抽象把不同厂商差异压在适配层；也可以延伸到 ABI 兼容，即层间二进制接口如何演进而不破坏已编译的算子。

### 7. 常见追问及回答要点

- **框架里那次调用是同步的吗？** 取决于具体 API；多数 launch 是异步提交，返回不代表完成。
- **为什么错误在很晚才出现？** 设备错误要经驱动异步上报，join 点才被检查。
- **性能瓶颈怎么定位到层？** 用 trace 分段量排队/提交/执行/同步时间。

### 8. 易错点与反例

- 说「runtime 负责计算」——计算在设备。
- 把 driver 与 runtime 混为一谈，忽略句柄/地址映射这层。
- 认为框架层能保证设备完成。

### 9. 实践与验证

写一个最小程序：提交一个长 kernel 后立刻打印时间戳并释放资源，观察是否崩溃/数值错误；用 nvidia-smi/时间分解确认「返回」与「完成」之间的差距。

### 10. 评分标准

- 合格：能区分四层职责。
- 良好：说出异步边界与错误反向传播。
- 优秀：能解释分层如何影响性能归因和可插拔后端设计。

## B002. context、device、stream、module 这些执行对象之间是什么关系？

- 难度：入门级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：设备执行模型、句柄与资源生命周期、CUDA/HIP 的上下文概念
- 关联题目：B001, B007
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

device 是物理加速卡，context 是进程与设备之间建立的一套资源域，stream 是 context 内的有序命令队列，module 是加载进 context 的代码镜像。面试里常把「一颗卡」和「一个上下文」混着说，才会在跨进程、跨流时踩坑。

### 2. 问题分析

要区分四者是「硬件实体」「资源归属域」「执行顺序域」「代码实体」四种不同性质的对象。理清包含关系和句柄有效期，才能解释为什么跨 context 用指针会失效、为什么 stream 不能跨卡。

### 3. 具体答案

- device：物理设备，有唯一编号，负责真正计算；多卡时先选 device 才有后续对象。
- context：绑定到某个 device 的资源容器，拥有地址空间、分配器、module 与 stream。同一 device 上可以有多个 context，它们之间显存地址和句柄互不相通。runtime 还会维护一个隐式的 primary context，方便默认使用与跨进程共享。
- stream：context 内的一条命令队列，同一条 stream 上的命令按提交顺序执行；stream 归属某个 context/device，不能跨卡。
- module：加载进 context 的设备代码镜像，内含若干可 launch 的 kernel function。

包含关系是 device ⊃ context ⊃ {stream, module, 显存分配}。kernel 从 module 里取出句柄，被 launch 到某条 stream 上，读写 context 内分配的 buffer。

### 4. 技术洞察

- 任何 device 侧指针、event、module 句柄都只在创建它的 context 内有效，跨 context 直接使用属于未定义行为。
- 一个 device 上多 context 时，显存不共享、同步原语不互通；卡间访问还要显式启用对等能力。
- current context 是线程局部状态：同一进程的不同线程可能处于不同 context。

### 5. 图文说明

```text
Device (加速卡 #0)
 └─ Context A ── 地址空间 / 分配器 / module 表
      ├─ Stream 0 ── 有序队列: kernel, memcpy, event
      ├─ Stream 1
      └─ Module(s) ── kernel f0, f1 ...（已加载的代码）
```

### 6. 拓展知识

可延伸到位线程/进程的 current context 语义、多进程共享 primary context 与 IPC、cubin 与 JIT 的模块加载差异、stream 优先级对调度的影响。

### 7. 常见追问及回答要点

- **stream 是全局的吗？** 不是，它属于某个 context/device；默认流也是 context 级的。
- **同一块 buffer 能换 context 用吗？** 不能直接使用，需要跨进程共享机制重新映射。
- **module 和 kernel 什么区别？** module 是代码容器，kernel 是其中可被 launch 的函数。

### 8. 易错点与反例

- 把 device 当成只有一个 context。
- 认为 stream 可以跨卡复用。
- 以为 module 是全局可见的。

### 9. 实践与验证

在同一 device 上建立两个 context，各自分配 buffer，尝试互相访问，观察报错或异常；再打印当前 context/stream，验证线程局部性。

### 10. 评分标准

- 合格：说清四者的层级与包含关系。
- 良好：指出 context 是资源域、stream 是顺序域。
- 优秀：解释跨 context 句柄失效、primary context 与线程局部性。

## B003. 同步 API 与异步 API 的「完成语义」有什么区别？

- 难度：入门级
- 知识域：K01（Runtime 分层与设备边界）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B001、设备命令队列、host/device 内存模型
- 关联题目：B001, B007, B009
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

「函数返回」在设备编程里有好几层含义：命令被接受、命令进入队列、设备执行完成、结果对 host 可见。同步与异步 API 的差别，就落在返回时停在哪一层。

### 2. 问题分析

核心区分是「提交完成」与「执行完成」。同步 API 的返回一般等价于「执行已完成且结果可见」；异步 API 的返回只表示「已提交」，不代表设备做完，也不代表数据可读。

### 3. 具体答案

- 同步 API：调用返回时保证该操作在设备上已完成，host 后续读取能看到结果。内部通常阻塞或自旋等待完成信号。要注意同步范围，可能只覆盖「本操作」，也可能覆盖「此前默认流上的全部操作」。
- 异步 API：调用返回仅表示命令被接受，执行可能尚未开始。此时 host 不能立即读取结果，也不能释放被引用的资源，除非插入同步点，如 device/stream synchronize、event wait，或一次同步的 D2H 拷贝。
- 完成对象不同：同步的「完成」是设备执行完成；异步的「完成」是提交完成，两者差着一次设备执行。
- 异步不等于乱序：同一条 stream 内部依然按提交顺序执行，异步只是让 host 不必等设备。

### 4. 技术洞察

- 被异步操作引用的 host/device 内存，在完成被确认前都不能失效。
- 同步是用确定性和流水线效率换来的：host 阻塞等待，牺牲了「提交下一个任务掩盖延迟」的机会。
- 异步的收益来自 host 持续提交，把提交、传输与计算的延迟叠起来。

### 5. 图文说明

```text
同步: [host 提交]→[设备执行]══[host 阻塞等待]══[返回, 已可见]
异步: [host 提交→立即返回]   [设备后台执行......]
                              └─ 需 synchronize/event 才确认可见
```

### 6. 拓展知识

可接到 pinned memory 与异步拷贝、stream 顺序语义、图捕获对同步调用的限制、以及设备错误为何常在很晚才被上报。

### 7. 常见追问及回答要点

- **异步返回后能立刻 free 输入吗？** 通常不能，要等设备用完；缓存分配器靠 stream 记录来延迟复用。
- **同步一定比异步慢吗？** 常如此，因为它串行化并等待，但推理简单、易保证正确。
- **device synchronize 与 stream synchronize 区别？** 前者等所有 stream，后者只等指定 stream。

### 8. 易错点与反例

- 把异步提交当成执行完成。
- 认为「函数没报错」就等于「设备执行成功」。
- 用 sleep 或经验时延代替正确的同步原语。

### 9. 实践与验证

提交一个异步 kernel 后立即做同步 D2H 拷贝，对比先用 deviceSynchronize 再拷贝的时序与数值，观察哪些读取会拿到未完成数据。

### 10. 评分标准

- 合格：区分「返回」与「完成」。
- 良好：说明内存可见性与资源生命周期约束。
- 优秀：把同步语义与流水线性能、错误延迟暴露联系起来。

## B004. allocated、reserved、free、cached 分别代表什么？

- 难度：入门级
- 知识域：K02（显存与内存管理）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：显存分配器分层、驱动显存记账、B003 的异步语义
- 关联题目：B005, B006
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

同一时刻，驱动、分配器、框架各有一套显存账本，所以 nvidia-smi 的数字和框架统计常对不上。四个词分别属于不同账本，混用就会得出「显存泄漏」的错误结论。

### 2. 问题分析

关键是分清「谁在记账」：分配器向驱动申请得到 reserved，再把自己的份额切成 allocated 和 cached；free 则要在「驱动角度」和「分配器池内」两个语境里分辨。

### 3. 具体答案

- allocated：分配器已经交给上层 tensor 使用、尚未归还池的字节数，反映「正在用」的显存。
- reserved：分配器已经向驱动申请到的总量（各段之和），只有释放整段时才归还给驱动。
- free：有两种含义。驱动视角是设备剩余可用显存；分配器视角是池内当前可复用的空闲块。要按上下文区分。
- cached：reserved 中当前未被 allocated 的部分，也就是池里缓存下来备用的块。

关系式：allocated ≤ reserved ≤ 设备总显存；cached = reserved − allocated；驱动视角的 free 大致等于 总量 − reserved − 其它进程占用。

### 4. 技术洞察

- allocated ≤ reserved 在同一个分配器内恒成立，是查账的第一条约束。
- cached 偏高不等于泄漏，只说明有可复用但未使用的缓存；真正的泄漏是 allocated 持续单调上涨且不回落。
- reserved 只增不减会挤压同机其它进程或框架的可用显存。

### 5. 图文说明

```text
设备总显存
 ├─ reserved（分配器已向驱动申请）
 │    ├─ allocated（tensor 正在用）
 │    └─ cached   （池中空闲，可复用）
 └─ 驱动侧 free（尚未被本分配器申请）
```

### 6. 拓展知识

可连接到框架的 memory_stats 字段、expandable segments、每进程显存配额、OOM 时应先看 allocated 还是 reserved、以及多进程共享设备时的份额划分。

### 7. 常见追问及回答要点

- **reserved 很高是泄漏吗？** 不一定，很可能只是 cached。
- **free 总量够为何还 OOM？** 可能没有足够大的连续块，见碎片问题。
- **怎么把 reserved 降下来？** 调用清空缓存，或重启/降低 batch，让分配器释放未用整段。

### 8. 易错点与反例

- 把 reserved 当成「已用显存」。
- 把 cached 当成泄漏。
- 只看 nvidia-smi 判断框架到底用了多少。

### 9. 实践与验证

跑一个小模型，分别打印 allocated、reserved 与 nvidia-smi；再做分配-释放循环，观察 cached 先涨后稳、allocated 回落的现象。

### 10. 评分标准

- 合格：说清四个词各自含义。
- 良好：给出关系式并能判读 OOM。
- 优秀：区分碎片与泄漏，并用曲线定位真实占用。

## B005. 显存碎片分几种，分别在什么场景出现？

- 难度：入门级
- 知识域：K02（显存与内存管理）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B004、分配器的段/块概念
- 关联题目：B004, B006
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

显存由分配器按段和块管理，动态分配释放会让空闲区域变得零散。碎片最直接的后果是「总量够，却分不出请求」。弄清碎片的种类，才能判断某次 OOM 是否可避免。

### 2. 问题分析

需要区分「外部碎片」和「内部碎片」，再补上地址空间/对齐这一类。判断分配能否成功，看的是最大连续空闲块，而不是空闲总和。

### 3. 具体答案

- 外部碎片：空闲块被已占用块切成若干小块，最大连续块小于请求。典型场景是变长序列、activation 反复分配释放、KV cache 随长度动态增长。
- 内部碎片：分配的块粒度或对齐取整后大于实际请求，块尾被浪费。典型场景是小 tensor 很多、按尺寸分桶的分配器。
- 地址空间/对齐碎片：即使物理上够，虚拟地址不连续或对齐不满足也会分配失败，常见于大页与大块请求。

### 4. 技术洞察

- 分配成功的条件是「最大空闲块 ≥ 请求大小且对齐满足」，仅凭空闲总和判断会误判。
- 碎片程度随 workload 的时序变化，固定 shape 能明显降低碎片。
- 常见缓解是池化与分桶、合并相邻空闲块、预分配、使用可扩展段、在图执行时复用固定地址。

### 5. 图文说明

```text
[used][free 8][used][free 8][used]   请求 16 → 失败（无连续 16）
[used][free 8 ][free 8 ][used]       合并后 16 → 成功
```

### 6. 拓展知识

可连接到 best-fit/first-fit 策略、块的切分与合并、size-class 划分、可扩展段选项，以及推理里 KV 的分页管理。

### 7. 常见追问及回答要点

- **为什么定长 shape 训练更稳？** 请求尺寸一致，池化命中率高，碎片自然少。
- **碎片能完全消除吗？** 不能，只能通过池化、定长、预分配把影响压小。
- **怎么观测碎片？** 看最大可分配块与分配失败时仍剩多少空闲总量。

### 8. 易错点与反例

- 把缓存当碎片。
- 认为空闲总量大就不会 OOM。
- 忽略对齐要求，漏掉一类失败原因。

### 9. 实践与验证

交错分配多种大小再释放其中一部分，观察能否复用到新请求；再换成固定 shape 循环，对比可分配最大块的变化。

### 10. 评分标准

- 合格：分清内部与外部碎片。
- 良好：说明各自出现场景与缓解手段。
- 优秀：联系分配器策略给 OOM 做归因。

## B006. caching allocator 为什么保留 reserved 而不还给驱动？

- 难度：入门级
- 知识域：K02（显存与内存管理）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B004、B005、驱动分配的开销
- 关联题目：B004, B005
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

向驱动申请/释放显存是重操作，可能触发设备同步和页表映射，且粒度较大。训练或推理每一步有成百上千次分配释放，如果每次都直连驱动，开销会主导整体耗时。

### 2. 问题分析

问题问的是设计动机：为什么 free 之后不马上归还驱动。答案围绕分配延迟、同步代价、复用率和地址稳定性展开。

### 3. 具体答案

- 驱动分配很慢，还可能同步设备；高频分配若直连驱动会拖垮每步耗时。
- 保留 reserved 让同尺寸请求直接从池里复用，只需微秒级操作，且不触发设备同步。
- 一旦释放给驱动，下次未必能拿回相同块，反复申请释放还会加剧碎片。
- 地址保持稳定，也便于图捕获与固定的中间复用。

代价是 reserved 不会自动还给系统，会占住显存、挤压同机其它负载，需要在长空闲或多租户时主动释放。

### 4. 技术洞察

- 这是「空间换时间」：分配器里的 free 是逻辑可用，不是驱动可见的释放。
- 回收受 stream 语义约束，正在被某条 stream 使用的块，要等该 stream 到达同步点才能重新入池。
- reserved 的峰值通常等于历史峰值，之后趋于平稳，除非工作集持续变大。

### 5. 图文说明

```text
请求 → 池中有空闲块? ──是──→ 直接复用（快，无驱动调用）
                     └─否──→ 向驱动申请（慢，可能同步）→ 变成 reserved
free → 块回到池（reserved 不减）→ 下轮请求再次复用
```

### 6. 拓展知识

可延伸到清空缓存、每进程显存配额、可扩展段、多租户显存共享，以及 stream 有序分配器这一类更贴近硬件语义的方案。

### 7. 常见追问及回答要点

- **那它会不会一直涨？** 涨到历史峰值后通常稳住，除非工作集持续增大。
- **什么时候该归还？** 长空闲、多租户、显存紧张时主动清空未用段。
- **保留会影响正确性吗？** 不会，只是容量占用；真正影响正确性的是错误的提前释放。

### 8. 易错点与反例

- 说 caching allocator 每次都直接向驱动释放。
- 把 reserved 偏高当成 bug。
- 以为清空缓存会把正在用的数据也抹掉。

### 9. 实践与验证

循环迭代打印 reserved，观察首次申请后 reserved 稳定、不再随每步增长；再调用清空缓存，看 reserved 是否回落。

### 10. 评分标准

- 合格：说出「分配慢、复用快」。
- 良好：补充同步代价与碎片考量。
- 优秀：讲清空间换时间以及多租户下的释放权衡。

## B007. 同一 stream 内的执行顺序是如何保证的？

- 难度：入门级
- 知识域：K03（异步执行与同步原语）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B002、B003、命令队列模型
- 关联题目：B002, B008
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

stream 是一条命令队列，同一条 stream 上先后提交的 kernel、拷贝、event 会顺序执行。这个顺序是异步编程里最基础的确定性来源。

### 2. 问题分析

要回答的是「顺序由什么保证」。它不是靠 host 阻塞，而是靠队列的先进先出和设备的顺序调度：提交顺序直接决定执行顺序。同时要分清「同 stream 有序」与「跨 stream 无序」。

### 3. 具体答案

- runtime 把同一 stream 上的命令按提交顺序放入队列，设备按队列顺序取出执行，前一个命令完成之前，同 stream 的下一个不会开始。
- 因此同 stream 内「A 写 buffer、B 读 buffer」天然具有先后关系，不需要额外 event。
- 顺序由队列语义保证，host 提交的先后就是设备执行的先后，host 全程不必阻塞。
- 跨 stream 之间没有这层保证，必须用 event 显式建立依赖。

### 4. 技术洞察

- 同 stream 内命令是全序的，跨 stream 之间是无序的，这是判断要不要加同步的分界线。
- 顺序不等于并行：单 stream 牺牲并发换简单；要并发就得多 stream。
- 默认流有特殊语义，在某些模式下会与其它流隐式同步，容易成为隐性串行化的来源。

### 5. 图文说明

```text
Stream0: [K1]→[K2]→[K3]     严格顺序, K2 等 K1 完成
Stream1: [Kx]──────[Ky]     与 Stream0 之间无序
```

### 6. 拓展知识

可连接到传统默认流与每线程默认流的差异、stream 优先级、以及图中显式依赖节点的表达方式。

### 7. 常见追问及回答要点

- **同 stream 顺序是硬件保证的吗？** 是队列与调度语义保证的，由提交顺序决定。
- **多 stream 共享 buffer 会怎样？** 不加同步会出现数据竞争或读到旧值。
- **默认流为什么特殊？** 某些模式下它会与所有阻塞流隐式同步。

### 8. 易错点与反例

- 以为不同 stream 之间也有序。
- 忽视默认流的隐式同步。
- 跨 stream 共享 buffer 却不加 event。

### 9. 实践与验证

两条 stream 交错 launch，对同一 buffer 分别读和写，分别在不加与加 event 的情况下运行，比较结果是否稳定正确。

### 10. 评分标准

- 合格：说清同 stream 的 FIFO 顺序。
- 良好：说明顺序与并行的取舍。
- 优秀：讲清默认流语义以及跨流同步的必要性。

## B008. 跨 stream 如何表达依赖？event 的 record/wait 做了什么？

- 难度：入门级
- 知识域：K03（异步执行与同步原语）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B007、B003、happens-before 概念
- 关联题目：B007, B003
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

多 stream 并行时，有些点必须建立先后关系，比如一个 stream 产出的数据要被另一个 stream 消费。event 是最轻量的同步对象，用来跨 stream 传递进度而不必全局阻塞。

### 2. 问题分析

问题分两半：跨 stream 依赖怎么表达，以及 event 的 record/wait 各自做了什么。核心是理解 event 表达的是「某条 stream 的进度点」，它只传递顺序，不搬运数据。

### 3. 具体答案

- event 是一个设备侧的时间/进度标记对象。
- record：把 event 插入某条 stream 的队列，表示「当该 stream 执行到此点之前的全部工作完成时，event 变为已触发」。
- wait：让另一条 stream 在此处暂停，直到该 event 被触发为止，从而建立跨 stream 的先后关系。
- record 和 wait 都是异步的，不阻塞 host，只在设备队列上制造依赖。
- 若要让 host 等待，用 event synchronize 阻塞 host 直到 event 触发，或定期 query 查询状态。

### 4. 技术洞察

- event 传递的是顺序，不是数据本身；一旦顺序建立，被保护 buffer 的可见性也随 happens-before 一起成立。
- 它是单向依赖，比全局 barrier 轻，避免了把所有流串成一条。
- 带计时的 event 还能测量两个标记之间的设备耗时。

### 5. 图文说明

```text
Stream0: [K1]→[K2]→record(E)─┐
                             │ E 在 K2 完成后触发
Stream1:        wait(E)→[K3]─┘  K3 等 E 触发才开始
```

### 6. 拓展知识

可延伸到 event 的标志位（是否计时、是否阻塞同步）、耗时查询、跨进程共享 event，以及图中依赖节点的刻画。

### 7. 常见追问及回答要点

- **record 后 host 能立刻读到耗时吗？** 不能，要先 synchronize 等它触发。
- **wait 会阻塞 host 吗？** 不会，只在设备队列上排依赖。
- **event 能替代数据可见性保证吗？** 建立顺序即建立可见性，因为存在 happens-before。

### 8. 易错点与反例

- record 之后立即查询耗时或释放资源。
- 把 wait 当成 host 阻塞。
- 跨 stream 共享 buffer 却忘记 record/wait。

### 9. 实践与验证

两条 stream，一条写、一条读，用 event 串联验证结果正确；再用计时 event 测两标记间耗时，与 wall clock 对比其含义差异。

### 10. 评分标准

- 合格：说明 record/wait 的语义。
- 良好：讲清 happens-before 与异步不阻塞。
- 优秀：联系计时 event 和图依赖的表达能力。

## B009. 调用 device API 后立刻释放 buffer 为什么可能出错？

- 难度：入门级
- 知识域：K03（异步执行与同步原语）
- 题型：故障排查
- 面试频率：高频
- 前置知识：B003、B007、B008、分配器的 stream 语义
- 关联题目：B003, B008
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

常见的诡异 bug：提交一个异步操作后立刻释放内存，程序要么崩溃，要么结果偶发错误。根因是异步调用返回后，设备可能还在用这块内存。

### 2. 问题分析

要分两种释放对象来看：host 侧缓冲区被释放会造成悬空指针，device 侧缓冲区被释放后地址可能被立刻复用，新老操作踩同一块显存。还要说明缓存分配器如何靠 stream 语义降低这种风险。

### 3. 具体答案

- host 侧：如果传入的是 host 缓冲区（pinned 或普通内存），异步传输期间 host 就把它释放，设备随后读到的是失效地址，导致数据损坏或崩溃。
- device 侧：如果把 device buffer 释放回池，分配器可能马上把同一地址分给新 tensor，而旧 kernel 尚未执行完，于是新旧操作写到同一块显存。
- 缓存分配器默认用 stream 语义缓解：块被释放时记录使用它的 stream，只有该 stream 到达新的同步点后才允许复用；若块被跨 stream 使用却没登记，仍会出错。
- 正确做法是在释放前对相关 stream 同步，或调用 record_stream 让分配器知道该块被哪些流使用，以延迟复用。

### 4. 技术洞察

- 异步访问在完成被确认前，其存储不能释放也不能复用。
- 这类错误常常延迟暴露且非确定，取决于 kernel 时长和分配时序，很难复现。
- stream 感知的释放是关键防护；跨流共享必须显式登记，否则防护失效。

### 5. 图文说明

```text
host:   launch(K, buf) 返回 ─→ free(buf)        ← 危险
device: ..............K 仍在读 buf..........
正确:   launch(K,buf) → synchronize / record_stream → free
```

### 6. 拓展知识

可延伸到 record_stream 的语义、stream 有序分配器的释放时机、pinned memory 的生命周期，以及图执行里固定地址带来的约束。

### 7. 常见追问及回答要点

- **为什么有时又没事？** kernel 恰好跑完或地址尚未被复用，属于运气而非正确。
- **怎么根治？** 让释放与使用处在同一 stream 语义内，或显式 event 同步。
- **record_stream 起什么作用？** 告知分配器该块被其它 stream 使用，从而延迟复用。

### 8. 易错点与反例

- 认为 free 之后设备会立即停用该地址。
- 依赖「跑得快就没问题」。
- 跨 stream 复用却不做登记。

### 9. 实践与验证

提交一个较长的 kernel 后立刻释放并复用 host pinned buffer，观察数值错乱；改成先 synchronize 再释放，验证恢复正常。

### 10. 评分标准

- 合格：指出异步未完成是根因。
- 良好：区分 host 与 device 两种释放路径。
- 优秀：讲清 record_stream 与 stream 有序分配的作用。

## B010. tensor 的 shape、dtype、stride、contiguous 各是什么含义？

- 难度：入门级
- 知识域：K04（张量与图执行）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：数组内存布局、行优先存储
- 关联题目：B011
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

tensor 本质是「一块内存 + 一套解释规则」。shape 和 dtype 定义逻辑结构，stride 把多维索引映射到内存偏移，contiguous 描述布局是否规整。

### 2. 问题分析

要点是区分逻辑形状与物理布局：两个 tensor 可以 shape 相同但布局不同。理解 stride 才能解释为什么转置常常不拷贝数据，以及为什么把非连续 tensor 送进某些 kernel 会触发隐式拷贝。

### 3. 具体答案

- shape：各维度的元素个数，如 (2, 3)，描述逻辑形状。
- dtype：元素类型与位宽（如 fp32、fp16、int8），决定每个元素占多少字节以及如何解释。
- stride：某一维索引加一时，内存地址前进的元素个数（或字节数，取决于约定）。行优先连续时，stride[i] 等于其后所有维度长度的乘积。
- contiguous：当遍历顺序对应内存地址单调连续、stride 满足行优先公式时，称为连续。转置、permute 往往只改 stride 不改数据，得到的是非连续视图；reshape 在无法用视图表达时会触发拷贝。

### 4. 技术洞察

- shape 相同不代表布局相同，真正决定访存模式的是 stride。
- 把非连续 tensor 送入要求连续的 kernel，框架会隐式拷贝，是常见性能陷阱。
- 广播可以用 stride 为 0 的维度来表达，即同一元素被重复读取。

### 5. 图文说明

```text
shape=(2,3), dtype=fp32, 连续时 stride=(3,1)
内存:  [a0 a1 a2 a3 a4 a5]
        row0^^^^^  row1^^^^^
转置后 shape=(3,2), stride=(1,3) → 非连续视图
```

### 6. 拓展知识

可延伸到 NCHW/NHWC 等内存格式、channels_last、memory_format 转换、广播的 stride=0 语义，以及 view 与 reshape 的区别。

### 7. 常见追问及回答要点

- **加 contiguous() 总是对的吗？** 不一定，它会拷贝，先确认内核是否支持非连续输入。
- **shape 一样就能直接运算吗？** 不一定，布局可能不同。
- **stride 的单位是什么？** 元素或字节，取决于框架约定，别混。

### 8. 易错点与反例

- 认为 shape 相同就是同一布局。
- 忽视隐式 contiguous 拷贝的开销。
- 把元素步长与字节步长混为一谈。

### 9. 实践与验证

创建 tensor，转置后打印 shape、stride、is_contiguous，比较内存指针与显式拷贝后的差异。

### 10. 评分标准

- 合格：解释四个概念。
- 良好：说明 stride 与连续性的关系。
- 优秀：讲清非连续导致的隐式拷贝与内存格式影响。

## B011. eager 模式与 graph 模式的执行流程有什么不同？

- 难度：入门级
- 知识域：K04（张量与图执行）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B010、B003、算子分派流程
- 关联题目：B010, B015
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

eager 模式逐个算子立即执行，graph 模式先把一段计算捕获成可重放的图再整体提交。两者的差别在于「何时确定执行计划」以及「每次执行的固定开销来自哪里」。

### 2. 问题分析

要对比执行流程、灵活性、开销来源和约束。graph 把大量小操作合并提交，减少 host 分派与 launch 开销，但要求执行序列和内存地址稳定。

### 3. 具体答案

- eager：每个算子即时由框架分派到 runtime，逐条 launch kernel。灵活、易调试、支持动态控制流，但每步都有分派、launch 和解释开销。
- graph：在捕获阶段记录一条设备命令序列（kernel、拷贝及其依赖），形成图；重放时一次性提交，减少 host 介入，并可做更优调度。
- graph 通常在捕获时就分配并固定中间 buffer（借助内存池），重放时复用同一地址。
- 动态 shape 或动态控制流需要重新捕获，或使用条件/循环节点表达。

### 4. 技术洞察

- graph 重放默认执行序列与内存地址稳定，一旦打破这个假设就会出错。
- 加速来自减少 CPU launch、减少同步、批量提交；对 CPU 受限的多小 kernel 场景收益大，对单个大 kernel 的 GPU 受限场景收益有限。
- 权衡是灵活性、可调试性对吞吐；捕获期间不允许非法的同步或分配。

### 5. 图文说明

```text
eager:  op1→launch  op2→launch  op3→launch   （每步 host 参与）
graph:  capture: [op1, op2, op3 + 依赖] → Graph
        replay : Graph.submit()              （一次提交）
```

### 6. 拓展知识

可延伸到图捕获/实例化/重放三阶段、条件与循环节点、通信与计算的重叠，以及编译器自动捕获图的方案。

### 7. 常见追问及回答要点

- **graph 一定更快吗？** 不一定，GPU 受限的大 kernel 场景收益有限。
- **graph 能处理动态 shape 吗？** 需要重捕获或使用条件节点。
- **捕获期能同步吗？** 一般不允许非法同步与分配，需使用图安全的分配器。

### 8. 易错点与反例

- 在捕获区内做 device synchronize。
- 假设 graph 自动支持任意动态控制流。
- 忽略地址固定带来的约束。

### 9. 实践与验证

同一个小模型分别用 eager 和 graph 循环执行，对比 host 时间与端到端时间，观察多小 kernel 场景下的收益差异。

### 10. 评分标准

- 合格：分清两种执行流程。
- 良好：说明捕获/重放与开销来源。
- 优秀：讲清固定地址约束与收益边界。

## B012. AllReduce 的语义是什么？它和 ReduceScatter + AllGather 是什么关系？

- 难度：入门级
- 知识域：K05（集合通信）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：数据并行梯度聚合、ring 算法直觉
- 关联题目：B007
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

数据并行训练每一步都要把各 rank 的梯度聚合起来，AllReduce 是最常用的集合通信原语。理解它和 ReduceScatter、AllGather 的关系，能解释为什么实际实现要拆成两个阶段。

### 2. 问题分析

问题包含两部分：AllReduce 的语义（每个 rank 都拿到全部归约结果），以及它与 ReduceScatter + AllGather 的等价关系。这个等价性是 ring allreduce 的算法基础。

### 3. 具体答案

- AllReduce：对 N 个 rank 的输入张量按元素做归约（sum、max 等），结果广播给所有 rank，因此每个 rank 得到相同的结果。
- ReduceScatter：先归约，再把结果切分，每个 rank 只保留其中一份分片。
- AllGather：把各 rank 的数据拼接起来，每个 rank 得到完整的拼接结果，不做归约。
- 关系：AllReduce 等价于 ReduceScatter + AllGather。先做 reduce-scatter 让每个 rank 持有一部分部分和，再 all-gather 把各分片拼回，使数据搬运更均衡，这正是 ring allreduce 的两阶段结构。

### 4. 技术洞察

- AllReduce 完成后各 rank 输出一致，这是数据并行正确性的前提。
- 分解的意义在于两个阶段各自带宽友好、便于与计算重叠，也是参数分片优化的基础。
- 拓扑与消息大小会改变实现：小消息偏向用树形降低延迟，大消息偏向用环形追求带宽。

### 5. 图文说明

```text
rank0: A   rank1: B   rank2: C
AllReduce(sum)  →  每个 rank: A+B+C
ReduceScatter   →  rank0 持(A+B+C)第0片, rank1 第1片 ...
AllGather       →  把各片拼回, 每个 rank 得到完整 A+B+C
```

### 6. 拓展知识

可延伸到 ring/tree/halving-doubling 等算法、通信量模型、参数分片策略，以及通信库如何按规模自动选算法。

### 7. 常见追问及回答要点

- **AllReduce 各 rank 结果一样吗？** 一样。
- **为什么拆成两步？** 均衡带宽、便于与计算重叠、支持分片。
- **小消息怎么优化？** 用树形或分层结构，降低启动延迟。

### 8. 易错点与反例

- 把 AllReduce 当成 AllGather，漏掉归约。
- 忽略各 rank 结果必须一致。
- 估算通信量时用错算法模型。

### 9. 实践与验证

用多进程模拟对同一数组做 AllReduce，再与 ReduceScatter + AllGather 的结果逐一比对验证等价，并记录通信时间随规模的变化。

### 10. 评分标准

- 合格：说出 AllReduce 的语义。
- 良好：给出 ReduceScatter + AllGather 的等价分解。
- 优秀：讲清通信量、拓扑选择与分片优化。

## B013. prefill 与 decode 阶段有什么区别？TTFT 和 TPOT 分别衡量什么？

- 难度：入门级
- 知识域：K06（LLM 推理与 KV Cache）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：Transformer 推理、注意力计算、KV cache
- 关联题目：B014, B016
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

大模型推理分两个阶段：处理整段输入的 prefill，以及逐个 token 生成的 decode。两阶段的硬件瓶颈不同，衡量指标 TTFT 与 TPOT 也分别对应它们。

### 2. 问题分析

要对比两阶段的并行度与计算/访存特征，再把 TTFT 与 TPOT 的定义、包含范围对应到阶段上，说明端到端延迟如何由二者组成。

### 3. 具体答案

- prefill：一次并行处理整段 prompt，矩阵规模大、算力利用率高，属于计算受限，决定首 token 出现前的等待。
- decode：每步只生成一个 token，逐 token 自回归，主要时间花在读取 KV cache 与权重上，属于带宽受限，算力利用率低。
- TTFT（Time To First Token）：从请求开始到首 token 输出的时延，主要受 prefill 加排队调度影响。
- TPOT（Time Per Output Token）：首 token 之后平均每 token 的生成时间，等于（总时延 − TTFT）/（输出 token 数 − 1），反映 decode 速度。
- 简化关系：端到端时延约为 TTFT + (输出 token 数 − 1) × TPOT。

### 4. 技术洞察

- prefill 与 decode 落在 roofline 的不同区间，优化手段不同，不能混为一谈。
- prefill 靠批处理摊薄成本；decode 靠增大 batch 摊薄权重读取。
- 把新请求的 prefill 与在跑请求的 decode 混合调度，是提升吞吐的关键手段。

### 5. 图文说明

```text
请求 → [prefill: 处理整段 prompt, L 个 token 并行] → 首 token (TTFT)
     → [decode t1]→[decode t2]→...   每步耗时 TPOT
端到端 ≈ TTFT + (n_out − 1) × TPOT
```

### 6. 拓展知识

可延伸到 KV cache 显存占用、chunked prefill、分页注意力、连续批处理，以及 prefill/decode 分离部署。

### 7. 常见追问及回答要点

- **为什么 decode 慢？** 每步访存量与权重规模成正比，算术强度低，受带宽限制。
- **TTFT 与吞吐冲突吗？** 常有取舍，大 batch 提升吞吐却可能抬高排队导致 TTFT 上升。
- **怎么提升 TPOT？** 增大 batch、量化权重、投机解码。

### 8. 易错点与反例

- 把 TTFT 当成总时延。
- 认为两阶段是同一瓶颈。
- 忽视排队对 TTFT 的影响。

### 9. 实践与验证

固定 prompt 与输出长度，分别测量 TTFT 与 TPOT；再改变 batch 与 prompt 长度，观察两者的变化趋势。

### 10. 评分标准

- 合格：区分两阶段与两指标。
- 良好：说明各自的计算/访存特征。
- 优秀：联系连续批处理、prefill/decode 分离与取舍。

## B014. 服务端为什么需要队列、背压和超时？

- 难度：入门级
- 知识域：K07（服务端调度与稳定性）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：服务端并发、SLO、请求生命周期
- 关联题目：B013, B016
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

推理服务要面对突发流量、长度不一的请求和有限的设备资源。如果来者不拒、无限排队，系统会在过载时雪崩。队列、背压、超时正是用来维持稳定的三种手段。

### 2. 问题分析

要说明三者各自解决什么问题、如何配合。队列解耦到达与处理，背压在过载时强制入口降速，超时控制单个请求占用资源的时间。

### 3. 具体答案

- 队列：到达速率与处理速率经常不匹配，用队列缓冲，配合批处理调度可提高吞吐；但队列无上限增长会导致内存膨胀和时延无限。
- 背压：当队列超过阈值或资源饱和时，向上游反馈（拒绝、限流、降级），防止过载把系统拖垮，代价是牺牲部分请求。
- 超时：对单个请求设置截止时间，超时即取消并释放资源（如 KV、占用的设备时间），避免慢请求长期占坑，并配合幂等的重试。
- 三者配合：超时管单请求占用，队列管缓冲水位，背压管入口速率。

### 4. 技术洞察

- 系统稳定的必要条件是到达率不超过处理率，否则队列必爆；只有背压能强制这个条件。
- 尾延迟治理靠超时与优先级隔离，把长请求的影响限制在可控范围。
- 取消必须真正释放资源，否则超时只是「假装止损」。

### 5. 图文说明

```text
请求流 → [限流/背压] → [等待队列] → [调度/批处理] → [执行] → 响应
            ↑过载反馈      ↑超时出队      ↑deadline 取消释放
```

### 6. 拓展知识

可延伸到 Little 定律、准入控制、优先级队列与抢占、连续批处理调度，以及优雅降级策略。

### 7. 常见追问及回答要点

- **队列越长越好吗？** 不，越长时延越大、超时概率越高，有限队列加背压更稳。
- **超时后请求怎么处理？** 取消执行、释放 KV 与显存，向上游报错或降级。
- **背压会丢请求吗？** 会拒绝一部分，这是保护系统的代价，需要配合重试或降级。

### 8. 易错点与反例

- 用无限队列掩盖过载。
- 超时后不释放资源。
- 只加机器、不设背压。

### 9. 实践与验证

对服务做压测，观察队列深度与延迟曲线，对比有背压和无背压时的崩溃点与 P99 差异。

### 10. 评分标准

- 合格：说出三者各自的作用。
- 良好：说明过载稳定性与取消释放。
- 优秀：联系 Little 定律、尾延迟与 SLO 权衡。

## B015. 为什么性能优化前必须先建立正确性基线和 oracle？

- 难度：入门级
- 知识域：K08（性能测量与可观测性）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B011、性能测量与控制变量
- 关联题目：B016, B017
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

优化最危险的失败是「跑得更快，但结果悄悄变了」。没有正确性基线，无从判断改动是否等价；没有可信的参考结果，就无法自动发现数值回归。

### 2. 问题分析

问题问的是方法论：为什么先要 baseline（基准实现及其性能/正确性数据）和 oracle（可信的正确结果来源），以及它们在优化流程中的位置。

### 3. 具体答案

- baseline：优化前的实现及其性能、正确性数据，作为对照。缺了它，任何性能变化都无法归因。
- oracle：一个独立可信的正确结果来源，比如 CPU 参考实现、高精度库或数学恒等式，用来自动判定每次改动是否保持正确。
- 优化常引入近似、重排或换后端，都可能改变数值，只有 oracle 能自动抓住回归。
- 流程是：先固定输入与期望，建立可复现的 baseline，再做改动，每次都用 oracle 校验正确性并用指标衡量性能。

### 4. 技术洞察

- 正确性优先于性能，任何提速都以不破坏 oracle 等价为前提。
- oracle 要独立于被测实现，避免与被测代码同源而同时出错。
- 性能对比必须控制变量：同输入、同硬件、同版本，否则数字没有意义。

### 5. 图文说明

```text
固定输入 → [baseline] 记录性能与正确性
              │ 引入优化
              ▼
          [新实现] → 对 oracle 验正确性 + 对 baseline 比性能
              │ 等价且更快 → 采纳；否则回退
```

### 6. 拓展知识

可延伸到黄金样本测试、随机种子固定、数值容差、影子流量比对，以及把回归校验接进持续集成门禁。

### 7. 常见追问及回答要点

- **oracle 本身会错吗？** 会，尽量用独立且更高精度的来源并交叉验证。
- **性能数字波动大怎么办？** 多次运行取中位数与分位数，控制环境，先确认稳定性。
- **近似优化还需要 oracle 吗？** 需要，用容差或误差分布来约束。

### 8. 易错点与反例

- 先优化后补测试。
- 拿被测实现自己当 oracle。
- 只看单次跑分就下结论。

### 9. 实践与验证

以 CPU 实现为 oracle，把算子改到设备实现，用随机多组输入比对最大误差；再固定样张记录延迟，作为后续优化的基准。

### 10. 评分标准

- 合格：说出 baseline 与 oracle 的作用。
- 良好：说明独立性与控制变量。
- 优秀：讲清近似优化的容差门禁与回归流程。

## B016. kernel、step、端到端 latency 有什么区别，各自指标口径是什么？

- 难度：入门级
- 知识域：K08（性能测量与可观测性）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B011、B013、profiler 基础
- 关联题目：B013, B017
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

「延迟」在不同粒度上的含义完全不同。同一个系统，测单个 kernel、测一个 step、测整条请求，得到的数可能相差一个数量级，混用会引出错误结论。

### 2. 问题分析

要在三个粒度上分别定义：单 kernel 执行、一个训练/推理迭代、整条请求端到端，并说明各自包含哪些时间成分、用什么口径测量。

### 3. 具体答案

- kernel latency：单个 kernel 在设备上的执行时间，用设备 event 或 profiler 测量，不含 launch、排队与前后同步，反映算子本身的效率。
- step latency：一个训练或推理迭代的墙钟时间，包含该 step 内所有 kernel、通信、host 开销与同步，是吞吐基准的倒数，口径需说明是否含数据加载与优化器。
- 端到端 latency：从请求进入到响应完成（或数据进到结果出）的全部时间，含排队、网络、预处理、计算、后处理，面向用户 SLO。
- 关系：kernel 时间之和约等于设备忙碌时间，但 step 和端到端会因分派、通信、排队、同步而远大于 kernel 之和。

### 4. 技术洞察

- 越靠近端到端，非 kernel 开销占比越高，只优化 kernel 可能对端到端没有感知。
- 口径必须声明边界（含不含同步、含不含 IO），否则数字不可比。
- 平均值会掩盖问题，要看 P50/P99 与稳定性。

### 5. 图文说明

```text
端到端: |排队|预处理|  --- step ---  |后处理|网络|    ← 用户感知
step  :   [k1][k2][comm][k3][sync]                 ← 吞吐基准
kernel:   [k1]  [k2]        [k3]                   ← 设备执行
```

### 6. 拓展知识

可延伸到用 profiler 对齐时间轴、忙碌时间与墙钟时间的差异、算力利用率、吞吐与时延的权衡，以及分位数统计。

### 7. 常见追问及回答要点

- **kernel 优化了但端到端没变？** 说明非 kernel 开销占比高，如分派、通信、排队。
- **step 时间含数据加载吗？** 取决于口径，必须明确声明。
- **怎么对齐三种口径？** 用同一份 trace 分段量各段占比。

### 8. 易错点与反例

- 用 kernel 时间代表端到端。
- 忽略同步与排队开销。
- 只报平均值。

### 9. 实践与验证

用 profiler 分别测单 kernel、整 step 与端到端，画出时间占比，验证瓶颈落在哪一层。

### 10. 评分标准

- 合格：区分三种粒度。
- 良好：说明各自口径与包含项。
- 优秀：用 trace 对端到端瓶颈做归因并关注分位数。

## B017. 日志、metrics、trace 各自回答什么问题？

- 难度：入门级
- 知识域：K08（性能测量与可观测性）
- 题型：概念辨析
- 面试频率：高频
- 前置知识：B016、服务运行时观测
- 关联题目：B015, B016
- 事实状态：[S-已确认] [推断]

### 1. 背景知识

可观测性常被归纳为三支柱：日志、metrics、trace。它们粒度不同、成本不同，用错了要么信息不够，要么开销失控。

### 2. 问题分析

要区分三者的粒度与用途：日志是离散事件，metrics 是聚合数值时间序列，trace 是请求级跨组件的调用链。再说明它们如何协同定位问题。

### 3. 具体答案

- 日志：记录「发生了什么具体事件」，带上下文（错误信息、参数、时间），适合定位个案、审计与排查报错。代价是数据量大、聚合查询难、存储成本高。
- metrics：聚合的数值时间序列（QPS、延迟分位、显存、错误率），适合监控趋势、告警和容量规划，缺点是没有个案细节、可携带维度有限。
- trace：一次请求在多个组件与层次上的调用链及各段耗时，适合定位「慢在哪一段」、跨服务瓶颈。
- 协同路径：用 metrics 发现异常，用 trace 定位慢点，用日志查明具体原因。

### 4. 技术洞察

- 三者粒度互补，缺一不可；高基数信息（如请求 id）不适合放进 metrics。
- 成本随基数和采样上升，需要采样与分级保留。
- trace 的 span 边界要和 kernel/step/端到端的口径对齐，才能做准确归因。

### 5. 图文说明

```text
metrics: 每秒聚合值 ─────── 发现「延迟 P99 升高」
trace  : |--排队--|--prefill--|--decode--|  定位「慢在 prefill」
logs   : "request X OOM at ..."              查明「具体原因」
```

### 6. 拓展知识

可延伸到 RED/USE 方法论、OpenTelemetry、采样策略、结构化日志，以及上下文在服务间传递。

### 7. 常见追问及回答要点

- **metrics 能定位单个慢请求吗？** 一般不能，需要 trace 或日志。
- **日志越多越好吗？** 不，成本与噪声上升，需要结构化与采样。
- **trace 开销大吗？** 有开销，通常采样并限制 span 数量。

### 8. 易错点与反例

- 只靠日志做聚合监控。
- 把高基数指标塞进 metrics。
- trace 不做采样导致自身过载。

### 9. 实践与验证

给一个小服务同时打日志、metrics、trace，构造一个慢请求，演示三者分别能回答哪种问题。

### 10. 评分标准

- 合格：说出三者各自的用途。
- 良好：说明粒度、成本与互补关系。
- 优秀：讲清高基数处理、采样与归因链。

### 2. 问题分析

问题问的是叙事结构：如何用能力主线串联经历，并把通用系统能力映射到 AI Runtime 的具体问题。要突出可迁移的机制理解，同时诚实标注没做过的部分。

### 3. 具体答案

- 主线可以是：分层与边界意识、异步与并发模型、资源与内存管理、性能测量与归因、稳定性与运维。
- 映射示例：操作系统调度对应 stream 调度与优先级；用户态/内核态边界对应 host/device 边界；内存管理与碎片对应显存分配器；分布式一致性对应集合通信与分布式训练；性能剖析对应 profiler 与 kernel/step/端到端归因；驱动与中断对应 runtime/device 分层。
- 表达结构：每段经历用「问题—约束—机制—验证—结果」来讲，突出机制而非只报做了什么。
- 没做过的内容要如实标注为 [P-待补充]，不编造。

### 4. 技术洞察

- 面试官看重的是迁移能力与机制级理解，不是项目清单的长度。
- 用 AI Runtime 的语言重述原经历（术语映射），但不要夸大两者的等价程度。
- 每条主线都要有可追问的细节支撑，否则会显得空。

### 5. 图文说明

```text
系统软件能力        →   AI Runtime 落点
调度/并发          →   stream / event / 调度
内存/碎片          →   显存分配器
驱动/中断          →   runtime / device 分层
分布式一致         →   集合通信 / 分布式训练
性能剖析           →   profiler / kernel·step·端到端
```

### 6. 拓展知识

可延伸到「问题—约束—机制—验证」叙述法、术语映射表、避免堆砌名词，以及准备一到两个可深挖的案例。

### 7. 常见追问及回答要点

- **没有 AI 经验怎么办？** 用机制迁移讲清可复用的心智模型，并说明补充计划。
- **怎么避免显得空？** 每个映射配一个具体机制细节和验证方式。
- **要不要背术语？** 要理解机制，术语是理解的结果而不是装饰。

### 8. 易错点与反例

- 按时间罗列项目。
- 把系统经历硬说成 AI 经历。
- 只有名词，没有机制。

### 9. 实践与验证

把自己的三到五段经历各写一句「可迁移能力 + AI Runtime 对应点 + 验证证据」，连成一条主线，做两分钟口述练习并录音复盘。

### 10. 评分标准

- 合格：能串出一条主线。
- 良好：每段都有机制与映射。
- 优秀：有可深挖的案例，并诚实区分 [P-已确认] 与 [P-待补充]。
