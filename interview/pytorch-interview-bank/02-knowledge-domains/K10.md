# K10 序列化、导出、部署与兼容性

## 范围

state_dict、Export、runtime、schema、迁移、供应链和回滚。

## 领域边界

**在本域内**

- 持久化格式与语义：`state_dict`、`torch.save`/`torch.load`、检查点（checkpoint）字典、`map_location`、安全反序列化。
- 图导出：TorchScript（`torch.jit.trace`/`torch.jit.script`、`torch.jit.save`）、`torch.export`（`ExportedProgram`）、ONNX（`torch.onnx.export`、opset、`dynamic_axes`）。
- 推理优化：量化（PTQ/QAT）、算子融合、面向推理的后端编译与打包。
- 服务化：TorchServe、libtorch/C++ 服务、ONNX Runtime/TensorRT/OpenVINO 等运行时；批处理、warmup。
- 兼容性与治理：state_dict 键兼容、opset 版本、C++ ABI、弃用与迁移、回滚。
- 供应链安全：pickle 任意代码执行风险、模型签名与来源校验。

**在本域外**

- 模型结构设计、训练循环与优化器内部（K03/K05）。
- `torch.compile` 的编译策略与图变换细节（K08），本域只关心它与导出的接口边界。
- 分布式集合通信（K07）、底层 kernel 性能（K09）。
- 纯服务基础设施（K8s、网关）只有在影响 PyTorch runtime 行为时纳入。

**边界判定规则**

- 问题是否涉及“把 Python 运行时冻结成可移植产物 / 加载产物 / 跨环境消费”——是则本域。
- 问题是否涉及训练期数值或调度——归 K02/K05/K06。
- 自定义算子能否导出、序列化后能否被加载——跨 K10/K11，需同时在两处标注。

## 核心机制

### 1. 序列化：state_dict 与整对象

`torch.save(obj, f)` 底层用 `pickle` 序列化 Python 对象。推荐只保存 `state_dict`（`OrderedDict[str, Tensor]`），而不是整个 `nn.Module`：

```python
sd = model.state_dict()                     # name -> Tensor（含参数与 buffer）
torch.save(sd, "model.pt")
sd2 = torch.load("model.pt", map_location="cpu", weights_only=True)
model.load_state_dict(sd2, strict=True)
```

- `torch.load` 默认 `map_location` 可重定向设备；跨 GPU 加载到 CPU 或另一号卡都靠它。
- `weights_only` 控制是否只允许反序列化张量与白名单对象。为降低 pickle RCE 面，较新版本把默认值收紧为 `True` **[待验证，具体版本]**；`True` 下遇到自定义类会报错，需要显式放行或改用白名单。
- `load_state_dict(strict=True)`（默认）在键缺失/多余时抛错；`strict=False` 允许部分匹配。

`state_dict` 的结构与扩展点：

- 键是模块路径拼接（`layer1.weight`、`bn.running_mean` 等）；`parameters` 与 `buffers` 都进 `state_dict`，但只有 `parameters` 会进优化器。
- 层可覆写 `_load_from_state_dict` 做自定义迁移；`register_load_state_dict_pre_hook`/`register_state_dict_post_hook` 在加载前后介入。
- `get_extra_state`/`set_extra_state` 允许模块把非张量状态写入 `state_dict` 的 `_extra_state` 键。
- `state_dict()` 支持 `destination`、`prefix`、`keep_vars` 参数。

失败模式：pickle 反序列化执行任意代码（不可信来源）；`strict=True` 因键名变化失败；`torch.compile` 包裹后键名可能带 `_orig_mod.` 前缀 **[待验证]**；buffer 的 dtype/设备不匹配。

### 2. TorchScript：trace 与 script 的差异

| 维度 | `torch.jit.trace` | `torch.jit.script` |
|---|---|---|
| 捕获方式 | 用示例输入 eager 执行，记录实际发生的 aten 算子 | 解析 Python 源码 AST，编译成 TorchScript IR |
| 控制流 | 只记录走到的分支，数据依赖分支被**固化** | 支持 `if/while/for`（条件为张量或常量） |
| Python 互操作 | 几乎任意 Python 都能跑通但未必被正确记录 | 受 TorchScript 语言子集限制，越界即编译错误 |
| 动态形状 | 弱，形状常被当成常量 | 相对更好，但仍受类型系统约束 |
| 典型失败 | `if x.sum() > 0:` 分支固定；`.item()` 变常量 | 不支持的语法/类型 → `CompilationError` |

trace 丢失控制流的机制：trace 不做数据流分析，只是“跑一遍记一遍”。示例输入走哪条分支，导出的图就只有哪条：

```python
class M(nn.Module):
    def forward(self, x):
        if x.sum() > 0:        # 数据依赖
            return x * 2
        return x - 1

m = torch.jit.trace(M(), torch.randn(3))   # 分支被固化
# check_trace=True 时若两次运行结果不一致会给出 warning，但图已固化
```

script 的写法与限制：

```python
@torch.jit.script
def f(x: torch.Tensor, flag: bool) -> torch.Tensor:
    if flag:
        return x * 2
    return x - 1
```

TorchScript 子集不支持：异构容器、带复杂方法的自定义类、未标注类型的 `*args`、`with`、闭包捕获复杂 Python 对象、部分动态属性访问。可用 `@torch.jit.ignore` 跳过函数、`@torch.jit.unused` 标注不参与、`@torch.jit.export` 暴露方法。

**TorchScript 产物与优化**：

- `torch.jit.save(scripted, "m.pt")`（zip 归档，含代码与参数），`torch::jit::load` 在 C++ 侧加载。
- `torch.jit.freeze(m)` 内联常量的属性（如 `self.training=False`），消除仅存的 Python 依赖；冻结后参数变为常量，只为推理服务。
- `torch.jit.optimize_for_inference(m)` 做算子融合等推理优化 **[待验证，具体算子集]**。
- 产物有算子版本（bytecode/operator version）概念，跨版本加载需版本兼容 **[待验证]**。

选择策略：无数据依赖控制流、只需权重图时 trace 简单；有控制流或需要静态类型检查时 script；新项目优先 `torch.export`。

### 3. ONNX 导出：opset 与动态轴

```python
torch.onnx.export(
    model, args, "m.onnx",
    opset_version=17,                      # 目标算子集版本
    input_names=["x"], output_names=["y"],
    dynamic_axes={"x": {0: "batch"},      # 声明可变维
                  "y": {0: "batch"}},
    do_constant_folding=True,
)
```

- **opset** 是导出的“语法”。图里每个算子必须在目标 opset 有对应（symbolic）。opset 越高算子越全，但旧运行时可能不支持；过低则出现 “operator not supported”。
- **dynamic_axes** 用 `{输入名: {维度序号: 符号}}` 声明。不声明则形状被写死为示例形状。`input_names` 必须与 `dynamic_axes` 的键一致。
- 导出前应 `model.eval()`，否则 dropout/batchnorm 的 training 语义会被带入图。
- 校验：`onnx.checker.check_model("m.onnx")`；再用 ONNX Runtime 在多个 batch/seq 长度下与 PyTorch 输出 `allclose`。

**算子映射与扩展**：

- 每个 `aten::*` 通过 symbolic 函数映射到 ONNX 算子；某些算子在某 opset 才出现，或需要分解成多个 ONNX 算子。
- 缺少 symbolic 时可用 `torch.onnx.register_custom_op_symbolic` 注册自定义映射，或把逻辑改写成导出友好形式。
- 较新版本提供基于 Dynamo 的导出路径（`torch.onnx.export(..., dynamo=True)` 或 `torch.onnx.dynamo_export`）**[待验证，具体版本]**。
- 导出后可做图简化（常量折叠、去冗余）以缩小体积 **[待验证，工具链]**。

失败模式：算子无 symbolic（缺 opset 或后端不支持）；动态轴漏声明；数据依赖控制流无法导出；训练态算子被固化；自定义算子未注册 symbolic。

### 4. torch.export 与 ExportedProgram

`torch.export` 用 Dynamo + FakeTensor 捕获，产出函数式图：

```python
from torch.export import export, Dim

dyn = {"x": {0: Dim("batch")}}
ep = export(model, (x,), dynamic_shapes=dyn)
ep = ep.run_decompositions()      # 下沉到核心 aten 算子，供后端消费
# ep.graph_module    -> 函数式 FX GraphModule（无 Python 副作用）
# ep.graph_signature -> 输入/输出/参数/buffer 契约
# ep.range_constraints -> 动态维的取值范围
```

与其他方式的关键差异：

- **函数式**：原地写（in-place）在导出时被改写为显式输出（functionalization），图不再有可变的 Python 状态。
- **可靠失败**：无法安全捕获的数据依赖控制流会让导出**报错**，而不是像 trace 那样静默固化。真正的条件逻辑需改用 `torch.cond` 或重写为张量运算。
- **契约**：`graph_signature` 声明输入输出，`range_constraints` 记录动态维约束，`state_dict` 绑定参数。
- **动态维语义**：`Dim("batch")` 给符号名；可用 `Dim.AUTO`/`Dim.DYNAMIC`/`Dim.STATIC` 表达自动推断、动态、静态；约束（min/max）会写进 `range_constraints`，导出后改维不必重导。
- **后端衔接**：`run_decompositions()` 后可交给推理后端打包（AOTInductor 等）**[待验证，具体 API]**。
- **产物持久化**：`torch.export.save`/`torch.export.load` 提供导出图序列化格式 **[待验证，格式名与版本]**。
- **逃生舱**：`torch.library.custom_op`、`register_fake` 让自定义算子可被捕获；`torch._check` 表达运行期断言；`torch.export.register_dataclass` 支持自定义输入结构。

失败模式：数据依赖控制流 → 约束违例/`UserError`；算子无 fake/meta 实现；Python 副作用（文件、全局状态）；未声明动态维导致被编译成常量。

### 5. 推理优化：量化 PTQ/QAT 与融合

**量化映射（affine）**：给定浮点值 `x`、尺度 `s>0`、零点 `z`（整数）、位宽 `b`：

```
q = clamp(round(x / s) + z, q_min, q_max)      # 量化
x̂ = (q - z) · s                                 # 反量化
```

对称量化取 `z = 0`，`s = max|x| / (2^(b-1) - 1)`，int8 时 `q ∈ [-128, 127]`。量化误差 `|x - x̂| ≤ s/2`（截断区间内）。权重常用**逐通道**（per output channel）以减小离群通道误差，激活常用**逐张量**。

**PTQ（训练后量化）**：在代表性数据上校准 observer（min/max、移动平均、直方图/分位数），再 `convert` 成 int8。

```python
# FX 图模式（示意）
from torch.ao.quantization.quantize_fx import prepare_fx, convert_fx
qconfig = get_default_qconfig("fbgemm")        # 或 "qnnpack"（ARM）
prepared = prepare_fx(model.eval(), qconfig, example_inputs)
for xb in calib_loader:                        # 校准：只跑前向收集统计
    prepared(xb)
qmodel = convert_fx(prepared)                  # 转成量化表示
```

- 静态量化：权重与激活都量化，需校准。
- 动态量化：只量化权重，激活在运行时量化（适合 LSTM/Linear 密集场景）。
- 逐通道：`per_channel` 在 `QConfig` 的 `weight` observer 中开启，`ch_axis` 指定通道。

**QAT（量化感知训练）**：前向插入 `FakeQuantize`（模拟量化），反向用直通估计器（STE）：

```
∂q/∂x ≈ 1   当 x̂ 在 [q_min, q_max] 内
∂q/∂x ≈ 0   否则
```

用 fp32 主权重训练后 `convert`。精度更高，成本更大。

**算子融合**：Conv+BN 折叠是典型——

```
W' = W · γ / σ
b' = (b - μ) · γ / σ + β
```

消除 BN 后推理只算一次卷积。后端还会做逐元素融合、LayerNorm 融合、GEMM+激活融合。

后端：`fbgemm`（x86）、`qnnpack`/`XNNPACK`（ARM）；权重**分位宽**（int4/重量化）见 GPTQ/AWQ 风格方案 **[待验证]**。

失败模式：校准集不具代表性导致截断误差；逐张量对离群通道过粗；softmax/LayerNorm 等敏感算子应保持浮点；QAT→PTQ 流程不一致；目标后端缺少某些量化算子。

### 6. 服务化

- **TorchServe**：`.mar` 归档（模型 + handler + 配置）。Management API 注册/扩缩、Inference API 预测、Metrics API 导出 Prometheus 指标。
- **自定义 handler** 至少实现 `initialize`（加载模型）、`preprocess`（请求→张量）、`inference`（前向）、`postprocess`（张量→响应）；示例骨架：

  ```python
  class Handler(BaseHandler):
      def initialize(self, ctx):
          self.model = torch.jit.load(ctx.model_dir + "/model.pt").eval()
      def preprocess(self, data):
          return torch.as_tensor(data[0]["body"]).float()
      def inference(self, x):
          with torch.inference_mode():
              return self.model(x)
      def postprocess(self, y):
          return y.tolist()
  ```

- **libtorch/C++ 服务**：

  ```cpp
  torch::jit::script::Module m = torch::jit::load("m.pt");
  torch::NoGradGuard guard;
  auto out = m.forward({input}).toTensor();
  ```

- **运行时后端**：ONNX Runtime（`CPUExecutionProvider`/`CUDAExecutionProvider`/`TensorrtExecutionProvider`）、TensorRT、OpenVINO，按 provider 选择与图优化。
- **批处理**：动态批处理提升吞吐但增加尾延迟；warmup 消除首轮编译/分配开销；GPU 上用独立流并发。
- **打包**：`torch.package` 可打包模型及其 Python 依赖；`torch::deploy` 提供多解释器推理 **[待验证，稳定性]**。

失败模式：handler 抛异常；输入 dtype/device 不匹配；后端缺算子；libtorch 与 pip torch 版本不一致；批处理引入尾延迟尖刺。

### 7. 兼容性与迁移

| 兼容维度 | 影响因素 | 检查手段 |
|---|---|---|
| state_dict 键 | 层命名、compile 前缀、重构 | 加载时对比键集合 |
| 图/opset | 目标 opset、后端算子覆盖 | `onnx.checker`、目标运行时试跑 |
| ABI | `_GLIBCXX_USE_CXX11_ABI`、C++ 标准 | 链接期符号、`torch._C` 探测 |
| 默认值 | `weights_only`、默认 dtype、`torch.load` | 升级回归测试 |
| TorchScript | 算子版本、ir_version | 跨版本加载测试 |

- **BC 承诺**：公共 API 与 `state_dict` 键尽量稳定；`_` 前缀为私有，不保证。
- **升级流程**：钉住版本 → 跑 golden/兼容测试 → 对比 `state_dict` 键 → 检查默认值变化 → 灰度 → 保留回滚产物。
- **回滚**：保存上一版模型与 schema，做 canary/shadow 评测，记录模型签名哈希。

**导出方式决策树**：

1. 需要训练/继续求导 → 不在本域（用 `torch.compile` 或直接 eager）。
2. 需要跨框架/跨硬件交换 → ONNX，先确认目标 opset 覆盖所有算子。
3. 需要 C++ 直跑、控制流复杂 → TorchScript `script`，或 `torch.export` + 后端。
4. 需要 AOT 推理性能、可控动态维 → `torch.export` + decompositions + 后端打包。

## 常见陷阱与反例

1. **trace 固化数据依赖控制流**：`if x.sum() > 0` 被固定到示例分支，线上换输入结果错。反例见 B020 与 E020。
2. **`dynamic_axes` 与 `input_names` 不一致或漏声明**：维度被编译成常量，换 batch 即失败。
3. **opset 选择不当**：过高旧运行时缺算子；过低目标算子无 symbolic。
4. **`torch.save(model)` 整对象**：耦合类定义、跨版本加载失败，且 pickle 有 RCE 风险。
5. **`strict=True` 加载失败或 `_orig_mod.` 前缀**：compile 后键名变化，需重映射或统一保存点。
6. **导出时未 `eval()`**：dropout/batchnorm 训练语义混入推理图。
7. **量化校准集泄漏/不代表性**：线上分布外数据截断严重，精度坍塌。
8. **只测单一 shape**：固定 batch 通过，变长序列触发布局/形状错误。
9. **libtorch 与 torch ABI 不一致**：链接期或加载期报未定义符号。
10. **把离线导出当作训练的替代**：导出图不含 autograd，误用会丢梯度。
11. **对 TorchScript 产物不 `freeze`**：残留 `self.training` 等属性导致结果随环境变化。
12. **对动态维不设约束**：`range_constraints` 过宽触发后端保守编译或运行期错误。

## 与其他知识域的连接

- **K03（Module/状态）**：`state_dict` 的键结构与 `parameters`/`buffers` 直接决定加载兼容性。
- **K06（AMP/Checkpoint/复现）**：检查点内容、scaler 状态、RNG 状态影响迁移与复现。
- **K08（编译栈）**：`torch.export` 与 `torch.compile` 共享 Dynamo/FakeTensor 捕获；AOT 后端是两者的衔接点。
- **K09（性能）**：量化/融合/服务化直接影响延迟、吞吐、显存；性能数字须实测并标 `[待验证]`。
- **K11（自定义算子）**：自定义算子要能被导出与服务，需要 schema、fake/meta 注册，跨域联动。
- **K12（测试与治理）**：golden 输出、兼容回归、灰度与回滚是本域质量的落地手段。
- **K01/K02**：dtype/device/layout 决定后端支持；autograd 决定 QAT 的反向路径。
