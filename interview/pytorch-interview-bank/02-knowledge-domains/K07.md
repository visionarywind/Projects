## 先修知识

- **自动微分**：反向图、叶子张量、`.grad` 累加语义、hook 触发顺序（见 K02）。DDP 的通信时机完全由 autograd 决定。
- **`nn.Module` 与 `state_dict`**：参数注册顺序、buffer、`named_parameters()` 的迭代顺序（见 K03）。bucket 顺序依赖参数注册顺序。
- **张量与设备**：`.to(device)`、`torch.cuda.set_device`、跨设备拷贝是同步还是异步（见 K01）。
- **优化器**：Adam 的一阶/二阶动量、`state_dict` 结构（见 K05）。ZeRO 分片的分片对象就是这些状态。
- **集合通信概念**：MPI 风格的 collective 语义；all-reduce 的输出在所有 rank 相同，reduce-scatter 的输出分散，all-gather 的输入分散。不熟悉时先区分“4 种基本原语”的输入/输出形状。
- **基础性能模型**：带宽（bytes/s）、延迟（每消息固定开销 α）、通信量（bytes）。用于理解 ring 算法与 overlap 收益。
- **进程模型**：`torchrun` 每个进程一个 Python 解释器、一个 CUDA context；GIL 与 NCCL 通信线程的关系。

## 核心机制

### 1. 进程组、初始化与 backend

所有分布式操作都发生在一个 `ProcessGroup` 内。`init_process_group` 建立默认组（world）：

```python
import os
import torch
import torch.distributed as dist

def setup():
    # torchrun 会注入这些环境变量；手动启动时自行设置
    rank = int(os.environ["RANK"])
    local_rank = int(os.environ["LOCAL_RANK"])
    world_size = int(os.environ["WORLD_SIZE"])

    # 关键：先绑定本进程使用的 GPU，再建组
    torch.cuda.set_device(local_rank)

    dist.init_process_group(
        backend="nccl",          # GPU 集合通信用 nccl
        init_method="env://",    # env:// 读 MASTER_ADDR/MASTER_PORT
        rank=rank,
        world_size=world_size,
        timeout=torch.timedelta(seconds=1800),  # 具体默认值 [待验证]
    )
    return rank, local_rank, world_size
```

- `init_method`：`env://`（推荐，torchrun 配套）、`tcp://host:port`、`file:///path`。
- `MASTER_ADDR`/`MASTER_PORT` 只用于初始化握手，建立完集合通信后 NCCL 走自己的通道。
- backend 契约（详见 §3）：NCCL 管 GPU collective；Gloo 管 CPU collective 与部分 host 侧通信；MPI 需要专门构建。
- 结束要 `dist.destroy_process_group()`，否则下次初始化可能残留端口/资源。

**失败模式**

- 先建 CUDA context 后改 device：`set_device` 必须在使用该 device 之前调用，否则 DDP 会把通信绑到错误设备。
- `MASTER_PORT` 被占用或 rank 之间不一致 → 初始化挂起或 `Connection reset`。
- backend 与张量设备不匹配：Gloo 收到 CUDA 张量、或 NCCL 收到 CPU 张量会在运行期报错。

### 2. rank、local_rank 与拓扑

| 概念 | 含义 | 取值范围 |
|---|---|---|
| `world_size` | 全局进程数 | 通常 = GPU 总数 |
| `rank` | 全局唯一进程编号 | `[0, world_size)` |
| `local_rank` | 本节点内编号 | `[0, gpus_per_node)` |

- 只有 `rank == 0` 才应做日志、写 checkpoint、`print`，否则输出重复。
- `local_rank` 决定 `torch.cuda.set_device(local_rank)`，从而决定本进程可见/使用的 GPU。
- 拓扑会影响 collective 性能：同一节点内多卡走 NVLink/PCIe，跨节点走网络（InfiniBand/RoCE）。NCCL 会按拓扑自动选择 ring/tree 算法与通道数，可用 `NCCL_DEBUG=INFO` 观察它选了哪些通道。

### 3. Collective 原语与语义

| 原语 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `broadcast` | 一个 root 有数据 | 所有 rank 相同 | 初始参数/buffer 同步 |
| `all_reduce` | 各 rank 不同 | 所有 rank 相同（求和） | DDP 梯度同步 |
| `reduce` | 各 rank 不同 | 只有 root 拿到 | 汇总指标 |
| `reduce_scatter` | 各 rank 相同形状 | 各 rank 拿到归约后的一片 | FSDP 梯度分片 |
| `all_gather` | 各 rank 一片 | 所有 rank 拿到全部片 | 收集分片参数 |
| `all_gather_object` | 任意 Python 对象 | 所有 rank 拿到全部 | 收集字符串/指标 |
| `all_to_all` | 各 rank 分块发往各 rank | 各 rank 收到各来源分块 | 专家并行/MoE |
| `barrier` | 无 | 无（同步点） | 调试，慎用于生产 |

**语义要点**

- collective 是 **集合操作**：同一组内所有 rank 必须用相同的原语、相同的顺序、相互兼容的 shape/dtype 调用同一次通信。顺序不一致是死锁的头号来源。
- `all_reduce` 默认 `ReduceOp.SUM`，可指定 `AVG`/`MAX`/`MIN`/`PRODUCT`。
- 通信挂上后可 `work.wait()`（阻塞）或配合 `dist.all_reduce(..., async_op=True)` 得到 `Work` 句柄，异步 wait。DDP 内部就用异步通信与反向重叠。

### 4. Ring allreduce 与通信量下界

Ring allreduce 分两阶段：**reduce-scatter** 与 **all-gather**。

设 `N` 个 rank，每个 rank 有 `M` 个元素（bytes）。

```
Phase 1 reduce-scatter: N-1 步
  第 k 步：rank i 把 (i-k) mod N 号块发给 (i+1) mod N
  每步每 rank 发送 M/N 字节
  → 每 rank 累计发送 (N-1)·M/N

Phase 2 all-gather: N-1 步
  同样每步 M/N 字节
  → 每 rank 累计发送 (N-1)·M/N
```

**每 rank 总通信量**：

```
V_ring = 2·(N-1)/N · M
```

当 `N` 很大时趋近 `2M`，即 allreduce 是**带宽最优**的：每个字节至少被读一次、写一次。

**时间模型**（α = 每消息固定延迟，β = 1/带宽）：

```
T_ring ≈ 2·(N-1)·α + 2·(N-1)/N · M · β
```

- 小消息时 `2(N-1)α` 主导 → 延迟受限。
- 大消息时带宽项主导 → 与 `N` 弱相关，接近 `2Mβ`。
- 树形 / recursive halving-doubling 把延迟项降到 `O(log N)`，适合小消息与多节点。

**NCCL 的选择**：小消息、拓扑不对称时可能用 tree；大消息用 ring。通道数（channels）决定并行度。这些是运行时决策，想确认必须看 `NCCL_DEBUG=INFO` 的实际日志，不要凭经验断言 [待验证]。

### 5. DDP：梯度同步、bucket 与反向重叠

DDP 的模型是**每卡一份完整副本**，反向传播时同步梯度。

构造：

```python
model = MyModel().to(device)
model = torch.nn.parallel.DistributedDataParallel(
    model,
    device_ids=[local_rank],
    output_device=local_rank,
    find_unused_parameters=False,   # 默认 False，正确性代价换性能
    broadcast_buffers=True,         # 构造时广播 buffer
)
```

**初始化契约**：`DDP.__init__` 会把 `rank 0` 的参数/buffer 广播给所有 rank，保证初始权重一致。因此**所有 rank 必须用相同种子、相同架构**，否则训练起点就发散了。

**bucket 机制（核心）**

- DDP 把梯度按 bucket 分组，默认 bucket 上限约 **25 MB**（`bucket_bytes_cap`，具体默认值以目标版本为准 [待验证]）。
- bucket 的构建顺序与参数注册顺序**相反**：最后注册的参数放进第一个 bucket。
- 反向传播从最后一层往第一层算，**最后注册的参数最先拿到梯度**。于是第一个 bucket 最先就绪，可以最早开始 allreduce，与后续反向计算重叠。
- 每个 bucket 内所有参数的 `.grad` 就绪后，触发一次该 bucket 的异步 allreduce。

伪代码：

```
forward()                        # 各 rank 独立
loss.backward()                  # autograd 逐层算出 grad
   ├─ 每当某 bucket 全部参数 grad ready
   │     allreduce_async(bucket.grads)     # 后台 NCCL
   └─ 反向继续计算下一段，与上面的 allreduce 重叠
optimizer.step()                 # 此时 grad 必须已归约完成
```

**`no_sync`：梯度累积的省通信手段**

梯度累积（如想模拟大 batch）时，如果每个 micro-step 都 allreduce，通信量翻倍：

```python
for i, (x, y) in enumerate(loader):
    with model.no_sync() if i % accum_steps != 0 else contextlib.nullcontext():
        loss = criterion(model(x), y) / accum_steps
        loss.backward()
    if (i + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```

`no_sync()` 抑制除最后一个 micro-step 之外的所有 allreduce，只在累积窗口结束时同步一次。注意：`no_sync` 期间梯度仍在本地累加。

**`gradient_as_bucket_view`**

```python
model = DDP(model, gradient_as_bucket_view=True)
```

- 开启后，参数 `.grad` 直接是 bucket 存储的视图，省掉“bucket → 各参数独立 grad 张量”的那份拷贝。
- 收益：降低峰值显存、减少内存拷贝。
- 限制：grad 与 bucket 生命周期绑定，不能随意重新赋值/释放；有些依赖“grad 是独立张量”的代码会失效。

**`static_graph=True`**

- 声明“每次迭代的计算图与用到的参数集合完全相同”。
- 允许 DDP 预先确定 bucket 与通信顺序，跳过每次迭代的 bucket 重建与未用参数探测，降低开销。
- 代价：一旦图变了（条件分支、动态跳过层）会出错或 hang。

**`find_unused_parameters`（默认 False）**

- 当一次迭代里某些参数没有参与 loss，它们的 grad 永远不会 ready，bucket 永远不齐 → hang。
- 置 `True` 后 DDP 在每个反向遍历 autograd 图，找出未用参数并标记 ready，避免 hang。
- 代价：每步额外图遍历，明显拖慢。正解通常是让所有参数都参与，或改用 `static_graph`。

### 6. FSDP 与 ZeRO

DDP 的问题是每卡都存完整参数、梯度、优化器状态。FSDP 把这三者**分片**到各 rank。

**ZeRO 三阶段（DeepSpeed 提出，FSDP 对应 Stage-3 思路）**

以 Adam 混合精度为例，记总参数量为 `Ψ`（元素数），参数/梯度用 2 bytes，优化器状态用 fp32：

| 项 | 每参数 bytes | 说明 |
|---|---|---|
| fp16 参数 | 2 | 计算用 |
| fp16 梯度 | 2 | 反向产出 |
| fp32 master 参数 | 4 | 优化器更新用 |
| Adam m | 4 | 一阶动量 |
| Adam v | 4 | 二阶动量 |
| **合计** | **16** | |

- **Stage 1**：只分片优化器状态（4+4+4=12 bytes/param）。每卡内存 ≈ `2+2 + 12/N`。
- **Stage 2**：再分片梯度。每卡 ≈ `2 + 2/N + 12/N`。
- **Stage 3**：再分片参数。每卡 ≈ `(2+2+12)/N = 16/N`（外加激活、通信缓冲区）。
- 数字 [待验证]，随 dtype、是否 offload、优化器类型变化。

**FSDP 的运行循环（per FSDP unit，通常一层或多层）**

```
forward:
  all_gather 本 unit 的完整参数（从各 rank 分片拼出）
  用完整参数做前向
  丢弃完整参数，只留在 all-gather 缓冲/保留策略

backward:
  再次 all_gather 该 unit 的参数（若未保留）
  计算梯度
  reduce_scatter 梯度，每个 rank 只留自己负责的分片
  unit 的完整参数再次释放
```

- 通信量约是 DDP 的 2 倍量级：正向一次 all-gather、反向一次 all-gather + 一次 reduce-scatter。换来的是参数/梯度/优化器状态按 `N` 缩小。
- 分片单元（wrap 粒度）是主要调参项：单元太大 → 峰值参数内存高、分片粒度粗；单元太小 → collective 次数多、通信开销大。

**FSDP1 vs FSDP2**

- FSDP1：把参数拍平成 `FlatParameter`，用 `auto_wrap_policy` 控制分片单元。
- FSDP2：`torch.distributed.fsdp.fully_shard`，基于 `DTensor` 做**逐参数分片**，接口更接近普通 Module，支持更细粒度的分片与更好的组合性。API 名称与行为以目标版本为准 [待验证]。

```python
# FSDP2 风格（目标版本为准）
from torch.distributed.fsdp import fully_shard
for layer in model.layers:
    fully_shard(layer)
fully_shard(model)
```

**激活内存**：FSDP/ZeRO 只省参数相关内存，激活仍随 batch × 序列长 × 层数增长，通常需要梯度检查点（K06）配合。

### 7. 张量并行与流水线并行基础

数据并行切“batch”，模型并行切“模型”。

**张量并行（Tensor Parallel, TP）**

- 列并行 Linear：权重按输出维切，各 rank 算出部分输出，无需立即通信。
- 行并行 Linear：权重按输入维切，各 rank 算出部分和后需要 **all-reduce** 才能得到完整输出。
- Transformer 一层里通常 MLP 段有 1~2 次 all-reduce、Attention 段有 1 次（具体视实现）。TP 的通信在**每层内**，对延迟敏感，通常限制在单机 NVLink 域内。
- 常见组合：TP 在节点内，DP 跨节点。

**流水线并行（Pipeline Parallel, PP）**

- 把层切成 `P` 个 stage，每个 stage 放不同 rank；一个 batch 切成 `M` 个 micro-batch 流过流水线。
- **气泡（bubble）**：流水线填充/排空阶段有空闲。GPipe 的近似气泡比例 `(P-1)/(M+P-1)`。
- **1F1B**（one-forward-one-backward）：每 stage 在稳态下交替做一次前向、一次反向，显著降低激活内存占用；精确气泡公式与调度变体以实现为准 [待验证]。
- 关键权衡：`M` 越大气泡越小，但激活内存越高；`P` 越大单卡层数越少但气泡与通信越多。

### 8. DistributedSampler 与启动

**`DistributedSampler`**：把数据集按 rank 切分，保证各 rank 看到不重叠子集。

```python
sampler = torch.utils.data.DistributedSampler(
    dataset, num_replicas=world_size, rank=rank,
    shuffle=True, drop_last=True,
)
loader = DataLoader(dataset, batch_size=bs, sampler=sampler, num_workers=4)

for epoch in range(epochs):
    sampler.set_epoch(epoch)   # 必须！否则每个 epoch 的 shuffle 相同
    for x, y in loader:
        ...
```

- `set_epoch` 改变 shuffle 的随机种子；忘了它 → 每轮顺序一致，等于降低了数据随机性。
- `drop_last=True` 让各 rank 步数一致；否则最后一步 batch 数不齐可能触发 DDP 通信次数不一致而 hang。
- `world_size` 变化（弹性）时，总样本数不能被整除的余数会被 pad/丢弃，具体行为看 `drop_last`。

**torchrun 启动**

```bash
torchrun \
  --nnodes=2 --nproc_per_node=8 \
  --node_rank=0 --master_addr=10.0.0.1 --master_port=29500 \
  train.py
```

注入的环境变量：`RANK`、`LOCAL_RANK`、`WORLD_SIZE`、`MASTER_ADDR`、`MASTER_PORT`。`torchrun` 还负责进程监控与（配 `--max_restarts` 的）弹性重启。

### 9. 容错、超时与 hang 排查

**hang 的因果链**

```
某 rank 少调一次 collective
  → 其它 rank 在 NCCL kernel 里等它，永远等不到
  → 卡死数分钟
  → watchdog 超时后 abort（或一直挂）
```

**常见根因**

1. 各 rank collective 次数/顺序不一致：条件分支里调用通信、某 rank `continue`/`return` 早退。
2. batch 数不齐：rank A 比 rank B 多一次 backward → 多一次 allreduce。
3. `find_unused_parameters=False` 下有条件跳过的层。
4. 某 rank 抛异常先退出，其余 rank 在通信里等。
5. 设备未绑定正确导致两个进程抢同一张卡。

**排查手段**

- `NCCL_DEBUG=INFO`（或 `WARN`）：看 NCCL 选了什么算法、哪个 rank 卡住。
- `NCCL_DEBUG_SUBSYS=COLL`：聚焦 collective 调用。
- `py-spy dump --pid <pid>`：看 Python 栈停在哪，区分“停在通信等待”还是“停在 Python 逻辑”。
- `torch.distributed.monitored_barrier()`：带超时的 barrier，能定位到是哪个 rank 没到。
- `TORCH_NCCL_TRACE_BUFFER_SIZE` + `TORCH_NCCL_DUMP_ON_TIMEOUT`（Flight Recorder）：超时时 dump 每个 rank 最后的集合通信记录，适合生产环境分析。环境变量名与默认值以目标版本为准 [待验证]。
- `faulthandler` / `Handler`：拿到 C++ 栈与 Python 栈，判断是 hang 在 Python 还是 NCCL。
- 二分法：注释掉可疑通信/分支，或把 `world_size` 降到 2 复现。

**超时**：`init_process_group(timeout=...)` 控制初始化与部分集合操作的超时；NCCL watchdog 另有独立超时（`TORCH_NCCL_*` 系列）。精确默认值随版本变化，需在目标环境核对 [待验证]。

## 常见陷阱与反例

- **反例：CUDA 设备与通信绑定错位**
  ```python
  dist.init_process_group("nccl")     # 先建组
  torch.cuda.set_device(local_rank)   # 后设设备：通信可能绑到默认卡
  ```
  正解：先 `set_device(local_rank)` 再 `init_process_group`。

- **反例：用 Gloo 做 GPU 梯度同步**。Gloo 不优化 GPU collective，会先拷到 host 再通信，性能极差且可能不支持某些 dtype。GPU 用 NCCL。

- **反例：忘了 `set_device`，所有进程用 cuda:0**。表现是显存暴涨、单卡打满、其余卡空闲。

- **反例：只 `rank 0` 保存但没加 `dist.barrier()`**，其它 rank 可能在 checkpoint 写完前就开始下一轮，产生数据竞争。

- **反例：评估阶段走 DDP 前向却在 `no_grad` 下不激活通信**。`no_grad` 下 DDP 不做梯度同步，但如果代码里手动调用了 collective（如 `all_gather` 收集预测），各 rank 调用次数必须一致，否则 hang。

- **反例：BatchNorm 在 DDP 下各卡用本地统计**。每卡 batch 统计不同 → 正则化不一致。做法：`SyncBatchNorm.convert_sync_batchnorm(model)`，或用 GroupNorm/LayerNorm。SyncBN 自身引入跨卡通信。

- **反例：`no_sync` 里改了 batch size 或跳 step**，导致累积窗口长度在各 rank 上不一致。

- **反例：把 `find_unused_parameters=True` 当默认**。它能救正确性但拖慢每一迭代；应先定位为什么有未用参数。

- **反例：FSDP 用超大 wrap 单元 + 不 checkpoint**，以为分片就解决了显存；激活仍是瓶颈。

- **反例：`DistributedSampler` 忘 `set_epoch`**，每轮相同的“随机”顺序。

- **反例：弹性训练里用静态 `world_size` 写死 dim**，重启后 rank 数变化导致 shape 不匹配。

- **反例：在通信调用里传 Python 对象（非张量）到 NCCL**。NCCL 只处理张量；Python 对象用 `all_gather_object`/Gloo。

- **反例：靠 `print` 调试 hang**。输出被缓冲，且 rank 顺序不可预测；用 `NCCL_DEBUG` + `py-spy`。

## 与其他知识域的连接

- **K02 autograd 与梯度**：DDP 的 bucket 触发完全依赖 autograd hook 与 `.grad` 累加语义；`no_sync` 改的是 hook 行为。理解 hang 必须先理解“反向里 grad 何时 ready”。
- **K05 训练与优化器**：ZeRO/FSDP 分片的核心对象是优化器状态（Adam m/v）与 master 权重；`optimizer.step()` 的同步点位置决定正确性。
- **K03 Module 与状态**：bucket 顺序 = 参数注册顺序；`state_dict` 的 sharding/save 是 checkpoint 的核心问题。
- **K06 AMP、Checkpoint 与复现**：混合精度决定 ZeRO 的内存系数；梯度检查点与 FSDP 常一起用；跨 rank 复现要求种子与 sampler 一致。
- **K01 张量、设备与布局**：设备绑定、跨设备拷贝的同步性、通信缓冲区的内存布局。
- **K09 性能与显存**：通信-bound 的判定、NCCL 带宽在 timeline 里的形态、重叠是否真的生效、FSDP 峰值显存分析。
- **K08 编译栈**：`torch.compile` 与 DDP/FSDP 组合时的图捕获、graph break 与通信边界。
- **K04 数据管道**：`DistributedSampler` 的切分与 `DataLoader` worker 的交互。
