# K08 torch.compile 与编译栈

## 范围

Dynamo、AOTAutograd、Inductor、guards、graph break、动态 shape 和缓存。

## 领域边界

**纳入范围**

- 端到端流水线：`torch.compile` 从 Python 函数/Module 到生成后端的三个核心阶段——TorchDynamo（抓图 + guards）、AOTAutograd（前进/反向联合图 + functionalization）、TorchInductor（lowering + 调度 + codegen）。
- 抓图机制：PEP 523 frame 求值钩子、FX graph、graph break 的产生与后果、`fullgraph`、`allow_in_graph`、`torch.compiler.disable`。
- 正确性守护：guards（类型/形状/dtype/常量）、recompile、recompile limit、`torch._dynamo.explain`。
- 动态 shape：符号形状（SymInt）、`dynamic=True`、形状特化与重新编译、`mark_dynamic`、`constrain_as_size`。
- 后端与模式：`inductor` 默认后端、`mode="default"|"reduce-overhead"|"max-autotune"`、`cudagraphs`。
- CUDA Graph 捕获：静态 shape/静态地址约束、`cudagraph_trees`、输入拷贝与内存池。
- 性能与缓存：融合、autotune、编译缓存目录、首次编译开销、预热。

**排除范围**

- 通用编译器理论（SSA、寄存器分配、指令调度算法）。
- 其他后端（XLA、TensorRT、ONNX Runtime、TVM）的内部实现，仅作对比。
- 手写 Triton/CUDA kernel 的编写方法（见 K11），本域只关心 Inductor 何时生成它们。
- `torch.export` 的完整序列化契约（见 K10），但共享 Dynamo 抓图机制。

判断归属：如果话题的核心是“Python 代码如何变成图/内核，以及这个转换的边界与正确性”，属于本域；如果是“某个 kernel 怎么写”，属于 K11；如果是“编译后到底快了多少、如何测”，属于 K09。

## 先修知识

- **Python 执行模型**：字节码、frame 对象、PEP 523（`frame.f_eval` 级求值钩子）。Dynamo 不是静态分析，而是在运行时逐帧跟踪。
- **自动微分与 functionalization**：反向图、叶子/非叶子、in-place 与 view 的语义（见 K02）。AOTAutograd 需要把可变操作“函数化”。
- **FX Graph**：`torch.fx.Graph`/`GraphModule`：Node、target、args/kwargs。看懂 Dynamo 抓出的图是调试起点。
- **张量形状与设备语义**：广播、dtype 提升、device 一致性（见 K01）。这些是 guard 与分解的基础。
- **算子融合与内存层级**：为什么融合 elementwise 能省内存带宽，为什么 matmul 不该被融合掉。属于理解 Inductor 的动机（亦见 K09）。
- **Triton 基础概念**：block、program、launch grid。不需要会写，但要能读懂 Inductor 生成的 Triton。
- **常见瓶颈来源**：Python 解释器开销、kernel launch 开销、内存带宽。理解 `reduce-overhead` 与 CUDA Graph 为什么存在。

## 核心机制

### 1. 三阶段流水线总览

```
your_fn / model.forward
        │
        ▼
┌───────────────────────┐
│ TorchDynamo           │  逐帧跟踪 Python bytecode
│  → FX Graph + guards  │  不支持处 graph break，回退 eager
└───────────────────────┘
        │  一张或多张子图
        ▼
┌───────────────────────┐
│ AOTAutograd           │  functionalize（消除可变）
│  → 联合 forward+backward│  分解（decompose）到基本算子
│  → 分区（partitioner） │  min-cut 减少保留的激活
└───────────────────────┘
        │  前向图 + 反向图
        ▼
┌───────────────────────┐
│ TorchInductor         │  lower 到 loop-level IR
│  → 融合 + 调度        │  autotune
│  → codegen (Triton/C++)│  → 缓存 .so / kernel
└───────────────────────┘
```

一次 `torch.compile` 调用通常要经历：首次运行触发抓图与编译（慢，可能秒级到分钟级），之后命中缓存直接跑。因此**基准测试必须先预热**。

### 2. Dynamo：抓图与 guards

```python
import torch

def f(x, y):
    return torch.relu(x @ y + 1.0)

cf = torch.compile(f)
x = torch.randn(1024, 1024, device="cuda")
y = torch.randn(1024, 1024, device="cuda")
cf(x, y)   # 第一次：抓图 + 编译
cf(x, y)   # 命中缓存
```

- Dynamo 在 frame 求值时把张量操作记录成 FX Node，遇到“无法符号化”的 Python 行为就 **graph break**：把已抓到的部分编译执行，剩下的回退 eager，再继续抓下一段。
- 产出不只是图，还有 **guards**：一串布尔条件，描述“这张图在什么前提下有效”：
  - 张量属性：`shape`、`dtype`、`device`、`stride`（有时）、`requires_grad`。
  - 非张量：Python 对象的类型、`id`、常量值、模块属性。
- 每次调用先求 guards；全部通过才复用旧图，否则**重新编译**（recompile）。

**guard 不通过 → 重新编译**是性能陷阱：形状每变一次就编一次。

```python
# 形状不断变化的输入 → 反复编译，编译时间吃掉所有收益
for n in [1, 2, 3, 4, ...]:
    cf(torch.randn(n, 128, device="cuda"))
```

Dynamo 有 recompile limit（`torch._dynamo.config.cache_size_limit` / `recompile_limit`），超过后放弃编译退回 eager。具体配置名与默认值以目标版本为准 [待验证]。

### 3. Graph break：来源、观测与处理

**典型触发源**

- 数据依赖的控制流：`if x.sum() > 0:`（`x` 是张量，值未知）。
- `.item()`、`.tolist()`、`.numpy()`、`.cpu()`：把张量值拉回 CPU，图必须断。
- `print`、日志、`assert` 里含张量值。
- 注册表/全局状态查询、类型分发、`getattr` 到动态属性。
- 自定义对象、numpy 交互、部分 `torch.*` 未被支持的算子。

**观测**

```python
# 打印为什么断图
explanation = torch._dynamo.explain(f)(x, y)
print(explanation.graph_break_count)
print(explanation.break_reasons)

# 环境变量日志
# TORCH_LOGS="graph_breaks"  只看断点
# TORCH_LOGS="dynamo"        完整 Dynamo 跟踪
# TORCH_LOGS="guards"        看 guard 求值
# TORCH_LOGS="recompiles"    看重新编译原因
```

**处理策略**

- **消除**：把 `.item()` 换成张量运算；用 `torch.where` 替代 Python `if`；把 host 侧逻辑移到图外。
- **标记跳过**：`torch._dynamo.disable` 让某函数始终 eager；`torch.compiler.disable(fn)` 是较新接口 [待验证]。
- **信任自定义 op**：`torch._dynamo.allow_in_graph(fn)` 或 `torch.library.custom_op` 让 Dynamo 把整个函数当一个节点抓进去（正确性自负）。
- **强制成功**：`torch.compile(f, fullgraph=True)` 在遇到 graph break 时直接报错，用于暴露隐藏断点。

**注意**：graph break 不是错误，但每次断图都损失一部分融合与重叠机会，并把中间张量物化到显存。评估编译收益时应先看断图数量。

### 4. AOTAutograd：联合图与激活优化

- **Functionalization**：PyTorch 允许 in-place（`x.add_`）与 view 别名。AOTAutograd 把它们改写成函数式（生成新张量 + 显式 mutation 列表），否则反向与图优化都不安全。
- **Joint graph**：前向和反向合成一张图，再 partition，把 node 分配给 forward 或 backward。
- **Partitioner（min-cut）**：目标是选择一条切分，使 forward 需要保存到 backward 的**激活内存最小**。这就是“重算换显存”的自动版本：某些中间量不保存，反向时重算。
- **Decompositions**：把复合算子拆成更少、更易融合的基本算子，同时保证分解后的反向更容易。分解表是能量与正确性的来源，版本间会变。

**失败模式**

- 某些高阶梯度（`create_graph=True`、double backward）或自定义 autograd.Function 可能无法 functionalize/分区，退回 eager 或报错。
- 就地修改输入张量后再跨 graph break 使用，可能触发 copy-back 或错误别名假设。

### 5. Inductor：lowering、融合、codegen、autotune

- **Lowering**：FX 图 → loop-level IR（TensorBox / FlexibleLayout → Loop）。在这一层做布局推断（连续/转置/广播）。
- **融合**：把多个 elementwise / reduction 合成一个 kernel，减少 HBM 往返。这是 `torch.compile` 对 memory-bound 模型提速的主要来源。
- **Scheduling**：决定 tile 大小、block 维度、循环顺序、是否用 shared memory。GPU 上生成 **Triton**；CPU 上生成 **C++/OpenMP**。
- **Autotune**：对候选配置实测，选最快的。`max-autotune` 会显著拉长首次编译时间。
- **Codegen 缓存**：生成物写到磁盘缓存（`TORCHINDUCTOR_CACHE_DIR`，默认在 `/tmp/torchinductor_<user>` 之类位置 [待验证]），跨进程复用；改代码/改配置会使相关缓存失效。

```python
model = torch.compile(
    model,
    mode="default",       # default / reduce-overhead / max-autotune / max-autotune-no-cudagraphs
    dynamic=False,        # 默认关闭动态 shape
    fullgraph=False,      # True 时遇 graph break 报错
    backend="inductor",   # 默认
)
```

**后端**：`inductor`（默认）、`aot_eager`（抓图但不生成优化 kernel，用于定位“是抓图还是 codegen 的问题”）、`cudagraphs`、以及各厂商后端。切换后端是隔离问题的常用手段。

### 6. mode 与 CUDA Graph 捕获

| mode | 主要动作 | 适用 |
|---|---|---|
| `default` | 融合 + 常规调度 | 通用起点 |
| `reduce-overhead` | 额外用 **CUDA Graph** 降低 CPU/launch 开销 | 小 kernel 多、launch 密集，且 shape 静态 |
| `max-autotune` | 对每个算子做 Triton 配置 autotune | 想让 matmul/attention 逼近手写性能 |
| `max-autotune-no-cudagraphs` | 只 autotune，不用 CUDA Graph | 需要 autotune 但不能用图捕获时 |

**CUDA Graph 捕获的硬约束**

CUDA Graph 把一串 kernel launch 录制成一张图，之后一次 launch 重放，省掉逐个 host 侧下发。它要求：

1. **静态形状**：图里的 shape 被固化。
2. **静态地址**：参与张量的显存地址必须稳定。`cudagraph_trees` 的做法是：为每个输入准备固定缓冲，重放前把真实输入拷贝进去。
3. **不能有非法操作**：图内不能有需要 host 同步/动态分配/改变地址的操作（如 `.item()`、某些动态 shape kernel）。
4. **内存池固定**：捕获期间分配的显存被 graph 私有池接管，地址固定。

**失败模式**

- 输入 shape 变化 → 捕获的图不适用，触发回退或重新捕获；配合 `dynamic=True` 常常直接禁用 CUDA Graph。
- 输入被原地改写 → 下次重放读到脏数据；`cudagraph_trees` 会尝试拷贝输入规避，但用户原地改输入仍可能出错。
- 只跑一次就测性能 → 看到的是捕获开销，不是稳态；必须预热。
- 显存池增长：多次捕获不同形状会累积多个图与池，显存上升。

### 7. 动态 shape

- 默认 `dynamic=False`：每个新 shape 生成特化图（可能反复重编译）。
- `dynamic=True`：用**符号形状**（`SymInt`）编译一张能覆盖一段形状范围的图。代价是部分优化（如 autotune、CUDA Graph）受限，且需要足够的形状多样性“泛化”，否则仍会 guard 失败。
- 手动控制：
  ```python
  torch._dynamo.mark_dynamic(x, 0)      # 标记第 0 维为动态
  torch._dynamo.constrain_as_size(n, min=1)  # 约束符号形状可用作 size
  ```
- 符号形状在 guard 中用表达式比较，避免“每个 batch 大小都重编译”。但某些动态维度会被特化（例如参与整除判断），仍可能重编译。

### 8. 编译缓存与生命周期

- **缓存键**包含：代码、guards 条件、后端配置、Inductor 配置、设备能力等。
- 缓存分两层：Dynamo 的已编译 frame/图缓存（进程内），Inductor 的磁盘生成物缓存（跨进程）。
- **失效**：改源码、改 `torch._dynamo.config`、改 `torch._inductor.config`、改依赖算子实现都会失效。
- 工具：`torch._inductor.utils` 下的缓存清理入口、`TORCHINDUCTOR_CACHE_DIR` 指定位置。接口以目标版本为准 [待验证]。
- **调试重置**：`torch.compiler.reset()` 清掉进程内缓存，强迫重新编译（用于确认“是不是缓存导致行为不一致”）。

**训练态与推理态的差异**：`model.train()` 与 `model.eval()` 会改变 dropout/BatchNorm 的分支，Dynamo 会为不同分支生成不同图；`eval()` 下若包在 `torch.no_grad()`/`inference_mode` 中，AOTAutograd 不再需要反向图，编译路径与训练态不同。部署前应在**目标态**下预热并验证，不能拿训练态的编译结果推断推理性能。图缓存以代码与配置为键，切换 `train()`/`eval()` 不会自动失效，需显式重置或分别编译。

### 9. 编译栈调试工作流

```
1. 先确认 eager 是否真的慢        → profiler 看 Python/launch 占比
2. 量化 graph break              → torch._dynamo.explain / TORCH_LOGS=graph_breaks
3. 换 aot_eager 后端对比         → 判断问题在抓图还是 codegen
4. 调 mode / dynamic             → default → reduce-overhead / max-autotune
5. 查重新编译                    → TORCH_LOGS=recompiles
6. dump 生成代码                 → TORCH_LOGS=output_code / TORCH_COMPILE_DEBUG=1
7. 与 eager 做数值对比           → 确认语义/精度一致
8. 用同一基线复测                → 收益必须大于噪声
```

- **`TORCH_LOGS="output_code"`**：打印 Inductor 生成的 Triton/C++，用于确认融合是否发生、kernel 长什么样。
- **`TORCH_COMPILE_DEBUG=1`**：把各阶段产物（FX 图、loop-level IR、生成代码）dump 到目录，逐步对照 [待验证]。
- **数值对比**：编译会改变算子分解与归约顺序，可能出现末位浮点差异；比较时用容差，并区分“合理浮点误差”与“真 bug”。
- **二分回退**：`torch._dynamo.config` / `torch._inductor.config` 里可关闭某类优化做二分，定位是哪一步引入变慢或数值差异。

## 常见陷阱与反例

- **反例：直接跑一次就宣称“编译更快”**。首次包含抓图 + codegen + autotune；必须 warmup 后再计时，并在相同条件下对比 eager。

- **反例：数据依赖控制流**
  ```python
  def f(x):
      if x.sum() > 0:      # graph break
          return x * 2
      return x + 1
  ```
  正解：`torch.where(cond, x * 2, x + 1)` 保持图完整（两个分支都会算，但可融合）。

- **反例：`loss.item()` 用于日志放在被编译的 forward 里**，每步断图。做法：把日志与 `.item()` 移到编译范围之外。

- **反例：以为 `torch.compile` 一定加速**。对已高度优化的自定义 kernel、或 Python 开销不是瓶颈的场景，编译可能变慢（编译开销 + 不完美的融合）。必须实测。

- **反例：`reduce-overhead` 与动态 batch size 混用**。CUDA Graph 要求静态 shape，二者冲突；要么修 shape，要么不用 CUDA Graph。

- **反例：编译后直接原地改输入**
  ```python
  with torch.cuda.graph(g): out = model(inp)  # 概念示意
  inp.copy_(new_data)                          # 若在错误时机，可能读到旧/脏数据
  ```
  依赖 `cudagraph_trees` 的输入拷贝机制，不要假设任意原地改写都安全。

- **反例：把 `fullgraph=True` 当默认**。模型里任意一处断图都会报错；它是调试开关，不是生产默认。

- **反例：忽略 recompile**。看到“首次快、之后忽快忽慢”，大概率是 shape/guard 变化导致反复编译。用 `TORCH_LOGS="recompiles"` 确认。

- **反例：在 `torch.compile` 范围内抛 Python 异常 / 做 I/O / 动态 `getattr`**。这些会把图切碎，收益归零。

- **反例：用 `aot_eager` 后端测性能**。它故意不做 kernel 优化，只用于定位问题；拿它比性能毫无意义。

- **反例：改了 Inductor/Triton 配置却以为复用旧缓存**。配置进缓存键，改配置必然重新编译。

- **反例：把 graph break 当 bug 去追**。它是设计边界。先量化断图带来的损失，再决定是否值得消除。

- **反例：拿训练态的编译结果推断推理性能**。`train()`/`eval()` 分支不同、有无反向图不同，图与缓存都不同，必须在目标态单独预热与验证。
