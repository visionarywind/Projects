# K09 性能、显存与算子分析

## 范围

关键路径、带宽、算力、通信、显存、profiler 和统计方法。

## 领域边界

**纳入范围**

- 计时与观测：`torch.profiler`（kineto 后端）、CUDA event 计时、NVTX 标注、Chrome trace 导出、`key_averages`。
- 瓶颈分类：CPU-bound / GPU-compute-bound / memory-bound / 通信-bound / 同步停顿，以及如何从 timeline 与计数器判断。
- 性能模型：算术强度、roofline、ridge point、带宽与算力的上界推导。
- 显存分析：缓存分配器（caching allocator）的 block/segment/pool、`memory_allocated` vs `memory_reserved`、`memory_summary`、`memory_snapshot`、碎片、`expandable_segments`。
- 激活内存：激活随 batch × 序列 × 层数的增长、梯度检查点（checkpoint）的取舍。
- 外部工具集成：Nsight Systems（系统级 timeline）、Nsight Compute（kernel 级 roofline/计数器）、`nvidia-smi dmon`。
- 统计方法：warmup、多次迭代、中位数/分位数、A/B 交错、控制变量、时钟与温度。

**排除范围**

- 手写 kernel 的优化（见 K11），本域只做“定位 + 建模 + 度量”。
- 分布式通信内部协议（见 K07），本域关注“通信是否成为瓶颈、重叠是否生效”。
- 编译器内部（见 K08），本域关注“编译后到底快了多少”。
- 硬件微架构细节（SM 内部流水、bank 冲突的电路级解释），只在解释计数器时点到。

判断归属：如果话题的核心是“测量、定位、建模与显存核算”，属于本域；如果是“把某个算子写得更快”，属于 K11。

## 先修知识

- **CUDA 异步执行模型**：host 下发、device 排队、stream 内有序、跨 stream 并发；launch 是异步的。
- **同步语义**：`.item()`、`.cpu()`、`torch.cuda.synchronize()` 何时强制同步，以及同步如何制造“气泡”。
- **事件计时**：CUDA event 记录在 stream 上，`elapsed_time` 只在两个 event 都完成后有效。
- **内存层级**：HBM 带宽、L2、shared memory、寄存器；为什么 memory-bound 算子受带宽限制。
- **算术强度**：`FLOPs / bytes`，以及峰值算力与峰值带宽的比值（ridge point）。
- **缓存分配器概念**：PyTorch 不每次 `cudaMalloc`，而是维护池；理解池才能理解 `reserved` 与碎片。
- **基础统计**：均值/中位数/方差、离群值、样本量。性能数字的噪声常被低估。

## 核心机制

### 1. torch.profiler 与 kineto

```python
from torch.profiler import profile, ProfilerActivity, schedule, tensorboard_trace_handler

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=schedule(wait=1, warmup=1, active=3, repeat=1),
    on_trace_ready=torch.profiler.tensorboard_trace_handler("./log"),
    record_shapes=True,
    profile_memory=True,
    with_stack=True,
) as prof:
    for step, batch in enumerate(loader):
        train_step(batch)
        prof.step()          # 驱动 schedule 状态机
```

- **activities**：`CPU` 记录 host 侧算子/调度；`CUDA` 记录 device kernel、memcpy、CUDA Graph。
- **schedule(wait, warmup, active, repeat)**：`wait` 跳过、`warmup` 预热（丢弃）、`active` 采集、循环 `repeat` 次。避免把编译/首拉开销算进去。
- **记录维度**：`record_shapes` 记张量形状、`profile_memory` 记分配、`with_stack` 记 Python 栈（额外开销大）。
- **输出**：
  ```python
  print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
  # 按 self_cuda_time_total / self_cpu_time_total 排序看热点
  # 导出 Chrome trace：
  prof.export_chrome_trace("trace.json")
  ```
- **重叠判读**：timeline 里 CPU 一行、GPU 一行。若 CPU 段长时间在“launch/调度”而 GPU 空闲 → CPU-bound/launch-bound；若 GPU 条几乎无缝铺满 → GPU-bound。

**开销警示**：profiler 本身有开销（尤其 `with_stack=True`、高频采集），采集期的时间不能当作真实性能数字；用 warmup 段丢弃、用非采集期做基准。

### 2. CUDA event 计时

```python
start = torch.cuda.Event(enable_timing=True)
end   = torch.cuda.Event(enable_timing=True)

# 预热若干次
for _ in range(warmup):
    run()

start.record()
for _ in range(iters):
    run()
end.record()
torch.cuda.synchronize()          # 关键：等 device 真正做完
ms = start.elapsed_time(end) / iters
```

- event 计时的是 **device 时间线**，比 CPU `time.time()` 准确，且不受 host 调度抖动影响。
- 必须 `synchronize()` 后读 `elapsed_time`，否则读到的是未完成的状态。
- 循环里不要放 `.item()`/`.cpu()`/`print`，否则把异步拆成同步，测到的是延迟而非吞吐。
- 若要分别测 CPU 与 GPU：`torch.cuda.Event` 给 GPU；`time.perf_counter()` 给 host 侧下发吞吐。

### 3. 瓶颈分类

| 类型 | 现象 | 判据 | 常见根因 |
|---|---|---|---|
| CPU/launch-bound | GPU 条有大量空隙，CPU 在忙 | CPU 时间 ≈ 墙钟，GPU 利用率低 | Python 开销、算子太碎、DataLoader、频繁同步 |
| GPU compute-bound | GPU 条满，算力计数接近峰值 | SM/FP 单元利用率高 | 大 matmul/attention，算力饱和 |
| Memory-bandwidth-bound | GPU 满但算力远低于峰值 | DRAM 吞吐接近峰值带宽 | elementwise/reduction、缺融合、多余拷贝 |
| 通信-bound | 多卡 timeline 出现长 NCCL 段，计算被等待 | 通信时间占比高、重叠差 | allreduce/FSDP all-gather、拓扑差 |
| Sync stalls | timeline 出现“CPU 等待 GPU 或反之”的空档 | `.item()`/`.cpu()`/`synchronize` 附近 | 控制流拉回 host |

**定位顺序建议**：先看 GPU 利用率（`nvidia-smi`）区分“GPU 忙不忙”，再用 profiler timeline 区分“等 CPU / 等通信 / 真的在算”，最后用 Nsight Compute 对热点 kernel 做 roofline。

### 4. Roofline 与算术强度

对某个 kernel 或算子：

```
算术强度 I = FLOPs / bytes_moved      # 单位：FLOP/byte
峰值算力 P (FLOP/s) 与 峰值带宽 B (bytes/s)
ridge point I* = P / B

若 I < I*  → memory-bound，上限 ≈ B · I
若 I > I*  → compute-bound，上限 ≈ P
```

**如何建模一个算子**

- 逐元素 `y = a*x + b`：每元素读 2 write 1（简化）→ I ≈ 极低 → 纯带宽受限，融合是唯一出路。
- 归约 `sum(x)`：读一次、算一次加 → 带宽受限。
- GEMM `C = A@B`（M=N=K=n）：FLOPs ≈ 2n³，bytes ≈ 3n² → I ≈ (2/3)n，随 n 线性增长，大 n 时 compute-bound。

**示例（仅示意，数字 [待验证]）**：某数据中心 GPU 峰值 fp16 张量算力约数百 TFLOPS、HBM 带宽约 1–3 TB/s，ridge point 在几十到上百 FLOP/byte 量级。具体值随型号、dtype、是否用张量核变化，必须查目标硬件规格。

**用途**：给出“这个 kernel 理论上限是多少”，据此判断优化空间；roofline 图把“已达带宽上限”和“远未达算力上限”分开。

### 5. 显存分析

```python
print(torch.cuda.memory_summary(abbrev=False))
print("allocated:", torch.cuda.memory_allocated() / 1e9, "GB")
print("reserved :", torch.cuda.memory_reserved() / 1e9, "GB")
print("max alloc:", torch.cuda.max_memory_allocated() / 1e9, "GB")
```

**allocated vs reserved vs total**

- `allocated`：当前真正被张量占用的字节。
- `reserved`：缓存分配器从 CUDA 拿到的总池（含已 free 但留在池里的 block）。
- `reserved - allocated`：池内空闲（碎片/可复用空间），**不等于泄漏**。
- `total`：设备总显存。OOM 发生在 `reserved` 增长到接近 `total` 时。

**缓存分配器（caching allocator）**

- 以 **block** 为单位分配，按 **segment** 从 CUDA 申请大块，再切成 block。找到可复用 block 就不调 `cudaMalloc`。
- block 按大小分桶；请求大小落在哪个桶决定能否复用。大小略变的请求可能落到不同桶 → 复用失败 → 新 segment → 碎片。
- 每个 stream 有独立的池；跨 stream 复用受限。

**碎片类型**

- **reserved-allocated 差距大**但 allocated 并不高：池里有很多无法复用的 block（形状/生命周期错配）。
- **OOM 但 `nvidia-smi` 显示有空闲**：可能是池无法扩展、或别的进程占用。
- 缓解：`PYTORCH_CUDA_ALLOC_CONF`，如 `expandable_segments:True`（让 segment 可增长，减少碎片，具体支持以版本/设备为准 [待验证]）、`max_split_size_mb` 限制拆分。

**memory_snapshot：定位泄漏**

```python
torch.cuda.memory._record_memory_history(max_entries=100000)
# ... 跑一段训练 ...
torch.cuda.memory._dump_snapshot("mem.pickle")
# 用工具把 pickle 渲染成 timeline，看每块显存在哪分配、谁持有
torch.cuda.memory._record_memory_history(enabled=None)  # 关闭
```

接口名以目标版本为准 [待验证]。用途：区分“持续增长的真泄漏”与“峰值导致的 OOM”。

### 6. 激活内存与梯度检查点

**激活内存**粗略模型（每层保留的反向所需中间量）：

```
A ≈ batch_size × seq_len × hidden × layers × k × bytes_per_elem
```

`k` 是每层保留张量的个数（视算子实现）。这解释了为什么：

- 增大 batch 或序列长度会**线性**推高激活，先于参数触顶；
- 长序列/大模型 OOM 主要来自激活。

**梯度检查点（activation checkpointing）**

```
普通：保存所有中间激活，反向直接用     → 显存高、算力省
检查点：只保存段边界激活，反向前向重算 → 显存低、算力多一次前向
```

- 典型把每层的激活内存从 O(L) 降到 O(√L)（分段检查点）或 O(1)（逐层），代价是额外一次前向。
- 权衡：memory-bound 场景下重算可能几乎免费（反正不是算力瓶颈）；compute-bound 场景下重算代价明显。
- 与 AMP、FSDP 组合时，检查点对显存峰值的贡献需要单独 profiling。

### 7. Nsight 集成与 NVTX

- **Nsight Systems（`nsys`）**：系统级 timeline，覆盖 CPU 线程、CUDA API、kernel、NCCL、memcpy。适合看“谁在等谁”。
- **Nsight Compute（`ncu`）**：单 kernel 级，给 roofline、DRAM/L2 吞吐、SM 利用率、occupancy、stall 原因。适合热点 kernel 微观定位。
- **NVTX 标注**：把业务语义打进 timeline。
  ```python
  with torch.cuda.nvtx.range("forward"):
      out = model(x)
  torch.cuda.nvtx.range_push("backward")
  loss.backward()
  torch.cuda.nvtx.range_pop()
  ```
- **二者分工**：先用 `torch.profiler` / `nsys` 找热点与瓶颈类型，再用 `ncu` 深挖单个 kernel 为何慢。不要一上来就 `ncu` 全量跑。
- 本工作区 `LeetCUDA/` 的 profiling 模块（Triton/CUTLASS/Nsight 资料）与 `cuda/` 的 stream/kernel launch 生命周期可作为交叉参考。

### 8. 统计方法

**基准测试的基本纪律**

1. **预热**：丢弃前若干次（CUDA context、cudnn benchmark、`torch.compile` 首次编译、分配器扩张）。
2. **多次迭代 + 聚合**：报中位数或 p50/p90，而不是单次或均值（离群值拉偏均值）。
3. **控制变量**：同进程、同设备、同 dtype、同输入分布、同 batch。A/B 交错跑，避免热/冷漂移。
4. **锁定时钟/温度**：GPU 会动态降频（功耗/温度）；未锁定则前后不可比 [待验证 具体锁定手段与权限]。
5. **分离测量**：把 host 侧数据准备与 device 侧计算分开测，避免把 DataLoader 时间混进算子时间。
6. **明确口径**：说清是延迟（单次）还是吞吐（单位时间处理量）、是否含通信、是否含 ZLUDA/图捕获。
7. **噪声估计**：跑多组，给出方差；两组差异小于噪声时不要下结论。

### 9. 端到端定位工作流

```
1. nvidia-smi / dmon        → GPU 空不空？（区分 CPU-bound）
2. torch.profiler timeline  → 谁在等谁？kernel/memcpy/NCCL 各占多少？
3. key_averages 排序        → 前 N 个热点算子
4. Nsight Systems           → 复现并确认系统级瓶颈（多进程/多卡）
5. Nsight Compute (热点)    → roofline：带宽受限还是算力受限？
6. memory_summary/snapshot  → 是否 OOM/碎片/泄漏？
7. 改一处 → 用同一套基线复测 → 确认收益 > 噪声
```

### 10. 分层计时示例（一个训练 step）

把 step 拆成段分别计时，先回答“哪一段占比最大”，再对该段深挖：

```text
step 总时间
├─ data wait（DataLoader 取数）      ← CPU/IO，常被忽略
├─ H2D 拷贝                          ← PCIe/NVLink 带宽
├─ forward（若干 kernel）            ← 计算或带宽
├─ loss + .item()                    ← 同步点，制造气泡
├─ backward                          ← 计算 + 激活读写
├─ allreduce / all_gather（多卡）    ← 通信（见 K07）
└─ optimizer.step                    ← 计算 + 优化器状态读写
```

用 CUDA event 或 NVTX range 把每段括起来，或在 profiler 里按 NVTX 区间聚合。只有先定位到主因段，roofline / `ncu` 才有的放矢；否则容易优化了非瓶颈段。

## 常见陷阱与反例

- **反例：用 CPU 墙钟给 GPU 计时**
  ```python
  t0 = time.time(); run(); t1 = time.time()   # 只测到 launch 开销
  ```
  GPU 是异步的；不 `synchronize` 测到的是下发时间。用 CUDA event + synchronize。

- **反例：不做 warmup**。首次跑包含懒初始化、cudnn autotune、`torch.compile` 编译、分配器扩张，数字虚高。

- **反例：把 `reserved - allocated` 当内存泄漏**。这是缓存池里的空闲/碎片，不是泄漏。判断泄漏要看 `max_memory_allocated` 是否随迭代单调增长。

- **反例：`nvidia-smi` 利用率 100% 就以为算力打满**。利用率只表示“有 kernel 在跑”，可能是 pure-memory-bound 或大量小 kernel，算力远未饱和。

- **反例：用单次测量下结论**。GPU 抖动大；至少多次取中位数。

- **反例：在 profiler 采集期做基准计时**。profiler 有开销，数字偏慢。基准用非采集期（warmup/其间）。

- **反例：`.item()` 藏在日志/回调里**，造成隐藏同步停顿，timeline 上表现为 GPU 气泡。把日志移出热路径。

- **反例：对比两次运行但机器在降频/被别的进程抢占**。控制变量、锁频、独占设备。

- **反例：用 nsys/ncu 一次就抓全量**。`ncu` 逐 kernel 回放，全量巨慢且干扰大；先用 profiler 定位再精测。

- **反例：只盯单个 kernel 快慢，忽略端到端**。单个 kernel 变快但引入额外同步/拷贝，端到端可能更慢。

- **反例：CUDA Graph 场景不预热就测**。测到的是捕获开销；必须重放稳定后再计时。

- **反例：把 memory_snapshot 的“分配点”与“持有者”混淆**。快照能看分配时机，泄漏定位还需结合 Python 引用（是否被 list/dict 意外持有）。
