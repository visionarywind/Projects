# K04 数据管道与输入规范

## 范围

Dataset、Sampler、DataLoader、collate、padding、worker 和数据版本。

## 领域边界

本知识域覆盖数据从磁盘/内存到设备张量的整条通路：`torch.utils.data` 下的抽象（`Dataset`、`IterableDataset`、`Sampler`、`BatchSampler`、`DataLoader`）、批组织（`collate_fn`、padding、`drop_last`）、并发取数（`num_workers` 多进程、`prefetch_factor`、`persistent_workers`、`worker_init_fn`）、主机侧驻留（`pin_memory`）以及分布式分片（`DistributedSampler`）。

纳入范围的是这些组件对训练正确性、吞吐与可复现性的影响。明确排除：

- 存储格式与压缩算法本身（parquet、LMDB、WebDataset 封装）只在改变 `DataLoader` 行为时讨论。
- tokenizer/图像增强算法本身；这里只关心它们是否可安全地进入 worker、是否持有不可 fork 的状态。
- 模型侧对输入的消费（embedding、mask 构造）属于 K03/K08；分布式梯度同步属于 K07。
- 设备放置与张量布局细节属于 K01。

判据：如果把某问题改写成"如何把样本组织成 batch 并送达设备"，属于本域；如果改写为"如何在设备上计算"，属于相邻域。

## 先修知识

- Python 迭代协议：`__iter__`/`__next__`、生成器、`__getitem__`/`__len__`。
- 多进程基础：`fork` 与 `spawn` 的差异、进程间通信（队列/共享内存）、`pickle` 的限制（lambda、打开的文件句柄、CUDA 对象、锁不可序列化）。
- 操作系统概念：页锁定（pinned/page-locked）内存、`fork` 的写时复制、GIL 对纯 Python 取数的影响。
- PyTorch 前置：`Tensor.to(device, non_blocking=)`、CUDA 流语义（默认流与侧流）、`torch.Generator` 与全局 RNG 的关系（见 K01）。
- 分布式前置：`torch.distributed` 的 `rank`/`world_size` 与进程组初始化（见 K07），否则 `DistributedSampler` 只会被当作单机 sampler 误用。

## 核心机制

### Map-style 与 Iterable-style Dataset

两种契约决定 DataLoader 如何切分与调度：

- **Map-style**：实现 `__getitem__(index)` 与 `__len__()`。支持随机访问，因此可以使用 `Sampler` 生成 index 序列、`shuffle=True`、`DistributedSampler` 分片。`DataLoader` 只把 index（而非样本）在进程间传递。
- **Iterable-style**：实现 `__iter__()`，不保证 `__len__()`。适合流式/无法随机访问的数据。`DataLoader` 无法替你分片，必须由 `__iter__` 内部通过 `torch.utils.data.get_worker_info()` 判断当前 worker 并自行跳过/切分副本。

```python
from torch.utils.data import IterableDataset, get_worker_info

class ShardedStream(IterableDataset):
    def __init__(self, urls):
        self.urls = urls
    def __iter__(self):
        info = get_worker_info()
        if info is None:                 # 单进程 / num_workers=0
            urls = self.urls
        else:                            # 每个 worker 只读自己的分片
            urls = self.urls[info.id::info.num_workers]
        for u in urls:
            yield from read_records(u)
```

失败模式：Iterable-style 若不做分片判断，多 worker 下每个 worker 都会遍历全量数据，导致 epoch 内样本被重复 `num_workers` 次。

### DataLoader 的构造契约与互斥参数

`DataLoader(dataset, batch_size=1, shuffle=False, sampler=None, batch_sampler=None, num_workers=0, collate_fn=None, pin_memory=False, drop_last=False, timeout=0, worker_init_fn=None, multiprocessing_context=None, generator=None, prefetch_factor=2, persistent_workers=False, pin_memory_device='')`

互斥规则（违反会直接报错）：

- `sampler` 与 `shuffle=True` 不能同时给出。
- `batch_sampler` 与 `batch_size`/`shuffle`/`sampler`/`drop_last` 不能同时给出（`batch_sampler` 已内建这些语义）。
- `prefetch_factor` 仅在 `num_workers > 0` 时有效；`persistent_workers=True` 要求 `num_workers > 0`。

`collate_fn` 默认为 `default_collate`：对样本的每个字段沿 batch 维堆叠；遇到 `int` 转 `torch.long`，`float` 转 `torch.float`（具体 dtype 规则随版本演进 [待验证]）。变长序列必须自定义 `collate_fn` 做 padding，或使用 `pad_sequence`/`pad_sequence` 的封装。

```python
def collate_pad(batch):
    xs, ys = zip(*batch)
    lengths = torch.tensor([len(x) for x in xs])
    x = torch.nn.utils.rnn.pad_sequence(xs, batch_first=True)
    return x, torch.stack(ys), lengths
```

失败模式：自定义 `collate_fn` 若在 worker 内执行（`num_workers>0` 时 collate 发生在 worker 进程），其闭包必须可 pickle；引用主进程中的不可序列化对象会抛 `AttributeError`/`PicklingError`。

### Sampler 家族与 BatchSampler

- `SequentialSampler`：按 `range(len(dataset))`。
- `RandomSampler(dataset, replacement=False, generator=None, num_samples=)`：`replacement=False` 时长度等于数据集大小；`replacement=True` 时必须给 `num_samples`；随机性由 `generator`（缺省为全局生成器）驱动。
- `WeightedRandomSampler(weights, num_samples, replacement=True)`：按权重有放回采样，常用于类别不均衡。
- `SubsetRandomSampler(indices)`：只在给定子集上随机。
- `BatchSampler(sampler, batch_size, drop_last)`：把 index 序列切成 batch；`drop_last` 在最后一个不满 batch 时丢弃。

`shuffle` 与 `drop_last` 的语义落在 `RandomSampler` + `BatchSampler` 组合上：`shuffle=True` 等价于使用 `RandomSampler`；`drop_last=True` 只丢弃不足一个 batch 的尾部。语义正确性依赖两者组合，而非 `DataLoader` 单点。

### 多进程 worker 的执行模型

`num_workers` 是核心开关：

- `num_workers=0`：取数在主进程、与训练串行，简单但无重叠。
- `num_workers>0`：主进程把 index 放入 `index_queue`，worker 进程取 index、调用 `dataset.__getitem__` 与 `collate_fn`，把 batch 放入 `data_queue`；主进程消费。默认启动方式 Linux 为 `fork`，Windows/macOS(3.8+) 为 `spawn`（可用 `multiprocessing_context` 覆盖）。

伪代码（单个 worker 循环）：

```text
worker(worker_id, dataset, seed, index_queue, data_queue, collate_fn):
    set_seed(seed + worker_id)          # 见 worker_init_fn 小节
    if worker_init_fn: worker_init_fn(worker_id)
    while True:
        idx = index_queue.get()
        if idx == SENTINEL: break
        sample = dataset[idx]
        data_queue.put(collate_fn([sample]))
```

关键参数：

- `prefetch_factor`（默认 2）：每个 worker 预取多少个 batch。总预取量约为 `num_workers * prefetch_factor`。
- `persistent_workers=True`：epoch 结束后不销毁 worker，下一 epoch 复用，省去重新 fork 与重建数据集的成本；会持续占用内存。
- `timeout`：worker 在给定秒数内未产出 batch 则报错，用于发现卡死。

失败模式：

- `fork` 后子进程触碰 CUDA 会报 `Cannot re-initialize CUDA in forked subprocess`。取数逻辑、增强都不应初始化 CUDA；设备搬运应留在主进程。
- macOS/Windows 因 `spawn`，顶层脚本必须写 `if __name__ == "__main__":`，否则 worker 重新导入模块时会递归启动。
- worker 数过大时，`fork` 的写时复制失效（数据集在 worker 内被写）或 IPC 队列积压，反而降低吞吐；拐点取决于数据集大小与 CPU/PCIe 带宽 [待验证]。

### worker_init_fn 与随机种子

即使不传 `worker_init_fn`，`DataLoader` 也会在每次迭代开始生成一个 `base_seed`，并在每个 worker 中执行等价于：

```text
seed = base_seed + worker_id
random.seed(seed); torch.manual_seed(seed)
numpy.random.seed(seed)   # 若已导入 numpy
```

因此使用全局 `random`/`torch`/`numpy` 随机源做增强时，各 worker 默认会得到不同种子。但有两类陷阱：

1. 数据集在 `__init__` 中创建了独立的 RNG 对象（如 `random.Random(0)`、自建 `numpy` Generator），fork 后各 worker 持有完全相同的状态 → 增强结果重复。
2. 每个 epoch 使用相同 `base_seed`（当 `generator` 固定或手工传入相同 seed）会导致跨 epoch 增强模式固化。

`worker_init_fn(worker_id)` 用于显式重置这些私有随机源：

```python
def worker_init_fn(worker_id):
    info = get_worker_info()
    base = torch.initial_seed() % 2**32
    np.random.seed((base + worker_id) % 2**32)
    random.seed(base + worker_id)
    info.dataset.rng.seed(base + worker_id)   # 私有 RNG
```

### pin_memory 与 non_blocking 重叠

`pin_memory=True` 时，`DataLoader` 用一个后台线程把出来的 batch 拷到页锁定（pinned）主机内存。这样主进程可以：

```python
for x, y in loader:
    x = x.to(device, non_blocking=True)
    y = y.to(device, non_blocking=True)
    ...
```

`non_blocking=True` 使 H2D 拷贝对主机线程异步。需要精确理解重叠边界：

- 页锁定内存是异步 H2D 拷贝的前提；普通可分页内存的 H2D 通常必须同步（驱动会先暂存）。
- 拷贝默认在默认流上排队。若计算也在默认流上，则同一流内拷贝与 kernel 是**串行**的，此时 `non_blocking` 只让主机线程提前返回，并不与设备计算重叠。
- 要实现"上一迭代计算"与"下一迭代拷贝"真正重叠，通常需要侧流（side stream）+ 事件同步，或依赖框架的高阶 prefetcher。

失败模式：在 CPU 上 `pin_memory=True` 无收益甚至更慢；`non_blocking=True` 后立即读取张量、或张量未 pin，会静默退化为同步而看不出差别。相关吞吐数字必须实测 [待验证]。

### DistributedSampler

`DistributedSampler(dataset, num_replicas=None, rank=None, shuffle=True, seed=0, drop_last=False)`：

```text
num_samples = ceil(len(dataset)/num_replicas)      # drop_last=False
            = floor(len(dataset)/num_replicas)     # drop_last=True
indices = randperm(len(dataset)) if shuffle else arange(len(dataset))
if not drop_last: pad indices by wrapping to num_replicas*num_samples
indices = indices[rank::num_replicas]              # 交错分片
```

使用要点：

- 必须显式 `sampler=DistributedSampler(...)`，且**不要**同时 `shuffle=True`。
- `shuffle` 的分片每 epoch 需要调用 `sampler.set_epoch(epoch)` 才会变化；否则各 epoch 顺序固定，且各 rank 的同步随机性不正确。
- `drop_last=False` 时会用数据头部补齐，使各 rank 样本数相等；`drop_last=True` 则可能丢弃每个 rank 的尾部，配合 `BatchSampler(drop_last=True)` 才能保证 batch 数一致。

失败模式：`num_replicas`/`rank` 缺省时从默认进程组推断，若未 `init_process_group` 会退化为单进程语义 → 每个 rank 都取全量数据再各自训练，梯度同步下等价于放大 batch 却不报错。

### 数据加载瓶颈诊断

定位"GPU 打不满"是否源于数据管道：

1. 对比 `num_workers` 与 `num_workers=0` 的吞吐；若无提升，瓶颈可能在 CPU 增强或 IPC。
2. 用 `torch.profiler` 或 Nsight 观察 `H2D` 拷贝与 kernel 的间隙（见 K09）；大量气泡暗示取数不足。
3. 检查是否 `pin_memory` 且张量确实走了异步路径。
4. 逐步替换：去掉增强、缩小数据、调 `prefetch_factor`、开 `persistent_workers`，观察拐点。
5. `num_workers` 超过物理核数通常无益；纯 Python 取数受 GIL 限制，需靠多进程而非多线程。

### collate 与 padding 的细节

`default_collate` 对 batch 中每个样本逐字段处理，行为规则：

- 张量沿第 0 维 `torch.stack`；`numpy.ndarray`、数值标量转张量。
- Python `int`/`float` 按默认 dtype 转（`int64`/`float32`，具体随版本 [待验证]）。
- `dict`/`list`/`tuple`/`namedtuple` 递归 collate，保持容器结构。
- `str`、`bytes` 等不可堆叠类型保持为 Python 列表，不做张量转换。
- 样本形状在同一字段内不一致时 `stack` 报错——变长序列必须自定义 `collate_fn`。

变长序列的常见处理：

```python
def collate_pad(batch):
    xs, ys = zip(*batch)
    lengths = torch.tensor([len(x) for x in xs])
    x = nn.utils.rnn.pad_sequence(xs, batch_first=True)   # 右侧补 0
    return x, torch.stack(ys), lengths
```

- `pack_padded_sequence` 要求序列按长度降序排列；否则需 `enforce_sorted=False`。
- `pad_sequence` 只能补同维张量；多层嵌套结构需自定义递归 padding。
- 逐样本 padding 到 batch 内最大值（动态 padding）比全局 `max_length` 省显存，但每 batch 形状变化会触发 `torch.compile` 重编译（见 K08）。
- 用 bucketing 采样器把长度相近的样本放同一 batch，可显著减少 padding 浪费。

### 采样概率与 WeightedRandomSampler

`WeightedRandomSampler(weights, num_samples, replacement=True)` 中 `weights` 是每个样本被抽到的相对权重（非概率，内部归一化）。类别不均衡时常用"类频率倒数"。公式上第 `i` 个样本被抽中概率为 `w_i / sum(w)`（有放回）。`replacement=False` 时退化为对权重的无放回加权采样，需 `num_samples <= len(weights)`。失败模式：用未归一化或含零/负数的权重（负权无效），或把 `weights` 设为每类的样本数而非倒数——这会把不均衡放大而非纠正。

### 数据缓存与版本一致性

`DataLoader` 本身不做缓存。自定义缓存需注意：

- 多 worker 下每个 worker 持有独立内存副本，缓存在 `__getitem__` 内会各存一份 → 内存放大 `num_workers` 倍；应改用磁盘缓存或主进程预取。
- 缓存键必须包含变换（transform）版本，否则换增强后仍命中旧缓存，训练与验证看到不同数据分布（train/serve skew 的变体）。
- 数据版本变化（新增/删除样本）时，`len(dataset)` 与索引映射会变；断点续训需与 DataLoader 一致的数据快照，否则"第 N 步"对应的样本不再相同。

### 关键参数速查

| 参数 | 默认 | 作用 | 常见取值考量 |
|---|---|---|---|
| `num_workers` | 0 | 取数进程数 | 0 排查用；常取 CPU 核数的 1/2~1 |
| `prefetch_factor` | 2 | 每 worker 预取 batch 数 | 增大可掩盖抖动，占用内存 |
| `persistent_workers` | False | 跨 epoch 保留 worker | 数据准备昂贵时开启 |
| `pin_memory` | False | 页锁定主机内存 | GPU 训练开启 |
| `drop_last` | False | 丢弃不满 batch | 训练期通常 True |
| `collate_fn` | default | 组批函数 | 变长/多模态需自定义 |
| `timeout` | 0 | worker 超时秒数 | 定位卡死，>0 才生效 |
| `worker_init_fn` | None | worker 初始化 | 需精细控制 RNG 时 |

补充：`generator` 参数用于给 `RandomSampler`/worker 的 `base_seed` 提供确定性随机源。固定同一个 `generator` 种子可使整个取数顺序可复现；若不传，则每次迭代的 `base_seed` 不同，跨 run 不可复现。断点续训时若要让"第 N 步"对应相同样本，必须同时固定 `generator`、`worker_init_fn` 与 `sampler.set_epoch`。

### 数据加载瓶颈诊断决策树

1. 测 `num_workers=0` 与当前设置的吞吐差；无差 → 瓶颈不在取数。
2. 看 profiler 时间线（K09）：`H2D` 拷贝与 kernel 之间的空隙是否长期存在。
3. 检查是否 `pin_memory=True` 且确走异步；CPU 训练无收益。
4. 关掉数据增强再测；若吞吐跳升，瓶颈在增强（多为纯 Python/GIL）。
5. 逐步增大 `num_workers` 找拐点；拐点后吞吐下降说明 IPC/内存成为瓶颈。
6. 开 `persistent_workers` 观察 epoch 边界处的停顿是否消失。
7. 缩小样本或换更快的存储格式，区分"CPU 计算"与"IO"瓶颈。

## 常见陷阱与反例

| 陷阱 | 症状 | 根因 / 修正 |
|---|---|---|
| IterableDataset 未分片 | 每 epoch 样本重复 `num_workers` 次 | 用 `get_worker_info()` 切分副本 |
| fork 后初始化 CUDA | `Cannot re-initialize CUDA in forked subprocess` | 取数不碰 CUDA；`spawn` 或 `num_workers=0` |
| 私有 RNG 未重置 | 各 worker 增强完全一致 | `worker_init_fn` 重置数据集内 RNG |
| `sampler` 与 `shuffle` 同传 | 构造直接报错 | 二选一 |
| DistributedSampler 忘 `set_epoch` | 各 epoch 顺序固定、rank 间不同步 | 每 epoch 调用 `set_epoch(epoch)` |
| 未 `init_process_group` 就用 DistributedSampler | 每 rank 取全量、静默放大 batch | 先建进程组，见 K07 |
| `drop_last=False` + BN | 尾批 batch 均值/方差估计抖动 | 训练期 `drop_last=True` |
| macOS/Windows 缺 `__main__` 守卫 | 递归启动/卡死 | `if __name__ == "__main__":` |
| 变长序列用默认 collate | `stack` 形状不一致报错 | 自定义 `collate_fn` + padding |
| 大 `num_workers` + 大对象 | 内存暴涨、吞吐反降 | 调小 worker、精简样本、用 `persistent_workers` |
| `non_blocking=True` 但未 pin | 实际同步、无加速 | 先 `pin_memory=True` |
| collate 闭包不可 pickle | worker 构建失败 | 用顶层函数，避免 lambda/句柄 |

反例：把所有增强都放进 `__getitem__` 且使用 `np.random` 全局源却不设 `worker_init_fn`——看起来各 worker 不同，实际若 `generator` 固定，跨 epoch 与跨 run 的增强序列可能完全可复现，掩盖了大量重复。
