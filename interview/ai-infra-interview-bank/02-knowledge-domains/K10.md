# K10 性能、容量与可观测性

## 范围与定位

本域回答三类问题：**数字怎么测才可信**、**数字怎么解释**（归因）、**数字怎么用**（容量与扩容），是其他域的取证层。三条硬边界：**口径必须先于数字** [已确认] `insights/04-design-decision-and-validation.md:3-14`；**静态源码只能指出关键路径，不能替代 benchmark** [已确认] `sglang/99-roadmap/performance-guide.md:23-35`；**历史 profile 不能当当前数据** [已确认] `LeetCUDA/01-modules/M11-triton-cutlass-profiling/README.md:15-21`。与 K11 的分工是本域只处理"慢"、K11 处理"错"，但共用同一套分段定位。

## 核心概念与机制

### 1. 指标口径：先定义分母

- **定义**：同一词在不同语境指不同量，不约定口径的对比没有意义。
- **原理**：口径表逐项给出"等于什么、不等于什么"——KV occupancy = live KV ÷ physical capacity（≠ allocator allocated）；external fragmentation = free 总量与最大可满足请求的差异（≠ page 内浪费）；prefix hit ratio = 命中 ÷ 需处理 prefix（≠ cache size）；retraction rate = 被撤回 request/step（≠ OOM 次数）[已确认] `insights/04-design-decision-and-validation.md:5-14`。
- **不变量**：`cost/request` 的分母是"一个请求"，可以靠加 batch 换来改善而延迟变差；**至少同时报吞吐、TTFT、TPOT、P99、显存峰值和错误/撤回率**，平均值改善但 P99 或 abort 上升不能判定更优 [已确认] `insights/05-sglang-inference-technical-insights.md:399`。
- **例子**：调大 page 会让 internal fragmentation 升、external fragmentation 降，只写"内存效率"就看不出是哪一项变了。

### 2. 分段测量：把"慢"切成互斥的时间桶

- **原理（两套切法）**：服务侧五段 = 请求侧（tokenize/IPC/排队）→ prefill（prefix hit、chunk、KV 分配）→ decode（batch size、step 时间、retraction）→ worker（forward/collective/attention/sampling）→ 输出侧（copy-to-CPU、detokenize、stream 通知）[已确认] `sglang/99-roadmap/performance-guide.md:15-21`；驱动侧三段 = API CPU 时间 → 排队与提交延迟（`queued`/`submitted` 时间戳差）→ 分配/释放与 GPU 执行 [已确认] `musa/99-roadmap/performance-guide.md:71-79`。段必须首尾相接、互不重叠，否则归因会重复计数。
- **关键参数**：先单独测出空 API 调用基线（`InitPlatform` + `ApiTrace` + tools 回调），否则把固定开销误判成业务开销 [已确认] `musa/99-roadmap/performance-guide.md:53-59`；调优顺序不可跳步——workload 稳定 → prefix/KV 与 admission → decode batch 与 prefill budget → overlap / CUDA Graph / backend → 输出 IPC 与多卡通信 [已确认] `sglang/99-roadmap/performance-guide.md:27-33`。
- **例子**：低 GPU 利用率可能来自 tokenize/IPC 排队或 admission 拒绝，分阶段指标表把"归因于 batch 小"列为常见误判 [已确认] `insights/05-sglang-inference-technical-insights.md:386-397`。

### 3. FLOPs 与 MFU：同一尺度上的量

- **定义**：`MFU = 实际模型 FLOPs / (GPU 数 × 峰值 FLOPs × 运行时长)`。
- **原理**：step 时间分解为 `compute + comm + idle`，其中 `compute = 总模型 FLOPs / (卡数 × 峰值 × MFU)`，总 FLOPs 可由参数量、激活层、tokenizer 和数据集推算 [推断] `insights/05-megatron-architecture.md:1087-1100`。报告 MFU 必须给出口径（分子是否含 recompute、分母取稠密还是稀疏峰值），口径不同则数字不可比 [推断] `insights/05-megatron-architecture.md:1436-1443`。
- **例子**：改 overlap 后 step 时间降 8% 而 MFU 不变，说明省的是 `comm/idle` 而非 `compute`，报告须把两类收益分开写 [推断]。

### 4. 扩展效率与容量规划

- **定义**：weak scaling（每卡数据固定）与 strong scaling（总数据固定）测的是不同问题。
- **原理**：`扩展效率 = 基线吞吐 × 基线卡数 / (新卡数 × 新吞吐)` [已确认] `insights/05-megatron-architecture.md:1116-1122`；FLOPs 规划由目标 token 吞吐倒推卡数与 MFU 假设 [已确认] `insights/05-megatron-architecture.md:1124-1136`；推理容量由 KV 预算决定 `max_total_tokens ≈ floor(HBM_for_KV / bytes_per_token)` [已确认] `insights/04-design-decision-and-validation.md:35`。
- **不变量**：`cost/request` 要折算 GPU、CPU、存储、网络与重算，**它不等于吞吐** [已确认] `insights/04-design-decision-and-validation.md:14`——压低延迟的同时它可能上升，两个指标必须并列。
- **例子**：DP 从 8 扩到 64 若气泡占比上升、扩展效率跌到 60%，"加 8 倍卡得 8 倍吞吐"的容量计划会直接失败 [推断]。

### 5. 计时器、warmup 与统计：benchmark 的可信度

- **定义**：测量工具本身引入偏差，单次运行不构成证据。
- **原理（三条规则）**：① 必须记录 warmup、并发、输入输出长度、设备和版本，否则结果不可比较 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:50`；② benchmark 衡量吞吐/延迟/显存/kernel 性能，**不能作为 correctness 测试** [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:35`；③ 变体矩阵含 backend/device、API、execution、model/input、deployment 五维，单点结果不可外推 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:52-60`。
- **计时器选择**：超短操作上 GPU event 读数可能被主机侧提交时序污染；同一段代码同时用 GPU event 与 CPU 墙钟各测一遍，若 `gpu_ms / cpu_ms > 1` 说明 event 偏大；再看跨进程变异系数是否可接受 [待验证]（来自工作区外 `~/Workspace/insights/skills/bench-timing/SKILL.md`，本仓库无对应文档）。
- **例子**：只跑 0.2 ms 的 kernel，一次 `printf` 就能贡献几十微秒；把循环放大到总时长 ≥10 ms 后 CV 明显下降 [待验证] 同上。

## 常见误区

1. **"GPU util 低就说明有瓶颈"**。util 是时间占比不是工作量占比；静态源码与 util 都不能替代分段计时 [已确认] `sglang/99-roadmap/performance-guide.md:23-35`。
2. **"单次跑出来的数字就是结果"**。没有 warmup/并发/长度/设备/版本记录的结果不可比较 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:50`。
3. **"benchmark 通过 = 功能正确 / 延迟改善 = 整体更好"**。测试文件存在只证明入口存在，只有日志与结果才证明运行成功 [已确认] `sglang/01-modules/M18-testing-benchmark-ci/README.md:72`；`cost/request` 也可能反向变化 [已确认] `insights/04-design-decision-and-validation.md:14`。
4. **"直接改热路径试试看"**。热路径新增日志/断言/锁要在关观测开关的构建下复测；改合并与依赖扫描前要做多流、多设备、同步/异步四象限对比 [已确认] `musa/99-roadmap/performance-guide.md:83-88`。
