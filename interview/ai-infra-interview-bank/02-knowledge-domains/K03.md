# K03 显存、主机内存与存储

## 范围与定位

K03 处理"数据放在哪、谁拥有、什么时候能拿回来"：显存分配与池化、对象生命周期、pinned/pageable/统一内存三类主机侧内存、KV cache 的容量与分页、以及 OOM 与非法访问的定位方法。它在 AI Infra 栈中位于 K02（提交与完成语义）与 K04（数据跨设备搬运）之间——分配本身是 host 侧管理动作，但释放时机必须服从 K02 的完成证据，而跨卡/跨机的 KV 传输则进入 K04。

与相邻域的边界：K03 不讲 warp/带宽瓶颈的成因（K01），只把带宽当作 offload 与恢复的代价参数；不讲 stream 的依赖解析规则（K02），只引用其"完成才能复用"的不变量；不讲集合通信算法（K04），但 PagedAttention 的页大小会直接改变 RDMA/KV 传输的粒度，属于交界点。

证据结构上，本域有三条硬证据链：CUDA suballocator 的源码级三层模型、CANN SOMA 两级池与 Segment 状态机、SGLang 的 KV 分层池与 radix/allocator 行级分析；pinned 与 pageable 的 H2D 差异只有间接证据，具体速率对比标 [待验证]。

## 核心概念与机制

### 1. 三层显存池：用户对象、backing 块、物理分配

定义：CUDA 快照没有 `cuMemPool*` 公共 API，可确认的池化是"一次较大的 `CUmemblock` 被切成多个 `CUmemobj`，由 suballocator 的 best-fit radix tree 管理空闲区" [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:12`。

工作原理：`CUmemobj`（offset+size）→ `CUmemblock`（一次 backing）→ `DMAL.memblockAlloc/Free`（真实申请）三层 [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:14-24`。分配先按 descriptor 兼容性查 tree，再 best-fit；找不到就申请 `max(size, genericBlocksize)` 的新 block 并按 page size 向上取整 [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:30`。

关键不变量：descriptor 兼容比较 location、cache、type、layout、owner、mapping、page size、compression、handle types，**每种属性组合可能有独立的 suballocator tree** [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:33`。

例子：碎片率定义为 `(totalFree - largestFree) / totalFree`，只对可 suballocate 的 block 报告；`noSuballoc` block 碎片率固定为 0 [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:40`。

### 2. 两级池与 Segment 状态机（BUSY → CACHED → FREE）

定义：上层 Runtime 只改 segment 元数据，底层 Driver/HAL 持有大段 VA 与 HBM backing，真正的设备映射在指定 stream 上由 AICPU 任务执行 [已确认] `cann/memory_pool_analysis.md:12-19`。

工作原理：`freeSegs_` / `cachedSegs_` 按 `(size, basePtr)` 升序，`AllocFromFreeSegs` 的 `lower_bound` 选最小满足请求的 FREE segment，即 Best-Fit（同尺寸取低地址）[已确认] `cann/90-cross-module/memory-and-resource-lifecycle.md:74`。异步 free 默认不是 forceFree，段先进 CACHED，因为设备上可能仍有该 stream 的任务在用这块地址 [已确认] `cann/memory_pool_analysis.md:76-84`。

关键不变量：CACHED ≠ 可立即复用；当前 `TryToReuse` 直接返回 nullptr，实际流程会跳过 CACHED 只查 FREE [已确认] `cann/memory_pool_analysis.md:95`。

例子：64MB 池、2MB 粒度下，stream 7 先后申请 8MB/4MB，再异步释放 8MB——释放后的块保持 CACHED，直到满足 stream 顺序或 event 依赖 [已确认] `cann/memory_pool_analysis.md:35-95`。

### 3. pinned / pageable / 统一内存

定义：pinned（页锁定）内存可被设备 DMA 直接寻址；pageable 是普通可换页内存，需驱动内部暂存；UVM 让 CPU/GPU 共享同一虚拟地址，靠 fault/migration 补页。

工作原理：MUSA 侧 `muapiMemHostAlloc` 走 pinned host 分配，`Memory::PinnedHostAlloc` 按 flags 组合 property，MAP_FAILED 时 heap 降级 general [已确认] `musa/01-modules/M05-memory-mempool/source-map.md:30,67`。CUDA 侧 `memblockAllocResources` 在创建新 block 时依次保留 UVA、**检查 pinned-memory 限额**、调 DMAL 分配、再映射 [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:44`。

关键不变量：host register 要在 pin/map 能力不足时维护 Runtime 软件表，free/unregister 顺序必须与 location、map、pin 状态相符 [已确认] `cann/90-cross-module/memory-and-resource-lifecycle.md:82`。

例子：pinned 是有上限的稀缺资源，驱动用限额检查约束；把 pinned 当作"普通 malloc 加速版"会导致分配失败或挤占他人。

### 4. KV cache 容量与分页

定义：KV cache 是自回归推理中随 token 增长的主要显存消耗，容量可用一阶公式估算。

工作原理：

```text
bytes_per_token = num_layers × 2(K,V) × num_kv_heads × head_dim × bytes_per_element
```

[已确认] `insights/00-concepts-and-taxonomy.md:26`。PagedAttention 用 logical blocks → block table → physical blocks 解耦逻辑与物理，使 KV 可按需增长而不必物理连续 [已确认] `insights/03-arxiv-reading-notes.md:26-29`。

关键不变量：页内浪费与 kernel 访问开销随 page size 反向变化；`free_segment` 依赖"起点 page-aligned、每页固定 `page_size` 个 token"的契约，partial tail 释放的是完整最后一页而非半页 [已确认] `sglang/01-modules/M08-kv-cache/README.md:96`。

例子：SGLang 中 row 不足与 KV token slot 不足是**两种不同失败原因**，`available_size()` 同时计入 free 和 deferred release，"可立即取出的连续页"还要看 `merge_and_sort_free()` [已确认] `sglang/01-modules/M08-kv-cache/README.md:92,100`。

### 5. 两类风险：泄漏 vs 提前复用

定义：显存泄漏是"再也没人能释放它"；提前复用是"释放路径执行了，但设备还在读写它"。

工作原理：CUDA 释放时逻辑对象可先从用户可查找结构移除，**但物理 backing 是否立即回收取决于异步 tracking marker** [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:102`。CANN 侧 `rtFreeWithDevSync` 显式先同步设备再释放，它不是普通 free 的别名 [已确认] `cann/90-cross-module/memory-and-resource-lifecycle.md:101`。

关键不变量：任务引用的内存不能在完成前释放；只释放 GPU tensor 而不更新 request row、prefix node 或 request metadata，会让下一轮读到悬挂映射 [已确认] `sglang/01-modules/M08-kv-cache/README.md:82`。

例子：SGLang 的 `ReqToTokenPool` 释放时先断言请求持有 KV，再释放 row 并清除 `req_pool_idx`，用 row generation 区分重复利用后的生命周期 [已确认] `sglang/01-modules/M08-kv-cache/README.md:32`。

## 常见误区

- **"池化命中就是物理显存被复用"** —— 错。池化命中只证明复用已有 block，不证明 RM/设备端采用了某种物理页分配算法；"复用 block"与"释放 GPU 物理资源"必须分开描述 [已确认] `cuda/01-modules/M04-memory-uvm/gpu-memory-pooling.md:12,44`。
- **"free 返回了，显存就还给驱动了"** —— 错。SOMA 释放先转 CACHED，force free 才进 FREE [已确认] `cann/memory_pool_analysis.md:78`；MUSA 侧释放段先合并相邻空闲段，整个 chunk 空闲后还按 lazy-free 阈值决定保留或销毁 [已确认] `musa/01-modules/M05-memory-mempool/README.md:34`。
- **"异步提交后立刻复用 buffer 没问题"** —— 错。这正是与泄漏不同的一类风险：地址已被重新分配，设备仍在按旧命令写入，症状是偶发的错误数据或非法访问，且只在异步路径复现。
- **"OOM 就是显存不够"** —— 错。行不足与 token slot 不足是不同失败原因；page 内部碎片会让"free block 不少但可用 token 偏低" [已确认] `insights/01-static-dynamic-hybrid-pools.md:92`。
- **"offload 等于把显存变大"** —— 错。它把容量问题转化为 PCIe/NVLink/CPU 带宽、调度与恢复时延问题 [已确认] `insights/00-concepts-and-taxonomy.md:77`。
