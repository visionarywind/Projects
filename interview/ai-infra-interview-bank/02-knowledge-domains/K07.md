# K07 数据管道与数据血缘

## 范围与定位

数据管道位于存储层与训练 step 之间，回答一个问题：**每个 DP rank 第 N 步拿到哪一段 token**。它向上承接 tokenizer/split/blend 与索引文件，向下交付给 `get_batch`；Megatron 把 data loading 与 attention、P2P、gradient reduce 并列为性能关键路径，因素是 index cache、sampler、CPU→GPU 搬运和 TP broadcast [已确认] `megatron-lm/90-cross-module/performance-critical-paths.md:15-24`。

边界：与 K08 的接口是一条硬约束——sampler 产出的 rank-local batch 数量必须与 schedule 的 microbatch 数一致 [已确认] `megatron-lm/01-modules/M02-parallelism/README.md:51`；与 K10 的关系是 K10 提供分段计时，本域用它判断瓶颈在 decode、H2D 还是计算；与 K11 的关系是断点续读属可恢复性问题。需要声明：本仓库没有数据血缘的专门文档，凡涉及 manifest/checksum 一律标 [待验证]。

## 核心概念与机制

### 1. 索引化数据集：三张索引把变长文档变成定长样本

- **定义**：`GPTDataset` 把所有文档拼成连续 token 流，用 document index、sample index、shuffle index 映射回训练 sample [已确认] `megatron-lm/01-modules/M04-data-pipeline/implementation.md:15-17`。
- **工作原理**：document index 记文档边界，sample index 记第 i 个样本覆盖哪段 token，shuffle index 只重排样本顺序、不重排文档内部 token。
- **不变量**：tokens/labels 长度与 sequence-length 一致、loss mask 与有效 label 对齐、packed sequence 必须带 cu-seqlens、sampler 的 DP rank/size 决定每个进程的 batch [已确认] `megatron-lm/01-modules/M04-data-pipeline/README.md:35-40`。
- **例子**：两篇 3000 与 5000 token 的文档拼成 seq=4096，样本会跨文档边界；mask 漏配不会报错，只会让模型学到"上一篇结尾预测下一篇开头"的假相关。

### 2. 两级切分：global batch → DP rank → PP microbatch

- **定义**：global batch 先按 DP 切到各 rank，再在 rank 内按 PP 切 microbatch。
- **工作原理**：`build_pretraining_data_loader` 按 dataset 与 DP 参数构造 rank-local DataLoader，sampler（普通/random/CP/validation）决定取样语义，随机数据集包装器保证 seed 可复现 [已确认] `megatron-lm/01-modules/M04-data-pipeline/implementation.md:23-25`。
- **不变量**：同 DP 域内各 rank 样本互不重叠；microbatch 数不匹配 schedule 时在 group/schedule 层直接抛错 [已确认] `megatron-lm/01-modules/M02-parallelism/README.md:45-51`。
- **例子**：global_batch=64、DP=8、PP=4 → 每 rank 8 个样本、每 stage 2 个 microbatch。误配 global_batch=8 则每 rank 只 1 个样本，通信占比与梯度噪声同时上升 [推断]。

### 3. prefetch 与 worker：把读盘链路藏进计算

- **定义**：GPU 执行第 N 步时，CPU worker 提前完成读盘、解压、tokenize、拼 batch 并入队，主进程只取队列与 H2D。
- **工作原理**：这条链本身串行，prefetch 把它变成与 forward/backward 重叠的流水线；`get_batch` 取到字典后还要按 TP source rank 做 CUDA 搬运与广播，说明 H2D/广播就在链路上 [已确认] `megatron-lm/01-modules/M04-data-pipeline/implementation.md:27-29`。
- **关键参数**：worker 数 k、prefetch 深度、H2D 是否 pinned + 非阻塞。**不变量：稳态下只要最慢一段 / k > step 时间，GPU 就必然空转** [推断]。
- **例子**：单 worker 解码要 0.40 s、step 是 0.30 s，无论 GPU 多快每步都等 0.10 s；提到 k=2 才可能打满。若 CPU 核已被 tokenizer 与日志占满，加 worker 只会互相抢占——这是"调大反而变慢"的常见原因 [推断]。

### 4. shuffle buffer：随机性范围与吞吐的交换

- **定义**：对顺序读的数据源，维护容量 B 的缓冲区随机弹出样本，再从数据流随机补入。
- **工作原理**：样本可被移动的范围约等于 B；B 越大随机性越好，但解码缓存与顺序读局部性越差。B→∞ 即全局 shuffle，B=1 即完全顺序。
- **关键参数**：缓冲区内存 ≈ `B × seq_len × dtype_bytes × 字段数` [推断]；真实约束通常是 worker 内存上限。
- **例子**：按时间聚集的网页语料，B 太小会让模型连续看到同一时段文档，loss mask 层面无异常，但换数据源时曲线突然抖动。[待验证] 仓库无 shuffle buffer 实现与调参记录。

### 5. 数据血缘与幂等：证明"这次的数据和上次一致"

- **定义**：血缘是可核验的证据集合，幂等是"同输入重跑得到同取样序列"。
- **工作原理**：checkpoint 保存范围含模型、optimizer、scheduler、RNG、tokenizer、**数据加载状态与 tracker** [已确认] `megatron-lm/01-modules/M05-optimizer-checkpointing/README.md:41`；恢复链返回 iteration 与 consumed samples [已确认] `megatron-lm/01-modules/M05-optimizer-checkpointing/execution-flows.md:37-43`。
- **不变量**：`consumed_samples` 与 iteration 必须来自同一 checkpoint；tokenizer 与 index 版本必须进指纹；复现 ≠ 逐位相同（TP/PP 改变归约顺序）[已确认] `insights/05-megatron-architecture.md:1237-1244`。
- **例子**：换 tokenizer 后 index 文件名与 split 都没变，只比文件名会误判"数据一致"；正确做法是把 tokenizer 版本、split、seed、index checksum 写进 manifest 并比对 [待验证]（本仓库无该机制）。

## 常见误区

1. **"GPU util 低 = 数据管道瓶颈"**。分阶段指标表把"把低 GPU 利用率全归因于 batch 小"列为常见误判，同一现象也可能来自 tokenize/IPC 队列或 admission 拒绝 [已确认] `insights/05-sglang-inference-technical-insights.md:386-399`。正确认识：先分段计时再归因。
2. **"shuffle buffer 调大一定更好"**。B 只决定随机性与吞吐的交换点，超过数据有效多样性后收益归零，且单靠局部 buffer 达不到全局 shuffle [推断]。
3. **"DataLoader 不报错就等于数据正确"**。mask 错位、跨文档未屏蔽都静默污染 loss；正确性要靠不变量检查而非异常捕获 [已确认] `megatron-lm/01-modules/M04-data-pipeline/README.md:35-40`。
4. **"重跑一次数据当然一样"**。DP rank 数、epoch 包装、blend 权重变化都会改变取样序列；复现的单位是"配置 + checkpoint 状态"，不是数据目录 [已确认] `insights/05-megatron-architecture.md:1237-1244`。
