# K09 推理服务与弹性伸缩

## 范围与定位

本域覆盖一次生成请求从入队到吐出 token 的链路，以及副本数如何随负载变化。核心对象是 KV cache 的容量与生命周期、prefill/decode 两类负载的调度、replica 增减与路由。边界：与 K08 是"训练激活传输"与"推理 KV 传输"的同构不同生命周期，后者必须跨实例且幂等 [已确认] `insights/03-arxiv-reading-notes.md:116-118`；与 K10 是指标对象与测量方法的分工；与 K11 的 abort/retract/backpressure 属正常控制手段而非故障。

证据边界：容量与口径来自设计文档 [已确认]；分页与 P/D 结论来自 arXiv PDF 解析 [已确认，PDF] 但未本地复现；伸缩阈值与冷启动数据无文档，一律 [待验证]。

## 核心概念与机制

### 1. Prefill 与 Decode 是两种资源模型

- **定义**：prefill 一次处理整段 prompt 并产出 KV；decode 每轮只追加一个 token，却要读越来越长的历史 KV [已确认] `sglang/01-concepts/01-推理服务基础概念.md:32-49`。
- **原理**：prefill 是大矩阵运算、计算密度高但 shape 波动大，目标压 TTFT；decode 是小步反复，launch 开销与带宽主导，目标压 TPOT/P99 [已确认] `insights/05-sglang-inference-technical-insights.md:118-124`。
- **不变量**：continuous batching 的成员变化**只发生在 iteration 边界**，新请求不会被插入已发射的 kernel [已确认] `insights/05-sglang-inference-technical-insights.md:126-128`。
- **例子**：`t0` A/B prefill → `t1` A/B decode 且 C prefill → `t2` A 完成、B/C decode、D 加入 [已确认] `sglang/01-concepts/01-推理服务基础概念.md:57-63`。真实准入还要同时满足 token budget、page size、tree cache、最大 running 数、priority、chunking、PP microbatch、backend tile 八类约束 [已确认] `sglang/01-modules/M04-scheduler-batching/README.md:132-142`。

### 2. KV 容量预算与两种"不够"

- **定义**：KV cache 是每层 K/V 按请求持久化的部分，decode 靠它避免重算 prompt。
- **公式**：`KV_bytes = live_tokens × layers × 2 × kv_heads × head_dim × dtype_bytes`；再从 HBM 中减权重/workspace/激活/静态 buffer/通信 buffer/安全余量，得 `max_total_tokens ≈ floor(HBM_for_KV / bytes_per_token)` [已确认] `insights/04-design-decision-and-validation.md:16-36`。
- **不变量**：SGLang 里"容量不足"有两种原因——**request row 不够**与 **KV token slot/页不够**，前者不是后者 [已确认] `sglang/01-modules/M08-kv-cache/README.md:100`。分页下 `page_waste = allocated_pages × page_size − live_tokens`，是页内浪费而非外部碎片 [已确认] `insights/04-design-decision-and-validation.md:38-43`。
- **例子**：H100 80GB，权重 40GB、余量 10GB → KV 约 30GB；bytes_per_token=128KB 则约 24 万 token。输出长度未知时 reservation 不能取 `max_context_len`，要用历史分布 + SLO + 抢占重算成本 + 配额决定 [已确认] `insights/04-design-decision-and-validation.md:45`。### 3. 分页与前缀复用

- **定义**：PagedAttention 把每请求 KV 切成固定 token 数的 block，经 `logical blocks → block table → physical blocks` 三层映射，不要求物理连续 [已确认，PDF] `insights/03-arxiv-reading-notes.md:26-30`。
- **原理**：物理不连续消除外部碎片，按需增长缓解内部碎片；block 粒度共享与 copy-on-write 支撑 parallel sampling/beam search 的公共前缀 [已确认，PDF] `insights/03-arxiv-reading-notes.md:28-29`。SGLang 侧是两类映射：`ReqToTokenPool` 记"row 第 n 个 token 用哪个 slot"，`RadixCache` 记"前缀对应哪些 KV indices" [已确认] `sglang/01-modules/M08-kv-cache/README.md:15-22`。
- **不变量**：`ReqToTokenPool` 形状 `(size+1, max_context_len)`，row 0 是 padding row 承接 CUDA Graph dummy 读写 [已确认] `sglang/01-modules/M08-kv-cache/README.md:26-28`；**前缀命中受 page 对齐限制**，未对齐尾部不进 radix 节点 [已确认] `sglang/01-modules/M08-kv-cache/README.md:44`。
- **指标口径**：prefix hit ratio = 命中 ÷ 需处理 prefix（≠ cache size）；retraction rate = 被撤回 request/step（≠ OOM 次数）[已确认] `insights/04-design-decision-and-validation.md:10-11`。

### 4. Prefill/Decode 分离：KV 成为跨实例协议

- **定义**：prefill 与 decode 部署在不同实例、用不同 batch 配置，KV 由 prefill owner 产生、decode owner 消费。
- **原理**：P/D-Serve PDF 指出 KV 需在 P/D 间传输，并列出三挑战——prefix 多样性使简单 mixed pool 不足、workload 估计不准造成比例与迁移问题、cluster 级 RDMA 上固定 block 的 D2D 传输难打满 [已确认，PDF] `insights/03-arxiv-reading-notes.md:111-114`。
- **不变量**：KV ownership 从单进程 allocator 变成跨实例协议，transfer layer 必须幂等、支持 backpressure 与错误恢复 [已确认] `insights/03-arxiv-reading-notes.md:118`；control metadata 与 payload 可走不同通道，两者成功与否不能互推 [已确认] `insights/05-sglang-inference-technical-insights.md:365`。
- **例子**：HiCache 是纵向加层（GPU 外加 host/storage，做 prefetch/restore/eviction），P/D 是横向拆角色；利用率都提高但故障模型完全不同 [已确认] `insights/05-sglang-inference-technical-insights.md:344-365`。P/D 比例与迁移触发本仓库无实测 [待验证]。

### 5. 弹性伸缩：副本、准入与背压联动

- **定义**：伸缩 = 改变 replica 数 + 决定请求何时被拒绝、排队或降级。
- **原理**：Ray Serve 链路 `Deployment.bind → serve.run → Controller.deploy_applications → DeploymentState target/reconcile → replica start/health → router → DeploymentHandle.remote`，滚动更新、autoscaling、health check、backpressure 都是改变状态机的分支 [已确认] `ray/01-modules/M12-serve/README.md:14-33`。服务内部，`PrefillAdder` 预算不足返回 `NO_TOKEN`，允许截断时建立 chunked prefill [已确认] `sglang/01-modules/M04-scheduler-batching/README.md:94`。
- **不变量**：伸缩信号必须用请求侧指标——KV occupancy 是 live KV ÷ physical capacity，不等于 allocator allocated [已确认] `insights/04-design-decision-and-validation.md:7`。
- **例子**：新副本要拉权重、建 KV pool、预热 CUDA Graph，冷启动期间 QPS 已打入；只按排队数立刻扩会造成超调，只按 GPU util 扩又会因长 prompt 让两者反向变化 [推断]。阈值/冷却/冷启动耗时本仓库无文档 [待验证]。

## 常见误区

1. **"KV 占用 = 显存 allocated"**。后者还含 workspace 与碎片，用它做扩容信号会高估压力 [已确认] `insights/04-design-decision-and-validation.md:7`。
2. **"prefill 快 = 服务快"**。常见误判写明"单请求 kernel 快等于 TTFT 好"不成立 [已确认] `insights/05-sglang-inference-technical-insights.md:392`；两者指标不同，须分阶段观测。
3. **"GPU 完成 = 客户端收到"**。输出侧还有 D2H、detokenize 与流式背压，尾延迟常藏在这一段 [已确认] `insights/05-sglang-inference-technical-insights.md:397`。
4. **"cache 调大就等于命中高"**。命中受 prefix 分布与 page 对齐约束，容量与命中是两个变量 [已确认] `sglang/01-modules/M08-kv-cache/README.md:44`。
5. **"加副本一定降延迟 / 抢占就是故障"**。扩容有冷启动且原副本 prefix cache 不迁移，新副本初期命中率接近 0 [推断]；retraction 是预算不足的正常恢复路径，与 OOM 是不同事件，计入错误率会误导容量决策 [已确认] `insights/04-design-decision-and-validation.md:11`。
