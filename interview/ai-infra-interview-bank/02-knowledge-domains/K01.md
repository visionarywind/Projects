# K01 计算硬件与加速器

## 范围与定位

K01 是整个 AI Infra 栈的物理底座，回答两件事：一次计算在加速器内部到底怎么被执行，以及一个算子的性能上限由什么决定。它覆盖 SM/warp 执行模型、算力与带宽的量化关系（roofline）、HBM 访存层级、Tensor Core 一类矩阵加速单元，以及决定数据怎么在设备间流动的拓扑。本域只关心"设备内"与"设备标称能力"，不关心任务从哪里来。

与 K02 的边界很硬：K01 解释 warp 被谁调度、指令如何在 SM 上展开，K02 解释 host 线程如何把 kernel 送进设备队列。两者在"launch 完成"这个点交接——host 提交成功属于 K02 的完成语义，SM 上发生什么属于 K01。与 K03/K04 的边界是：HBM 容量与带宽、NVLink/PCIe 的带宽数值是 K01 层的输入参数，但显存分配器的生命周期（K03）和集合通信算法（K04）不归本域。

需要注意本仓库的证据结构：warp/SM 执行模型有源码级文档支撑，roofline 与硬件峰值数字主要靠推导，具体型号的带宽/算力标称值仓库无沉淀。

## 核心概念与机制

### 1. warp 是调度单位，SIMT 是执行模型

定义：GPU 不为每个 CUDA thread 提供独立取指与调度单元，而是把 thread 组织成 warp 后交给 SM 的 warp scheduler 调度 [已确认] `insights/sm-block-warp-technical-insight.md:102`。

工作原理：绝大多数 NVIDIA CUDA 架构中一个 warp 含 32 个 thread，`warp_count = ceil(threads_per_block / 32)`，末尾不满 32 的 lane 被屏蔽 [已确认] `insights/sm-block-warp-technical-insight.md:108-125`。同一 warp 共享一条指令流，但每个 lane 维护自己的寄存器值、地址和 predicate，这就是 SIMT [已确认] `insights/sm-block-warp-technical-insight.md:153-160`。

关键不变量：发散只发生在 warp 内部，不跨 warp；block 的 thread 数不是 32 倍数时，最后一个 warp 依然完整占位。

例子：`kernel<<<1,100>>>` 实际组织成 4 个 warp，第 4 个 warp 只有 4 个活跃 lane、28 个 inactive lane [已确认] `insights/sm-block-warp-technical-insight.md:129-140`。

### 2. SM 的资源占用与驻留

定义：SM 是承载 kernel 执行的主要硬件单元，内含 warp scheduler、指令分发、FP32/INT/LD-ST 执行单元、Tensor Core、register file、shared memory/L1 与 block/warp 驻留状态 [已确认] `insights/sm-block-warp-technical-insight.md:194-215`。

工作原理：grid 中的 block 被分配到 SM；block 完成释放资源后，调度器再把未执行的 block 填进来 [已确认] `insights/sm-block-warp-technical-insight.md:221-236`。

关键不变量：block 资源（寄存器、shared memory）用得越多，同一 SM 能驻留的 warp 越少，延迟隐藏能力越差——这是"GPU 性能问题不是 thread 数不够"四类根因之一 [已确认] `insights/sm-block-warp-technical-insight.md:183-188`。

例子：一个 block 用满寄存器时，SM 上驻留 warp 数下降，访存延迟无法被其他 warp 掩盖，吞吐掉下来但指令数没变。

### 3. roofline：算术强度决定用算力还是用带宽

定义：算术强度 AI = FLOPs / Bytes（每搬运 1 字节做多少次浮点运算）；roofline 把算子性能上限写成两条线的取小。

工作原理：

```text
P_attainable = min(P_peak, B_mem × AI)
AI_roof       = P_peak / B_mem     # 拐点：超过它就不再是带宽受限
```

[推断] 该式由算力/带宽两个标称上限直接导出，本仓库无 roofline 实测文档；仓库内最接近的可引证据是"先判断瓶颈是 global memory、shared memory、计算、同步还是 occupancy，再选优化手段"的优化顺序 [已确认] `LeetCUDA/99-roadmap/performance-guide.md:16-20`。

关键不变量：AI < AI_roof 时优化方向是减少搬运（融合、分块、量化），AI > AI_roof 时优化方向是提高并行度与指令吞吐。

例子：GEMM 的 AI 随 tile 尺寸上升，大 GEMM 落在 roofline 拐点右侧；elementwise kernel 的 AI ≈ 0.5，必然压在带宽线上——对应仓库中 `global load → arithmetic → global store` 的主路径 [已确认] `LeetCUDA/90-cross-module/performance-critical-paths.md:14-16`。

### 4. HBM 与"存储墙"

定义：HBM 是设备侧主存，容量与带宽同时构成推理与训练的硬约束。

工作原理：自回归 decode 每步只生成少量 token，却要读出全部权重与 KV cache，属于访存主导；仓库把它表述为"小步反复，launch/内存带宽更敏感"，而 prefill 是"较强计算密度，shape 波动大" [已确认] `insights/05-sglang-inference-technical-insights.md:116-124`。

关键不变量：当 AI 很低时，带宽而非算力决定 P99；用 CPU offload 换容量会把问题转移成 PCIe/NVLink/CPU 带宽与恢复时延问题 [已确认] `insights/00-concepts-and-taxonomy.md:77`。

例子：一个 KV cache 从 HBM 恢复到 GPU 的动作，同时抬高了带宽需求与尾延迟，而不是"显存变大了" [已确认] `insights/01-static-dynamic-hybrid-pools.md:93`。

### 5. Tensor Core 的对齐与 shape 要求

定义：矩阵加速单元以固定形状的 MMA 原子（如 `m16n8k16`）执行乘加，结果进 accumulator [已确认] `LeetCUDA/01-modules/M06-hgemm-tensorcore/data-structures.md:21`。

工作原理：实现路径从 naive → WMMA `m16n16k16` → MMA `m16n8k16` → CuTe/WGMMA，沿途必须处理 layout、shared-memory bank conflict 与访存/计算重叠 [已确认] `LeetCUDA/01-modules/M06-hgemm-tensorcore/README.md:13`。

关键不变量：M、N、K 必须与 MMA atom 和 tile 对齐；NN 布局用 shared-memory padding、TN 布局用 swizzle 消除 bank conflict，二者不可混用 [已确认] `LeetCUDA/01-modules/M06-hgemm-tensorcore/design.md:15`。

例子：`hgemm_mma_m16n8k16_*` 由模板参数决定每 warp 的 M/N tile、padding 与 stage 数，改 shape 必须同步改 launcher [已确认] `LeetCUDA/01-modules/M06-hgemm-tensorcore/implementation.md:53`。

## 常见误区

- **"GPU 有很多核心所以核越多越快"** —— 错。更准确的说法是 GPU 由多个 SM 组成，SM 内含多类执行单元，CUDA core 只是其中一类；warp scheduler 才是选择可执行 warp 的主体 [已确认] `insights/sm-block-warp-technical-insight.md:209-217`。
- **"分支写成 `?:` 就没有发散代价"** —— 错。短分支可能被编译成谓词指令，双路径"执行"变成双路径"求值后选择"，指令数仍增加；是否值得要反汇编或 profile 验证。
- **"算力高就一定快"** —— 错。roofline 是取小运算；AI 低于拐点时，提高 P_peak 对结果没有任何帮助，只能减少搬运字节数。
- **"优化后 TFLOPS 涨了就说明改对了"** —— 错。所有比较必须固定 GPU、驱动、dtype、shape、warmup、iters、同步点，且先过 correctness 与 sanitizer [已确认] `LeetCUDA/90-cross-module/performance-critical-paths.md:50`。
- **"block 的 thread 数设成 100 没有隐藏成本"** —— 错。仍占 4 个 warp 槽，末尾 warp 只用 4/32 lane，浪费的占位是隐性损失。
