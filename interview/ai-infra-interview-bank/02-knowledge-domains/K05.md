# K05 容器、Kubernetes 与节点

## 范围与定位

K05 回答"GPU 如何被装进容器、被调度器看见、被配额限制"。它站在驱动与编排的交界处：底层依赖 K02 提供的设备句柄与上下文，上层为 K06 调度器提供资源视图。本域覆盖 GPU 容器化组件栈（driver、runtime、device-plugin、容器运行时）、GPU 共享/隔离方案（MPS、时间片、MIG）、配额与可见性控制。

与 K06 的边界：K05 解决"单节点上 GPU 怎么被容器用"，K06 解决"多节点上任务怎么分到 GPU"。与 K02 的边界：K05 不重新解释 stream/context 语义，它只关心 host 侧如何把这些能力暴露给容器。

## 核心概念与机制

### 1. GPU 容器化的组件栈

要让容器内进程使用 GPU，至少需要四层协作：

| 层 | 组件 | 职责 |
|---|---|---|
| 内核 | 驱动（nvidia.ko / musa.ko） | 提供设备节点 `/dev/nvidia*`、管理 GPU 硬件 |
| 用户态库 | libnvidia-container / nvidia-container-runtime | 把驱动库与设备节点注入容器，替换默认 OCI runtime |
| 编排接口 | nvidia-device-plugin（DaemonSet） | 向 kubelet advertise GPU 资源，使调度器能分配 |
| 容器内 | 用户态驱动库（libcudart 等） | 与宿主机驱动版本 ABI 兼容 |

关键约束：容器内的用户态驱动库必须与宿主机内核驱动 ABI 兼容——这不是"版本相等"，而是"用户态版本 ≥ 内核驱动版本"的兼容方向 [推断]，具体兼容矩阵需查官方文档 [待验证]。

### 2. GPU 可见性控制

两种常用手段：
- **MPS + primary context**：多个进程共享一个 MPS context，由驱动内部做时间片交织 [已确认] `cuda/01-modules/M02/README.md:34`。隔离性弱——一个进程的 OOM 会拖垮同组进程，但利用率与吞吐最优。
- **MIG（Multi-Instance GPU）**：A100/H100 支持的硬件分区，把一张 GPU 切成最多 7 个独立实例，各有自己的 SM、显存、地址空间。隔离性强，但分区后总利用率通常低于 100% [推断]，且分区方案需重启 [待验证]。

### 3. device-plugin 的资源暴露

nvidia-device-plugin 向 Kubernetes 注册 `nvidia.com/gpu` 扩展资源。Pod 通过 `resources.requests/limits` 申请 GPU。配额在调度阶段生效（kube-scheduler 计数）、在运行阶段由 kubelet 调用 runtime 执行 [待验证]。

一个常见误解：device-plugin 不负责隔离，只负责"让调度器知道有多少 GPU"。隔离依赖 runtime + 用户态配置 [推断]。

## 常见误区

- "容器里装了驱动"：容器通常只需用户态库，内核驱动在宿主机。装反了反而可能引发版本冲突。
- "MIG 分区像 CPU 核一样灵活"：MIG 分区方案在驱动初始化时固定，修改需重启 [待验证]。
- "device-plugin 能限制单容器显存"：标准 device-plugin 只暴露整卡计数，显存限制需 MPS/MIG 或第三方方案 [待验证]。
