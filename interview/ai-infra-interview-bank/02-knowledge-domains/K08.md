# K08 分布式训练与容错

## 范围与定位

本域覆盖训练侧两件事：多卡如何协同（DP/TP/PP/SP/CP/EP）与坏掉后如何恢复（checkpoint、hang 检测、弹性与故障域）。`parallel_state` 负责 rank 拓扑与通信组，`pipeline_parallel/` 负责调度顺序与 P2P，二者都不拥有参数更新、也不构造数据集 [已确认] `megatron-lm/01-modules/M02-parallelism/README.md:14-16`。边界：与 K07 在 sampler/microbatch 契约处相接，与 K09 是"训练激活传输"与"推理 KV 传输"的同构不同生命周期 [已确认] `insights/05-megatron-architecture.md:1219-1223`，与 K10 是模型与测量的分工。

证据纪律：通信量与带宽数字要么来自论文/官方文档，要么标 [推断]，多卡实测一律 [待验证] [已确认] `insights/05-megatron-architecture.md:1436-1443`。

## 核心概念与机制

### 1. DP 梯度归约：每步必须做，且不止 all-reduce

- **定义**：各 rank 持完整副本、处理不同 microbatch，backward 后梯度必须归约成同一份。
- **工作原理**：`finalize_model_grads` 在 DP/CP/SP 域做 reduce-scatter 或 allreduce，之后 optimizer 才能用统一梯度更新 [已确认] `insights/05-megatron-architecture.md:476`。工程上按 gradient bucket 打包发送，bucket 边界按参数内存顺序对齐，以减少 NCCL 调用与 launch 开销 [已确认] `insights/05-megatron-architecture.md:488`。
- **不变量**：不归约的后果不是慢一点，而是 N 个副本从第 2 步起走出 N 条轨迹，checkpoint 失去意义。distributed optimizer 用 reduce-scatter 替代 allreduce，把优化器状态降到 1/N [已确认] `insights/05-megatron-architecture.md:495`。
- **例子**：7B 模型的 Adam 状态约 16–20× 参数量（84–105 GB），单卡装不下——这是分片优化器存在的根本原因 [已确认] `insights/05-megatron-architecture.md:1016`。

### 2. TP/PP/DP 的通信特征差异

- **定义**：三者通信的次数、体积、延迟敏感性不同，混为一谈会导致排布错误。
- **原理与数值**：TP 每层 forward 2 次 + backward 2 次 = **4 次 allreduce，与 t 无关** [已确认] `insights/05-megatron-architecture.md:589-599`；单次 ring 传输约 `2·(t-1)/t·s·b·h` 元素，每层合计约 `8·s·b·h·(t-1)/t` [推断] `insights/05-megatron-architecture.md:601-606`。PP 只有 stage 边界 P2P，延迟敏感体现在气泡与负载均衡；DP 每步一次、对带宽总量敏感 [已确认] `insights/05-megatron-architecture.md:499-508`。
- **不变量**：SP 不引入额外带宽——ring allreduce = reduce-scatter + all-gather，TP 的 4 次 allreduce 与 TP+SP 的 4 次 all-gather + 4 次 reduce-scatter 在带宽维度等价 [已确认] `insights/05-megatron-architecture.md:698-706`。
- **例子**：t=8 时单次只传 1.75 倍数据，几乎不随 t 恶化；"TP 越大通信越多"是误解，真正变多的是未重叠的 RTT 与变小的 GEMM [已确认] `insights/05-megatron-architecture.md:1291`，这也是 TP 限于同节点 NVLink 的原因 [已确认] `insights/05-megatron-architecture.md:606-608`。

### 3. 1F1B：在飞 microbatch 决定显存峰值

- **定义**：稳定阶段每个 rank 交替执行一次 forward 与一次 backward。
- **原理**：naive 管线最坏效率趋近 `1/PP`；1F1B 的收益是**在飞 microbatch 数被 bound 到 stage 数而非总 MB 数** [已确认] `insights/05-megatron-architecture.md:724-743`。
- **公式**：`efficiency ≈ 1 − (PP−1)/(MB+PP−1)`；`MB=4×PP` 约 81%，`MB=8×PP` 约 90% [已确认] `insights/05-megatron-architecture.md:745-753`。每 rank 驻留"本 stage 权重 + 优化器 + ≤stage 数个在飞 microbatch 的激活 + P2P 缓冲" [推断] `insights/05-megatron-architecture.md:788-793`。
- **不变量**：PP 减压的是权重与优化器状态，**不是激活**；激活要靠 microbatch 数、SP 和 recompute 单独控制 [已确认] `insights/05-megatron-architecture.md:1294`。
- **例子**：PP=4、MB=8，rank0 时间轴 `F0 F1 F2 F3 B0 F4 B1 …`，在飞 ≤4，首尾各 3 个时间片是气泡（正比 PP−1）[已确认] `insights/05-megatron-architecture.md:755-772`。

### 4. Checkpoint：状态完整性与异步边界

- **定义**：可恢复的 checkpoint 是能重启训练循环的完整状态集合，不是权重文件。
- **原理**：保存链 `save_checkpoint → 生成 model/optimizer/training state → dist writer → tracker`，恢复链含 `check_checkpoint_args` 并返回 iteration 与 consumed samples [已确认] `megatron-lm/01-modules/M05-optimizer-checkpointing/execution-flows.md:25-43`；分布式 checkpoint 用 sharded state dict，支持并行度变化后 reshard [已确认] `insights/05-megatron-architecture.md:1215-1217`。
- **为什么必须存优化器状态**：Adam 的 m/v 是跨 step 递归量，只恢复权重等于清零 moment，恢复后第一步用不同的有效步长，表现为 loss 尖峰；fp16 + 动态 loss scaling 下还可能直接 skip update [推断] `insights/05-megatron-architecture.md:1036-1050`。
- **异步边界**：异步保存依赖文件系统带宽，且必须在 step 完成后读取一致分片；保存窗口内若 overlap 重排改变累加顺序，跨配置逐位一致不保证 [已确认] `insights/05-megatron-architecture.md:309,1209`。

### 5. Hang 检测与爆炸半径

- **定义**：某 rank 停在集合通信里，其余 rank 永久等待。
- **原理**：检测靠 watchdog/heartbeat——记每个 rank 的"最近进度时间戳"，超阈值判 hang 并抓栈 [推断，本仓库无训练侧 watchdog 文档，待验证]。定位顺序：先 rank/env/config，再 tensor shape，再 backend/kernel；pipeline hang 首查 `schedules` 与 P2P，启动失败首查 `initialize.py`/`parallel_state.py` [已确认] `megatron-lm/99-roadmap/debugging-guide.md:15-24`。
- **不变量**：排查 collective hang 必须**按每个 group 分别**记录 members、local rank、shape、padding、顺序、是否 graph capture、rank 是否走不同分支——"所有 rank 都初始化完成"推不出 collective 正确 [已确认] `insights/07-parallel-and-backend-capability-matrix.md:193-200,292`。
- **故障域**：同交换机/同电力域下故障不独立，会把 `1−(1−p)^N` 抬高，因此 TP/EP 等高危集合通信应限制在最小物理域 [推断]。**万卡通信故障域的实测与设计本仓库完全没有，整体 [待验证]**。

## 常见误区

1. **"DP 就是复制 + all-reduce" / "TP 越大通信越多"**。前者：distributed optimizer 已把 reduce-scatter 与分片对齐，优化器状态可降到 1/N [已确认] `insights/05-megatron-architecture.md:1293`；后者：次数是常数 4、单次体积 `2(t−1)/t` 趋近饱和，真实代价是 GEMM 变小与未重叠延迟 [已确认] `insights/05-megatron-architecture.md:1291`。
2. **"checkpoint 只要权重就能接着训"**。丢 moment 等于换一个优化器重启，loss 尖峰是必然 [推断] `insights/05-megatron-architecture.md:1036-1050`。
3. **"逐位相同才算恢复正确 / 所有 rank 启动成功就算通信正确"**。前者只保证数学等价，验收应用梯度范数、loss 曲线与层参数 diff [已确认] `insights/05-megatron-architecture.md:1244`；后者的成员顺序、shape、次序不一致典型症状是 hang 而非报错 [已确认] `insights/07-parallel-and-backend-capability-matrix.md:292`。
