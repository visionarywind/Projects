# K02 驱动、运行时与设备管理

## 范围与定位

K02 描述 host 侧软件栈如何把一次计算送上设备并确认它完成：host 线程、device context、stream、event、异步提交、kernel launch 调用链，以及把多次 launch 合并成一次提交的 Graph。它处理的是"提交路径与完成语义"，不含 SM 内部执行（K01），也不含显存分配器的容量与碎片策略（K03）。

与相邻域的边界有三条。其一，K01 的 warp 调度发生在设备侧，K02 的 launch 链停在 host 提交与设备消费的交界——本仓库 CUDA 文档明确把"RM/firmware/GPU 消费"划为源码之外的未验证边界。其二，K03 的 buffer 复用时机完全由 K02 的完成证据决定：没有完成证据就不能复用，这使 K02 成为 K03 生命周期不变量的前置条件。其三，K04 的集合通信也以 stream/event 表达依赖，但通信原语本身的算法不归本域。

证据上，本域是仓库沉淀最厚的一块：CUDA 侧有端到端 launch 源码级拆解，MUSA 侧有提交合并与依赖解析的行级证据。

## 核心概念与机制

### 1. host 线程、TLS current context 与 stream 的关系

定义：current context 是**线程局部**状态，不是进程全局变量；stream 是某 context 下的命令提交顺序与依赖对象。

工作原理：CUDA 的 `cuiInitCheckEx` 检查顺序是"线程是否允许调用 → globals 是否 initialized → TLS current context → context 活跃/API 版本/sticky error" [已确认] `cuda/01-modules/M02-runtime-context/README.md:30`。MUSA 侧 `Context` 是资源生命周期中心，`Context::CreateMemory/CreateStream/DestroyMemory` 统一登记与回收 [已确认] `musa/00-overview/architecture.md:17-19,237`。

关键不变量：跨线程把 handle 传出去，不等于 context 已在目标线程成为 current [已确认] `cuda/01-modules/M02-runtime-context/README.md:38`。

例子：工作线程 A 创建 stream 后交给线程 B 提交 kernel，若 B 未设置 current context，提交会在前置检查阶段失败，而不是在设备侧失败。

### 2. kernel launch 是异步的，API 返回成功不是完成证明

定义：launch 把命令写入提交队列即返回，设备执行在 host 之后异步发生。

工作原理：CUDA 的一次普通 launch 不是单个函数调用，而是"参数/句柄检查 → TLS context → launchData packing → syscall 与 memory tracking → HAL 检查与 QMD 编码 → pushbuffer → GPFIFO entry 发布 → tracking semaphore/marker → completion 查询与 reclaim"的组合 [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:11-29`。`writeGPPut` 是发布新的生产者位置，**而非 GPU completion 证明** [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:274-278`。

关键不变量：`resource.reusable == true ⇔ task completion is proven`，完成证据必须绑定同步返回、event wait 或 callback 中的至少一种。

例子：`cuStreamDestroy` 的 host-side detach 不代表 GPU 已停用对应 QMD/pushbuffer，CUI 对象要等 marker 报告 GPU 完成才回收 [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:293-312`、`cuda/01-modules/M05-stream-submit/README.md:19-25`。

### 3. stream 与 event 控制异步顺序，默认流有隐性全局代价

定义：stream 内命令按提交顺序执行；event 用于跨 stream 建立 happens-before。

工作原理：MUSA 的 `Context::ResolveDependencyAndQueueCommand` 对默认流、barrier 流、普通 blocking 流走三套规则，最后统一 `QueueCommand` [已确认] `musa/01-modules/M06-stream-command/README.md:46`。默认流提交时会遍历该 context 下**所有**非 barrier、非 non-blocking 的流逐个 `RecordDependency`，流越多单次提交固定成本越高 [已确认] `musa/99-roadmap/performance-guide.md:45`。

关键不变量：同步默认流（MUSA `LockedSyncDefaultStream`）要等 context 内所有非 non-blocking 流 [已确认] `musa/01-modules/M06-stream-command/README.md:57`；`nullptr`/`MU_STREAM_LEGACY` 解析为默认流，`MU_STREAM_PER_THREAD` 解析为线程私有默认流 [已确认] `musa/01-modules/M06-stream-command/README.md:58`。

例子：一个高吞吐服务里混入默认流提交，等于给每条命令额外挂上全 context 的依赖扫描与隐性全同步。

### 4. launch 链各层的延迟来源

定义：从 API 调用到命令发布的每一段都是可测量的固定开销。

工作原理：MUSA 的固定开销包括每个 `muapi*` 开头的 `InitPlatform`、包装层 `ApiTrace` 构造/析构、以及 tools 回调 [已确认] `musa/99-roadmap/performance-guide.md:53-59`；排队段有 `QueueCommand` 的容量自旋与 `m_SubmitMtx`，提交段有 `AsyncSubmit` 的合批循环 [已确认] `musa/99-roadmap/performance-guide.md:24-25`。

关键不变量：微基准必须先单独测出"空 API 调用"基线，否则容易把固定开销误判成业务路径开销 [已确认] `musa/99-roadmap/performance-guide.md:59`。

例子：CUDA 侧的分层责任表把参数/引用/回滚放在 CUI、per-launch syscall 资源放在 syscall 层、ABI/QMD 放在 HAL、push 空间与顺序放在 stream/channel [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:219-227`——任何一层失败都意味着已付出但未产出的提交成本。

### 5. Graph：把多次 launch 压成一次提交

定义：CUDA/MUSA Graph 把操作记录为节点与依赖边，经 instantiate 编译成执行计划，launch 时一次性驱动。

工作原理：三阶段是 Capture（API 副作用转节点）→ Instantiate（验证、展开、拓扑排序、编译执行计划）→ Launch（接入 API stream 按依赖驱动）[已确认] `cuda/01-modules/M06-module-launch/graph-control-flow.md:9-41`。Graph launch 可把 scheduling group 中多个 kernel 节点合并到一个 push sequence [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:346`。

关键不变量：`cuGraphExecUpdate` 只允许改参数，改拓扑/节点类型/QMD 或 scheduler 需求会返回 update failure，因为 graph exec 已把控制流编译到 launch mode 与资源索引 [已确认] `cuda/01-modules/M06-module-launch/graph-control-flow.md:408-419`。

例子：MUSA Graph 承接 `capture / add-node → instantiate → launch → update → destroy` 全链路，是命令式 stream 之外的第二套依赖调度模型 [已确认] `musa/01-modules/M08-graph/README.md:13-15`。

## 常见误区

- **"API 返回 0 就说明算完了"** —— 错。CANN 文档把主机 API 成功、Runtime 元数据改变、Driver 接受请求、设备任务完成视为四个不同时刻 [已确认] `cann/90-cross-module/memory-and-resource-lifecycle.md:25`。返回成功只证明通过了当前层检查或进入队列。
- **"多开 stream 就一定更并行"** —— 错。默认流提交要遍历 context 内所有非阻塞流建依赖 [已确认] `musa/99-roadmap/performance-guide.md:45`；流数量越多，单次提交固定成本越高，且过度同步会把并发吃光。
- **"Graph 能加速任何负载"** —— 错。Graph 适合形状固定、launch 次数密集、依赖静态的重复结构；capture 期间把 API 记录成图而不是发布命令 [已确认] `cuda/90-cross-module/end-to-end-kernel-launch.md:164-177`，动态控制流必须走 conditional 节点，且 update 不得改拓扑。
- **"销毁 stream 就等于资源立刻可回收"** —— 错。公开 handle 在 detach 时立即失效，但 CUI 对象要等 marker 报告 GPU 完成才回到 free pool [已确认] `cuda/01-modules/M05-stream-submit/README.md:19-25`。
- **"sticky error 会在出错的那次调用返回"** —— 错。sticky error 在后续 API 的初始化检查阶段才出现，不能只在产生错误的异步提交点找返回值 [已确认] `cuda/01-modules/M02-runtime-context/README.md:39`。
