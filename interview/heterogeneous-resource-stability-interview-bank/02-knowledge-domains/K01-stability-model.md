# K01：稳定性目标、边界与故障模型

## 边界

本知识域定义“异构资源稳定性”这个目标本身：它由哪些可观察属性组成、在哪些故障模型下被评估、以及用什么语言描述失败。它不负责具体某个资源对象（Context、Stream、内存池、队列）的内部实现，也不提供具体的容量或性能数值。

本域解决三件事：

1. 给“稳定”一组可检查属性，而不是把“进程不崩溃”当定义；
2. 建立“提交 / 接受 / 完成 / 可见”四时刻模型，明确 API 返回值的证明力边界；
3. 建立故障模型与三态结果（`SUCCESS`/`FAILURE`/`UNKNOWN`），供其他域引用。

本域不负责：

- 设备能力与版本配套的具体判定（K02）；
- 生命周期销毁顺序（K03）；
- 内存池碎片与容量计算（K04、K11）；
- 完成证据的机制细节（K05）；
- 调度与配额的具体算法（K06）。

与相邻域的接口：K01 输出“契约 + 状态 + 证据”的判定框架；K02–K06 输出各自域内可核对的不变量；K07–K12 把局部不变量组合成拓扑、通信、恢复、观测、容量和演进策略。任何下游域声称“稳定”都必须回落到 K01 的五维交集和四时刻定义。

## 核心机制

### 1. 稳定性是五维交集，不是并集

稳定性契约应同时包含：

```text
稳定性 = 正确性 ∩ 可用性 ∩ 资源安全 ∩ 可恢复性 ∩ 可诊断性
```

- **正确性**：结果、顺序、数据可见性和资源归属正确；
- **可用性**：成功率、延迟、明确失败符合 SLO；
- **资源安全**：无泄漏、越界、重复释放、死锁和无界耗尽；
- **可恢复性**：可重试、迁移、降级或回滚，且不扩大故障；
- **可诊断性**：保留设备、Context、Stream、任务阶段和原始错误证据。

交集的含义是：任一维度失败都会破坏稳定，其他维度的高分不能补偿。一个只用平均延迟衡量的系统，即使 P99 严重超标，仍可能被误判为稳定。

### 2. 四时刻模型

CANN 文档把异步路径拆成四个不同时刻，并明确它们不必同时发生。[已确认] 来源：`cann/90-cross-module/memory-and-resource-lifecycle.md:25`。

```text
A 主机 API 返回
B Runtime 元数据改变
C Driver 接受请求
D 设备任务完成
```

- A 只代表当前调用阶段没有立即拒绝；
- B 代表软件对象或状态发生变化（例如 SOMA `Segment` 由 BUSY 转 CACHED）；
- C 代表请求进入 Driver queue/HDC/esched 等下游承载路径；
- D 才是设备执行语义，其具体时序在硬件上验证前属于 `[待验证]`。

只有拿到 D 的证明（同步、Event wait 或已确认 callback），结果才可消费、buffer 才可复用。K05 负责展开这一边界，K01 只负责给出“A ≠ D”的判定原则。

### 3. 三态结果

异步任务的结果不能只分成功和失败。K01 强制引入第三态：

```text
SUCCESS: 完成证据 + 结果校验通过   -> 可释放
FAILURE: 观察到明确错误             -> 按幂等性重试/降级
UNKNOWN: 超时 / 取消未确认 / 进程异常 -> 隔离, 不释放, 不盲重试
```

把 `UNKNOWN` 擅自转成 `SUCCESS` 会破坏仍被设备引用的数据；转成 `FAILURE` 并重试会重复副作用。三态模型是 K09 错误恢复、K10 观测和 K12 灾备的共同基础。

### 4. 故障模型与错误分类

错误沿“设备/驱动 → Runtime `rtError_t` → ACL `aclError` 或 GE `graphStatus` → 同步返回/异步回调/日志”向上传播。[已确认] 来源：`cann/90-cross-module/error-boundaries.md:16-24`。

错误按类别区分，不同类别对应不同的调用方动作。[已确认] 来源：`cann/00-overview/global-error-model.md:29-37`：

| 类别 | 示例 | 调用方动作 |
|---|---|---|
| 参数错误 | 空指针、数量不匹配、非法设备 ID | 修正参数，不重试同一请求 |
| 状态错误 | 未初始化、Executor 非 Loaded、活动 session 仍存在 | 按生命周期补齐或释放 |
| 资源错误 | 内存、Stream、Queue、HDC 资源不足 | 记录上下文，按策略清理/重试 |
| 设备/驱动错误 | 设备不可用、IOCTL/HDC 失败 | 检查驱动、固件、设备日志 |
| 编译/模型错误 | 图不合法、shape/算子不支持 | 回到模型和编译配置排查 |
| 异步错误 | callback 返回失败、任务执行失败 | 等待完成通知并保留原始错误上下文 |

分类的价值在于：它把“是否可重试”从直觉变成按类别的判定。参数错误和状态错误通常不能靠重试修复，异步错误必须等完成证据才能判定。

### 5. 故障域与爆炸半径

一个局部失败（单卡、单 Stream、单 session）不应无限阻塞其他请求。故障域的粒度可以是设备、Context、Stream、进程或节点。CANN 用一个具体例子说明残余状态风险：SOMA V3 free ioctl 失败时源码明确标注“不回滚”，上层 Runtime 元数据、Driver 用户态 VMM segment、远端 pool client 和 AICPU 操作可能短暂处于不同状态。[已确认] 来源：`cann/90-cross-module/memory-and-resource-lifecycle.md:93-97`。

这形成一个必须测试的故障窗口：

```text
SOMA free: 删除本地 VMM segment --(ioctl 失败)--> 设备侧未回滚
=> 本地元数据与设备侧状态可能不一致
```

故障隔离的目标是把不一致窗口限制在可解释、可恢复、可观测的范围内，而不是假装它不存在。具体隔离手段属于 K09（恢复）和 K06（隔离）。

### 6. 可观察指标

稳定性契约必须可验证。建议按维度和域给出可观察量：

- 可用性：成功率、P50/P95/P99、明确失败率；
- 资源安全：OOM 率、队列深度、资源水位、泄漏数、重复释放数；
- 可恢复性：检测时间、隔离时间、恢复时间、回滚成功率；
- 可诊断性：错误上下文完整率、证据关联命中率、最小复现成功率。

指标要绑定作用域（哪台设备、哪个池、哪一层）。笼统的“平均延迟”和“总空闲显存”都属于不可用于稳定性判定的口径，这一点在 K04 和 K11 会反复用到。

### 7. 契约范式

一个可检查的稳定性契约至少写明六项：输入、输出、状态转移、资源所有权、完成信号和失败动作。例如一个异步提交契约：

```text
输入:   buffer / model / stream / event / callback data
输出:   结果 buffer + 完成证据
状态转移: SUBMITTED -> DONE | FAILED | UNKNOWN
所有权: 调用方持有 buffer, 直至完成证据被观察
完成信号: 同步 / Event wait / 已确认 callback (非提交返回值)
失败动作: FAILURE -> 按幂等重试; UNKNOWN -> 隔离
```

契约的伪代码表达见 HRS-B001 的状态机练习。契约文本自身不证明任何硬件行为，硬件相关部分保持 `[待验证]`。

### 8. 稳定性、可用性、可靠性的区别

这三个词常被混用，但对异构资源系统的判定口径不同：

| 概念 | 回答的问题 | 典型指标 | 缺口 |
|---|---|---|---|
| 可用性 | 请求是否在约定时间内得到成功或明确失败？ | 成功率、SLO 达成率、P99 | 不保证结果正确、不保证资源安全 |
| 可靠性 | 结果是否正确且可持久？ | 结果 oracle 通过率、数据一致性 | 不保证可恢复与可诊断 |
| 稳定性 | 正常/紧张/局部故障下是否同时正确、可用、资源安全、可恢复、可诊断？ | 上表全部 + 泄漏、恢复时间、证据完整率 | 需要跨域协同 |

因此“服务可用”只是稳定性的一个子集，“高可用”强调可服务时间，“高可靠”还包含正确性和持久性；具体定义需结合组织语境。稳定性把三者放入交集，并补上资源安全、可恢复和可诊断。

### 9. 最小可验证状态机

一个不依赖真实设备的验证模型（见 HRS-B001 的实践设计）：

```text
任务状态: NEW / SUBMITTED / COMPLETED / FAILED / CANCELLED
资源状态: HELD / REUSABLE / RELEASED

事件: 提交成功 / 设备失败 / 超时 / 取消 / 重复完成
非法边(必须被拒绝): SUBMITTED -> RELEASED 且无完成证据
终态约束: COMPLETED/FAILED/CANCELLED 各只出现一次
引用约束: 所有路径结束后引用计数归零
```

该模型的 oracle 是：状态转移表中的非法边全部被拒绝，资源引用计数最终归零，终态无重复。它可以独立于硬件执行，是把“稳定性”从口号变成可检查对象的最小手段。真实 GPU/NPU 的异步时序和性能数据必须另行在目标环境验证，保持 `[待验证]`。

## 常见失效条件

- **把“进程存活”当稳定。** 反例：后台队列死锁，进程仍在但请求永不完成。
- **把“API 返回 0”当完成。** 反例：异步提交后设备执行失败，错误只在同步或 callback 处出现。
- **把超时当失败并直接重试。** 反例：任务可能仍在设备上运行，重试造成重复副作用并放大拥塞。
- **把 `UNKNOWN` 当成功并释放。** 反例：仍被设备引用的 buffer 被回收，产生数据损坏或悬空访问。
- **只看顶层错误码。** 反例：`ACL_ERROR` 掩盖了 Driver/HAL 的第一个失败边界。
- **增加资源掩盖生命周期缺陷。** 反例：根因是 Context/Stream 生命周期错误，加卡只会扩大泄漏范围。
- **用单一指标下结论。** 反例：吞吐很高但 P99 超出 SLO，或总显存充足但碎片导致分配失败。

## 关键不变量

1. **唯一终态**：每个请求最终只落入 `SUCCESS`、`FAILURE`、`UNKNOWN` 之一，且终态不可被后续事件改写。
2. **完成证明**：`resource.reusable == true` 当且仅当存在可观察的完成证据，不能由提交返回值推出。
3. **未知保守**：`UNKNOWN` 状态下不得释放被引用资源，也不得假设任务未执行而重试。
4. **类别对应动作**：错误分类到调用方动作的映射稳定，不因顶层错误码变化而改变重试策略。
5. **观测旁路**：日志、指标、Tracing、dump 不改变资源所有权和完成语义。[已确认] 来源：`cann/00-overview/global-error-model.md:39-43`。
6. **域内收敛**：一个故障域内的失败不应无条件阻塞其他故障域的请求。[推断] 具体边界随实现而定。

## 与其他知识域的连接

- → **K02**：能力快照的时效性与准入判定，是“稳定性契约在提交前成立”的前提。
- → **K03**：生命周期顺序是“资源安全”的主要来源，违序会破坏唯一终态和所有权不变量。
- → **K04**：内存池的分层可用量是“资源安全”和“正确性”的量化基础。
- → **K05**：完成证据机制直接实现“完成证明”不变量。
- → **K06**：调度与隔离决定故障域边界和可用性口径。
- → **K09**：三态模型与错误分类在本域定义，在 K09 展开超时、取消、恢复与注入。
- → **K10**：可诊断性维度在 K10 落成日志/指标/Tracing/dump 的证据链。
- → **K11/K12**：容量、成本、降级与演进策略都必须回落到本域五维交集验收。
