# 领域总览：异构资源稳定性

## 1. 领域定位

异构资源稳定性研究的是：当一个系统同时使用 CPU、GPU、NPU、专用加速器及其主机内存、设备内存、队列和通信链路时，如何在资源有限、执行异步、设备能力不同和局部故障存在的条件下，持续提供正确、可观测、可恢复且成本可控的服务。

稳定性不是“进程没有崩溃”或“API 返回成功”。至少要同时观察：

- **正确性**：结果、顺序、数据可见性和资源归属符合契约；
- **可用性**：请求能在 SLO 内完成或得到明确失败；
- **资源安全**：没有泄漏、越界、重复释放、死锁或不可控耗尽；
- **可恢复性**：局部失败能隔离、重试、迁移、降级或回滚；
- **可诊断性**：能沿设备、Context、Stream/Queue、任务和错误边界保留证据；
- **效率**：吞吐、延迟、容量和成本在约束内可接受。

## 2. 典型端到端链路

```text
应用/框架
  -> 设备发现与能力协商
  -> Context/Stream/Queue 建立
  -> Host/Device memory 与传输准备
  -> 异步任务提交
  -> Driver/HAL/设备执行
  -> Event/Callback/Synchronize 完成边界
  -> 结果返回、资源回收或故障恢复
```

在 CANN 证据基座中，GE 负责图和模型组织，Runtime 负责设备、内存、流、事件和任务接口，Driver 负责硬件接入；这是一条分层模型，不等于所有异构平台具有相同 API 或相同完成语义。[已确认] 来源：[cann/docs/project-understanding/00-overview/architecture.md:10-34]

## 3. 关键边界

- API 提交成功、Runtime 元数据更新、Driver 接收请求、设备任务完成是不同时刻；
- 主机指针、设备虚拟地址、物理 backing 和 DMA 可见性不是同一概念；
- “设备可用”需要包含能力、拓扑、驱动/固件、上下文和资源水位，而不只是枚举到一个编号；
- 恢复动作必须以任务幂等性、资源所有权和故障域为前提，不能盲目重试；
- 性能结论必须绑定设备型号、版本、shape、并发度、同步方式和测量口径。

## 4. 先修知识

C/C++ 或 Python 基础、操作系统进程/线程、虚拟内存、并发同步、网络基础、数据结构与复杂度、基本线性代数和性能指标。涉及特定厂商时，还需要阅读对应 Runtime/Driver API 和错误码文档。

## 5. 排除范围

本题库不替代具体设备的运维手册、固件升级流程或安全应急预案；不把 CUDA、MUSA、CANN、ROCm 的同名 API 当作可互换实现。真实硬件行为、固件错误码、跨节点网络和性能数字必须通过目标环境验证。
