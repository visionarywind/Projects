# 排障案例

这些案例用于训练“先保护用户，再定位首个分歧事件”的方法。示例数据是 fixture，非真实事故记录。

## 案例 1：成功率下降，模型未变

- **现象**：最终任务成功率下降，平均延迟上升。
- **先做什么**：冻结高风险写操作，保留 trace 和版本快照，按租户、任务桶、工具、索引、policy、队列分桶。
- **假设**：工具 429/超时、索引污染、权限变更、队列拥塞、prompt/config 漂移。
- **最小实验**：用脱敏 trace 回放；定位首个不同事件；逐一固定模型、工具、索引和 policy 做反事实替换。
- **oracle/指标**：golden trace 分歧位置、工具错误率、P95/P99、重试率、每成功任务成本；结论标 `[待验证]`。

## 案例 2：工具超时后重复退款

- **现象**：客户端未收到响应，重试后外部系统出现一笔或两笔退款。
- **判断**：超时只说明响应未知，不说明副作用未发生；进入 `UNKNOWN`，先用幂等键或外部查询确认。
- **修复**：将 canonical 参数和 run/step 绑定到幂等键；没有查询/去重能力时转人工对账，禁止盲重试。
- **oracle/指标**：外部副作用计数、对账差异、重复率、人工恢复时间。

## 案例 3：跨租户检索结果泄露

- **现象**：答案引用了另一租户的文档片段。
- **隔离步骤**：撤销受影响 run 的 capability，隔离缓存和索引，保留脱敏审计证据；不要把泄露内容复制进更多日志。
- **检查**：向量/全文检索过滤、cache key、RLS、权限快照、tool gateway 二次授权。
- **修复验证**：构造相同 query 的跨租户对抗 fixture，要求检索结果、上下文和最终答案均无越界来源。

## 案例 4：Agent 进入循环并耗尽预算

- **现象**：同一工具参数反复出现，token 和工具费用持续增长。
- **检查**：状态转移、重复 action signature、失败 observation 是否提供新信息、planner 是否忽略终止条件。
- **缓解**：步数/时间/token/工具预算、重复检测、circuit breaker、有限重规划；预算耗尽进入明确失败态。
- **oracle/指标**：循环检测延迟、最大步数、预算上界、用户可解释错误率。

## 通用排障模板

```text
保护面 → 固定版本 → 分桶 → 找首个分歧事件 → 最小回放
→ 反事实替换 → 修复/回滚 → 复测 oracle → 记录残余风险
```
