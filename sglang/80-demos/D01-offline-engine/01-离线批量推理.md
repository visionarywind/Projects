> Demo：D01。源文件：`examples/runtime/engine/offline_batch_inference.py`。本文解剖一个真实存在的 offline Engine 示例，不把它简化成“调用一个黑盒模型函数”。
>
> 版本证据以当前 checkout `78be4b50af88e9ea72d75b4c3a3e42b7297d2501` 为准。本文没有在当前环境下载模型或启动服务；涉及真实模型、GPU、子进程和端到端输出的部分均标记为“未验证”。
>
> 前置阅读：[启动链路](../../02-request-flow/01-启动链路.md)、[请求进入与分发](../../02-request-flow/02-请求进入与分发.md)、[模型执行与输出](../../02-request-flow/04-模型执行与输出.md)、[M07 分布式并行](../../01-modules/M07-分布式并行.md)。

## 1. Demo 要做什么？

示例只有一个目标：接收命令行中的模型参数，创建离线 `sgl.Engine`，把四个 prompt 作为一批请求送入模型，逐项打印生成文本。

```text
命令行
  -> argparse Namespace
  -> ServerArgs
  -> dataclasses.asdict(ServerArgs)
  -> sgl.Engine(**kwargs)
  -> 主进程 TokenizerManager + scheduler/detokenizer 子进程
  -> llm.generate(prompts, sampling_params)
  -> tokenization + IPC
  -> Scheduler 选择批次
  -> ModelRunner forward + sample
  -> BatchStrOutput / ReqState
  -> outputs[i]["text"]
  -> print
  -> atexit Engine.shutdown
```

**已确认**：上述入口和 Python 层连接都直接出现在示例或当前源码中。[`examples/runtime/engine/offline_batch_inference.py:1-43`][`python/sglang/srt/entrypoints/engine.py:222-346`][`python/sglang/srt/entrypoints/engine.py:383-491`]

**未验证**：没有实际模型文件，因此不能声称这条命令在本机成功完成生成。

## 2. 运行前提和命令

示例文件顶部给出的用法是：

```bash
python3 offline_batch_inference.py --model meta-llama/Llama-3.1-8B-Instruct
```

示例实际调用的是 `ServerArgs` 的 CLI 元数据，而不是手写一个只有 `--model` 的 parser：

```python
parser = argparse.ArgumentParser()
ServerArgs.add_cli_args(parser)
args = parser.parse_args()
server_args = ServerArgs.from_cli_args(args)
main(server_args)
```

`ServerArgs.add_cli_args` 先从 record field metadata 生成大部分选项，再注册运行时动态 choices，例如 sampling backend、reasoning parser 和 tool-call parser。[`python/sglang/srt/server_args.py:344-381`]

`from_cli_args` 只收集 Namespace 中确实存在的 record fields，让没有 CLI surface 的内部字段继续使用默认值。[`python/sglang/srt/server_args.py:418-424`]

### 2.1 关于示例中的 `--model`

本文以 checkout 中示例原样为证据。不同版本的 `ServerArgs` 可能把模型参数展示成 `--model-path` 或兼容别名；实际运行前应以当前 checkout 执行 `python3 offline_batch_inference.py --help` 的结果为准。

该 help 命令本身只解析参数，不下载模型；当前没有执行它，因此结果也是“未验证”。

### 2.2 `__main__` 为什么不能删除？

示例明确保留：

```python
if __name__ == "__main__":
    ...
```

注释给出的原因是 Engine 使用 `spawn` 创建子进程。spawn 会重新导入入口模块；没有这个保护，子进程可能再次执行 Engine 构造，从而递归创建更多子进程。[`examples/runtime/engine/offline_batch_inference.py:36-43`]

这不是装饰性的 Python 模板，而是该 Demo 的进程启动约束。

## 3. `main`：从 ServerArgs 到 Engine

### 3.1 prompts 和 sampling params 是两种不同输入

```python
prompts = [
    "Hello, my name is",
    "The president of the United States is",
    "The capital of France is",
    "The future of AI is",
]
sampling_params = {"temperature": 0.8, "top_p": 0.95}
```

- `prompts` 是四条独立请求的文本输入；
- `sampling_params` 是每条请求共享的采样设置；
- 这时还没有 token id、KV slot 或 GPU tensor；它们在 Engine/TokenizerManager 和 scheduler runtime 中才产生。

### 3.2 `dataclasses.asdict` 是兼容转换，不是推理

```python
llm = sgl.Engine(**dataclasses.asdict(server_args))
```

这一行做两件事：

1. 把 `ServerArgs` record 转成字典；
2. 用关键字参数调用 `Engine` 构造器。

真正的副作用从 `Engine.__init__` 开始：加载插件、确定 server args、注册 atexit shutdown，然后启动子进程。[`python/sglang/srt/entrypoints/engine.py:247-307`]

因此断点不应只放在 `main` 的这一行；应继续进入 `Engine.__init__` 和 `_launch_subprocesses`。

## 4. Engine 构造：谁在什么进程？

`Engine` 的类文档直接说明三部分：

```text
主进程：Engine + TokenizerManager
子进程：Scheduler
子进程：DetokenizerManager
```

其 ongoing IPC 使用 ZMQ；scheduler 启动 ready 使用 `mp.Pipe`。[`python/sglang/srt/entrypoints/engine.py:222-234`][`python/sglang/srt/entrypoints/engine.py:846-962`]

### 4.1 `_launch_subprocesses` 的启动阶段

当前普通路径的关键顺序是：

```python
configure_logger(server_args)
server_args.resolve_once()
_set_envs_and_config(server_args)
load_plugins()
server_args.check_server_args()
resolve_auto_parsers(server_args)  # 必要时
publish(server_args, role="tokenizer")
port_args = PortArgs.init_new(server_args)
scheduler_init_result, scheduler_procs = cls._launch_scheduler_processes(...)
_launch_detokenizer_subprocesses(...)
tokenizer_manager = init_tokenizer_manager_func(server_args, port_args)
scheduler_init_result.wait_for_ready()
SubprocessWatchdog(...).start()
```

这些语句位于 `Engine._launch_subprocesses`。[`python/sglang/srt/entrypoints/engine.py:1051-1260`]

要注意两个边界：

- `resolve_once`/`publish` 是配置投影，不能替换成“直接把原始 Namespace 传给所有子进程”；
- `wait_for_ready` 发生在 TokenizerManager 初始化之后，父进程不会把 scheduler 构造当作同步完成，直到收到 ready 信息。

### 4.2 scheduler 子进程的 ready 不是 process-started

scheduler 入口执行：

```python
load_plugins()
publish(server_args, role="scheduler")
dp_rank = configure_scheduler_process(...)
scheduler = Scheduler(...)
pipe_writer.send(scheduler.get_init_info())
scheduler.run_event_loop()
```

因此 ready pipe 的发送点在 `Scheduler(...)` 构造之后。[`python/sglang/srt/managers/scheduler.py:5744-5811`]

`Scheduler` 构造会进一步初始化 worker、模型和 KV/attention 资源；模型加载或 group 初始化异常会在发送 ready 前发生，并由 scheduler 异常处理记录、通知父进程。[`python/sglang/srt/managers/scheduler.py:5813-5833`]

### 4.3 Detokenizer 的位置

Engine 会启动 detokenizer worker；默认一个 worker 直接监听 `port_args.detokenizer_ipc_name`，多个 worker 时还会有 router。[`python/sglang/srt/entrypoints/engine.py:964-1019`]

普通文本输出最终从 scheduler/输出流到 detokenizer，再返回 TokenizerManager；`BatchStrOutput` 在 TokenizerManager 的 handle loop 中进入 `_handle_batch_output`。[`python/sglang/srt/managers/tokenizer_manager.py:2200-2240`]

## 5. `generate`：从四条文本到请求对象

Demo 调用：

```python
outputs = llm.generate(prompts, sampling_params)
```

`Engine.generate` 先处理 routed DP 等调用级选项，再构造 `GenerateReqInput`：

```python
obj = GenerateReqInput(
    text=prompt,
    input_ids=input_ids,
    sampling_params=sampling_params,
    ...,
)
generator = self.tokenizer_manager.generate_request(obj, None)
```

非流式模式只推进异步生成器一次并返回最终结果；流式模式则包装为同步 Python generator，重复调用 `__anext__()` 直到 `StopAsyncIteration`。[`python/sglang/srt/entrypoints/engine.py:383-491`]

这里的“非流式”不是模型只做一次 forward，而是调用者只等待最终完成的 response。scheduler 仍然会进行 prefill/decode 多轮调度。

## 6. TokenizerManager：请求状态、tokenize 和 dispatch

### 6.1 先建立 `rid_to_state`

`TokenizerManager.generate_request` 的顺序是：

```python
self.auto_create_handle_loop()
obj.normalize_batch_and_arguments()
self._set_default_priority(obj)
self._init_req_state(obj, request)
...
```

然后在模型更新读锁中 tokenize，并发送 tokenized request。[`python/sglang/srt/managers/tokenizer_manager.py:776-845`]

`_init_req_state` 为每个 `rid` 创建：

```python
state = ReqState([], False, asyncio.Event(), sub_obj, time_stats)
self.rid_to_state[rid] = state
```

这就是异步 response 能够回到原请求的本地状态表；即使四个 prompt 组成一个 batch，也会按各自 rid 建立 state。[`python/sglang/srt/managers/tokenizer_manager.py:3463-3506`]

### 6.2 每条文本的 tokenize

单请求路径最终进入 `_tokenize_one_request`：

```python
if obj.input_ids is not None:
    input_ids = obj.input_ids
else:
    input_ids, token_type_ids = await self._tokenize_texts(
        input_text, is_cross_encoder_request
    )
...
self._validate_one_request(obj, input_ids)
return self._create_tokenized_object(
    obj, input_text, input_ids, input_embeds, mm_inputs, token_type_ids
)
```

普通文本 Demo 没有 `input_ids`，因此会调用 tokenizer；多模态处理分支不会被普通文本触发。[`python/sglang/srt/managers/tokenizer_manager.py:970-1137`]

`_create_tokenized_object` 把 Python list 转为 `array("q", input_ids)`，将 sampling dictionary 构造成 `SamplingParams`，校验词表大小，并生成 `TokenizedGenerateReqInput`；同时写入 tokenize 完成时间。[`python/sglang/srt/managers/tokenizer_manager.py:1356-1470`]

### 6.3 dispatch 的真实外部效果

`_send_one_request` 不是最终执行点，但它跨越了主进程到 scheduler 的 IPC 边界：

```python
prepared_mm_items = await self.cuda_vmm_feature_transport.prepare_for_dispatch_async(...)
tokenized_obj = wrap_shm_features(tokenized_obj)
tokenized_obj.wrap_pickle_fields()
self._dispatch_to_scheduler(tokenized_obj)
self._mark_state_dispatched(tokenized_obj.rid)
```

其中 `_dispatch_to_scheduler` 将消息交给 IPC socket；成功后 state 标记为 dispatched，失败则取消已准备的资源。[`python/sglang/srt/managers/tokenizer_manager.py:1577-1613`]

普通纯文本通常没有 multimodal item，但仍然经过相同的 request transport/IPC 契约。

## 7. Scheduler：从 IPC 请求到连续批处理

scheduler 每轮普通事件循环的骨架是：

```python
while True:
    self.ingest_requests()
    plan = self.get_next_batch_to_run(
        running_batch=self.running_batch,
        last_batch=self.last_batch,
    )
    self.running_batch = plan.running_batch
    batch = plan.batch_to_run
    if batch:
        result = self.run_batch(batch)
        self.process_batch_result(batch, result)
    else:
        self._sched_idled = True
        self.on_idle()
    self.last_batch = batch
```

当前代码在 `event_loop_normal` 中直接体现这个流程；`dispatch_event_loop` 会根据 PP、overlap、PDMUX 和 disaggregation 选择具体 event loop。[`python/sglang/srt/managers/scheduler.py:1839-1925`][`python/sglang/srt/managers/scheduler.py:5646-5673`]

### 7.1 ingest 的输入和状态改变

`ingest_requests` 由 request receiver 收取本轮请求，调用 `process_input_requests`；后者将请求交给 dispatcher，控制类响应再通过 IPC 发回。[`python/sglang/srt/managers/scheduler.py:2050-2105`]

对生成请求，后续 admission 会把 scheduler-side `Req` 放入 waiting/running 结构，执行 prefix matching、KV admission 和 batch 构造。这里发生的状态改变不在 offline Demo 文件中，而在 scheduler 的 request/batch 实现中；因此 Demo 文章必须链接到 M04，而不能把 `Engine.generate` 写成完整算法。

### 7.2 普通 batch 与四个 prompt

在没有特殊 parallel sampling 时，`TokenizerManager._handle_batch_request` 可以选择：

- batch tokenize 后用一个 `BatchTokenizedGenerateReqInput` 发送；或
- 逐条 tokenize 并分别 `_send_one_request`。

该选择由 `enable_tokenizer_batch_encode` 和请求是否已经有 text/input ids 等条件决定。[`python/sglang/srt/managers/tokenizer_manager.py:1854-1897`]

所以“示例传入一个 Python list”不等价于“永远只有一条 IPC 消息”；运行时的 batch tokenization policy 会决定具体传输形态。

## 8. 实际模型执行：从 `ScheduleBatch` 到 token id

scheduler 的 `run_batch` 最终调用 model worker。普通生成 worker 的关键代码是：

```python
forward_batch = ForwardBatch.init_new(
    batch,
    self.model_runner,
    capture_hidden_mode=capture_hidden_mode,
    return_hidden_states_before_norm=False,
)

if self.pp_group.is_last_rank:
    out = self.model_runner.forward(
        forward_batch,
        pp_proxy_tensors=pp_proxy_tensors,
    )
    logits_output = out.logits_output
    if not forward_batch.is_prefill_only:
        batch_result.next_token_ids = self.model_runner.sample(
            logits_output, forward_batch
        )
```

[`python/sglang/srt/managers/tp_worker.py:593-692`]

`ModelRunner.forward` 增加 forward pass id，调用 `_forward_raw`，收集可能的 expert/indexer 输出，并返回 `ModelRunnerOutput`；这是从 worker API 继续进入模型计算的真实实现层。[`python/sglang/srt/model_executor/model_runner.py:1612-1706`]

`ModelRunner.sample` 对 logits 做约束/偏置预处理，调用 sampler 得到 `next_token_ids`，并更新采样相关状态。[`python/sglang/srt/model_executor/model_runner.py:1884-1938`]

这里才发生 GPU tensor 计算、模型层访问和采样状态变化。具体是否选择 eager/CUDA Graph、如何使用 TP/PP/KV backend，取决于启动时已经建立的 runner 和 batch 条件；本 Demo 没有实际运行这些路径。

### 8.1 回到 scheduler 的结果处理

`Scheduler.run_batch` 把结果交给 `process_batch_result`；后者根据 forward mode 选择 decode 或 prefill 结果处理器。[`python/sglang/srt/managers/scheduler.py:4199-4209`][`python/sglang/srt/managers/scheduler.py:4548-4589`]

结果处理会把 next token、finish state、KV/request 状态和输出 payload 关联回 scheduler-side request，再由 output streamer 发送 `BatchStrOutput` 或 `BatchTokenIDOutput`。不同调度 variant 会有不同 result processor，但“forward → result process → output IPC”是主线边界。

## 9. 返回路径：BatchStrOutput 如何变成 `outputs[i]`

TokenizerManager 的 `handle_loop` 从 detokenizer socket 收到对象：

```python
recv_obj = await async_sock_recv(self.recv_from_detokenizer)
if isinstance(recv_obj, (BatchStrOutput, BatchEmbeddingOutput, BatchTokenIDOutput)):
    await self._handle_batch_output(recv_obj)
else:
    self._result_dispatcher(recv_obj)
```

[`python/sglang/srt/managers/tokenizer_manager.py:2225-2238`]

`_handle_batch_output` 对每个 `rid` 查找 `rid_to_state`，组装 `meta_info`，把增量文本和 token ids 追加到 state；完成时删除 state，并把最终 `out_dict` 放入 `state.out_list`，触发 `state.event`。[`python/sglang/srt/managers/tokenizer_manager.py:2240-2548`]

对 `BatchStrOutput` 的非流式请求，完成时的核心结构是：

```python
out_dict = {
    "text": state.get_text(),
    "output_ids": state.output_ids.copy(),
    "meta_info": meta_info,
}
```

如果调用者请求 prompt token ids，也会附加 `prompt_token_ids`。[`python/sglang/srt/managers/tokenizer_manager.py:2384-2434`]

Engine 的非流式 `generate` 只取 `_wait_one_response` 生成器的首个最终结果；`_stream_one_response` 等待 event、排空 out list、记录完成时间并 yield 输出。[`python/sglang/srt/managers/tokenizer_manager.py:1730-1831`]

于是 Demo 中：

```python
for prompt, output in zip(prompts, outputs):
    print(f"Prompt: {prompt}\nGenerated text: {output['text']}")
```

的 `output['text']` 不是 ModelRunner 直接返回的字符串，而是经过 scheduler result、detokenizer/TokenizerManager response state 汇聚后的最终字段。

## 10. 失败和 cleanup

### 10.1 请求级失败

`generate_request` 用 `try/except BaseException` 包住 tokenize/dispatch/wait：

- 尚未 dispatch 的 rid 从 `rid_to_state` 删除；
- 已 dispatch 的 rid 发送 abort，并保留 state 等 scheduler response 完成清理；
- 编码 dispatch event 也被释放或唤醒。[`python/sglang/srt/managers/tokenizer_manager.py:836-845`][`python/sglang/srt/managers/tokenizer_manager.py:3508-3528`]

若调用者断开连接，`_stream_one_response` 会调用 `abort_request`，避免 scheduler 继续无意义生成。[`python/sglang/srt/managers/tokenizer_manager.py:1740-1765`][`python/sglang/srt/managers/tokenizer_manager.py:1840-1852`]

### 10.2 启动级失败

如果 scheduler 在发送 ready 前模型加载、distributed 或 KV 初始化失败，`run_scheduler_process` 记录异常并向 parent 发送 SIGQUIT；可选配置还会 kill process group。[`python/sglang/srt/managers/scheduler.py:5813-5823`]

Engine 等待 ready 失败时不会把一个未完成的 Engine 当作可用对象返回；启动阶段的 tokenizer VMM transport 也在 `finally` 中关闭。[`python/sglang/srt/entrypoints/engine.py:1237-1263`]

### 10.3 进程退出

Engine 在构造时注册 `atexit(self.shutdown)`。显式退出或解释器退出时，shutdown 会停止 watchdog、关闭 RPC socket、终止 weight-cache daemon，并杀掉 Engine 子进程树；最后关闭 multimodal processor/VMM transport（如果存在）。[`python/sglang/srt/entrypoints/engine.py:286-291`][`python/sglang/srt/entrypoints/engine.py:1273-1309`]

因此示例没有显式写 `llm.shutdown()` 也不是没有 cleanup，而是依赖 Engine 的生命周期注册；调试时仍建议在异常场景确认 atexit 是否被正常触发。

## 11. 四条 prompt 的具体追踪表

| 阶段 | 输入 | 关键对象/状态 | 真实效果 |
|---|---|---|---|
| CLI | 字符串参数 | argparse Namespace | 解析命令行，不加载模型 |
| 配置 | Namespace | `ServerArgs` | 形成启动参数；动态 CLI 字段已映射 |
| Engine 构造 | ServerArgs dict | `Engine`, `PortArgs`, child processes | 创建通信端点、worker 和 watchdog |
| 请求输入 | 四条 prompt + sampling dict | `GenerateReqInput`, `rid_to_state` | 建立请求关联状态 |
| tokenization | 每条文本 | `TokenizedGenerateReqInput`, `SamplingParams` | 产生 token ids 和规范化采样参数 |
| dispatch | tokenized request | IPC message | 从主进程进入 scheduler |
| scheduling | scheduler-side requests | waiting/running `Req`, `ScheduleBatch` | 前缀匹配、KV admission、构造执行批次 |
| execution | `ForwardBatch` | ModelRunner logits/sample | 产生 next token ids；真实 GPU 路径未验证 |
| response | batch output | `rid_to_state`, `out_list` | 组装最终 text/output_ids/meta_info |
| print | output dict | Python stdout | 用户可见文本输出；端到端未验证 |
| exit | Engine object | watchdog/process tree/transport | 释放运行时资源 |
