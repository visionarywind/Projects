# 01 整体架构：SGLang 到底是什么

## 1. 先用一句话理解

SGLang 是一个**大语言模型推理服务运行时**。它把模型权重加载到一个或多个加速器上，接收客户端请求，持续把不同请求拼成批次执行，并把新生成的 token 流式返回。

“运行时”这个词很关键：SGLang 不是一个只实现 Transformer `forward()` 的模型库，而是负责模型从启动到服务的全生命周期，包括请求协议、tokenization、排队、内存分配、批处理、并行通信、采样、缓存、错误处理和监控。

## 2. 从仓库的四层看系统

### 2.1 用户接口层

入口主要有两类：

- `sglang serve ...`：推荐的 CLI，实现在 `python/sglang/cli/`。
- `python -m sglang.launch_server ...`：兼容入口，实现在 `python/sglang/launch_server.py`。

CLI 不直接执行模型。它只解析参数、选择后端，然后调用服务器启动函数。这样做让 LLM 服务和 diffusion 服务可以共享一个顶层命令，而具体参数仍由各自后端解析。

### 2.2 网络与协议层

`python/sglang/srt/entrypoints/http_server.py` 使用 FastAPI/Starlette 提供：

- SGLang 原生生成接口；
- OpenAI-compatible completions/chat completions；
- embedding、rerank、tokenize 等接口；
- health、profile、权重更新、LoRA 等管理接口。

网络层的职责是把 JSON/HTTP 对象转换成内部请求对象。它不应该决定 GPU 上如何排批次；这属于下层 TokenizerManager 和 Scheduler。

### 2.3 请求控制与执行编排层

`TokenizerManager` 位于 CPU 侧，典型职责是：

1. 接收已经通过协议层校验的请求；
2. 调用 tokenizer，把文本变成 token ids；
3. 准备采样参数、多模态输入和请求元数据；
4. 通过 IPC 把请求发给一个或多个 Scheduler；
5. 接收生成结果，增量 detokenize，并组织流式响应。

`Scheduler` 是每个 worker 的核心控制循环。它管理等待队列和运行中请求，决定这一轮是 prefill 还是 decode、每个请求执行多少 token、是否需要抢占或回收缓存，并调用 worker/model runner。

### 2.4 GPU 执行层

`ModelRunner` 和具体模型类完成真正的张量计算：

- 依据 `ForwardBatch` 准备 input ids、位置、slot mapping 等张量；
- 调用模型的 embedding、attention、MLP/MoE、norm 和 lm head；
- 选择 attention backend 和 CUDA graph 等优化路径；
- 输出 logits 或隐藏状态；
- 调用 sampler 得到下一个 token。

具体模型在 `python/sglang/srt/models/` 中实现共同协议。`ModelConfig`/`ServerArgs` 决定加载哪种模型实现、精度、并行度和后端。

## 3. 为什么要拆成 TokenizerManager 和 Scheduler

初学者常见的疑问是：为什么 HTTP handler 不直接调用 `model.generate()`？

因为服务场景下请求是并发到达的，而模型执行需要共享 GPU 和 KV cache。把网络处理和 GPU 调度拆开有三个好处：

1. **隔离慢操作**：tokenizer、HTTP 和 JSON 序列化不会直接阻塞 GPU worker。
2. **统一批处理**：Scheduler 可以把多个请求的 token 拼成一个 batch，并在每一轮重新决定 batch。
3. **进程级容错与并行**：每个 GPU worker 可以独立运行，控制进程通过 IPC 传递结构化消息。

这是一种“控制面/执行面”分离：TokenizerManager 更像控制面，Scheduler/ModelRunner 更像数据面。

## 4. 两种时间尺度：请求生命周期和调度迭代

### 请求生命周期

一个请求通常经历：`waiting → running(prefill/decode) → finished/aborted`。请求对象携带 prompt token、已生成 token、采样参数、停止条件、KV cache 状态等。

### 调度迭代

Scheduler 不会一次完成所有请求，而是不断循环：

```text
while server_is_running:
    batch = select_requests_for_next_step()
    output = run_model(batch)
    update_requests_and_cache(output)
    send_ready_results()
```

decode 阶段经常是一轮给每个请求追加一个 token；prefill 阶段可能一次处理 prompt 的一段或全部 token。连续批处理的含义就是：每轮结束后，可以加入新请求、移除已结束请求，并继续使用同一个 GPU 执行循环。

## 6. 一个具体例子

假设客户端请求：

```json
{
  "model": "Qwen/Qwen3-8B",
  "messages": [{"role": "user", "content": "1+1 等于多少？"}],
  "max_tokens": 16,
  "stream": true
}
```

系统不会把这段字符串原样送进 GPU。它会经历：

1. OpenAI 路由把 messages 转成内部生成请求；
2. tokenizer 根据 chat template 生成 token ids；
3. Scheduler 检查是否已有相同前缀的 KV cache；
4. 未命中的 token 在 prefill 中计算；
5. sampler 从最后一个位置的 logits 采样出 token；
6. 每个新 token 写入请求状态和 KV cache；
7. TokenizerManager 增量解码出文本并通过 SSE 返回。

后续文章会沿着这个例子逐个函数展开。
