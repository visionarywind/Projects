这一章先不看复杂实现，用一个小模型和三个请求理解 SGLang 要解决的问题。

## 1. token：模型真正看到的单位

人类看到的是字符串，模型通常看到的是整数 token id。例如文本 `Hello world` 可能被编码成 `[15496, 995]`。token 不一定等于一个字，也可能是字的一部分、标点或空格。

因此服务内部至少有两种表示：

- **外部表示**：字符串、messages、JSON；
- **内部表示**：token ids、位置、采样参数和缓存索引。

tokenizer 负责两者之间转换。模型执行和 KV cache 只关心 token ids。

## 2. Prefill 与 Decode

一次生成可以分成两个阶段。

### Prefill：处理提示词

给定 prompt `[A, B, C, D]`，模型需要依次计算这四个位置，并为它们保存 KV。prefill 的特点是：

- 一次有很多 token；
- 矩阵运算规模较大，GPU 利用率通常较好；
- 结果主要是最后位置的 logits，以及每层的 KV cache。

### Decode：逐 token 生成

模型根据 prompt 得到的状态生成 `E`，再根据 `[A,B,C,D,E]` 生成 `F`，如此循环。每次 decode 通常只新增一个 token，但要访问越来越长的历史 KV。

```text
prefill: [A B C D] ──一次计算──> KV(A..D), logits(D)
decode:  [E]       ──追加计算──> KV(E), logits(E) ──> F
```

这解释了为什么推理服务不能只调用训练时的普通 `forward(input_ids)`：它需要把历史状态持久化，并让不同请求共享一个 GPU 内存池。

## 3. Continuous batching：动态批处理

传统静态 batch 需要等一批请求都结束，才能处理下一批。生成长度不同时，会出现大量空转。

连续批处理把每一个调度迭代视为一个新 batch：

```text
时间 t0: 请求 A prefill, 请求 B prefill
时间 t1: A decode, B decode, 新请求 C prefill
时间 t2: A 完成, B decode, C decode, 新请求 D 加入
```

每轮 batch 的成员可以变化。SGLang 的 `ScheduleBatch` 表达本轮要执行的请求，`Scheduler.get_next_batch_to_run` 负责选择它。

### 一个直观比喻

把 GPU 想成餐厅厨房：

- 请求是订单；
- Scheduler 是领班；
- batch 是一次送进厨房的一组订单；
- prefill 是准备整桌食材；
- decode 是每道菜每次再做一小步；
- KV cache 是已经准备好的食材，下一单相同前缀可以复用。

领班每轮都重新组合订单，而不是固定等某几桌全部吃完。

## 4. 为什么需要分块（paged/block）内存

如果为每个请求预留 `max_seq_len` 的连续 KV 内存：

- 短请求会浪费大量空间；
- 请求长度不可预测；
- 请求结束后的空洞很难复用。

SGLang 使用 token-to-KV 的映射和各种 allocator，把 KV 放在固定大小的 token block 中。请求只保存自己对应的 block/token 槽位。这样不同请求可以动态增长、释放和复用。

核心相关代码：

- `srt/mem_cache/memory_pool.py:ReqToTokenPool`：请求 token 位置到 KV pool 槽位的映射；
- `srt/mem_cache/allocator/`：分配和回收 token/KV；
- `srt/mem_cache/radix_cache.py:RadixCache`：管理可复用的前缀路径。

## 5. Sampling：logits 不是文本

模型最后输出的是词表大小的 logits，例如词表有 100,000 个 token，就有 100,000 个分数。采样策略把分数变成一个 token：

1. temperature 缩放；
2. top-k/top-p 等过滤；
3. repetition/frequency/presence penalty；
4. greedy 或随机采样。

SGLang 把采样参数放入请求/批次元数据，并使用 batch sampler 尽量一次处理多个请求，而不是在 Python 中逐请求处理。

## 6. 结构化生成和停止条件

请求不一定在生成 `eos` 时结束，还可能因为：

- 达到 `max_new_tokens`；
- 命中停止 token 或字符串；
- 命中正则、JSON grammar 或 tool-call 约束；
- 客户端 abort。

这些条件必须在每轮输出后检查，否则服务会多生成 token，浪费 GPU 和网络带宽。`schedule_batch.py` 中的 `BaseFinishReason` 及其派生类型描述了结束原因。

## 7. 用一个小例子串起来

两个请求：

```text
A prompt = ["请", "计算", "1+1"]
B prompt = ["请", "计算", "2+2"]
```

首轮可能是：

- tokenizer 产生两个 token 序列；
- Scheduler 发现公共前缀 `[请, 计算]`，只需为它计算一次；
- 两个请求各自 prefill 末尾 token；
- sampler 得到候选输出；
- 下一轮 A/B 进入 decode；
- 一个请求命中停止条件后离开 batch，另一个继续。

这个例子中同时出现了 tokenization、前缀缓存、prefill、decode、连续批处理和停止条件。后面的源码分析会把抽象概念对应到具体函数。
