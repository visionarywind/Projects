# M07 分布式并行：从 global rank 到可通信的并行组

> 模块 ID：M07。本文只讨论 SGLang Runtime 中“多个 worker 如何建立坐标和通信关系”，不把分布式训练的参数同步模型套到推理服务上。

## 1. 先回答：为什么一个模型需要这么多组？

在单卡上，模型可以把所有层和所有中间张量放在一张 GPU 上。模型变大以后，SGLang 会把工作拆到多个 scheduler/worker 进程中。拆分后每个进程至少需要两类信息：

1. **我是谁**：global rank、设备和本机进程位置；
2. **我应该和谁通信**：例如 TP 的伙伴、PP 的上游/下游、MoE expert 的伙伴。

可以把 global rank 想成一张总座位表，把 process group 想成不同用途的临时小组。一个 rank 可以同时属于多个组，但每个组的成员顺序和本地 rank 都可能不同。

> **已确认**：SGLang 为 WORLD、TP、PP、attention CP/TP、MoE DP/EP/TP、DCP 等用途分别维护 `GroupCoordinator`；某些宽度相同的用途直接复用已有对象，而不是必然创建新的 group。依据 `initialize_model_parallel` 的分支和赋值逻辑。[`python/sglang/srt/distributed/parallel_state.py:2298-2682`]

### 1.1 TP、PP 和 DP 不要混为一谈

用一个 8-rank 的例子：`tp_size=2`、`pp_size=4`，因此 `world_size=8`。

```text
global rank:  0  1  2  3  4  5  6  7

TP 组：       [0,1] [2,3] [4,5] [6,7]
PP 组：       [0,2,4,6] [1,3,5,7]
```

- **TP（Tensor Parallel）**：同一 pipeline stage 内，沿 tensor 维度拆开的伙伴；一层计算通常需要 collective。
- **PP（Pipeline Parallel）**：模型层按阶段拆开，前一阶段把中间激活传给下一阶段。
- **DP（Data Parallel）**：多个副本处理不同请求或 token；在 SGLang 中 attention DP、MoE DP 还有各自的专用拓扑。
- **EP（Expert Parallel）**：MoE 的 expert 分布到不同 rank；它不等同于普通 dense 模型的 TP。
- **CP/DCP**：attention context 或 decode context 的并行维度，影响 token/KV 的分布和 collective 范围。

同一个进程可能同时是：TP 组内 rank 1、PP 组内 rank 2、MoE EP 组内 rank 0。调用 collective 时必须使用正确的 coordinator，不能只看 global rank。

## 2. rank 从哪里来，GPU 又从哪里来？

### 2.1 Engine 先创建 worker 进程

普通（非 DP controller）路径中，Engine 遍历本机负责的 PP/TP rank 组合，为每个组合建立一条单向 startup pipe，并计算 GPU 绑定：

```python
for pp_rank in pp_rank_range:
    for tp_rank in tp_rank_range:
        reader, writer = mp.Pipe(duplex=False)
        gpu_id = (
            get_device().base_gpu_id
            + ((pp_rank % pp_size_per_node) * tp_size_per_node)
            + (tp_rank % tp_size_per_node) * get_device().gpu_id_step
        )
        attn_cp_rank, moe_dp_rank, moe_ep_rank = _compute_parallelism_ranks(
            tp_rank
        )
        proc = mp.Process(
            target=run_scheduler_process_func,
            args=(server_args, port_args, gpu_id, tp_rank,
                  attn_cp_rank, moe_dp_rank, moe_ep_rank, pp_rank,
                  None, writer),
        )
        proc.start()
```

这段代码表达了一个重要边界：`gpu_id` 是**本地设备选择**，`tp_rank`/`pp_rank` 是**模型拓扑坐标**，不能假设三者永远相同。[`python/sglang/srt/entrypoints/engine.py:846-917`]

每个 scheduler 进程还可以通过 `configure_scheduler_process` 设置日志前缀、CPU affinity 和 NUMA；随后才进入 `run_scheduler_process`。[`python/sglang/srt/managers/scheduler.py:5676-5775`]

### 2.2 scheduler 进程先发布配置，再构造 Scheduler

```python
load_plugins()
publish(server_args, role="scheduler")
dp_rank = configure_scheduler_process(...)
scheduler = Scheduler(...)
pipe_writer.send(scheduler.get_init_info())
scheduler.run_event_loop()
```

`publish` 必须早于 `Scheduler(...)`，因为构造链中的 ModelConfig、ModelRunner 和通信初始化会读取 role-specific runtime config。`pipe_writer.send` 又晚于 `Scheduler(...)`，所以 ready 不是“进程刚启动”，而是构造阶段已经完成的信号。[`python/sglang/srt/managers/scheduler.py:5744-5811`]

### 2.3 WORLD 的 rank 公式

`bootstrap._init_parallel_groups` 在普通模式下使用：

```python
world_size = tp_size * pp_size
rank = tp_size * pp_rank + tp_rank

init_distributed_environment(
    backend=backend,
    world_size=world_size,
    rank=rank,
    local_rank=gpu_id,
    distributed_init_method=dist_init_method,
    ...,
)
```

弹性 EP scale/joiner 模式会额外使用 `rank_offset`，所以文档中的普通公式不能无条件套用到 joiner。[`python/sglang/srt/distributed/bootstrap.py:250-299`]

`init_distributed_environment` 调用 `torch.distributed.init_process_group`，随后用全局 rank 列表构造 WORLD `GroupCoordinator`。它还保存 group timeout，并为某些 MoE A2A 后端创建全局 TCPStore。[`python/sglang/srt/distributed/parallel_state.py:2206-2296`]

## 3. `GroupCoordinator` 实际做了什么？

### 3.1 一个逻辑组对应 device group 和 CPU group

`init_model_parallel_group` 并不直接返回一个裸的 PyTorch group，而是构造 `GroupCoordinator`，并把 group ranks、local rank、backend、通信优化选项传入。[`python/sglang/srt/distributed/parallel_state.py:1895-1935`]

在 `GroupCoordinator.__init__` 中，对每个 rank 列表创建：

- 一个用于设备 tensor collective 的 device group；
- 一个 backend 为 `gloo` 的 CPU group，用于对象/元数据协调；
- `ranks`、`world_size`、`rank_in_group` 等本地坐标；
- 可选的 PyNCCL、MScclpp、custom all-reduce、对称内存或硬件专用 communicator。[`python/sglang/srt/distributed/parallel_state.py:290-412`]

只有当前 rank 属于某个 rank 列表时，该列表才成为这个 coordinator 的本地成员信息；但所有进程都会执行 group 的创建循环。这解释了为什么“组成员”和“当前进程是否参与某个 collective”是两个不同问题。

### 3.2 communicator 是 group 的执行策略，不是新的拓扑

创建 coordinator 后，代码根据配置决定是否实例化 PyNCCL、custom all-reduce、quick all-reduce、对称内存 communicator，以及 HPU/XPU/NPU communicator。[`python/sglang/srt/distributed/parallel_state.py:415-545`]

因此应区分：

```text
拓扑：哪些 global rank 在一起
  -> torch ProcessGroup / GroupCoordinator

执行策略：这个组的 all_reduce 用什么实现
  -> NCCL/RCCL/HCCL、PyNCCL、custom all-reduce、硬件 communicator
```

这也是为什么关闭 custom all-reduce 不会改变 TP 成员，只会改变该组可能采用的通信实现。

## 4. `initialize_model_parallel` 的建组顺序与拓扑

### 4.1 先建 TP，再建派生组

函数首先检查 distributed 已初始化，确定 backend，验证 `world_size == tp_size * pp_size`；DCP 还必须大于等于 1、受设备平台限制，并整除 TP size。[`python/sglang/srt/distributed/parallel_state.py:2298-2400`]

随后按连续区间构造 TP：

```python
num_tensor_model_parallel_groups = world_size // tensor_model_parallel_size
for tp_group_idx in range(num_tensor_model_parallel_groups):
    ranks = list(range(
        tp_group_idx * tensor_model_parallel_size,
        (tp_group_idx + 1) * tensor_model_parallel_size,
    ))
    group_ranks.append(ranks)
_TP = init_model_parallel_group(..., group_name="tp", ...)
```

这就是 8-rank、TP=2 时的 `[0,1]`、`[2,3]`、`[4,5]`、`[6,7]`。[`python/sglang/srt/distributed/parallel_state.py:2400-2424`]

如果启用 PD-Multiplexing 的 duplicate TP，还会用同一份成员列表创建名为 `pdmux_prefill_tp` 的独立 coordinator。[`python/sglang/srt/distributed/parallel_state.py:2426-2444`]

### 4.2 DCP、attention CP/TP

DCP 组在每个 TP 组内部按连续片段切分；例如 TP 组 `[0,1,2,3]`、DCP=2，会得到 `[0,1]`、`[2,3]`。代码在每个 TP group 上以 `decode_context_parallel_size` 为步长生成列表。[`python/sglang/srt/distributed/parallel_state.py:2445-2466`]

attention 拓扑由 `derive_parallel_widths` 推导出 attention TP 宽度。若 CP 覆盖整个 TP，attention CP 直接复用 `_TP`；否则代码按 attention DP、attention TP 和 CP 的组合生成跨 rank 列表。[`python/sglang/srt/distributed/parallel_state.py:2468-2515`]

若 attention TP 覆盖整个 TP，也直接令 `_ATTN_TP = _TP`；否则按 CP×DP 的分组连续切分，并以 `group_name="attention_tp"` 创建专用组。[`python/sglang/srt/distributed/parallel_state.py:2517-2552`]

### 4.3 MoE DP/EP/TP

MoE 的三个组分别服务不同的数据交换：

- MoE DP：不同数据副本之间协作；当 CP 与 MoE DP 的关系满足特定条件时，代码可以令 `_MOE_DP = _ATTN_CP`，避免重复建组；
- MoE EP：expert 所在的 rank；NPU 即使 EP 宽度等于 TP，也有 standalone group 的特殊路径；
- MoE TP：expert 内部 tensor 维度的伙伴；宽度等于 TP 时复用 `_TP`。[`python/sglang/srt/distributed/parallel_state.py:2554-2645`]

这几个条件说明“组名”与“对象是否独立”不能只凭概念推断，必须看当前参数分支。对读者而言，最安全的检查方式是同时观察 `group_name`、`ranks` 和赋值是否复用已有对象。

### 4.4 PP 使用跨区间的步长序列

PP 组数量为 `world_size // pipeline_model_parallel_size`，每个组从不同起点开始，以组数量为步长：

```python
for pp_group_idx in range(num_pipeline_model_parallel_groups):
    ranks = list(range(pp_group_idx, world_size, num_pipeline_model_parallel_groups))
    group_ranks.append(ranks)
_PP = init_model_parallel_group(..., group_name="pp", ...)
```

所以 TP=2、PP=4 的 PP 组是 `[0,2,4,6]` 与 `[1,3,5,7]`，而不是 `[0,1,2,3]`。[`python/sglang/srt/distributed/parallel_state.py:2647-2667`]

最后，代码为 one-layer draft 建立每个 rank 的 singleton self-PP group；注释明确说明每个 rank 都创建全部 singleton group，因为 `new_group` 是 collective。[`python/sglang/srt/distributed/parallel_state.py:2669-2680`]

> **已确认**：在当前实现中，建组的逻辑顺序是 TP、可选 duplicate TP、DCP、attention CP、attention TP、MoE DP/EP/TP、PP、self-PP；某些组在条件满足时复用已有 coordinator。这个顺序来自函数中的实际语句顺序，而不是抽象架构图。[`python/sglang/srt/distributed/parallel_state.py:2400-2682`]

## 5. 自定义 group：为什么要 all-gather 和排序？

另一个入口 `create_custom_parallel_group` 允许每个进程提出自己希望加入的 rank 列表。代码先排序、去重，然后 `all_gather_object` 收集所有进程的配置；再去重并按首 rank 排序，最后让所有进程以相同的 `unique_groups` 顺序调用 `torch.distributed.new_group`。[`python/sglang/srt/distributed/parallel_state.py:2684-2730`]

```text
每个 rank 的 local_config
  -> all_gather_object
  -> 收集所有候选组
  -> 去重
  -> 按首 rank 排序
  -> 所有 rank 依次 new_group
  -> 当前 rank 返回自己所属的 group
```

这里的“排序后统一创建”是当前函数明确实现的行为；不要把它扩大成“所有可能的 GroupCoordinator 都由这个函数创建”，因为标准模型并行路径直接调用 `GroupCoordinator` 内部的建组逻辑，而不是 `create_custom_parallel_group`。

## 6. collective 到底在哪个对象上发生？

`GroupCoordinator` 的通信方法会按 tensor 所在设备和硬件选择路径。例如 `all_gather`：

1. world size 为 1 时直接返回或复制，避免无意义 collective；
2. GPU tensor 走 device group 或注册的 opaque custom op；
3. CPU tensor 在可用时走 shared-memory all-gather，否则走 PyTorch distributed；
4. 最终 reshape/movedim，把 rank 维拼到调用者期望的维度。[`python/sglang/srt/distributed/parallel_state.py:1281-1353`]

因此，代码中看到 `get_tp_group().all_reduce(...)` 时，真正的外部效果不是 Python 方法调用本身，而是下层 process group/communicator 在设备间传输数据。阅读 collective 路径时至少要继续追到 `device_group`、`cpu_group` 或具体 communicator 字段。

PP 的 activation 传递、attention 的 token/KV 交换和 MoE 的 expert all-to-all 会选择不同 coordinator；不能用 TP group 替代所有通信。

## 7. 启动预热和内存检查

初始化 parallel groups 后，`init_torch_distributed` 在满足条件时用一次 TP all-reduce 预热 NCCL/RCCL/HCCL，减少第一次请求的冷启动延迟；TP/PP/EP 都为 1 时不会走这条分支。[`python/sglang/srt/distributed/bootstrap.py:119-126`]

它还记录模型加载前可用显存，并在 TP>1 时比较 rank 间显存是否平衡。这个数值会参与后续模型加载/KV cache 的内存预算；因此通信初始化不只是“建立连接”，也会影响资源测量的基线。[`python/sglang/srt/distributed/bootstrap.py:145-172`]

### 未验证边界

以下内容在本地没有用真实多 GPU 环境运行：

- `torch.distributed.init_process_group` 的 NCCL/RCCL/HCCL 建立；
- 多节点 TCPStore/RDMA；
- custom all-reduce、PyNCCL、MScclpp 或 Mooncake 后端；
- DCP、MoE EP/DP 的真实 collective；
- group timeout、rank 崩溃和恢复 joiner 的实际表现。

源码支持“调用了这些路径”的结论，但不支持“本机已成功完成通信”的结论。

## 8. 清理：为什么要处理 alias？

`destroy_model_parallel` 释放各类 group，并把全局变量重置为 `None`。关键细节是 `_MOE_DP` 可能复用 `_ATTN_CP` 或 `_TP`，所以清理时先判断对象身份，避免同一个 process group 被销毁两次；随后再销毁 `_ATTN_CP`。[`python/sglang/srt/distributed/parallel_state.py:2929-2982`]

每个 `GroupCoordinator.destroy` 会销毁 device group、CPU group，并释放 communicator/broadcaster 引用。[`python/sglang/srt/distributed/parallel_state.py:1851-1866`]

最后，`destroy_distributed_environment` 销毁 WORLD 和底层 torch distributed process group；更高层的 `cleanup_dist_env_and_memory` 还会做垃圾回收和设备 cache 清理。[`python/sglang/srt/distributed/parallel_state.py:2984-3018`]

这条清理链的实际意义是：Engine shutdown 不仅杀掉 scheduler 子进程，还必须让 worker 内的通信资源、CPU group、GPU group 和设备缓存有机会退出。异常路径则可能跳过同步性很强的清理，以免 GPU 已经 wedged 时再次 hang。[`python/sglang/srt/managers/scheduler.py:5813-5833`]

## 9. 端到端例子：4 GPU、TP=2、PP=2

假设普通启动参数解析后得到：

```text
tp_size = 2
pp_size = 2
world_size = 4
```

### 9.1 进程和 rank

Engine 在本机创建四个 scheduler worker（实际是否都在本机还取决于 node placement，下面只演示逻辑 rank）：

```text
(pp=0,tp=0) -> rank=0 -> gpu_id 由设备 placement 计算
(pp=0,tp=1) -> rank=1 -> gpu_id 由设备 placement 计算
(pp=1,tp=0) -> rank=2 -> gpu_id 由设备 placement 计算
(pp=1,tp=1) -> rank=3 -> gpu_id 由设备 placement 计算
```

每个 worker 调用同一个 `init_process_group` 配置，但传入不同的 `rank` 和 `local_rank`。

### 9.2 组

```text
TP: [0,1], [2,3]
PP: [0,2], [1,3]
```

rank 2 的视角是：

```text
我的 global rank = 2
我的 TP group = [2,3]，rank_in_group = 0
我的 PP group = [0,2]，rank_in_group = 1
```

### 9.3 模型层和通信

若模型有 32 层，`get_pp_indices` 默认给 PP stage 0 `[0,16)`、stage 1 `[16,32)`（整除时）。rank 2 只实例化/保留第二阶段相关层；该阶段内部的 tensor 计算与 rank 3 协作，前后阶段之间通过 PP group 传递激活。[`python/sglang/srt/distributed/utils.py:95-135`]

注意：这只是由源码拓扑和层分区逻辑得到的结构示例，未在本机启动该 4-GPU 服务，不能声称实际权重加载或 activation collective 成功。

## 10. 入口、出口、错误和断点

### 10.1 模块边界

| 项目 | 具体位置 | 结果 |
|---|---|---|
| 入口 | `Engine._launch_scheduler_processes` | 创建 worker、分配 startup pipe、传入 rank/GPU |
| 分布式入口 | `bootstrap.init_torch_distributed` | 解析 backend、init method，建立 WORLD/并行组 |
| 拓扑入口 | `parallel_state.initialize_model_parallel` | 创建各用途 coordinator |
| 实际通信 | `GroupCoordinator` 的 collective 方法 | 设备/CPU group 或专用 communicator 产生通信效果 |
| 出口 | `Scheduler.get_init_info` → parent `wait_for_ready` | ready 信息被父进程接收，服务继续启动 |
| 清理 | `destroy_model_parallel` / `destroy_distributed_environment` | 释放组和 distributed 环境 |

### 10.2 典型错误边界

- `world_size` 与 TP×PP 不一致：`initialize_model_parallel` 抛出 `RuntimeError`；
- DCP 非法或不能整除 TP：初始化前抛出 `RuntimeError`；
- distributed backend/地址/timeout 错误：`init_process_group` 或后续建组失败；
- 某 rank 模型加载失败：TP barrier 或 scheduler 异常路径把失败传播到父进程，可能触发 sibling 进程清理；
- alias 销毁顺序错误：可能造成重复销毁或残留资源，因此清理代码显式按身份判断。

### 10.3 推荐断点

1. `engine.py:883-915`：确认本机 worker 的 PP/TP 与 GPU placement；
2. `bootstrap.py:250-299`：确认 world size、global rank 和 rank offset；
3. `parallel_state.py:2400-2424`：确认 TP 成员；
4. `parallel_state.py:2647-2680`：确认 PP/self-PP 成员；
5. `parallel_state.py:388-412`：确认当前 rank 的 `rank_in_group` 和 device/CPU group；
6. `parallel_state.py:2929-2982`：检查清理时的 alias 判断；
7. `bootstrap.py:314-323`：检查通信预热是否实际被触发。

## 12. 小结

```text
Engine placement
  -> worker 的 gpu_id / tp_rank / pp_rank
  -> init_process_group(WORLD)
  -> GroupCoordinator 的 device + CPU groups
  -> initialize_model_parallel 的多种拓扑
  -> ModelRunner / attention / MoE 使用对应 coordinator
  -> startup ready
  -> shutdown 时按 alias 安全销毁
```
