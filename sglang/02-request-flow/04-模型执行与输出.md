上一章解释了 Scheduler 如何决定“这一轮运行哪些请求”。本章继续沿着 GPU 执行路径向下追踪：一个已经选好的 `ScheduleBatch`，怎样变成模型能读取的 device tensor，怎样经过 Transformer、attention 和 KV cache 得到 logits，怎样采样出下一个 token，最后怎样回到 HTTP 客户端。

本文先忽略少数特殊后端，把普通的 decoder-only 生成模型作为主线；遇到 CUDA Graph、连续批处理、PP、speculative decoding、grammar 和 embedding 模型时，再说明它们如何在同一条主线上分叉。

## 1. 先看完整路径

```text
Scheduler.get_next_batch_to_run()
          │
          ▼
     ScheduleBatch
          │  描述本轮请求、序列长度、KV 槽位、采样信息
          ▼
   ForwardBatch.init_new()
          │  构造本次 forward 的 device/host 元数据
          ▼
TpModelWorker.forward_batch_generation()
          │  组织 worker 级别的 forward 和 sampling
          ▼
      ModelRunner.forward()
          │
          ├─ CUDA Graph replay（条件满足时）
          ├─ split prefill（按层切分时）
          ├─ prefill CUDA Graph
          └─ EagerRunner
                 │
                 ▼
          model.forward()
                 │
       embedding → Transformer layers
                 │
       attention 读取/写入 KV cache
                 │
          LM head → logits
                 ▼
        LogitsProcessorOutput
                 │
                 ├─ grammar mask / logits bias
                 └─ sampler
                       │
                       ▼
                 next_token_ids
                       │
                       ▼
             GenerationBatchResult
                       │
                       ▼
          Scheduler.process_batch_result()
                       │
              更新 Req、停止状态、KV bookkeeping
                       │
                       ▼
       SchedulerOutputStreamer → BatchTokenIDOutput
                       │  ZMQ / Rust egress
                       ▼
             DetokenizerManager
                       │  token ids → 增量文本
                       ▼
             TokenizerManager
                       │  唤醒 ReqState.event
                       ▼
                 HTTP JSON / SSE
```

最容易混淆的地方是：**forward 不一定产生最终字符串**。模型执行只产生 logits、token ids 以及可选的 logprob/hidden state；请求状态更新和 token 到文本的转换分别由 Scheduler、DetokenizerManager 完成。

## 2. 四种 batch 不要混为一谈

### 2.1 `Req`：一个请求的运行时状态

`Req` 位于 `python/sglang/srt/managers/schedule_batch.py`。它记录单个请求的可变状态，例如：

- `origin_input_ids`：原始 prompt token；
- `output_ids`：已经生成或接受的 token；
- `extend_range`：本轮需要 prefill 的 token 范围；
- `kv`：KV 已提交长度、缓存索引等信息；
- `finished_reason`、`to_finish`：停止状态；
- `grammar`、`sampling_params`、LoRA 和多模态状态；
- 增量 detokenization 所需的 `decoded_text`、`read_offset` 等。

它是“一个订单的完整状态”，不等同于 GPU 上的一行 tensor。

### 2.2 `ScheduleBatch`：Scheduler 本轮的计划

`ScheduleBatch` 是多个 `Req` 的集合，同时保存本轮调度结果：

- `reqs`：本批请求；
- `input_ids`：本轮实际要送入模型的 token；
- `req_pool_indices`：请求在 `ReqToTokenPool` 中的行号；
- `seq_lens`：每个请求当前的序列长度；
- `out_cache_loc`：本轮新 token 要写入的 KV 槽位；
- `forward_mode`：`EXTEND`、`DECODE`、`MIXED` 等；
- `sampling_info`：温度、top-k、grammar 等采样元数据；
- `extend_lens`、`prefix_lens`、`extend_num_tokens`：prefill 的形状信息。

`ScheduleBatch` 是“这一轮的执行计划”，但还不是专门为某次模型 forward 整理的最终输入。

### 2.3 `ForwardBatch`：一次 forward 的执行视图

`ForwardBatch` 位于 `python/sglang/srt/model_executor/forward_batch_info.py`。它把 `ScheduleBatch` 中的信息整理为模型执行需要的形态：

- device 上的 `input_ids`、`positions`、`seq_lens`、`out_cache_loc`；
- host 上的 request id、LoRA id、logprob 配置；
- attention backend 的 metadata；
- speculative decoding、M-RoPE、context parallel 等附加信息；
- `sampling_info` 和 grammar 信息。

可以把它看成“计划的编译结果”：Scheduler 关心请求是否能运行，模型 runner 关心 tensor 的 dtype、shape、device 和布局。

### 2.4 `GenerationBatchResult`：一次 forward 的结果容器

`python/sglang/srt/managers/utils.py` 中的 `GenerationBatchResult` 不只包含 token：

- `logits_output`：logits、logprob、hidden states 等；
- `next_token_ids`：采样出的 token；
- speculative decoding 的接受长度和 draft 状态；
- CUDA Graph 可运行标记；
- overlap scheduling 所需的异步 D2H event；
- routed experts、indexer top-k 等可选输出。

它连接“模型执行”和“调度结果处理”两个阶段。

## 3. `ForwardBatch.init_new`：把调度计划翻译成执行输入

源文件：`python/sglang/srt/model_executor/forward_batch_info.py:758` 附近。

### 3.1 不修改输入的约束

函数开头的注释明确说明：

```python
# init_new must not mutate the input ScheduleBatch;
# per-forward overrides go through explicit keyword arguments.
```

原因是 overlap scheduling 可能同时保存一个 batch 的 snapshot，或者让下一轮 forward 读取同一个 `ScheduleBatch` 的字段。如果构造 `ForwardBatch` 时随意修改原 batch，另一条执行路径可能看到半更新状态。

这是一条很重要的工程原则：**调度对象和执行对象之间尽量使用显式映射，而不是隐式地“顺手改一下”共享对象**。

当前实现中仍有一个兼容性的例外：如果 `batch.seq_lens_sum` 为空但有 CPU sequence lengths，会回填 `batch.seq_lens_sum`。源码注释说明这是迁移到 KV-committed lengths 期间暂时容忍的 mutation，不应把它当作新代码的常规模式。

### 3.2 选择 hidden-state 捕获模式

```python
if capture_hidden_mode is None:
    request_capture_hidden_mode = max(
        batch.return_hidden_states_mode,
        get_server_return_hidden_states_mode(),
    )
```

如果调用者没有给本次 forward 明确 override，系统会在 request 需求和 server 全局配置中取更高模式。这样多个请求可以共享一个 CUDA Graph：即使某个请求只需要较低级别的 hidden state，batch 仍按统一的最大模式准备。

draft worker 通常不需要返回这些状态，因此会使用 `CaptureHiddenMode.NULL`。

### 3.3 decode 和 extend 使用不同的字段

```python
if batch.forward_mode.is_decode_or_idle():
    extend_seq_lens = extend_prefix_lens = None
else:
    extend_seq_lens = batch.extend_lens
    extend_prefix_lens = batch.prefix_lens
```

- **decode**：每个请求通常只输入一个新 token，位置来自当前 sequence length；
- **extend/prefill**：每个请求可能输入不同数量的 token，需要知道已有 prefix 长度和本轮 extend 长度；
- **idle**：没有真实请求，但 DP/MLP 同步可能仍要求执行一个占位 forward。

因此 `ForwardBatch` 不是简单地把所有字段复制过去，而是根据 `forward_mode` 决定哪些 metadata 有意义。

### 3.4 核心字段映射

源码在 `ForwardBatch` 构造器中将字段逐一映射：

```python
ret = cls(
    forward_mode=batch.forward_mode,
    batch_size=len(batch.seq_lens),
    input_ids=batch.input_ids,
    req_pool_indices=batch.req_pool_indices,
    seq_lens=batch.seq_lens,
    out_cache_loc=batch.out_cache_loc,
    seq_lens_sum=batch.seq_lens_sum,
    seq_lens_cpu=batch.seq_lens_cpu,
    orig_seq_lens=batch.orig_seq_lens,
    input_embeds=batch.input_embeds,
    return_logprob=batch.return_logprob,
    is_prefill_only=batch.is_prefill_only,
    sampling_info=batch.sampling_info,
    spec_info=batch.spec_info,
)
```

实际字段更多，但可以按用途分成四组：

| 组 | 典型字段 | 用途 |
|---|---|---|
| 模型输入 | `input_ids`、`input_embeds`、`positions` | 送进 embedding 和 Transformer |
| KV 定位 | `req_pool_indices`、`out_cache_loc`、`seq_lens` | 找到历史 KV 并写入新 KV |
| 调度/采样 | `forward_mode`、`sampling_info`、`spec_info` | 决定计算和采样方式 |
| 返回控制 | `return_logprob`、hidden-state mode、LoRA id | 决定额外输出 |

### 3.5 positions：decode 一行，extend 一段

对于 decode 或 target verify，若 speculative metadata 没有提供特殊 positions，代码使用当前 sequence lengths 计算位置：

```python
if ret.forward_mode.is_decode() or ret.forward_mode.is_target_verify():
    if ret.positions is None:
        ret.positions = clamp_position(batch.seq_lens)
```

假设三个请求当前长度为 `[10, 25, 7]`，普通 decode 的 positions 就大致是 `[10, 25, 7]`，每个请求各处理一个新 token。

extend 则要根据 prefix 和 extend 长度生成一段连续位置。例如：

```text
请求 A：prefix=10, extend=3 → positions 10,11,12
请求 B：prefix=25, extend=2 → positions 25,26
```

`compute_position(...)` 同时生成扁平 token 布局的 `positions` 和 `extend_start_loc`。后者让 attention backend 知道每个请求的 token 在扁平输入数组中的起止位置。

### 3.6 M-RoPE 和额外 metadata

如果模型是多模态 rotary position embedding（M-RoPE），`init_new` 还会根据文本、图像、视频 token 的位置生成多维 positions。speculative decoding 可能直接提供 positions；普通多模态请求则调用 `_compute_mrope_positions`。

类似地，函数还会初始化：

- Mamba 的 COW/clear metadata；
- n-gram embedding 信息；
- LoRA batch；
- DP/MLP sync metadata；
- input token logprob 的 device buffer。

这说明 `ForwardBatch` 不只是“input_ids 加 seq_lens”，而是各种可选执行功能的汇合点。

## 4. `TpModelWorker.forward_batch_generation`：worker 如何组织一次生成

源文件：`python/sglang/srt/managers/tp_worker.py:1-564` 附近。

### 4.1 创建 ForwardBatch

普通调用从 `ScheduleBatch` 开始：

```python
forward_batch = ForwardBatch.init_new(
    batch,
    self.model_runner,
    capture_hidden_mode=capture_hidden_mode,
    return_hidden_states_before_norm=False,
)
```

worker 在这里还会设置 HiCache consumer，并处理已经废弃的 attention metadata 参数。真正的模型执行仍委托给 `ModelRunner`。

### 4.2 PP 最后一个 rank 才负责 logits 和 sampling

```python
if self.pp_group.is_last_rank:
    out = self.model_runner.forward(
        forward_batch,
        pp_proxy_tensors=pp_proxy_tensors,
    )
    logits_output = out.logits_output
```

Pipeline Parallel 中，前面的 rank 只有中间 hidden states，没有完整的 LM head 输出；最后一个 rank 才能产生 logits。因此：

- 非最后 rank 返回 `pp_hidden_states_proxy_tensors`；
- 最后 rank 构造 `GenerationBatchResult`，并继续 sampling。

这也是为什么不能简单地在每个 worker 上都调用 sampler。

### 4.3 普通生成与 prefill-only

普通生成请求需要采样下一个 token：

```python
if not forward_batch.is_prefill_only:
    batch_result.next_token_ids = self.model_runner.sample(
        logits_output, forward_batch
    )
```

prefill-only 请求的目标可能是计算 prompt logprob 或 embedding，而不是继续生成。此时代码生成与 batch size 对齐的 dummy token ids，并在需要时调用：

```python
self.model_runner.compute_logprobs_only(logits_output, forward_batch)
```

dummy token 不会被当成真实输出追加到请求，因为后面的 prefill result processor 会依据 `is_prefill_only` 和请求状态处理它。

### 4.4 overlap 下的延迟采样

在 overlap scheduling 中，forward 可能先完成，sampling 延迟到合适的 stream/barrier 后再做：

```python
def sample_batch_func():
    batch_result.next_token_ids = self.model_runner.sample(
        logits_output, forward_batch
    )
    return batch_result

batch_result.delay_sample_func = sample_batch_func
```

这样下一个 batch 的 GPU forward 可以和当前 batch 的部分 CPU/D2H 工作重叠。Scheduler 稍后调用 `launch_batch_sample_if_needed`，执行这个 closure、relay token，并安排结果拷贝。

延迟采样 closure 会捕获 `forward_batch` 和 logits。采样完成后源码主动清理 `delay_sample_func` 和 `next_token_logits`，避免 grammar mask 和巨大 vocabulary tensor 被 result queue 长时间持有。

## 5. `ModelRunner.forward`：统一管理执行环境

源文件：`python/sglang/srt/model_executor/model_runner.py:1612` 附近。

`ModelRunner.forward` 的职责不是实现 Transformer 每一层，而是为一次 forward 建立运行环境并选择合适的执行后端。

### 5.1 forward pass 的外围工作

函数会：

1. 应用兼容参数；
2. 增加 `forward_pass_id`；
3. 创建 profiling step span；
4. 建立 KV/attention 所需的 `ForwardContext`；
5. 记录 MoE expert distribution；
6. 调用 `_forward_raw`；
7. 处理 elastic EP、expert capture 和 indexer capture；
8. 返回 `ModelRunnerOutput`。

因此 `ModelRunner.forward` 是“执行总管”，而不是单纯的 `self.model(...)` 包装器。

### 5.2 `_forward_raw` 的选择顺序

源码的关键分支可以压缩成：

```python
can_run_graph = bool(
    forward_batch.forward_mode.is_cuda_graph()
    and self.decode_cuda_graph_runner
    and self.decode_cuda_graph_runner.can_run_graph(forward_batch)
)

if can_run_graph:
    ret = self.decode_cuda_graph_runner.execute(forward_batch)
elif forward_batch.forward_mode.is_split_prefill():
    ret = self.forward_split_prefill(forward_batch, ...)
elif prefill_cuda_graph_can_run:
    ret = self.prefill_cuda_graph_runner.execute(forward_batch, ...)
else:
    ret = self.eager_runner.execute(forward_batch, ...)
```

顺序体现了性能优先级：

- 已捕获的 decode CUDA Graph 最快，但要求 shape、metadata 和模式满足约束；
- split prefill 按层分段执行，用于特定的长 prefill/并行场景；
- prefill CUDA Graph 是 piecewise graph；
- EagerRunner 最通用，适合动态 batch 和不规则输入。

在进入后续分支前，`_prepare_eager_forward_batch` 会完成 DP/MLP sync padding 和 attention-TP normalization。普通 eager、split prefill 和 prefill graph 都需要这一步；已经做好静态 padding 的 decode graph 可以直接 replay。

### 5.3 CUDA Graph 为什么要求静态形状

CUDA Graph 记录的是一组已经建立好的 GPU 操作及其依赖。它不适合每轮都改变任意 batch size 和 tensor 地址，所以 SGLang 通常：

- 为常见 decode batch size 预先 capture；
- 把真实 batch padding 到可捕获的形状；
- 用静态 buffer 接收 input ids、sequence lengths 和 cache locations；
- replay 后只读取有效请求行。

当请求数量或 token 布局不符合已捕获 graph，`can_run_graph` 为假，就会退回 eager。对正确性而言两者应产生同样的模型结果；区别主要是启动开销和 shape 灵活性。

## 6. EagerRunner：真正调用模型

源文件：`python/sglang/srt/model_executor/runner/eager_runner.py`。

### 6.1 按 forward mode 分派

`EagerRunner.execute` 根据模式分派：

```python
if mode.is_decode():
    return self._execute_decode(forward_batch, pp_proxy_tensors)
if mode.is_idle():
    return self._execute_idle(forward_batch, pp_proxy_tensors)
if mode.is_extend(include_draft_extend_v2=True):
    return self._execute_extend(forward_batch, pp_proxy_tensors)
```

普通 mixed batch 在多数 CUDA 路径会按 extend 形状处理，因为 decode 尾部实际上也是长度为 1 的 extend；某些 NPU 或 context-parallel 路径则保留专用 mixed 模式。

### 6.2 decode 路径

`_execute_decode` 的核心步骤是：

1. 将 `ForwardBatch` 装载进 runner 的静态/共享 buffer；
2. 如有需要，让模型准备专属 metadata；
3. 调用 `attn_backend.init_forward_metadata(forward_batch)`；
4. 执行 `model.forward(input_ids, positions, forward_batch, ...)`。

attention backend metadata 会告诉 kernel：每个 query 对应哪些 KV block、sequence length 是多少、写入哪个 cache location，以及是否需要 paged attention、DCP 或其他并行处理。

### 6.3 extend/prefill 路径

`_execute_extend` 也会初始化 attention metadata，但还要处理：

- `input_embeds` 和多模态 embedding 替换；
- context parallel 的输入切分与 hidden state gather；
- DCP KV gather metadata；
- prefill shared-read snapshot；
- target verify 和 speculative metadata；
- LoRA batch。

最后仍然落到：

```python
ret = model_runner.model.forward(
    forward_batch.input_ids,
    forward_batch.positions,
    forward_batch,
    **kwargs,
)
```

`kwargs` 可能包含 `input_embeds`、`get_embedding=True`、PP proxy tensors 或 hidden-state 相关参数。

### 6.4 input ids 和 input embeds

普通文本请求的模型入口通常从 `input_ids` 做 embedding。多模态请求可能已在 tokenizer/processor 阶段生成了 embedding，或者只替换其中若干位置：

```python
if forward_batch.input_embeds is not None:
    kwargs["input_embeds"] = forward_batch.input_embeds.bfloat16()

if replace_embeds and replace_positions:
    base_embeds = embed_layer(forward_batch.input_ids)
    base_embeds[replace_positions] = replace_embeds
```

因此 `input_ids` 仍然用于位置、logprob 和请求 bookkeeping，但模型的实际第一层输入可能是 `input_embeds`。

## 7. Transformer、attention 和 KV cache 在哪里发生

上层 runner 最终调用模型实现的 `model.forward`。具体模型类位于 `python/sglang/srt/models/`，不同模型会有不同的 layer、attention 和 MoE 实现，但通用结构大致如下：

```text
input_ids / input_embeds
        │
   token embedding
        │
   repeated transformer layers
   ┌──────────────────────────────┐
   │ RMSNorm / LayerNorm           │
   │ QKV projection                │
   │ attention                     │◄── read historical KV
   │ write new K/V to KV pool      │
   │ residual                      │
   │ MLP or MoE                   │
   │ residual                      │
   └──────────────────────────────┘
        │
   final norm + lm_head
        │
      logits
```

### 7.1 prefill

假设请求有 100 个未缓存 token：

- `ForwardBatch.input_ids` 扁平包含这 100 个 token；
- `extend_prefix_lens` 描述每个请求已经存在的 prefix；
- attention backend 读取 prefix 的 KV；
- 当前 100 个位置产生新的 K/V，并写入 `out_cache_loc` 指定的池槽；
- 最后一个有效位置的 hidden state 通常用于产生 next-token logits。

### 7.2 decode

下一轮每个请求只输入一个新 token：

- `input_ids` 长度大致等于 batch size；
- `positions` 是每个请求当前的末尾位置；
- attention 读取请求历史的所有 KV；
- 新 token 的 K/V 写入本轮分配的 decode slot；
- 产生每个请求一个 next-token logits 行。

`ReqToTokenPool` 把逻辑位置映射到 KV pool 的物理槽位，attention backend 再把这种映射编译成 kernel 可以消费的 metadata。模型层不需要知道 radix tree 的节点结构；它只使用已经准备好的 cache location 和 attention metadata。

### 7.3 MLP/MoE 和并行

如果是普通 MLP，hidden state 进入 feed-forward 网络；如果是 MoE，则 router 先选择 experts，再执行 token dispatch、expert computation 和 combine。TP/EP/DP 可能在 projection、expert 或 token 数量上插入 collective communication。

这也是 `ModelRunner.forward` 要包围 expert recorder、elastic EP 和同步逻辑的原因：模型数学结构在 `model.forward` 中，而跨 rank 的执行协调由 runner/parallel state 和特定 layer 共同完成。

## 8. `LogitsProcessorOutput`：logits 不只是一个矩阵

模型 forward 的结果通常由 `LogitsProcessorOutput` 表示，定义和使用位于 `python/sglang/srt/layers/logits_processor.py` 及 `model_runner.py`。

对普通生成来说最重要的是：

- `next_token_logits`：每个请求下一 token 的 vocabulary logits；
- `next_token_logprobs`：需要返回 logprob 时产生；
- input token logprobs；
- top logprobs 和指定 token ids 的 logprobs；
- hidden states；
- sampling mask、entropy 等可选结果。

prefill 期间，模型可能产生每个输入位置的 logits，而 Scheduler 只需在对应范围内提取 prompt logprob，或者使用最后位置 logits 采样第一个输出 token。decode 则通常每个请求只有一行 next-token logits。

`LogitsProcessorOutput` 的好处是把“模型原始输出”和“采样/观测附加结果”放在同一个结构中，后续可以按 request flags 只复制需要的字段。

## 9. logits processor 和 sampler

### 9.1 先处理限制，再采样

`ModelRunner.sample` 位于 `model_runner.py:1884` 附近，核心流程是：

```python
observer_state = self._preprocess_logits(
    logits_output, forward_batch.sampling_info
)

next_token_ids = self.sampler(
    logits_output,
    forward_batch.sampling_info,
    forward_batch.return_logprob,
    forward_batch.top_logprobs_nums,
    forward_batch.token_ids_logprobs,
    positions,
)
```

`_preprocess_logits` 会：

1. 根据 grammar/regex 更新 vocabulary mask；
2. 应用 logits bias；
3. 在 grammar mask 使用后释放 GPU mask；
4. 如果启用了 sampling observer，记录观测状态。

例如 JSON grammar 要求下一个字符只能是引号、数字或某些结构符号，那么不允许的 vocabulary token 会被设为极小值，sampler 就不会选择它。

### 9.2 sampler 处理什么

sampler 根据 `SamplingBatchInfo` 处理：

- temperature；
- top-k；
- top-p / min-p；
- frequency/presence/repetition penalty；
- grammar mask 和 logits bias；
- logprob 计算；
- 指定 token 的概率查询。

在 greedy decoding 中，结果近似是取 logits 最大的 token；在随机采样中，则先按 temperature 和过滤规则得到分布，再使用随机数采样。

### 9.3 prefill 为什么也会 sample

prefill 处理 prompt 的最后一个位置后，需要知道第一个输出 token。因此普通生成请求的 prefill 也调用 `sample`，得到一个 token 并写入 `GenerationBatchResult.next_token_ids`。

这不代表 prefill 中每个输入位置都采样；通常只有每个请求的末位置用于 next-token generation。若请求是 prefill-only，则不继续生成，而是使用 dummy ids，并可单独走 logprob-only 路径。

### 9.4 logprob-only 路径

```python
self.sampler.compute_logprobs_only(
    logits_output,
    forward_batch.sampling_info,
    forward_batch.top_logprobs_nums,
    forward_batch.token_ids_logprobs,
)
```

这条路径跳过真正的 next-token sampling，但仍填充用户指定 token 的概率信息。对于只做评分或 prompt logprob 的请求，避免了不必要的随机采样和后续 decode。

## 10. sampled token 怎样进入下一轮

一次 decode 得到的 token 不是只用于响应，它还要成为下一轮模型的输入。SGLang 对普通和 overlap 路径分别维护这个 relay：

```text
本轮 forward/sample
       │
       ▼
next_token_ids
       │
       ├─ Scheduler 结果处理：追加到 req.output_ids
       ├─ KV bookkeeping：确认新 KV 已提交
       └─ future_map / batch 输入 relay
                │
                ▼
下一轮 ForwardBatch.input_ids
```

在 overlap 模式，`_relay_forward_payload` 将 token 放入 `future_map`，下一轮通过 `resolve_forward_inputs` 消费。源码中普通非 speculative 情况会构造：

```python
payload = RelayPayload(bonus_tokens=batch_result.next_token_ids)
self.future_map.stash(future_indices, payload)
```

speculative decoding 则 relay draft input 或 n-gram payload，而不是简单的一列 token。验证结果还包含接受长度，Scheduler 必须只提交被接受的 token，不能把被拒绝的 draft token 写入请求状态或 KV cache。

## 11. Scheduler 如何消费 forward 结果

源文件：`python/sglang/srt/managers/scheduler_components/batch_result_processor.py`。

`Scheduler.process_batch_result` 先根据 `forward_mode` 分派：

```python
if batch.forward_mode.is_decode():
    process_batch_result_decode(batch, result)
elif batch.forward_mode.is_extend():
    process_batch_result_prefill(batch, result)
```

同时更新 load snapshot、metrics、多模态资源和 health check。

### 11.1 prefill result

`process_batch_result_prefill` 的主要动作是：

1. 等待异步 D2H copy 完成；
2. 将 `next_token_ids` 转为 CPU；
3. 将 logprobs/hidden states 拷贝或转换为 host 数据；
4. 对每个请求追加 prefill 产生的第一个 token；
5. 更新 reasoning token、finish state 和 grammar FSM；
6. 完成请求时释放 KV cache；
7. 未完成请求插入/更新 prefix cache；
8. 处理 chunked prefill 的中间 chunk；
9. 把结果交给 output streamer。

关键代码的语义是：

```python
if req.inflight_middle_chunks <= 0:
    req.output_ids.append(next_token_id)
    req.update_finish_state()
else:
    req.inflight_middle_chunks -= 1
```

中间 chunk 尚未完成整个 prompt，不能把 dummy/中间结果当成真正生成 token 发给客户端。只有最后一个 prefill chunk 才完成首次采样和正常输出。

### 11.2 decode result

`process_batch_result_decode` 首先把 device 输出规整为每个请求的 token 列表：

```python
# non-spec: [[token_a], [token_b], ...]
# spec:     each item contains accepted tokens
```

普通 decode 一行对应一个 token；speculative decode 一行可能对应多个被接受 token。随后对每个请求：

```python
req.output_ids.extend(next_token_id)
new_accept_len = len(next_token_id)
req.update_finish_state(new_accept_len)
```

还会处理：

- output token logprobs；
- hidden states；
- sampling mask；
- grammar FSM；
- beam search；
- speculative metrics；
- finished request 的 KV 释放。

`update_finish_state` 会综合 EOS、stop string、最大输出长度、grammar 完成等条件。如果请求完成，output streamer 会在这次输出中带上 `finish_reason`，并且请求不会在后续正常 decode 中继续占用资源。

### 11.3 finish reason 的时序

一个请求可能在采样出 token 的同一轮完成：

```text
采样 token EOS
    ▼
追加 output_ids
    ▼
update_finish_state()
    ▼
finished_reason = stop / length / ...
    ▼
释放或整理 KV
    ▼
stream_output() 发出最后一段文本
```

因此客户端最后一个 chunk 往往同时包含文本增量和非空 `finish_reason`；非流式请求则等待这个完成 chunk 后再返回完整结果。

## 12. SchedulerOutputStreamer：从 Req 到 IPC payload

源文件：`python/sglang/srt/managers/scheduler_components/output_streamer.py`。

`SchedulerOutputStreamer.stream_output(reqs, return_logprob)` 不直接操作 HTTP。它负责把若干 `Req` 的新增 token 和 metadata 聚合成 batch payload。

### 12.1 只发送新增部分

`_GenerationStreamAccumulator.accept` 会记录：

- `req.output_ids_through_stop` 中尚未发送的区间；
- `req.send_token_offset`；
- 增量 detokenization 所需的 `decode_ids` 和 `read_offset`；
- prompt/completion/cached token 数；
- finish reason、logprobs、hidden states 等。

```python
self.output_ids.append(output_ids_[send_token_offset:])
req.send_token_offset = len(output_ids_)
```

这使得一个长输出不会在每轮重复传输完整历史 token。

### 12.2 stream interval 和 stop string

请求可以指定 `stream_interval`。Accumulator 只在达到间隔时发送；如果尾部暂时匹配 stop string 的前缀，也可能暂缓发送，等待更多 token 判断这是否真的是停止序列。

这就是为什么 Scheduler 内部 `Req.output_ids` 的增长频率和客户端看到的 chunk 频率不一定相同。

### 12.3 `BatchTokenIDOutput`

生成场景通常先构造 `BatchTokenIDOutput`：

```python
BatchTokenIDOutput(
    rids=...,
    finished_reasons=...,
    decoded_texts=...,
    decode_ids=...,
    read_offsets=...,
    output_ids=...,
    prompt_tokens=...,
    completion_tokens=...,
    input_token_logprobs_val=...,
    output_token_logprobs_val=...,
    output_hidden_states=...,
)
```

这个结构是进程间协议，不是 HTTP response。字段使用平行数组：第 `i` 个 `rid` 对应第 `i` 个 output、finish reason 和 metadata。

如果启用 Rust server egress，payload 会进入 Rust ring；否则通过 ZMQ 发送给 DetokenizerManager。Scheduler 不需要知道客户端具体使用原生 `/generate` 还是 OpenAI 兼容 API。

## 13. DetokenizerManager：token ids 到增量文本

源文件：`python/sglang/srt/managers/detokenizer_manager.py:303` 附近。

Scheduler 发的是 token ids 和增量状态，DetokenizerManager 维护每个请求的 `DecodeStatus`：

- 已经收到的 `decode_ids`；
- `surr_offset`：用于 stop string 检查的范围；
- `read_offset`：已经读取/处理到的位置；
- `decoded_text` 和 `sent_offset`：已经提交和已经发出的文本长度。

### 13.1 增量 decode

每次收到 `BatchTokenIDOutput`：

1. 将新的 `decode_ids` 追加到请求状态；
2. 取尚未处理的 token 区间；
3. 调 tokenizer decode；
4. 去掉 stop string 匹配部分；
5. 只输出新增文本。

源码中未完成 UTF-8 字符会特殊处理：如果新文本以替换字符 `�` 结尾，系统只发出可确定的 printable prefix，不立即提交不完整字节，下一轮有更多 token 后再重试。这样可以避免多字节字符跨 chunk 时产生乱码或重复输出。

### 13.2 完成时清理状态

当 `finished_reasons[i]` 非空时，DetokenizerManager 会物化最终文本、应用 stop trim，然后删除该 rid 的 `decode_status`。请求状态不会无限留在 detokenizer 中；如果状态因容量压力提前淘汰，系统会给出明确错误并提示调整 `SGLANG_DETOKENIZER_MAX_STATES`。

### 13.3 输出 `BatchStrOutput`

DetokenizerManager 把 token payload 转换为 `BatchStrOutput`：

```python
BatchStrOutput(
    rids=recv_obj.rids,
    output_strs=output_strs,
    output_ids=recv_obj.output_ids,
    finished_reasons=recv_obj.finished_reasons,
    ...
)
```

注意：logprobs、hidden states、cached token 数等 metadata 会原样继续传递；只有文本字段在这一层由 token ids 计算出来。

## 14. TokenizerManager 如何唤醒 HTTP 协程

TokenizerManager 的 `handle_loop` 从 detokenizer channel 收到 `BatchStrOutput` 或 `BatchTokenIDOutput`，然后调用 `_handle_batch_output`。

对每个 rid，函数会：

1. 找到 `rid_to_state[rid]`；
2. 构造 `meta_info`，包括 finish reason、token 计数、cache 计数和时间信息；
3. 合并 logprob、hidden states、grammar/customized info；
4. 把 `output_strs[i]` 和 output ids 追加到 `ReqState`；
5. 设置 `state.finished`；
6. 设置 event，唤醒等待中的 `_stream_one_response`。

典型的增量流输出是：

```python
out_dict = {
    "text": delta_text,
    "output_ids": delta_output_ids,
    "meta_info": meta_info,
}
```

非增量 streaming 则可能在中间步骤只累计 state，等 finished 后一次性构造完整文本，避免每个 token 都复制整个历史字符串导致 O(n²) 成本。

如果客户端断开，`_stream_one_response` 会向 Scheduler 发送 abort；Scheduler 随后停止请求、释放 KV 并避免继续把结果推入已不存在的客户端状态。

## 15. HTTP 层如何形成最终响应

这一层在 `python/sglang/srt/entrypoints/http_server.py:911` 附近，上一章已经介绍过入口。现在把输出链路闭合起来。

### 15.1 非流式请求

```text
HTTP POST /generate
        │
        ▼
TokenizerManager.generate_request() 返回异步生成器
        │
        ▼
await generator.__anext__()
        │  直到 ReqState 收到完成输出
        ▼
BatchStrOutput → meta_info + 完整 text
        │
        ▼
JSON response
```

非流式 handler 只取异步生成器的第一个/最终输出，不需要自己轮询 Scheduler。

### 15.2 流式请求

```python
async def stream_results():
    async for out in tokenizer_manager.generate_request(obj, request):
        yield b"data: " + dumps_json(out) + b"\n\n"
    yield b"data: [DONE]\n\n"
```

每个 `out` 都可能是一个增量 chunk；HTTP 层把它编码成 SSE。最后额外发送：

```text
data: [DONE]

```

SSE 的 framing 是 HTTP 协议适配，不是模型生成逻辑。模型只知道 token，Scheduler 只知道 Req，TokenizerManager 才把结果组织成 API 字典。

### 15.3 OpenAI 兼容 API

OpenAI、Anthropic、Ollama 等路由可能重新组织字段，例如把 `text` 包装成 `choices[0].delta.content`，但它们仍然共享底层的 `TokenizerManager.generate_request` 和 ReqState 生命周期。换句话说，兼容协议改变的是“最后一公里的 JSON 形状”，不是 GPU batch。

## 16. 一个具体例子：两个请求如何经历 prefill 和 decode

假设有两个请求：

```text
A: "The capital of France is"
B: "The capital of Germany is"
```

### 第一步：prefill

Scheduler 发现 A、B 都在 waiting queue，且 KV 空间允许一起运行：

```text
ScheduleBatch.reqs = [A, B]
forward_mode = EXTEND
extend_lens = [6, 6]       # 示例 token 数
prefix_lens = [0, 0]
```

`ForwardBatch.init_new` 将两个 prompt 扁平化为输入 token，并生成对应 positions。模型执行后得到两个末位置 logits：

```text
logits(A, last prompt position)
logits(B, last prompt position)
```

sampler 可能得到：

```text
A → "Paris"
B → "Berlin"
```

`process_batch_result_prefill` 把 token 写入各自 `output_ids`，并把 A/B 放入 running batch，除非 token 已经触发停止条件。

### 第二步：decode

下一轮每个请求只输入一个 token：

```text
input_ids = [Paris, Berlin]
positions = [6, 6]
out_cache_loc = [slot_A, slot_B]
forward_mode = DECODE
```

attention 分别读取 A/B 的历史 KV，并将新 token 的 KV 写入各自 slot。采样得到下一 token 后，`process_batch_result_decode` 追加到 `output_ids`，output streamer 只发送本轮新增部分。

### 第三步：请求长度不同

如果 A 很快生成 EOS，而 B 还要继续：

```text
t0: A decode, B decode
 t1: A finished, B decode, C prefill
 t2: B decode, C decode, D prefill
```

continuous batching 的关键就在于：下一轮 `ScheduleBatch` 可以移除 A、保留 B，同时加入 C；模型 runner 不要求整个静态 batch 一起结束。

## 17. overlap scheduling 下同一条路径有什么不同

非 overlap 模式可以近似理解为：

```text
run forward → D2H → process result → choose next batch
```

overlap 模式则尽可能变为：

```text
forward(batch N)
       ├─ relay token / next inputs
       ├─ D2H copy on copy stream
       └─ process result while forward(batch N+1) runs
```

`Scheduler.run_batch` 中可以看到：

- forward stream 等待 schedule stream；
- batch result 的 `copy_to_cpu` 可以在 copy stream 执行；
- `copy_done` event 让 result processor 在需要时同步；
- sampled token 通过 `future_map` relay 给下一轮；
- batch snapshot 和 `_forward_isolation` 防止下一轮调度修改当前 forward 正在使用的对象。

对初学者来说，最重要的结论是：**overlap 不改变模型数学流程，而是改变各阶段的时间排列和数据生命周期**。因此源码中会有更多 event、record、snapshot 和 keep-alive reference，但最终仍然是 forward → sample → commit → stream。

## 18. 常见误解

### 误解一：`ModelRunner.forward` 返回字符串

错误。它返回 `ModelRunnerOutput`，其中可能有 logits、PP proxy tensors 和运行状态。token 到文本需要经过 sampler、Scheduler、DetokenizerManager。

### 误解二：每个 decode batch 都只调用一次模型且同步完成

在 eager 非 overlap 路径中可以这样近似，但 CUDA Graph、overlap、PP、speculative decoding 和 split prefill 都会改变具体调用关系。

### 误解三：prefill 只计算 KV，不会产生输出 token

普通生成请求的 prefill 会使用 prompt 最后位置 logits 采样第一个输出 token。只有 prefill-only 或某些中间 chunk 场景不会把当前结果当成可见生成输出。

### 误解四：sampler 负责所有停止逻辑

sampler 负责从 logits 选择 token；EOS、stop string、最大长度、grammar 完成等请求生命周期状态由 Scheduler 的 result processor 和 `Req.update_finish_state` 处理。

### 误解五：output streamer 就是 HTTP streamer

`SchedulerOutputStreamer` 是 Scheduler 到 detokenizer 的 IPC payload 聚合器；HTTP SSE streamer 在 `http_server.py`，两者位于不同进程/层次。

### 误解六：可以随便修改 `ScheduleBatch`

不应当。尤其在 overlap 中，forward batch、snapshot 和下一轮调度可能共享或引用相关对象。`ForwardBatch.init_new` 的注释就是为了防止这种隐式状态污染。

## 20. 小结

模型执行链路可以浓缩为五个边界：

```text
ScheduleBatch
  = Scheduler 的本轮计划

ForwardBatch
  = 模型 forward 的执行视图

GenerationBatchResult
  = GPU forward / sampling 的结果

BatchTokenIDOutput
  = Scheduler 到 detokenizer 的 IPC 协议

HTTP JSON / SSE
  = 面向客户端的最终协议
```

完整闭环是：

- Scheduler 选择请求和 KV 资源；
- `ForwardBatch.init_new` 准备 device/host metadata；
- TpModelWorker 和 ModelRunner 选择 graph/eager 路径；
- Transformer attention 读写 KV cache 并产生 logits；
- logits processor 应用 grammar/bias，sampler 产生 token；
- Scheduler 把 token 提交到 `Req`，更新停止状态和 cache；
- output streamer 发送增量 token payload；
- DetokenizerManager 把 token 转为文本；
- TokenizerManager 将结果放入 ReqState 并唤醒 HTTP；
- HTTP 层输出 JSON 或 SSE。

理解这个闭环后，后续阅读量化、MoE、TP/PP/DP/EP、投机解码和多模态代码时，可以把它们看成是在某个边界上插入专门逻辑，而不是重新发明一条完全不同的请求路径。
