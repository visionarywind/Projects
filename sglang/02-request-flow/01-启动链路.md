# 01 启动链路：从 `sglang serve` 到 HTTP 服务

本章先回答最实际的问题：执行 `sglang serve --model-path Qwen/Qwen3-8B` 后，程序是怎样一步步启动的？理解启动链路后，阅读任何运行时模块都会更容易，因为你知道对象从哪里创建、配置从哪里传入。

## 1. 先看整体流程

```text
命令行
  ▼
sglang.cli.main:main
  ▼
sglang.cli.serve:serve
  ├─ 解析 --model-type / positional model path
  ├─ 创建 backend registry
  └─ 选择 LLM 或 diffusion backend
       ▼
_run_llm
  ▼
prepare_server_args
  ▼
launch_server.run_server
  ├─ encoder-only？
  ├─ SMG gRPC？
  ├─ Ray？
  └─ 默认 HTTP
       ▼
 srt.entrypoints.http_server:launch_server
       ▼
 FastAPI + TokenizerManager + Scheduler processes
```

这里有一个重要的设计：**顶层 CLI 选择“服务类型”，运行时启动函数选择“部署模式”**。不要把 `sglang serve` 当成模型执行函数。

## 2. 顶层命令：`cli/main.py`

`python/sglang/cli/main.py` 的 `main` 注册顶层子命令，例如 `serve`、`generate`、`version`。它把命令行解析和具体业务分离：

- 顶层 parser 只处理通用命令；
- `serve` 的剩余参数交给 `cli/serve.py`；
- 这样新增后端时，不需要把所有模型参数塞进顶层 parser。

对初学者来说，可以把它看成 Linux 命令的路由器：先判断你要执行哪种命令，再把参数交给对应模块。

## 3. `serve` 如何做后端分发

源文件：`python/sglang/cli/serve.py`。

### 3.1 兼容位置参数

`_normalize_positional_model_path`（约第 54 行）允许下面两种写法：

```bash
sglang serve Qwen/Qwen3-8B
sglang serve --model-path Qwen/Qwen3-8B
```

第一种会被转成 `--model-path` 形式，再交给统一解析逻辑。这种“先规范化、后处理”的方式可以减少后续代码的分支。

### 3.2 `--model-type`

`_extract_model_type_override`（约第 22 行）从参数中提取 `--model-type`，默认值是 `auto`。它没有把后端选择硬编码到 argparse 的 choices 中，因为插件可以通过 entry point 动态添加后端。

这体现了一个扩展点：**内置后端和 out-of-tree 后端使用同一个 registry 协议**。

### 3.3 backend registry

`_create_backend_registry`（约第 128 行）注册：

- `llm` → `_run_llm`；
- `diffusion` → `_run_diffusion`，并提供 `_detect_diffusion`。

`serve` 函数（约第 165 行）执行如下步骤：

1. 提取 backend override；
2. 规范化模型路径；
3. 创建 `ServeRequest`，保存不可变的参数视图；
4. 处理 help；
5. 加载插件；
6. auto 模式下调用 registry 检测；
7. 检查后端是否要求模型路径；
8. 调用选中的 backend。

最后的 `finally: kill_process_tree(...)` 用于在服务退出时清理子进程。这一点很重要，因为一个 SGLang 服务通常会启动多个 worker 进程。

## 4. `run_server`：选择部署模式

源文件：`python/sglang/launch_server.py:16`。

核心代码可以压缩成伪代码：

```python
def run_server(server_args):
    server_args.resolve_once()
    cfg = resolving_view(server_args)

    if cfg.encoder_only:
        launch_encoder_server(server_args)
    elif cfg.smg_grpc_mode:
        asyncio.run(serve_grpc(server_args))
    elif cfg.use_ray:
        launch_ray_server(server_args)
    else:
        launch_http_server(server_args)
```

### 4.1 为什么先 `resolve_once`

`ServerArgs` 里既有用户原始输入，也有根据多个参数推导出的配置。例如一个旧 flag 可能折叠成新的内部字段。`resolve_once` 把配置解析成稳定视图，后面的代码不必每次重复解释参数。

### 4.2 为什么延迟 import

`run_server` 在不同分支中才 import 对应模块：

- 未启用 Ray 时不需要导入 Ray；
- 未启用 diffusion 时不需要加载 diffusion 依赖；
- 未启用 gRPC 时不需要初始化 gRPC 相关组件。

这能减少启动时间，也让不同硬件/安装变体的依赖保持可选。

### 4.3 默认 HTTP 分支

普通 LLM 服务最终调用 `srt.entrypoints.http_server.launch_server(server_args)`。这里才开始构造 HTTP 应用、TokenizerManager、worker 等运行时对象。

## 5. HTTP server 的职责边界

源文件：`python/sglang/srt/entrypoints/http_server.py`。

从文件布局可看到几个阶段：

1. 全局状态和初始化（约第 199 行起）；
2. FastAPI 请求/异常适配；
3. health 和管理接口；
4. `generate_request` 生成路由（约第 911 行）；
5. OpenAI/Anthropic/Ollama 等协议兼容路由；
6. warmup、profile、启动服务器（约第 2200 行以后）；
7. `launch_server`（约第 2798 行）。

HTTP 层做三件事：

- 把网络数据校验成 Python 内部结构；
- 调用 TokenizerManager 的异步接口；
- 把生成器转换为普通 JSON 或 SSE 流。

它不负责决定 batch，也不直接操作 GPU tensor。

## 6. 从原生生成路由进入管理器

`generate_request`（约第 911 行）的典型逻辑是：

```python
async def generate_request(obj, request):
    if obj.stream:
        async def stream_results():
            async for output in tokenizer_manager.generate_request(obj, ...):
                yield encode_as_sse(output)
        return StreamingResponse(stream_results(), media_type="text/event-stream")

    output = await tokenizer_manager.generate_request(obj, ...)
    return JSONResponse(output)
```

实际实现还会处理 abort、请求 id、异常和 OpenAI 格式，但边界很清晰：**路由只负责协议，TokenizerManager 负责生成请求的生命周期**。

## 7. 一个启动例子

```bash
sglang serve --model-path Qwen/Qwen3-8B --tp-size 2 --port 30000
```

执行时：

1. `cli/main.py` 识别 `serve`；
2. `cli/serve.py` 识别 model path，默认选择 `llm`；
3. `_run_llm` 调用 `prepare_server_args`；
4. `run_server` 解析 `tp-size=2`，进入默认 HTTP 路径；
5. HTTP server 创建控制侧对象和两个 tensor-parallel worker；
6. worker 初始化 device、通信组、ModelRunner，加载模型；
7. warmup 成功后开放端口。

## 8. 阅读建议

启动问题通常要同时追踪三类对象：

- **配置**：`server_args.py`、`arg_groups/`、`runtime_context.py`；
- **进程**：`http_server.py`、`tokenizer_manager.py`、`scheduler.py`；
- **设备**：`tp_worker.py`、`model_runner.py`、`distributed/`。

如果只看 FastAPI 路由，会误以为服务是单进程同步调用；如果只看 ModelRunner，又会看不到请求是怎样到达 GPU 的。

## 9. 小结

启动链路的核心思想是分层和延迟决策：

- CLI 决定服务类别；
- `run_server` 决定部署模式；
- HTTP 层决定协议；
- TokenizerManager 决定请求如何进入运行时；
- Scheduler 决定何时执行；
- ModelRunner 决定如何在设备上执行。
