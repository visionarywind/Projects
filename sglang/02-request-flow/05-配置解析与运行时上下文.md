# 05 配置解析与运行时上下文：从命令行参数到每个进程真正使用的配置

前面几章已经把“一次请求”从 HTTP 路由追到了 GPU，也看到了 Scheduler 和 ModelRunner 如何协作。本章先退一步，回答一个看似简单、实际上贯穿整个启动过程的问题：

> 用户写在命令行上的 `--tp-size 2`、`--attention-backend flashinfer`、`--max-running-requests 128`，最后究竟由谁读取？如果一个参数没有显式填写，模型、硬件和其他参数又是怎样给它决定默认值的？

本章分析的不是某个单独的模型，而是所有服务启动都会经过的**配置生命周期**。理解它之后，再去看 Scheduler、ModelRunner 或多进程启动代码，就能分清：某个模块读取的是用户原始输入，还是解析后的有效配置。

---

## 1. 先给初学者一个直观模型

### 1.1 配置不是一张字典，而是一条流水线

可以把启动配置想象成机场值机：

1. 用户带着自己的行李到柜台：这相当于 CLI 参数和 YAML 配置文件。
2. 柜台把行李贴上标签、检查尺寸：这相当于 `argparse` 解析和基础校验。
3. 航空公司根据航班、机型和天气调整行李规则：这相当于模型、平台、并行策略和内存策略的解析。
4. 最终每个乘客拿到一张登机牌：这相当于发布给进程的配置 namespace bags。

因此，下面三个概念不能混为一谈：

```text
ServerArgs 字段
    = 用户交给系统的原始输入

resolved overrides（声明暂存区）
    = 解析流水线作出的决定

runtime config bags
    = 某个进程运行时真正读取的有效配置
```

例如用户没有写 `--page-size`：

```text
原始输入：page_size = 1（字段声明的默认值）
解析决定：模型/注意力后端最终选择 page_size = 128
运行时读取：get_memory().page_size == 128
```

这里并不是把 `ServerArgs.page_size` 改成 128，而是把“最终决定”记录在另一处，再投影到运行时配置包中。

### 1.2 为什么不直接修改 `ServerArgs`？

传统写法可能是：

```python
if args.tp_size > 1:
    args.attention_backend = "flashinfer"
args.max_prefill_tokens = args.chunked_prefill_size
```

这种写法短期看起来很方便，但有几个问题：

- 你无法知道 `attention_backend` 是用户指定的，还是程序自动推导的。
- 第二次运行解析函数时，第一次的结果会被当成新的输入，某些“减半”“追加”类操作会重复生效。
- 父进程和子进程可能看到不同的对象状态。
- 代码中一个模块读原始字段，另一个模块读已修改字段，很容易产生顺序依赖。
- 配置发布之后，某个旧调用点继续修改 `ServerArgs`，会造成“写入一个存储、读取另一个存储”的不同步。

当前实现选择了更严格的方式：

```text
输入记录保持原样
       +
按顺序追加带来源的决定
       ↓
投影出有效配置
```

这也是本章最重要的设计思想。

## 2. 从 `sglang serve` 开始：CLI 参数是怎样进入 `ServerArgs` 的

### 2.1 一个具体命令

```bash
sglang serve \
  --model-path Qwen/Qwen3-8B \
  --tp-size 2 \
  --max-running-requests 128 \
  --attention-backend flashinfer
```

大致调用链是：

```text
sglang
  ▼
sglang.cli.main:main
  ▼
sglang.cli.serve:serve
  ▼
sglang.srt.server_args:prepare_server_args
  ▼
argparse.Namespace
  ▼
ServerArgs.from_cli_args
  ▼
未解析的 ServerArgs
```

CLI 层此时还没有决定所有运行时行为。它主要负责把字符串转换成字段值，并保留“用户到底写了什么”。

### 2.2 `add_cli_args`：大部分参数来自字段元数据

源文件：`python/sglang/srt/server_args.py`，约 345 行。

核心代码是：

```python
@staticmethod
def add_cli_args(parser: argparse.ArgumentParser):
    add_cli_args_from_dataclass(parser, ServerArgs)
```

`ServerArgs` 的字段由 `arg_groups/fields/` 下的 namespace 类声明。例如 `Parallel` 中的字段：

```python
tp_size: A[
    int,
    Arg(
        help="The tensor parallelism size.",
        aliases=["--tensor-parallel-size"],
    ),
] = 1
```

这段声明同时表达了四件事：

- Python 类型是 `int`；
- CLI 主名字根据字段名生成，即 `--tp-size`；
- 还支持别名 `--tensor-parallel-size`；
- 没有填写时，默认输入是 `1`。

`A[...]` 是项目自己的类型与参数元数据组合。这样新增一个普通参数时，通常只需要在合适 namespace 中声明字段，不需要在一个巨大的 argparse 函数里重复写类型、帮助文本和默认值。

### 2.3 特殊参数仍然手动注册

不是所有参数都能静态从字段元数据生成。`add_cli_args` 后面手动处理了三类特殊情况。

#### 动态 choices

```python
sampling_backend_choices = set(SAMPLING_BACKEND_CHOICES)
if envs.SGLANG_KV_CANARY_ENABLE_TOKEN_ORACLE.get():
    sampling_backend_choices.add("token_oracle")
parser.add_argument(
    "--sampling-backend",
    type=str,
    choices=sampling_backend_choices,
    default=_declared_default("sampling_backend"),
)
```

`token_oracle` 是否可用取决于环境变量，所以 choices 不能在模块静态定义时完全固定。

推理和工具调用解析器也是动态 choices：

```python
reasoning_parser_choices = list(ReasoningParser.DetectorMap.keys())
tool_call_parser_choices = list(FunctionCallParser.ToolCallParserEnum.keys())
```

这意味着插件注册了新的 parser 后，CLI 可以看到新选项。这里的扩展点不是“把所有插件名称硬编码进 argparse”，而是“在构造 parser 的时刻查询注册表”。

#### 配置文件元参数

```python
parser.add_argument(
    "--config",
    type=str,
    help="Read CLI options from a config file. Must be a YAML file ...",
)
```

`--config` 本身不是服务运行配置的普通叶子；它告诉解析器去哪里寻找更多配置。

#### 旧参数兼容

```python
parser.add_argument(
    "--disable-cuda-graph",
    action=DeprecatedStoreTrueAction,
    new_flag="--cuda-graph-backend-{decode,prefill}=disabled",
)
```

旧 flag 仍可被接受，但它会转换或提示新的表达方式。兼容逻辑属于 CLI 入口，而最终有效值仍应经过统一解析流水线。

### 2.4 `from_cli_args`：Namespace 变成结构化记录

源文件：`server_args.py`，约 418 行。

```python
@classmethod
def from_cli_args(cls, args: argparse.Namespace):
    attrs = [
        attr.name
        for attr in record_fields(cls)
        if hasattr(args, attr.name)
    ]
    return cls(**{attr: getattr(args, attr) for attr in attrs})
```

这里没有直接把整个 `Namespace.__dict__` 塞进对象，而是只收集 `ServerArgs` 的真实字段：

- argparse 中存在且属于 `ServerArgs` 的字段被复制；
- 没有 CLI 表面的字段继续使用结构体声明的默认值；
- `--config`、帮助参数等控制解析器本身的元信息不会变成运行时配置叶子。

`ServerArgs` 最终是由 `msgspec.defstruct` 组装成的结构化记录，而不是普通的松散字典。结构化记录的好处是字段集合明确、类型信息保留、序列化和跨进程传递更可控。

## 3. YAML 配置文件：为什么是 CLI 覆盖配置文件

### 3.1 一个 YAML 示例

`server.yaml`：

```yaml
model-path: Qwen/Qwen3-8B
tp-size: 2
max-running-requests: 64
cuda-graph-backend-decode: piecewise
```

命令行又写：

```bash
sglang serve --config server.yaml --max-running-requests 128
```

预期优先级是：

```text
命令行参数 > 配置文件 > 字段默认值
```

所以最终 `max_running_requests` 应为 128，而不是 YAML 中的 64。

### 3.2 `prepare_server_args` 的顺序

源文件：`python/sglang/srt/server_args.py`，约 690 行。

```python
def prepare_server_args(argv: list[str]) -> ServerArgs:
    parser = argparse.ArgumentParser(prog="sglang serve")
    ServerArgs.add_cli_args(parser)

    if "--config" in argv:
        from sglang.srt.utils.server_args_config_parser import ConfigArgumentMerger
        config_merger = ConfigArgumentMerger(parser)
        argv = config_merger.merge_config_with_args(argv)

    raw_args = parser.parse_args(argv)
    ...
    server_args = ServerArgs.from_cli_args(raw_args)
    server_args._launch_command = " ".join(argv)
    return server_args
```

注意关键顺序：

1. 先构造完整 parser；
2. 如果出现 `--config`，先读取 YAML；
3. 把 YAML 转成类似 CLI 的 token；
4. 把两者合并；
5. 最后只调用一次 argparse；
6. 用解析结果创建 `ServerArgs`。

### 3.3 `ConfigArgumentMerger` 如何实现优先级

源文件：`python/sglang/srt/utils/server_args_config_parser.py`，约 52 行。

```python
config_data = self._parse_yaml_config(config_file_path)
config_args = self._convert_config_to_args(config_data)

config_index = cli_args.index("--config")
before_config = cli_args[:config_index]
after_config = cli_args[config_index + 2:]

return config_args + before_config + after_config
```

配置文件被转换成参数序列，并插入到原始 CLI 参数之前。`argparse` 对普通单值参数通常采用后出现的值，因此用户真正写在命令行上的参数覆盖了配置文件值。

例如：

```text
YAML 转换结果：
--max-running-requests 64

用户 CLI：
--config server.yaml --max-running-requests 128

合并后：
--max-running-requests 64 --max-running-requests 128
```

解析结果就是 128。

### 3.4 YAML 中不同值的转换

`_convert_config_to_args` 约在 141 行：

```python
for key, value in config.items():
    key_norm = key.replace("-", "_")
    if isinstance(value, bool):
        self._add_boolean_arg(args, key, value)
    elif isinstance(value, list):
        self._add_list_arg(args, key, value)
    elif isinstance(value, dict):
        self._add_scalar_arg(args, key, json.dumps(value))
    else:
        self._add_scalar_arg(args, key, value)
```

它把 YAML 值映射到 argparse 能理解的 token：

```yaml
trust-remote-code: true
```

可能变成：

```text
--trust-remote-code true
```

如果字段是 `store_true` action，则 `true` 变成只出现 flag，`false` 则跳过；列表展开成多个 token；字典序列化成 JSON 字符串，以便现有参数类型解析器继续处理。

实现还会拒绝不支持的 argparse action，并检查：

- 只能指定一个配置文件；
- `--config` 后必须有路径；
- 后缀必须是 `.yaml` 或 `.yml`；
- 文件存在；
- YAML 根节点必须是字典。

因此配置文件功能不是绕过 CLI 校验，而是先把另一种输入格式规整成相同的 CLI 输入。

## 4. `ServerArgs` 的真实身份：原始输入记录

### 4.1 namespace 类与扁平 record

源码把字段按职责分散到：

```text
arg_groups/fields/
├── model.py
├── parallel.py
├── memory.py
├── schedule.py
├── spec.py
├── exec_*.py
├── device.py
└── ...
```

例如：

- `Model` 描述模型路径、dtype、量化和 tokenizer；
- `Parallel` 描述 TP、PP、DP、CP 和通信；
- `Memory` 描述显存比例、KV cache 和页布局；
- `Schedule` 描述请求数、prefill token 预算和调度策略；
- `Spec` 描述 speculative decoding；
- `Exec*` 描述执行后端和运行时 feature。

但 `ServerArgs` 并不通过继承这些 namespace 来形成嵌套对象，而是把输入字段组装为一个扁平结构体。这样旧的 positional constructor 和很多已有调用点仍保持兼容。

源码中的 `_INPUT_NAMESPACES`（`server_args.py` 约 515 行）列出这些输入 namespace，再由 `collect_input_fields` 收集注解和默认值。

随后：

```python
ServerArgs = msgspec.defstruct(
    "ServerArgs",
    [...],
    namespace={...},
    dict=True,
)
```

`dict=True` 很关键：

- 结构体的字段仍然是明确的配置字段；
- `__dict__` 可以保存不属于配置字段的 bookkeeping；
- `_raw_input`、`_resolved_overrides`、解析状态和模型配置缓存可以随对象携带。

### 4.2 字段顺序为什么单独冻结

源文件：`python/sglang/srt/arg_groups/field_order.py`。

注释指出，结构体字段顺序会影响 positional constructor：

```python
ServerArgs(model_path, tokenizer_path, ...)
```

如果仅仅因为把 namespace 拆成多个文件就改变字段顺序，旧代码传入的第二个位置参数可能静默落到错误字段。因此项目用 `POSITIONAL_FIELD_ORDER` 保持兼容，namespace 的组织方式不会改变 record 的外部字段形状。

这给初学者一个重要启发：

> “代码文件怎样分组”与“对象在运行时怎样布局”是两件事。

## 5. 解析前、解析中、解析后的三种视图

### 5.1 原始字段：用户输入

`ServerArgs` 上的公开字段代表输入记录。例如：

```python
server_args.tp_size
server_args.attention_backend
server_args.chunked_prefill_size
```

在解析期间，这些字段不应该被 resolver 改写。它们保留了用户传入值（包括字段默认值）。

### 5.2 `resolving_view`：动态读取当前已决定的值

源文件：`python/sglang/srt/arg_groups/model_override_base.py`，约 106-139 行。

```python
class ResolvingConfig:
    def __getattr__(self, name: str) -> Any:
        server_args = object.__getattribute__(self, "_server_args")
        for _source, declared in reversed(
            getattr(server_args, "_resolved_overrides", None) or ()
        ):
            if name in declared:
                return declared[name]
        return getattr(server_args, name)
```

`resolving_view(server_args)` 返回这个 live view：

```python
def resolving_view(server_args: Any) -> ResolvingConfig:
    return ResolvingConfig(server_args)
```

每一次属性读取都会从声明暂存区的末尾向前找。找不到时，才回退到原始字段。

假设流水线已经做了：

```python
declare_resolution(sa, "platform", attention_backend="flashinfer")
```

那么：

```python
sa.attention_backend                 # 仍是用户输入，例如 None
resolving_view(sa).attention_backend # "flashinfer"
```

之后的 resolver 必须读取 `resolving_view`，否则它会看不到前面阶段刚作出的决定。

视图拒绝写入：

```python
def __setattr__(self, name, value):
    raise AttributeError(
        "ResolvingConfig is read-only; resolution writes through declarations"
    )
```

### 5.3 `resolved_view`：在某个阶段固定一个快照

同一模块还提供 `ResolvedView`。它把当前声明合并成 overlay：

```python
def _declaration_overlay(server_args):
    overlay = {}
    for _source, declared in ...:
        overlay.update(declared)
    return overlay
```

然后：

```python
def resolved_view(server_args):
    return ResolvedView(
        server_args,
        overlay=_declaration_overlay(server_args),
    )
```

区别可以这样记：

```text
resolving_view：每次读取都看最新暂存区（live）
resolved_view：创建时把当前决定拍成快照（snapshot）
```

一个后处理 pass 如果必须观察“它所在阶段开始时”的状态，使用 snapshot 更合适；一个后续 resolver 如果要看刚刚追加的决定，则使用 live view。

### 5.4 外部插件的 `_ForeignDefaults`

项目不能要求所有 out-of-tree 插件立刻改成“返回 declaration”的新接口。有些旧 resolver 的约定是：

```python
def resolve(defaults):
    defaults.attention_backend = "flashinfer"
```

因此 `record_foreign_defaults` 会给它一个 stand-in：

```python
class _ForeignDefaults:
    def __init__(self, server_args):
        object.__setattr__(self, "_cfg", resolving_view(server_args))
        object.__setattr__(self, "_written", {})

    def __getattr__(self, name):
        if name in self._written:
            return self._written[name]
        return getattr(self._cfg, name)

    def __setattr__(self, name, value):
        self._written[name] = value
```

插件以为自己在写配置对象，实际上写入的是 `_written` 字典。调用结束后，项目只提取真正的 `ServerArgs` 字段，再通过 `declare_resolution` 记录。

这叫**兼容旧写法，但不破坏新不变式**：解析期间真实 record 仍然没有被 resolver 直接修改。

## 6. 声明暂存区：解析结果怎样保存

### 6.1 `declare_resolution`

源文件：`python/sglang/srt/arg_groups/overrides.py`，约 142-181 行。

```python
def declare_resolution(server_args, source: str, **fields):
    if is_record(server_args):
        unknown = sorted(set(fields) - field_names(type(server_args)))
        if unknown:
            raise AttributeError(...)

    published = ...
    if published is server_args:
        raise ValueError(...)

    stash = getattr(server_args, "_resolved_overrides", None)
    if stash is None:
        stash = []
        server_args._resolved_overrides = stash
    stash.append((source, dict(fields)))
```

它做三项工作：

1. 拒绝不存在的字段；
2. 拒绝对已经发布的 record 继续声明；
3. 把 `(source, fields)` 追加到列表。

例如：

```python
[
    ("platform_defaults", {"dtype": "bfloat16"}),
    ("qwen3_model_override", {"attention_backend": "flashinfer"}),
    ("cuda_graph_config", {"max_running_requests": 128}),
]
```

`source` 不是装饰品。它使配置具备来源信息，调试时可以回答：

> 为什么这个字段最终是这个值？是用户传的、平台默认的、模型 override，还是 CUDA Graph 阶段决定的？

### 6.2 最后声明覆盖之前声明

`resolution_result` 约在 `overrides.py:246`：

```python
def resolution_result(server_args, field, default=None):
    for _source, declared in reversed(
        getattr(server_args, "_resolved_overrides", None) or ()
    ):
        if field in declared:
            return declared[field]

    raw = getattr(server_args, "_raw_input", None)
    if raw is not None and field in raw:
        return with_fallback(type(server_args), field, raw[field])

    return with_fallback(
        type(server_args),
        field,
        getattr(server_args, field, default),
    )
```

优先级是：

```text
最新 declaration
    > 较早 declaration
    > raw input snapshot
    > 字段声明的 fallback/default
```

这是一种**按解析顺序的 last-writer-wins**，但必须注意：它不是随意的覆盖。流水线通过顺序表达依赖关系，后面的阶段通常是在更完整的信息上作出最终决定。

### 6.3 一个小例子：attention backend

假设：

```text
用户没有写 attention_backend
字段默认：None
```

依次发生：

```python
declare_resolution(
    sa,
    "model_capability",
    attention_backend="flashinfer",
)

declare_resolution(
    sa,
    "deterministic_inference",
    attention_backend="torch_native",
)
```

那么：

```python
sa.attention_backend                      # None，原始输入没有被破坏
resolution_result(sa, "attention_backend") # "torch_native"
resolving_view(sa).attention_backend       # "torch_native"
```

如果调试需要来源，可以遍历 `_resolved_overrides`，看到最终声明来自 `deterministic_inference`。

## 7. `resolve_once`：为什么解析只能安全地运行一次

### 7.1 入口代码

源文件：`python/sglang/srt/server_args.py`，约 253-292 行。

```python
def resolve_once(self) -> None:
    if getattr(self, "_resolution_finished", False):
        return
    if getattr(self, "_resolution_failed", False):
        raise RuntimeError(
            "resolution already failed on this ServerArgs ..."
        )

    self._input_frozen = True
    try:
        run_resolution_pipeline(self)
    except BaseException:
        self._resolution_failed = True
        raise
    finally:
        self._input_frozen = False
    self._resolution_finished = True
```

### 7.2 成功后的重复调用

如果解析已经完成：

```python
if _resolution_finished:
    return
```

第二次调用不会再次运行流水线。这不仅是性能优化，也是正确性要求。

某些阶段不是简单地赋值，而可能根据当前配置进行变换。例如 DP attention 可能调整 token 预算。如果同一阶段在已经解析后的结果上再执行一次，可能再次除以某个比例，造成错误配置。

### 7.3 失败后的重复调用为什么拒绝

解析不是事务式地把所有结果一次性生成；某个阶段失败前，前面阶段可能已经追加 declaration：

```text
阶段 A：成功，写入 declaration
阶段 B：成功，写入 declaration
阶段 C：抛出异常
```

此时 record 带着“半完成”的暂存区。如果允许直接重试，阶段 A/B 可能把自己的输出当输入，产生与第一次不同的结果。因此代码将 `_resolution_failed` 设为真，第二次调用直接报错，并要求从修正后的参数构造一个新 record。

这是一种很重要的工程取舍：

> 不假装失败解析可以自动回滚；明确告诉调用者必须建立新的输入记录。

### 7.4 `_input_frozen`：解析期间也禁止直接写字段

`ServerArgs.__setattr__` 约在 `server_args.py:447`：

```python
if not name.startswith("_") or name in _underscore_field_names():
    if getattr(self, "_input_frozen", False):
        raise AttributeError(
            "server_args assigned during resolution ... use declare_resolution"
        )
```

解析器内部确实需要写 bookkeeping，比如：

```python
self._raw_input = ...
self._resolved_overrides = ...
self._resolution_failed = True
```

所以代码不能简单地“所有 setattr 都拒绝”。它专门识别真正的配置字段，即使字段名字以 `_` 开头，也不会留下一个意外可写的漏洞。

resolver 若错误地写：

```python
server_args.tp_size = 4
```

会立即失败，而不是静默改变输入。正确写法是：

```python
declare_resolution(
    server_args,
    "some_resolver",
    tp_size=4,
)
```

### 7.5 完成后的只读 record

解析成功后，公开配置字段继续禁止赋值：

```python
if getattr(self, "_resolution_finished", False):
    raise AttributeError(
        "server_args assigned after resolution; server_args is read-only ..."
    )
```

如果运行时确实需要改变有效配置，不应改 `ServerArgs`，而应通过：

```python
get_context().override("control_api", max_running_requests=256)
```

或者在测试中使用 namespace bag 的 scoped override。这样修改发生在“运行时有效配置”这一层，输入 record 仍可用于复现启动命令。

## 8. `run_resolution_pipeline`：一个有依赖顺序的总调度器

### 8.1 为什么 pipeline 文件保持“薄”

源文件：`python/sglang/srt/arg_groups/pipeline.py`。

顶层函数的设计原则是：

```text
pipeline.py 负责排序
各 arg_groups hook 负责具体判断、声明和报错
```

它不把所有模型和厂商条件都直接写在一个函数里，而是导入命名清楚的 handler：

```python
handle_hicache_ratio_default(server_args)
handle_offload_compatibility(server_args)
validate_prefill_decode_interval(server_args)
handle_hardware_runtime_validation()
handle_model_source_paths(server_args)
handle_cuda_graph_config(server_args)
handle_gpu_memory_settings(server_args, gpu_mem)
handle_attention_backend_compatibility(server_args)
handle_speculative_decoding(server_args)
```

这样阅读顺序可以从 pipeline 总览开始，再进入感兴趣的 hook 文件。

### 8.2 第一件事：快照原始输入

```python
server_args._raw_input = {
    field.name: getattr(server_args, field.name)
    for field in record_fields(type(server_args))
}
```

这是整个设计的基准线。之后即使解析声明了一个值，系统仍然知道调用者最初给了什么。

随后保留可能在 launcher 阶段已经产生的 declarations：

```python
server_args._resolved_overrides = list(
    getattr(server_args, "_resolved_overrides", ())
)
```

例如 CLI backend 检测、LoRA 参数规范化或其他启动前逻辑已经作出的有效决定，不应在进入 Engine 后丢失。

### 8.3 dummy/absent-model 边界

pipeline 前面执行与模型无关的检查，然后：

```python
cfg = resolving_view(server_args)
...
handle_hardware_runtime_validation()
if cfg.model_path.lower() in ["none", "dummy"]:
    return
```

为什么 dummy 模型要尽早 return？

- 单元测试、profile 和某些 benchmark 只需要构造运行时对象；
- 不应因为没有真实权重而触发模型下载、读取 Hugging Face 配置或模型特定探测；
- 但硬件 runtime 等应当真正错误的检查仍然要在边界前执行。

`resolve_once` 在 finally 后会统一设置 `_resolution_finished = True`，所以 dummy 路径虽然没有走完整模型解析，也不会下次重复进入。

### 8.4 大致的阶段顺序

当前 pipeline 的主要顺序可压缩成：

```text
1. 记录 raw input 和已有 declarations
2. 通用 bootstrap/API/安全/兼容性检查
3. 硬件 runtime 检查
4. dummy 模型早退
5. 模型来源、路径和多模态配置
6. 缺省值、deprecated 参数、expert pack
7. PD disaggregation、DCP、KV cache 前置验证
8. 模型相关 CUDA Graph 默认值
9. DWDP、CUDA Graph 和平台后端
10. 显存容量、memory、chunked prefill
11. 模型特定调整
12. sampling 与 attention backend
13. Mamba、linear attention、KV dtype/page size
14. grammar、HiCache、DP、load balancing、CP
15. MoE 与 expert distribution
16. PP overlap 禁用策略
17. speculative decoding 与 layernorm SP
18. load format、encoder disaggregation、tokenizer、环境变量
19. cache/debug/其他验证
20. 最后的模型能力调整与收尾验证
```

阶段顺序不是按文件名或历史添加顺序排列，而是按依赖关系排列。

### 8.5 依赖例子一：显存预算依赖 chunked prefill

代码在处理 GPU memory settings 前，先处理 CUDA Graph 和部分模型特定 chunked-prefill 默认值：

```python
handle_cuda_graph_config(server_args)
apply_glm5_chunked_prefill_default(server_args)
...
gpu_mem = get_device_memory_capacity(cfg.device)
handle_gpu_memory_settings(server_args, gpu_mem)
```

原因是 chunk size 会影响 activation 工作集和 KV cache 预算。如果先算显存，再决定 chunk size，预算依据就是旧值。

这就是为什么 pipeline 注释常写：

```text
必须在 handle_gpu_memory_settings 之前运行，
因为 chunk size 会进入 memory budgeting。
```

### 8.6 依赖例子二：确定性推理要早于 attention 自动选择

代码明确写出：

```python
run_post_process_pass(server_args, _sampling_backend_default)
handle_deterministic_inference(server_args)
handle_attention_backend_compatibility(server_args)
```

如果用户要求确定性推理，确定性阶段可能先把 backend 锁定；attention compatibility 阶段再做自动探测时必须看到这个决定，不能把它覆盖回一个不确定的后端。

### 8.7 依赖例子三：speculative decoding 的后置派生值

pipeline 后段：

```python
handle_speculative_decoding(server_args)
handle_layernorm_sp(server_args)
validate_cutedsl_a2a_token_budget(server_args)
```

注释说明，`layernorm_sp` 要在 speculative hook 之后，因为 `speculative_algorithm` 此时才是最终值；CuteDSL token budget 又依赖最终的 `num_tokens_per_req`。

由此可以看出，“函数在文件中的位置”本身就是配置设计的一部分。随意调换两个 handler 可能改变最终配置，甚至让验证使用过时的中间值。

## 9. 从 declaration 到 runtime config bags

### 9.1 为什么需要发布层

解析完成后，服务会启动不同角色的进程：

```text
TokenizerManager / tokenizer worker
Scheduler
TP/PP worker
Detokenizer
DP controller
Encoder worker
```

这些进程都需要配置，但它们不应继续到处读取一个可能被误解的 raw record。运行时上下文提供了统一的访问方式：

```python
get_model()
get_device()
get_exec()
get_memory()
get_schedule()
get_spec()
get_parallel()
get_disagg()
get_serving()
```

例如：

```python
get_model().dtype
get_memory().page_size
get_schedule().max_running_requests
get_exec().moe.moe_runner_backend
```

### 9.2 `publish` 的调用链

源文件：`python/sglang/srt/runtime_context.py`，约 1563 行。

```python
def publish(server_args, *, role: str, hf_config=None):
    if _ROLE_NS_MODE == "enforce" and role not in ROLE_NAMESPACE_SETS:
        raise ValueError(...)
    server_args.resolve_once()
    discarded = _CONTEXT.overrides_log()
    _CONTEXT.set_server_args(server_args)
    ...
    _CONTEXT._publish_role = role
    return _CONTEXT
```

发布做了两件有顺序要求的事：

1. 先确保 `ServerArgs` 已解析；
2. 再把有效结果投影到当前进程的配置 bags。

`role` 用于记录这是 scheduler、tokenizer 还是其他进程角色；在 namespace enforcement 模式下，还用于限制该角色可以读取哪些顶层 namespace。

### 9.3 `_build_config_bags`：按 namespace 投影

源文件：`runtime_context.py`，约 848-899 行。

```python
def _build_config_bags(server_args):
    for field, path in namespace_of(type(server_args)).items():
        value = resolution_result(server_args, field, _MISSING)
        ...
        parts = path.split(".")
        ...
        bag._set(field, value)
    _install_derived_leaves(tops, server_args)
    return tops
```

比如：

```text
field: max_running_requests
path: schedule
```

就会产生：

```python
bags["schedule"].max_running_requests = effective_value
```

如果路径是：

```text
exec.moe
```

则会建立嵌套结构：

```python
bags["exec"].moe.moe_runner_backend
```

每个叶子通过 `resolution_result` 得到，所以使用的是 declaration > raw input > default 的有效结果，而不是直接从 record 字段读取。

### 9.4 derived fields：发布时只计算一次

namespace 中除了输入字段，还有 `Derived` 声明。例如：

```python
is_startup_weight_load_overlap = Derived(
    fn="...startup_weight_load_overlap_of",
)
```

`_install_derived_leaves` 会在 bags 建成后调用声明的纯函数，把结果作为普通叶子写入 bag：

```python
bag._set(
    name,
    getattr(importlib.import_module(module), attr)(view),
)
```

这样运行时读取是普通属性访问，而不是每次重新计算。对编译路径尤其重要：配置读取可以被 `torch.compile` 追踪，不需要因为动态 property 或 Python 逻辑频繁 graph break。

### 9.5 `_ConfigBag` 是只读的

源文件：`runtime_context.py`，约 764-845 行。

```python
class _ConfigBag:
    def __setattr__(self, name, value):
        raise AttributeError(
            "config namespace ... is read-only; write via ... override"
        )
```

发布和受控 override 使用内部 `_set`：

```python
def _set(self, name, value):
    self._fields[name] = value
    object.__setattr__(self, name, value)
```

叶子同时写入 `_fields` 和 `__dict__`：

- `_fields` 用于校验 override 的字段是否存在；
- `__dict__` 让 `bag.leaf` 成为普通、可追踪的属性读取。

直接写：

```python
get_memory().page_size = 256
```

会失败。永久性的运行时修改应走：

```python
get_context().override(
    "admin_api",
    page_size=256,
)
```

测试只想在一个作用域内改值时，可以：

```python
with get_memory().override(page_size=256):
    run_test_path()
```

退出上下文后会恢复原值。

## 10. `get_server_args` 与 `get_memory` 为什么是两个不同问题

runtime context 的模块级说明很明确：

```text
get_server_args() 返回用户的 raw input
get_memory()/get_exec()/... 返回 resolved config namespace bags
```

例如：

```python
raw = get_server_args()
effective = get_memory()
```

如果用户没有设置 page size，而解析器自动决定 128：

```python
raw.page_size             # 用户输入/字段默认
effective.page_size       # 解析后真正使用的值
```

（实际代码中请勿在变量名之间留下空格，这里只强调两个对象的概念差异。）

旧的 `get_global_server_args()` 被保留为一个会抛错的兼容入口，目的是防止业务代码继续把 raw record 当成运行时有效配置。错误消息会指向诸如：

```python
get_exec().kernel.attention_backend
get_schedule().max_running_requests
```

这种“故意让错误暴露出来”的做法，比让旧调用点悄悄读到过时值更容易迁移。

## 11. 运行时 override：发布之后怎样合法改变配置

### 11.1 与启动解析的区别

启动解析：

```text
输入 ServerArgs
   ▼
声明 resolution
   ▼
publish 投影
```

运行时 override：

```text
已经发布的 bags
   ▼
RuntimeContext.override
   ▼
直接更新有效配置叶子 + 记录来源
```

`RuntimeContext.override` 约在 `runtime_context.py:1112`：

```python
def override(self, source: str, **fields):
    if not fields:
        return
    ...
    targets = []
    for name, value in fields.items():
        path = nsmap.get(name)
        if path is None:
            raise ValueError(...)
        ...
        targets.append((bag, name, value))

    for bag, name, value in targets:
        bag._set(name, value)
    self._overrides_log.append((source, dict(fields)))
```

它先解析并验证所有目标，再进行任何写入，因此未知字段不会导致“改了一半”。

### 11.2 运行时状态的可追踪性

`resolved_server_args_dict` 会先获取解析后的配置，再叠加这个进程发生的 runtime overrides：

```python
d = self.server_args.resolved_dict()
for _source, fields in self._overrides_log:
    d.update(fields)
```

所以 `/server_info` 或内部状态接口可以展示当前进程有效配置，而不是只展示启动时的静态输入。

典型场景包括：

- HiCache attach/detach；
- forward-pass metrics endpoint；
- `/set_internal_state` 调整的运行时 tunable；
- model reload 时 scheduler 进程自己的 `model_path` 或 `load_format`。

## 12. 配置怎样跨进程：pickle 不只传字段

### 12.1 为什么只 pickle Struct 字段不够

SGLang 的启动过程会把配置交给子进程。如果只序列化结构体字段，会丢失：

```text
_raw_input
_resolved_overrides
_resolution_finished
_resolution_failed
_model_config
_launch_command
```

一旦子进程只拿到公开字段，它可能重新解析、重新推导，或无法知道父进程已经做过哪些模型和平台决定。

### 12.2 `ServerArgs.__reduce__`

源文件：`server_args.py:481-494`。

```python
def __reduce__(self):
    return (
        _rebuild_server_args,
        (
            type(self),
            msgspec.structs.asdict(self),
            dict(self.__dict__),
        ),
    )
```

重建函数：

```python
def _rebuild_server_args(cls, fields, bookkeeping):
    record = cls(**fields)
    record.__dict__.update(bookkeeping)
    return record
```

顺序也有意义：

1. 先通过构造器恢复字段；
2. 再恢复 bookkeeping；
3. 于是 `_resolution_finished`、declaration stash 等状态被重新装回。

子进程的 publish 入口还会调用 `resolve_once`，但如果 `_resolution_finished` 已经随 pickle 传来，调用会直接返回，然后从已有 declaration 投影 bags，而不会重复解析。

可以把跨进程流程画成：

```text
父进程：raw fields + declarations + finished
                   │ pickle
                   ▼
子进程：恢复同一份解析结果
                   │ publish
                   ▼
本进程自己的 config bags
```

注意：bags 本身通常不是跨进程共享的同一个 Python 对象；跨进程传递的是可重建的配置记录，子进程在本地建立自己的运行时视图。

## 13. 从一个真实配置例子串起所有阶段

现在用一个稍复杂的命令：

```bash
sglang serve \
  --model-path deepseek-model \
  --tp-size 4 \
  --max-running-requests 256 \
  --cuda-graph-backend-decode piecewise \
  --chunked-prefill-size 4096 \
  --speculative-algorithm EAGLE
```

### 第一步：CLI 解析

```text
argv
  ▼
argparse
  ▼
ServerArgs
```

record 中保存：

```text
model_path = "deepseek-model"
tp_size = 4
max_running_requests = 256
cuda_graph_backend_decode = "piecewise"
chunked_prefill_size = 4096
speculative_algorithm = "EAGLE"
```

### 第二步：raw snapshot

进入 pipeline 后：

```python
_raw_input = {
    "model_path": "deepseek-model",
    "tp_size": 4,
    "max_running_requests": 256,
    ...,
}
```

### 第三步：模型和平台解析

模型配置被加载后，某个模型 override 可能声明：

```python
("DeepSeek_override", {
    "attention_backend": "flashinfer_mla",
    "kv_cache_dtype": "fp8_e4m3",
})
```

平台阶段可能根据 GPU 能力和用户显式输入声明：

```python
("platform_defaults", {
    "dtype": "bfloat16",
})
```

### 第四步：memory 与 CUDA Graph

用户显式写了 chunk size 和 decode graph backend，相关 handler 会验证组合并计算 memory budget：

```text
chunked_prefill_size = 4096
max_running_requests = 256
CUDA Graph decode backend = piecewise
```

如果某个模型默认只支持较小 chunk，模型特定阶段可能在“用户未显式指定”的前提下声明另一个值；如果用户显式指定过，则该阶段应尊重输入或报出不兼容错误，而不是无声覆盖。

### 第五步：speculative decoding

spec hook 根据算法名称、draft model 和 token 数量决定：

```python
("speculative_hook", {
    "speculative_num_draft_tokens": 5,
    "enable_mtp": False,
})
```

### 第六步：发布

最终 projection 可能是：

```text
get_parallel().tp_size                  == 4
get_memory().chunked_prefill_size       == 4096
get_exec().kernel.attention_backend     == "flashinfer_mla"
get_spec().speculative_num_draft_tokens == 5
get_schedule().max_running_requests     == 256
```

Scheduler 和 worker 进程读取的是这些 namespace bag。HTTP 层如果需要展示用户原始命令，则读取 `get_server_args().launch_command` 或 raw record，而不是把两种语义混在一起。

## 14. 几个容易误解的地方

### 14.1 “默认值”只有一种吗？

不是。至少要区分：

```text
字段声明默认值
    argparse / msgspec 构造时使用

模型默认值
    由模型 architecture 或 HF config 推导

平台默认值
    由 CUDA/AMD/CPU/HPU/NPU 等运行环境推导

功能默认值
    由 CUDA Graph、KV cache、speculative decoding 等阶段推导

运行时 override
    服务已经启动后由控制接口改变
```

它们最终可能都表现为一个字段值，但来源和时机不同。

### 14.2 “最后声明覆盖”是否意味着用户参数会被覆盖？

不是简单地这样判断。解析器必须区分：

- 用户明确指定了某个值；
- 用户没有指定，字段只带了静态默认；
- 某个后处理阶段需要根据硬件强制修正；
- 一个值与另一个显式选择不兼容，此时应报错。

具体 hook 会根据字段的 explicit-input 记录和业务规则决定是尊重、声明覆盖还是抛错。last-writer-wins 描述的是 declaration stash 的机械读取规则，不代替每个 handler 的语义判断。

### 14.3 `resolving_view` 是最终配置吗？

在 pipeline 中，它是“截至当前阶段的有效配置”。后面仍可能追加 declaration，所以它是 live view。

发布之后，真正稳定且适合业务代码读取的是 runtime bags。发布时会把当时的 `resolution_result` 投影进去；之后的变化必须明确走 `RuntimeContext.override`。

### 14.4 为什么某些代码还直接用 `server_args`？

有些代码处在：

- 构造和解析阶段；
- 需要保留 raw input 的调试路径；
- 兼容旧接口的边界；
- 尚未迁移的特定 manager 对象。

但一般业务读取应逐渐使用对应 bag。项目明确把“operator input”和“effective runtime config”分为两个问题，避免通过名称相同而产生语义误读。

### 14.5 为什么不把 bags 直接做成普通 dict？

`_ConfigBag` 选择属性访问而不是每次 `bag["field"]`，主要原因包括：

- 与现有 `get_memory().page_size` 等调用习惯一致；
- namespace 层次能直接表达 `exec.moe`；
- 真实属性在 `__dict__` 中，便于编译/追踪路径；
- 统一的只读 guard 和 override 路由；
- 发布时可以检测 namespace collision 和缺失字段。

## 15. 如何阅读这套配置源码

推荐顺序：

### 第一步：看字段是什么

```text
python/sglang/srt/arg_groups/fields/
```

先找目标参数属于哪个 namespace，确认类型、默认值、CLI alias 和 `resolvable` 元数据。

### 第二步：看 CLI 组装

```text
python/sglang/srt/server_args.py:add_cli_args
python/sglang/srt/server_args.py:from_cli_args
python/sglang/srt/server_args.py:prepare_server_args
```

确认参数是自动生成、动态 choices、配置文件元参数还是 deprecated compatibility。

### 第三步：看 pipeline 顺序

```text
python/sglang/srt/arg_groups/pipeline.py:run_resolution_pipeline
```

先不要急着读每个 hook 的几百行实现，先回答：它在模型路径前、memory 前、attention 后还是 speculative 后？

### 第四步：看声明和 precedence

```text
python/sglang/srt/arg_groups/overrides.py:
    declare_resolution
    resolution_result
    resolving_view
    resolved_view
```

确认某个值是如何被声明、后续代码怎样读取、最终谁覆盖了谁。

### 第五步：看 publish

```text
python/sglang/srt/runtime_context.py:
    publish
    RuntimeContext.set_server_args
    _build_config_bags
    _install_derived_leaves
```

这一步回答“解析结果如何进入 Scheduler/worker 的常规业务读取路径”。

### 第六步：看跨进程入口

搜索：

```text
publish(server_args, role="scheduler")
publish(server_args, role="tokenizer")
publish(server_args, role=...)
```

确认每种进程是否先 publish，再构造依赖配置的对象。若构造器在未 publish 时读取 bag，应该尽早失败，而不是得到一个隐含默认值。

## 16. 小结：配置系统的四条主线

### 主线一：输入和决定分离

```text
ServerArgs = 用户输入记录
_declaration stash = 解析决定
```

### 主线二：解析是有顺序的纯组织过程

每个 hook 可以依赖前面已经解析出的值，但通过 view 读取；它不应该破坏原始 record。pipeline 负责把这些依赖顺序显式写出来。

### 主线三：发布是进程边界

```text
resolve_once
    ▼
publish
    ▼
config namespace bags
    ▼
Tokenizer / Scheduler / Worker
```

每个 OS 进程有自己的 context 和 bags，但可以从跨进程传来的已解析 record 重建相同的有效配置。

### 主线四：所有后续修改都必须有语义

- 启动阶段的推导：`declare_resolution`；
- 发布后的永久运行时改变：`get_context().override`；
- 测试的临时改变：bag 的 scoped `override`；
- raw input：只用于观察、诊断和复现，不作为业务配置的隐式写入目标。

把这四条主线记住后，再看下一章的模型加载、并行初始化和 attention backend，就能一直追问：

> 这个模块读的是哪一层配置？这个值来自用户、模型、平台还是 runtime override？这个决定发生在什么阶段？

这正是从“会使用 SGLang”走向“能读懂 SGLang 源码”的关键。
