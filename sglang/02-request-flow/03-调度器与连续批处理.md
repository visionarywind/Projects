上一篇文章追踪了请求从 HTTP 到 Scheduler 的过程。请求进入 `waiting_queue` 以后，并不会立刻执行模型。本篇回答三个核心问题：

1. Scheduler 每一轮怎样决定“现在执行谁”？
2. prefill 和 decode 为什么要区别处理？
3. continuous batching 怎样让新请求和旧请求在不同阶段共同利用 GPU？

先给出最重要的心智模型：

```text
waiting_queue                         running_batch
    │                                      │
    │ ① 按策略排序                         │ 已经在生成的请求
    │ ② 前缀匹配                           │
    │ ③ 检查 KV 空间和 token budget         │
    │ ④ 分配 prompt 所需 cache slots        │
    ▼                                      │
new prefill ScheduleBatch ── forward ──► 请求变成 decode
                                           │
                                           └─ 下一轮继续生成
```

Scheduler 不是一个“一次取一批请求然后等待全部完成”的静态 batcher。它是一个不断重复的控制循环：每轮读取新消息、检查完成请求、决定 prefill 或 decode、准备 batch、启动 forward、处理上轮结果，然后进入下一轮。

## 1. 先用餐厅例子理解动态调度

把 GPU 想成一间昂贵的厨房：

- 等待队列是门外排队的订单；
- `Req` 是一张订单卡，保存一个请求的全部状态；
- prefill 是厨师第一次读取整张订单，把已有材料全部准备好；
- decode 是在已有材料基础上，每次追加一个新菜品步骤；
- KV cache 是已经准备好的半成品；
- `ScheduleBatch` 是这一轮真正放到厨房里的订单集合。

静态 batch 的做法是：等 8 个订单都到齐，一起处理；其中一个订单很长，其他订单也必须等它。

continuous batching 的做法是：

```text
时刻 t0: A、B 到达，开始处理 A/B 的 prompt（prefill）
时刻 t1: A/B 开始 decode；C 新到达，加入下一轮 prefill
时刻 t2: A/B 继续 decode；C 做 prefill
时刻 t3: A 完成，D 可以补进 decode 空间或等待下一次 prefill
```

注意：C 不是把自己“插入正在运行的 CUDA kernel”。它是在当前 forward 完成、下一次调度决策时加入新的 batch。动态性来自“每一轮重新组成 batch”，而不是修改已经发射的 kernel。

## 2. Scheduler 的两个时间维度

理解 Scheduler 需要同时看两种状态。

### 2.1 请求状态

每个 `Req` 可能处于：

```text
刚收到
  ▼
waiting_queue
  ▼
prefill batch
  ▼
running decode batch
  ├─ 生成新 token，继续 decode
  ├─ 被抢占/撤回，回到 waiting_queue
  └─ 完成，释放 cache 并发送结果
```

请求不会永远只在一个队列中。KV cache 不够时，正在 decode 的请求可能被 retract（撤回），释放资源后回到等待队列；chunked prefill 则可能在多个轮次中处理同一个长 prompt。

### 2.2 批次状态

Scheduler 还维护批次级对象：

- `running_batch`：当前仍在持续 decode 的请求集合；
- `last_batch`：上一轮执行的 batch，用于下一轮合并和结果处理；
- `batch_to_run`：这一次真正要送入 worker 的 batch；
- overlap 模式下的 `result_queue`：已经完成 GPU forward、等待 CPU/Scheduler 处理的结果。

`running_batch` 和 `last_batch` 不是同一个概念。`running_batch` 描述“哪些请求仍然活跃”；`last_batch` 描述“上一轮 forward 的具体批次”。上一轮可能是 prefill，也可能是 decode，下一轮需要据此决定怎样合并。

## 3. `dispatch_event_loop`：先选择调度循环变体

源码位置：`python/sglang/srt/managers/scheduler.py:1-4005`。

Scheduler 初始化完成后，`dispatch_event_loop` 根据部署模式选择循环：

```python
def dispatch_event_loop(scheduler):
    if disaggregation_mode == NULL:
        if enable_pdmux:
            scheduler.event_loop_pdmux()
        elif pp_size > 1:
            scheduler.event_loop_pp()
        elif enable_overlap_mlx:
            scheduler.event_loop_overlap_mlx()
        elif enable_overlap:
            scheduler.event_loop_overlap()
        else:
            scheduler.event_loop_normal()
    elif disaggregation_mode == PREFILL:
        ...
    elif disaggregation_mode == DECODE:
        ...
```

对初学者来说，先只看普通非 disaggregation 模式：

- `event_loop_normal`：调度、GPU forward、结果处理在同一条控制流程中串行推进；
- `event_loop_overlap`：当前 GPU forward 运行时，CPU 可以准备下一轮；结果先放进队列，稍后处理。

PP、PD disaggregation、MLX 和 PDMUX 是专门的循环变体，但它们仍然遵循同样的抽象：接收请求，构造 batch，运行 batch，处理 batch 结果。

## 4. 普通循环：每一轮做什么

源码位置：`scheduler.py:1892-1925`。

简化后的 `event_loop_normal` 是：

```python
while True:
    if self.gracefully_exit:
        break

    self.ingest_requests()
    if self._engine_paused:
        self._record_scheduler_state_for_paused_engine()
        continue

    plan = self.get_next_batch_to_run(
        running_batch=self.running_batch,
        last_batch=self.last_batch,
    )
    self.running_batch = plan.running_batch
    batch = plan.batch_to_run

    if batch:
        result = self.run_batch(batch)
        self.process_batch_result(batch, result)
    else:
        self._sched_idled = True
        self.on_idle()

    self.last_batch = batch
```

逐行解释：

### 4.1 `ingest_requests`

这一步从 IPC 通道取出 TokenizerManager 发来的消息，可能包括：

- 新的 `TokenizedGenerateReqInput`；
- batch generate 请求；
- abort；
- pause/continue；
- 权重更新或控制请求。

新生成请求最终会经过 `handle_generate_request`，创建 `Req` 并加入等待队列。Scheduler 先接收请求，再做本轮 batch 决策，因此刚到的请求有机会和已有请求一起参与下一轮。

### 4.2 `get_next_batch_to_run`

这是调度决策中心。它不仅“从队列取前 N 个”，还要处理：

- 上一轮 prefill 完成后的状态合并；
- chunked prefill；
- prefix cache；
- 优先级和调度策略；
- KV cache 可用空间；
- LoRA adapter 是否可用；
- decode batch 是否需要撤回；
- DP attention、speculative decoding、disaggregation 等特殊约束。

返回 `NextBatchPlan`，同时包含：

```text
batch_to_run: 这一次 forward 要执行的 batch
running_batch: 决策后保留下来的运行 batch
```

分开返回这两个对象很重要：一次 prefill 可能加入新请求，但不应该把整个 running decode 状态粗暴覆盖掉。

### 4.3 `run_batch` 和 `process_batch_result`

`run_batch` 负责把 batch 送给 worker/ModelRunner，并取得 forward 结果；`process_batch_result` 负责把 token 写回请求状态、判断是否完成、更新 KV cache、发送输出，并为下一轮准备状态。

Scheduler 自己通常不直接执行每一层 Transformer；它是 GPU 执行的编排者，真正的模型计算在 TP worker 的 `forward_batch_generation` 和 `ModelRunner.forward` 中完成。

## 5. `get_next_batch_to_run` 的第一部分：合并和清理旧 batch

源码位置：`scheduler.py:3499-3644`。

### 5.1 chunked request 不能和普通请求简单混合

长 prompt 可能被切成多个 chunk。`self.chunked_req` 记录当前跨轮处理的请求。

每一轮开始时，代码会把 chunked request 从待合并集合中排除，并在上一 chunk 产生了新 KV 时调用 `stash_chunked_request`。这样做的本质是：

```text
长 prompt: [chunk 1][chunk 2][chunk 3]

第 1 轮：计算 chunk 1，保存已产生 KV
第 2 轮：恢复同一个请求，计算 chunk 2
第 3 轮：恢复同一个请求，计算 chunk 3
```

如果把它当成三个独立请求，就会丢失 prompt 进度和 cache 归属；如果一次性处理，又可能让一个超长 prompt 独占整个 batch。

### 5.2 把上一轮 prefill 结果并入 running batch

```python
if last_batch and last_batch.forward_mode.is_extend():
    last_batch.filter_batch(...)
    if not last_batch.is_empty():
        if running_batch.is_empty():
            running_batch = last_batch
        else:
            running_batch.merge_batch(last_batch)
```

`extend` 是 SGLang 中覆盖 prefill/扩展上下文的一类 forward mode。上一轮 prefill 结束后，仍然活跃的请求需要被纳入后续运行状态；已经完成或被排除的请求必须过滤掉。

这段代码表达了 continuous batching 的关键：**prefill batch 的请求在完成 prompt 处理后，不会消失，而是转入持续运行的 decode 集合。**

### 5.3 为什么 prefill 和 decode 有优先顺序

后续代码先尝试：

```python
prefill_plan = self.get_new_batch_prefill(running_batch)
new_batch = prefill_plan.batch_to_run
```

如果拿到了新 prefill batch，就优先运行它；否则：

```python
if not running_batch.is_empty() and not running_batch.is_prefill_only:
    running_batch = self.update_running_batch(running_batch)
    ret = running_batch if not running_batch.is_empty() else None
```

也就是：

```text
有合适的新 prompt -> 做 prefill
否则             -> 做已有请求的 decode
```

这是一个调度策略，不是 Transformer 的硬性要求。系统可以根据 token budget、TTFT/吞吐目标和配置在两者之间调节，但无论策略怎样，prefill 和 decode 的资源模型不同：prefill 一次处理很多 token，decode 通常每个请求只追加一个 token。

## 6. 调度策略：不是简单 FCFS

源码位置：`python/sglang/srt/managers/schedule_policy.py:222-301`，以及 `scheduler.py:3749-3754`。

在构造 prefill batch 之前，Scheduler 调用：

```python
self.policy.calc_priority(
    self.waiting_queue,
    running_batch,
    processed_tokens=self.processed_tokens_counter,
)
```

可用策略包括：

```text
Cache-aware:
  LPM        longest prefix match，最长前缀优先
  DFS_WEIGHT 深度优先权重
  HRRN       基于等待和已处理 token 的响应比

Cache-agnostic:
  FCFS       先到先服务
  LOF        longest output first
  RANDOM     随机
  ROUTING_KEY 按运行 batch 中 routing key 的频率
```

### 6.1 为什么最长前缀优先有价值

假设等待队列有：

```text
A: [system, policy, user, "weather"]  命中 1000 token
B: [another, unrelated, prompt]       命中 0 token
```

如果当前 GPU cache 可以容纳 A，优先 A 就能复用更多已有 KV，减少 prefill 计算和 cache 分配。这里的排序不是为了改变模型语义，而是为了让已有 cache 更有效。

`match_prefix_for_req` 会用：

```python
req.origin_input_ids + req.output_ids
```

作为匹配 key，并把匹配结果写到 `req.prefix_indices`、`req.last_node`、`req.host_hit_length` 等字段。前面 KV cache 文章已经解释过 Radix tree；在这里它成为调度排序的输入。

### 6.2 队列很大时为什么关闭昂贵匹配

`SchedulePolicy._determine_active_policy` 在等待队列超过 128 个请求时，会把 LPM/HRRN 暂时降为 FCFS。原因很实际：对每个等待请求做完整前缀匹配和排序，可能让 CPU 调度成本本身变成瓶颈。

这是一个典型的系统工程折中：少量请求时用 cache-aware 策略提高 GPU 利用率；队列很大时优先保证调度延迟和可预测性。

### 6.3 优先级调度和公平性

`processed_tokens_counter` 会累计 prefill token 数，供 HRRN 等策略计算等待老化。否则一个短请求或高 cache-hit 请求可能一直插队，导致长时间等待的请求饥饿。

如果启用 priority scheduling，优先级还会参与排序、队列满时的淘汰和 KV 紧张时的抢占。优先级是调度输入，不是 sampling priority；它不会改变模型输出概率。

## 7. `PrefillAdder`：决定哪些 waiting request 能进入 batch

源码位置：`scheduler.py:3666-4025`，重点是 `3778-3951`。

`get_new_batch_prefill` 创建 `PrefillAdder`：

```python
adder = PrefillAdder(
    self.page_size,
    self.tree_cache,
    self.token_to_kv_pool_allocator,
    running_batch,
    self.new_token_ratio_tracker.current,
    self.max_prefill_tokens,
    chunked_prefill_size,
    running_bs if self.is_mixed_chunk else 0,
    self.priority_scheduling_preemption_threshold,
    max_prefill_bs=int(self.max_prefill_bs),
    max_running_requests=self.max_running_requests,
    prefill_max_requests=get_schedule().prefill_max_requests,
    ...
)
```

可以把它看成一个“入场检查器”。它同时考虑：

- 最多允许多少个请求；
- 本轮最多处理多少 prompt token；
- KV pool 还有多少 slot；
- running decode 请求已经占用了多少容量；
- chunked prefill 的大小；
- LoRA 数量和加载能力；
- beam search 需要的额外 request rows；
- preemption/retraction 是否可以释放空间。

### 7.1 running request budget

`get_num_allocatable_reqs` 的核心计算是：

```python
pp_budget = pp_max_micro_batch_size - running_bs
available = req_to_token_pool.available_size()
res = min(pp_budget, available)
```

含义是：可加入的新请求数同时受两种资源约束：

1. PP/调度配置允许的 micro batch 上限；
2. request-to-token pool 还能提供多少 request 行。

beam width 大于 1 时，一个逻辑请求可能需要多个行，因此代码还会用 `available // beam_width` 限制结果。

### 7.2 token budget

`PrefillAdder` 不只看请求数量，还看 prompt token 数。假设：

```text
max_prefill_tokens = 4096
等待请求 A = 3000 tokens
等待请求 B = 2000 tokens
```

即使 request 数量仍有空间，也不能同时把 A+B 放进本轮，因为 5000 超过 token budget。结果可能是本轮运行 A，下轮运行 B。

这正是 chunked prefill 和 mixed chunk 的基础：超长输入可以拆分，避免一个请求让其他请求长时间得不到 GPU 时间。

### 7.3 前缀匹配和资源分配

对每个候选请求，代码先调用：

```python
req.init_next_round_input(self.tree_cache)
res = adder.add_one_req(
    req,
    has_chunked_req=self.chunked_req is not None,
    truncation_align_size=self.truncation_align_size,
)
```

`init_next_round_input` 会根据 Radix cache 命中情况计算本轮真正需要扩展的范围；`add_one_req` 再尝试为这些新 token 分配 KV 位置。

因此“prompt 有 4096 token”不一定意味着本轮要计算 4096 token：如果前缀 cache 命中 3000，本轮可能只需扩展剩余 1096 token。

### 7.4 `AddReqResult` 为什么会停止遍历

如果 `add_one_req` 返回 `CONTINUE`，继续尝试下一个等待请求；如果返回 `NO_TOKEN` 或其他非 continue 结果，通常意味着当前资源预算不足。

代码会设置 `batch_is_full`，必要时尝试 `preempt_to_schedule(req)`。如果不能通过抢占腾出空间，就停止继续从队列取请求。

这种“遇到第一个不能调度的请求就谨慎停止”的行为还和优先级、公平性有关：如果排序后的高优先级请求都无法放入，盲目跳过并选择更后面的请求可能破坏调度语义。

## 8. 由请求集合创建 `ScheduleBatch`

当 `adder.can_run_list` 非空时，Scheduler 会把已经选中的请求从 waiting queue 移除：

```python
can_run_list = adder.can_run_list
can_run_set = set(can_run_list)
self.waiting_queue = [
    x for x in self.waiting_queue if x not in can_run_set
]
```

随后创建 batch：

```python
new_batch = ScheduleBatch.init_new(
    can_run_list,
    self.req_to_token_pool,
    self.token_to_kv_pool_allocator,
    self.tree_cache,
    self.model_config,
    self.enable_overlap,
    self.spec_algorithm,
    chunked_req=self.chunked_req,
)
new_batch.prepare_for_extend()
```

### 8.1 `ScheduleBatch` 是什么

源码位置：`python/sglang/srt/managers/schedule_batch.py:2185`。

它保存本轮 scheduler 和 worker 共享的 batch 元数据，例如：

```python
reqs: List[Req]
req_to_token_pool
 token_to_kv_pool_allocator
tree_cache
input_ids
req_pool_indices
seq_lens
out_cache_loc
forward_mode
return_logprob
has_grammar
seq_lens_sum
extend_num_tokens
```

可以这样区分：

- `Req`：单个请求的长期状态；
- `ScheduleBatch`：多个请求在同一轮 forward 中的打包状态；
- `ForwardBatch`：更靠近 ModelRunner 的设备执行表示，通常从 ScheduleBatch 派生。

### 8.2 `init_new` 的批次级推导

`ScheduleBatch.init_new` 会根据请求集合计算：

```python
return_logprob = any(req.return_logprob for req in reqs)
has_grammar = any(req.grammar for req in reqs)
return_hidden_states = get_batch_return_hidden_states_mode(reqs)
is_prefill_only = all(req.is_prefill_only for req in reqs)
```

这说明 batch 中只要有一个请求需要 logprob，batch 就要携带相应能力；只要有一个请求需要 grammar，就需要对应的 grammar metadata。批次属性是请求属性的聚合结果。

### 8.3 `prepare_for_extend`

prefill/extend 准备阶段通常会构造：

- 每个请求的 prefix length；
- 本轮要扩展的 token 数；
- flatten 后的 `input_ids`；
- 每个新 token 对应的 `out_cache_loc`；
- request pool indices；
- device 上的 sequence lengths。

例如两个请求：

```text
A: cache 命中 4，新增 3 token
B: cache 命中 2，新增 2 token
```

模型输入可以展平为 5 个本轮需要计算的 token，同时 batch metadata 仍保存 A/B 各自的边界：

```text
input_ids       = [A_new1, A_new2, A_new3, B_new1, B_new2]
extend_lens     = [3, 2]
prefix_lens     = [4, 2]
```

attention backend 依靠这些边界知道每个 query 应该读取哪个请求的历史 KV。

## 9. decode batch：每个活跃请求追加一步

如果本轮没有可运行的 prefill，Scheduler 调用：

```python
running_batch = self.update_running_batch(running_batch)
```

源码位置：`scheduler.py:4055-4137`。

### 9.1 先过滤已完成请求

```python
initial_bs = batch.batch_size()
batch.filter_batch()
if batch.is_empty():
    batch.batch_is_full = False
    return batch
```

已达到 EOS、stop string、max tokens 或 abort 状态的请求必须从下一轮 decode 中移除。否则它会继续占用 request row、KV slot 和 GPU batch 位置。

### 9.2 decode OOM 和 retract

代码检查：

```python
if not batch.check_decode_mem():
    retracted_reqs, new_token_ratio, reqs_to_abort = batch.retract_decode()
```

decode 每前进一步，通常要为每个活跃请求增加一个 KV slot。长期运行后，KV pool 可能没有足够空间。`retract_decode` 会撤回部分请求：

1. 释放其当前占用的 decode 资源；
2. 更新 token ratio 等调度估计；
3. 必要时为无法继续的请求发送 abort；
4. 将可恢复请求重新放入 waiting queue：

```python
for req in retracted_reqs:
    self._add_request_to_queue(req, is_retracted=True)
```

这不是删除请求，而是让它们稍后在资源足够时继续。retraction 是 continuous batching 在有限 KV 内存下保持服务可用的重要机制。

### 9.3 `prepare_for_decode`

没有需要 retract 的请求后，调用：

```python
batch.prepare_for_decode()
```

源码位置：`schedule_batch.py:3343-3435`。核心操作包括：

```python
self.forward_mode = ForwardMode.DECODE
self.out_cache_loc = alloc_for_decode(self, token_per_req=1)
self.seq_lens = self.seq_lens + 1
self.seq_lens_cpu = self.seq_lens_cpu + 1
self.orig_seq_lens = self.orig_seq_lens + 1
self.seq_lens_sum = None
```

直观地说：

- 当前 batch 进入 decode 模式；
- 每个请求分配一个新的 KV 写入位置；
- 所有请求的序列长度增加 1；
- 下一次 forward 需要重新计算序列长度总和。

在 overlap 调度下，这些 tensor 字段不能随便原地改写，因为上一个 forward 可能仍在读取旧对象。当前实现通过创建新 tensor 并重新绑定字段，并用 batch snapshot 保持跨 stream 生命周期。这是一个很值得关注的并发正确性约束。

## 10. prefill 和 decode 的具体差异

| 维度 | Prefill / Extend | Decode |
|---|---|---|
| 输入 | prompt 中尚未缓存的一段或多段 token | 每个请求最近生成的 token |
| 每请求 token 数 | 可以很多 | 通常 1（speculation 可能更多） |
| 主要目标 | 批量建立 KV cache | 反复追加 KV 并采样 |
| 计算形态 | 更像大矩阵计算，吞吐高 | batch 中每请求少量 token，延迟敏感 |
| cache 操作 | 查 prefix、分配一段新位置 | 每请求分配下一个位置 |
| 结束后 | 活跃请求转入 decode | 继续 decode 或 finished |

假设请求 A 的 prompt 有 1000 token，B 已经生成到第 20 步，C 刚刚到达：

```text
第 N 轮：A prefill 1000 token，B 可能暂不 decode，C 等待
第 N+1：A decode 1，B decode 1，C prefill 300 token
第 N+2：A decode 1，B 已结束，C decode 1
```

是否在同一轮混合 A/B/C，取决于 `is_mixed_chunk`、logprob、beam、speculative 和 backend 支持。即使不能混合，continuous batching 仍然可以在相邻轮次交替推进它们。

## 11. mixed chunk：同一轮合并 prefill 和 decode

在满足条件时，`_get_new_batch_prefill_raw` 会：

```python
running_batch.filter_batch()
running_batch.prepare_for_decode()
new_batch.mix_with_running(running_batch)
new_batch.decoding_reqs = running_batch.reqs
```

这表示新 prefill batch 可以把已有 decode 请求的行一起带入一次 forward。这样做的好处是减少 kernel launch 和调度间隙；代价是输入布局、logprob、beam、speculation 和 attention metadata 更复杂。

代码明确限制了某些情况，例如：

- return_logprob 时暂不支持这种混合；
- input embeds 存在时，不能简单拼接 input ids；
- beam member rows 不放入 mixed extend batch。

这里体现了一个通用原则：**batch 合并不是免费操作，只有当所有请求的输入布局和结果语义可兼容时才合并。**

## 12. overlap 调度：CPU 不必等待上一轮结果处理

源码位置：`scheduler.py:1927-2000`。

简化后的 overlap 循环：

```python
self.result_queue = deque()

while True:
    self.ingest_requests()
    plan = self.get_next_batch_to_run(...)
    self.running_batch = plan.running_batch
    batch = plan.batch_to_run

    disable_overlap = self.is_disable_overlap_for_batch(
        batch, last_batch=self.last_batch
    )
    if disable_overlap:
        pop_and_process()

    if batch:
        batch_result = self.run_batch(batch)
        self._apply_war_barrier()
        self.result_queue.append((batch.copy(), batch_result))

    if self.last_batch and not disable_overlap:
        pop_and_process()

    if self.is_generation:
        self.launch_batch_sample_if_needed(batch_result, batch)

    self.last_batch = batch
```

### 12.1 为什么结果要保存 `batch.copy()`

`run_batch` 返回的 GPU tensor 结果和 batch metadata 可能在后续调度迭代仍被需要。overlap 模式下，Scheduler 可能马上构造下一轮 batch；如果直接复用并修改同一个 batch 对象，结果处理会读到已经被下一轮改变的字段。

因此代码把 batch 和结果放入 `result_queue`，并保存一个 batch snapshot。这里的 copy 不只是 Python 容器复制，而是为了维持 forward 所需的字段和 tensor 引用在正确的时间窗口内有效。

### 12.2 什么时候必须关闭 overlap

`is_disable_overlap_for_batch` 会在一些条件下强制同步，例如：

- 连续 prefill overlap 可能不利于第一个 batch 的 TTFT；
- grammar 状态必须先由上一轮结果推进，再生成下一轮 mask；
- 某些 speculative decoding 路径需要结果顺序；
- 分布式 collective 需要所有 rank 做一致决策。

因此 overlap 是优化，不是永远成立的语义。遇到需要严格先后关系的阶段，代码会先 `pop_and_process()`，再启动下一轮。

### 12.3 overlap 的正确性重点

当前 Scheduler 使用 snapshot、forward-only sampling info、stream/event barrier 等机制，处理：

- schedule stream 和 forward stream 的先后关系；
- 上一个 forward 仍在读取的 tensor 不被提前释放；
- speculative/grammar 结果与下一轮输入的依赖；
- unified memory allocator 的读写冲突。

阅读这部分时，不要只看“是否快”。它首先要保证“下一轮写入不会覆盖上一轮还在读的对象”，然后才谈吞吐提升。

## 13. 一次完整的 continuous batching 例子

假设系统配置：

```text
max_prefill_tokens = 6
max_running_requests = 3
KV pool 还有 8 个 token slot
```

三个请求：

```text
A: prompt 4 token，预计输出 3 token
B: prompt 3 token，预计输出 2 token
C: prompt 2 token，稍后到达
```

### t0：A、B 在等待

```text
waiting_queue = [A, B]
running_batch = []
```

策略计算 prefix hit 和优先级；`PrefillAdder` 发现 A+B 是 7 token，超过 6，于是只加入 A：

```text
batch_to_run = prefill(A, 4)
waiting_queue = [B]
running_batch = []
```

### t1：A 完成 prefill，开始 decode

A 的 prompt KV 已建立，A 进入 `running_batch`。本轮可以为 A 分配一个 decode slot：

```text
running_batch = [A]
batch_to_run = decode(A, 1)
```

如果 C 在此时到达，`ingest_requests` 会把 C 加入等待队列，但不会改变已经发射的 `decode(A)`。

### t2：A decode，同时 B/C 竞争 prefill

```text
waiting_queue = [B, C]
running_batch = [A]
```

调度器重新计算。假设 token budget 允许 B 的 3 token，但 B+C 共 5 token 也允许，那么它可以选择：

```text
batch_to_run = prefill(B, 3) + prefill(C, 2)
running_batch = [A]
```

如果 mixed chunk 条件满足，A 也可能被合并进同一个 forward；否则 A 在相邻轮次继续 decode。

### t3：B、C 转入 decode

上一轮 prefill 结果被并入运行状态：

```text
running_batch = [A, B, C]
batch_to_run = decode(A, B, C)
```

此时一个 GPU batch 中有三个不同生命周期的请求。A 已经生成几步，B/C 刚完成 prompt；它们通过各自的 `seq_lens`、`prefix_lens` 和 cache locations 保持独立。

### t4：A 完成

`filter_batch` 删除 A，释放其不再需要的资源；下一轮只对 B/C decode：

```text
running_batch = [B, C]
batch_to_run = decode(B, C)
```

这就是 continuous batching 的核心收益：GPU 不必因为 A 完成而等待下一批固定大小的请求，也不必让 B/C 等 A、B、C 全部同时完成。

## 14. 从输出到下一轮：`process_batch_result` 的概念位置

虽然模型执行和结果字段会在下一篇详细分析，但调度闭环必须先知道它做了什么：

```text
run_batch(batch)
  ▼
ModelRunner / sampling
  ▼
GenerationBatchResult
  ▼
process_batch_result
  ├─ 把 sampled token 写入 Req.output_ids
  ├─ 更新 sequence length 和 KV bookkeeping
  ├─ 检查 EOS / stop / max_new_tokens / grammar
  ├─ 已完成 -> 发送 BatchStrOutput / BatchTokenIDOutput
  └─ 未完成 -> 保留在 running_batch
```

如果请求完成，Scheduler 不会在下一轮继续把它放进 decode；如果未完成，下一轮 `update_running_batch` 会重新准备 decode 输入。

这也是为什么调度器必须知道 sampling 和 stopping 的结果：它虽然不做 Transformer 层计算，但必须根据模型输出决定请求的生命周期。

## 15. 队列满、抢占和 abort

### 15.1 等待队列满

`_abort_on_queued_limit` 位于 `scheduler.py:3207-3251`。当 `max_queued_requests` 设置且队列已满时，默认拒绝新请求，并通过 tokenizer IPC 返回 service unavailable。

启用 priority scheduling 时，如果新请求优先级严格更高，可以选择淘汰等待队列中较不优先的已有请求：

```text
队列满
  ├─ 新请求优先级不够高 -> 拒绝新请求
  └─ 新请求更高优先级   -> abort 一个旧等待请求，接纳新请求
```

这和 KV retract 不同：队列满发生在请求尚未执行时；decode retract 发生在请求已经占用运行资源时。

### 15.2 客户端 abort

TokenizerManager 发送 `AbortReq` 后，Scheduler 会：

- 从 waiting queue 删除尚未开始的请求；
- 通知 TokenizerManager 清理对应 state；
- 对 disaggregation 模式释放 metadata/KV 资源；
- 对运行中的请求设置待完成状态，并在安全边界处理。

代码不会在任意 CUDA forward 中途直接删除 `Req`，而是通过 `to_finish` 等状态让事件循环在一致的阶段完成清理。

### 15.3 retract 和重新排队

decode OOM 时，可恢复请求重新进入 waiting queue，并带 `is_retracted=True`。再次调度时，它可以重新做 prefix match；已经存在的 cache 仍可能被复用。这个过程使有限显存能服务更多长生命周期请求，但会增加重新调度和潜在 prefill 成本。

## 小结

本篇最重要的结论是：

1. Scheduler 是每一轮重新做决定的动态控制循环，而不是一次性静态 batcher；
2. `waiting_queue` 中的请求经过调度策略、prefix match、token budget 和 KV admission 后，才进入 `ScheduleBatch`；
3. prefill 建立 prompt 的 KV，decode 为活跃请求逐步追加 token；
4. `running_batch` 保存仍活跃的请求，`last_batch` 保存上一轮 forward 的批次，二者共同形成 continuous batching 的状态机；
5. KV 紧张时可以 retract 并重新排队，队列满时可以拒绝或按优先级淘汰；
6. overlap 通过结果队列、snapshot 和 stream barrier 把 CPU 调度与 GPU forward 重叠，但在 grammar、speculation 或 collective 需要时会回到同步边界。

从请求视角看，当前完整链路已经是：

```text
HTTP
  -> TokenizerManager
  -> Req
  -> waiting_queue
  -> prefix-aware admission
  -> ScheduleBatch
  -> prefill/decode decision
  -> run_batch
```

下一步的 `ModelRunner` 文章将解释最后一段：`ScheduleBatch` 如何携带设备上的输入、位置和 KV 地址进入模型执行，以及一个采样 token 怎样驱动下一轮调度。
