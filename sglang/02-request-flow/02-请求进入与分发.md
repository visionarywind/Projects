# 02 请求进入与分发：从 HTTP JSON 到 Scheduler 的 `Req`

上一篇文章说明了服务怎样启动。本篇只关注一件事：**客户端已经发出一个生成请求以后，它怎样穿过 HTTP 层、TokenizerManager 和进程间通信，最后变成 Scheduler 能够调度的请求对象？**

这一步还没有执行 Transformer。它主要做三类工作：

1. 把网络协议中的 JSON 转成内部请求对象；
2. 把文本、聊天模板、多模态输入转换成模型需要的 token ids 和附加数据；
3. 把一个完整、可序列化的请求发送给 Scheduler，并等待 Scheduler 通过另一条通道返回结果。

可以先记住下面这条链路：

```text
HTTP POST /generate
        │
        ▼
FastAPI 生成 handler
        │ GenerateReqInput
        ▼
TokenizerManager.generate_request
        │ normalize / 校验 / 创建 ReqState
        ▼
_tokenize_one_request
        │ text -> input_ids
        │ image/audio -> MultimodalInputs（可选）
        ▼
_create_tokenized_object
        │ TokenizedGenerateReqInput
        ▼
_send_one_request
        │ ZMQ PUSH
        ▼
Scheduler.handle_generate_request
        │
        ▼
Req + waiting_queue
```

这里有一个容易混淆的地方：HTTP 层看到的是 `GenerateReqInput`，TokenizerManager 中间产生的是 `TokenizedGenerateReqInput`，Scheduler 内部长期保存的是 `Req`。它们不是三个重复的类，而是同一个请求在不同边界上的三种表示。

---

## 1. 先用一个最小例子建立直觉

假设客户端发送：

```bash
curl http://127.0.0.1:30000/generate \\
  -H 'Content-Type: application/json' \\
  -d '{
    "text": "Explain KV cache in one sentence.",
    "sampling_params": {
      "temperature": 0,
      "max_new_tokens": 32
    },
    "stream": false
  }'
```

从用户角度，这是一个 JSON；从运行时角度，它会逐步变成：

```text
{
  text: "Explain KV cache in one sentence.",
  sampling_params: {...},
  stream: false
}
        │ FastAPI/Pydantic 或 msgspec 输入模型
        ▼
GenerateReqInput(
    text="Explain KV cache in one sentence.",
    input_ids=None,
    sampling_params={...},
    rid="自动生成的请求 ID"
)
        │ tokenizer
        ▼
TokenizedGenerateReqInput(
    input_text="Explain KV cache in one sentence.",
    input_ids=array("q", [若干 token id]),
    sampling_params=SamplingParams(...),
    stream=False,
    rid="同一个请求 ID"
)
        │ ZMQ 发给 scheduler
        ▼
Req(
    rid="同一个请求 ID",
    origin_input_ids=array("q", [...]),
    output_ids=array("q"),
    kv=ReqKvInfo(),
    finished_reason=None
)
```

`GenerateReqInput` 适合表达“用户想要什么”；`TokenizedGenerateReqInput` 适合跨进程传输；`Req` 适合表达“Scheduler 当前怎样管理这个请求”。例如，`Req` 会额外保存：

- 已经生成的 `output_ids`；
- 前缀缓存对应的 `prefix_indices`；
- KV cache 的分配信息 `kv`；
- `finished_reason`、`to_finish` 等结束状态；
- 增量 detokenization 所需的 `read_offset`、`decoded_text`；
- streaming、logprob、LoRA、session、disaggregation 等调度状态。

因此，**tokenize 不是请求处理的终点，而是从“API 对象”到“执行对象”的第一道转换。**

## 2. HTTP handler：协议层只负责接住和返回

源码位置：`python/sglang/srt/entrypoints/http_server.py:906-957`。

核心 handler 可以压缩成下面的伪代码：

```python
@app.api_route("/generate", methods=["POST", "PUT"])
async def generate_request(obj: GenerateReqInput, request: Request):
    if header_overrides_enabled:
        apply_header_overrides(obj, request.headers)

    if obj.stream:
        async def stream_results():
            async for out in tokenizer_manager.generate_request(obj, request):
                yield b"data: " + dumps_json(out) + b"\n\n"
            yield b"data: [DONE]\n\n"

        return StreamingResponse(
            stream_results(),
            media_type="text/event-stream",
            background=tokenizer_manager.create_abort_task(obj),
        )
    else:
        ret = await tokenizer_manager.generate_request(obj, request).__anext__()
        return orjson_response(ret)
```

### 2.1 FastAPI 如何得到 `obj`

handler 的参数写成：

```python
async def generate_request(obj: GenerateReqInput, request: Request):
```

FastAPI 会根据 `GenerateReqInput` 的定义，把 HTTP body 解析成 Python 对象。handler 因而不需要自己调用 `await request.json()`，也不需要自己把字符串字段转换成 sampling 参数。

这里的 `request: Request` 是 Starlette/FastAPI 的请求上下文，主要用于：

- 判断客户端是否断开；
- 读取请求头；
- 在客户端断开后取消上游请求。

`obj` 则是业务数据。两者分工不同：HTTP 连接的生命周期属于 `request`，生成任务的内容属于 `obj`。

### 2.2 请求头覆盖

源码第 913-914 行先检查 `SGLANG_ENABLE_REQUEST_HEADER_OVERRIDES`，开启时调用 `apply_header_overrides(obj, request.headers)`。这意味着某些部署可以通过 HTTP header 覆盖请求对象中的运行参数。

阅读这段代码时要注意：header 覆盖发生在 TokenizerManager 之前，所以后面的 normalize、校验和 tokenization 看到的是覆盖后的最终对象，而不是原始 JSON。

### 2.3 非流式和流式不是两条推理路径

两种模式都会调用同一个：

```python
_global_state.tokenizer_manager.generate_request(obj, request)
```

差别只在于 HTTP 层怎样消费这个异步生成器：

- 非流式：调用一次 `__anext__()`，拿到最终结果后返回 JSON；
- 流式：持续 `async for`，每拿到一个中间结果就包装成 SSE event。

所以 `stream=true` 并不会让 Scheduler 使用另一套模型执行代码。它改变的是结果何时发送给客户端，以及 TokenizerManager 是否要产生中间输出。

### 2.4 SSE 的具体格式

流式返回使用：

```text
Content-Type: text/event-stream

data: {"text":"KV", ...}

data: {"text":" cache", ...}

data: [DONE]
```

源码中的：

```python
yield b"data: " + dumps_json(out) + b"\n\n"
```

把内部 Python 字典编码成 JSON，再加上 SSE 要求的 `data:` 前缀和两个换行。HTTP handler 不负责理解 `meta_info` 的每一个字段；它只负责把 TokenizerManager 交出来的结果转换为传输格式。

## 3. `TokenizerManager.generate_request`：请求入口的总编排器

源码位置：`python/sglang/srt/managers/tokenizer_manager.py:776-845`。

这个函数是 TokenizerManager 侧的主入口。它的结构很像一段流程图：

```python
async def generate_request(obj, request=None):
    self.auto_create_handle_loop()
    obj.normalize_batch_and_arguments()
    self._set_default_priority(obj)
    self._init_req_state(obj, request)

    try:
        log_received_request(...)
        await pause_condition.wait_for(not paused)
        async with model_update_lock.reader_lock:
            await validate_and_resolve_lora(obj)

            if obj.is_single:
                tokenized_obj = await self._tokenize_one_request(obj)
                await self._send_one_request(tokenized_obj)
                async for response in self._wait_one_response(obj, request):
                    yield response
            else:
                async for response in self._handle_batch_request(obj, request, rids):
                    yield response
    except BaseException:
        self._release_req_states_on_failure(rids)
        raise
```

下面逐段理解它。

### 3.1 `auto_create_handle_loop`：先确保有结果接收循环

TokenizerManager 不只是“一个 tokenizer”。它还维护一个异步 handle loop，持续从 detokenizer 或 Scheduler 返回通道接收结果，并把结果放进相应请求的 `ReqState`。

`generate_request` 一开始调用：

```python
self.auto_create_handle_loop()
```

`auto_create_handle_loop` 只在第一次调用时创建任务。它启动 `handle_loop`，后者的核心逻辑是：

```python
while True:
    recv_obj = await async_sock_recv(self.recv_from_detokenizer)
    if isinstance(recv_obj, (BatchStrOutput, BatchEmbeddingOutput, BatchTokenIDOutput)):
        await self._handle_batch_output(recv_obj)
    else:
        self._result_dispatcher(recv_obj)
```

这是一种典型的“请求发送和结果接收分离”设计：当前 HTTP 协程把请求发出去后，不需要自己轮询 socket；后台 handle loop 收到结果，再通过 `rid` 找到等待中的 `ReqState`，唤醒对应请求。

### 3.2 `normalize_batch_and_arguments`：先统一输入形状

一个 API 可能支持：

- 单个字符串；
- `input_ids`；
- 一批字符串；
- 一批 sampling 参数；
- `parallel_sample_num`；
- session 或多模态字段。

如果每个后续函数都处理这些形状，分支会迅速膨胀。因此入口首先调用：

```python
obj.normalize_batch_and_arguments()
```

它的目标是让后续代码可以使用统一的属性，例如 `obj.is_single`、`obj.batch_size` 和 `obj.rid`。对于 batch 请求，`obj[i]` 可以得到一个请求级子对象。

这一步的思想是：**在边界处承担输入复杂性，内部尽量使用稳定的表示。**

### 3.3 默认优先级和严格 thinking 校验

入口随后设置默认优先级：

```python
self._set_default_priority(obj)
```

如果客户端提供了 `max_thinking_tokens`，代码还会检查服务器是否以 `--enable-strict-thinking` 启动。未开启时直接抛出 `ValueError`。这类检查放在调度前，原因是无须让一个注定失败的请求占用 Scheduler 的 request state、队列和 KV 资源。

`routed_dp_rank` 也在这一阶段检查范围：当请求指定了 data-parallel rank 时，TokenizerManager 根据当前 elastic worker 数量判断它是否落在合法区间。

### 3.4 初始化 `ReqState`

```python
self._init_req_state(obj, request)
```

`ReqState` 是 TokenizerManager 侧的等待状态，不是 GPU 上的 `Req`。它通常负责保存：

- 原始 API 对象 `obj`；
- 一个 `asyncio.Event`；
- Scheduler 返回但尚未交给 HTTP 的输出列表；
- 已累计的文本和 output token ids；
- time stats、logprob 累积信息；
- 是否已 dispatch、是否 finished、是否已发送 abort。

可以把它想成快递系统中的“取件单”：Scheduler 只需要知道 `rid`，TokenizerManager 用这个 `rid` 把返回包放回正确的客户端协程。

### 3.5 为什么要在异常路径清理 state

代码的 `except BaseException` 不是多余的：

```python
except BaseException:
    self._release_req_states_on_failure(request_rids)
    raise
```

正常情况下，Scheduler 返回最终结果后，`_handle_batch_output` 会清理对应状态。但如果异常发生在“请求已创建、尚未送到 Scheduler”之间，例如：

- 输入超过 context length；
- tokenizer 失败；
- LoRA 校验失败；
- 多模态输入格式非法；

那么 Scheduler 永远不会返回完成消息。如果不清理，`rid_to_state` 会无限增长。实现因此区分“已经 dispatch 的请求”和“尚未 dispatch 的请求”：前者需要发送 abort 让 Scheduler 清理，后者直接删除本地 state。

## 4. 文本 tokenization：从字符串得到 `input_ids`

### 4.1 三种输入来源

源码 `tokenizer_manager.py:970-1010` 的 `_tokenize_one_request` 首先判断输入优先级：

```python
if obj.input_embeds is not None:
    input_embeds = obj.input_embeds
    input_ids = obj.input_ids
elif obj.input_ids is not None:
    input_ids = obj.input_ids
else:
    input_ids, token_type_ids = await self._tokenize_texts(...)
```

也就是：

1. 用户给了 `input_embeds`：直接使用 embedding，同时要求显式关闭 radix cache；
2. 用户给了 `input_ids`：跳过 tokenizer；
3. 否则：把文本交给 tokenizer。

为什么 `input_embeds` 默认不能和 radix cache 一起使用？Radix cache 需要一个稳定的离散 token 序列作为前缀 key，而任意浮点 embedding 没有同样的 token-key 语义。代码选择提前拒绝，而不是静默得到不可靠的缓存行为。

如果服务器以 `skip_tokenizer_init=True` 启动，却收到纯文本请求，也会立即报错，因为此时没有 tokenizer 可以把文本变成 ids。

### 4.2 `_tokenize_texts` 的输入格式判断

源码 `tokenizer_manager.py:898-968` 把输入分成：

- `SINGLE_STRING`：一个字符串；
- `CROSS_ENCODER_PAIRS`：cross-encoder 的文本对；
- `BATCH_STRINGS`：一批字符串。

单字符串会被包装成长度为 1 的列表，以便统一调用 tokenizer：

```python
if input_format == InputFormat.SINGLE_STRING:
    tokenizer_input = [texts]
```

之后再通过 `_extract_tokenizer_results` 把长度为 1 的结果还原成单条 `List[int]`。这是典型的“内部 batch 化、外部保持 API 形状”的实现。

### 4.3 普通 tokenizer 与异步动态 batch tokenizer

代码根据配置决定两条路径：

```python
use_async_tokenizer = (
    self.async_dynamic_batch_tokenizer is not None
    and input_format == InputFormat.SINGLE_STRING
)
```

如果启用了动态 batch tokenizer，单条文本会调用：

```python
result = await self.async_dynamic_batch_tokenizer.encode(
    tokenizer_input[0], **tokenizer_kwargs
)
```

多个 HTTP 请求可以在 CPU tokenizer 层短暂聚合，减少重复调用和线程开销。

否则使用常规 tokenizer。对于非 fast tokenizer，代码逐条调用 `self.tokenizer.encode(t)`；对于 fast tokenizer 或 cross encoder，则调用 tokenizer 的批量接口并提取 `input_ids`、`token_type_ids`。

这一步只产生 token ids，不会执行模型，也不会分配 GPU KV cache。

### 4.4 chat template 在哪一层发生

OpenAI chat 请求通常先在 HTTP/API 适配层被转换成内部文本或消息表示，随后由请求输入对象携带到 TokenizerManager。具体 chat template 解析依赖模型和配置，但从请求流角度可以这样理解：

```text
messages = [system, user]
        │ chat template
        ▼
一段模型 prompt 文本
        │ tokenizer
        ▼
input_ids
```

Scheduler 不应该再次理解 `messages` 或 chat template；它接收的核心输入已经是 token ids。这样做既降低 GPU 进程的职责，也避免每个 TP rank 重复执行高层协议解析。

### 4.5 输入长度校验

`_tokenize_one_request` 在 tokenization 和多模态处理之后调用：

```python
self._validate_one_request(obj, input_ids)
```

`_validate_one_request` 会计算：

```python
input_token_num = len(input_ids) + self.num_reserved_tokens
```

并检查：

1. prompt 是否超过 `context_len`；
2. `input + max_new_tokens` 是否超过最大上下文；
3. embedding 请求是否真的连接到 embedding 模型；
4. `token_ids_logprob` 是否为合法、且在词表范围内；
5. hidden states、custom logit processor 等功能是否已由服务器启用。

若允许自动截断，代码会截断 input 或降低 `max_new_tokens`；否则抛出错误。注意：这一步在发送到 Scheduler 前进行，因此错误通常可以直接转换成 HTTP 400，而不会让 GPU 进程处理一个非法请求。

## 5. 多模态请求：tokenize 之后还要加工 prompt

多模态请求不能简单理解为“把图片变成一串 token”。通常还需要：

- 图像、音频或视频预处理；
- 计算视觉/音频 encoder 的输入；
- 用 dummy token 扩展语言模型 prompt；
- 保存 image embeddings 与位置映射；
- 某些模型需要 M-RoPE positions。

源码 `_tokenize_one_request` 在得到初始 `input_ids` 后检查：

```python
contains_mm_input = obj.contains_mm_input()
should_run_mm_processor = self.mm_processor is not None and (
    contains_mm_input or is_mossvl
)
```

如果需要处理，就调用 `self.mm_processor.process_mm_data_async(...)`，可能得到 `MultimodalInputs`。它可以覆盖或补充：

```python
if mm_inputs and mm_inputs.input_ids is not None:
    input_ids = mm_inputs.input_ids
if mm_inputs and mm_inputs.token_type_ids is not None:
    token_type_ids = mm_inputs.token_type_ids
```

这解释了一个重要现象：对图片请求来说，TokenizerManager 输出的 token ids 可能不是普通 tokenizer 对原始文本直接编码的结果，而是 multimodal processor 根据模型占位符和图像信息加工后的结果。

随后 Scheduler 侧还会执行模型相关的本地准备，例如把单个 image token 扩展成接收 image embedding 所需的多个 dummy tokens，并计算 M-RoPE。跨进程边界之前和之后各有一部分处理，是因为：

- CPU/网络侧适合做异步预处理和数据传输；
- 每个 TP rank 需要看到一致的请求元数据；
- 某些轻量的模型特定操作必须在 Scheduler 进程内完成。

因此不要把“TokenizerManager 处理多模态”理解成“Scheduler 完全不碰多模态”；正确的理解是：TokenizerManager 负责把外部媒体变成可传输的 multimodal payload，Scheduler 负责把 payload 接入本 rank 的执行布局。

## 6. `_create_tokenized_object`：固定跨进程消息的字段

源码位置：`tokenizer_manager.py:1356-1470`。

完成 tokenization 后，TokenizerManager 调用：

```python
return self._create_tokenized_object(
    obj, input_text, input_ids, input_embeds, mm_inputs, token_type_ids
)
```

### 6.1 token ids 转成紧凑数组

```python
input_ids_arr = (
    array("q", input_ids) if input_ids is not None else None
)
```

这里把 Python list 转成 `array("q")`。它表达的是 64 位整数 token ids，并且比 Python 整数列表更适合序列化和跨进程传输。

### 6.2 sampling 参数的两层处理

代码先合并 preferred sampling params 和请求显式参数：

```python
if self.preferred_sampling_params:
    sampling_kwargs = {**self.preferred_sampling_params, **obj.sampling_params}
else:
    sampling_kwargs = obj.sampling_params
```

由于后面的请求参数覆盖前面的 preferred 参数，部署方可以设置默认值，但客户端仍可以显式指定自己的值。

然后构造并规范化：

```python
sampling_params = self.sampling_params_class(**sampling_kwargs)
sampling_params.normalize(self.tokenizer)
sampling_params.verify(self.model_config.vocab_size)
```

三步分别可以理解为：

1. 把字典变成有明确字段的 SamplingParams 对象；
2. 结合 tokenizer 补全或解析 token 相关设置；
3. 根据 vocab size 检查 top-k、token id 等值是否合法。

`max_thinking_tokens` 如果存在，还会被放入 `custom_params["thinking_budget"]`，让后续采样和停止逻辑能够读取这个请求级预算。

### 6.3 生成请求对象包含什么

`TokenizedGenerateReqInput(...)` 中保存的字段远多于 `text` 和 `input_ids`，其中比较关键的有：

```python
TokenizedGenerateReqInput(
    input_text=input_text,
    input_ids=input_ids_arr,
    mm_inputs=mm_inputs,
    sampling_params=sampling_params,
    return_logprob=obj.return_logprob,
    top_logprobs_num=obj.top_logprobs_num,
    stream=obj.stream,
    rid=obj.rid,
    lora_id=obj.lora_id,
    session_id=obj.session_id,
    custom_logit_processor=obj.custom_logit_processor,
    require_reasoning=obj.require_reasoning,
    return_hidden_states=obj.return_hidden_states,
    routed_dp_rank=obj.routed_dp_rank,
    priority=obj.priority,
    extra_key=obj.extra_key,
    cache_salt=obj.cache_salt,
    routing_key=obj.routing_key,
)
```

这些字段决定了 Scheduler 后续如何安排请求。例如：

- `stream` 决定输出是否需要中间结果；
- `lora_id` 影响使用哪一个 adapter；
- `extra_key` 和 `cache_salt` 参与前缀缓存隔离；
- `return_logprob` 改变 forward 后需要保留哪些概率信息；
- `routed_dp_rank` 影响请求去哪个 DP rank；
- `session_id` 让连续请求可以复用 session 相关状态。

### 6.4 `time_stats` 也随请求穿过边界

最后：

```python
tokenized_obj.time_stats = self.rid_to_state[obj.rid].time_stats
tokenized_obj.time_stats.set_tokenize_finish_time()
```

这表示性能统计不是在请求返回时凭空推算，而是在各阶段打时间戳：收到请求、tokenize 完成、dispatch 开始/结束、首 token、响应发送等。后续 Scheduler 返回的时间统计会被合并进 `meta_info`。

## 7. `_send_one_request`：通过 ZMQ 穿过进程边界

源码位置：`tokenizer_manager.py:1577-1604`。

核心代码可以概括为：

```python
async def _send_one_request(tokenized_obj):
    prepared_mm_items = await transport.prepare_for_dispatch_async(
        (tokenized_obj.mm_inputs,)
    )
    tokenized_obj.time_stats.set_api_server_dispatch_time()
    tokenized_obj = wrap_shm_features(tokenized_obj)
    time_stats = tokenized_obj.time_stats
    tokenized_obj.wrap_pickle_fields()
    self._dispatch_to_scheduler(tokenized_obj)
    self._mark_state_dispatched(tokenized_obj.rid)
    tokenized_obj.time_stats = time_stats
    tokenized_obj.time_stats.set_api_server_dispatch_finish_time()
```

### 7.1 多模态数据的 transport preparation

`prepare_for_dispatch_async` 负责为可能跨进程或跨设备传输的 multimodal features 做准备。不同配置可能使用共享内存、CUDA VMM 或其他 transport。它的存在让“请求控制消息”和“大块 feature 数据”可以采用合适的传输方式，而不是简单把所有 GPU tensor 都 pickle 一遍。

如果后续 dispatch 失败，`finally` 中会调用：

```python
self.cuda_vmm_feature_transport.cancel_for_dispatch(prepared_mm_items)
```

这避免预留的传输资源泄漏。

### 7.2 `wrap_shm_features` 和 `wrap_pickle_fields`

跨进程消息不能假设接收方可以直接引用发送进程的 Python 对象或 GPU 指针。发送前需要：

- 把适合共享内存的 feature 包装成接收方可解析的句柄；
- 把不能直接传输的字段转换成 pickle-safe 表示。

接收方再做反向 unwrap。这个边界解释了为什么源码中会看到很多 `wrap_*` / `unwrap_*`：它们不是业务字段，而是进程通信的表示层。

### 7.3 `send_to_scheduler` 的单 tokenizer 与多 tokenizer 模式

TokenizerManager 初始化 IPC channel 的代码在 `tokenizer_manager.py:558-573`：

- tokenizer worker 数为 1：直接 PUSH 到 `scheduler_input_ipc_name`；
- tokenizer worker 数大于 1：先 PUSH 到 tokenizer worker channel，并记录自己的 `tokenizer_ipc_name`。

多 tokenizer 模式下，消息需要带上来源 worker 的 IPC 地址。`_dispatch_to_scheduler` 和 `_async_dispatch_to_scheduler` 会先调用 `stamp_http_worker_ipc`，再发送对象。

这是一种路由信息：Scheduler 完成后，必须知道结果应该回到哪个 HTTP/tokenizer worker，而不能只依靠 `rid` 在所有进程中广播。

### 7.4 为什么生成请求是同步发送、异步等待

`_send_one_request` 本身很快：准备 payload、发送一条消息、标记 dispatched。它不会等待模型执行完成。随后 `_wait_one_response` 返回一个异步生成器，真正等待的是 `ReqState.event`。

这让一个 TokenizerManager 可以同时挂起很多 HTTP 请求，而 Scheduler 只在资源允许时挑选其中一部分进入 GPU batch。

## 8. Scheduler 如何把消息变成 `Req`

Scheduler 进程的接收循环会根据消息类型调用对应 handler。生成消息进入：

```python
Scheduler.handle_generate_request(recv_req)
```

源码位置：`python/sglang/srt/managers/scheduler.py:2708-3057`。

其第一步是确认 session 类型：

```python
session_id = (
    recv_req.session_params.id
    if recv_req.session_params is not None
    else None
)
radix_native_session = (
    recv_req.session_id is not None and self.enable_session_radix_cache
)
```

然后大致分三种情况：

1. 普通请求，或者启用 radix-native session 的请求；
2. 已存在且未关闭的 session 请求；
3. 找不到 session 或 session 正在关闭。

### 8.1 普通请求创建 `Req`

普通路径把 tokenized 消息字段传给 `Req(...)`：

```python
req = Req(
    recv_req.rid,
    recv_req.input_text,
    recv_req.input_ids,
    recv_req.sampling_params,
    return_logprob=recv_req.return_logprob,
    top_logprobs_num=recv_req.top_logprobs_num,
    stream=recv_req.stream,
    lora_id=recv_req.lora_id,
    session_id=recv_req.session_id,
    input_embeds=recv_req.input_embeds,
    custom_logit_processor=recv_req.custom_logit_processor,
    return_hidden_states=recv_req.return_hidden_states,
    routed_dp_rank=recv_req.routed_dp_rank,
    priority=recv_req.priority,
    extra_key=recv_req.extra_key,
    cache_salt=recv_req.cache_salt,
    routing_key=recv_req.routing_key,
)
```

构造完成后：

```python
req.tokenizer = self.tokenizer
```

Scheduler 因而拥有一个可用于调度和输出处理的完整请求对象。这里的 `Req` 不是 msgspec message，而是 Scheduler 内部的有状态运行对象。

### 8.2 `Req` 的输入、输出和缓存状态

`Req.__init__` 位于 `schedule_batch.py:926` 附近。几个字段特别重要：

```python
self.rid = rid
self.origin_input_ids = origin_input_ids
self.output_ids = array("q")
self.full_untruncated_fill_ids = array("q")
self.extend_range = None
self.kv = ReqKvInfo()
self.finished_reason = None
self.to_finish = None
self.stream = stream
```

含义是：

- `origin_input_ids` 永远表示原始 prompt token；
- `output_ids` 记录模型生成的 token；
- `full_untruncated_fill_ids` 用于维护完整填充序列和缓存计算；
- `kv` 保存该请求的 KV 资源关系；
- `finished_reason` 表示已经确定的最终结束原因；
- `to_finish` 是中途请求 abort 等情况下的待完成标记；
- `stream` 让输出处理知道是否发送中间结果。

`Req` 同时保存增量 detokenization 状态：

```python
self.surr_offset = None
self.read_offset = None
self.decoded_text = ""
```

Scheduler 每生成一批 token 后，结果可以先通过 detokenizer 处理成文本增量，再由 TokenizerManager 组织成 API 输出。

### 8.3 处理 session

如果 session 已存在且没有 `close_on_finish`，Scheduler 使用 session controller 创建请求：

```python
req = session.create_req(
    recv_req,
    self.tokenizer,
    self.model_config.vocab_size,
    eos_token_ids=self.model_config.hf_eos_token_id,
)
```

这和普通 `Req(...)` 的区别不是简单地多一个 `session_id`。Session 可能持有上一轮的上下文、会话缓存和关闭策略，因此新请求要由 session controller 决定怎样继承这些状态。

如果 session 不存在，Scheduler 构造一个带 abort finish reason 的请求，把错误沿正常 output stream 返回。这样客户端得到的仍然是一个结构化错误，而不是 Scheduler 进程直接崩溃。

### 8.4 Scheduler 侧的第二次校验

TokenizerManager 已经做过输入长度和参数校验，但 Scheduler 仍会根据运行时状态继续校验，例如：

- disaggregation 是否有 bootstrap room；
- 多模态输入能否在本 rank 处理；
- speculative decoding 参数是否与当前 worker 配置兼容；
- `return_sampling_mask` 是否与 backend、disaggregation、speculation 兼容；
- prompt 扩展多模态 token 后是否超出长度；
- logprob 起始位置是否在 prompt 范围内。

这不是重复劳动。TokenizerManager 的校验面向 API 输入，Scheduler 的校验面向执行环境；有些条件只有 Scheduler 知道，例如当前 disaggregation mode、attention backend 和 worker 特性。

### 8.5 放入等待队列

校验完成后，Scheduler 调用：

```python
self._add_request_to_queue(req)
```

普通模式的大致路径是：

```python
if self.disaggregation_mode == DisaggregationMode.NULL:
    if self._abort_on_queued_limit(req):
        return
    self._prefetch_kvcache(req)
    self.waiting_queue.append(req)
    req.time_stats.set_wait_queue_entry_time()
```

这几行非常关键：

1. 队列长度限制可能直接拒绝请求；
2. 可以在正式 forward 前预取 HiCache/KV cache；
3. `req` 进入 `waiting_queue`，等待下一次调度；
4. 记录进入队列时间，用于排队延迟和调度策略。

对于 prefill/decode disaggregation，代码不会统一放入普通 waiting queue，而是放入 prefill bootstrap queue 或 decode prealloc queue。这正是同一个 API 请求在不同部署模式下具有不同调度入口的地方。

## 9. Scheduler 返回结果：反向穿过 IPC

请求送出后，TokenizerManager 的 `_wait_one_response` 调用 `_stream_one_response`。它不直接读取 socket，而是等待：

```python
await asyncio.wait_for(
    state.event.wait(), timeout=_REQUEST_STATE_WAIT_TIMEOUT
)
```

与此同时，后台 `handle_loop` 收到 Scheduler 或 detokenizer 的结果，并调用：

```python
await self._handle_batch_output(recv_obj)
```

### 9.1 `_handle_batch_output` 先建立 `meta_info`

源码位置：`tokenizer_manager.py:2240` 附近。对每一个返回的 `rid`，它先查找：

```python
state = self.rid_to_state.get(rid, None)
```

然后构造：

```python
meta_info = {
    "id": rid,
    "finish_reason": recv_obj.finished_reasons[i],
    "prompt_tokens": recv_obj.prompt_tokens[i],
    "weight_version": self.config_value("weight_version"),
    "num_retractions": recv_obj.retraction_counts[i],
}
```

根据请求和返回类型，后续还会加入：

- `completion_tokens`、`cached_tokens`；
- logprobs；
- reasoning tokens；
- hidden states；
- routed experts；
- sampling mask；
- 多模态 token 数；
- speculative decoding 统计。

因此 HTTP 返回中的 `meta_info` 是在 TokenizerManager 侧组装的，不是模型 forward 直接返回的 JSON。

### 9.2 累积文本和 token ids

对 `BatchStrOutput`，代码取出：

```python
delta_text = recv_obj.output_strs[i]
delta_output_ids = list(recv_obj.output_ids[i])
state.append_text(delta_text)
state.output_ids.extend(delta_output_ids)
```

这里有两个层次：

- `delta_text` 是这次 Scheduler 迭代新产生的文本片段；
- `state` 保存从开始到目前为止的累计文本和 token ids。

如果是增量 streaming，直接返回 delta：

```python
out_dict = {
    "text": delta_text,
    "output_ids": delta_output_ids,
    "meta_info": meta_info,
}
```

如果不是增量 streaming，非最终 chunk 的 `text` 可以暂时设为 `None`，等 `_stream_one_response` 需要发送时再通过 `state.get_text()` 得到完整文本。这样避免每一步都重新拼接完整字符串，降低长回答的 O(n²) 风险。

### 9.3 Event 如何唤醒正确的 HTTP 协程

`_handle_batch_output` 会把构造好的输出放到对应 `state.out_list`，然后设置 `state.event`。等待中的 `_stream_one_response` 被唤醒，执行：

```python
out_list = state.out_list
state.out_list = []
finished = state.finished
state.event.clear()
```

它一次性取走当前积累的输出并清空 event。这种设计允许 Scheduler 在 HTTP 协程尚未运行时连续产生多个 chunk；恢复后，TokenManager 可以把多个增量 chunk 合并，而不会因为 event 只有“已设置/未设置”两种状态而丢失消息。

## 10. `_stream_one_response`：流式与非流式的最后分叉

源码位置：`tokenizer_manager.py:1730-1852`。

其核心循环是：

```python
while True:
    await state.event.wait()
    out_list = state.out_list
    state.out_list = []
    finished = state.finished

    if incremental_stream and len(out_list) > 1:
        out = self._coalesce_streaming_chunks(out_list, ...)
    else:
        out = out_list[-1]

    if finished:
        yield out
        break

    if is_stream:
        yield out
```

### 10.1 增量 streaming 的 coalesce

当 HTTP 客户端较慢时，多个小 chunk 可能积累在 `out_list`。如果每次只取最后一个，前面的 delta 就会丢失。因此 `_coalesce_streaming_chunks` 会：

- 拼接所有 chunk 的 `text`；
- 拼接所有 chunk 的 `output_ids`；
- 从最后一个 chunk 取得一般 meta_info；
- 对 incremental meta keys 继续拼接。

这说明 `output_ids` 在增量模式下是“delta”，而不是每次都重复发送完整序列。

### 10.2 非增量 streaming

非增量 streaming 的中间消息可能不包含完整 text，而是延迟构造：

```python
if is_stream and not incremental_stream and out["text"] is None:
    out["text"] = state.get_text()
```

最终客户端仍然收到完整文本，但内部避免了每一次 Scheduler step 都复制越来越长的字符串。

### 10.3 非流式请求如何等待最终结果

非流式模式下，即使 Scheduler 已经产生了中间 token，`_stream_one_response` 也不会 yield；它会继续等到 `finished=True`。所以 HTTP handler 的：

```python
await tokenizer_manager.generate_request(obj, request).__anext__()
```

拿到的是最终结果，而不是第一个 token。

### 10.4 客户端断开和 abort

等待 event 超时时，代码检查 `request.is_disconnected()`。如果连接已经断开，就调用：

```python
self.abort_request(obj.rid)
```

`abort_request` 构造 `AbortReq`，通过同一条 scheduler IPC 通道发送。Scheduler 收到后会清理等待或运行中的请求，释放相应资源。

流式 handler 另外注册：

```python
background=tokenizer_manager.create_abort_task(obj)
```

这个 background task 在响应结束后延迟检查请求是否仍存在，作为客户端断开时的补充清理机制。

### 10.5 结束原因和错误

当 `finished=True`，代码会检查 `meta_info["finish_reason"]`。正常结束原因可能是 EOS、length 或 stop string；Scheduler 侧产生的 abort/error 也沿同一输出结构回来。

- 非流式错误：转换为 `ValueError` 或 `HTTPException`，由 HTTP handler 返回错误 JSON；
- 流式错误：作为一个 SSE data event 发给客户端，然后结束 stream。

这样错误也保持了与正常输出相同的 request-id 和 finish_reason 语义。

## 11. batch 请求和 parallel sampling

单条请求只是最容易读的路径。`generate_request` 发现 `obj.is_single` 为 false 时，会调用 `_handle_batch_request`。

### 11.1 普通 batch

如果启用了 batch tokenization，并且输入满足约束：

```python
tokenized_objs = await self._batch_tokenize_and_process(batch_size, obj)
await self._send_batch_request(tokenized_objs)
```

`_send_batch_request` 把多个 tokenized objects 封装成：

```python
BatchTokenizedGenerateReqInput(batch=tokenized_objs)
```

一次发给 Scheduler。Scheduler 收到后调用：

```python
for tokenized_req in recv_req:
    self.handle_generate_request(tokenized_req)
```

也就是说，batch IPC 消息减少了发送次数，但 Scheduler 最终仍然为每个请求创建独立的 `Req`，然后由调度器决定它们是否进入同一个 GPU batch。

**API batch 和推理 batch 不是同一个概念：**

- API batch：客户端在一个 HTTP body 中提交多个请求；
- 推理 batch：Scheduler 根据 KV、token budget、优先级和运行状态，在某一轮 forward 中选择的请求集合。

两者可能相同，也可能完全不同。

### 11.2 batch streaming

`_stream_batch_responses` 为每个子请求创建一个 response generator，然后使用：

```python
done, _ = await asyncio.wait(
    task_map.keys(), return_when=asyncio.FIRST_COMPLETED
)
```

哪个请求先产生输出，就先返回哪个请求的结果，并根据 `rid_to_index` 添加其原始 batch index。因此一个 batch 中较短的请求不必等待最长请求完成。

### 11.3 `parallel_sample_num`

parallel sampling 的处理更特殊：同一 prompt 可以生成多条独立 completion。源码会先发送一个 `max_new_tokens=0` 的请求，以便缓存共同 prompt；然后复制 tokenized object，为每个采样分支生成新的 rid，再分别发送。

例如：

```text
prompt P, parallel_sample_num=3

第一次：P + max_new_tokens=0  -> 建立/填充共同前缀缓存
之后：  P + rid-1              -> completion A
        P + rid-2              -> completion B
        P + rid-3              -> completion C
```

这解释了为什么并行采样代码会复制 sampling params、重新生成 rid，并为每个分支创建独立 `ReqState`。共享的是 prompt/KV 前缀，不能共享输出状态。

## 12. 一个请求的完整时序

把前面的细节串成时间线：

```text
客户端
  │ POST /generate
  ▼
FastAPI generate_request
  │ 得到 GenerateReqInput
  │ stream? 决定 JSON 或 SSE 外壳
  ▼
TokenizerManager.generate_request
  │ 启动 handle_loop（首次调用）
  │ normalize batch/arguments
  │ 初始化 rid -> ReqState
  │ 等待 pause / model update reader lock
  ▼
_tokenize_one_request
  │ input_ids 已提供？直接使用
  │ 否则 text -> tokenizer -> input_ids
  │ 可选 multimodal processor
  │ 校验 context length 和 sampling params
  ▼
_create_tokenized_object
  │ list[int] -> array("q")
  │ dict -> SamplingParams
  │ 保存 stream/logprob/LoRA/session/cache keys
  ▼
_send_one_request
  │ 准备共享内存或 feature transport
  │ wrap pickle fields
  │ ZMQ PUSH
  ▼
Scheduler.handle_generate_request
  │ TokenizedGenerateReqInput -> Req
  │ session / multimodal / disagg 校验
  │ prefix cache prefetch
  │ Req -> waiting_queue
  ▼
get_next_batch_to_run（后续调度迭代）
  │ 选 prefill 或 decode batch
  ▼
GPU forward + sampling
  │ 结果经 detokenizer/IPC 返回
  ▼
TokenizerManager.handle_loop
  │ rid -> ReqState
  │ 组装 meta_info
  │ 累积 text/output_ids
  │ state.event.set()
  ▼
_stream_one_response
  │ stream: 发送增量 chunk
  │ non-stream: 等待 finished
  ▼
HTTP
  │ JSON 或 data: ... SSE
  ▼
客户端
```

假设 prompt 被 tokenizer 编成 12 个 token，模型生成 3 个 token：

```text
t=0  API 收到文本
 t=1  TokenizerManager 得到 input_ids[12]
 t=2  Scheduler 创建 Req，加入 waiting_queue
 t=3  prefill：一次处理 prompt 的 12 token
 t=4  decode：生成 token 13，可能发送 "The"
 t=5  decode：生成 token 14，可能发送 " KV"
 t=6  decode：生成 token 15，检测 EOS 或 stop
 t=7  返回 finished=true 的最终 chunk
```

如果 `stream=false`，客户端通常只在 t=7 收到完整答案；如果 `stream=true`，客户端可能在 t=4、t=5、t=7 分别收到 SSE event。

## 13. 初学者最容易混淆的几个边界

### 13.1 TokenizerManager 不等于 tokenizer

TokenizerManager 的职责包括 tokenizer，但还包括：

- HTTP 请求和 Scheduler 消息之间的桥接；
- 请求状态和异步等待；
- detokenization 和流式输出；
- LoRA、metrics、abort、权重更新等控制面操作。

### 13.2 `ReqState` 不等于 `Req`

`ReqState` 在 HTTP/tokenizer 进程，面向“如何等结果”；`Req` 在 Scheduler 进程，面向“如何执行和调度”。两者通过同一个 `rid` 关联，而不是通过共享 Python 对象关联。

### 13.3 发给 Scheduler 不代表马上执行

`_send_one_request` 完成后，`Req` 只是进入 waiting queue。什么时候执行由 `get_next_batch_to_run` 决定，还要考虑：

- 当前是否有 running batch；
- prefill 和 decode 的优先顺序；
- token budget；
- KV cache 是否有空间；
- prefix cache 命中多少；
- chunked prefill、优先级、抢占和 disaggregation。

### 13.4 API batch 不等于模型 batch

一个 body 中的 8 个请求可能被拆分、延后或和别的 HTTP 请求合并；Scheduler 的 batch 是每一个调度迭代重新计算的执行计划。

### 13.5 HTTP 返回不是模型原始输出

模型产生 logits，采样器产生 token ids；中间还会经过 finish 检查、detokenization、logprob/meta_info 组装和 SSE/JSON 编码。客户端看到的是协议层结果，不是 `ModelRunner.forward` 的 Python 返回值。

## 小结

本篇的核心结论可以压缩成四句话：

1. HTTP handler 只负责把 JSON 变成输入对象，并把结果包装成 JSON 或 SSE；
2. TokenizerManager 负责 normalize、tokenize、多模态预处理、参数校验、请求状态和 IPC；
3. Scheduler 收到 `TokenizedGenerateReqInput` 后创建有状态的 `Req`，再把它放入适合当前部署模式的队列；
4. 结果通过 `rid -> ReqState` 反向关联，经过 detokenization 和 meta_info 组装后才返回客户端。

因此，一条请求真正进入 GPU 前，已经完成了多次有意的表示转换：

```text
JSON
  -> GenerateReqInput
  -> TokenizedGenerateReqInput
  -> Req
  -> ScheduleBatch
  -> ForwardBatch
  -> token ids / text response
```

这些转换不是形式主义。每个表示都服务于一个边界：API 协议、CPU 预处理、进程通信、Scheduler 状态管理、GPU batch 执行和客户端响应。理解这些边界，后面阅读调度器、KV cache 和 ModelRunner 时就不会把不同层次的对象混在一起。
