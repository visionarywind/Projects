# 模型加载与并行初始化

> 模块：M06 模型加载与权重、M07 分布式并行、M05 ModelRunner、M08 KV Cache、M09 Attention/CUDA Graph。  
> 前置阅读：`source-doc/00-overview/architecture.md`、`source-doc/02-request-flow/03-调度器与连续批处理.md`、`source-doc/02-request-flow/04-模型执行与输出.md`、`source-doc/02-request-flow/05-配置解析与运行时上下文.md`、`source-doc/02-request-flow/06-多进程与IPC.md`。

本文回答一个启动阶段的核心问题：**一条 `--model-path` 配置，如何变成每张 GPU 上可执行的模型分片、通信组、KV cache、attention backend 和 CUDA Graph？**

结论先行（证据状态：已确认）：普通离线/HTTP LLM 主线中，模型不是在每个请求到来时才加载。模型加载发生在 scheduler worker 子进程初始化阶段，顺序大致是：主进程解析并发布配置，启动 scheduler 子进程；子进程绑定 rank/GPU，初始化 `torch.distributed` 和模型并行组；`TpModelWorker` 创建 `ModelConfig` 与 `ModelRunner`；`ModelRunner` 选择 loader、实例化模型类、遍历 checkpoint、调用 `load_weights`/参数 `weight_loader` 写入权重；加载后 scheduler 再创建 KV cache、attention backend、CUDA Graph，最后通过启动 pipe 报告 ready。[`python/sglang/srt/entrypoints/engine.py:847-962`][`python/sglang/srt/managers/scheduler.py:5744-5811`][`python/sglang/srt/model_executor/model_runner.py:1146-1280`]

---

## 1. 直观解释：启动模型像组装一条多 GPU 生产线

可以把 SGLang worker 启动想成组装一条生产线：

1. **先分工**：哪些进程负责哪些 GPU？哪些 rank 是 TP 伙伴？哪些 rank 是 PP 上下游？
2. **再建通信**：所有 rank 按相同规则加入 WORLD、TP、PP、MoE、attention 等 process group。
3. **再搬机器**：为每个 worker 创建模型对象，把 checkpoint 中的 tensor 搬到参数里。
4. **再接仓库**：创建 KV cache 池、请求到 token 的映射表、Radix/tree cache。
5. **再调试流水线**：初始化 attention backend、捕获 CUDA Graph、预热 sampler。
6. **最后开工**：向父进程报告初始化完成，进入 scheduler event loop 接请求。

初学者最容易混淆三件事：

| 容易混淆的东西 | 正确理解 |
|---|---|
| global rank 与 GPU id | rank 是分布式通信坐标；GPU id 是本地设备绑定。它们可能相等，但不是同一概念。 |
| checkpoint 文件 shard 与 TP 张量分片 | 文件遍历顺序只决定读哪些文件、先读哪个文件；TP 分片通常由参数的 `weight_loader` 或专用 loader 决定。 |
| 启动加载与请求执行 | 权重、KV pool、attention backend、CUDA Graph 在启动时准备；请求到来时复用这些资源构造 `ForwardBatch` 执行。 |

## 2. 启动时序总览

证据状态：已确认。

```text
主进程 Engine / HTTP server
  │
  ├─ ServerArgs.resolve_once / publish(role="tokenizer")
  │
  ├─ 启动 detokenizer 子进程
  │
  └─ Engine._launch_scheduler_processes
        │
        ├─ 为每个 PP/TP 组合计算 gpu_id、tp_rank、pp_rank、attn_cp_rank、moe_dp_rank、moe_ep_rank
        ├─ mp.Process(target=run_scheduler_process_func, ...)
        └─ mp.Pipe 等待 scheduler.get_init_info()
              │
              ▼
        run_scheduler_process 子进程
              │
              ├─ load_plugins()
              ├─ publish(server_args, role="scheduler")
              ├─ configure_scheduler_process(...)
              ├─ Scheduler(...)
              │    │
              │    ├─ 构造 ParallelState
              │    ├─ init_model_config()
              │    ├─ init_ipc_channels()
              │    ├─ init_model_worker()
              │    │    │
              │    │    ├─ TpModelWorker._init_model_config()
              │    │    ├─ TpModelWorker._init_model_runner()
              │    │    │    │
              │    │    │    └─ ModelRunner(...)
              │    │    │         ├─ set_device(gpu_id)
              │    │    │         ├─ init_torch_distributed()
              │    │    │         │    ├─ init_process_group(WORLD)
              │    │    │         │    └─ initialize_model_parallel(...)
              │    │    │         ├─ initialize()
              │    │    │         │    └─ load_model()
              │    │    │         │         ├─ build_load_config(...)
              │    │    │         │         ├─ get_model_loader(...)
              │    │    │         │         ├─ _initialize_model(...)
              │    │    │         │         ├─ checkpoint iterator
              │    │    │         │         ├─ model.load_weights(...)
              │    │    │         │         ├─ post_load / quant postprocess
              │    │    │         │         └─ TP monitored barrier
              │    │    │         └─ ModelRunner ready
              │    │    ├─ init_memory_pools() / build_kv_cache(...)
              │    │    ├─ init_attention_backends()
              │    │    ├─ init_cuda_graphs()
              │    │    ├─ prewarm_sampling()
              │    │    └─ finalize_startup_weight_load()（可选）
              │    └─ init_request_receiver / output streamer / processors
              │
              ├─ pipe_writer.send(scheduler.get_init_info())
              └─ scheduler.run_event_loop()
```

要点：`pipe_writer.send(...)` 在 `Scheduler(...)` 构造完成之后才执行，所以父进程收到 ready 时，scheduler worker 已经完成模型加载、KV cache 分配、attention backend/CUDA Graph 初始化等启动资源准备。[`python/sglang/srt/managers/scheduler.py:5792-5811`]

## 3. rank、GPU、TP、PP、DP、EP、CP/DCP：先把坐标讲清楚

### 3.1 global rank 不是 GPU id

证据状态：已确认。

`Engine._launch_scheduler_processes` 在普通非 DP-controller 分支中，遍历本节点负责的 `pp_rank_range` 和 `tp_rank_range`。每个 `(pp_rank, tp_rank)` 组合都会创建一个 scheduler worker process，并计算这个进程应绑定的本地 `gpu_id`：

```python
pp_rank_range, tp_rank_range, pp_size_per_node, tp_size_per_node = (
    _calculate_rank_ranges(
        get_parallel().nnodes,
        get_parallel().pp_size,
        get_parallel().tp_size,
        get_parallel().node_rank,
    )
)

for pp_rank in pp_rank_range:
    for tp_rank in tp_rank_range:
        reader, writer = mp.Pipe(duplex=False)
        gpu_id = (
            get_device().base_gpu_id
            + ((pp_rank % pp_size_per_node) * tp_size_per_node)
            + (tp_rank % tp_size_per_node) * get_device().gpu_id_step
        )
        attn_cp_rank, moe_dp_rank, moe_ep_rank = _compute_parallelism_ranks(
            tp_rank
        )
```

行级解释：

- `pp_rank_range` / `tp_rank_range`：当前节点要启动的 PP/TP rank 坐标。
- `mp.Pipe(duplex=False)`：给父进程一个只读端，用来等待 worker 初始化结果；长期请求/输出流不是靠这个 pipe，而是 ZMQ/IPC。
- `gpu_id`：本地设备 id，由 base id、PP 本地位置、TP 本地位置和设备步长共同决定。
- `_compute_parallelism_ranks(tp_rank)`：从 TP rank 派生 attention CP、MoE DP、MoE EP 坐标。

随后进程启动时把这些坐标全部传给 `run_scheduler_process_func`：

```python
proc = mp.Process(
    target=run_scheduler_process_func,
    args=(
        server_args,
        port_args,
        gpu_id,
        tp_rank,
        attn_cp_rank,
        moe_dp_rank,
        moe_ep_rank,
        pp_rank,
        None,
        writer,
    ),
)
```

这说明：**rank 坐标是分布式逻辑位置，`gpu_id` 是本地设备绑定，二者由启动器同时传给 worker，但用途不同。**[`python/sglang/srt/entrypoints/engine.py:867-918`]

### 3.2 DP controller 是另一条进程分支

证据状态：已确认。

当 `dp_size > 1` 或 elastic EP scale join 模式打开时，`Engine._launch_scheduler_processes` 不再直接为所有 TP/PP 组合启动 worker，而是先启动 data parallel controller：

```python
use_dp_controller = (
    get_parallel().dp_size > 1 or get_exec().moe.ep_join_mode == "scale"
)
...
proc = mp.Process(
    target=run_data_parallel_controller_process,
    kwargs=dict(
        server_args=server_args,
        port_args=port_args,
        pipe_writer=writer,
        run_scheduler_process_func=run_scheduler_process_func,
    ),
)
```

父进程会把 controller 返回的 scheduler child PIDs 加入监控列表：

```python
if use_dp_controller:
    for info in infos:
        if SCHEDULER_PIDS_ARG in info:
            all_child_pids.extend(info[SCHEDULER_PIDS_ARG])
```

因此文档和调试时不能把 DP controller 模式简化成“多启动几个普通 TP worker”。它有额外 controller 进程和子 PID 回传逻辑。[`python/sglang/srt/entrypoints/engine.py:862-945`]

### 3.3 TP 和 PP 的 group 排列

证据状态：已确认。

`initialize_model_parallel` 的 docstring 给了 8 GPU、TP=2、PP=4 的例子：

```text
4 tensor model-parallel groups:
    [g0, g1], [g2, g3], [g4, g5], [g6, g7]
2 pipeline model-parallel groups:
    [g0, g2, g4, g6], [g1, g3, g5, g7]
```

直观解释：

- TP group 横向切同一层里的矩阵/张量。例如同一个 attention/MLP 层的不同列或行放在不同 rank 上。
- PP group 纵向切模型层。例如 rank 0 拥有前几层，rank 2 拥有中间层，rank 4/6 拥有后续层。
- 同一个 global rank 同时属于一个 TP group 和一个 PP group，但这两个 group 的成员集合不同。

`initialize_model_parallel` 还给出 attention CP/TP 与 MoE DP/EP 的例子：

```text
1 tensor model-parallel group:
    [g0, g1, g2, g3, g4, g5, g6, g7]
4 attention context-parallel groups:
    [g0, g4], [g1, g5], [g2, g6], [g3, g7]
2 attention tensor-parallel groups:
    [g0, g1, g2, g3], [g4, g5, g6, g7]
2 moe expert-parallel groups:
    [g0, g1, g2, g3], [g4, g5, g6, g7]
4 moe data-parallel groups:
    [g0, g4], [g1, g5], [g2, g6], [g3, g7]
```

这说明 attention 的 context/tensor group 和 MoE 的 data/expert group 可以按不同维度重组同一批 rank。[`python/sglang/srt/distributed/parallel_state.py:2298-2365`]

## 4. scheduler 子进程：为什么必须先 publish 再构造 Scheduler

证据状态：已确认。

`scheduler.py` 的进程入口是 `run_scheduler_process`：

```python
def run_scheduler_process(
    server_args: ServerArgs,
    port_args: PortArgs,
    gpu_id: int,
    tp_rank: int,
    attn_cp_rank: int,
    moe_dp_rank: int,
    moe_ep_rank: int,
    pp_rank: int,
    dp_rank: Optional[int],
    pipe_writer,
    display_tp_rank: Optional[int] = None,
    display_dp_rank: Optional[int] = None,
    display_moe_ep_rank: Optional[int] = None,
):
    load_plugins()
    publish(server_args, role="scheduler")
    dp_rank = configure_scheduler_process(...)
    parent_process = psutil.Process().parent()
```

行级解释：

- `load_plugins()`：允许插件在 scheduler 构造前注册/覆盖相关依赖。
- `publish(server_args, role="scheduler")`：把已经 resolve 的 `ServerArgs` 投影成 scheduler 进程可读的 runtime config bags。
- `configure_scheduler_process(...)`：设置进程标题、日志前缀、fault handler、CPU affinity、NUMA binding。
- `parent_process = psutil.Process().parent()`：异常时用来通知父进程。

`configure_scheduler_process` 会把 rank 信息拼到日志 prefix 和进程标题中：

```python
if shown_dp is not None:
    prefix += f" DP{shown_dp}"
if get_parallel().pp_size > 1:
    prefix += f" PP{pp_rank}"
if get_parallel().attn_cp_size > 1:
    prefix += f" ATTN_CP{attn_cp_rank}"
if get_parallel().moe_dp_size > 1:
    prefix += f" MOE_DP{moe_dp_rank}"
if get_parallel().tp_size > 1:
    prefix += f" TP{shown_tp}"
if get_parallel().ep_size > 1:
    prefix += f" EP{shown_moe_ep}"
```

这也是调试多卡启动时判断“哪一个 rank 报错”的重要线索。[`python/sglang/srt/managers/scheduler.py:5676-5741`]

构造和 ready 发送发生在 try 块中：

```python
scheduler = Scheduler(
    server_args,
    port_args,
    gpu_id,
    tp_rank,
    moe_ep_rank,
    pp_rank,
    attn_cp_rank,
    moe_dp_rank,
    dp_rank,
)

pipe_writer.send(scheduler.get_init_info())
scheduler.run_event_loop()
```

异常路径会记录 traceback 并向父进程发 `SIGQUIT`：

```python
except Exception:
    traceback = get_exception_traceback()
    logger.error(f"Scheduler hit an exception: {traceback}")
    parent_process.send_signal(signal.SIGQUIT)
```

所以启动失败不是普通请求错误；它可能触发父进程清理整棵进程树。[`python/sglang/srt/managers/scheduler.py:5744-5833`]

## 5. 分布式初始化：WORLD 先成立，模型并行 group 再成立

### 5.1 `ModelRunner` 中触发分布式初始化

证据状态：已确认。

`TpModelWorker._init_model_runner` 把本 rank 的 `ParallelState`、GPU id、NCCL port、内存池引用等传给 `ModelRunner`：

```python
self._model_runner = ModelRunner(
    model_config=self.model_config,
    mem_fraction_static=get_schedule().mem_fraction_static,
    gpu_id=self.gpu_id,
    ps=self.ps,
    nccl_port=self.nccl_port,
    server_args=self.server_args,
    is_draft_worker=self.is_draft_worker,
    req_to_token_pool=self.req_to_token_pool,
    token_to_kv_pool_allocator=self.token_to_kv_pool_allocator,
    memory_pool_config=self.memory_pool_config,
    draft_attention_backend=self.draft_attention_backend,
    draft_model_idx=0 if self.is_multi_layer_eagle else None,
)
```

`ModelRunner.__init__` 先保存配置和 rank 状态，然后设置设备，再初始化分布式：

```python
self.gpu_id = gpu_id
self.ps = ps
self.model_config = model_config
self.dist_port = nccl_port
self.server_args = server_args
...
torch.get_device_module(self.device).set_device(ps.gpu_id)
...
self.init_torch_distributed()
```

这说明分布式初始化属于每个 target model runner 的启动阶段，不是 scheduler event loop 的每轮逻辑。[`python/sglang/srt/managers/tp_worker.py:480-496`][`python/sglang/srt/model_executor/model_runner.py:318-467`]

### 5.2 `init_torch_distributed` 做了什么

证据状态：已确认。

`ModelRunner.init_torch_distributed` 调用 `bootstrap.init_torch_distributed` 并保存返回的 group：

```python
result = bootstrap.init_torch_distributed(
    server_args=self.server_args,
    model_config=self.model_config,
    device=self.device,
    ps=self.ps,
    dist_port=self.dist_port,
    is_draft_worker=self.is_draft_worker,
    local_omp_cpuid=self.local_omp_cpuid if self.device == "cpu" else None,
)
self.tp_group = result.tp_group
self.pp_group = result.pp_group
self.attention_tp_group = result.attention_tp_group
self.pre_model_load_memory = result.pre_model_load_memory
```

`bootstrap.init_torch_distributed` 的关键步骤：

```python
backend = _resolve_backend(device=device)
before_avail_memory = get_available_gpu_memory(device, ps.gpu_id)
if not get_parallel().enable_p2p_check:
    monkey_patch_p2p_access_check()

dist_init_method = _resolve_dist_init_method(dist_port=dist_port)
_set_all_reduce_flags()
```

然后在 target worker 上初始化并行组：

```python
_init_parallel_groups(
    backend=backend,
    dist_init_method=dist_init_method,
    server_args=server_args,
    model_config=model_config,
    gpu_id=ps.gpu_id,
    tp_rank=ps.tp_rank,
    tp_size=ps.tp_size,
    pp_rank=ps.pp_rank,
    pp_size=ps.pp_size,
    attn_dp_size=ps.attn_dp_size,
    attn_cp_size=ps.attn_cp_size,
    moe_ep_size=ps.moe_ep_size,
    moe_dp_size=ps.moe_dp_size,
    dcp_size=ps.attn_dcp_size,
)
```

还会可选预热 NCCL/RCCL/HCCL，并在模型加载前记录显存基线：

```python
pre_model_load_memory = get_available_gpu_memory(
    device,
    ps.gpu_id,
    distributed=get_world_group().world_size > 1 and not is_draft_worker,
    cpu_group=get_world_group().cpu_group,
)
```

这个 baseline 后续会用于 KV cache sizing 和显存统计，所以通信预热产生的持久分配需要在 baseline 前发生。[`python/sglang/srt/distributed/bootstrap.py:70-172`]

### 5.3 WORLD rank 公式

证据状态：已确认。

`bootstrap._init_parallel_groups` 使用基础公式：

```text
world_size = tp_size * pp_size
rank = tp_size * pp_rank + tp_rank
```

在 elastic EP scale join 场景会加 `rank_offset`。随后调用 `init_distributed_environment(...)` 和 `initialize_model_parallel(...)`。

`init_distributed_environment` 里真正调用 PyTorch：

```python
torch.distributed.init_process_group(
    backend=backend,
    init_method=distributed_init_method,
    world_size=world_size,
    rank=rank,
    timeout=timeout,
    pg_options=pg_options,
)
```

然后创建 SGLang 自己保存的 WORLD group：

```python
if _WORLD is None:
    ranks = list(range(torch.distributed.get_world_size()))
    _WORLD = init_world_group(
        ranks, local_rank, backend, recovered_rank=recovered_rank
    )
```

WORLD 是基础通信域；TP、PP、attention、MoE 等 group 都建立在这个 rank 空间之上。[`python/sglang/srt/distributed/parallel_state.py:2206-2296`]

### 5.4 `initialize_model_parallel` 的校验和 group 创建

证据状态：已确认。

`initialize_model_parallel` 先校验 world size：

```python
if world_size != tensor_model_parallel_size * pipeline_model_parallel_size:
    raise RuntimeError(...)
```

还校验 DCP：

```python
if decode_context_parallel_size < 1:
    raise RuntimeError(...)
if decode_context_parallel_size > 1 and not (is_hip() or is_cuda()):
    raise RuntimeError(...)
if tensor_model_parallel_size % decode_context_parallel_size != 0:
    raise RuntimeError(...)
```

TP group 的 rank 列表按连续区间创建：

```python
num_tensor_model_parallel_groups = world_size // tensor_model_parallel_size
for tp_group_idx in range(num_tensor_model_parallel_groups):
    ranks = list(
        range(
            tp_group_idx * tensor_model_parallel_size,
            (tp_group_idx + 1) * tensor_model_parallel_size,
        )
    )
```

PP group 则按 stride 创建：

```python
num_pipeline_model_parallel_groups = world_size // pipeline_model_parallel_size
for pp_group_idx in range(num_pipeline_model_parallel_groups):
    ranks = list(
        range(pp_group_idx, world_size, num_pipeline_model_parallel_groups)
    )
```

推断：所有 rank 必须以兼容顺序执行这段初始化逻辑，否则 collective group 创建可能互相等待。该推断来自 PyTorch distributed group 创建的一般约束和 SGLang 对统一 rank 列表的集中生成；本文尚未逐行展开 `init_model_parallel_group` 内部同步细节。[`python/sglang/srt/distributed/parallel_state.py:2298-2409`]

## 6. `ModelConfig` 与 `ModelRunner`：模型加载前先确定“要加载什么”

证据状态：已确认。

`TpModelWorker._init_model_config` 通过 `ModelConfig.from_server_args` 创建模型配置：

```python
self.model_config = ModelConfig.from_server_args(
    self.server_args,
    model_path=(
        get_model().model_path
        if not self.is_draft_worker
        else get_spec().speculative_draft_model_path
    ),
    model_revision=(
        get_model().revision
        if not self.is_draft_worker
        else get_spec().speculative_draft_model_revision
    ),
    is_draft_model=self.is_draft_worker,
    context_length=self.context_length,
)
```

直观解释：

- target worker 使用普通 `--model-path` / `revision`。
- speculative draft worker 使用 draft model path/revision。
- 二者都走 `ModelConfig`，但输入字段不同。

`ModelRunner.initialize` 的核心顺序是：

```python
self.init_memory_saver_adapter()
self.maybe_init_remote_instance_transfer_engine()
self.maybe_init_expert_location_metadata()
self.maybe_init_lplb_solvers()
self.maybe_init_eplb_manager()
self.expert_location_updater = ExpertLocationUpdater()
self.maybe_init_elastic_ep()
self.init_token_oracle()
self.sampler = create_sampler()
self.load_model()
prepare_moe_topk(...)
...
self.layer_info: ModelLayerInfo = resolve_layer_indices(...)
...
self.maybe_init_lora_manager()
```

主流程：

```python

        load_config=load_config,
```

直观解释：

## 11. `AutoWeightsLoader` 和 `StackedParamsDispatch`：名字路由与融合参数

### 11.1 融合参数为什么需要 dispatch

很多模型 checkpoint 中有分开的名字：

```text
q_proj.weight
k_proj.weight
v_proj.weight
gate_proj.weight
up_proj.weight
```

但 SGLang runtime 里为了执行效率，可能使用融合参数：

```text
qkv_proj.weight
gate_up_proj.weight
```

`StackedParamsDispatch` 负责把 checkpoint 名字映射到融合 runtime 参数，并附带 shard id：

```python
class StackedParamsDispatch(msgspec.Struct, frozen=True):
    mappings: tuple[tuple[str, str, Union[int, str]], ...] = ()

    def try_load(
        self,
        name: str,
        tensor: torch.Tensor,
        params_dict: dict[str, Parameter],
    ) -> str | None:
        for fused_name, source_name, shard_id in self.mappings:
            if source_name not in name:
                continue
            target = name.replace(source_name, fused_name)
            param = params_dict.get(target)
            if param is None:
                return target
            param.weight_loader(param, tensor, shard_id)
            return target
        return None
```

标准映射：

```python
STANDARD_QKV_MAPPING = StackedParamsDispatch(
    mappings=(
        ("qkv_proj", "q_proj", "q"),
        ("qkv_proj", "k_proj", "k"),
        ("qkv_proj", "v_proj", "v"),
    )
)

STANDARD_GATE_UP_MAPPING = StackedParamsDispatch(
    mappings=(
        ("gate_up_proj", "gate_proj", 0),
        ("gate_up_proj", "up_proj", 1),
    )
)
```

注意：`StackedParamsDispatch` 自己不做量化；注释明确说 quantization 由 layer 上的 `param.weight_loader` 处理。它只负责“把哪个 tensor 交给哪个融合参数、带哪个 shard id”。[`python/sglang/srt/model_loader/auto_loader.py:62-148`]

### 11.2 PP 过滤：每个 pipeline stage 只加载自己的层

证据状态：已确认。

`filter_pp_weights` 会丢弃不属于当前 PP layer range 的 checkpoint entry：

```python
def filter_pp_weights(
    weights: Iterable[tuple[str, torch.Tensor]],
    start_layer: int,
    end_layer: int,
) -> Iterable[tuple[str, torch.Tensor]]:
    for name, tensor in weights:
        layer_id = get_layer_id(name)
        if layer_id is not None and (layer_id < start_layer or layer_id >= end_layer):
            continue
        yield name, tensor
```

如果权重名没有可解析 layer id，例如 embedding、lm_head、final norm 等，会继续传递。具体模型是否保留这些非层权重还要看模型自身 `load_weights` 或 PP stage 逻辑。[`python/sglang/srt/model_loader/auto_loader.py:156-170`]

PP layer range 通常来自 `get_pp_indices`：

```python
base_layers = num_hidden_layers // pp_size
remainder = num_hidden_layers % pp_size
if pp_rank >= pp_size - remainder:
    partitions_without_extra_layer = pp_size - remainder
    start_layer = pp_rank * (base_layers + 1) - partitions_without_extra_layer
    end_layer = start_layer + (base_layers + 1)
else:
    start_layer = pp_rank * base_layers
    end_layer = start_layer + base_layers
```

也可以通过 `SGLANG_PP_LAYER_PARTITION` 指定自定义层数列表，但列表长度必须等于 PP size，总和必须等于 hidden layer 数。[`python/sglang/srt/distributed/utils.py:95-135`]

## 13. 4 GPU 小例子：TP=2、PP=2 时某个 rank 发生什么

假设：

```text
GPU: g0, g1, g2, g3
TP size = 2
PP size = 2
world_size = 4
rank = tp_size * pp_rank + tp_rank
```

那么基础 rank 是：

| pp_rank | tp_rank | global rank | 直观角色 |
|---|---:|---:|---|
| 0 | 0 | 0 | stage 0 的 TP 分片 0 |
| 0 | 1 | 1 | stage 0 的 TP 分片 1 |
| 1 | 0 | 2 | stage 1 的 TP 分片 0 |
| 1 | 1 | 3 | stage 1 的 TP 分片 1 |

TP group：

```text
[0, 1]：PP stage 0 内，同一层参数横向切分
[2, 3]：PP stage 1 内，同一层参数横向切分
```

PP group：

```text
[0, 2]：TP shard 0 的 pipeline 前后 stage
[1, 3]：TP shard 1 的 pipeline 前后 stage
```

如果模型有 32 层，默认 `get_pp_indices(32, pp_rank, 2)` 会得到：

```text
pp_rank=0: [0, 16)
pp_rank=1: [16, 32)
```

启动时 rank 2（`pp_rank=1,tp_rank=0`）的主线可以这样理解：

1. `Engine._launch_scheduler_processes` 给它传入 `gpu_id`、`tp_rank=0`、`pp_rank=1`。
2. `run_scheduler_process` 在子进程中 `publish(role="scheduler")`。
3. `Scheduler.__init__` 构造 `ParallelState`，记录它是 TP 0、PP 1。
4. `ModelRunner.__init__` 绑定本地 GPU，并在 WORLD 中使用 global rank 2。
5. `initialize_model_parallel` 让它加入 TP group `[2,3]` 和 PP group `[0,2]`。
6. `_initialize_model` 实例化完整模型类，但具体 layer range 会让当前 stage 只拥有/加载自己负责的层。
7. `filter_pp_weights` 会丢弃 layer id 不在 `[16,32)` 的 checkpoint entries。
8. 对于保留的 tensor，TP 分片由参数 `weight_loader` 或专用 loader 决定；rank 2 和 rank 3 属于同一 TP group，分别持有对应 shard。
9. 加载后 `dist_barrier_after_load` 等待 TP group 内其他 rank 完成，避免某个 rank OOM 而其他 rank 继续进入 ready。
10. Scheduler 创建 KV cache、attention backend、CUDA Graph，最后通过 pipe 报告 ready。
11. 请求执行时，rank 2 不是重新加载模型，而是接收 pipeline 上游的 proxy tensors/hidden states，执行自己 stage 的后半层，再把结果交给下游或 last rank 输出 logits。该请求执行细节可回看 `source-doc/02-request-flow/04-模型执行与输出.md`。

## 14. 常见调试断点

| 问题 | 建议断点/日志位置 | 关注字段 |
|---|---|---|
| 子进程没 ready | `run_scheduler_process` 构造 `Scheduler` 前后 | `gpu_id`、`tp_rank`、`pp_rank`、异常 traceback |
| rank/GPU 对不上 | `Engine._launch_scheduler_processes` 的 `gpu_id` 计算 | `base_gpu_id`、`gpu_id_step`、`pp_size_per_node`、`tp_size_per_node` |
| distributed 卡住 | `init_torch_distributed` / `init_distributed_environment` | `dist_init_method`、`world_size`、`rank`、backend、timeout |
| TP/PP group 错误 | `initialize_model_parallel` | TP size、PP size、DCP size、rank list |
| 找不到权重文件 | `DefaultModelLoader._prepare_weights` | `model_name_or_path`、`allow_patterns`、`revision`、`download_dir` |
| 某 rank 加载后卡住 | `dist_barrier_after_load` | 其他 TP rank 是否 OOM/慢加载 |
| PP 层缺失 | `get_pp_indices` / `filter_pp_weights` | `start_layer`、`end_layer`、checkpoint layer id |
| 融合参数加载错位 | `StackedParamsDispatch.try_load` / 参数 `weight_loader` | `source_name`、`fused_name`、`shard_id` |
| graph capture 失败 | `init_cuda_graphs` | KV pool 大小、batch size、backend、startup overlap 状态 |

## 16. 本文结论清单

| 结论 | 状态 | 证据 |
|---|---|---|
| 普通非 DP-controller 模式下，Engine 为每个本节点 PP/TP rank 组合启动 scheduler worker | 已确认 | [`python/sglang/srt/entrypoints/engine.py:867-918`] |
| DP controller 模式有额外 controller 进程，不等同于普通 worker fan-out | 已确认 | [`python/sglang/srt/entrypoints/engine.py:862-945`] |
| scheduler 子进程必须先 `publish(role="scheduler")` 再构造依赖 runtime config 的对象 | 已确认 | [`python/sglang/srt/managers/scheduler.py:5744-5763`] |
| `ModelRunner` 设置设备后初始化 distributed，再加载模型 | 已确认 | [`python/sglang/srt/model_executor/model_runner.py:414-467`] |
| WORLD rank 基础公式是 `tp_size * pp_rank + tp_rank`，elastic EP scale join 可加入 offset | 已确认 | [`python/sglang/srt/distributed/bootstrap.py:70-172`] |
| TP group 和 PP group 的 rank 排列不同 | 已确认 | [`python/sglang/srt/distributed/parallel_state.py:2298-2409`] |
| 默认 loader 先实例化模型类，再调用模型 `load_weights` 和量化 postprocess | 已确认 | [`python/sglang/srt/model_loader/loader.py:274-336`] |
| `StackedParamsDispatch` 只做融合参数名称和 shard id 路由，不做量化 | 已确认 | [`python/sglang/srt/model_loader/auto_loader.py:62-148`] |
| `filter_pp_weights` 按 layer id 过滤 pipeline stage 权重 | 已确认 | [`python/sglang/srt/model_loader/auto_loader.py:156-170`] |
| startup-overlap 下 `load_model()` 返回时不能直接声称真实权重已提交 | 已确认 | [`python/sglang/srt/model_executor/model_runner.py:1281-1303`] |
| 所有 rank 必须以兼容顺序创建 distributed groups | 推断 | 基于 PyTorch distributed 约束和统一 group-rank 生成；需继续展开 `init_model_parallel_group` |
| `ModelConfig.from_server_args` 的全部 HF config 解析细节 | 未知 | 需要后续补 `model_config.py` 专题 |
