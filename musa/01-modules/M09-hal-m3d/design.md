# HAL/M3D 适配：设计分析

## 设计问题

该模块把 `HAL interface -> M3D device/queue/memory/cmd buffer` 拆成稳定边界：入口负责契约，核心负责状态，底层负责资源或平台副作用。这样做减少了公共 ABI 对硬件实现的直接依赖，但也形成多层错误传播和生命周期耦合。

## 设计取舍

| 取舍 | 好处 | 代价 | 证据状态 |
|---|---|---|---|
| 分层而非 API 直达硬件 | 可替换 HAL、集中管理对象 | 调用链长、排查成本高 | 已确认/推断 |
| 延迟初始化或懒创建 | 降低启动开销、按需创建 | 首次调用承担失败和锁开销 | 已确认于相关模块 |
| 兼容 wrapper | 保持 v1/v2 和旧调用方 | 符号数量多、容易漏导出 | 已确认 |
| 共享状态 + 锁 | 支持多线程/跨 stream | 锁序和死锁风险 | 部分确认 |

## 不变量

1. 公共句柄在使用前必须能映射到有效对象。
2. Core 资源登记成功前，底层初始化失败不得暴露半初始化对象。
3. 异步操作的资源必须活到对应 Command 完成。
4. 销毁路径必须先处理未完成工作，再释放 HAL 对象。

以上第 1、2、4 项由多处校验/析构路径支持；第 3 项是异步资源管理的实现约束，完整证明仍需覆盖所有 Command。
